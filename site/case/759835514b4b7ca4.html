판정 근거

CCTV 앞 팔 동작(D7·D9)을 COCO-17 관절 추출→자체 학습 분류기로 판정해 관제요원에게 후보만 띄우는 현장 감지 PoC이므로 B5, 제어 흐름은 관절 추출→분류→기권(abstention) 순차 파이프라인(B′1). 합성 골격 데이터 1,088건으로 학습(A1)한 비LLM 자체 모델(A2.5)을 개인이 직접 제작(A7). 사람 확정 흐름과 50장 홀드아웃 평가는 구현·기록되었으나 실제 CCTV 실증이 없어 R3에 따라 C1·C9는 implemented. 화면에 골격 오버레이·예측·기권 사유를 보여 주므로 F9, 한계를 명시 고지하므로 F7. 스피커·통보 등 액추에이션(A11)과 C7·C4·C2는 없음. Windows 로컬 실행·정지사진 단건이라 로컬 완결, 인물 영상이라 S(민감). GitHub README 확인.

구현 가이드

주 패턴 B5 현장 감지·경보을 구현할 때

구현 단계

  1. 감시 대상 사건과 등급(위험·경고·잠재위험 등), 등급별 대응 주체를 먼저 정한다.
  2. 기존 CCTV·센서를 우선 재사용하고, 탐지 위치(A5 엣지 또는 현장 폐쇄망 서버)를 E1에 맞춰 정한다.
  3. 탐지 모델과 판정 규칙을 분리해 기준이 바뀌면 재학습 없이 설정만 바꾸게 한다(B′9).
  4. 등급별 자동 대응·관제 이관을 C2로, 물리 출력은 A11a로 연결하고 경보 발송 상한(S1)을 둔다.
  5. C7 Fail-safe를 설계하고, 오탐 판별을 C4에 원장으로 남겨 C6 재학습으로 되돌린다.

점검표

  • 탐지 모델과 판정 규칙이 분리되어 있는가
  • 장애 시 Fail-safe 경로가 있는가(C7)
  • 모든 경보와 조치가 기록되는가(C4)
  • 오탐 판별이 재학습으로 이어지는가(C6)

환경 조건

E1 로컬·폐쇄망 + E2 비LLM 비전 모델이 전형. 유형 ③ 필수는 'A5 또는 A2.2 또는 A2.5'(R10)이며 A11a는 물리 액추에이션이 있을 때만 필수다. 물리 설비 구동은 E4 P2a, 자동 대응은 P2다. 적대적 위협은 스푸핑·경보 채널 남용이며 S1 경보 발송 상한과 S10이 필요하다(§7.4).

주의할 점

  • 오탐에 따른 경보 피로
  • 상시 가동 부담과 Fail-safe 필수
  • 물리 출력은 오작동이 곧 현장 결과(P2a)
  • 스푸핑·오탐 유도 위협

  • C7 폴백 스위치 모델·API·도구가 멈추거나 품질이 떨어질 때 대체 모델·규칙 기반 축소·수동 처리로 경로를 바꿔 서비스가 끊기지 않게 한다.
  • C4 감사 로그·지표 처리 건마다 흔적을 적재하고 수정률·처리시간·자동처리율·가용성을 집계해, '지난달 수정률'을 숫자로 말할 수 있게 한다.
  • C2 위험도 라우터 건별 위험도·신뢰도를 매겨 저위험은 자동 처리, 중간은 검토 큐, 고위험은 숙련자에게 보내 사람의 검토를 필요한 곳에 집중시킨다.

피해야 할 안티패턴

  • X2 설계도만 있는 운영 위험도 분기·롤백·재학습 같은 운영 부품이 '예정'·'설계됨'으로만 등장하고 실증 기간에 한 번도 실행되지 않은 채 운영 체계를 갖췄다고 보고하는 함정이다. 대처: 모든 운영 부품을 R3의 3단계(present·implemented·planned)로 정직하게 기록하고, 가장 중요한 부품부터 실증 기간 안에 완결된 실행 사이클을 한 번 이상 돌린다(R12). 먼저 C4 감사 로그·지표를 켜서 기록처를 만들고, C2는 실제 분기 비율을 실측하고, C3는 롤백·재처리를 한 건 이상 실행하고, C6는 재학습·기준 개정을 한 번 돌리고, C7은 장애 주입으로 전환을 한 번 실행한다. 실행하지 못한 부품은 planned로 내리고 transition.stage를 '미착수'나 '구현·미배포'로 적어 설계와 운영을 구분한다.
  • X5 성능표만 있는 학습 학습 모델의 정확도는 보고하지만 배포 후 수정률을 누가 집계해 무엇을 바꾸는지가 없어, 개선이 배포 시점에 멈추는 함정이다. 대처: 배포 후 사람이 고친 기록을 C4 감사 로그·지표로 모아 수정률·오탐·이의를 숫자로 말하게 한다. C1 검토 큐의 수정 내역을 C4·C6의 입력으로 연결하고, C6 환류 파이프라인에 재학습·기준 개정의 주기와 트리거(예: 수정률 임계)를 정한다. 재학습한 모델은 C9 평가 세트로 재검증한 뒤 교체한다. 판정 질문은 '지난 분기 지표 때문에 바뀐 규칙이 하나라도 있는가'다.

B′1 순차 파이프라인 제어 흐름

한 단계의 출력을 다음 단계의 입력으로 넘기는 고정 순서 배선이다. 한 프롬프트에 많은 일을 몰아 시켜 품질이 떨어지는 문제를 막는다.

PAX 사례 109건이 이 부품을 쓴다

맥락

B4 인식 파이프라인의 기본 배선이며, B1·B0·B5 안에서도 흔하다. 단계 순서가 업무 절차로 미리 정해져 있고 AI가 순서를 고를 필요가 없을 때 쓴다.

맞서는 힘(긴장)

  • 디버깅·출처 추적의 쉬움 vs 병렬화 불가로 인한 지연
  • 단계 분리의 품질 이점 vs 단계가 늘수록 오류 누적
  • 고정 순서의 예측 가능성 vs 예외 경로 처리의 경직성

해법

업무 절차를 단계로 나누고 각 단계의 입력·출력 형식을 정해 앞 단계 출력을 다음 단계에 넘긴다. 단계 사이에 형식 검증(스키마)을 두어 오류가 번지기 전에 멈추고, 멈춘 건은 C1 검토 큐나 C3 재처리로 보낸다. 판정·산수 단계는 가능한 한 규칙(B′9)으로 두고 모델은 추출·서술 단계만 맡긴다. 단계 순서를 AI가 바꿔야 한다면 B′8이나 B′7로 옮긴다.

이럴 때 쓴다

  • 업무 절차가 고정 순서로 정해져 있을 때
  • 각 단계를 따로 검증·추적해야 할 때(유형 ② 접수·심사, ⑧ 취합·변환)
  • 단일 에이전트에서 시작하는 첫 배선일 때

이럴 때는 쓰지 않는다

  • 하위 작업이 서로 독립이라 동시에 돌려야 지연이 줄 때(B′3)
  • 입력에 따라 AI가 다음 도구를 골라야 할 때(B′7)
  • 긴 업무를 계획부터 세워야 할 때(B′8)

얻는 것

  • 디버깅과 출처 추적이 쉬움
  • 단계별 품질 검증 가능
  • 구현이 가장 단순

점검표

  • 단계마다 입력·출력 형식이 정의되어 있는가
  • 단계 사이 검증에서 실패하면 멈추는가
  • 단계별 중간 결과를 추적할 수 있는가

A1 데이터 자산 서비스 공통 서비스

흩어진 업무 기록을 정제·라벨링해 AI 부품이 붙여 쓸 수 있는 데이터셋·라벨·데이터 사전 형태의 기준선으로 제공한다.

PAX 사례 110건이 이 부품을 쓴다

맥락

학습 모델(A2.5·B2), 지식 접지(B3)의 코퍼스, 평가 세트(C9)의 정답 출처가 필요한 과제라면 모두 이 부품을 쓴다. 서비스 유형 5a·9·10·11에서는 필수 기반이다. 비LLM 규칙 기반 대민 안내에서는 A2를 거치지 않고 결정론 조회의 대상이 된다(R21).

맞서는 힘(긴장)

  • 정제 품질 vs 구축 기간·라벨링 인력 비용
  • 과제 전용 가공(빠름) vs 기관 공통 기준선(재사용)
  • 데이터 활용 범위 vs 데이터 등급(E5) 보호
  • 기준선 고정(재현성) vs 원천 갱신 반영

해법

원천 기록을 수집→정제(중복·결측 처리)→라벨링→정의 문서화 순으로 가공하고, 결과를 정제 데이터셋·라벨·데이터 사전의 세 산출물로 고정해 제공한다. 'N건→M건 정제'처럼 정제 전후 규모와 기준을 기록하고, 변수·테이블·인터페이스 정의서로 소비 부품이 같은 정의를 쓰게 한다. 기준선은 버전으로 관리해 C9 평가 세트의 정답 출처와 C6 재학습의 입력으로 재사용한다. 데이터 경계는 부품별로 두고(DB per Service), 타 기관 데이터와의 결합은 A4로 분리한다.

이럴 때 쓴다

  • 예측·추천기(B2)나 비전 모델(A2.5)을 학습·재학습할 때
  • 지식 접지(B3)의 코퍼스를 구축할 때
  • 평가 세트(C9)의 정답 출처가 필요할 때
  • 서비스 유형 5a-agg·9·10·11처럼 A1이 필수인 조립

이럴 때는 쓰지 않는다

  • 공공 API 응답을 가공 없이 조회만 할 때(A3)
  • 정제·정의 없이 파일을 올려 바로 검색하는 경우(태그 대상 아님)
  • 타 기관 데이터 결합이 핵심일 때는 A4를 함께 태그해 계약·키 매핑을 따로 드러낸다

얻는 것

  • 모델 교체와 무관하게 남는 기관 자산
  • C9·C6·B3가 같은 기준선을 재사용
  • 데이터 사전이 기관 간 표준 확산의 단위가 됨

점검표

  • 정제 전후 규모와 정제 기준이 기록되어 있는가
  • 데이터 사전(정의·단위·출처)이 있는가
  • 기준선에 버전이 있고 평가용 분할이 학습용과 분리되어 있는가
  • 데이터 등급(E5)에 맞는 가명·비식별 처리가 적용되었는가

구조 — 참여 부품

  • 원천 시스템·기록 — 가공 전 업무 기록을 내주는 출처
  • 정제·라벨링 파이프라인 — 중복 제거·결측 처리·라벨 부여·품질관리를 수행
  • 데이터 사전 — 정의·단위·출처를 문서로 고정해 소비 부품이 같은 뜻으로 쓰게 함
  • C9 평가 세트·회귀시험 — 기준선을 정답 출처로 사용
  • A2.5 비LLM 학습 모델 — 기준선으로 학습·재학습하는 소비 부품

변형

  • 학습데이터 구축형: 영상·이미지 등을 수집해 품질관리 단계(중복 제거·재라벨링·학습/검증/평가 분리)를 거쳐 학습 기준선으로 만든다.

A2.5 모델 서빙 · 비LLM 학습 모델 공통 서비스

XGBoost·LightGBM·YOLO·U-Net처럼 기관이 직접 학습한 비LLM 예측·비전 모델을 서빙하고 재학습·버전 롤백이 붙을 자리를 제공한다.

PAX 사례 15건이 이 부품을 쓴다

맥락

B2 예측·추천기, B5 현장 감지·경보, B4 비전 판독의 추론 엔진이 된다. 서비스 유형 5a·10에서는 필수이고(R7, R10 'A2.5 또는 결정론 점수 엔진'), 유형 3에서는 A5·A2.2와 함께 셋 중 하나를 고른다. 학습 기준선(A1)이 먼저 있어야 한다.

맞서는 힘(긴장)

  • 모델 성능 vs 설명 가능성(F9)
  • 배포 후 데이터 드리프트 vs 재학습 비용
  • 모델 교체 속도 vs 이전 안정판으로의 복귀 보장

해법

학습한 모델을 서빙 계층에 버전과 함께 올려 업무 부품이 점수·등급·탐지 결과만 받게 한다. 서빙 계층은 모델 버전과 드리프트 지표를 함께 내보내 C4에 기록하고, 재학습 파이프라인(C6)이 새 버전을 올리는 자리와 이전 안정판으로 되돌리는 자리(모델 버전 롤백, C7 변형)를 둔다. 재학습 버전은 C9 독립 시험세트에서 이전 버전을 넘을 때만 배포한다. 판정 근거는 F9로 이용자에게 보인다.

이럴 때 쓴다

  • 기관이 자체 데이터로 비LLM 모델을 학습해 운영할 때
  • 유형 5a-brief가 아닌 분석·위험 예측(유형 10)·현장 감시(유형 3) 조립
  • 재학습과 버전 롤백이 필요한 예측·탐지 서비스

이럴 때는 쓰지 않는다

  • LLM을 튜닝했으면 A2.3
  • 벤더 장비·솔루션에 내장돼 기관이 모델을 못 바꾸면 A2.6
  • 학습 없는 규칙 점수 엔진이면 B0(R10 대안)

얻는 것

  • 비LLM 과제가 A2 계층에 정식 자리를 가짐
  • 재학습·버전 롤백으로 운영 개선
  • C6·C7을 끼울 자리 확보

점검표

  • 모델 버전과 학습 데이터 버전이 짝지어 기록되는가
  • 독립 시험세트가 학습 데이터와 분리되어 있는가
  • 이전 안정판으로 되돌릴 수 있는가
  • 재학습 버전 배포 기준이 수치로 있는가

구조 — 참여 부품

  • A1 데이터 자산 서비스 — 학습·재학습 기준선
  • A2 서빙 계층 — 모델 버전별 노출과 롤백
  • C6 환류 파이프라인 — 재학습 주기·트리거
  • C9 평가 세트 — 재학습 버전 배포 게이트
  • F9 판정 근거·기여도 표시 — SHAP·BBox 등 근거를 이용자에게 표시

변형

A7 자체 제작 환경 공통 서비스

외부 용역 없이 기관 인력이 저작도구·AI 코딩 에이전트로 도구를 직접 만들고 고치는 제작 환경이다.

PAX 사례 317건이 이 부품을 쓴다

맥락

업무 담당자가 AI 코딩 도구·저작도구·오픈소스로 직접 만드는 과제에 쓴다. 유형 8(취합·변환 자동화)에서는 필수 기반이다. PAX 557건에서 A7이 붙고 BYO 모델을 쓰는 사례는 29건이다.

맞서는 힘(긴장)

  • 제작 속도·현장 적합성 vs 유지보수 연속성
  • 개인 역량 의존 vs 조직 인수인계
  • 무예산 제작 vs 보안 검토·기관 공식화 절차

해법

기관 인력이 AI 코딩 에이전트·저작도구·오픈소스로 직접 만들되, 처음부터 전이를 전제로 한다. 설정·데이터(연락처·업무분장 등)는 코드 밖 파일로 빼 비개발자도 고치게 하고, 작업 지시서 자체를 코딩 에이전트가 수행할 프롬프트로 설계해 제작 절차를 남긴다. MIT·Apache 등 라이선스를 명시하고 공공 깃랩(A3)이나 혁신24 자료실에 등재해 담당자가 바뀌어도 이어지게 한다. 실사용 건수로 성과를 재 기관 공식으로 올린다.

이럴 때 쓴다

  • 반복 업무를 줄이는 소규모 도구를 빠르게 만들 때
  • 용역 없이 작은 수정을 계속해야 할 때
  • 유형 8 취합·변환 자동화

이럴 때는 쓰지 않는다

  • P2 이상 시스템 쓰기·처분이 걸려 보안 검토·통제 부품이 먼저 필요한데 이를 갖출 수 없을 때
  • 라이선스·저장소·인수인계를 정할 수 없어 전이가 불가능할 때(X9 위험)

얻는 것

  • 제작 속도와 현장 적합성
  • 내부 유지보수 역량 축적
  • 무예산·소예산 제작

점검표

  • 라이선스가 명시되어 있는가
  • 저장소가 개인 PC가 아닌 공유 위치에 있는가
  • 담당자가 바뀌어도 고칠 수 있는 문서·설정 분리가 있는가
  • 실사용 지표가 있는가

구조 — 참여 부품

  • 업무 담당자 — 요구를 알고 직접 만드는 제작자
  • AI 코딩 에이전트·저작도구 — 코드·화면·워크플로 생성
  • A3 공공 깃랩·자료실 — 등재처 — 담당자 이동 후에도 이어지게
  • A9 업무 규범 스킬 — 제작 규범·지시서를 재사용 가능한 형태로

변형

  • 비개발자 바이브코딩: 교육 후 비개발 직원이 AI 코딩으로 웹앱을 만들고 실사용 지표까지 잰다.

C1 검토 큐 운영 컴포넌트

AI 산출물이 다음 단계로 넘어가기 전에 사람이 맞고 틀림을 확인·수정·확정하는 대기열을 두어, 오류가 업무 결과로 흘러가지 않게 한다.

PAX 사례 46건이 이 부품을 쓴다

맥락

AI 산출물이 공문·처분·대민 안내·기록으로 이어지는 모든 B 부품(B1 코파일럿, B4 인식 파이프라인, B2 예측기, B7 콘텐츠 생성기 등). 이용자 본인이 최종 확정자인 자기서비스형 도구도 포함한다(R16).

맞서는 힘(긴장)

  • 정확성·책임성 vs 처리 속도(전건 검토는 자동화 이득을 깎는다)
  • 검토자의 숙련 vs 자동화 편향(AI 결과를 그대로 승인하는 경향)
  • 전건 검토의 안전 vs 위험도별 분기(C2)로 가야 하는 효율 압력

해법

AI 산출물에 신뢰도·근거를 붙여 검토 대기열에 올리고, 검토자가 승인·수정·반려 중 하나를 고르게 한다. 수정·반려 내역은 C4 감사 로그에 남겨 수정률을 집계하고 C6 환류의 입력으로 쓴다. 검토 화면은 원문 위치·근거를 함께 보여 줘 확인 비용을 줄인다. 전건 검토로 시작하되, 수정률 실측이 쌓이면 C2 위험도 라우터로 저위험 건을 자동 종결하는 단계로 옮긴다.

이럴 때 쓴다

  • AI 산출물이 공문·처분·대민 안내로 그대로 이어질 때
  • E4가 P1 이상이고 되돌리는 데 사람 시간이 많이 드는 조치가 있을 때
  • 서비스 유형 ② 접수·심사, ④ 기안 코파일럿, ⑥ 콘텐츠 제작, ⑦ 대조·점검, ⑩ 위험 예측, ⑪ 추천·매칭, ⑫ 개발 코파일럿처럼 C1이 필수인 유형

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 런타임 AI 산출물이 없을 때
  • 쉽게 되돌릴 수 있고 저위험인 조치를 이미 C2로 자동 종결하도록 실측 근거를 갖춘 구간(전건 검토를 영원히 남기지 않는다)

얻는 것

  • 오류가 업무 결과로 나가기 전에 차단
  • 책임 소재가 명확해짐
  • 수정 내역이 C4 지표와 C6 환류의 원천 데이터가 됨

점검표

  • AI 산출물이 확정 전 상태로 머무는 지점이 명시되어 있는가
  • 검토자와 승인·수정·반려 선택지가 정해져 있는가
  • 검토 결정과 수정 내역이 로그로 남는가

B2 예측·추천기, B4 인식 파이프라인, B5 감지·경보. 유형 ③ 현장 감시, 5a 분석, ⑩ 위험 예측, ⑪ 추천·매칭(추천 사유). v0.6에서 추가.

맞서는 힘(긴장)

  • 설명의 충실성 vs 이해 가능성
  • 근거 공개 vs 적대적 이용자에게 탐지 기준 노출(X16)

해법

판정마다 기여 요인(SHAP)·의심 부위(BBox)·사유 코드·자연어 근거를 결과와 함께 보인다. 담당자가 근거를 열어 확인하고 최종 판단하게 한다. 위조 탐지처럼 적대적 이용자가 있는 D3 접점에서는 이용자에게 '정상/위조의심'만 보이고 세부 근거는 관리자 화면에만 둔다(근거 은닉).

이럴 때 쓴다

  • B2·B4·B5의 판정 결과를 사람이 검토할 때
  • 유형 ③⑤a⑩⑪처럼 F9가 필수인 유형

이럴 때는 쓰지 않는다

  • 위조 탐지 등 적대적 이용자에게 근거를 그대로 보이는 경우(X16 — 관리자 전용으로)
  • 문서 출처만 보이면 되는 지식 접지 응답(F1)

얻는 것

  • 담당자가 판정을 검토할 근거
  • 오판 원인 파악
  • 추천·선별 결과의 설명 책임

점검표

  • 판정마다 근거가 보이는가
  • 적대적 접점에서 근거가 관리자에게만 노출되는가
  • 최종 판단 주체가 명시되는가

구조 — 참여 부품

  • A2.5 비LLM 학습 모델 서빙 — 판정과 기여도 산출
  • 근거 표시 화면 — 요인·BBox·사유 코드 제시
  • 담당자 — 근거를 보고 최종 판단

변형

  • 요인 기여도: SHAP 등 요인 문장
  • 위치 표시: 의심 부위 BBox
  • 사유 코드·자연어 근거: 판정 사유 코드와 판독 이유 문장
  • 관리자 전용 근거(근거 은닉): 적대적 접점에서 세부 근거를 관리자에게만 노출

참조 구현 예

  • PAX 3b195a5faf820769 — 정비 대상 판정의 근거를 따로 열어 확인하게 하고 오류 가능성을 화면에 명시한 F9+F7 표준형

D6 점검·감시 서비스 블록

시설·환경·안전을 상시 또는 주기적으로 점검하는 현장 접점 블록이다. Levine 목록에 없어 추가했고 B5·B2가 이 자리에 들어간다.

PAX 사례 5건이 이 부품을 쓴다

맥락

CCTV·센서·드론·위성 영상 등 관측 스트림으로 현장을 점검하는 접점. §7.3 유형 ③ 현장 감시·경보(D6·D5, P1~P2a)와 유형 ⑩ 위험 예측·표적 선별(D6·D3·D8.4)의 무대다.

맞서는 힘(긴장)

  • 점검 빈도·범위 vs 오탐으로 인한 출동 비용
  • 현장 폐쇄망·엣지 제약 vs 모델 성능
  • 자동 대응 vs 사람 확인
  • 센서 스푸핑·오탐 유도 위협 vs 상시 운영

해법

관측 스트림을 A5 엣지 런타임이나 현장 폐쇄망 서버 추론(A2.2·A2.5)에서 B5 감지·경보로 판독한다. 판독 결과는 B′9 판정 게이트로 규칙이 등급을 정하고, C2가 등급별로 자동 대응과 관제 이관을 가른다. 사람 확인이 필요한 건은 C1 검토 큐로 보내고(v0.6 유형 ③ 필수 추가), 판정 근거는 F9(BBox·사유 코드)로 보여 준다. 점검 대상 선별형은 B2 위험 예측 모델이 순서를 정한다. 상시 서비스라 C7 Fail-safe, C4 운영 지표, C6 오탐 환류를 함께 둔다.

이럴 때 쓴다

  • 사람 순회로는 빈도·범위를 채울 수 없는 시설·환경·안전 점검
  • 기존 CCTV·센서를 재사용할 수 있을 때
  • 점검 대상이 많아 우선순위를 정해야 할 때

이럴 때는 쓰지 않는다

  • 국민 신청 건의 요건 판정이면 D3
  • 문서·규정 대조로 확인 대상을 고르면 D8.4
  • 관측이 없고 경보 전달만 하면 D5

얻는 것

  • 점검 빈도·범위 확대
  • 기존 현장 장비 재사용
  • 사고 전 이상 발견

점검표

  • 탐지 결과에 사람 확인 단계가 있는가
  • 오탐·미탐이 기록되어 재학습·임계 조정에 쓰이는가
  • 모델 장애 시 규칙 기반 점검으로 전환되는가
  • 현장 망 조건에 맞는 추론 위치가 정해져 있는가

구조 — 참여 부품

  • A5 엣지 추론 런타임 — 현장 기기에서 판독
  • B5 감지·경보 — 관측 스트림에서 이상을 탐지
  • B2 예측·판정 모델 — 점검 대상 선별·위험 예측
  • B′9 결정론 판정 게이트 — 판독 결과를 규칙이 등급화
  • C2 위험도 라우터 — 등급별 자동 대응 / 관제 이관
  • 현장 요원·관제 담당자 — 경보를 확인하고 조치

변형

  • 상시 스트림형: CCTV·센서를 상시 판독(B5, R5).
  • 주기 점검형: 항공·위성 영상 등 주기 관측을 비교해 변화·미등록 시설을 찾음.
  • 탐지→VLM 2단 검증형: 경량 탐지 모델 후 VLM이 재확인(R5).
  • 이동체형: 드론·로봇이 순회하며 관측(R5).
  • 표적 선별형: B2가 점검 대상 우선순위를 정함(유형 ⑩).

관련 부품

A11 액추에이션·현장 통지 어댑터 공통 서비스

AI 판정을 화면이 아니라 스피커·경광등·VMS·PTZ·모바일 푸시·알림톡으로 내보내고, 재알림·에스컬레이션과 처리 상태 종결까지 추적한다.

PAX 사례 6건이 이 부품을 쓴다

맥락

B5 현장 감지·경보나 대민 알림·통지(D5)가 있는 과제에 쓴다. 유형 3에서 물리 액추에이션이 있으면 A11a가 필수다(R10·R14). PAX 557건에서 A11이 붙은 사례는 6건이다.

맞서는 힘(긴장)

  • 즉시 출력(대응 시간 단축) vs 오탐 시 물리·사회적 피해
  • 자동 구동 vs 사람 개입 가능성(킬스위치)
  • 알림 도달 보장(재알림) vs 알림 피로

해법

판정 이벤트·등급을 받아 등급별 출력 채널(물리 설비 또는 통지 채널)로 내보내는 어댑터를 둔다. 미처리 이벤트는 정해진 간격(예: 300초)으로 재알림하고 에스컬레이션하며, 처리 상태 코드로 종결까지 추적해 C4에 남긴다. 물리 설비를 구동하는 A11a는 E4를 P2a로 두고 C8 킬스위치와 C7 안전 상태 전환을 반드시 함께 단다. 통지 채널인 A11b는 일반 P1~P2 규칙을 따르되, 대민 알림톡·아웃바운드 발신은 P2로 본다(R8).

이럴 때 쓴다

  • 감지 결과를 현장 설비로 즉시 출력해야 할 때(A11a)
  • 이동 중인 담당자·시민에게 통지하고 처리 종결을 추적해야 할 때(A11b)
  • 유형 3에서 물리 액추에이션이 있을 때(필수)

이럴 때는 쓰지 않는다

  • 판정을 사람이 먼저 검토하고 나서 조치하는 구조(C1 검토 큐가 주)
  • 대시보드 화면 표시만 있을 때
  • 킬스위치·안전 상태를 둘 수 없는데 물리 설비를 자동 구동하려 할 때

얻는 것

  • 대응 시간 단축
  • 현장·이동 담당자에게 도달
  • 처리 종결 추적

점검표

  • 물리 구동을 즉시 멈추는 스위치가 있는가
  • 장애 시 안전 상태가 정의되어 있는가
  • 미처리 이벤트가 재알림·에스컬레이션되는가
  • 이벤트별 처리 상태가 종결까지 추적되는가

구조 — 참여 부품

  • B5 현장 감지·경보 — 판정 이벤트·등급을 발생
  • 출력 어댑터 — 등급별로 설비·채널을 골라 명령·통지를 보냄
  • 재알림·에스컬레이션 정책 — 미처리 이벤트를 주기 재알림하고 상위로 올림
  • C8 권한 경계·킬스위치 — 물리 구동 즉시 중단
  • C4 감사 로그·지표 — 발송·처리 상태·반응 시간 기록

변형

  • 물리 액추에이션: 스피커·경광등·PTZ·전광판·자동 개폐 등 물리 설비를 구동한다. permission_scope는 P2a이고 C8 킬스위치·C7 안전 상태 전환이 필수다(R14).
  • 통지·알림 채널: 이메일·문자·알림톡·푸시로 알리고 재알림한다. permission_scope는 일반 P1~P2 규칙을 따르고, 대민 알림톡·아웃바운드 발신은 P2다(R8·R14).

C7 폴백 스위치 운영 컴포넌트

모델·API·도구가 멈추거나 품질이 떨어질 때 대체 모델·규칙 기반 축소·수동 처리로 경로를 바꿔 서비스가 끊기지 않게 한다.

PAX 사례 12건이 이 부품을 쓴다

맥락

상용 API 또는 단일 모델에 의존하는 모든 B 부품. 특히 E2가 해외 상용 API이거나 B5처럼 상시 가동해야 하는 서비스.

맞서는 힘(긴장)

  • 가용성 vs 비용(대체 경로를 상시 유지하는 비용)
  • 품질 일관성 vs 대체 경로의 품질 저하
  • 자동 전환의 신속성 vs 전환 판단의 오작동 위험

해법

오류율·지연·단가 신호를 감시하다가 임계를 넘으면 재시도 → 기존 API → 대체 MCP → 대체 모델 → 규칙 기반 축소 → 수동 전환 순으로 경로를 바꾼다. 장애 범위는 격리(Bulkhead)로 한 부품에 가두고, 모델 교체는 무중단(Blue-Green)으로 한다. 전환은 C4 감사 로그에 남기고, 복구 후에는 원래 경로로 되돌리는 조건도 함께 정한다. 대체 경로의 품질 저하는 이용자에게 F7 한계 안내로 알린다.

이럴 때 쓴다

  • E2가 해외 상용 API이거나 혼합일 때
  • B5 현장 감지·경보처럼 상시 서비스일 때 필수
  • 대민 자동응답(B3 대민형)처럼 중단 비용이 큰 경우
  • 유형 ① 대민 상담(상시), ③ 현장 감시

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 런타임 AI가 없을 때
  • 로컬 완결 도구로 외부 의존이 없을 때
  • 유형 ①·⑦에서 model_dependency가 없음(비LLM)일 때는 필수에서 면제(R7)

얻는 것

  • 핵심 서비스 연속성
  • 벤더 종속 완화(X4 예방)

점검표

  • 대체 경로가 최소 하나 구현되어 있는가

모든 운영 부품을 R3의 3단계(present·implemented·planned)로 정직하게 기록하고, 가장 중요한 부품부터 실증 기간 안에 완결된 실행 사이클을 한 번 이상 돌린다(R12). 먼저 C4 감사 로그·지표를 켜서 기록처를 만들고, C2는 실제 분기 비율을 실측하고, C3는 롤백·재처리를 한 건 이상 실행하고, C6는 재학습·기준 개정을 한 번 돌리고, C7은 장애 주입으로 전환을 한 번 실행한다. 실행하지 못한 부품은 planned로 내리고 transition.stage를 '미착수'나 '구현·미배포'로 적어 설계와 운영을 구분한다.

이럴 때 쓴다

  • C2·C3·C6·C7이 '예정·계획·검토 중·설계됨'으로만 등장한다
  • 운영 부품 서술은 많은데 실증 기간 중 실행 횟수·날짜·결과가 하나도 없다
  • 스크린샷·아키텍처 그림은 있으나 전환·롤백·재학습 로그가 없다
  • AI-Native를 주장하면서 운영 증거가 없다

이럴 때는 쓰지 않는다

  • 부품을 planned로 정직하게 적고 AX 단계도 그에 맞게 낮춰 주장한 경우(계획 서술 자체는 함정이 아니다)
  • 구현이 확인되고 실측만 남은 implemented 부품이 일부 있는 경우
  • 완결된 실행 사이클이 한 번이라도 원문에 서술된 경우

얻는 것

  • 보고서가 완결되어 보이고 상위 AX 단계를 주장하기 쉽다
  • 운영 데이터·담당자 없이도 문서를 채울 수 있다

점검표

  • present로 적은 운영 부품마다 실행 날짜·건수·결과가 있는가
  • '설계됨'·'예정' 서술을 implemented·planned로 낮춰 적었는가
  • C4에 실행 사이클의 로그가 남는가
  • AX 단계 주장이 운영 증거 수준과 맞는가

구조 — 참여 부품

  • C2 위험도 라우터 — 분기 비율 실측이 있어야 present
  • C3 상태 머신·롤백 — 되돌림 경로를 한 번 이상 실행해야 present
  • C6 환류 파이프라인 — 재학습·기준 개정 사이클을 한 번 돌려야 present
  • C4 감사 로그·지표 — 실행 사이클의 증거가 쌓이는 기록처

변형

  • 예정형: '향후 재학습 예정', '롤백 기능 도입 계획'처럼 미래형으로만 서술
  • 설계됨형: '~하도록 설계됨', '지속적으로 개선함'처럼 진행형·의지형 서술. 최대 implemented(R12)
  • 화면만 있는 형: 스크린샷·코드 존재만 있고 실행 기록이 없음. implemented의 증거일 뿐 present가 아님(R12)

X5 성능표만 있는 학습 안티패턴

학습 모델의 정확도는 보고하지만 배포 후 수정률을 누가 집계해 무엇을 바꾸는지가 없어, 개선이 배포 시점에 멈추는 함정이다.

맥락

B2 예측·추천, B4 인식 파이프라인, B5 감지·경보처럼 자체 학습 모델(A2.3·A2.5)을 가진 과제. 사람이 AI 산출물을 고치는 C1이 있는데도 그 수정이 모이지 않는 과제.

맞서는 힘(긴장)

  • 계약 종료 시점의 성능 증명 vs 배포 후 지속 개선
  • 운영 기록 비용 vs 재학습·기준 개정의 근거
  • 과제 성과 지표 vs 현장 수정률

해법

배포 후 사람이 고친 기록을 C4 감사 로그·지표로 모아 수정률·오탐·이의를 숫자로 말하게 한다. C1 검토 큐의 수정 내역을 C4·C6의 입력으로 연결하고, C6 환류 파이프라인에 재학습·기준 개정의 주기와 트리거(예: 수정률 임계)를 정한다. 재학습한 모델은 C9 평가 세트로 재검증한 뒤 교체한다. 판정 질문은 '지난 분기 지표 때문에 바뀐 규칙이 하나라도 있는가'다.

이럴 때 쓴다

  • 정확도·F1 같은 성능 수치는 있으나 배포 후 수정률·오탐률 지표가 없다
  • C1 검토가 있는데 수정 내역을 어디에 저장·집계하는지 서술이 없다
  • 재학습의 주기·트리거·담당 주체가 없다
  • '지속적으로 고도화'만 있고 구체 사이클이 없다

이럴 때는 쓰지 않는다

  • 학습 모델이 없는 B0·규칙 기반 도구
  • C6 환류가 주기·트리거와 함께 한 번 이상 실행된 경우
  • 상용 API만 쓰고 자체 학습이 없어 재학습 대신 C9 재평가·프롬프트 개정으로 환류하는 경우(그 환류가 있으면 정상)

얻는 것

  • 계약 종료 시점에 성능을 명확히 증명한다
  • 운영 기록·재학습 비용이 들지 않는다

점검표

  • 배포 후 수정률을 월 단위로 말할 수 있는가
  • 재학습·기준 개정의 주기·트리거·담당자가 정해져 있는가
  • 재학습 결과가 C9로 재검증되는가
  • 지난 분기 지표 때문에 바뀐 규칙이 하나라도 있는가

구조 — 참여 부품

  • C4 감사 로그·지표 — 수정률·오탐을 집계하는 빠진 부품
  • C6 환류 파이프라인 — 주기·트리거로 재학습·기준 개정
  • C1 검토 큐 — 사람의 수정 내역이 발생하는 곳
  • C9 평가 세트·회귀시험 — 재학습 결과의 재검증

변형

  • 정확도 단발 보고: 테스트 세트 정확도 한 번만 보고하고 배포 후 지표가 없음
  • 수정은 있으나 버려짐: 담당자가 결과를 고치지만 수정 내역이 저장·집계되지 않음
  • 재학습 주체 부재: 재학습 필요성은 쓰지만 누가 언제 하는지가 없음
