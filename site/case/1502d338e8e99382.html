판정 근거

전자문서 화면에서 버튼 하나로 할 일 카드(무엇을·언제까지·어떻게)를 만들고 결재 전 AI 검토까지 해주는 브라우저 확장이다. 한컴 웹한글 캔버스 위에 결과 패널을 덧입히는 구조는 B8 레거시 오버레이이나, 최종 가치는 사람이 확정하는 요약·검토 초안이라 R1에 따라 B1을 주 부품, B8을 secondary로 둔다. 한컴 API 우회 추출→요약→검토의 순차 흐름이 B′1, '잘된 점·보완점·확인사항'을 원문 근거로만 제시하는 결재 전 검토는 생성물에 대한 비평이라 B′5. 한컴 웹한글 API 활용이 A10, 로컬 LLM 기본이 A2.2, Gemini 옵션이 A2.1. '근거 없는 지적을 방지'가 C5, 로컬-Gemini 전환 옵션이 대체 경로라 C7, 둘 다 implemented. 동일 출처 iframe만 분석하고 결과 패널을 closed Shadow DOM으로 격리한 것이 S3, 첨부파일을 브라우저 내에서만 파싱하고 업로드하지 않는 것이 S12다. 원문 근거 표시가 F1, Gemini 선택 시 공공기관 사용 비권장 경고가 F7.

구현 가이드

주 패턴 B1 코파일럿을 구현할 때

구현 단계

  1. 대상 문서의 서식·필수 항목·문체 규범을 정리해 A9 스킬(프롬프트 템플릿)로 만든다.
  2. 업무 질문·모범 답안·채점 기준으로 C9 평가 세트를 먼저 만들어 모델·프롬프트 선택을 잰다.
  3. E1·E5에 맞는 모델 경로를 정한다. 행정망이면 BYO 대신 A2 내부망 프록시, 민감 자료면 C5 비식별을 앞단에 둔다.
  4. 산출물을 F2 편집 가능 출력과 A10 서식으로 내고, C1 검토 큐에서 담당자가 확정하게 한다.
  5. 수정률·처리시간을 C4로 집계하고, 저위험 유형이 확인되면 C2 자동 확정 분기를 검토한다.

점검표

  • 담당자가 최종 확정한다는 절차가 운영되는가
  • 서식·문체 규범이 A9 스킬로 분리되어 있는가
  • 초안을 이용자가 직접 고칠 수 있는가(F2)
  • 수정 내역이 기록되어 품질 개선에 쓰이는가

환경 조건

E1 행정망이면 BYO 코딩 에이전트를 쓸 수 없어 A2 내부망 프록시가 필요하다. E1 로컬 PC 완결이면 A9 스킬 + A10 어댑터 조합이 된다. E2 해외 상용 API면 직접 호출 대신 A2 게이트웨이를 거친다. E2 모델 중립(BYO)이면 A9 스킬 형태로 배포하고 모델 교체 가능성이 곧 C7이다. E4는 P1이 기본이고, P2로 올라가면 C1 전건 검토 → C2 분기로 바꾼다.

주의할 점

  • 전건 검토가 영원히 남으면 업무 순서는 그대로(First 불가)
  • 상용 API 직접 호출 시 X4 위험
  • 행정망에서는 BYO 불가로 A2 내부망 프록시가 선행되어야 함

보완이 필요한 필수 부품

이 조합에서 카탈로그가 함께 갖추라고 권하는 부품 가운데 아직 확인되지 않은 것이다.

  • A9 업무 규범 스킬 보고서 구조·문체·서식·검증 절차 같은 업무 규범을 모델 중립 스킬(지침 + 검증기 + 출력 서식)로 패키징해 어떤 모델·에이전트에서든 재사용한다.
  • C1 검토 큐 AI 산출물이 다음 단계로 넘어가기 전에 사람이 맞고 틀림을 확인·수정·확정하는 대기열을 두어, 오류가 업무 결과로 흘러가지 않게 한다.
  • F2 편집 가능한 출력 생성물을 이용자가 직접 고쳐 확정하게 한다. 통제감의 실체이며, 수정 내역은 C4 지표와 C6 환류의 입력이 된다.

피해야 할 안티패턴

  • X1 AI 스티커 기존 화면에 요약·챗봇 버튼만 붙이고 업무 순서와 사람·AI의 역할 분담은 그대로 두어, AI가 있어도 업무 산출물이 바뀌지 않는 함정이다. 대처: 먼저 가치 흐름 규칙(R1)으로 사람 또는 국민이 최종으로 받는 핵심 산출물을 정하고, 그 산출물을 AI가 어떤 모양으로 분담할지 B 업무 컴포넌트를 하나 고른다(초안→사람 확정이면 B1, 근거 접지 답변이면 B3, 서류 추출이면 B4). 사람이 확정하는 지점은 C1 검토 큐로, 이용자가 고쳐 확정하는 면은 F2 편집 가능한 출력으로 명시한다. 흐름이 바뀌었는지는 C4 감사 로그·지표의 처리시간·수정률로 잰다. AI 런타임이 전혀 없는 행정정보시스템이라면 AI로 포장하지 말고 R24대로 B0·service_type 0·platform 공란·X1(AI 무관)으로 정직하게 분류한다.
  • X4 단일 모델 인질 상용 API 하나에 전 기능이 묶여 있어, 그 API가 멈추거나 바뀌면 무슨 일이 생기는지 아무도 답하지 못하는 함정이다. 대처: 모델 호출을 A2 모델 서빙 계층 뒤로 숨겨 B 부품이 특정 벤더 API를 직접 부르지 않게 한다. 그 위에 C7 폴백 스위치로 재시도 → 기존 API → 대체 MCP → 대체 모델(A2.2 주권형 로컬 등) → 규칙 기반 축소 → 수동 전환의 경로를 정하고 전환 이력을 C4에 남긴다. 모델 교체가 실제로 안전한지는 C9 평가 세트로 재어 버전을 고정한다. 모델 중립(BYO) 배포라면 A9 스킬 형태로 배포해 모델 교체 가능성 자체를 폴백으로 삼는다.
  • X10 평가 없는 RAG, RAG 없는 튜닝 평가 세트 없이 검색을 붙여 '좋아진 것 같다'로 배포하고, 검색으로 풀릴 문제를 파인튜닝으로 푸는, 진행 경로를 건너뛰는 함정이다. 대처: §7.2 진행 경로를 순서대로 밟는다. B1 직접 프롬프트에서 시작해 두 번째 단계에서 C9 평가 세트(업무 질문·정답·채점 기준)를 먼저 만들고, 이후 A9 규범 스킬·F4, B3 지식 접지(A1 데이터 자산), B3 검색 품질(Hybrid·Rewriting·Reranker), C5 가드레일·F1 순으로 붙이며 매 단계를 C9로 잰다. A2.3 튜닝은 진행 경로의 마지막 단계로, 검색·규범 스킬로 풀리지 않는다는 것이 C9 점수로 확인됐을 때만 한다. 모델·프롬프트·설정 조합은 릴리스처럼 버전 관리한다.

B8 레거시 오버레이 업무 컴포넌트

API가 닫힌 표준 업무 시스템(온나라·나이스·K-에듀파인·업무포털) 화면 위에 브라우저 확장·사이드패널로 검색·요약 기능을 덧입힌다. 시스템 자체는 고치지 않는다.

PAX 사례 13건이 이 부품을 쓴다

맥락

행정망의 표준 업무 시스템을 쓰는 담당자가 개인·부서 단위로 만든 도구가 여기에 든다. 문서가 PC 밖으로 나가면 안 되므로 로컬 모델과 짝을 이룬다. PAX 557건에서 13건이 확인됐다.

맞서는 힘(긴장)

  • 즉시 도입 vs 시스템 개편에 따른 취약성(DOM 의존)
  • 사용자 세션 공유의 편의 vs 권한 경계
  • 요약 기능 추가 vs 문서 외부 유출 금지

해법

브라우저 확장·사이드패널이 담당자 로그인 세션 안에서 화면 DOM과 다운로드 파일을 읽어 통합 검색, 일괄 다운로드, 원클릭 이동을 제공한다. 요약·분석이 필요하면 로컬 오픈웨이트 모델(A2.2)로 처리해 문서가 PC 밖으로 나가지 않게 한다. 권한은 P0~P1(읽기·산출물)에 묶고, 쓰기 조작이 있으면 C3 되돌림을 둔다. 화면 텍스트는 모두 신뢰 불가 입력으로 보고 S3·S4를 적용하며, 표준 시스템에 정식 API·MCP(A8)가 열리면 이 부품을 걷어낸다.

이럴 때 쓴다

  • API가 닫힌 표준 시스템 위에서 반복 조회·다운로드가 병목일 때
  • 행정망에서 문서를 PC 밖으로 내보낼 수 없을 때
  • 정식 연계가 열리기 전 과도기 도구가 필요할 때

이럴 때는 쓰지 않는다

  • 표준 시스템에 정식 API·MCP가 이미 있을 때(A8로 연결)
  • 화면 조작으로 시스템에 쓰기를 해야 하는데 되돌림을 보장할 수 없을 때
  • 독립 화면에서 파일을 처리하는 도구일 때(B0)

얻는 것

  • 표준 시스템을 고치지 않고 즉시 도입
  • 행정망에서 로컬 완결 가능
  • 현장 반복 조작 제거

점검표

  • 권한이 읽기·산출물 생성(P0~P1)에 묶여 있는가
  • 문서가 PC 밖으로 나가지 않는가
  • 시스템 개편 시 점검 절차가 있는가
  • 정식 연계가 열리면 걷어낼 조건이 적혀 있는가

  • A10 문서 형식 어댑터 — 첨부 파싱
  • C5 가드레일 필터 — 민감정보 처리

B1 코파일럿 업무 컴포넌트

사람이 하던 문서·판단 작업 옆에 AI가 초안·요약·검토안을 놓고, 사람이 고쳐서 확정한다.

PAX 사례 111건이 이 부품을 쓴다

맥락

문서·기안·검토의견처럼 산출물 형식이 정해져 있고 최종 확정자가 사람인 업무에 쓴다. BYO 코딩 에이전트와 A9 스킬을 쓰는 스킬 코파일럿이 PAX 자생 도구에 많다.

맞서는 힘(긴장)

  • 초안 속도 vs 전건 검토에 드는 사람 시간
  • 상용 모델 품질 vs 행정망·민감정보 제약(E1·E5)
  • 양식 일관성(A9 규범) vs 사안별 유연성

해법

업무 서식과 참고 자료를 입력으로 받아 모델(A2 또는 BYO 구독)이 초안·근거·신뢰도를 내고, 사람이 편집 가능한 형태(F2)로 받아 고쳐서 확정한다. 보고서 구조·문체·검증 절차는 A9 규범 스킬로 코드 밖에 두고, 공공 문서 형식은 A10 어댑터로 입출력한다. 확정 전 검토는 C1 검토 큐로 운영하고 수정 내역을 C4·C6의 입력으로 남긴다. First로 가려면 저위험 건을 C2로 자동 확정하는 분기를 더한다.

이럴 때 쓴다

  • 산출물 형식이 정해진 문서를 반복 작성할 때
  • 최종 판단과 책임이 사람에게 남아야 할 때(P1 산출물 생성)
  • 유형 ④ 내부 문서·기안, 유형 ⑫ 개발 코파일럿의 기본 조립일 때

이럴 때는 쓰지 않는다

  • 답이 기관 규정·선례 속에 있어 접지와 출처가 핵심일 때(B3)
  • 추출 결과가 사람 확정 없이 다음 판정 단계로 흐를 때(B4)
  • 런타임에 모델이 필요 없는 정형 취합일 때(B0)

얻는 것

  • 문서 작성 시간 단축
  • 책임 소재가 사람에게 명확히 남음
  • 도입이 쉬워 Enabled의 전형 경로

점검표

  • 담당자가 최종 확정한다는 절차가 운영되는가
  • 서식·문체 규범이 A9 스킬로 분리되어 있는가
  • 초안을 이용자가 직접 고칠 수 있는가(F2)
  • 수정 내역이 기록되어 품질 개선에 쓰이는가

구조 — 참여 부품

  • A2 모델 서빙 계층 — 초안 생성 모델 호출(행정망이면 내부망 프록시)
  • A9 업무 규범 스킬 — 서식·문체·검증 절차를 프롬프트 템플릿으로 고정
  • A10 문서 형식 어댑터 — HWPX·엑셀 입출력
  • C1 검토 큐 — 담당자가 초안을 확인·수정·확정
  • 담당자 — 최종 확정자이자 책임자

변형

  • 시스템 내장형: 기관 업무 시스템 안에 초안 기능을 넣은 형태

B′1 순차 파이프라인 제어 흐름

한 단계의 출력을 다음 단계의 입력으로 넘기는 고정 순서 배선이다. 한 프롬프트에 많은 일을 몰아 시켜 품질이 떨어지는 문제를 막는다.

PAX 사례 109건이 이 부품을 쓴다

맥락

B4 인식 파이프라인의 기본 배선이며, B1·B0·B5 안에서도 흔하다. 단계 순서가 업무 절차로 미리 정해져 있고 AI가 순서를 고를 필요가 없을 때 쓴다.

맞서는 힘(긴장)

  • 디버깅·출처 추적의 쉬움 vs 병렬화 불가로 인한 지연
  • 단계 분리의 품질 이점 vs 단계가 늘수록 오류 누적
  • 고정 순서의 예측 가능성 vs 예외 경로 처리의 경직성

해법

업무 절차를 단계로 나누고 각 단계의 입력·출력 형식을 정해 앞 단계 출력을 다음 단계에 넘긴다. 단계 사이에 형식 검증(스키마)을 두어 오류가 번지기 전에 멈추고, 멈춘 건은 C1 검토 큐나 C3 재처리로 보낸다. 판정·산수 단계는 가능한 한 규칙(B′9)으로 두고 모델은 추출·서술 단계만 맡긴다. 단계 순서를 AI가 바꿔야 한다면 B′8이나 B′7로 옮긴다.

이럴 때 쓴다

  • 업무 절차가 고정 순서로 정해져 있을 때
  • 각 단계를 따로 검증·추적해야 할 때(유형 ② 접수·심사, ⑧ 취합·변환)
  • 단일 에이전트에서 시작하는 첫 배선일 때

이럴 때는 쓰지 않는다

  • 하위 작업이 서로 독립이라 동시에 돌려야 지연이 줄 때(B′3)
  • 입력에 따라 AI가 다음 도구를 골라야 할 때(B′7)
  • 긴 업무를 계획부터 세워야 할 때(B′8)

얻는 것

  • 디버깅과 출처 추적이 쉬움
  • 단계별 품질 검증 가능
  • 구현이 가장 단순

점검표

  • 단계마다 입력·출력 형식이 정의되어 있는가
  • 단계 사이 검증에서 실패하면 멈추는가
  • 단계별 중간 결과를 추적할 수 있는가

구조 — 참여 부품

  • 단계 처리기 — 각 단계에서 추출·변환·작성 수행
  • 단계 간 형식 검증 — 다음 단계로 넘기기 전 스키마 확인
  • C3 상태 머신·롤백 — 실패 단계 재처리

관련 부품

B′5 생성자-비평가 제어 흐름

생성과 검증을 분리해, 비평이 통과시킬 때까지 생성물을 고쳐 다시 만드는 배선이다. 반복 상한이 없으면 비용이 폭주한다.

PAX 사례 11건이 이 부품을 쓴다

맥락

B1 코파일럿(유형 ④ 내부 문서·기안, ⑫ 개발 코파일럿)과 B4 접수·심사, 유형 ⑦ 대조·점검의 기본 배선이다. C5 Model Critic도 이 원형에서 나왔다.

맞서는 힘(긴장)

  • 품질 향상 vs 호출 비용·지연
  • LLM 비평의 유연성 vs 비결정성(규칙 검사로 보강 필요)
  • 반복 수정의 개선 효과 vs 수렴하지 않는 루프

해법

생성자가 초안을 만들면 비평자(다른 프롬프트·모델 또는 규칙 검사)가 기준에 따라 통과·불통과와 수정 사유를 내고, 불통과면 사유를 붙여 다시 생성한다. 반복은 2~3회로 상한을 두고, 상한에 도달하면 사람에게 넘긴다. LLM 자가채점의 비결정성은 글자 수·필수 항목·논리 모순 같은 규칙 검사로 보강한다. 비평 기준은 A9 스킬에 두고 C9 평가 세트로 기준 자체를 검증한다.

이럴 때 쓴다

  • 출력 품질이 들쭉날쭉할 때(§7.5)
  • 품질 기준을 비평 규칙으로 적을 수 있을 때
  • 유형 ④·⑦·⑫ 조립 템플릿

이럴 때는 쓰지 않는다

  • 기준이 수치 목표(정확도·길이·형식)라 그 목표까지 순환하면 되는 경우(B′6)
  • 재생성 없이 기각·강등만 하면 되는 판정일 때(B′9)
  • 반복 상한과 비용 지표를 둘 수 없을 때(X12)

얻는 것

  • 출력 품질 안정
  • 비평 이력으로 수정 사유 추적
  • 규칙 검사와 결합하면 비결정성 완화

점검표

  • 반복 상한이 설정되어 있는가
  • 비평자가 생성자와 분리되어 있는가
  • 규칙으로 검사 가능한 항목을 코드로 검사하는가
  • 비평 도입 효과를 평가 세트로 쟀는가

구조 — 참여 부품

  • 생성자 — 초안 생성과 수정
  • 비평자 — 기준 검사, 통과 여부와 수정 사유 제시(LLM 또는 규칙)
  • A9 업무 규범 스킬 — 비평 기준 보관
  • C1 검토 큐 — 반복 상한 도달 건 처리

A10 문서 형식 어댑터 공통 서비스

HWP·HWPX·엑셀·한셀·PDF 같은 한국 공공 문서 형식을 AI 부품이 읽고(구조화) 쓰게(서식 생성) 하는 변환 계층이다.

PAX 사례 136건이 이 부품을 쓴다

맥락

문서를 입력으로 받거나 기안·보고서·취합본을 산출하는 과제라면 거의 다 쓴다. 유형 2·4·8에서는 필수 기반이고 유형 6·7에서도 쓰인다. E1 로컬 PC 조건에서 도는 경우가 많다.

맞서는 힘(긴장)

  • 형식 충실도(표·각주·조항 구조 보존) vs 파서 구현 비용
  • 로컬 처리(무반출) vs 클라우드 변환 도구의 편의
  • 기관별 서식 다양성 vs 공통 어댑터 재사용

해법

입력 쪽에서는 HWPX 압축 구조·PDF에서 조·항·호·별표 계층과 표를 보존해 구조화 텍스트·표로 바꾸고, 머리말·각주 같은 잡음을 걷어 조항 단위로 정규화한다. 출력 쪽에서는 스킬(A9)의 출력 서식을 받아 HWPX·XLSX 기안 서식을 역방향으로 생성한다. 민감 문서는 PC 밖으로 보내지 않도록 로컬에서 변환하고, 파서를 라이브러리·CLI·MCP로 함께 제공하면 다른 부품과 기관이 그대로 쓴다. 형식 변환 정확도는 C9 판정 체계로 잰다.

이럴 때 쓴다

  • 입력이 HWP·HWPX·엑셀·PDF 공공 문서일 때
  • 산출물을 기안·보고 서식으로 내보내야 할 때
  • 유형 2·4·8 조립

이럴 때는 쓰지 않는다

  • 스캔 이미지·음성처럼 인식이 필요한 입력은 B4 인식 파이프라인(OCR·STT)
  • 입출력이 이미 정형 데이터·API인 경우

얻는 것

  • 공공 문서를 AI 입력·출력으로 연결
  • 기관 간 재사용 가능한 공통 부품
  • 로컬 처리로 무반출

점검표

  • 표·조항 계층이 변환 후에도 보존되는가
  • 출력이 기관 기안 서식 그대로 열리는가
  • 민감 문서가 변환 과정에서 PC 밖으로 나가지 않는가
  • 변환 정확도 판정 기록이 있는가

구조 — 참여 부품

  • 입력 파서 — 조·항·호·표 구조를 보존해 구조화
  • 서식 생성기 — 구조화 결과를 HWPX·엑셀 서식으로 출력
  • A9 업무 규범 스킬 — 출력 서식 규범 제공
  • B3 지식 접지 상담 — 구조화된 규정을 색인해 검색

변형

  • 규정 구조 파서: HWP/HWPX·PDF 규정을 조항 단위로 정규화한다.

A2.2 모델 서빙 · 주권형 온프레미스 공통 서비스

오픈웨이트 모델을 기관 서버·폐쇄망·로컬 PC 안에서 Ollama·vLLM 등으로 구동해 데이터를 기관 밖으로 내보내지 않고 추론한다.

PAX 사례 54건이 이 부품을 쓴다

맥락

E1은 폐쇄망·행정망·로컬 PC, E2는 해외 오픈웨이트(로컬) 또는 국산 오픈웨이트, E5는 S 이상이다. 폐쇄망 B3·B6·B8, 유형 3(현장 폐쇄망 서버 추론), 유형 12 개발 코파일럿은 이 변형을 기본으로 쓴다.

맞서는 힘(긴장)

  • 데이터 주권 vs 상용 최신 모델 대비 성능
  • GPU·서버 고정비 vs 종량 과금
  • 모델 운영·갱신 역량 vs 외부 의존 제거
  • 저사양 장비 구동 vs 모델 크기

해법

오픈웨이트 모델을 기관 안에 설치하고 서빙 계층(Ollama·vLLM·LM Studio 등)으로 업무 부품에 노출한다. 임베딩 모델도 로컬로 두어 B3 검색까지 망 안에서 끝낸다(§5 E1 폐쇄망 행 '로컬 임베딩'). 모델 선정은 C9 평가 세트로 상용·온프레미스 후보를 같은 조건에서 비교해 정한다. 폐쇄망에서 C7 경로는 수동 전환·다른 로컬 모델로 제한되므로 둘 이상의 로컬 모델이나 수동 절차를 미리 둔다. 모델·패키지 반입은 S11 인제스천 검증을 거친다.

이럴 때 쓴다

  • E1이 폐쇄망·행정망이거나 문서가 PC 밖으로 나가면 안 될 때
  • E5가 S 이상인데 내부망 프록시(A2.4)를 쓸 수 없을 때
  • 현장 폐쇄망 서버에서 추론해야 하는 유형 3
  • C7의 대체 경로로 로컬 모델을 둘 때

이럴 때는 쓰지 않는다

  • 추론 인프라·운영 인력을 확보할 수 없을 때
  • 현장 기기 자체에서 돌아야 하면 A5(엣지 런타임)
  • 모델을 재학습했으면 A2.3

얻는 것

  • 데이터가 기관 밖으로 나가지 않음
  • 호출 비용이 고정비로 바뀜
  • 폐쇄망에서도 LLM 사용 가능
  • C7의 대체 경로 후보

점검표

A2.1 모델 서빙 · 상용 API 호출 공통 서비스

GPT·Gemini·Claude·HyperCLOVA X·Upstage 등 상용 모델 API를 서빙 계층을 거쳐 호출해 자체 인프라 없이 최신 모델 성능을 쓴다.

PAX 사례 88건이 이 부품을 쓴다

맥락

E2는 해외 상용 API(또는 국산 상용 모델 API), E1은 인터넷망·클라우드다. E5 등급이 O이거나 비식별 후 전송해도 되는 업무에 맞는다. 대민 상담(B3)·코파일럿(B1)·콘텐츠 생성(B7)에서 흔하다.

맞서는 힘(긴장)

  • 모델 성능·도입 속도 vs 데이터 반출·주권
  • 종량 과금의 초기 저비용 vs 호출량 증가 시 비용 예측 어려움
  • 벤더의 모델 개선 vs 예고 없는 품질 회귀
  • 단일 API의 단순함 vs 장애 시 서비스 중단

해법

업무 코드는 서빙 계층만 부르고, 서빙 계층이 상용 API를 호출한다. 행정망 본문이 나가는 경로 앞에는 C5 비식별 전처리를 두고, 대체 모델을 등록해 C7 폴백을 건다(§5 매트릭스 E2 해외 상용 API 행). 모델 버전을 고정하고 모델·프롬프트·설정 조합을 릴리스처럼 관리해 업데이트 전후를 C9로 비교한다. 비용이 문제면 라우팅·캐싱으로 큰 모델 호출을 줄인다. E5가 S 이상이면 이 변형 단독으로는 안 되고 A2.4 내부망 프록시를 거친다.

이럴 때 쓴다

  • 인터넷망·클라우드 환경이고 데이터 등급이 O이거나 비식별 후 전송 가능할 때
  • PoC 초기에 모델 성능을 빠르게 확인해야 할 때
  • 자체 GPU·운영 인력이 없을 때

이럴 때는 쓰지 않는다

  • E1이 폐쇄망이면 조립 오류(A2.2·A2.4로)
  • E5가 S 이상인데 내부망 프록시가 없을 때(A2.4 필수)
  • 상시 서비스인데 대체 경로를 둘 수 없을 때

얻는 것

  • 인프라 없이 최신 모델 성능
  • 빠른 PoC
  • 벤더의 지속적 개선

점검표

  • 업무 코드가 상용 API를 직접 부르지 않는가
  • 외부로 나가는 프롬프트에서 무엇이 걸러지는지 답할 수 있는가
  • API 장애 시 대체 경로가 있는가
  • 모델 버전과 호출당 비용·지연이 기록되는가

구조 — 참여 부품

  • A2 서빙 계층 — 업무 코드 대신 상용 API를 호출하고 버전·사용량을 기록
  • C5 가드레일(비식별 전처리) — 외부 전송 전 민감정보 제거
  • 상용 모델 API — 기관 밖에서 추론을 수행
  • C7 폴백 스위치 — API 장애·품질 저하 시 대체 모델·수동 처리로 전환

변형

  • 국산 상용 API: HyperCLOVA X·Upstage 등 국내 사업자 API. 망·등급 조건은 해외와 같이 따진다.

맥락

C7 폴백 스위치 운영 컴포넌트

모델·API·도구가 멈추거나 품질이 떨어질 때 대체 모델·규칙 기반 축소·수동 처리로 경로를 바꿔 서비스가 끊기지 않게 한다.

PAX 사례 12건이 이 부품을 쓴다

맥락

상용 API 또는 단일 모델에 의존하는 모든 B 부품. 특히 E2가 해외 상용 API이거나 B5처럼 상시 가동해야 하는 서비스.

맞서는 힘(긴장)

  • 가용성 vs 비용(대체 경로를 상시 유지하는 비용)
  • 품질 일관성 vs 대체 경로의 품질 저하
  • 자동 전환의 신속성 vs 전환 판단의 오작동 위험

해법

오류율·지연·단가 신호를 감시하다가 임계를 넘으면 재시도 → 기존 API → 대체 MCP → 대체 모델 → 규칙 기반 축소 → 수동 전환 순으로 경로를 바꾼다. 장애 범위는 격리(Bulkhead)로 한 부품에 가두고, 모델 교체는 무중단(Blue-Green)으로 한다. 전환은 C4 감사 로그에 남기고, 복구 후에는 원래 경로로 되돌리는 조건도 함께 정한다. 대체 경로의 품질 저하는 이용자에게 F7 한계 안내로 알린다.

이럴 때 쓴다

  • E2가 해외 상용 API이거나 혼합일 때
  • B5 현장 감지·경보처럼 상시 서비스일 때 필수
  • 대민 자동응답(B3 대민형)처럼 중단 비용이 큰 경우
  • 유형 ① 대민 상담(상시), ③ 현장 감시

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 런타임 AI가 없을 때
  • 로컬 완결 도구로 외부 의존이 없을 때
  • 유형 ①·⑦에서 model_dependency가 없음(비LLM)일 때는 필수에서 면제(R7)

얻는 것

  • 핵심 서비스 연속성
  • 벤더 종속 완화(X4 예방)

점검표

  • 대체 경로가 최소 하나 구현되어 있는가
  • 전환 임계와 복귀 조건이 수치로 정의되어 있는가
  • 전환 이력이 로그로 남는가
  • 실증 기간에 전환을 1회 이상 실행한 기록이 있는가

구조 — 참여 부품

  • A2 모델 서빙 계층 — 주 경로와 대체 모델을 함께 노출하는 끼울 자리
  • 상태 감시기 — 오류율·지연을 임계와 비교해 전환을 결정
  • C4 감사 로그·지표 — 전환 시점·사유·복구를 기록

S3 컨텍스트 방화벽 보안 패턴

맥락

맞서는 힘(긴장)

  • 구현이 가벼움 vs 모델이 구역 경계를 넘겨 해석할 수 있음(증명 불가)
  • 요약 품질(문맥 전체 활용) vs 외부 텍스트의 영향 제한
  • 구역 표식의 일관성 vs 부품마다 다른 프롬프트 조립 방식

해법

  • 장기 기억을 쓰는 에이전트

이럴 때는 쓰지 않는다

  • E4가 P2 이상이고 신뢰 불가 입력을 읽는데 S3만으로 끝내려 할 때 — 규칙상 S4·S5·S6 중 하나가 따로 필요

얻는 것

  • 시스템 지시(프롬프트) 유출 축소
  • 구현이 가벼워 모든 B1·B8에 기본 장착 가능

점검표

  • 모든 프롬프트가 구역 표식을 거쳐 조립되는가

F7 한계·신뢰도 안내 상호작용 패턴

AI가 무엇을 못 하는지, 얼마나 확신하는지, 공식 판단이 아님을 이용자가 볼 수 있는 곳에 적어 과신을 막는다.

PAX 사례 63건이 이 부품을 쓴다

맥락

대민 상담·안내(유형 ①), 대조·점검(⑦), 분석·예측(5a·⑩), 비식별 도구(⑬). 대체 경로로 운영 중인 C7 상황.

맞서는 힘(긴장)

  • 정직한 한계 고지 vs 서비스 신뢰도 하락 우려
  • 신뢰도 수치 표시의 정확성 vs 이용자 이해

해법

화면에 사용 한계(대상 범위·미검증 항목·처리 시간), 신뢰도, '공식 판단 아님' 고지를 결과 옆에 배치한다. 저신뢰 결과는 표시를 달리하고, C7 대체 경로로 운영 중이면 품질 저하를 알린다. 고지 문구는 법률 자문·유권해석을 대체하지 않는다는 점을 분명히 적는다.

이럴 때 쓴다

  • 대민 서비스 D1~D7(F1·F2·F7 최소 요건)
  • 유형 ①⑦5a⑩⑬처럼 F7이 필수인 유형
  • C7 대체 경로 운영 중

이럴 때는 쓰지 않는다

  • 유형 ①·⑦에서 model_dependency가 없음(비LLM)이면 필수에서 면제(R7). 단 비LLM 도구도 한계 고지는 권장된다

얻는 것

  • 과신·오인 방지
  • 기관 책임 범위 명확화

점검표

  • 이용자가 '공식 판단이 아님'을 결과 화면에서 읽을 수 있는가

구조 — 참여 부품

D8.2 요약·추출 서비스 블록

공문·회의록·공람 문서에서 무엇을 언제까지 해야 하는지를 뽑아 카드·일정으로 만드는 내부 운영 블록이다. B1, B8 오버레이, B4가 전형 부품이다.

PAX 사례 24건이 이 부품을 쓴다

맥락

  • 외부에서 온 공문·첨부(간접 인젝션) vs 자동 요약
  • 등급 문서 요약의 외부 유출 vs 상용 모델 성능

D8.4 대조·점검 서비스 블록

법령·규정·서식·인용·근태·보안 기준과 대조해 확인할 대상을 먼저 골라 주는 내부 운영 블록이다. "최종 판단은 사람"이 가장 자주 붙는다.

PAX 사례 81건이 이 부품을 쓴다

맥락

기관 내부 문서·자료를 기준과 대조하는 업무. §7.3 유형 ⑦ 대조·점검 도우미(D8.4, P0~P1)와 유형 ⑩ 위험 예측·표적 선별(D6·D3·D8.4)의 무대. PAX 81건(주 부품 B0 73%, B1 12%), 감사·법무 25건·문서·기안 12건.

맞서는 힘(긴장)

  • 점검 범위 확대 vs 오탐으로 인한 확인 부담
  • 규칙 점검의 결정성 vs LLM 대조의 유연성
  • 점검 대상이 점검기를 속이는 위협 vs 자동 점검
  • 출처 대조의 엄격성 vs 원문 접근 권한(공공 API 인가)

해법

기준이 규칙으로 옮겨지면 B0 규칙 점검기로, 해석이 필요하면 B3 법령 접지로 대조한다. 기준 원문은 A3 공공 API(법령·판례)에서 가져와 C5 출처 검증으로 인용이 실제 원문과 일치하는지 확인한다. 결과는 판정이 아니라 "확인할 대상 목록"으로 내고, C1으로 "최종 판단은 사람"을 명시하며, F7 한계와 F1 출처를 붙인다. 점검 대상 문서·코드가 점검기를 속이지 못하게 대상별 격리(S6)나 고정 규칙 실행(S4)을 쓰고, 코드 점검이면 S9 샌드박스를 둔다. C9 평가 세트로 누락률을 잰다.

이럴 때 쓴다

  • 문서·자료를 법령·규정·서식과 한 줄씩 대조하는 업무
  • 인용·근거가 원문과 맞는지 확인해야 할 때
  • 점검 대상이 많아 확인 대상을 먼저 좁혀야 할 때

이럴 때는 쓰지 않는다

  • 국민 신청 건의 자격 판정이면 D3
  • 현장 시설을 관측해 점검하면 D6
  • 대조 없이 자료를 찾아 보여 주면 D8.1

얻는 것

  • 대조 시간 단축과 누락 감소
  • 사람 판단을 확인 대상에 집중
  • 인용 오류의 사전 차단

점검표

  • 결과가 판정이 아닌 확인 대상으로 표시되는가
  • 근거 원문 출처가 연결되는가
  • 누락률을 평가 세트로 재는가
  • 점검 대상 속 문장이 점검 결과를 바꾸지 못하는가

구조 — 참여 부품

  • 담당자 — 확인 대상을 검토해 최종 판단
  • B0 결정적 도구(규칙 점검기) — 규칙화된 기준으로 대조
  • B3 지식 접지 상담 — 법령·규정에 접지해 해석 대조
  • A3 공공 API 제공자 — 법령·판례 원문 제공
  • C5 가드레일·출처 검증 — 인용을 원문과 대조
  • C1 검토 큐 — 최종 판단은 사람

변형

  • 규칙 점검기형: B0로 서식·근태·보안 기준을 결정적으로 대조(Attendance Checker).
  • 법령 접지 대조형: B3가 법령·규정에 접지해 해석 필요 항목을 대조(Legal Reviewer).
  • 인용 검증형: 보고서·논문의 법령·판례·문헌 인용을 원본과 대조(paper-verify).
  • 표적 선별형: B2 위험 예측이 점검 대상을 좁힘(유형 ⑩, B′9).

A9 업무 규범 스킬 공통 서비스

보고서 구조·문체·서식·검증 절차 같은 업무 규범을 모델 중립 스킬(지침 + 검증기 + 출력 서식)로 패키징해 어떤 모델·에이전트에서든 재사용한다.

PAX 사례 54건이 이 부품을 쓴다

맥락

기안·보고서·콘텐츠처럼 서식과 문체가 정해진 산출물을 만드는 B1·B7, BYO 코딩 에이전트 환경(E2 모델 중립), 개발 코파일럿에서 쓴다. 유형 4·6·12에서는 필수 기반이고, §7.2 진행 경로에서는 3단계에 놓인다.

맞서는 힘(긴장)

  • 규범 고정(일관성) vs 담당자 재량
  • 모델 중립(이식성) vs 특정 모델 최적화
  • 규범 공개·재사용 vs 프롬프트·규범 유출
  • 가중치에 넣기(튜닝) vs 문서로 주입하기

해법

규정집·매뉴얼·서식 예시에서 업무 규범을 뽑아 지침(구조·문체·금지 사항), 검증기(형식·인용·수치 검사), 출력 서식(HWPX·DOCX 등)으로 묶은 스킬 패키지로 만든다. 모델 호출 코드와 분리된 파일로 두어 어떤 코딩 에이전트·모델에서도 같은 절차가 돌게 한다(External Configuration). 산출·검증된 수치와 출처만 주입하고 미제공 수치·순위 생성을 금지하는 식으로 생성 범위를 규범으로 좁힌다. 스킬은 버전으로 관리해 규범 유출·변경을 추적하고, C9로 스킬 변경 전후 품질을 잰다.

이럴 때 쓴다

  • 산출물 서식·문체·구조가 정해져 있을 때
  • 출력 품질이 들쭉날쭉할 때(§7.5)
  • BYO 환경에서 모델과 무관하게 같은 절차를 돌려야 할 때
  • 갱신이 잦은 규범을 튜닝 없이 반영해야 할 때

이럴 때는 쓰지 않는다

  • 규범이 문서로 정리되지 않았고 정리할 담당도 없을 때
  • 지식 검색이 필요한 문제(B3 접지가 먼저)
  • 스킬 내용 자체가 민감해 배포할 수 없는데 버전 관리·접근 통제를 둘 수 없을 때

얻는 것

  • 출력 일관성
  • 모델 교체 가능(BYO에서는 교체 가능성이 곧 C7)
  • 타 기관 재사용
  • 튜닝 없이 규범 갱신

점검표

  • 규범이 모델 호출 코드와 분리된 파일로 있는가
  • 검증기가 출력 형식·인용·수치를 실제로 검사하는가
  • 스킬에 버전이 있는가
  • 다른 모델로 바꿔도 같은 서식이 나오는지 확인했는가

구조 — 참여 부품

  • 규범 원천(규정집·매뉴얼·서식) — 스킬로 옮길 업무 규범의 출처
  • 스킬 패키지 — 지침·검증기·출력 서식을 모델 밖 파일로 묶음
  • 코딩 에이전트·모델(BYO) — 스킬을 불러 규범대로 산출
  • A10 문서 형식 어댑터 — 출력 서식을 HWPX·DOCX로 내보냄
  • C9 평가 세트 — 스킬 변경 전후 품질 비교

변형

  • 보고서·문서 규범 스킬: gov-report-skill(기획보고서 7대 항목), 원페이퍼 스킬(A4 한 쪽·DOCX 검증).
  • 스타일·콘텐츠 스킬: Public Cardnews(6개 스타일), 제작 가이드·검수 체크리스트를 묶은 제작 스킬 패키지.
  • 검증 스킬: paper-verify(인용 검증)처럼 검증 절차 자체를 패키징한다.
  • 규정집→스킬 변환: book-to-skill은 PDF 규정집을 에이전트 스킬로 자동 변환한다(A9+A10 조합).
  • 지식 가이드 In-Context 주입: 파인튜닝 대신 추출·판정 기준을 문서형 가이드로 증류해 주입한다.

참조 구현 예

  • PAX paper-verify — 인용 검증 스킬(§6 A9 카드)

C1 검토 큐 운영 컴포넌트

AI 산출물이 다음 단계로 넘어가기 전에 사람이 맞고 틀림을 확인·수정·확정하는 대기열을 두어, 오류가 업무 결과로 흘러가지 않게 한다.

PAX 사례 46건이 이 부품을 쓴다

맥락

AI 산출물이 공문·처분·대민 안내·기록으로 이어지는 모든 B 부품(B1 코파일럿, B4 인식 파이프라인, B2 예측기, B7 콘텐츠 생성기 등). 이용자 본인이 최종 확정자인 자기서비스형 도구도 포함한다(R16).

맞서는 힘(긴장)

  • 정확성·책임성 vs 처리 속도(전건 검토는 자동화 이득을 깎는다)
  • 검토자의 숙련 vs 자동화 편향(AI 결과를 그대로 승인하는 경향)
  • 전건 검토의 안전 vs 위험도별 분기(C2)로 가야 하는 효율 압력

해법

AI 산출물에 신뢰도·근거를 붙여 검토 대기열에 올리고, 검토자가 승인·수정·반려 중 하나를 고르게 한다. 수정·반려 내역은 C4 감사 로그에 남겨 수정률을 집계하고 C6 환류의 입력으로 쓴다. 검토 화면은 원문 위치·근거를 함께 보여 줘 확인 비용을 줄인다. 전건 검토로 시작하되, 수정률 실측이 쌓이면 C2 위험도 라우터로 저위험 건을 자동 종결하는 단계로 옮긴다.

이럴 때 쓴다

  • AI 산출물이 공문·처분·대민 안내로 그대로 이어질 때
  • E4가 P1 이상이고 되돌리는 데 사람 시간이 많이 드는 조치가 있을 때
  • 서비스 유형 ② 접수·심사, ④ 기안 코파일럿, ⑥ 콘텐츠 제작, ⑦ 대조·점검, ⑩ 위험 예측, ⑪ 추천·매칭, ⑫ 개발 코파일럿처럼 C1이 필수인 유형

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 런타임 AI 산출물이 없을 때
  • 쉽게 되돌릴 수 있고 저위험인 조치를 이미 C2로 자동 종결하도록 실측 근거를 갖춘 구간(전건 검토를 영원히 남기지 않는다)

얻는 것

  • 오류가 업무 결과로 나가기 전에 차단
  • 책임 소재가 명확해짐
  • 수정 내역이 C4 지표와 C6 환류의 원천 데이터가 됨

점검표

  • AI 산출물이 확정 전 상태로 머무는 지점이 명시되어 있는가
  • 검토자와 승인·수정·반려 선택지가 정해져 있는가
  • 검토 결정과 수정 내역이 로그로 남는가
  • 실증 기간의 검토·수정 건수가 기록되어 있는가
  • 전건 검토에서 분기로 옮길 조건이 정해져 있는가

구조 — 참여 부품

  • 검토 대기열 — AI 산출물을 확정 전 상태로 보관하고 검토자에게 배정
  • 검토자(담당자 또는 이용자 본인) — 승인·수정·반려를 결정하는 최종 책임자
  • F2 편집 가능한 출력 — 검토자가 산출물을 직접 고치는 화면
  • C4 감사 로그·지표 — 검토 결정과 수정 내역을 적재해 수정률로 집계

변형

  • 전건 검토형: 모든 AI 산출물을 담당자가 확인·확정
  • 예외 검수형: 정상 건은 일괄 승인하고 저신뢰 항목만 개별 검수하는 검수 UI
  • 파이프라인 내장 관문형: 멀티에이전트·다단계 파이프라인의 각 관문에 승인·보완·재작성 선택지를 둠
  • 자기서비스형: 이용자 본인이 최종 확정자인 HITL. 실제 운영 중이면 C1 present(R16)
  • 심의 게이트: 팩트체크·법무·윤리처럼 제3자 전문가가 수행하는 승인 게이트

참조 구현 예

  • PAX 9dc1a7081bc869b1 — 광진구 — 담당자·팀장 최종 판단 책임 등 4대 관리 원칙 명문화

F2 편집 가능한 출력 상호작용 패턴

생성물을 이용자가 직접 고쳐 확정하게 한다. 통제감의 실체이며, 수정 내역은 C4 지표와 C6 환류의 입력이 된다.

PAX 사례 50건이 이 부품을 쓴다

맥락

B1 코파일럿(필수 면), B7 콘텐츠 생성기, B4 인식 결과 확정. 유형 ② 접수·심사, ④ 기안 코파일럿, ⑫ 개발 코파일럿, 5a-agg(R19), 2b 시민 제출 준비(R20).

맞서는 힘(긴장)

  • 편집 자유도 vs 원본 추적(무엇을 고쳤는지)
  • 편집 가능한 공공 서식(HWPX 등) 출력 vs 구현 비용

해법

생성물을 이용자가 바로 고칠 수 있는 형식(편집 화면, HWPX·PPTX 등 네이티브 파일)으로 내고, 이용자가 고친 뒤 확정하게 한다. AI 원안과 수정본의 차이를 기록해 C4 수정률과 C6 환류 입력으로 쓴다. 문서 형식 출력은 A10 어댑터가 받친다.

이럴 때 쓴다

  • B1 코파일럿 전반(필수 면)
  • 대민 서비스 D1~D7(F1·F2·F7이 최소 요건)
  • 유형 ②④⑫, 5a-agg, 2b처럼 F2가 필수인 유형

이럴 때는 쓰지 않는다

  • 이용자가 결과를 수정하면 안 되는 판정 결과(판정은 C1 확정 절차로 다룸)
  • 조회 결과만 보여 주는 P0 도구

얻는 것

  • 이용자 통제감
  • 수정 내역이 품질 지표·환류 데이터가 됨

X1 AI 스티커 안티패턴

기존 화면에 요약·챗봇 버튼만 붙이고 업무 순서와 사람·AI의 역할 분담은 그대로 두어, AI가 있어도 업무 산출물이 바뀌지 않는 함정이다.

맥락

기존 행정정보시스템·업무 포털에 AI 기능을 추가하는 과제, 특히 성과 지표가 'AI 기능 탑재 여부'나 호출 수로 잡힌 과제. R24에 따라 AI 런타임이 전혀 없는 순수 행정정보시스템도 이 태그(AI 무관)로 표기한다.

맞서는 힘(긴장)

  • 빠른 도입 실적 vs 업무 흐름 재설계 비용
  • 기존 시스템 무변경(안정성) vs 산출물 단위의 역할 분담
  • 'AI 탑재' 홍보 효과 vs 실제 처리시간·수정률 개선

해법

먼저 가치 흐름 규칙(R1)으로 사람 또는 국민이 최종으로 받는 핵심 산출물을 정하고, 그 산출물을 AI가 어떤 모양으로 분담할지 B 업무 컴포넌트를 하나 고른다(초안→사람 확정이면 B1, 근거 접지 답변이면 B3, 서류 추출이면 B4). 사람이 확정하는 지점은 C1 검토 큐로, 이용자가 고쳐 확정하는 면은 F2 편집 가능한 출력으로 명시한다. 흐름이 바뀌었는지는 C4 감사 로그·지표의 처리시간·수정률로 잰다. AI 런타임이 전혀 없는 행정정보시스템이라면 AI로 포장하지 말고 R24대로 B0·service_type 0·platform 공란·X1(AI 무관)으로 정직하게 분류한다.

이럴 때 쓴다

  • AI 기능이 추가됐다는 서술은 있으나 처리 단계 수·결재선·담당자 역할이 바뀌었다는 서술이 없다
  • 성과 지표가 AI 호출 수·이용 만족도뿐이고 처리시간·수정률 같은 산출물 지표가 없다
  • 챗봇이 기관 업무 데이터·시스템과 연결되지 않은 범용 대화에 머문다
  • AI 런타임이 전혀 없는 행정정보시스템이 AX 과제로 분류되어 있다(R24)

이럴 때는 쓰지 않는다

  • B1 코파일럿처럼 AI가 초안을 만들고 사람이 확정하는 역할 분담이 실제로 서술된 경우
  • B8 레거시 오버레이처럼 표준 시스템 위에 얹었지만 업무 산출물을 AI가 만들어 내는 경우
  • B0 결정적 도구가 반복 취합 업무를 실제로 줄이고 AI로 포장하지 않은 경우(Ready 부품으로 정직하게 분류된 경우)

얻는 것

  • 기존 시스템을 건드리지 않아 도입이 빠르고 장애 위험이 낮다
  • 'AI 탑재' 실적을 즉시 보고할 수 있다

점검표

  • AI 도입 전후 처리 단계·담당자 역할의 차이를 한 장으로 보여 줄 수 있는가
  • AI가 만드는 산출물과 사람이 확정하는 지점이 명시되어 있는가
  • 처리시간·수정률 같은 산출물 지표가 도입 전 기준선과 함께 있는가
  • AI 런타임이 없는데 AI 과제로 보고하고 있지 않은가

구조 — 참여 부품

  • 덧붙인 AI 기능 — 요약·대화 버튼. 업무 산출물 생산에 역할이 없음
  • B1 코파일럿 — 교정 후 초안→사람 확정으로 산출물 역할을 나누는 대체 부품
  • C1 검토 큐 — 교정 후 사람이 확정하는 지점을 명시
  • C4 감사 로그·지표 — 흐름이 실제로 바뀌었는지 처리시간·수정률로 측정

변형

  • 요약 버튼형: 기존 화면에 '요약' 버튼만 추가하고 결재·처리 단계는 그대로
  • 범용 챗봇 부착형: 업무 데이터와 연결되지 않은 범용 대화창을 포털에 부착
  • AI 무관 행정시스템(R24): AI 런타임이 전혀 없는 순수 행정정보시스템(예: 교육·인증 학습관리시스템). B0·service_type 0·platform 공란과 함께 X1(AI 무관)로 표기

X4 단일 모델 인질 안티패턴

상용 API 하나에 전 기능이 묶여 있어, 그 API가 멈추거나 바뀌면 무슨 일이 생기는지 아무도 답하지 못하는 함정이다.

맥락

맞서는 힘(긴장)

  • 최고 성능 단일 모델 vs 대체 경로 유지 비용
  • 빠른 시범 구축 vs 게이트웨이·폴백 설계
  • 모델 업데이트의 성능 향상 vs 예고 없는 동작 변화

해법

모델 호출을 A2 모델 서빙 계층 뒤로 숨겨 B 부품이 특정 벤더 API를 직접 부르지 않게 한다. 그 위에 C7 폴백 스위치로 재시도 → 기존 API → 대체 MCP → 대체 모델(A2.2 주권형 로컬 등) → 규칙 기반 축소 → 수동 전환의 경로를 정하고 전환 이력을 C4에 남긴다. 모델 교체가 실제로 안전한지는 C9 평가 세트로 재어 버전을 고정한다. 모델 중립(BYO) 배포라면 A9 스킬 형태로 배포해 모델 교체 가능성 자체를 폴백으로 삼는다.

이럴 때 쓴다

  • E2가 해외 상용 API인데 C7 폴백이 없다(분류기준 검증 경고 조건)

  • 모델 버전 고정·교체 시험 기록이 없다
  • A2 게이트웨이 없이 B 부품이 벤더 API를 직접 호출한다

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 런타임 AI가 없는 경우
  • 로컬 완결 도구로 외부 의존이 없는 경우
  • 모델 중립(BYO) 배포로 A9 스킬 형태라 이용자가 모델을 바꿀 수 있는 경우
  • 상용 API를 쓰되 A2 게이트웨이와 C7 대체 경로가 구현된 경우

얻는 것

  • 게이트웨이·대체 모델 유지 비용이 없다

점검표

  • 모든 모델 호출이 A2 한 곳을 지나는가
  • 대체 경로가 하나 이상 구현되어 있는가
  • 대체 모델의 품질이 C9로 측정되어 있는가
  • 모델 버전이 고정되어 있고 교체가 릴리스처럼 관리되는가

구조 — 참여 부품

X10 평가 없는 RAG, RAG 없는 튜닝 안티패턴

평가 세트 없이 검색을 붙여 '좋아진 것 같다'로 배포하고, 검색으로 풀릴 문제를 파인튜닝으로 푸는, 진행 경로를 건너뛰는 함정이다.

맥락

B3 지식 접지·B1 코파일럿에 RAG를 붙이거나 A2.3 튜닝형 모델을 만드는 과제, 특히 규정·매뉴얼 기반 질의응답.

맞서는 힘(긴장)

  • 눈에 보이는 기술 성과 vs 지루한 평가 세트 구축
  • 빠른 배포 vs 변경마다 재는 자
  • 자체 모델 보유 인상 vs 검색으로 충분한 문제

해법

§7.2 진행 경로를 순서대로 밟는다. B1 직접 프롬프트에서 시작해 두 번째 단계에서 C9 평가 세트(업무 질문·정답·채점 기준)를 먼저 만들고, 이후 A9 규범 스킬·F4, B3 지식 접지(A1 데이터 자산), B3 검색 품질(Hybrid·Rewriting·Reranker), C5 가드레일·F1 순으로 붙이며 매 단계를 C9로 잰다. A2.3 튜닝은 진행 경로의 마지막 단계로, 검색·규범 스킬로 풀리지 않는다는 것이 C9 점수로 확인됐을 때만 한다. 모델·프롬프트·설정 조합은 릴리스처럼 버전 관리한다.

이럴 때 쓴다

  • RAG·튜닝을 도입했는데 업무 질문·정답·채점 기준 세트가 없다
  • '답변 품질 향상'을 수치 없이 서술하거나 단발 정확도만 보고한다
  • 자주 바뀌는 규정·매뉴얼 질의를 파인튜닝으로 풀었다
  • 검색 품질(재현율·리랭킹)을 재지 않고 튜닝으로 넘어갔다

이럴 때는 쓰지 않는다

  • C9 세트로 RAG 전후를 비교한 뒤 배포한 경우
  • 검색·스킬로 풀리지 않음을 C9 점수로 확인한 뒤 튜닝한 경우
  • B2·B4처럼 비LLM 학습 모델로 원래 학습이 해법인 경우(RAG가 대안이 아님)

얻는 것

  • RAG·튜닝이라는 눈에 보이는 기술 성과를 빨리 낸다
  • 평가 세트 구축에 현업 시간을 쓰지 않는다

점검표

  • 업무 질문·정답·채점 기준 세트가 있는가
  • RAG 전후 점수 비교가 있는가
  • 튜닝을 선택한 근거가 C9 점수로 설명되는가
  • 모델·프롬프트·설정 조합이 버전 관리되는가

구조 — 참여 부품

  • C9 평가 세트·회귀시험 — 빠진 부품. 모든 변경을 같은 자로 잼
  • B3 지식 접지 — 튜닝 전에 먼저 시도할 검색 기반 접지
  • A2.3 튜닝형 모델 — 진행 경로의 마지막 단계
  • A1 데이터 자산 서비스 — 정답 출처와 검색 코퍼스

변형

  • 평가 없는 RAG: 검색을 붙이고 몇 개 질문을 눈으로 보고 배포
  • RAG 없는 튜닝: 문서 검색으로 풀릴 최신 규정 질의를 파인튜닝으로 해결하려 함
  • 평가 없는 튜닝: 튜닝 전후를 같은 세트로 비교하지 않음
