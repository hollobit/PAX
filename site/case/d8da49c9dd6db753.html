판정 근거

경력증명서·자격증·졸업증명서를 로컬 OCR로 읽어 교원 호봉 획정·재획정 산정을 보조하는 100% 로컬 CPU 프로그램. model_dependency는 없음(비LLM)이지만 서류 인식→경력 구조화→호봉 산정 판정으로 이어지는 흐름이므로 R5에 따라 B4 인식 파이프라인(OCR·서류)을 주 부품으로, 규칙 산정 부분을 B0 secondary로 두었다. OCR 결과가 규칙 산정으로 흐르고 인사 담당자가 확정하는 구조는 B′9 결정론 판정 게이트에 해당. OCR 모델은 로컬 비LLM 학습 모델 서빙(A2.5). '외부 API나 문서 업로드 없이'는 민감 서류가 서버에 도달하지 않는 S12 데이터 비도달 설계로 판정. 사람 확정 절차(C1)는 '지원'이라는 표현뿐 명시가 없어 태그하지 않음. 호봉은 보수에 직결되나 도구는 산정 보조이므로 P1 잠정, 개인 인사정보라 S(민감). URL 없음.

구현 가이드

주 패턴 B4 인식 파이프라인을 구현할 때

구현 단계

  1. 입력 종류와 추출할 필드, 필드별 기준정보(대장·코드표)를 정의한다.
  2. 인식 단계는 정형 출력(JSON 스키마)만 내게 하고, 판정·산수는 규칙 단계로 분리한다(B′9).
  3. 신뢰도 임계와 보류 조건을 정해 C1 검토 큐로 보내고, C3로 재처리 경로를 둔다.
  4. E5 민감 서류면 행정망 + 로컬 모델로 두고, 제출 서류를 읽는 P2 이상 구성은 S6 문서별 격리를 둔다.
  5. C9 시험 세트로 필드별 정확도를 재고 C4로 보류율·수정률을 집계한다.

점검표

  • 인식과 판정이 서로 다른 단계로 분리되어 있는가
  • 저신뢰 건이 보류되어 사람에게 가는가
  • 오인식 건을 되돌리는 경로가 있는가(C3)
  • 필드별 정확도를 잰 시험 세트가 있는가

환경 조건

E5 민감 서류면 E1 행정망 + A2 로컬(Whisper 로컬 등). E4는 P1~P2이며, 건별 검수 없이 운영 DB로 직행하면 P2, 승인·반려에 직결되면 P3다. 제출 서류는 신뢰 불가 입력이므로 P2 이상이면 S6 문서별 격리 + 규칙 집계가 필수다(§7.4 유형 ②).

주의할 점

  • 오인식이 판정으로 번질 위험(C3 필수)
  • 민감 서류는 로컬 모델 제약
  • 제출 서류 속 숨은 지시로 판정이 조작될 위협

기본 배선 예

보완이 필요한 필수 부품

이 조합에서 카탈로그가 함께 갖추라고 권하는 부품 가운데 아직 확인되지 않은 것이다.

  • A3 공공 API 제공자 정부·공공이 운영하는 모델·데이터·개발 도구(범정부 AI 공통기반, 모두의 AI 실험실, 공공데이터포털, 공공 깃랩)를 범정부 Provider로 소비한다.
  • C1 검토 큐 AI 산출물이 다음 단계로 넘어가기 전에 사람이 맞고 틀림을 확인·수정·확정하는 대기열을 두어, 오류가 업무 결과로 흘러가지 않게 한다.
  • C5 가드레일 필터 개인정보·환각·편향·형식 오류가 프롬프트나 산출물에 들어가지 못하게 시스템이 경계에서 걸러낸다. 비식별 전처리, 출처 검증, 구조적 출력 제약이 대표 변형이다.

피해야 할 안티패턴

  • X13 도구 출력이 지시가 되는 에이전트 검색 결과·첨부·API 응답을 읽은 모델이 그 안의 문장을 새 명령으로 받아 도구를 부르는 구조를, 탐지 필터 하나로 지키려는 함정이다. 대처: 과제의 AI가 읽는 입력 중 기관 밖에서 작성된 것을 untrusted_inputs로 나열하고, §4.2 신뢰 불가 입력 규칙대로 S4 행동 선택기(미리 정한 행동 중 선택만, 결과가 LLM으로 돌아가지 않음), S5 계획 후 실행(외부 데이터를 읽기 전에 도구 호출 계획을 고정), S6 격리 LLM(도구 있는 LLM은 외부 데이터를 읽지 않고, 읽는 LLM은 도구가 없음) 중 하나를 갖춘다. S3 컨텍스트 방화벽과 S8 독립 검증기는 보조로 붙이되 S8만으로는 규칙을 충족하지 못한다. C8 승인 게이트도 신뢰 불가 입력 규칙의 대체 통제로 인정되지 않는다(R6). 그 전 단계에서는 E4를 P0~P1 읽기·산출물 범위에 묶어 두는 것이 곧 보안이다.

B0 결정적 도구 업무 컴포넌트

AI 코딩으로 만들었지만 런타임에는 AI를 부르지 않고 규칙과 원문 발췌만으로 같은 입력에 같은 결과를 내는 취합·변환·검색·시각화 도구다.

PAX 사례 413건이 이 부품을 쓴다

맥락

AI 코딩 도구(A7)로 기관 인력이 직접 만든 자생 도구가 대부분이다(PAX 557건 가운데 주 부품이 B0인 사례 390건, 70%). 로컬 PC 완결이나 폐쇄망 이식이 필요한 업무, 판정 재현성이 감사에서 중요한 업무에도 맞는다. model_dependency가 '없음(비LLM)'으로 확인될 때만 해당한다.

맞서는 힘(긴장)

  • 재현성·설명 가능성 vs 비정형 입력을 다루는 유연성
  • 로컬 완결의 보안 이점 vs 기관 전이 시 처리 로그(C4)와 인수인계가 사라지는 문제
  • 규칙을 코드에 넣는 단순함 vs 규정이 바뀔 때마다 사람이 규칙을 고쳐야 하는 유지 부담

해법

업무 절차를 입력 형식(A10 어댑터)과 처리 규칙으로 나누고, AI 코딩 도구(A7)는 개발 시점에만 써서 규칙 코드와 화면을 만든다. 런타임에는 모델을 호출하지 않으므로 같은 입력에 같은 결과가 나오고 인터넷 없이 로컬에서 돈다. 판정이 필요한 경우에도 결정적 규칙 엔진이 낸다. 비정형 입력을 다뤄야 하는 단계가 생기면 그 단계만 B1·B3로 승격하고 결정적 부분은 전처리로 남긴다. 부서 밖으로 옮길 때는 라이선스·저장소·처리 로그를 함께 갖춘다.

이럴 때 쓴다

  • 입력이 정형(엑셀·서식)이고 처리 결과를 규칙으로 정의할 수 있을 때
  • 파일이 PC 밖으로 나가면 안 되거나 폐쇄망·로컬 완결이 필요할 때
  • 판정 재현성이 필요해 같은 입력에 늘 같은 결과가 나와야 할 때(규칙 점검기, 결정론 점수 엔진)
  • LLM 도입 전에 데이터·기준선을 정비하는 단계일 때

이럴 때는 쓰지 않는다

  • 비정형 문서의 요약·초안처럼 규칙으로 산출물을 정의할 수 없을 때(B1)
  • 질문이 다양해 규정·선례 접지가 필요한 상담일 때(B3)
  • 학습 모델의 수치·등급 예측이 핵심 산출물일 때(B2)

얻는 것

  • 재현성과 감사 가능성
  • 폐쇄망·로컬 이식이 가장 쉬움
  • 모델 호출 비용과 모델 장애 위험이 없음
  • B1·B3의 전처리 부품으로 승격할 자산

점검표

  • 런타임에 LLM·ML 호출이 전혀 없는가
  • 규칙 표가 코드와 별도로 문서화되어 있는가
  • 같은 입력에 같은 결과가 나오는지 확인했는가
  • 라이선스와 저장소 위치가 명시되어 인수인계가 가능한가

구조 — 참여 부품

PAX 사례 34건이 이 부품을 쓴다

맥락

접수·심사(유형 ②), 서류 진위확인, 민원 통화 정리, 실시간 자막, 원격탐사·도면 판독처럼 비정형 입력이 업무의 출발점인 경우에 쓴다. 민감 서류가 많아 행정망·로컬 모델 조건이 자주 붙는다.

맞서는 힘(긴장)

  • 자동 연결의 효율 vs 오인식이 판정으로 번지는 위험
  • 인식 정확도 vs 로컬 모델 제약(E1·E5)
  • 단계 분리의 추적 용이성 vs 단계 간 지연

해법

인식(OCR·STT·비전·VLM)은 정형 필드만 내게 하고, 기준정보와의 대조·요건 판정은 규칙 단계가 맡는다(B′1 + B′9). 저신뢰·불일치 건은 보류해 C1 검토 큐로 보내고, 오인식은 C3 상태 머신으로 되돌린다. 공공 문서 형식은 A10으로 받으며 OCR·STT 엔진은 A2 공통 후보를 쓴다. 제출 서류처럼 신뢰 불가 입력을 읽고 시스템 쓰기가 있으면 문서별 격리(S6)로 서류 속 지시가 판정을 바꾸지 못하게 한다.

이럴 때 쓴다

  • 비정형 입력을 사람이 옮겨 적는 단계가 업무의 병목일 때
  • 추출값이 규칙 판정·다음 처리로 이어질 수 있을 때
  • 유형 ② 접수·심사 자동화의 기본 조립일 때

이럴 때는 쓰지 않는다

  • 추출 결과가 초안으로 멈추고 사람이 확정할 때(B1)
  • 추출 뒤 질의응답이 핵심 산출물일 때(B3)
  • 상시 관측 스트림 감시가 핵심일 때(B5)

얻는 것

  • 옮겨 적기 단계 제거
  • 판정 기준이 규칙으로 남아 설명 가능
  • OCR·STT 엔진을 범정부 공통으로 공유 가능

점검표

  • 인식과 판정이 서로 다른 단계로 분리되어 있는가
  • 저신뢰 건이 보류되어 사람에게 가는가
  • 오인식 건을 되돌리는 경로가 있는가(C3)
  • 필드별 정확도를 잰 시험 세트가 있는가

  • A2 모델 서빙 계층 — OCR·STT·VLM 엔진

B′1 순차 파이프라인 제어 흐름

한 단계의 출력을 다음 단계의 입력으로 넘기는 고정 순서 배선이다. 한 프롬프트에 많은 일을 몰아 시켜 품질이 떨어지는 문제를 막는다.

PAX 사례 109건이 이 부품을 쓴다

맥락

B4 인식 파이프라인의 기본 배선이며, B1·B0·B5 안에서도 흔하다. 단계 순서가 업무 절차로 미리 정해져 있고 AI가 순서를 고를 필요가 없을 때 쓴다.

맞서는 힘(긴장)

  • 디버깅·출처 추적의 쉬움 vs 병렬화 불가로 인한 지연
  • 단계 분리의 품질 이점 vs 단계가 늘수록 오류 누적
  • 고정 순서의 예측 가능성 vs 예외 경로 처리의 경직성

해법

업무 절차를 단계로 나누고 각 단계의 입력·출력 형식을 정해 앞 단계 출력을 다음 단계에 넘긴다. 단계 사이에 형식 검증(스키마)을 두어 오류가 번지기 전에 멈추고, 멈춘 건은 C1 검토 큐나 C3 재처리로 보낸다. 판정·산수 단계는 가능한 한 규칙(B′9)으로 두고 모델은 추출·서술 단계만 맡긴다. 단계 순서를 AI가 바꿔야 한다면 B′8이나 B′7로 옮긴다.

이럴 때 쓴다

  • 업무 절차가 고정 순서로 정해져 있을 때
  • 각 단계를 따로 검증·추적해야 할 때(유형 ② 접수·심사, ⑧ 취합·변환)
  • 단일 에이전트에서 시작하는 첫 배선일 때

이럴 때는 쓰지 않는다

  • 하위 작업이 서로 독립이라 동시에 돌려야 지연이 줄 때(B′3)
  • 입력에 따라 AI가 다음 도구를 골라야 할 때(B′7)
  • 긴 업무를 계획부터 세워야 할 때(B′8)

얻는 것

  • 디버깅과 출처 추적이 쉬움
  • 단계별 품질 검증 가능
  • 구현이 가장 단순

점검표

  • 단계마다 입력·출력 형식이 정의되어 있는가
  • 단계 사이 검증에서 실패하면 멈추는가
  • 단계별 중간 결과를 추적할 수 있는가

구조 — 참여 부품

  • 단계 처리기 — 각 단계에서 추출·변환·작성 수행
  • 단계 간 형식 검증 — 다음 단계로 넘기기 전 스키마 확인
  • C3 상태 머신·롤백 — 실패 단계 재처리

B′9 결정론 판정 게이트 제어 흐름

판정 모델(LLM·VLM·비전 분류기·통계 모델)은 정형 출력만 내고, 규칙 엔진이 최종 판정·산수·분기를 하며, 사람 또는 시스템이 확정한다.

PAX 사례 17건이 이 부품을 쓴다

맥락

법정 기준·지침 임계값이 있는 심사·점검·감시 업무에 쓴다. B4 인식 파이프라인, B5 감지·경보(유형 ③), B2 위험 예측(유형 ⑩)에서 판정 단계를 맡는다. v0.6에서 LLM·VLM 한정으로 신설하고 R11에서 판정 모델 일반으로 확장했다.

맞서는 힘(긴장)

  • 모델의 추출 유연성 vs 판정의 재현성·설명 가능성
  • 기준 변경 시 설정만 바꾸는 편의 vs 규칙 유지보수 부담
  • 강등·기각의 보수성 vs 자동 처리율

해법

판정 모델은 JSON 스키마로 제약된 정형 출력(추출값·근거 문장·신뢰도·확률)만 낸다. 규칙 엔진이 기준 임계값·산식·대조로 판정과 산수를 수행하고, 기준이 바뀌면 재학습 없이 설정만 고친다. 서버가 근거 문장을 원문과 재대조해 '문서확인/AI추정/문서에없음'으로 강등하는 비루프 검증을 둘 수 있다. 불합격·저신뢰 건은 재생성하지 않고 기각·강등해 사람 확정(C1)으로 보낸다.

이럴 때 쓴다

  • 판정 기준이 법령·지침·임계값으로 정해져 있을 때
  • 판정 재현성과 근거 설명이 필요할 때
  • 기준 변경 시 재학습 없이 설정만 바꾸고 싶을 때

이럴 때는 쓰지 않는다

  • 판정 기준을 규칙으로 적을 수 없는 서술형 평가일 때
  • 불통과 시 다시 생성해 품질을 올려야 할 때(B′5)
  • 추출 없이 규칙만으로 판정할 수 있을 때(B0)

얻는 것

  • 임의 확정·환각 수치 방지
  • 기준 변경 시 재학습 불필요
  • 판정 근거를 조항 단위로 설명 가능
  • C2 자동 분기의 신뢰 근거

점검표

  • 모델이 판정·산수를 하지 않는가
  • 기준 변경이 재학습 없이 설정 변경으로 가능한가
  • 저신뢰·근거 불일치 건이 강등되어 사람에게 가는가
  • 같은 입력에 같은 판정이 나오는가

구조 — 참여 부품

  • 판정 모델 — 정형 출력(추출값·근거·신뢰도·확률)만 생성
  • 규칙 엔진 — 임계값·산식·대조로 판정과 산수
  • C5 가드레일 필터 — 구조적 출력 제약·스키마 검증, 근거 재대조
  • C1 검토 큐 — 강등·저신뢰 건의 사람 확정

변형

  • 비전·통계 판정 모델형: 비전 분류기·통계 모델 확률을 규칙이 판정한다(R11 확장)
  • 근거 재대조 강등형: 근거 문장을 원문과 재대조해 문서확인/AI추정/문서에없음으로 강등한다(비루프 검증)

  • 정형 IR → 결정론 컴파일: 에이전트가 정형 중간표현을 내고 결정론적으로 변환한다(§13 해외 참고)

이럴 때 쓴다

맥락

D8.4 대조·점검 서비스 블록

법령·규정·서식·인용·근태·보안 기준과 대조해 확인할 대상을 먼저 골라 주는 내부 운영 블록이다. "최종 판단은 사람"이 가장 자주 붙는다.

PAX 사례 81건이 이 부품을 쓴다

맥락

기관 내부 문서·자료를 기준과 대조하는 업무. §7.3 유형 ⑦ 대조·점검 도우미(D8.4, P0~P1)와 유형 ⑩ 위험 예측·표적 선별(D6·D3·D8.4)의 무대. PAX 81건(주 부품 B0 73%, B1 12%), 감사·법무 25건·문서·기안 12건.

맞서는 힘(긴장)

  • 점검 범위 확대 vs 오탐으로 인한 확인 부담
  • 규칙 점검의 결정성 vs LLM 대조의 유연성
  • 점검 대상이 점검기를 속이는 위협 vs 자동 점검
  • 출처 대조의 엄격성 vs 원문 접근 권한(공공 API 인가)

해법

기준이 규칙으로 옮겨지면 B0 규칙 점검기로, 해석이 필요하면 B3 법령 접지로 대조한다. 기준 원문은 A3 공공 API(법령·판례)에서 가져와 C5 출처 검증으로 인용이 실제 원문과 일치하는지 확인한다. 결과는 판정이 아니라 "확인할 대상 목록"으로 내고, C1으로 "최종 판단은 사람"을 명시하며, F7 한계와 F1 출처를 붙인다. 점검 대상 문서·코드가 점검기를 속이지 못하게 대상별 격리(S6)나 고정 규칙 실행(S4)을 쓰고, 코드 점검이면 S9 샌드박스를 둔다. C9 평가 세트로 누락률을 잰다.

이럴 때 쓴다

  • 문서·자료를 법령·규정·서식과 한 줄씩 대조하는 업무
  • 인용·근거가 원문과 맞는지 확인해야 할 때
  • 점검 대상이 많아 확인 대상을 먼저 좁혀야 할 때

이럴 때는 쓰지 않는다

  • 국민 신청 건의 자격 판정이면 D3
  • 현장 시설을 관측해 점검하면 D6
  • 대조 없이 자료를 찾아 보여 주면 D8.1

얻는 것

  • 대조 시간 단축과 누락 감소
  • 사람 판단을 확인 대상에 집중
  • 인용 오류의 사전 차단

점검표

  • 결과가 판정이 아닌 확인 대상으로 표시되는가
  • 근거 원문 출처가 연결되는가
  • 누락률을 평가 세트로 재는가
  • 점검 대상 속 문장이 점검 결과를 바꾸지 못하는가

구조 — 참여 부품

  • 담당자 — 확인 대상을 검토해 최종 판단
  • B0 결정적 도구(규칙 점검기) — 규칙화된 기준으로 대조

  • C1 검토 큐 — 최종 판단은 사람

  • 인가·검증 절차의 통제 vs 에이전트 루프의 병목(PAX 공공API 진단)

해법

기반을 새로 만들기 전에 범정부 AI 공통기반(모델), 공공데이터포털·법령 API(데이터), 모두의 AI 실험실·공공 깃랩(개발·실험 환경)에서 먼저 찾아 소비한다. 인증은 GPKI·디지털원패스 같은 연합 신원(Federated Identity)으로 위임하고, 공공 API 응답은 출처·조회 시각과 함께 업무 부품에 넘긴다. 에이전트가 부를 수 있게 하려면 A8 MCP 서버로 감싸고, 결과를 재가공해 기준선으로 고정하면 A1을 더한다. 기관이 만든 도구는 공공 깃랩에 등재해 다음 기관의 Provider가 되게 한다.

이럴 때 쓴다

  • 모델·데이터·개발 환경을 기관이 새로 만들려 할 때 — 먼저 Provider 확인
  • 법령·기준 원문을 최신으로 대조해야 하는 유형 7
  • 여러 부서가 같은 기반을 따로 만들고 있을 때(X3 교정)

이럴 때는 쓰지 않는다

  • 필요한 모델·데이터가 공공 Provider에 없을 때(만들고 레지스트리에 올림)
  • 타 기관 데이터를 계약·키 매핑으로 결합하는 경우는 A4

얻는 것

  • 기관별 중복 구축 방지(X3 교정)
  • 공인된 원천 데이터·모델 사용
  • 등재를 통해 전이 경로 확보

점검표

  • 같은 기반을 기관 안에서 따로 만들지 않았는가
  • 공공 API 응답의 출처·조회 시각이 결과에 남는가
  • API 장애·변경 시 어떻게 되는지 답할 수 있는가
  • 만든 도구가 공공 깃랩 등에 등재되었는가

구조 — 참여 부품

  • 공공 Provider — 범정부 AI 공통기반·공공데이터포털·모두의 AI 실험실·공공 깃랩
  • 연합 신원 인증 — GPKI·디지털원패스 등으로 호출 주체를 확인
  • 소비 부품(B·A2·A8) — Provider를 직접 만들지 않고 가져다 씀
  • S1 AI 게이트웨이·단일 진입점 — 공공 인증을 위임받아 호출을 통제

변형

C1 검토 큐 운영 컴포넌트

AI 산출물이 다음 단계로 넘어가기 전에 사람이 맞고 틀림을 확인·수정·확정하는 대기열을 두어, 오류가 업무 결과로 흘러가지 않게 한다.

PAX 사례 46건이 이 부품을 쓴다

맥락

AI 산출물이 공문·처분·대민 안내·기록으로 이어지는 모든 B 부품(B1 코파일럿, B4 인식 파이프라인, B2 예측기, B7 콘텐츠 생성기 등). 이용자 본인이 최종 확정자인 자기서비스형 도구도 포함한다(R16).

맞서는 힘(긴장)

  • 정확성·책임성 vs 처리 속도(전건 검토는 자동화 이득을 깎는다)
  • 검토자의 숙련 vs 자동화 편향(AI 결과를 그대로 승인하는 경향)
  • 전건 검토의 안전 vs 위험도별 분기(C2)로 가야 하는 효율 압력

해법

AI 산출물에 신뢰도·근거를 붙여 검토 대기열에 올리고, 검토자가 승인·수정·반려 중 하나를 고르게 한다. 수정·반려 내역은 C4 감사 로그에 남겨 수정률을 집계하고 C6 환류의 입력으로 쓴다. 검토 화면은 원문 위치·근거를 함께 보여 줘 확인 비용을 줄인다. 전건 검토로 시작하되, 수정률 실측이 쌓이면 C2 위험도 라우터로 저위험 건을 자동 종결하는 단계로 옮긴다.

이럴 때 쓴다

  • AI 산출물이 공문·처분·대민 안내로 그대로 이어질 때
  • E4가 P1 이상이고 되돌리는 데 사람 시간이 많이 드는 조치가 있을 때
  • 서비스 유형 ② 접수·심사, ④ 기안 코파일럿, ⑥ 콘텐츠 제작, ⑦ 대조·점검, ⑩ 위험 예측, ⑪ 추천·매칭, ⑫ 개발 코파일럿처럼 C1이 필수인 유형

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 런타임 AI 산출물이 없을 때
  • 쉽게 되돌릴 수 있고 저위험인 조치를 이미 C2로 자동 종결하도록 실측 근거를 갖춘 구간(전건 검토를 영원히 남기지 않는다)

얻는 것

  • 오류가 업무 결과로 나가기 전에 차단
  • 책임 소재가 명확해짐
  • 수정 내역이 C4 지표와 C6 환류의 원천 데이터가 됨

점검표

  • AI 산출물이 확정 전 상태로 머무는 지점이 명시되어 있는가
  • 검토자와 승인·수정·반려 선택지가 정해져 있는가
  • 검토 결정과 수정 내역이 로그로 남는가
  • 실증 기간의 검토·수정 건수가 기록되어 있는가
  • 전건 검토에서 분기로 옮길 조건이 정해져 있는가

구조 — 참여 부품

  • 검토 대기열 — AI 산출물을 확정 전 상태로 보관하고 검토자에게 배정
  • 검토자(담당자 또는 이용자 본인) — 승인·수정·반려를 결정하는 최종 책임자
  • F2 편집 가능한 출력 — 검토자가 산출물을 직접 고치는 화면
  • C4 감사 로그·지표 — 검토 결정과 수정 내역을 적재해 수정률로 집계

변형

  • 전건 검토형: 모든 AI 산출물을 담당자가 확인·확정
  • 예외 검수형: 정상 건은 일괄 승인하고 저신뢰 항목만 개별 검수하는 검수 UI
  • 파이프라인 내장 관문형: 멀티에이전트·다단계 파이프라인의 각 관문에 승인·보완·재작성 선택지를 둠
  • 자기서비스형: 이용자 본인이 최종 확정자인 HITL. 실제 운영 중이면 C1 present(R16)
  • 심의 게이트: 팩트체크·법무·윤리처럼 제3자 전문가가 수행하는 승인 게이트

참조 구현 예

  • PAX 9dc1a7081bc869b1 — 광진구 — 담당자·팀장 최종 판단 책임 등 4대 관리 원칙 명문화

C5 가드레일 필터 운영 컴포넌트

개인정보·환각·편향·형식 오류가 프롬프트나 산출물에 들어가지 못하게 시스템이 경계에서 걸러낸다. 비식별 전처리, 출처 검증, 구조적 출력 제약이 대표 변형이다.

PAX 사례 44건이 이 부품을 쓴다

맥락

외부 모델을 부르거나 대민에 답하는 모든 B 부품. 특히 E2 해외 상용 API, E5 S 이상 데이터, B3 지식 접지 상담, 유형 ① 대민 상담, ④ 기안, ⑥ 콘텐츠, ⑦ 대조·점검, ⑨ 인수인계, ⑬ 비식별·정제 도구.

맞서는 힘(긴장)

  • 차단의 엄격함 vs 과잉 차단으로 인한 유용성 저하
  • 비식별 강도 vs 문맥 보존
  • 결정적 검증의 신뢰성 vs 구현 범위

해법

프롬프트가 기관 밖으로 나가기 전 PII를 마스킹하고 원복 키를 보관하는 비식별 전처리기를 둔다. 응답에는 인용을 원본(법령정보센터·통계표 등)과 대조하는 출처 검증기와, JSON 스키마·허용 목록 같은 구조적 출력 제약을 건다. 근거가 없으면 답하지 않거나 '확인 필요'로 표시한다. 차단 사유는 C4에 남기고, 이용자에게는 F1 출처와 F7 한계 안내로 보인다. 사람이 하는 팩트체크·법무 심의는 C5가 아니라 C1.2에 둔다.

이럴 때 쓴다

  • E2 해외 상용 API로 행정망 본문이 외부로 나갈 때(필수)
  • E5 S 이상 개인정보·민감정보를 다룰 때
  • B3 대민 응답처럼 인용·수치의 정확성이 신뢰의 핵심일 때
  • C5가 필수인 유형 ①④⑥⑦⑨⑪⑬

이럴 때는 쓰지 않는다

  • E1 로컬 PC 완결로 데이터가 밖으로 나가지 않을 때 비식별은 불필요해질 수 있다(§5 매트릭스, 단 출처 검증은 별개)
  • 사람이 수행하는 심의만 있을 때(C1.2로 태그)
  • 적대적 입력 탐지가 목적일 때(S8)

얻는 것

  • 개인정보 외부 유출 차단
  • 환각 인용 감소
  • 상용 API 사용 조건 충족

점검표

  • 외부 전송 전 무엇이 걸러지는지 답할 수 있는가
  • 인용이 원본과 대조되는가
  • 근거 없을 때의 동작이 정해져 있는가
  • 차단 사유가 기록되는가

구조 — 참여 부품

  • 비식별 전처리기 — 외부 전송 전 PII 마스킹과 원복
  • 출처 검증기 — 인용을 원본과 대조해 환각을 걸러냄
  • 출력 제약 — 스키마·허용 목록·금칙어로 출력 형식 제한
  • F1 출처 표시 — 검증된 출처를 이용자에게 보임

변형

  • 로컬 비식별 전처리기: 외부 전송 전 PII 마스킹·원복(PAX에서 독립 부품으로 확인)

X13 도구 출력이 지시가 되는 에이전트 안티패턴

검색 결과·첨부·API 응답을 읽은 모델이 그 안의 문장을 새 명령으로 받아 도구를 부르는 구조를, 탐지 필터 하나로 지키려는 함정이다.

맥락

E4가 P2 이상(시스템 쓰기·처분 보조)이면서 민원 입력·제출 서류·웹 문서·타 기관 API 응답 같은 신뢰 불가 입력을 읽는 에이전트. 특히 B6·5b 데이터 에이전트.

맞서는 힘(긴장)

  • 범용 에이전트의 유연성 vs 신뢰 불가 입력 뒤의 행동 제약
  • 단일 LLM 구조의 단순함 vs 격리·계획 고정의 설계 비용
  • 탐지 필터의 손쉬움 vs 증명 가능한 보증

해법

과제의 AI가 읽는 입력 중 기관 밖에서 작성된 것을 untrusted_inputs로 나열하고, §4.2 신뢰 불가 입력 규칙대로 S4 행동 선택기(미리 정한 행동 중 선택만, 결과가 LLM으로 돌아가지 않음), S5 계획 후 실행(외부 데이터를 읽기 전에 도구 호출 계획을 고정), S6 격리 LLM(도구 있는 LLM은 외부 데이터를 읽지 않고, 읽는 LLM은 도구가 없음) 중 하나를 갖춘다. S3 컨텍스트 방화벽과 S8 독립 검증기는 보조로 붙이되 S8만으로는 규칙을 충족하지 못한다. C8 승인 게이트도 신뢰 불가 입력 규칙의 대체 통제로 인정되지 않는다(R6). 그 전 단계에서는 E4를 P0~P1 읽기·산출물 범위에 묶어 두는 것이 곧 보안이다.

이럴 때 쓴다

  • E4가 P2 이상이고 untrusted_inputs가 비어 있지 않은데 S4·S5·S6이 모두 없다(신뢰 불가 입력 규칙 위반)
  • 외부 문서를 읽는 LLM이 같은 컨텍스트에서 쓰기 도구를 호출할 수 있다
  • 인젝션 대책이 탐지 필터·프롬프트 경고문뿐이다
  • 읽은 텍스트 중 어떤 것이 어떤 도구를 부를 수 있는지 답하지 못한다

이럴 때는 쓰지 않는다

  • E4가 P0~P1로 읽기·산출물 생성에만 묶여 도구 호출·시스템 쓰기가 없는 경우(S4·S5·S6 판정 전제 불충족, R6)
  • S4·S5·S6 중 하나가 구조적으로 갖춰진 경우(보안 목적 서술이 없어도 구조가 일치하면 충족)
  • AI가 읽는 입력이 모두 기관 내부에서 작성된 경우

얻는 것

  • 단일 LLM 범용 에이전트로 구조가 단순하다
  • 새 입력·새 도구를 자유롭게 붙인다

점검표

  • untrusted_inputs가 나열되어 있는가
  • 신뢰 불가 입력을 읽은 LLM이 쓰기 도구를 직접 부를 수 없는가
  • S4·S5·S6 중 하나가 구조로 구현되어 있는가
  • S8 탐지를 유일한 방어로 두지 않았는가

구조 — 참여 부품

  • S4 행동 선택기 — LLM이 정해진 행동 중 선택만 하게 제약
  • S5 계획 후 실행·코드 후 실행 — 외부 데이터를 읽기 전에 도구 계획 고정
  • S6 격리 LLM·맵리듀스 — 읽는 LLM과 도구 있는 LLM을 분리
  • S8 독립 검증기·이중 심판 — 보조 탐지. 단독으로는 보증이 아님

변형

  • 문서 속 지시: 첨부·제출 서류 안의 문장대로 에이전트가 도구를 호출
  • API 응답 오염: 타 기관 API·웹 검색 결과에 섞인 지시가 후속 행동을 바꿈
  • 탐지 단독 방어: 인젝션 탐지 필터(S8) 하나만 두고 구조적 제약이 없음

관련 부품

X16 기준을 노출하는 위조 탐지 안티패턴

진위 판정 근거를 이용자 화면에 그대로 보여 줘 위조범이 탐지 기준을 역추적하게 만드는 함정이다. F9 근거 표시가 적대적 접점에서는 취약점이 된다.

맥락

D3 자격·심사, D2 접수·제출에서 제출 서류·이미지의 진위를 판정하는 B4 인식 파이프라인·B2 분류기. 이용자 중 일부가 탐지를 회피하려는 동기를 가진 경우.

맞서는 힘(긴장)

  • 설명 가능성·투명성 vs 적대적 이용자의 기준 역추적
  • 이용자 자기확인 편의 vs 판정 기준 보호
  • 행정 절차상 사유 고지 vs 탐지 성능 유지

해법

F9 판정 근거·기여도 표시를 역할별로 나눈다. 이용자 화면에는 '정상/위조의심'만 노출하고, 의심 부위·사유 코드·기여도 같은 세부 근거는 관리자 화면에만 보여 준다(근거 은닉, anti-oracle — 카탈로그가 S 계층 후보로 둔 반대편 부품). 관리자 화면 접근은 C8 권한 경계로 제한하고, '위조의심' 건은 C1 검토 큐에서 담당자가 세부 근거를 보고 확정한다. 이용자에게는 F7 한계·신뢰도 안내로 추가 확인 절차를 알리고, 반복 제출·판정 이력은 C4·S10에 남겨 역추적 시도를 탐지할 근거로 삼는다.

이럴 때 쓴다

  • 진위·위조 판정 결과와 함께 세부 근거(의심 부위·사유 코드·점수)가 제출자 화면에 표시된다
  • 제출자가 근거를 보고 수정해 반복 재제출할 수 있다
  • 이용자 중 탐지 회피 동기를 가진 적대자가 있을 수 있다
  • 관리자와 이용자의 판정 화면이 같다

이럴 때는 쓰지 않는다

  • 내부 담당자만 쓰는 판독 도구로 제출자에게 결과가 노출되지 않는 경우
  • 이용자가 적대자가 아닌 접점(예: 내부 품질 점검, 자기 서류 오류 안내)에서 F9로 근거를 보여 주는 경우 — 이때 F9는 정상 부품이다
  • 이용자에게 '정상/위조의심'만 보여 주고 세부 근거는 관리자 화면에 둔 경우

얻는 것

  • 투명성·설명 가능성 요구를 쉽게 충족한다
  • 선의의 이용자가 오류를 스스로 고칠 수 있다

점검표

  • 제출자 화면에 세부 판정 근거가 노출되지 않는가
  • 세부 근거가 관리자 화면에서만 보이고 접근이 제한되는가
  • 위조의심 건을 사람이 확정하는가
  • 반복 재제출 이력이 기록되는가

구조 — 참여 부품

  • F9 판정 근거·기여도 표시 — 적대적 접점에서 역할별로 나눠야 할 설명
  • 근거 은닉(anti-oracle, S 후보) — 이용자에게는 판정만, 세부 근거는 관리자에게만
  • C1 검토 큐 — 위조의심 건을 담당자가 세부 근거로 확정
  • C8 권한 경계 — 관리자 화면 접근 제한

변형

  • 의심 부위 표시형: 이용자 화면에 BBox·히트맵으로 위조 의심 부위를 표시
  • 사유 코드 노출형: 반려 사유 코드·점수를 이용자에게 그대로 반환
  • 무제한 재제출형: 근거를 보고 고쳐 무제한 재제출할 수 있어 기준 탐색이 가능
