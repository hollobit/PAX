판정 근거

내부망 로컬 LLM 하나로 사규검색(그래프RAG), 문서작성(HWPX), 비전 인식 안전분석, AI 광고 도안 심의, AI 리터러시 퀴즈 등을 묶은 사내 AI 체험 플랫폼이 팀 단위 바이브 코딩으로 만들어졌고, 2026년 8월 코레일유통이 'AX Playground'로 공식 출시했다. 여러 B 부품이 섞여 있어 R1에 따라 대표 기능인 그래프RAG 사내지식 검색을 B3(변형: 폐쇄망 로컬 RAG)로 주 부품 삼고, 비전 안전분석(B5)·광고 도안 판정(B4)을 secondary로 둔다. 여러 기능 메뉴로 분기하므로 B′2. 그래프RAG가 A6, 로컬 LLM 하나로 전체를 서빙해 A2.2, HWPX 작성이 A10, 바이브코딩 자체제작이 A7. '외부 네트워크 호출 제로'와 '로컬 LLM 하나'로 모든 기능을 서빙하는 구조는 S1과 형태는 일치하나 인증·상한 서술이 없어 structural로만 표시, '관리자 설정을 통한 기관별 커스터마이징'은 C8로 implemented. 광고 도안 업로드가 F5.

구현 가이드

주 패턴 B3 지식 접지 상담을 구현할 때

구현 단계

  1. 대표 질문·정답·채점 기준으로 C9 평가 세트를 먼저 만든다.
  2. A1로 코퍼스를 정리하고 데이터 등급(E5)과 공개 범위를 메타로 붙인다. 등급 문서가 섞이면 S2 권한 인식 검색을 둔다.
  3. E1에 맞게 임베딩·벡터DB·모델 위치를 정한다(폐쇄망이면 전부 로컬, A2.2·A2.4).
  4. 근거 밖 답변 금지·출처 상시 표시·근거 없으면 이관하는 규칙을 C5·F1·B′2로 구현한다.
  5. 검색 품질 3패턴을 하나씩 붙이며 C9로 재고, 문서 갱신 주기를 C6으로 운영한다.

점검표

  • 답마다 출처가 표시되는가
  • 근거가 없을 때 답하지 않고 이관하는가
  • 평가 세트로 검색·답변 품질을 재고 있는가
  • 코퍼스 갱신 주기와 책임자가 정해져 있는가

환경 조건

E1 폐쇄망·행정망이면 임베딩·벡터DB·모델 전부 로컬(A2.2 주권형 또는 A2.4 내부망 프록시 + 로컬 임베딩). E2 해외 상용 API면 C5 비식별 전처리와 C7 폴백이 필수다. E4는 P0~P1이 기본이다. 신뢰 불가 입력(민원 입력·공개 웹)을 읽고 P2 이상이면 S6 문서별 격리와 S2가 필요하다. 대민형은 S4·S7이 권장된다(§7.4).

주의할 점

  • 평가 없이 붙이면 품질을 알 수 없음(X10)
  • 코퍼스 갱신이 멈추면 오답이 됨
  • 부서마다 따로 만들면 중복(X3)
  • 대민형은 인젝션·유출 위협에 노출

기본 배선 예

A1 → A2.2 → B3 (B′7 · B′2) → F1 · B3 → C2 → 담당자 이관

보완이 필요한 필수 부품

이 조합에서 카탈로그가 함께 갖추라고 권하는 부품 가운데 아직 확인되지 않은 것이다.

  • A1 데이터 자산 서비스 흩어진 업무 기록을 정제·라벨링해 AI 부품이 붙여 쓸 수 있는 데이터셋·라벨·데이터 사전 형태의 기준선으로 제공한다.
  • C5 가드레일 필터 개인정보·환각·편향·형식 오류가 프롬프트나 산출물에 들어가지 못하게 시스템이 경계에서 걸러낸다. 비식별 전처리, 출처 검증, 구조적 출력 제약이 대표 변형이다.

피해야 할 안티패턴

  • X3 부서마다 챗봇 같은 기관의 과제들이 각자 모델·벡터DB·프롬프트를 따로 만들어, 공유할 수 있는 기반 부품을 부서 수만큼 중복 구축하는 함정이다. 대처: §7.1의 두 번째 단계대로 기반 부품은 새로 만들지 말고 Provider에서 먼저 가져온다. 모델 호출은 A2 모델 서빙 계층(범정부 AI 공통기반 또는 기관 게이트웨이) 뒤로 모으고, S1 단일 진입점에서 인증·요청 상한·비용 상한·감사 기록을 일괄 적용한다. 공공 API·공공 클라우드·공공 깃랩은 A3 공공 API 제공자로 쓴다. 부서별 차이는 모델을 따로 두지 말고 A9 업무 규범 스킬과 부서 코퍼스(A1)로 표현하며, 부서·등급별 코퍼스 분리가 필요하면 S2 권한 인식 검색으로 푼다. 없어서 새로 만든 부품은 §13 참조 구현 레지스트리에 올린다.
  • X10 평가 없는 RAG, RAG 없는 튜닝 평가 세트 없이 검색을 붙여 '좋아진 것 같다'로 배포하고, 검색으로 풀릴 문제를 파인튜닝으로 푸는, 진행 경로를 건너뛰는 함정이다. 대처: §7.2 진행 경로를 순서대로 밟는다. B1 직접 프롬프트에서 시작해 두 번째 단계에서 C9 평가 세트(업무 질문·정답·채점 기준)를 먼저 만들고, 이후 A9 규범 스킬·F4, B3 지식 접지(A1 데이터 자산), B3 검색 품질(Hybrid·Rewriting·Reranker), C5 가드레일·F1 순으로 붙이며 매 단계를 C9로 잰다. A2.3 튜닝은 진행 경로의 마지막 단계로, 검색·규범 스킬로 풀리지 않는다는 것이 C9 점수로 확인됐을 때만 한다. 모델·프롬프트·설정 조합은 릴리스처럼 버전 관리한다.

맥락

맞서는 힘(긴장)

  • 탐지 재현율 vs 오탐으로 인한 경보 피로
  • 즉시 대응(자동 출력) vs 사람 확인
  • 상시 가동 요구 vs 모델·장비 장애
  • 기준 변경 시 재학습 비용 vs 설정만 바꾸는 규칙 분리

해법

이럴 때 쓴다

  • 기존 CCTV·센서 스트림을 재사용할 수 있을 때
  • 등급별 대응 절차(자동·이관)를 정의할 수 있을 때

이럴 때는 쓰지 않는다

  • 배치로 들어온 영상·서류를 판독·구조화하는 일이면(B4)
  • 과거 데이터로 점검 대상을 선별하는 일이면(B2)
  • Fail-safe와 조치 기록을 운영할 체계가 없을 때

얻는 것

  • 사고의 사전 인지
  • 기존 설비 재사용으로 경제적 구축
  • C2·C4·C6·C7을 갖추면 Native까지 가능

점검표

  • 탐지 모델과 판정 규칙이 분리되어 있는가
  • 장애 시 Fail-safe 경로가 있는가(C7)
  • 모든 경보와 조치가 기록되는가(C4)
  • 오탐 판별이 재학습으로 이어지는가(C6)

구조 — 참여 부품

PAX 사례 34건이 이 부품을 쓴다

맥락

접수·심사(유형 ②), 서류 진위확인, 민원 통화 정리, 실시간 자막, 원격탐사·도면 판독처럼 비정형 입력이 업무의 출발점인 경우에 쓴다. 민감 서류가 많아 행정망·로컬 모델 조건이 자주 붙는다.

맞서는 힘(긴장)

  • 자동 연결의 효율 vs 오인식이 판정으로 번지는 위험
  • 인식 정확도 vs 로컬 모델 제약(E1·E5)
  • 단계 분리의 추적 용이성 vs 단계 간 지연

해법

이럴 때 쓴다

  • 비정형 입력을 사람이 옮겨 적는 단계가 업무의 병목일 때
  • 추출값이 규칙 판정·다음 처리로 이어질 수 있을 때
  • 유형 ② 접수·심사 자동화의 기본 조립일 때

이럴 때는 쓰지 않는다

얻는 것

  • 옮겨 적기 단계 제거
  • 판정 기준이 규칙으로 남아 설명 가능
  • OCR·STT 엔진을 범정부 공통으로 공유 가능

점검표

  • 인식과 판정이 서로 다른 단계로 분리되어 있는가
  • 저신뢰 건이 보류되어 사람에게 가는가
  • 오인식 건을 되돌리는 경로가 있는가(C3)

규정·매뉴얼·FAQ·사례가 문서로 쌓인 기관에서 내부 검색·검수, 대민 자동응답, 폐쇄망 로컬 검색에 쓴다. PAX 557건에서 주 부품이 B3인 사례는 31건으로 B0·B1 다음이다. 유형 ① 대민 상담·안내의 기본 조립이기도 하다.

맞서는 힘(긴장)

  • 답변 범위 vs 환각 위험(근거 밖 답변 금지)

해법

  • 유형 ① 대민 상담·안내, 유형 ⑦ 법령 접지 점검

이럴 때는 쓰지 않는다

얻는 것

  • 반복 질의 처리 시간 단축
  • 범정부 엔진 + 기관별 코퍼스로 공유 가능

점검표

  • 평가 세트로 검색·답변 품질을 재고 있는가

B′2 라우터·디스패처 제어 흐름

요청의 의도·유형·난이도를 읽어 전문 경로·모델·도구·담당자로 보내는 배선이다. 모든 건을 같은 경로로 보내는 낭비를 막는다.

PAX 사례 23건이 이 부품을 쓴다

맥락

대민 상담(B3)의 예외 이관, 규칙 선필터로 LLM 호출 줄이기, 폐쇄망 모델과 외부 모델 사이의 모델 라우팅, 여러 MCP를 한 서버에서 경로별로 제공하는 구성에 쓴다. C2 위험도 라우터의 내부 원형이고, D4 분류·이관을 기술로 구현한 실체다.

맞서는 힘(긴장)

  • 경로 분리의 효율 vs 라우팅 오류라는 새 위험
  • 규칙 라우팅의 예측 가능성 vs 모델 라우팅의 유연성
  • 외부 모델 분기의 품질 vs 경계 통제(E1·E5)

해법

요청을 분류하는 단계(규칙·경량 모델·LLM)를 앞에 두고, 분류 결과마다 처리 경로(규칙 판정, LLM 판정, 담당자 이관, 판단 불필요)를 정한다. 경로별 처리 비율을 C4로 실측해 라우팅 품질을 보고, 분류가 불확실한 건은 사람에게 보낸다(C2·F11). 모델 라우팅은 A2 서빙 계층의 기능으로 두고 외부 모델로 나가는 분기에는 C5 비식별을 건다. 보안이 필요한 대민 접점에서는 LLM이 미리 정한 행동 중 선택만 하게 제약해 S4로 만든다.

이럴 때 쓴다

  • 요청 유형마다 처리 비용·방법이 뚜렷이 다를 때
  • 답할 수 없는 건을 담당자로 이관해야 할 때(유형 ① 대민 상담)
  • LLM 호출 비용을 줄여야 할 때

이럴 때는 쓰지 않는다

  • 요청 유형이 하나뿐일 때
  • 분류 오류의 비용이 큰데 분류 품질을 잴 방법이 없을 때
  • 라우팅 대신 규칙으로 판정 모델 호출 대상 자체를 좁히는 구조일 때(B′10)

얻는 것

  • 호출 비용 절감
  • 답할 수 없는 건의 이관
  • 경로별 전문화

점검표

  • 경로별 처리 비율을 실측하는가
  • 분류가 불확실할 때 사람에게 가는 경로가 있는가
  • 외부 모델로 나가는 분기에 비식별이 걸려 있는가

구조 — 참여 부품

  • 분류기 — 의도·유형·난이도 판별(규칙 또는 모델)
  • 전문 경로 — 유형별 처리 모델·도구·규칙
  • C2 위험도 라우터 — 위험도·신뢰도 기반 사람 이관
  • C4 감사 로그·지표 — 경로별 처리 비율 실측

변형

B′1 순차 파이프라인 제어 흐름

한 단계의 출력을 다음 단계의 입력으로 넘기는 고정 순서 배선이다. 한 프롬프트에 많은 일을 몰아 시켜 품질이 떨어지는 문제를 막는다.

PAX 사례 109건이 이 부품을 쓴다

맥락

B4 인식 파이프라인의 기본 배선이며, B1·B0·B5 안에서도 흔하다. 단계 순서가 업무 절차로 미리 정해져 있고 AI가 순서를 고를 필요가 없을 때 쓴다.

맞서는 힘(긴장)

  • 디버깅·출처 추적의 쉬움 vs 병렬화 불가로 인한 지연
  • 단계 분리의 품질 이점 vs 단계가 늘수록 오류 누적
  • 고정 순서의 예측 가능성 vs 예외 경로 처리의 경직성

해법

업무 절차를 단계로 나누고 각 단계의 입력·출력 형식을 정해 앞 단계 출력을 다음 단계에 넘긴다. 단계 사이에 형식 검증(스키마)을 두어 오류가 번지기 전에 멈추고, 멈춘 건은 C1 검토 큐나 C3 재처리로 보낸다. 판정·산수 단계는 가능한 한 규칙(B′9)으로 두고 모델은 추출·서술 단계만 맡긴다. 단계 순서를 AI가 바꿔야 한다면 B′8이나 B′7로 옮긴다.

이럴 때 쓴다

  • 업무 절차가 고정 순서로 정해져 있을 때
  • 각 단계를 따로 검증·추적해야 할 때(유형 ② 접수·심사, ⑧ 취합·변환)
  • 단일 에이전트에서 시작하는 첫 배선일 때

이럴 때는 쓰지 않는다

  • 하위 작업이 서로 독립이라 동시에 돌려야 지연이 줄 때(B′3)
  • 입력에 따라 AI가 다음 도구를 골라야 할 때(B′7)
  • 긴 업무를 계획부터 세워야 할 때(B′8)

얻는 것

  • 디버깅과 출처 추적이 쉬움
  • 단계별 품질 검증 가능
  • 구현이 가장 단순

점검표

  • 단계마다 입력·출력 형식이 정의되어 있는가
  • 단계 사이 검증에서 실패하면 멈추는가
  • 단계별 중간 결과를 추적할 수 있는가

구조 — 참여 부품

  • 단계 처리기 — 각 단계에서 추출·변환·작성 수행
  • 단계 간 형식 검증 — 다음 단계로 넘기기 전 스키마 확인
  • C3 상태 머신·롤백 — 실패 단계 재처리

관련 부품

A2.2 모델 서빙 · 주권형 온프레미스 공통 서비스

맥락

  • 모델 운영·갱신 역량 vs 외부 의존 제거
  • 저사양 장비 구동 vs 모델 크기

  • E5가 S 이상인데 내부망 프록시(A2.4)를 쓸 수 없을 때
  • 현장 폐쇄망 서버에서 추론해야 하는 유형 3
  • C7의 대체 경로로 로컬 모델을 둘 때

이럴 때는 쓰지 않는다

  • 추론 인프라·운영 인력을 확보할 수 없을 때
  • 현장 기기 자체에서 돌아야 하면 A5(엣지 런타임)
  • 모델을 재학습했으면 A2.3

얻는 것

  • 데이터가 기관 밖으로 나가지 않음
  • 호출 비용이 고정비로 바뀜
  • 폐쇄망에서도 LLM 사용 가능
  • C7의 대체 경로 후보

점검표

  • 추론·임베딩 어디에서도 데이터가 망 밖으로 나가지 않는가
  • 모델 선정 근거(평가 세트 비교)가 남아 있는가
  • 반입한 모델·패키지의 무결성 검사 기록이 있는가
  • 대체 로컬 모델 또는 수동 전환 절차가 있는가

구조 — 참여 부품

  • A2 서빙 계층 — 로컬 모델을 업무 부품에 노출
  • 오픈웨이트 모델·로컬 임베딩 — 기관 안에서 추론·색인

  • S11 인제스천·공급망 검증 — 폐쇄망 반입 모델·패키지 검사

변형

  • 기관 서버형: vLLM 등으로 기관 GPU 서버에서 다수 이용자에게 서빙한다.

A6 지식그래프 서비스 공통 서비스

규정·업무 개념·관계를 온톨로지로 명시해 여러 업무 부품이 같은 개념 체계로 검색·추론하게 한다.

PAX 사례 13건이 이 부품을 쓴다

맥락

개념 관계가 답의 품질을 좌우하는 B3 지식 접지에 쓴다. 인수인계·지식 보존(유형 9)에서는 승급할 때, 대민 상담(유형 1)에서는 선택으로 붙는다.

맞서는 힘(긴장)

  • 개념 체계의 정확성 vs 온톨로지 구축·유지 비용
  • 관계 판정의 LLM 활용 vs 검증 부담
  • 기관 고유 체계 vs 범정부 공통 개념 체계

해법

규정·서식·용어집에서 개념과 관계를 추출해 온톨로지로 명시하고, 질의 API로 여러 업무 부품에 제공한다. 추출 단계에서는 원문 보정·청킹·용어 원자화 뒤 사전 필터로 LLM 관계 판정 호출을 줄이고, 병합 전에 검증자 점검을 둔다. 기준문서를 넣으면 스키마가 재구성되는 템플릿 교체형으로 만들면 다른 조직이 통째로 가져다 쓸 수 있다. B3에서는 벡터 검색과 결합해 그래프 보조 검색(GraphRAG)으로 쓴다.

이럴 때 쓴다

  • 규정 간 상위·예외·선후 관계가 답을 좌우할 때
  • 인수인계처럼 업무 구조 전체를 옮겨야 할 때(유형 9 승급)
  • 여러 업무 부품이 같은 개념 체계를 공유해야 할 때

이럴 때는 쓰지 않는다

  • 로컬 PC 완결 조건에서 파일 기반 검색으로 충분할 때
  • 문서 검색만으로 목표 품질에 닿을 때(C9로 확인)
  • 온톨로지를 유지할 담당 조직이 없을 때

얻는 것

  • 개념 관계를 반영한 검색·추론
  • 여러 부품이 같은 개념 체계 공유
  • 템플릿화하면 조직 간 이식

점검표

  • 그래프가 문서 검색만 쓸 때보다 나은지 평가 세트로 확인했는가
  • 관계 판정에 사람 검증 단계가 있는가
  • 기준문서 개정 시 갱신 절차가 있는가

구조 — 참여 부품

  • 개념·관계 추출 파이프라인 — 원문에서 개념·관계를 뽑고 사전 필터·LLM 판정으로 관계를 정함
  • 검증자 — 병합 전 관계 판정을 점검
  • 그래프 저장소·질의 API — 업무 부품에 개념 체계를 제공
  • B3 지식 접지 상담 — 그래프 보조 검색의 소비처

변형

  • 템플릿 교체형 온톨로지: 기준문서를 넣으면 업무·필드·값·관계 스키마가 재구성된다.
  • 그래프 RAG: 그래프를 검색 보조로 결합한다(코레일유통 AX플레이그라운드, PAX d8b2afa5e72012a8).
  • MCP로 서빙하는 경량 KG: 대규모 개념·관계를 단일 파일로 경량화해 원격 MCP로 노출한다(PAX 655d61608d54c98a).

참조 구현 예

  • PAX AX플레이그라운드 — 코레일유통 그래프 RAG(§6 A6 카드)
  • PAX 655d61608d54c98a — NCS 개념 53만·관계 323만 온톨로지를 경량화해 원격 MCP로 노출(§13 A6)

A10 문서 형식 어댑터 공통 서비스

HWP·HWPX·엑셀·한셀·PDF 같은 한국 공공 문서 형식을 AI 부품이 읽고(구조화) 쓰게(서식 생성) 하는 변환 계층이다.

PAX 사례 136건이 이 부품을 쓴다

맥락

문서를 입력으로 받거나 기안·보고서·취합본을 산출하는 과제라면 거의 다 쓴다. 유형 2·4·8에서는 필수 기반이고 유형 6·7에서도 쓰인다. E1 로컬 PC 조건에서 도는 경우가 많다.

맞서는 힘(긴장)

  • 형식 충실도(표·각주·조항 구조 보존) vs 파서 구현 비용
  • 로컬 처리(무반출) vs 클라우드 변환 도구의 편의
  • 기관별 서식 다양성 vs 공통 어댑터 재사용

해법

입력 쪽에서는 HWPX 압축 구조·PDF에서 조·항·호·별표 계층과 표를 보존해 구조화 텍스트·표로 바꾸고, 머리말·각주 같은 잡음을 걷어 조항 단위로 정규화한다. 출력 쪽에서는 스킬(A9)의 출력 서식을 받아 HWPX·XLSX 기안 서식을 역방향으로 생성한다. 민감 문서는 PC 밖으로 보내지 않도록 로컬에서 변환하고, 파서를 라이브러리·CLI·MCP로 함께 제공하면 다른 부품과 기관이 그대로 쓴다. 형식 변환 정확도는 C9 판정 체계로 잰다.

이럴 때 쓴다

  • 입력이 HWP·HWPX·엑셀·PDF 공공 문서일 때
  • 산출물을 기안·보고 서식으로 내보내야 할 때
  • 유형 2·4·8 조립

이럴 때는 쓰지 않는다

  • 스캔 이미지·음성처럼 인식이 필요한 입력은 B4 인식 파이프라인(OCR·STT)
  • 입출력이 이미 정형 데이터·API인 경우

얻는 것

  • 공공 문서를 AI 입력·출력으로 연결
  • 기관 간 재사용 가능한 공통 부품
  • 로컬 처리로 무반출

점검표

  • 표·조항 계층이 변환 후에도 보존되는가
  • 출력이 기관 기안 서식 그대로 열리는가
  • 민감 문서가 변환 과정에서 PC 밖으로 나가지 않는가
  • 변환 정확도 판정 기록이 있는가

구조 — 참여 부품

  • 입력 파서 — 조·항·호·표 구조를 보존해 구조화
  • 서식 생성기 — 구조화 결과를 HWPX·엑셀 서식으로 출력
  • A9 업무 규범 스킬 — 출력 서식 규범 제공
  • B3 지식 접지 상담 — 구조화된 규정을 색인해 검색

변형

  • 규정 구조 파서: HWP/HWPX·PDF 규정을 조항 단위로 정규화한다.
  • 엑셀·한셀 취합: 폐쇄망에서 엑셀·한셀 파일을 취합한다(GatherFlow).
  • 서식 출력: HWPX 직무기술서·보도자료 등 공공 서식으로 역방향 생성한다(NCS JD, ReleasePick 입력).
  • 완결형 문서 엔진: HWP/HWPX 파싱·조판·렌더링·편집·PDF 출력을 자체 구현하고 MCP·CLI로 제공한다(PAX e18d5e018e0cd10d).

A7 자체 제작 환경 공통 서비스

외부 용역 없이 기관 인력이 저작도구·AI 코딩 에이전트로 도구를 직접 만들고 고치는 제작 환경이다.

PAX 사례 317건이 이 부품을 쓴다

맥락

업무 담당자가 AI 코딩 도구·저작도구·오픈소스로 직접 만드는 과제에 쓴다. 유형 8(취합·변환 자동화)에서는 필수 기반이다. PAX 557건에서 A7이 붙고 BYO 모델을 쓰는 사례는 29건이다.

맞서는 힘(긴장)

  • 제작 속도·현장 적합성 vs 유지보수 연속성
  • 개인 역량 의존 vs 조직 인수인계
  • 무예산 제작 vs 보안 검토·기관 공식화 절차

해법

기관 인력이 AI 코딩 에이전트·저작도구·오픈소스로 직접 만들되, 처음부터 전이를 전제로 한다. 설정·데이터(연락처·업무분장 등)는 코드 밖 파일로 빼 비개발자도 고치게 하고, 작업 지시서 자체를 코딩 에이전트가 수행할 프롬프트로 설계해 제작 절차를 남긴다. MIT·Apache 등 라이선스를 명시하고 공공 깃랩(A3)이나 혁신24 자료실에 등재해 담당자가 바뀌어도 이어지게 한다. 실사용 건수로 성과를 재 기관 공식으로 올린다.

이럴 때 쓴다

  • 반복 업무를 줄이는 소규모 도구를 빠르게 만들 때
  • 용역 없이 작은 수정을 계속해야 할 때
  • 유형 8 취합·변환 자동화

이럴 때는 쓰지 않는다

  • P2 이상 시스템 쓰기·처분이 걸려 보안 검토·통제 부품이 먼저 필요한데 이를 갖출 수 없을 때
  • 라이선스·저장소·인수인계를 정할 수 없어 전이가 불가능할 때(X9 위험)

얻는 것

  • 제작 속도와 현장 적합성
  • 내부 유지보수 역량 축적
  • 무예산·소예산 제작

점검표

  • 라이선스가 명시되어 있는가
  • 저장소가 개인 PC가 아닌 공유 위치에 있는가
  • 담당자가 바뀌어도 고칠 수 있는 문서·설정 분리가 있는가
  • 실사용 지표가 있는가

구조 — 참여 부품

  • 업무 담당자 — 요구를 알고 직접 만드는 제작자
  • AI 코딩 에이전트·저작도구 — 코드·화면·워크플로 생성
  • A3 공공 깃랩·자료실 — 등재처 — 담당자 이동 후에도 이어지게
  • A9 업무 규범 스킬 — 제작 규범·지시서를 재사용 가능한 형태로

변형

  • 비개발자 바이브코딩: 교육 후 비개발 직원이 AI 코딩으로 웹앱을 만들고 실사용 지표까지 잰다.
  • 용역 탈피 단계형: 1단계는 전문기업과, 2단계는 직원이 도구를 대여해 라벨링·학습·개발을 직접 한다.
  • 오픈소스 조립형: n8n·FastAPI·Qdrant·LM Studio 등 오픈소스로 워크플로를 직접 조립하고 설정을 공유한다.
  • 사람+에이전트 작업 단위형: 작업 지시서를 코딩 에이전트 입력 프롬프트로 설계해 '사람 1인 + 에이전트 1세션' 단위로 일한다.

C8 권한 경계·킬스위치 운영 컴포넌트

AI 부품이 할 수 있는 일의 상한을 P0~P4로 못 박고, 도구별 실행 승인·읽기/쓰기 분리·속도 제한·즉시 중단 스위치를 제공한다.

PAX 사례 22건이 이 부품을 쓴다

맥락

도구를 호출하거나 시스템에 쓰는 B6 오케스트레이터, A8 MCP 서버·호스트, B8 레거시 오버레이, 처분 보조(P3) 서비스. 유형 ⑤b 데이터 에이전트, ⑨ 인수인계(접근 범위).

맞서는 힘(긴장)

  • 자동화 범위 vs 통제
  • 승인 절차의 안전 vs 이용 마찰
  • 도구 설명의 편의 vs 실제 권한과의 일치 검증 비용

해법

부품별 허용 권한 범위(P0 읽기 전용 ~ P4 자율 처분)를 정하고, 도구 목록마다 읽기/쓰기를 분리한다. 위험도가 높은 도구는 실행 전 사람 승인(C2·F6)을 받게 하고, 호출 상한(속도 제한)을 둔다. 전역 킬스위치로 즉시 중단할 수 있게 하고, 승인·실패·중단 이력을 C4에 남긴다. MCP 도구는 설명과 실제 권한이 일치하는지 A8 6축 검증으로 확인한다.

이럴 때 쓴다

  • E4 P2 이상(필수, First 관문)
  • E3 MCP·CLI 환경에서 에이전트가 도구를 호출할 때
  • B6 오케스트레이터에 상용 API를 쓰는 경우(A2 + C7 + C8 도구별 승인)
  • 유형 ⑤b-host, ⑨ 인수인계(접근 범위)

이럴 때는 쓰지 않는다

  • 도구 호출·시스템 쓰기가 없는 서술 전용 코파일럿(P1)
  • B0 결정적 도구로 AI가 행동을 고르지 않을 때

얻는 것

  • 되돌릴 수 없는 조치 방지
  • 도구 설명과 실제 권한의 불일치(X7) 예방
  • 감사 가능한 행동 기록

점검표

  • AI가 쓸 수 있는 시스템 목록을 답할 수 있는가
  • 도구별 읽기/쓰기 구분과 위험도가 있는가
  • 고위험 도구에 실행 승인이 걸려 있는가
  • 킬스위치가 있고 누가 누를 수 있는지 정해져 있는가
  • 도구 설명과 실제 권한이 일치하는가

구조 — 참여 부품

  • 권한 정책 — 부품·도구별 허용 범위(P0~P4)와 읽기/쓰기 구분
  • A8 MCP 서버·호스트 — 도구 설명과 실제 권한의 일치 검증 대상
  • F6 에이전트 행동 검토·확인 — 실행 전 이용자 승인 화면
  • 킬스위치 — 전역 즉시 중단
  • C4 감사 로그·지표 — 승인·실패·롤백·중단 이력

변형

  • 읽기 전용·쓰기 배제: 도구 세트를 읽기 전용으로 한정하거나 쓰기 기능을 설계에서 배제
  • 도구별 위험도·실행 승인: 도구마다 위험도를 평가하고 고위험 도구는 실행 전 승인
  • 판정 필드 비도달 설계: AI가 판정·업무 필드에 쓸 수 없게 코드 수준으로 분리
  • 속도 제한: 도구 호출 상한(Rate Limiter)
  • 킬스위치: 전역 즉시 중단과 기존 절차 전환

참조 구현 예

  • PAX 망분리 환경용 로컬 AI 에이전트 — 도구별 위험도 평가·실행 승인·감사 대시보드(§9, PAX 557건 태깅에서 C8이 운영 중(present)으로 확인된 2건 가운데 하나. 구현 단계까지 합치면 22건)
  • PAX 갈피 법령 MCP — 쓰기 배제 설계

S1 AI 게이트웨이·단일 진입점 보안 패턴

모든 모델·도구 호출이 하나의 진입점을 지나게 해 인증·인가·요청 상한·감사 기록·비용 상한을 일괄 적용한다.

PAX 사례 3건이 이 부품을 쓴다

맥락

상용 API(E2)나 공용 모델 서빙(A2)을 여러 과제·부서가 함께 쓰는 기관, 대민 접점처럼 외부 이용자가 호출량을 좌우하는 서비스, 데이터 조회 에이전트(유형 ⑤)처럼 도구 호출이 반복되는 구조. 카탈로그 등재 상태는 후보(PAX 557건 중 3건).

맞서는 힘(긴장)

  • 중앙 통제·가시성 vs 단일 장애점과 지연 증가
  • 요청 상한으로 비용을 막는 효과 vs 정상 업무량 급증 시 서비스 거부
  • 기관별 자율 도입 속도 vs 범정부 공통기반 경유 의무

해법

모델·도구 호출을 받는 진입점을 하나 두고, 호출마다 주체·도구·모델·토큰을 식별한다. 진입점은 A3 공공 인증(GPKI·디지털원패스 등 연합 신원)에 신원 확인을 위임하고, 주체·도구별 허용 여부와 요청 상한·비용 상한을 적용한다. 허용·거부와 호출 내역은 C4 지표와 S10 재생 기록으로 흘려 보내고 비용을 집계한다. 모델 서빙 계층(A2)의 게이트웨이와 같은 자리에 두어 과제는 진입점 뒤의 모델을 고르기만 하게 한다.

이럴 때 쓴다

  • 여러 부서·과제가 같은 상용 API나 모델을 쓰는 기관
  • 대민 접점처럼 외부 이용자 행동이 호출량을 결정하는 서비스(유형 ①의 권장 부품)
  • 데이터 조회·분석 에이전트(유형 ⑤)의 필수 부품
  • 현장 감시·경보(유형 ③)에서 경보 채널 남용을 막아야 할 때

이럴 때는 쓰지 않는다

  • 로컬 PC에서 완결되는 1인 도구로 외부 호출이 없을 때(E1 로컬 PC 완결)
  • 런타임 AI가 없는 B0 결정적 도구
  • 호출 주체가 하나뿐이고 상한이 모델 제공자 쪽에서 이미 강제되는 실험 단계 — 다만 전이 시 재장착한다

얻는 것

  • 비용 소진을 상한으로 차단
  • 무인가 호출 차단과 호출 주체 식별
  • 부서별 중복 구축(X3) 해소와 범정부 공유 가능
  • S10·C4 기록의 시작점 확보

점검표

  • 진입점을 우회하는 모델·도구 호출 경로가 남아 있지 않은가
  • 주체별 요청 상한과 비용 상한이 수치로 설정되어 있는가
  • 거부·상한 초과 이벤트가 기록되고 집계되는가
  • API 키가 진입점 밖(코드·개인 PC)에 남아 있지 않은가

구조 — 참여 부품

  • A2 모델 서빙 계층 — 같은 자리에 놓이는 모델 게이트웨이. 진입점 뒤에서 실제 모델로 중계
  • A3 공공 API 제공자·공공 인증 — GPKI·디지털원패스 등 연합 신원 위임
  • 정책·상한 엔진 — 주체·도구별 인가, 요청 상한·비용 상한 판정
  • S10 결정적 재생 — 진입점에서 시작하는 호출 추적 기록
  • C4 감사 로그·지표 — 호출량·비용·거부율 집계

변형

  • 범정부 공통기반형: 범정부 AI 공통기반이 진입점 역할을 하고 기관은 그 뒤에서 모델·도구를 소비
  • 기관 게이트웨이형: 기관 내부망에 자체 진입점을 두고 부서별 키 대신 기관 단일 키로 중계(A2.4 내부망 프록시와 결합)
  • 경보 발송 상한형: 현장 감시·경보(유형 ③)에서 모델 호출 대신 경보 발송 채널에 상한을 두는 형태

관련 부품

A2 같은 자리 — 모델 게이트웨이에 보안 기능을 얹은 형태 · S10 기록처 — 진입점에서 재생 기록이 시작됨 · C8 짝 — S1이 진입점 일괄 통제, C8이 도구별 권한 · S5 짝 — 데이터 조회 에이전트(유형 ⑤)의 필수 조합 S5 + S1 · C7 보완 — 단일 진입점의 장애 대비 폴백

F5 참고자료 첨부 상호작용 패턴

이용자가 파일을 붙여 답의 범위를 좁힌다. A10 어댑터(HWPX·PDF)가 뒤에서 받치고, C5 비식별이 첨부 직후에 걸린다.

PAX 사례 15건이 이 부품을 쓴다

맥락

B1 코파일럿, B3 상담에서 이용자 문서를 범위로 쓰는 경우. 유형 ④ 기안 코파일럿의 필수 상호작용. 기관 밖에서 작성된 첨부물은 신뢰 불가 입력이다.

맞서는 힘(긴장)

  • 범위 지정의 정확성 vs 첨부 내 개인정보 유출
  • 첨부 형식 다양성 vs 파싱 품질
  • 첨부 편의 vs 간접 인젝션 표면

해법

파일 업로드로 답의 범위를 지정하게 하고, A10 어댑터로 HWPX·PDF·엑셀을 구조를 보존해 읽는다. 첨부 직후 C5 비식별을 거친 뒤 모델에 넘긴다. 외부에서 작성된 첨부는 신뢰 불가 입력으로 표시하고, 도구 호출이 있으면 S3·S6로 격리한다.

이럴 때 쓴다

  • 기관 코퍼스에 없는 이용자 문서를 근거로 해야 할 때
  • 유형 ④ 기안 코파일럿(F5 필수)

이럴 때는 쓰지 않는다

  • 기관 코퍼스 접지만으로 충분한 대민 상담(B3)
  • C5 비식별·A10 어댑터 없이 개인정보 문서를 외부 API로 보내게 되는 경우(먼저 C5)

얻는 것

  • 답의 범위가 이용자 의도에 맞음
  • 복사·붙여넣기로 인한 형식 손상 감소

점검표

  • HWPX·PDF가 형식을 유지해 파싱되는가
  • 첨부 직후 비식별이 걸리는가
  • 외부 첨부를 신뢰 불가 입력으로 취급하는가

구조 — 참여 부품

  • A10 문서 형식 어댑터 — HWPX·PDF·엑셀 파싱
  • C5 가드레일 필터 — 첨부 직후 비식별
  • S3 컨텍스트 방화벽 — 첨부 내용을 신뢰 구역과 분리

변형

  • 단일 문서 범위 지정: 첨부한 문서만 근거로 답
  • 서식 첨부: 기관 서식을 붙여 출력 형식을 지정

관련 부품

D8.1 탐색·조회 서비스 블록

데이터·법령·공고·선례·타 지역 사례를 찾아 담당자 화면에 놓는 내부 운영 블록이다. B0 탐색·시각화, MCP 도구 제공, B3가 전형 부품이다.

PAX 사례 176건이 이 부품을 쓴다

맥락

기관 내부 담당자가 자료를 찾아 보는 업무. §7.3 유형 ⑤b 데이터 에이전트(D8.1, P0)와 ⑤a 분석 대시보드·브리핑(D8.1, P0~P1)의 무대. PAX 176건(주 부품 B0 80%, B3 10%).

맞서는 힘(긴장)

  • 검색 편의 vs 출처·기준 시점 확인
  • 자연어 질의 vs 질의 조작·도구 출력 인젝션
  • 대시보드 고정 화면 vs 에이전트의 유연한 질의
  • MCP 서버 수 vs 실제 업무 호출(X8)

해법

답이 원천 데이터에서 나오게 한다. 공공데이터·통계는 A8 MCP 서버나 A3 공공 API로 도구화하고, 호스트 쪽 에이전트는 B′7 ReAct 도구 루프로 조회하되 C8로 읽기 전용에 묶는다. 결과에는 F1 출처(통계표 ID)와 조회 시점을 붙이고, 도구 호출은 C4로 추적한다. 도구 출력이 새 지시가 되지 않도록 S5 계획 후 실행과 S1 비용 상한을 둔다. 에이전트가 필요 없으면 B0 대시보드·검색기로 끝내고(5a-agg), LLM이 해설을 붙이면 5a-brief로 C9·F9를 더한다(R19). MCP 서버만 만드는 사례는 5b-server로 A8·S11만 필수다(R18).

이럴 때 쓴다

  • 담당자가 흩어진 데이터·법령·공고·선례를 찾느라 시간을 쓸 때
  • 공공데이터·통계를 자연어로 조회해야 할 때
  • 다른 지역·기관 사례를 모아 봐야 할 때

이럴 때는 쓰지 않는다

  • 찾은 문서에서 할 일·핵심을 뽑으면 D8.2
  • 규정·기준과 대조해 확인 대상을 고르면 D8.4
  • 국민이 서비스를 찾으면 D1

얻는 것

  • 자료 찾는 시간 절감
  • 출처·시점이 붙은 근거 확보
  • 공공데이터 MCP의 재사용

점검표

  • 결과마다 원천 출처와 기준 시점이 보이는가
  • 도구 권한이 읽기 전용으로 묶여 있는가
  • 도구 호출 순서를 나중에 볼 수 있는가
  • MCP 서버가 실제 업무에서 호출되는지 재는가

구조 — 참여 부품

  • 담당자 — 자료를 찾고 결과를 업무에 씀
  • A8 MCP 서버·호스트 — 공공데이터·통계를 도구로 노출
  • B0 결정적 도구(탐색·시각화) — 검색기·대시보드
  • B6 도구 호출 에이전트 — 로컬 MCP 호스트로 조회·차트 생성
  • C8 권한 경계 — 읽기 전용 제한
  • F1 출처 표시 — 통계표 ID·출처·시점 표시

변형

  • 검색·대시보드형(비LLM): B0 탐색·시각화. 유형 5a-agg(필수 A1·F2·C4, R19).
  • 브리핑형: LLM이 조회 결과를 요약·해설. 유형 5a-brief(필수 A2.1|A2.2|A2.6·F9·C9, R19).
  • MCP 서버 제공형: 공공데이터·법령을 MCP로 노출하는 서버 자체. 5b-server(필수 A8·S11, R18).
  • 데이터 에이전트형: 로컬 MCP 호스트가 도구를 불러 조회·차트 생성. 5b-host(필수 C4·F1·S5|S6, R18).

참조 구현 예

  • 망분리 환경용 로컬 AI 에이전트 + KOSIS 공식 MCP — 카탈로그 D8.1 카드·§9 조립 예시, 유형 ⑤b 참조 구현
  • Korean Stats MCP — 카탈로그 D8.1 카드 예: KOSIS 통계를 자연어로, 출처 자동 인용

관련 부품

A8 끼울 자리 — 공공데이터 MCP · C8 필수 통제 — 읽기 전용 · D8.2 이웃 블록 — 찾은 문서의 요약·추출 · S5 5b-host 필수 보안 · X8 이 블록에서 흔한 함정

D8.4 대조·점검 서비스 블록

법령·규정·서식·인용·근태·보안 기준과 대조해 확인할 대상을 먼저 골라 주는 내부 운영 블록이다. "최종 판단은 사람"이 가장 자주 붙는다.

PAX 사례 81건이 이 부품을 쓴다

맥락

기관 내부 문서·자료를 기준과 대조하는 업무. §7.3 유형 ⑦ 대조·점검 도우미(D8.4, P0~P1)와 유형 ⑩ 위험 예측·표적 선별(D6·D3·D8.4)의 무대. PAX 81건(주 부품 B0 73%, B1 12%), 감사·법무 25건·문서·기안 12건.

맞서는 힘(긴장)

  • 점검 범위 확대 vs 오탐으로 인한 확인 부담
  • 규칙 점검의 결정성 vs LLM 대조의 유연성
  • 점검 대상이 점검기를 속이는 위협 vs 자동 점검
  • 출처 대조의 엄격성 vs 원문 접근 권한(공공 API 인가)

해법

기준이 규칙으로 옮겨지면 B0 규칙 점검기로, 해석이 필요하면 B3 법령 접지로 대조한다. 기준 원문은 A3 공공 API(법령·판례)에서 가져와 C5 출처 검증으로 인용이 실제 원문과 일치하는지 확인한다. 결과는 판정이 아니라 "확인할 대상 목록"으로 내고, C1으로 "최종 판단은 사람"을 명시하며, F7 한계와 F1 출처를 붙인다. 점검 대상 문서·코드가 점검기를 속이지 못하게 대상별 격리(S6)나 고정 규칙 실행(S4)을 쓰고, 코드 점검이면 S9 샌드박스를 둔다. C9 평가 세트로 누락률을 잰다.

이럴 때 쓴다

  • 문서·자료를 법령·규정·서식과 한 줄씩 대조하는 업무
  • 인용·근거가 원문과 맞는지 확인해야 할 때
  • 점검 대상이 많아 확인 대상을 먼저 좁혀야 할 때

이럴 때는 쓰지 않는다

  • 국민 신청 건의 자격 판정이면 D3
  • 현장 시설을 관측해 점검하면 D6
  • 대조 없이 자료를 찾아 보여 주면 D8.1

얻는 것

  • 대조 시간 단축과 누락 감소
  • 사람 판단을 확인 대상에 집중
  • 인용 오류의 사전 차단

점검표

  • 결과가 판정이 아닌 확인 대상으로 표시되는가
  • 근거 원문 출처가 연결되는가
  • 누락률을 평가 세트로 재는가
  • 점검 대상 속 문장이 점검 결과를 바꾸지 못하는가

구조 — 참여 부품

  • 담당자 — 확인 대상을 검토해 최종 판단
  • B0 결정적 도구(규칙 점검기) — 규칙화된 기준으로 대조
  • B3 지식 접지 상담 — 법령·규정에 접지해 해석 대조
  • A3 공공 API 제공자 — 법령·판례 원문 제공
  • C5 가드레일·출처 검증 — 인용을 원문과 대조
  • C1 검토 큐 — 최종 판단은 사람

변형

  • 규칙 점검기형: B0로 서식·근태·보안 기준을 결정적으로 대조(Attendance Checker).
  • 법령 접지 대조형: B3가 법령·규정에 접지해 해석 필요 항목을 대조(Legal Reviewer).
  • 인용 검증형: 보고서·논문의 법령·판례·문헌 인용을 원본과 대조(paper-verify).
  • 표적 선별형: B2 위험 예측이 점검 대상을 좁힘(유형 ⑩, B′9).

참조 구현 예

  • paper-verify — 카탈로그 D8.4 카드·§7.3 유형 ⑦ 참조 구현: 인용을 원본과 대조
  • 민원 답변 작성 스킬 팩 — 카탈로그 D8.4 카드 예
  • Attendance Checker — §7.3 유형 ⑦ 참조 구현
  • Legal Reviewer — §7.3 유형 ⑦ 참조 구현

관련 부품

A1 데이터 자산 서비스 공통 서비스

흩어진 업무 기록을 정제·라벨링해 AI 부품이 붙여 쓸 수 있는 데이터셋·라벨·데이터 사전 형태의 기준선으로 제공한다.

PAX 사례 110건이 이 부품을 쓴다

맥락

학습 모델(A2.5·B2), 지식 접지(B3)의 코퍼스, 평가 세트(C9)의 정답 출처가 필요한 과제라면 모두 이 부품을 쓴다. 서비스 유형 5a·9·10·11에서는 필수 기반이다. 비LLM 규칙 기반 대민 안내에서는 A2를 거치지 않고 결정론 조회의 대상이 된다(R21).

맞서는 힘(긴장)

  • 정제 품질 vs 구축 기간·라벨링 인력 비용
  • 과제 전용 가공(빠름) vs 기관 공통 기준선(재사용)
  • 데이터 활용 범위 vs 데이터 등급(E5) 보호
  • 기준선 고정(재현성) vs 원천 갱신 반영

해법

원천 기록을 수집→정제(중복·결측 처리)→라벨링→정의 문서화 순으로 가공하고, 결과를 정제 데이터셋·라벨·데이터 사전의 세 산출물로 고정해 제공한다. 'N건→M건 정제'처럼 정제 전후 규모와 기준을 기록하고, 변수·테이블·인터페이스 정의서로 소비 부품이 같은 정의를 쓰게 한다. 기준선은 버전으로 관리해 C9 평가 세트의 정답 출처와 C6 재학습의 입력으로 재사용한다. 데이터 경계는 부품별로 두고(DB per Service), 타 기관 데이터와의 결합은 A4로 분리한다.

이럴 때 쓴다

  • 예측·추천기(B2)나 비전 모델(A2.5)을 학습·재학습할 때
  • 지식 접지(B3)의 코퍼스를 구축할 때
  • 평가 세트(C9)의 정답 출처가 필요할 때
  • 서비스 유형 5a-agg·9·10·11처럼 A1이 필수인 조립

이럴 때는 쓰지 않는다

  • 공공 API 응답을 가공 없이 조회만 할 때(A3)
  • 정제·정의 없이 파일을 올려 바로 검색하는 경우(태그 대상 아님)
  • 타 기관 데이터 결합이 핵심일 때는 A4를 함께 태그해 계약·키 매핑을 따로 드러낸다

얻는 것

  • 모델 교체와 무관하게 남는 기관 자산
  • C9·C6·B3가 같은 기준선을 재사용
  • 데이터 사전이 기관 간 표준 확산의 단위가 됨

점검표

  • 정제 전후 규모와 정제 기준이 기록되어 있는가
  • 데이터 사전(정의·단위·출처)이 있는가
  • 기준선에 버전이 있고 평가용 분할이 학습용과 분리되어 있는가
  • 데이터 등급(E5)에 맞는 가명·비식별 처리가 적용되었는가

구조 — 참여 부품

  • 원천 시스템·기록 — 가공 전 업무 기록을 내주는 출처
  • 정제·라벨링 파이프라인 — 중복 제거·결측 처리·라벨 부여·품질관리를 수행
  • 데이터 사전 — 정의·단위·출처를 문서로 고정해 소비 부품이 같은 뜻으로 쓰게 함
  • C9 평가 세트·회귀시험 — 기준선을 정답 출처로 사용
  • A2.5 비LLM 학습 모델 — 기준선으로 학습·재학습하는 소비 부품

변형

  • 학습데이터 구축형: 영상·이미지 등을 수집해 품질관리 단계(중복 제거·재라벨링·학습/검증/평가 분리)를 거쳐 학습 기준선으로 만든다.
  • RAG 코퍼스 정본화형: 법령·규정 원문을 현행 시행본 기준으로 정본화하고 조문 구조·메타데이터를 부여해 색인한다.
  • 지표 표준화형: 여러 자료원의 지표를 도메인별로 표준화하고 정의·단위·분모·결측·원본 링크를 메타데이터로 관리한다.
  • 자동 피처 파이프라인형: 수집→정제→파생 변수 생성→자동 검증→담당자 승인을 주기 실행하고 승인만 사람에게 남긴다.

PAX 사례 44건이 이 부품을 쓴다

맥락

  • 결정적 검증의 신뢰성 vs 구현 범위

해법

프롬프트가 기관 밖으로 나가기 전 PII를 마스킹하고 원복 키를 보관하는 비식별 전처리기를 둔다. 응답에는 인용을 원본(법령정보센터·통계표 등)과 대조하는 출처 검증기와, JSON 스키마·허용 목록 같은 구조적 출력 제약을 건다. 근거가 없으면 답하지 않거나 '확인 필요'로 표시한다. 차단 사유는 C4에 남기고, 이용자에게는 F1 출처와 F7 한계 안내로 보인다. 사람이 하는 팩트체크·법무 심의는 C5가 아니라 C1.2에 둔다.

X3 부서마다 챗봇 안티패턴

같은 기관의 과제들이 각자 모델·벡터DB·프롬프트를 따로 만들어, 공유할 수 있는 기반 부품을 부서 수만큼 중복 구축하는 함정이다.

맥락

한 기관 안에서 여러 부서가 동시에 대민·내부 챗봇, 문서 검색, 요약 도구를 추진하는 경우. 특히 각 과제가 상용 API를 직접 호출하는 경우.

맞서는 힘(긴장)

  • 부서의 빠른 자율 구축 vs 기관 전체의 중복 비용
  • 부서별 맞춤(코퍼스·문체) vs 공통 모델·게이트웨이
  • 과제 단위 예산·성과 vs 공통 기반 등재·유지 책임

해법

§7.1의 두 번째 단계대로 기반 부품은 새로 만들지 말고 Provider에서 먼저 가져온다. 모델 호출은 A2 모델 서빙 계층(범정부 AI 공통기반 또는 기관 게이트웨이) 뒤로 모으고, S1 단일 진입점에서 인증·요청 상한·비용 상한·감사 기록을 일괄 적용한다. 공공 API·공공 클라우드·공공 깃랩은 A3 공공 API 제공자로 쓴다. 부서별 차이는 모델을 따로 두지 말고 A9 업무 규범 스킬과 부서 코퍼스(A1)로 표현하며, 부서·등급별 코퍼스 분리가 필요하면 S2 권한 인식 검색으로 푼다. 없어서 새로 만든 부품은 §13 참조 구현 레지스트리에 올린다.

이럴 때 쓴다

  • 같은 기관의 두 과제 이상이 각자 모델 계약·API 키·벡터DB를 갖는다
  • 범정부 AI 공통기반·공공 API를 쓰지 않은 이유가 서술되지 않는다
  • 공통 규정·매뉴얼 코퍼스를 과제마다 따로 임베딩한다
  • 모델 호출 비용을 기관 단위로 집계할 수 없다

이럴 때는 쓰지 않는다

  • 데이터 등급(E5)이나 망 조건(E1) 때문에 공통 기반을 쓸 수 없고 그 사유가 서술된 경우
  • A2 게이트웨이를 공유하면서 부서별 코퍼스·스킬만 따로 둔 경우(정상 조립)
  • 개인이 만든 단일 도구로 기관 내 중복 과제가 없는 경우

얻는 것

  • 부서가 협의 없이 빠르게 만든다
  • 부서 요구에 딱 맞는 맞춤 구성을 갖는다

점검표

  • 기관의 모든 모델 호출이 하나의 게이트웨이를 지나는가
  • 부서별 API 키 직접 호출이 남아 있지 않은가
  • 공통 기반을 쓰지 않은 과제는 그 사유(E1·E5)가 적혀 있는가
  • 부서별 차이가 모델이 아니라 스킬·코퍼스로 표현되어 있는가

구조 — 참여 부품

  • A2 모델 서빙 계층 — 교정 후 모든 부서 호출이 모이는 공통 자리
  • A3 공공 API 제공자 — 범정부 AI 공통기반·공공 깃랩 등 Provider
  • S1 AI 게이트웨이·단일 진입점 — 부서별 API 키 직접 호출을 대체하는 인증·상한·기록 지점
  • A9 업무 규범 스킬 — 부서별 차이를 모델이 아니라 스킬로 표현

변형

  • 벡터DB 중복: 같은 규정·매뉴얼을 부서마다 따로 임베딩해 따로 검색
  • 프롬프트 사일로: 같은 공문 규범을 부서마다 다른 프롬프트로 재작성

X10 평가 없는 RAG, RAG 없는 튜닝 안티패턴

평가 세트 없이 검색을 붙여 '좋아진 것 같다'로 배포하고, 검색으로 풀릴 문제를 파인튜닝으로 푸는, 진행 경로를 건너뛰는 함정이다.

맥락

B3 지식 접지·B1 코파일럿에 RAG를 붙이거나 A2.3 튜닝형 모델을 만드는 과제, 특히 규정·매뉴얼 기반 질의응답.

맞서는 힘(긴장)

  • 눈에 보이는 기술 성과 vs 지루한 평가 세트 구축
  • 빠른 배포 vs 변경마다 재는 자
  • 자체 모델 보유 인상 vs 검색으로 충분한 문제

해법

§7.2 진행 경로를 순서대로 밟는다. B1 직접 프롬프트에서 시작해 두 번째 단계에서 C9 평가 세트(업무 질문·정답·채점 기준)를 먼저 만들고, 이후 A9 규범 스킬·F4, B3 지식 접지(A1 데이터 자산), B3 검색 품질(Hybrid·Rewriting·Reranker), C5 가드레일·F1 순으로 붙이며 매 단계를 C9로 잰다. A2.3 튜닝은 진행 경로의 마지막 단계로, 검색·규범 스킬로 풀리지 않는다는 것이 C9 점수로 확인됐을 때만 한다. 모델·프롬프트·설정 조합은 릴리스처럼 버전 관리한다.

이럴 때 쓴다

  • RAG·튜닝을 도입했는데 업무 질문·정답·채점 기준 세트가 없다
  • '답변 품질 향상'을 수치 없이 서술하거나 단발 정확도만 보고한다
  • 자주 바뀌는 규정·매뉴얼 질의를 파인튜닝으로 풀었다
  • 검색 품질(재현율·리랭킹)을 재지 않고 튜닝으로 넘어갔다

이럴 때는 쓰지 않는다

  • C9 세트로 RAG 전후를 비교한 뒤 배포한 경우
  • 검색·스킬로 풀리지 않음을 C9 점수로 확인한 뒤 튜닝한 경우
  • B2·B4처럼 비LLM 학습 모델로 원래 학습이 해법인 경우(RAG가 대안이 아님)

얻는 것

  • RAG·튜닝이라는 눈에 보이는 기술 성과를 빨리 낸다
  • 평가 세트 구축에 현업 시간을 쓰지 않는다

점검표

  • 업무 질문·정답·채점 기준 세트가 있는가
  • RAG 전후 점수 비교가 있는가
  • 튜닝을 선택한 근거가 C9 점수로 설명되는가
  • 모델·프롬프트·설정 조합이 버전 관리되는가

구조 — 참여 부품

  • C9 평가 세트·회귀시험 — 빠진 부품. 모든 변경을 같은 자로 잼
  • B3 지식 접지 — 튜닝 전에 먼저 시도할 검색 기반 접지
  • A2.3 튜닝형 모델 — 진행 경로의 마지막 단계
  • A1 데이터 자산 서비스 — 정답 출처와 검색 코퍼스

변형

  • 평가 없는 RAG: 검색을 붙이고 몇 개 질문을 눈으로 보고 배포
  • RAG 없는 튜닝: 문서 검색으로 풀릴 최신 규정 질의를 파인튜닝으로 해결하려 함
  • 평가 없는 튜닝: 튜닝 전후를 같은 세트로 비교하지 않음

관련 부품
