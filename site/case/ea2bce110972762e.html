판정 근거

Windows 빌더가 PDF·HWP·HWPX·DOCX 규정을 기관·규정·개정판·장절조문 구조로 파싱해(A10 문서형식 어댑터) 색인을 만드는 부분은 B0 결정적 도구(변형: MCP 도구 제공)이고, 이용자가 Qwen 로컬 RAG 챗(A2.2)이나 ChatGPT·Claude·Codex(A2.1)로 MCP를 통해 규정을 질의·응답받는 부분이 최종 산출물이므로 R1 가치흐름 규칙에 따라 B3(지식 접지 상담)를 주 부품, B0를 secondary로 둔다. '사람이 승인한 내용만 색인·응답에 포함'은 콘텐츠 반입 전 심의이므로 C1.2 심의 게이트로 implemented, 동시에 승인되지 않은 내용을 걸러내는 필터라 C5도 implemented. 조회 전용이라 permission_scope는 P0.

구현 가이드

주 패턴 B3 지식 접지 상담을 구현할 때

구현 단계

  1. 대표 질문·정답·채점 기준으로 C9 평가 세트를 먼저 만든다.
  2. A1로 코퍼스를 정리하고 데이터 등급(E5)과 공개 범위를 메타로 붙인다. 등급 문서가 섞이면 S2 권한 인식 검색을 둔다.
  3. E1에 맞게 임베딩·벡터DB·모델 위치를 정한다(폐쇄망이면 전부 로컬, A2.2·A2.4).
  4. 근거 밖 답변 금지·출처 상시 표시·근거 없으면 이관하는 규칙을 C5·F1·B′2로 구현한다.
  5. 검색 품질 3패턴을 하나씩 붙이며 C9로 재고, 문서 갱신 주기를 C6으로 운영한다.

점검표

  • 답마다 출처가 표시되는가
  • 근거가 없을 때 답하지 않고 이관하는가
  • 평가 세트로 검색·답변 품질을 재고 있는가
  • 코퍼스 갱신 주기와 책임자가 정해져 있는가

환경 조건

E1 폐쇄망·행정망이면 임베딩·벡터DB·모델 전부 로컬(A2.2 주권형 또는 A2.4 내부망 프록시 + 로컬 임베딩). E2 해외 상용 API면 C5 비식별 전처리와 C7 폴백이 필수다. E4는 P0~P1이 기본이다. 신뢰 불가 입력(민원 입력·공개 웹)을 읽고 P2 이상이면 S6 문서별 격리와 S2가 필요하다. 대민형은 S4·S7이 권장된다(§7.4).

주의할 점

  • 평가 없이 붙이면 품질을 알 수 없음(X10)
  • 코퍼스 갱신이 멈추면 오답이 됨
  • 부서마다 따로 만들면 중복(X3)
  • 대민형은 인젝션·유출 위협에 노출

이 조합에서 카탈로그가 함께 갖추라고 권하는 부품 가운데 아직 확인되지 않은 것이다.

  • C8 권한 경계·킬스위치 AI 부품이 할 수 있는 일의 상한을 P0~P4로 못 박고, 도구별 실행 승인·읽기/쓰기 분리·속도 제한·즉시 중단 스위치를 제공한다.
  • C4 감사 로그·지표 처리 건마다 흔적을 적재하고 수정률·처리시간·자동처리율·가용성을 집계해, '지난달 수정률'을 숫자로 말할 수 있게 한다.
  • S5 계획 후 실행·코드 후 실행 신뢰 불가 데이터를 읽기 전에 도구 호출 계획이나 프로그램을 고정하고 정책으로 검증해, 도구 출력이 새 행동을 끼워 넣지 못하게 한다.
  • S6 격리 LLM·맵리듀스 도구를 가진 권한 LLM은 신뢰 불가 데이터를 읽지 않고, 데이터를 읽는 격리 LLM은 도구가 없게 나눈 뒤 결과를 형식 제약이나 기호 참조로만 넘긴다.

피해야 할 안티패턴

  • X3 부서마다 챗봇 같은 기관의 과제들이 각자 모델·벡터DB·프롬프트를 따로 만들어, 공유할 수 있는 기반 부품을 부서 수만큼 중복 구축하는 함정이다. 대처: §7.1의 두 번째 단계대로 기반 부품은 새로 만들지 말고 Provider에서 먼저 가져온다. 모델 호출은 A2 모델 서빙 계층(범정부 AI 공통기반 또는 기관 게이트웨이) 뒤로 모으고, S1 단일 진입점에서 인증·요청 상한·비용 상한·감사 기록을 일괄 적용한다. 공공 API·공공 클라우드·공공 깃랩은 A3 공공 API 제공자로 쓴다. 부서별 차이는 모델을 따로 두지 말고 A9 업무 규범 스킬과 부서 코퍼스(A1)로 표현하며, 부서·등급별 코퍼스 분리가 필요하면 S2 권한 인식 검색으로 푼다. 없어서 새로 만든 부품은 §13 참조 구현 레지스트리에 올린다.
  • X10 평가 없는 RAG, RAG 없는 튜닝 평가 세트 없이 검색을 붙여 '좋아진 것 같다'로 배포하고, 검색으로 풀릴 문제를 파인튜닝으로 푸는, 진행 경로를 건너뛰는 함정이다. 대처: §7.2 진행 경로를 순서대로 밟는다. B1 직접 프롬프트에서 시작해 두 번째 단계에서 C9 평가 세트(업무 질문·정답·채점 기준)를 먼저 만들고, 이후 A9 규범 스킬·F4, B3 지식 접지(A1 데이터 자산), B3 검색 품질(Hybrid·Rewriting·Reranker), C5 가드레일·F1 순으로 붙이며 매 단계를 C9로 잰다. A2.3 튜닝은 진행 경로의 마지막 단계로, 검색·규범 스킬로 풀리지 않는다는 것이 C9 점수로 확인됐을 때만 한다. 모델·프롬프트·설정 조합은 릴리스처럼 버전 관리한다.

B0 결정적 도구 업무 컴포넌트

AI 코딩으로 만들었지만 런타임에는 AI를 부르지 않고 규칙과 원문 발췌만으로 같은 입력에 같은 결과를 내는 취합·변환·검색·시각화 도구다.

PAX 사례 413건이 이 부품을 쓴다

맥락

AI 코딩 도구(A7)로 기관 인력이 직접 만든 자생 도구가 대부분이다(PAX 557건 가운데 주 부품이 B0인 사례 390건, 70%). 로컬 PC 완결이나 폐쇄망 이식이 필요한 업무, 판정 재현성이 감사에서 중요한 업무에도 맞는다. model_dependency가 '없음(비LLM)'으로 확인될 때만 해당한다.

맞서는 힘(긴장)

  • 재현성·설명 가능성 vs 비정형 입력을 다루는 유연성
  • 로컬 완결의 보안 이점 vs 기관 전이 시 처리 로그(C4)와 인수인계가 사라지는 문제
  • 규칙을 코드에 넣는 단순함 vs 규정이 바뀔 때마다 사람이 규칙을 고쳐야 하는 유지 부담

해법

업무 절차를 입력 형식(A10 어댑터)과 처리 규칙으로 나누고, AI 코딩 도구(A7)는 개발 시점에만 써서 규칙 코드와 화면을 만든다. 런타임에는 모델을 호출하지 않으므로 같은 입력에 같은 결과가 나오고 인터넷 없이 로컬에서 돈다. 판정이 필요한 경우에도 결정적 규칙 엔진이 낸다. 비정형 입력을 다뤄야 하는 단계가 생기면 그 단계만 B1·B3로 승격하고 결정적 부분은 전처리로 남긴다. 부서 밖으로 옮길 때는 라이선스·저장소·처리 로그를 함께 갖춘다.

이럴 때 쓴다

  • 입력이 정형(엑셀·서식)이고 처리 결과를 규칙으로 정의할 수 있을 때
  • 파일이 PC 밖으로 나가면 안 되거나 폐쇄망·로컬 완결이 필요할 때
  • 판정 재현성이 필요해 같은 입력에 늘 같은 결과가 나와야 할 때(규칙 점검기, 결정론 점수 엔진)
  • LLM 도입 전에 데이터·기준선을 정비하는 단계일 때

이럴 때는 쓰지 않는다

  • 비정형 문서의 요약·초안처럼 규칙으로 산출물을 정의할 수 없을 때(B1)
  • 질문이 다양해 규정·선례 접지가 필요한 상담일 때(B3)
  • 학습 모델의 수치·등급 예측이 핵심 산출물일 때(B2)

얻는 것

  • 재현성과 감사 가능성
  • 폐쇄망·로컬 이식이 가장 쉬움
  • 모델 호출 비용과 모델 장애 위험이 없음
  • B1·B3의 전처리 부품으로 승격할 자산

점검표

  • 런타임에 LLM·ML 호출이 전혀 없는가
  • 규칙 표가 코드와 별도로 문서화되어 있는가
  • 같은 입력에 같은 결과가 나오는지 확인했는가
  • 라이선스와 저장소 위치가 명시되어 인수인계가 가능한가

구조 — 참여 부품

B3 지식 접지 상담 업무 컴포넌트

기관 규정·매뉴얼·사례 문서에 접지(RAG)해 질문에 답하고, 답마다 출처를 붙이며, 근거가 없으면 답하지 않고 담당자에게 넘긴다.

PAX 사례 48건이 이 부품을 쓴다

맥락

규정·매뉴얼·FAQ·사례가 문서로 쌓인 기관에서 내부 검색·검수, 대민 자동응답, 폐쇄망 로컬 검색에 쓴다. PAX 557건에서 주 부품이 B3인 사례는 31건으로 B0·B1 다음이다. 유형 ① 대민 상담·안내의 기본 조립이기도 하다.

맞서는 힘(긴장)

  • 답변 범위 vs 환각 위험(근거 밖 답변 금지)
  • 대민 자동응답의 효율 vs 예외 건 이관 필요
  • 검색 품질 개선 vs 평가 세트 없이는 개선을 잴 수 없음
  • 폐쇄망 요구 vs 로컬 임베딩·모델 품질

해법

기관 문서를 A1 자산으로 정리해 임베딩·색인하고, 질문이 오면 검색한 근거 범위 안에서만 모델이 답하게 한다. 답에는 출처(F1)를 상시 붙이고, 근거가 없으면 '확인 불가'로 답하거나 담당자·소관기관으로 이관한다(B′2). 검색 품질은 Hybrid Retriever·Query Rewriting·Reranker로 높이되, 변경마다 C9 평가 세트로 잰다. 대민형은 한계 안내(F7)와 폴백(C7)을 두고, 문서 갱신 주기를 C6으로 정한다.

이럴 때 쓴다

  • 같은 질문이 반복되고 답의 근거가 기관 문서에 있을 때
  • 답변에 조문·문서 출처를 반드시 붙여야 할 때
  • 유형 ① 대민 상담·안내, 유형 ⑦ 법령 접지 점검

이럴 때는 쓰지 않는다

  • 평가 세트가 없어 검색 품질을 잴 수 없을 때(먼저 C9, X10)
  • 질문 유형이 몇 개로 정해져 행동 선택기(S4)나 규칙 조회로 충분할 때
  • 문서를 요약해 초안을 쓰는 것이 핵심이면(B1)

얻는 것

  • 답변에 근거를 댈 수 있음
  • 반복 질의 처리 시간 단축
  • 범정부 엔진 + 기관별 코퍼스로 공유 가능

점검표

  • 답마다 출처가 표시되는가
  • 근거가 없을 때 답하지 않고 이관하는가
  • 평가 세트로 검색·답변 품질을 재고 있는가
  • 코퍼스 갱신 주기와 책임자가 정해져 있는가

구조 — 참여 부품

  • A1 데이터 자산 서비스 — 코퍼스 정제·등급 메타
  • A2 모델 서빙 계층 — 임베딩·생성 모델(폐쇄망이면 로컬)
  • 검색기 — 벡터·키워드 검색, 재작성·재순위

B′1 순차 파이프라인 제어 흐름

한 단계의 출력을 다음 단계의 입력으로 넘기는 고정 순서 배선이다. 한 프롬프트에 많은 일을 몰아 시켜 품질이 떨어지는 문제를 막는다.

PAX 사례 109건이 이 부품을 쓴다

맥락

B4 인식 파이프라인의 기본 배선이며, B1·B0·B5 안에서도 흔하다. 단계 순서가 업무 절차로 미리 정해져 있고 AI가 순서를 고를 필요가 없을 때 쓴다.

맞서는 힘(긴장)

  • 디버깅·출처 추적의 쉬움 vs 병렬화 불가로 인한 지연
  • 단계 분리의 품질 이점 vs 단계가 늘수록 오류 누적
  • 고정 순서의 예측 가능성 vs 예외 경로 처리의 경직성

해법

업무 절차를 단계로 나누고 각 단계의 입력·출력 형식을 정해 앞 단계 출력을 다음 단계에 넘긴다. 단계 사이에 형식 검증(스키마)을 두어 오류가 번지기 전에 멈추고, 멈춘 건은 C1 검토 큐나 C3 재처리로 보낸다. 판정·산수 단계는 가능한 한 규칙(B′9)으로 두고 모델은 추출·서술 단계만 맡긴다. 단계 순서를 AI가 바꿔야 한다면 B′8이나 B′7로 옮긴다.

이럴 때 쓴다

  • 업무 절차가 고정 순서로 정해져 있을 때
  • 각 단계를 따로 검증·추적해야 할 때(유형 ② 접수·심사, ⑧ 취합·변환)
  • 단일 에이전트에서 시작하는 첫 배선일 때

이럴 때는 쓰지 않는다

  • 하위 작업이 서로 독립이라 동시에 돌려야 지연이 줄 때(B′3)
  • 입력에 따라 AI가 다음 도구를 골라야 할 때(B′7)
  • 긴 업무를 계획부터 세워야 할 때(B′8)

얻는 것

  • 디버깅과 출처 추적이 쉬움
  • 단계별 품질 검증 가능
  • 구현이 가장 단순

점검표

  • 단계마다 입력·출력 형식이 정의되어 있는가
  • 단계 사이 검증에서 실패하면 멈추는가
  • 단계별 중간 결과를 추적할 수 있는가

구조 — 참여 부품

  • 단계 처리기 — 각 단계에서 추출·변환·작성 수행
  • 단계 간 형식 검증 — 다음 단계로 넘기기 전 스키마 확인
  • C3 상태 머신·롤백 — 실패 단계 재처리

A10 문서 형식 어댑터 공통 서비스

HWP·HWPX·엑셀·한셀·PDF 같은 한국 공공 문서 형식을 AI 부품이 읽고(구조화) 쓰게(서식 생성) 하는 변환 계층이다.

PAX 사례 136건이 이 부품을 쓴다

맥락

맞서는 힘(긴장)

  • 형식 충실도(표·각주·조항 구조 보존) vs 파서 구현 비용
  • 로컬 처리(무반출) vs 클라우드 변환 도구의 편의
  • 기관별 서식 다양성 vs 공통 어댑터 재사용

해법

입력 쪽에서는 HWPX 압축 구조·PDF에서 조·항·호·별표 계층과 표를 보존해 구조화 텍스트·표로 바꾸고, 머리말·각주 같은 잡음을 걷어 조항 단위로 정규화한다. 출력 쪽에서는 스킬(A9)의 출력 서식을 받아 HWPX·XLSX 기안 서식을 역방향으로 생성한다. 민감 문서는 PC 밖으로 보내지 않도록 로컬에서 변환하고, 파서를 라이브러리·CLI·MCP로 함께 제공하면 다른 부품과 기관이 그대로 쓴다. 형식 변환 정확도는 C9 판정 체계로 잰다.

이럴 때 쓴다

  • 입력이 HWP·HWPX·엑셀·PDF 공공 문서일 때
  • 산출물을 기안·보고 서식으로 내보내야 할 때
  • 유형 2·4·8 조립

얻는 것

  • 기관 간 재사용 가능한 공통 부품
  • 로컬 처리로 무반출

점검표

  • 표·조항 계층이 변환 후에도 보존되는가
  • 출력이 기관 기안 서식 그대로 열리는가
  • 민감 문서가 변환 과정에서 PC 밖으로 나가지 않는가
  • 변환 정확도 판정 기록이 있는가

구조 — 참여 부품

A2.2 모델 서빙 · 주권형 온프레미스 공통 서비스

오픈웨이트 모델을 기관 서버·폐쇄망·로컬 PC 안에서 Ollama·vLLM 등으로 구동해 데이터를 기관 밖으로 내보내지 않고 추론한다.

PAX 사례 54건이 이 부품을 쓴다

맥락

맞서는 힘(긴장)

  • 데이터 주권 vs 상용 최신 모델 대비 성능

  • 모델 운영·갱신 역량 vs 외부 의존 제거
  • 저사양 장비 구동 vs 모델 크기

얻는 것

A2.1 모델 서빙 · 상용 API 호출 공통 서비스

GPT·Gemini·Claude·HyperCLOVA X·Upstage 등 상용 모델 API를 서빙 계층을 거쳐 호출해 자체 인프라 없이 최신 모델 성능을 쓴다.

PAX 사례 88건이 이 부품을 쓴다

맥락

E2는 해외 상용 API(또는 국산 상용 모델 API), E1은 인터넷망·클라우드다. E5 등급이 O이거나 비식별 후 전송해도 되는 업무에 맞는다. 대민 상담(B3)·코파일럿(B1)·콘텐츠 생성(B7)에서 흔하다.

맞서는 힘(긴장)

  • 모델 성능·도입 속도 vs 데이터 반출·주권
  • 종량 과금의 초기 저비용 vs 호출량 증가 시 비용 예측 어려움
  • 벤더의 모델 개선 vs 예고 없는 품질 회귀
  • 단일 API의 단순함 vs 장애 시 서비스 중단

해법

업무 코드는 서빙 계층만 부르고, 서빙 계층이 상용 API를 호출한다. 행정망 본문이 나가는 경로 앞에는 C5 비식별 전처리를 두고, 대체 모델을 등록해 C7 폴백을 건다(§5 매트릭스 E2 해외 상용 API 행). 모델 버전을 고정하고 모델·프롬프트·설정 조합을 릴리스처럼 관리해 업데이트 전후를 C9로 비교한다. 비용이 문제면 라우팅·캐싱으로 큰 모델 호출을 줄인다. E5가 S 이상이면 이 변형 단독으로는 안 되고 A2.4 내부망 프록시를 거친다.

이럴 때 쓴다

  • 인터넷망·클라우드 환경이고 데이터 등급이 O이거나 비식별 후 전송 가능할 때
  • PoC 초기에 모델 성능을 빠르게 확인해야 할 때
  • 자체 GPU·운영 인력이 없을 때

이럴 때는 쓰지 않는다

  • E1이 폐쇄망이면 조립 오류(A2.2·A2.4로)
  • E5가 S 이상인데 내부망 프록시가 없을 때(A2.4 필수)
  • 상시 서비스인데 대체 경로를 둘 수 없을 때

얻는 것

  • 인프라 없이 최신 모델 성능
  • 빠른 PoC
  • 벤더의 지속적 개선

점검표

  • 업무 코드가 상용 API를 직접 부르지 않는가
  • 외부로 나가는 프롬프트에서 무엇이 걸러지는지 답할 수 있는가
  • API 장애 시 대체 경로가 있는가
  • 모델 버전과 호출당 비용·지연이 기록되는가

구조 — 참여 부품

  • A2 서빙 계층 — 업무 코드 대신 상용 API를 호출하고 버전·사용량을 기록
  • C5 가드레일(비식별 전처리) — 외부 전송 전 민감정보 제거
  • 상용 모델 API — 기관 밖에서 추론을 수행
  • C7 폴백 스위치 — API 장애·품질 저하 시 대체 모델·수동 처리로 전환

변형

  • 해외 상용 API: GPT·Gemini·Claude 등이다. E2 값은 해외 상용 API.
  • 국산 상용 API: HyperCLOVA X·Upstage 등 국내 사업자 API. 망·등급 조건은 해외와 같이 따진다.
  • 구조화 호출: function calling·JSON Schema로 출력 형식을 고정해 부른다. 판정은 규칙 엔진에 남긴다.

A8 MCP 서버·호스트 공통 서비스

공공 API·업무 시스템·로컬 파일을 에이전트가 부를 수 있는 도구로 감싸고, 도구 목록·권한·호출 로그를 한 층에서 관리한다.

PAX 사례 94건이 이 부품을 쓴다

맥락

에이전트(B6)·코파일럿(B1)이 도구를 호출하는 과제나, 공공데이터를 AI 도구로 공개하려는 기관에 쓴다. E3 값은 MCP·CLI 설정이다. 유형 5b에서는 필수이고(R10 'A8 또는 자체 도구 인터페이스'), 서버만 있는 사례는 5b-server로 분류한다(A8·S11 필수, R18).

맞서는 힘(긴장)

  • 도구 재사용·생태계 확산 vs 권한 표면 확대
  • 도구 설명의 편의 vs 실제 권한과의 불일치(X7)
  • 서버 개수 성과 vs 실제 업무 호출(X8)
  • 도구 출력 활용 vs 도구 출력을 타고 오는 간접 인젝션(X13)

해법

공공 API·업무 시스템·로컬 파일을 도구 설명·인증·정책과 함께 MCP 서버로 감싸 에이전트에 노출하고, 호출 결과에 출처·갱신 시각을 붙이며 호출 로그를 남긴다. 읽기(P0) 서버와 쓰기(P2) 서버를 분리하고 C8로 도구별 실행 승인을 건다. 배포·등재 전에 PAX MCP 6축 검증(권한 표면·비밀·공급망·위생·인젝션·데이터 흐름)을 통과시키고 S11로 반입을 검사하며, 통과하지 못한 축이 있으면 전이 범위를 부서 공유 이하로 둔다. 도구 목록·버전·갱신 공지는 레지스트리(Service Discovery)로 관리한다. 폐쇄망에서는 로컬 모델(A2.2)로 여러 MCP를 구동하는 로컬 호스트 변형을 쓴다.

이럴 때 쓴다

  • 에이전트가 공공 API·업무 시스템을 도구로 호출해야 할 때
  • 기관 데이터를 외부 AI 클라이언트와 타 기관이 직접 호출하게 공개할 때
  • 표준 시스템에 API를 열어 레거시 오버레이(B8)를 대체할 때

이럴 때는 쓰지 않는다

  • 호출할 도구가 로컬 파일뿐인 단순 작업(§5 E1 로컬 PC 행: 드묾)
  • 실제 업무 호출 없이 서버 개수를 성과로 삼으려 할 때(X8)
  • 6축 검증·권한 분리를 할 수 없는데 쓰기 도구를 노출하려 할 때

얻는 것

  • 도구 재사용과 생태계 확산
  • 권한·호출을 한 층에서 관리
  • 공공데이터를 AI가 직접 쓰는 경로

점검표

  • 도구 설명이 '조회'인데 쓰기·실행 권한을 가진 도구가 없는가
  • 6축 검증 결과가 기록되어 있는가
  • 호출 로그와 실제 업무 호출 지표가 있는가
  • 호스트가 도구 출력을 명령으로 받지 않도록 S5·S6 등이 있는가(P2 이상)

구조 — 참여 부품

  • MCP 서버 — 공공 API·업무 시스템·로컬 파일을 도구로 감쌈
  • MCP 호스트(에이전트) — 도구를 선택·호출하고 결과를 업무 흐름에 사용
  • C8 권한 경계·킬스위치 — 읽기/쓰기 분리와 도구별 실행 승인
  • S11 인제스천·공급망 검증 — 서버 반입·등재 전 6축 검증
  • C4 감사 로그·지표 — 호출 추적과 실제 업무 호출 지표

변형

C1.2 심의 게이트 운영 컴포넌트

팩트체크·법무·윤리 심의처럼 제3자 전문가가 수행하는 승인 게이트를 AI 산출물의 공개·반영 전에 두어, 업무 담당자 확인만으로 걸러지지 않는 법적·사실적 위험을 막는다.

PAX 사례 3건이 이 부품을 쓴다

맥락

B7 콘텐츠 생성기, 외부 공개 지식베이스·MCP 응답, 법정대리인 동의·개인정보 처리처럼 법무 기준이 필요한 서비스. C1.2는 v0.6에서 C1의 변형으로 신설되었고, v0.7(R16)에서 범위가 제3자 전문가 심의로 좁혀졌다.

맞서는 힘(긴장)

  • 공개 전 법적 안전 vs 발행 속도
  • 전문 심의 인력의 희소성 vs 심의 대상 물량
  • 심의 기준의 문서화 vs 심의자 재량

해법

AI 산출물이 외부로 공개되거나 색인·응답에 반영되기 전에, 작성 담당자와 분리된 심의 주체(법무·심의·윤리팀, 원문 대조 검증자)의 승인 단계를 둔다. 심의 기준(저작권·초상권·표시광고·법령 원문 일치 등)을 문서로 명시하고, 승인된 것만 다음 단계로 흐르게 한다. 심의 결과와 사유는 C4에 남긴다. 시스템이 할 수 있는 자동 검사는 C5로 앞단에 두고, C1.2는 사람의 판단이 필요한 부분만 맡는다.

이럴 때 쓴다

  • 산출물이 기관 밖으로 공개되는 D8.10 발간·홍보, 대민 안내
  • 저작권·초상권·표시광고·개인정보 등 법적 판단이 필요한 콘텐츠
  • 외부에 제공하는 지식베이스·MCP 응답의 정확성을 보증해야 할 때

이럴 때는 쓰지 않는다

  • 내부 참고용 초안으로 외부 공개가 없을 때(C1으로 충분)
  • 업무 담당자나 이용자 본인이 확정하는 절차(C1)
  • 시스템이 자동으로 수행하는 필터·스키마 검증(C5)

얻는 것

  • 외부 공개 산출물의 법적·사실적 위험 차단
  • 기관 책임 범위가 문서화됨
  • 공개 지식의 신뢰성 표시 근거

점검표

  • 심의 주체가 작성 담당자와 분리되어 있는가
  • 심의 기준이 문서로 명시되어 있는가
  • 승인 전 산출물이 공개·색인되지 않게 막혀 있는가
  • 심의 결과와 반려 사유가 기록되는가

구조 — 참여 부품

  • 작성 담당자 — AI 산출물을 1차 검수(C1)하고 심의에 올림
  • 제3자 심의자 — 법무·심의·윤리·팩트체크 기준으로 승인 여부 결정
  • C5 가드레일 필터 — 심의 전 시스템이 자동으로 거를 수 있는 항목 처리
  • C4 감사 로그·지표 — 심의 결정과 사유 기록

변형

  • 제작 사슬 내 승인 단계: 제작→법무·심의·윤리 승인→배포의 다단계 사람 통제 사슬 중 승인 단계
  • 색인 반영 전 승인: 사람이 승인한 내용만 검색 색인·MCP 응답에 포함
  • 원문 대조 검증 표시: 공식 원문과 대조해 검증 완료를 표시한 항목만 공개

답이 원천 데이터에서 나오게 한다. 공공데이터·통계는 A8 MCP 서버나 A3 공공 API로 도구화하고, 호스트 쪽 에이전트는 B′7 ReAct 도구 루프로 조회하되 C8로 읽기 전용에 묶는다. 결과에는 F1 출처(통계표 ID)와 조회 시점을 붙이고, 도구 호출은 C4로 추적한다. 도구 출력이 새 지시가 되지 않도록 S5 계획 후 실행과 S1 비용 상한을 둔다. 에이전트가 필요 없으면 B0 대시보드·검색기로 끝내고(5a-agg), LLM이 해설을 붙이면 5a-brief로 C9·F9를 더한다(R19). MCP 서버만 만드는 사례는 5b-server로 A8·S11만 필수다(R18).

이럴 때 쓴다

  • 담당자가 흩어진 데이터·법령·공고·선례를 찾느라 시간을 쓸 때
  • 공공데이터·통계를 자연어로 조회해야 할 때
  • 다른 지역·기관 사례를 모아 봐야 할 때

이럴 때는 쓰지 않는다

  • 찾은 문서에서 할 일·핵심을 뽑으면 D8.2
  • 규정·기준과 대조해 확인 대상을 고르면 D8.4
  • 국민이 서비스를 찾으면 D1

얻는 것

  • 자료 찾는 시간 절감
  • 출처·시점이 붙은 근거 확보
  • 공공데이터 MCP의 재사용

점검표

  • 결과마다 원천 출처와 기준 시점이 보이는가
  • 도구 권한이 읽기 전용으로 묶여 있는가
  • 도구 호출 순서를 나중에 볼 수 있는가
  • MCP 서버가 실제 업무에서 호출되는지 재는가

구조 — 참여 부품

  • 담당자 — 자료를 찾고 결과를 업무에 씀
  • A8 MCP 서버·호스트 — 공공데이터·통계를 도구로 노출
  • B0 결정적 도구(탐색·시각화) — 검색기·대시보드
  • B6 도구 호출 에이전트 — 로컬 MCP 호스트로 조회·차트 생성
  • C8 권한 경계 — 읽기 전용 제한
  • F1 출처 표시 — 통계표 ID·출처·시점 표시

변형

  • 브리핑형: LLM이 조회 결과를 요약·해설. 유형 5a-brief(필수 A2.1|A2.2|A2.6·F9·C9, R19).

C8 권한 경계·킬스위치 운영 컴포넌트

AI 부품이 할 수 있는 일의 상한을 P0~P4로 못 박고, 도구별 실행 승인·읽기/쓰기 분리·속도 제한·즉시 중단 스위치를 제공한다.

PAX 사례 22건이 이 부품을 쓴다

맥락

도구를 호출하거나 시스템에 쓰는 B6 오케스트레이터, A8 MCP 서버·호스트, B8 레거시 오버레이, 처분 보조(P3) 서비스. 유형 ⑤b 데이터 에이전트, ⑨ 인수인계(접근 범위).

맞서는 힘(긴장)

  • 자동화 범위 vs 통제
  • 승인 절차의 안전 vs 이용 마찰
  • 도구 설명의 편의 vs 실제 권한과의 일치 검증 비용

해법

부품별 허용 권한 범위(P0 읽기 전용 ~ P4 자율 처분)를 정하고, 도구 목록마다 읽기/쓰기를 분리한다. 위험도가 높은 도구는 실행 전 사람 승인(C2·F6)을 받게 하고, 호출 상한(속도 제한)을 둔다. 전역 킬스위치로 즉시 중단할 수 있게 하고, 승인·실패·중단 이력을 C4에 남긴다. MCP 도구는 설명과 실제 권한이 일치하는지 A8 6축 검증으로 확인한다.

이럴 때 쓴다

  • E4 P2 이상(필수, First 관문)
  • E3 MCP·CLI 환경에서 에이전트가 도구를 호출할 때
  • B6 오케스트레이터에 상용 API를 쓰는 경우(A2 + C7 + C8 도구별 승인)
  • 유형 ⑤b-host, ⑨ 인수인계(접근 범위)

이럴 때는 쓰지 않는다

  • 도구 호출·시스템 쓰기가 없는 서술 전용 코파일럿(P1)
  • B0 결정적 도구로 AI가 행동을 고르지 않을 때

얻는 것

  • 되돌릴 수 없는 조치 방지
  • 도구 설명과 실제 권한의 불일치(X7) 예방
  • 감사 가능한 행동 기록

점검표

  • AI가 쓸 수 있는 시스템 목록을 답할 수 있는가
  • 도구별 읽기/쓰기 구분과 위험도가 있는가
  • 고위험 도구에 실행 승인이 걸려 있는가
  • 킬스위치가 있고 누가 누를 수 있는지 정해져 있는가
  • 도구 설명과 실제 권한이 일치하는가

구조 — 참여 부품

  • 권한 정책 — 부품·도구별 허용 범위(P0~P4)와 읽기/쓰기 구분
  • A8 MCP 서버·호스트 — 도구 설명과 실제 권한의 일치 검증 대상
  • F6 에이전트 행동 검토·확인 — 실행 전 이용자 승인 화면
  • 킬스위치 — 전역 즉시 중단
  • C4 감사 로그·지표 — 승인·실패·롤백·중단 이력

변형

  • 읽기 전용·쓰기 배제: 도구 세트를 읽기 전용으로 한정하거나 쓰기 기능을 설계에서 배제

  • 판정 필드 비도달 설계: AI가 판정·업무 필드에 쓸 수 없게 코드 수준으로 분리
  • 속도 제한: 도구 호출 상한(Rate Limiter)

맥락

도구 호출 또는 시스템 쓰기가 있는 구조(R6)에서 계획을 미리 정할 수 있는 정형 업무. 데이터 조회·분석 에이전트(유형 ⑤, 5b-host), 그리고 '오늘 접수 건을 조회해 담당자에게 통지'하는 식의 접수·통지 자동화(유형 ②). 카탈로그 등재 상태는 후보(PAX 557건 중 1건).

맞서는 힘(긴장)

  • 행동 집합의 증명 가능한 고정 vs 중간에 계획을 바꿔야 하는 탐색 과제
  • 정책 검증의 엄격함 vs 계획 작성 실패율
  • 행동 고정 vs 인자 조작(도구 출력이 인자를 바꾸는 것)은 남음

해법

이용자 지시를 받아 신뢰 불가 데이터를 읽기 전에 도구 호출 목록 [tool1(…), tool2(…)] 또는 실행 코드를 먼저 확정한다. 고정된 계획은 제어면(C8 도구별 권한)이 허용 도구·권한·파괴적 행동·사람 승인 필요 여부를 규칙으로 검증한 뒤에만 실행한다. 도구 출력은 인자 값을 채울 수는 있지만 계획에 없는 행동을 추가할 수 없다. 코드 후 실행이면 코드는 S9 샌드박스에서 돌린다. 인자 조작까지 막으려면 S6을 함께 둔다.

이럴 때 쓴다

  • 데이터 조회·분석 에이전트(유형 ⑤)의 필수 부품(S1과 함께)
  • 5b-host(에이전트 호출자) 필수 S5 또는 S6(R18)
  • 접수·통지 자동화처럼 계획을 미리 정할 수 있는 정형 업무
  • 내부 문서 코파일럿(유형 ④)이 행정망에 쓰기를 할 때(권장)

이럴 때는 쓰지 않는다

  • 중간에 계획을 바꿔야 하는 탐색 과제
  • 도구 호출·시스템 쓰기가 없는 서술 전용 LLM(R6)
  • 도구 출력 속 인자 조작이 핵심 위협일 때 S5만으로는 부족 — S6 필요

얻는 것

  • 간접 인젝션에 의한 행동 변경에 증명 가능한 저항
  • 권한 상승 차단
  • 계획이 사전에 보이므로 감사·승인이 쉬움

점검표

  • 외부 데이터를 읽기 전에 계획이 확정되는가
  • 계획이 실행 전에 정책으로 검증되는가
  • 도구 출력이 계획에 없는 도구 호출을 유발할 수 없는가
  • 파괴적 행동에 사람 승인이 걸려 있는가

구조 — 참여 부품

  • 계획 LLM — 신뢰 불가 데이터를 읽기 전에 계획·코드를 작성
  • C8 권한 경계(제어면) — 허용 도구·권한·파괴적 행동·사람 승인 여부를 규칙으로 검증
  • C3 상태 머신 — 계획 단계 진행과 종료 상태 관리
  • S9 임시 샌드박스 — 코드 후 실행 시 코드 격리 실행
  • 실행기 — 검증된 계획만 실행하고 도구 출력은 인자 값으로만 사용

변형

S6 격리 LLM·맵리듀스 보안 패턴

도구를 가진 권한 LLM은 신뢰 불가 데이터를 읽지 않고, 데이터를 읽는 격리 LLM은 도구가 없게 나눈 뒤 결과를 형식 제약이나 기호 참조로만 넘긴다.

맥락

제출 서류(PDF·HWPX·이미지)를 읽어 판정하는 접수·심사 자동화(유형 ②), 대상 문서가 점검기를 속일 수 있는 대조·점검(유형 ⑦), 부서별 제출 파일을 취합하는 자동화(유형 ⑧). 모두 도구 호출 또는 시스템 쓰기가 있는 구조(R6)를 전제로 한다. 카탈로그 등재 상태는 후보(PAX 557건 중 0건).

맞서는 힘(긴장)

  • 증명 가능한 격리 vs 호출 수 증가
  • 형식 제약(불리언·숫자·정규식)의 안전성 vs 풍부한 판정 사유 전달
  • 기호 참조 설계 난이도 vs 권한 LLM의 유연성

해법

권한 LLM(도구 보유)과 격리 LLM(도구 없음)을 분리한다. 문서마다 격리 LLM 인스턴스를 띄워(맵) 요건 충족 여부처럼 형식이 제약된 값만 내게 하고, 비-LLM 규칙으로 합친다(리듀스). 권한 LLM은 격리 LLM의 결과를 $VAR 같은 기호 참조로만 다루고, 실제 값은 비-LLM 오케스트레이터가 실행 시 치환한다. 형식 제약 검증은 C9·스키마 검증으로 강제하고, OCR·파싱 같은 실행은 S9에 둔다. 악성 문서는 자기 판정만 속일 수 있을 뿐 다른 문서나 도구 호출에 영향을 줄 수 없다.

이럴 때 쓴다

  • 접수·심사 자동화(유형 ②)의 정석 — 필수 부품
  • 대조·점검 도우미(유형 ⑦)에서 대상별 격리(S4의 대안)
  • 취합·변환 자동화(유형 ⑧)에서 파일별 격리(권장)
  • 5b-host 필수 S5 또는 S6(R18)
  • S5로 막지 못하는 인자 조작이 위협일 때

이럴 때는 쓰지 않는다

  • 도구 호출·시스템 쓰기가 없는 서술 전용 LLM(R6)
  • 문서 간 교차 참조가 판정의 핵심이라 문서별 격리가 불가능할 때 — S5나 C1 사람 검토로 보완
  • 보안 목적 없이 판정-확정 분리만 있는 구조는 B′9(R11), 다만 신뢰 불가 입력 격리가 함께 있으면 둘 다 태그(R27)

얻는 것

  • 간접 인젝션 전파에 증명 가능한 저항
  • 문서 간 교차 오염 차단
  • 권한 상승 차단
  • 판정이 규칙 집계라 설명·재현이 쉬움

점검표

  • 도구를 가진 LLM이 신뢰 불가 데이터를 직접 읽지 않는가
  • 격리 LLM 출력이 형식 제약 값으로만 전달되는가
  • 문서별로 격리되어 한 문서가 다른 문서 판정에 영향을 줄 수 없는가
  • 집계가 LLM이 아닌 규칙으로 이루어지는가

구조 — 참여 부품

  • 격리 LLM(문서별) — 도구 없이 한 문서만 읽고 불리언·숫자·정규식 형식의 값만 출력
  • 비-LLM 집계기 — 문서별 판정을 규칙으로 합침(리듀스)
  • 권한 LLM — 도구를 가지되 신뢰 불가 데이터를 읽지 않고 기호 참조만 조작
  • 비-LLM 오케스트레이터 — 실행 시 기호 참조를 실제 값으로 치환
  • C9 평가 세트·형식 검증 — 격리 LLM 출력의 형식 제약 검증

변형

  • 이중 LLM(Dual LLM): 권한 LLM과 격리 LLM 두 역할로 나누고 기호 참조로 연결(Willison)
  • LLM 맵리듀스: 문서마다 격리 인스턴스를 띄우고 규칙으로 집계
  • 다중 에이전트 분할: 에이전트별로 읽는 데이터와 가진 도구를 분리
  • 수치·문장 분리형: 수치는 예측 모듈만 산출하고 LLM은 도구 결과를 설명만 하는 구조

X3 부서마다 챗봇 안티패턴

같은 기관의 과제들이 각자 모델·벡터DB·프롬프트를 따로 만들어, 공유할 수 있는 기반 부품을 부서 수만큼 중복 구축하는 함정이다.

맥락

한 기관 안에서 여러 부서가 동시에 대민·내부 챗봇, 문서 검색, 요약 도구를 추진하는 경우. 특히 각 과제가 상용 API를 직접 호출하는 경우.

맞서는 힘(긴장)

  • 부서의 빠른 자율 구축 vs 기관 전체의 중복 비용
  • 부서별 맞춤(코퍼스·문체) vs 공통 모델·게이트웨이
  • 과제 단위 예산·성과 vs 공통 기반 등재·유지 책임

해법

§7.1의 두 번째 단계대로 기반 부품은 새로 만들지 말고 Provider에서 먼저 가져온다. 모델 호출은 A2 모델 서빙 계층(범정부 AI 공통기반 또는 기관 게이트웨이) 뒤로 모으고, S1 단일 진입점에서 인증·요청 상한·비용 상한·감사 기록을 일괄 적용한다. 공공 API·공공 클라우드·공공 깃랩은 A3 공공 API 제공자로 쓴다. 부서별 차이는 모델을 따로 두지 말고 A9 업무 규범 스킬과 부서 코퍼스(A1)로 표현하며, 부서·등급별 코퍼스 분리가 필요하면 S2 권한 인식 검색으로 푼다. 없어서 새로 만든 부품은 §13 참조 구현 레지스트리에 올린다.

이럴 때 쓴다

  • 같은 기관의 두 과제 이상이 각자 모델 계약·API 키·벡터DB를 갖는다
  • 범정부 AI 공통기반·공공 API를 쓰지 않은 이유가 서술되지 않는다
  • 공통 규정·매뉴얼 코퍼스를 과제마다 따로 임베딩한다
  • 모델 호출 비용을 기관 단위로 집계할 수 없다

이럴 때는 쓰지 않는다

  • 데이터 등급(E5)이나 망 조건(E1) 때문에 공통 기반을 쓸 수 없고 그 사유가 서술된 경우
  • A2 게이트웨이를 공유하면서 부서별 코퍼스·스킬만 따로 둔 경우(정상 조립)
  • 개인이 만든 단일 도구로 기관 내 중복 과제가 없는 경우

얻는 것

  • 부서가 협의 없이 빠르게 만든다
  • 부서 요구에 딱 맞는 맞춤 구성을 갖는다

점검표

  • 기관의 모든 모델 호출이 하나의 게이트웨이를 지나는가
  • 부서별 API 키 직접 호출이 남아 있지 않은가
  • 공통 기반을 쓰지 않은 과제는 그 사유(E1·E5)가 적혀 있는가
  • 부서별 차이가 모델이 아니라 스킬·코퍼스로 표현되어 있는가

구조 — 참여 부품

  • A2 모델 서빙 계층 — 교정 후 모든 부서 호출이 모이는 공통 자리
  • A3 공공 API 제공자 — 범정부 AI 공통기반·공공 깃랩 등 Provider
  • S1 AI 게이트웨이·단일 진입점 — 부서별 API 키 직접 호출을 대체하는 인증·상한·기록 지점
  • A9 업무 규범 스킬 — 부서별 차이를 모델이 아니라 스킬로 표현

변형

  • 부서별 API 키 직접 호출: 각 과제가 상용 API 키를 따로 받아 직접 호출. S1 부재의 전형
  • 벡터DB 중복: 같은 규정·매뉴얼을 부서마다 따로 임베딩해 따로 검색
  • 프롬프트 사일로: 같은 공문 규범을 부서마다 다른 프롬프트로 재작성

평가 세트 없이 검색을 붙여 '좋아진 것 같다'로 배포하고, 검색으로 풀릴 문제를 파인튜닝으로 푸는, 진행 경로를 건너뛰는 함정이다.

맥락

B3 지식 접지·B1 코파일럿에 RAG를 붙이거나 A2.3 튜닝형 모델을 만드는 과제, 특히 규정·매뉴얼 기반 질의응답.

맞서는 힘(긴장)

  • 눈에 보이는 기술 성과 vs 지루한 평가 세트 구축
  • 빠른 배포 vs 변경마다 재는 자
  • 자체 모델 보유 인상 vs 검색으로 충분한 문제

해법

§7.2 진행 경로를 순서대로 밟는다. B1 직접 프롬프트에서 시작해 두 번째 단계에서 C9 평가 세트(업무 질문·정답·채점 기준)를 먼저 만들고, 이후 A9 규범 스킬·F4, B3 지식 접지(A1 데이터 자산), B3 검색 품질(Hybrid·Rewriting·Reranker), C5 가드레일·F1 순으로 붙이며 매 단계를 C9로 잰다. A2.3 튜닝은 진행 경로의 마지막 단계로, 검색·규범 스킬로 풀리지 않는다는 것이 C9 점수로 확인됐을 때만 한다. 모델·프롬프트·설정 조합은 릴리스처럼 버전 관리한다.

이럴 때 쓴다

  • RAG·튜닝을 도입했는데 업무 질문·정답·채점 기준 세트가 없다
  • '답변 품질 향상'을 수치 없이 서술하거나 단발 정확도만 보고한다
  • 자주 바뀌는 규정·매뉴얼 질의를 파인튜닝으로 풀었다
  • 검색 품질(재현율·리랭킹)을 재지 않고 튜닝으로 넘어갔다

이럴 때는 쓰지 않는다

  • C9 세트로 RAG 전후를 비교한 뒤 배포한 경우
  • 검색·스킬로 풀리지 않음을 C9 점수로 확인한 뒤 튜닝한 경우
  • B2·B4처럼 비LLM 학습 모델로 원래 학습이 해법인 경우(RAG가 대안이 아님)

얻는 것

  • RAG·튜닝이라는 눈에 보이는 기술 성과를 빨리 낸다
  • 평가 세트 구축에 현업 시간을 쓰지 않는다

점검표

  • 업무 질문·정답·채점 기준 세트가 있는가
  • RAG 전후 점수 비교가 있는가
  • 튜닝을 선택한 근거가 C9 점수로 설명되는가
  • 모델·프롬프트·설정 조합이 버전 관리되는가

구조 — 참여 부품

  • C9 평가 세트·회귀시험 — 빠진 부품. 모든 변경을 같은 자로 잼
  • B3 지식 접지 — 튜닝 전에 먼저 시도할 검색 기반 접지
  • A2.3 튜닝형 모델 — 진행 경로의 마지막 단계
  • A1 데이터 자산 서비스 — 정답 출처와 검색 코퍼스

변형

  • 평가 없는 RAG: 검색을 붙이고 몇 개 질문을 눈으로 보고 배포
  • RAG 없는 튜닝: 문서 검색으로 풀릴 최신 규정 질의를 파인튜닝으로 해결하려 함
  • 평가 없는 튜닝: 튜닝 전후를 같은 세트로 비교하지 않음
