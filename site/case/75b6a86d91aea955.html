B1 코파일럿 업무 컴포넌트

사람이 하던 문서·판단 작업 옆에 AI가 초안·요약·검토안을 놓고, 사람이 고쳐서 확정한다.

PAX 사례 111건이 이 부품을 쓴다

맥락

문서·기안·검토의견처럼 산출물 형식이 정해져 있고 최종 확정자가 사람인 업무에 쓴다. BYO 코딩 에이전트와 A9 스킬을 쓰는 스킬 코파일럿이 PAX 자생 도구에 많다.

맞서는 힘(긴장)

  • 초안 속도 vs 전건 검토에 드는 사람 시간
  • 상용 모델 품질 vs 행정망·민감정보 제약(E1·E5)
  • 양식 일관성(A9 규범) vs 사안별 유연성

해법

업무 서식과 참고 자료를 입력으로 받아 모델(A2 또는 BYO 구독)이 초안·근거·신뢰도를 내고, 사람이 편집 가능한 형태(F2)로 받아 고쳐서 확정한다. 보고서 구조·문체·검증 절차는 A9 규범 스킬로 코드 밖에 두고, 공공 문서 형식은 A10 어댑터로 입출력한다. 확정 전 검토는 C1 검토 큐로 운영하고 수정 내역을 C4·C6의 입력으로 남긴다. First로 가려면 저위험 건을 C2로 자동 확정하는 분기를 더한다.

이럴 때 쓴다

  • 산출물 형식이 정해진 문서를 반복 작성할 때
  • 최종 판단과 책임이 사람에게 남아야 할 때(P1 산출물 생성)
  • 유형 ④ 내부 문서·기안, 유형 ⑫ 개발 코파일럿의 기본 조립일 때

이럴 때는 쓰지 않는다

  • 답이 기관 규정·선례 속에 있어 접지와 출처가 핵심일 때(B3)
  • 추출 결과가 사람 확정 없이 다음 판정 단계로 흐를 때(B4)
  • 런타임에 모델이 필요 없는 정형 취합일 때(B0)

얻는 것

  • 문서 작성 시간 단축
  • 책임 소재가 사람에게 명확히 남음
  • 도입이 쉬워 Enabled의 전형 경로

점검표

  • 담당자가 최종 확정한다는 절차가 운영되는가
  • 서식·문체 규범이 A9 스킬로 분리되어 있는가
  • 초안을 이용자가 직접 고칠 수 있는가(F2)
  • 수정 내역이 기록되어 품질 개선에 쓰이는가

구조 — 참여 부품

  • A2 모델 서빙 계층 — 초안 생성 모델 호출(행정망이면 내부망 프록시)
  • A9 업무 규범 스킬 — 서식·문체·검증 절차를 프롬프트 템플릿으로 고정
  • A10 문서 형식 어댑터 — HWPX·엑셀 입출력
  • C1 검토 큐 — 담당자가 초안을 확인·수정·확정
  • 담당자 — 최종 확정자이자 책임자

B4 인식 파이프라인 업무 컴포넌트

서류·음성·영상·도면 같은 비정형 입력을 인식 → 구조화 → 판정으로 연쇄 처리해 사람이 옮겨 적던 단계를 없앤다.

PAX 사례 34건이 이 부품을 쓴다

맥락

접수·심사(유형 ②), 서류 진위확인, 민원 통화 정리, 실시간 자막, 원격탐사·도면 판독처럼 비정형 입력이 업무의 출발점인 경우에 쓴다. 민감 서류가 많아 행정망·로컬 모델 조건이 자주 붙는다.

맞서는 힘(긴장)

  • 자동 연결의 효율 vs 오인식이 판정으로 번지는 위험
  • 인식 정확도 vs 로컬 모델 제약(E1·E5)
  • 단계 분리의 추적 용이성 vs 단계 간 지연

해법

인식(OCR·STT·비전·VLM)은 정형 필드만 내게 하고, 기준정보와의 대조·요건 판정은 규칙 단계가 맡는다(B′1 + B′9). 저신뢰·불일치 건은 보류해 C1 검토 큐로 보내고, 오인식은 C3 상태 머신으로 되돌린다. 공공 문서 형식은 A10으로 받으며 OCR·STT 엔진은 A2 공통 후보를 쓴다. 제출 서류처럼 신뢰 불가 입력을 읽고 시스템 쓰기가 있으면 문서별 격리(S6)로 서류 속 지시가 판정을 바꾸지 못하게 한다.

이럴 때 쓴다

  • 비정형 입력을 사람이 옮겨 적는 단계가 업무의 병목일 때
  • 추출값이 규칙 판정·다음 처리로 이어질 수 있을 때
  • 유형 ② 접수·심사 자동화의 기본 조립일 때

이럴 때는 쓰지 않는다

  • 추출 결과가 초안으로 멈추고 사람이 확정할 때(B1)
  • 추출 뒤 질의응답이 핵심 산출물일 때(B3)
  • 상시 관측 스트림 감시가 핵심일 때(B5)

얻는 것

  • 옮겨 적기 단계 제거
  • 판정 기준이 규칙으로 남아 설명 가능
  • OCR·STT 엔진을 범정부 공통으로 공유 가능

점검표

  • 인식과 판정이 서로 다른 단계로 분리되어 있는가
  • 저신뢰 건이 보류되어 사람에게 가는가
  • 오인식 건을 되돌리는 경로가 있는가(C3)
  • 필드별 정확도를 잰 시험 세트가 있는가

구조 — 참여 부품

  • A10 문서 형식 어댑터 — PDF·HWPX·이미지 입력
  • A2 모델 서빙 계층 — OCR·STT·VLM 엔진
  • 규칙 대조기 — 기준정보와 대조하고 요건을 판정
  • C1 검토 큐 — 저신뢰·불일치 건 확인
  • C3 상태 머신·롤백 — 오인식 되돌림·재처리

변형

  • OCR·서류: 제출 서류 필드 추출·요건 검토
  • STT·음성: 통화·회의 음성의 텍스트화와 키워드 추출
  • 비전 판독·정량화: 결함·손상 판독과 정량화(R5)
  • VLM 문서이해(단일 모델): VLM 하나로 문서 이해·추출(R5)
  • 배치 원격탐사·시계열 차분: 항공·위성 영상의 회차 간 변화 판독(R5)
  • 통역(STT→MT→TTS): 음성 인식·번역·합성 연쇄(R5)
  • CAD·BIM 도면 파싱: 도면에서 구조 정보 추출(R5)

참조 구현 예

  • PAX 경기도의회 실시간 자막 — 개인 개발 → 기관 도메인 정식 개통(카드 참조 구현)

관련 부품

B′1 기본 배선 — 순차 파이프라인 · B′9 배선 — 인식은 추출만, 판정은 규칙 · C3 First 관문 — 오인식 되돌림 · S6 보안 짝 — 제출 서류별 격리 처리 · F9 이용자 쪽 대응 — 판정 근거 표시(위조 탐지는 관리자에게만)

B3 지식 접지 상담 업무 컴포넌트

기관 규정·매뉴얼·사례 문서에 접지(RAG)해 질문에 답하고, 답마다 출처를 붙이며, 근거가 없으면 답하지 않고 담당자에게 넘긴다.

PAX 사례 48건이 이 부품을 쓴다

맥락

규정·매뉴얼·FAQ·사례가 문서로 쌓인 기관에서 내부 검색·검수, 대민 자동응답, 폐쇄망 로컬 검색에 쓴다. PAX 557건에서 주 부품이 B3인 사례는 31건으로 B0·B1 다음이다. 유형 ① 대민 상담·안내의 기본 조립이기도 하다.

맞서는 힘(긴장)

  • 답변 범위 vs 환각 위험(근거 밖 답변 금지)
  • 대민 자동응답의 효율 vs 예외 건 이관 필요
  • 검색 품질 개선 vs 평가 세트 없이는 개선을 잴 수 없음
  • 폐쇄망 요구 vs 로컬 임베딩·모델 품질

해법

기관 문서를 A1 자산으로 정리해 임베딩·색인하고, 질문이 오면 검색한 근거 범위 안에서만 모델이 답하게 한다. 답에는 출처(F1)를 상시 붙이고, 근거가 없으면 '확인 불가'로 답하거나 담당자·소관기관으로 이관한다(B′2). 검색 품질은 Hybrid Retriever·Query Rewriting·Reranker로 높이되, 변경마다 C9 평가 세트로 잰다. 대민형은 한계 안내(F7)와 폴백(C7)을 두고, 문서 갱신 주기를 C6으로 정한다.

이럴 때 쓴다

  • 같은 질문이 반복되고 답의 근거가 기관 문서에 있을 때
  • 답변에 조문·문서 출처를 반드시 붙여야 할 때
  • 유형 ① 대민 상담·안내, 유형 ⑦ 법령 접지 점검

이럴 때는 쓰지 않는다

  • 평가 세트가 없어 검색 품질을 잴 수 없을 때(먼저 C9, X10)
  • 질문 유형이 몇 개로 정해져 행동 선택기(S4)나 규칙 조회로 충분할 때
  • 문서를 요약해 초안을 쓰는 것이 핵심이면(B1)

얻는 것

  • 답변에 근거를 댈 수 있음
  • 반복 질의 처리 시간 단축
  • 범정부 엔진 + 기관별 코퍼스로 공유 가능

점검표

  • 답마다 출처가 표시되는가
  • 근거가 없을 때 답하지 않고 이관하는가
  • 평가 세트로 검색·답변 품질을 재고 있는가
  • 코퍼스 갱신 주기와 책임자가 정해져 있는가

구조 — 참여 부품

  • A1 데이터 자산 서비스 — 코퍼스 정제·등급 메타
  • A2 모델 서빙 계층 — 임베딩·생성 모델(폐쇄망이면 로컬)
  • 검색기 — 벡터·키워드 검색, 재작성·재순위
  • C5 가드레일 필터 — 출처 검증·근거 밖 답변 차단
  • F1 출처 표시 — 근거 문서·조문을 답에 표시
  • 담당자 — 내부형 검수, 대민형 예외 건 처리

변형

  • 내부 검수형: 직원이 쓰고 답을 검수(Enabled)
  • 대민 자동응답형: 국민에게 직접 답하고 예외만 이관(이관 분기가 있으면 First)
  • 폐쇄망 로컬 RAG: 내부망 LLM + 로컬 임베딩·벡터DB
  • 검색 품질 하위 항목: Hybrid Retriever(벡터+키워드)·Query Rewriting·Reranker. 태깅 시 variant에 기재(Fowler)
  • 그래프 RAG: A6 지식그래프를 검색에 결합(rag_type = Graph)

참조 구현 예

  • PAX 전북AI — 자체 구축, 이용 10만 건(카드 참조 구현)
  • PAX 소방기술민원 답변생성기 — 관리자 승인·적재, '유권해석 아님' 고지(카드 참조 구현)
  • PAX bfcd190155ae69f7 — 코레일유통 그래프RAG 사내검색, 개인 시범 구축 → 기관 공식 플랫폼(§13)

관련 부품

C9 선행 — 평가 세트 없이 검색 품질을 개선할 수 없음 · F1 이용자 쪽 대응 — 출처 표시 · B′2 배선 — 근거 없거나 예외인 질문을 담당자로 이관 · A6 선택 부품 — 그래프 RAG · S2 보안 짝 — 등급 문서가 섞인 코퍼스의 권한 인식 검색 · C7 대민 상시 서비스의 폴백

B6 에이전트 오케스트레이터 업무 컴포넌트

역할을 나눈 LLM들이 도구를 호출하며 계획을 세우고 다단계 업무를 이어 가며, 사람은 승인과 예외 처리를 맡는다.

PAX 사례 15건이 이 부품을 쓴다

맥락

여러 시스템·도구(A8 MCP·API·문서)를 오가는 다단계 업무, 데이터 조회·분석 에이전트(유형 5b), 망분리 환경의 로컬 MCP 호스트에 쓴다. 하위 작업이 실제로 분리되거나 AI가 도구를 골라야 할 때만 해당한다.

맞서는 힘(긴장)

  • 자율성 vs 권한 통제(P2 이상에서 C8 필수)
  • 멀티에이전트의 분업 vs 조정 비용·충돌(X11)
  • 도구 출력 활용 vs 도구 출력 속 지시가 명령이 되는 위험(X13)
  • 탐색적 유연성 vs 재생·감사 가능성

해법

목표와 도구 목록(A8 MCP·API)을 받아 AI가 계획을 세우고 도구를 골라 호출하며, 필요하면 하위 전문 에이전트에 위임한다(B′4·B′7·B′8). 단일 에이전트에서 시작해 하위 작업이 분리될 때만 계층·병렬로 승급한다. 도구별 읽기/쓰기 권한과 실행 승인은 C8로, 단계 상태와 되돌림은 C3로, 모든 호출은 C4 추적 로그로 남긴다. 신뢰 불가 입력을 읽는 경우 S5 계획 고정이나 S6 격리로 도구 출력이 새 행동을 끼워 넣지 못하게 하고, 되돌리기 어려운 조치 앞에는 F6 확인을 둔다.

이럴 때 쓴다

  • 한 건의 처리가 여러 시스템 조회·작성·검증에 걸쳐 있고 AI가 도구 순서를 골라야 할 때
  • 하위 작업이 실제로 분리되거나 컨텍스트 창이 부족할 때
  • C8·C3·C4 통제를 함께 갖출 수 있을 때

이럴 때는 쓰지 않는다

  • 단계 순서가 고정된 파이프라인일 때(B′1을 가진 B1·B4)
  • 실제 흐름이 초안 → 사람 확정일 때(B1)
  • 스케줄러·크롤러 수준 자동화일 때(agent_system=true라도 B6 아님)
  • 단일 에이전트가 되기 전에 멀티에이전트부터 만들려 할 때(X11)

얻는 것

  • 여러 시스템을 오가는 업무 흐름 자체를 재설계
  • 도구 교체로 다른 기관이 그래프를 재사용 가능
  • First 지향 구조

점검표

  • 복수 LLM 역할·도구 호출 루프·AI의 계획 선택이 실제로 있는가(R2)
  • 도구별 읽기/쓰기 권한과 실행 승인이 명시되어 있는가
  • 모든 도구 호출이 추적되는가
  • 도구 출력이 새 행동을 촉발하지 못하게 막는 구조가 있는가

구조 — 참여 부품

  • 계획·감독 에이전트 — 목표를 쪼개고 도구·하위 에이전트를 선택
  • 전문 하위 에이전트 — 조회·작성·검증 등 역할별 수행
  • A8 MCP 서버·호스트 — 도구 인터페이스와 레지스트리
  • C8 권한 경계·킬스위치 — 도구별 권한·실행 승인·즉시 중단
  • C4 감사 로그·지표 — 호출 추적
  • 담당자 — 승인 관문과 예외 처리

변형

  • 멀티에이전트 오케스트레이션: 감독자가 역할별 에이전트에 일을 맡기고 결과를 합친다
  • 관문 내장형(스테이지-게이트): 파이프라인 안에 사람 승인 관문이 여럿 있다(R2)
  • 단일 에이전트 도구 연쇄: 하나의 에이전트가 계획하고 여러 도구를 호출한다(R2)
  • 자가검증 루프 내장: 실행 결과를 스스로 검증하고 재시도한다(R2)
  • 로컬 MCP 호스트: 망분리 환경에서 도구별 위험도·실행 승인·감사 대시보드를 갖춘다(E1 폐쇄망이면 이 변형만 가능)
  • 시뮬레이션: 여러 에이전트로 정책·여론 등을 모의 실행한다

B′2 라우터·디스패처 제어 흐름

요청의 의도·유형·난이도를 읽어 전문 경로·모델·도구·담당자로 보내는 배선이다. 모든 건을 같은 경로로 보내는 낭비를 막는다.

PAX 사례 23건이 이 부품을 쓴다

맥락

대민 상담(B3)의 예외 이관, 규칙 선필터로 LLM 호출 줄이기, 폐쇄망 모델과 외부 모델 사이의 모델 라우팅, 여러 MCP를 한 서버에서 경로별로 제공하는 구성에 쓴다. C2 위험도 라우터의 내부 원형이고, D4 분류·이관을 기술로 구현한 실체다.

맞서는 힘(긴장)

  • 경로 분리의 효율 vs 라우팅 오류라는 새 위험
  • 규칙 라우팅의 예측 가능성 vs 모델 라우팅의 유연성
  • 외부 모델 분기의 품질 vs 경계 통제(E1·E5)

해법

요청을 분류하는 단계(규칙·경량 모델·LLM)를 앞에 두고, 분류 결과마다 처리 경로(규칙 판정, LLM 판정, 담당자 이관, 판단 불필요)를 정한다. 경로별 처리 비율을 C4로 실측해 라우팅 품질을 보고, 분류가 불확실한 건은 사람에게 보낸다(C2·F11). 모델 라우팅은 A2 서빙 계층의 기능으로 두고 외부 모델로 나가는 분기에는 C5 비식별을 건다. 보안이 필요한 대민 접점에서는 LLM이 미리 정한 행동 중 선택만 하게 제약해 S4로 만든다.

이럴 때 쓴다

  • 요청 유형마다 처리 비용·방법이 뚜렷이 다를 때
  • 답할 수 없는 건을 담당자로 이관해야 할 때(유형 ① 대민 상담)
  • LLM 호출 비용을 줄여야 할 때

이럴 때는 쓰지 않는다

  • 요청 유형이 하나뿐일 때
  • 분류 오류의 비용이 큰데 분류 품질을 잴 방법이 없을 때
  • 라우팅 대신 규칙으로 판정 모델 호출 대상 자체를 좁히는 구조일 때(B′10)

얻는 것

  • 호출 비용 절감
  • 답할 수 없는 건의 이관
  • 경로별 전문화

점검표

  • 경로별 처리 비율을 실측하는가
  • 분류가 불확실할 때 사람에게 가는 경로가 있는가
  • 외부 모델로 나가는 분기에 비식별이 걸려 있는가

구조 — 참여 부품

  • 분류기 — 의도·유형·난이도 판별(규칙 또는 모델)

  • C2 위험도 라우터 — 위험도·신뢰도 기반 사람 이관
  • C4 감사 로그·지표 — 경로별 처리 비율 실측

변형

  • 모델 라우팅: 기본은 폐쇄망 사내 모델, 필요할 때만 외부 모델로 분기(InfoQ Intelligent Model Routing)

  • 현장 기기 자체에서 돌아야 하면 A5(엣지 런타임)

A8 MCP 서버·호스트 공통 서비스

공공 API·업무 시스템·로컬 파일을 에이전트가 부를 수 있는 도구로 감싸고, 도구 목록·권한·호출 로그를 한 층에서 관리한다.

PAX 사례 94건이 이 부품을 쓴다

맥락

에이전트(B6)·코파일럿(B1)이 도구를 호출하는 과제나, 공공데이터를 AI 도구로 공개하려는 기관에 쓴다. E3 값은 MCP·CLI 설정이다. 유형 5b에서는 필수이고(R10 'A8 또는 자체 도구 인터페이스'), 서버만 있는 사례는 5b-server로 분류한다(A8·S11 필수, R18).

맞서는 힘(긴장)

  • 도구 재사용·생태계 확산 vs 권한 표면 확대
  • 도구 설명의 편의 vs 실제 권한과의 불일치(X7)
  • 서버 개수 성과 vs 실제 업무 호출(X8)
  • 도구 출력 활용 vs 도구 출력을 타고 오는 간접 인젝션(X13)

해법

공공 API·업무 시스템·로컬 파일을 도구 설명·인증·정책과 함께 MCP 서버로 감싸 에이전트에 노출하고, 호출 결과에 출처·갱신 시각을 붙이며 호출 로그를 남긴다. 읽기(P0) 서버와 쓰기(P2) 서버를 분리하고 C8로 도구별 실행 승인을 건다. 배포·등재 전에 PAX MCP 6축 검증(권한 표면·비밀·공급망·위생·인젝션·데이터 흐름)을 통과시키고 S11로 반입을 검사하며, 통과하지 못한 축이 있으면 전이 범위를 부서 공유 이하로 둔다. 도구 목록·버전·갱신 공지는 레지스트리(Service Discovery)로 관리한다. 폐쇄망에서는 로컬 모델(A2.2)로 여러 MCP를 구동하는 로컬 호스트 변형을 쓴다.

이럴 때 쓴다

  • 에이전트가 공공 API·업무 시스템을 도구로 호출해야 할 때
  • 기관 데이터를 외부 AI 클라이언트와 타 기관이 직접 호출하게 공개할 때
  • 표준 시스템에 API를 열어 레거시 오버레이(B8)를 대체할 때

이럴 때는 쓰지 않는다

  • 호출할 도구가 로컬 파일뿐인 단순 작업(§5 E1 로컬 PC 행: 드묾)
  • 실제 업무 호출 없이 서버 개수를 성과로 삼으려 할 때(X8)
  • 6축 검증·권한 분리를 할 수 없는데 쓰기 도구를 노출하려 할 때

얻는 것

  • 도구 재사용과 생태계 확산
  • 권한·호출을 한 층에서 관리
  • 공공데이터를 AI가 직접 쓰는 경로

점검표

  • 도구 설명이 '조회'인데 쓰기·실행 권한을 가진 도구가 없는가
  • 6축 검증 결과가 기록되어 있는가
  • 호출 로그와 실제 업무 호출 지표가 있는가
  • 호스트가 도구 출력을 명령으로 받지 않도록 S5·S6 등이 있는가(P2 이상)

A10 문서 형식 어댑터 공통 서비스

HWP·HWPX·엑셀·한셀·PDF 같은 한국 공공 문서 형식을 AI 부품이 읽고(구조화) 쓰게(서식 생성) 하는 변환 계층이다.

PAX 사례 136건이 이 부품을 쓴다

맥락

문서를 입력으로 받거나 기안·보고서·취합본을 산출하는 과제라면 거의 다 쓴다. 유형 2·4·8에서는 필수 기반이고 유형 6·7에서도 쓰인다. E1 로컬 PC 조건에서 도는 경우가 많다.

맞서는 힘(긴장)

  • 형식 충실도(표·각주·조항 구조 보존) vs 파서 구현 비용
  • 로컬 처리(무반출) vs 클라우드 변환 도구의 편의
  • 기관별 서식 다양성 vs 공통 어댑터 재사용

해법

입력 쪽에서는 HWPX 압축 구조·PDF에서 조·항·호·별표 계층과 표를 보존해 구조화 텍스트·표로 바꾸고, 머리말·각주 같은 잡음을 걷어 조항 단위로 정규화한다. 출력 쪽에서는 스킬(A9)의 출력 서식을 받아 HWPX·XLSX 기안 서식을 역방향으로 생성한다. 민감 문서는 PC 밖으로 보내지 않도록 로컬에서 변환하고, 파서를 라이브러리·CLI·MCP로 함께 제공하면 다른 부품과 기관이 그대로 쓴다. 형식 변환 정확도는 C9 판정 체계로 잰다.

이럴 때 쓴다

  • 입력이 HWP·HWPX·엑셀·PDF 공공 문서일 때
  • 산출물을 기안·보고 서식으로 내보내야 할 때
  • 유형 2·4·8 조립

이럴 때는 쓰지 않는다

  • 스캔 이미지·음성처럼 인식이 필요한 입력은 B4 인식 파이프라인(OCR·STT)
  • 입출력이 이미 정형 데이터·API인 경우

얻는 것

  • 공공 문서를 AI 입력·출력으로 연결
  • 기관 간 재사용 가능한 공통 부품
  • 로컬 처리로 무반출

점검표

  • 표·조항 계층이 변환 후에도 보존되는가
  • 출력이 기관 기안 서식 그대로 열리는가
  • 민감 문서가 변환 과정에서 PC 밖으로 나가지 않는가
  • 변환 정확도 판정 기록이 있는가

구조 — 참여 부품

  • 입력 파서 — 조·항·호·표 구조를 보존해 구조화
  • 서식 생성기 — 구조화 결과를 HWPX·엑셀 서식으로 출력
  • A9 업무 규범 스킬 — 출력 서식 규범 제공
  • B3 지식 접지 상담 — 구조화된 규정을 색인해 검색

변형

  • 엑셀·한셀 취합: 폐쇄망에서 엑셀·한셀 파일을 취합한다(GatherFlow).

얻는 것

  • 현장 작업자의 손 자유
  • 채널을 바꿔도 업무 로직 유지

점검표

A1 데이터 자산 서비스 공통 서비스

흩어진 업무 기록을 정제·라벨링해 AI 부품이 붙여 쓸 수 있는 데이터셋·라벨·데이터 사전 형태의 기준선으로 제공한다.

PAX 사례 110건이 이 부품을 쓴다

맥락

학습 모델(A2.5·B2), 지식 접지(B3)의 코퍼스, 평가 세트(C9)의 정답 출처가 필요한 과제라면 모두 이 부품을 쓴다. 서비스 유형 5a·9·10·11에서는 필수 기반이다. 비LLM 규칙 기반 대민 안내에서는 A2를 거치지 않고 결정론 조회의 대상이 된다(R21).

맞서는 힘(긴장)

  • 정제 품질 vs 구축 기간·라벨링 인력 비용
  • 과제 전용 가공(빠름) vs 기관 공통 기준선(재사용)
  • 데이터 활용 범위 vs 데이터 등급(E5) 보호
  • 기준선 고정(재현성) vs 원천 갱신 반영

해법

원천 기록을 수집→정제(중복·결측 처리)→라벨링→정의 문서화 순으로 가공하고, 결과를 정제 데이터셋·라벨·데이터 사전의 세 산출물로 고정해 제공한다. 'N건→M건 정제'처럼 정제 전후 규모와 기준을 기록하고, 변수·테이블·인터페이스 정의서로 소비 부품이 같은 정의를 쓰게 한다. 기준선은 버전으로 관리해 C9 평가 세트의 정답 출처와 C6 재학습의 입력으로 재사용한다. 데이터 경계는 부품별로 두고(DB per Service), 타 기관 데이터와의 결합은 A4로 분리한다.

이럴 때 쓴다

  • 예측·추천기(B2)나 비전 모델(A2.5)을 학습·재학습할 때
  • 지식 접지(B3)의 코퍼스를 구축할 때
  • 평가 세트(C9)의 정답 출처가 필요할 때
  • 서비스 유형 5a-agg·9·10·11처럼 A1이 필수인 조립

이럴 때는 쓰지 않는다

  • 공공 API 응답을 가공 없이 조회만 할 때(A3)
  • 정제·정의 없이 파일을 올려 바로 검색하는 경우(태그 대상 아님)
  • 타 기관 데이터 결합이 핵심일 때는 A4를 함께 태그해 계약·키 매핑을 따로 드러낸다

얻는 것

  • 모델 교체와 무관하게 남는 기관 자산
  • C9·C6·B3가 같은 기준선을 재사용
  • 데이터 사전이 기관 간 표준 확산의 단위가 됨

점검표

  • 정제 전후 규모와 정제 기준이 기록되어 있는가
  • 데이터 사전(정의·단위·출처)이 있는가
  • 기준선에 버전이 있고 평가용 분할이 학습용과 분리되어 있는가
  • 데이터 등급(E5)에 맞는 가명·비식별 처리가 적용되었는가

구조 — 참여 부품

  • 원천 시스템·기록 — 가공 전 업무 기록을 내주는 출처
  • 정제·라벨링 파이프라인 — 중복 제거·결측 처리·라벨 부여·품질관리를 수행
  • 데이터 사전 — 정의·단위·출처를 문서로 고정해 소비 부품이 같은 뜻으로 쓰게 함
  • C9 평가 세트·회귀시험 — 기준선을 정답 출처로 사용
  • A2.5 비LLM 학습 모델 — 기준선으로 학습·재학습하는 소비 부품

A7 자체 제작 환경 공통 서비스

외부 용역 없이 기관 인력이 저작도구·AI 코딩 에이전트로 도구를 직접 만들고 고치는 제작 환경이다.

PAX 사례 317건이 이 부품을 쓴다

맥락

업무 담당자가 AI 코딩 도구·저작도구·오픈소스로 직접 만드는 과제에 쓴다. 유형 8(취합·변환 자동화)에서는 필수 기반이다. PAX 557건에서 A7이 붙고 BYO 모델을 쓰는 사례는 29건이다.

맞서는 힘(긴장)

  • 제작 속도·현장 적합성 vs 유지보수 연속성
  • 개인 역량 의존 vs 조직 인수인계
  • 무예산 제작 vs 보안 검토·기관 공식화 절차

해법

기관 인력이 AI 코딩 에이전트·저작도구·오픈소스로 직접 만들되, 처음부터 전이를 전제로 한다. 설정·데이터(연락처·업무분장 등)는 코드 밖 파일로 빼 비개발자도 고치게 하고, 작업 지시서 자체를 코딩 에이전트가 수행할 프롬프트로 설계해 제작 절차를 남긴다. MIT·Apache 등 라이선스를 명시하고 공공 깃랩(A3)이나 혁신24 자료실에 등재해 담당자가 바뀌어도 이어지게 한다. 실사용 건수로 성과를 재 기관 공식으로 올린다.

이럴 때 쓴다

  • 반복 업무를 줄이는 소규모 도구를 빠르게 만들 때
  • 용역 없이 작은 수정을 계속해야 할 때
  • 유형 8 취합·변환 자동화

이럴 때는 쓰지 않는다

  • P2 이상 시스템 쓰기·처분이 걸려 보안 검토·통제 부품이 먼저 필요한데 이를 갖출 수 없을 때
  • 라이선스·저장소·인수인계를 정할 수 없어 전이가 불가능할 때(X9 위험)

얻는 것

  • 제작 속도와 현장 적합성
  • 내부 유지보수 역량 축적
  • 무예산·소예산 제작

점검표

  • 라이선스가 명시되어 있는가
  • 저장소가 개인 PC가 아닌 공유 위치에 있는가
  • 담당자가 바뀌어도 고칠 수 있는 문서·설정 분리가 있는가
  • 실사용 지표가 있는가

구조 — 참여 부품

  • 업무 담당자 — 요구를 알고 직접 만드는 제작자
  • AI 코딩 에이전트·저작도구 — 코드·화면·워크플로 생성
  • A3 공공 깃랩·자료실 — 등재처 — 담당자 이동 후에도 이어지게
  • A9 업무 규범 스킬 — 제작 규범·지시서를 재사용 가능한 형태로

변형

  • 비개발자 바이브코딩: 교육 후 비개발 직원이 AI 코딩으로 웹앱을 만들고 실사용 지표까지 잰다.
  • 용역 탈피 단계형: 1단계는 전문기업과, 2단계는 직원이 도구를 대여해 라벨링·학습·개발을 직접 한다.
  • 오픈소스 조립형: n8n·FastAPI·Qdrant·LM Studio 등 오픈소스로 워크플로를 직접 조립하고 설정을 공유한다.

A3 공공 API 제공자 공통 서비스

정부·공공이 운영하는 모델·데이터·개발 도구(범정부 AI 공통기반, 모두의 AI 실험실, 공공데이터포털, 공공 깃랩)를 범정부 Provider로 소비한다.

PAX 사례 154건이 이 부품을 쓴다

맥락

모델·공공데이터·법령 원문·개발 환경을 공공 플랫폼에서 가져올 수 있다면 어느 과제든 해당한다. §7.1 2단계 '기반 부품은 새로 만들지 말고 Provider에서 먼저 찾는다'가 바로 이 부품을 가리킨다. 유형 7(대조·점검)에서는 법령·기준 출처를 대는 필수 기반이다.

맞서는 힘(긴장)

  • 공통 Provider 재사용 vs 기관 고유 요구 반영
  • 공공 API 가용성·갱신 주기 vs 서비스 신뢰성
  • 인가·검증 절차의 통제 vs 에이전트 루프의 병목(PAX 공공API 진단)

해법

기반을 새로 만들기 전에 범정부 AI 공통기반(모델), 공공데이터포털·법령 API(데이터), 모두의 AI 실험실·공공 깃랩(개발·실험 환경)에서 먼저 찾아 소비한다. 인증은 GPKI·디지털원패스 같은 연합 신원(Federated Identity)으로 위임하고, 공공 API 응답은 출처·조회 시각과 함께 업무 부품에 넘긴다. 에이전트가 부를 수 있게 하려면 A8 MCP 서버로 감싸고, 결과를 재가공해 기준선으로 고정하면 A1을 더한다. 기관이 만든 도구는 공공 깃랩에 등재해 다음 기관의 Provider가 되게 한다.

이럴 때 쓴다

  • 모델·데이터·개발 환경을 기관이 새로 만들려 할 때 — 먼저 Provider 확인
  • 법령·기준 원문을 최신으로 대조해야 하는 유형 7
  • 여러 부서가 같은 기반을 따로 만들고 있을 때(X3 교정)

이럴 때는 쓰지 않는다

  • 필요한 모델·데이터가 공공 Provider에 없을 때(만들고 레지스트리에 올림)
  • 타 기관 데이터를 계약·키 매핑으로 결합하는 경우는 A4

얻는 것

  • 기관별 중복 구축 방지(X3 교정)
  • 공인된 원천 데이터·모델 사용
  • 등재를 통해 전이 경로 확보

점검표

  • 같은 기반을 기관 안에서 따로 만들지 않았는가
  • 공공 API 응답의 출처·조회 시각이 결과에 남는가
  • API 장애·변경 시 어떻게 되는지 답할 수 있는가
  • 만든 도구가 공공 깃랩 등에 등재되었는가

구조 — 참여 부품

  • 공공 Provider — 범정부 AI 공통기반·공공데이터포털·모두의 AI 실험실·공공 깃랩
  • 연합 신원 인증 — GPKI·디지털원패스 등으로 호출 주체를 확인
  • 소비 부품(B·A2·A8) — Provider를 직접 만들지 않고 가져다 씀
  • S1 AI 게이트웨이·단일 진입점 — 공공 인증을 위임받아 호출을 통제

변형

  • 공공 모델 Provider: 범정부 AI 공통기반(HCX-GOV-THINK) 위에서 모델을 소비한다. 온나라 AI 문서 분배기가 공통기반 RAG 위에서 돈다.
  • 공공 데이터·법령 Provider: 공공데이터포털 OpenAPI·법제처 API 등을 실서비스 파이프라인에 상시 연동한다.
  • 개발·실험 환경 Provider: 모두의 AI 실험실·공공 깃랩에서 개발하고 결과물을 등재한다.

참조 구현 예

  • PAX ef389de4efadc258 — 법제처 API로 매일 최신성 검증(§13 A3)
  • PAX 3d07b6da99f5e1ed — 직제·시행규칙을 법령 API로 파싱·결합, 시행일 스냅샷 비교(§13 A3)

C8 권한 경계·킬스위치 운영 컴포넌트

AI 부품이 할 수 있는 일의 상한을 P0~P4로 못 박고, 도구별 실행 승인·읽기/쓰기 분리·속도 제한·즉시 중단 스위치를 제공한다.

PAX 사례 22건이 이 부품을 쓴다

맥락

도구를 호출하거나 시스템에 쓰는 B6 오케스트레이터, A8 MCP 서버·호스트, B8 레거시 오버레이, 처분 보조(P3) 서비스. 유형 ⑤b 데이터 에이전트, ⑨ 인수인계(접근 범위).

맞서는 힘(긴장)

  • 자동화 범위 vs 통제
  • 승인 절차의 안전 vs 이용 마찰
  • 도구 설명의 편의 vs 실제 권한과의 일치 검증 비용

해법

부품별 허용 권한 범위(P0 읽기 전용 ~ P4 자율 처분)를 정하고, 도구 목록마다 읽기/쓰기를 분리한다. 위험도가 높은 도구는 실행 전 사람 승인(C2·F6)을 받게 하고, 호출 상한(속도 제한)을 둔다. 전역 킬스위치로 즉시 중단할 수 있게 하고, 승인·실패·중단 이력을 C4에 남긴다. MCP 도구는 설명과 실제 권한이 일치하는지 A8 6축 검증으로 확인한다.

이럴 때 쓴다

  • E4 P2 이상(필수, First 관문)
  • E3 MCP·CLI 환경에서 에이전트가 도구를 호출할 때
  • B6 오케스트레이터에 상용 API를 쓰는 경우(A2 + C7 + C8 도구별 승인)
  • 유형 ⑤b-host, ⑨ 인수인계(접근 범위)

이럴 때는 쓰지 않는다

  • 도구 호출·시스템 쓰기가 없는 서술 전용 코파일럿(P1)
  • B0 결정적 도구로 AI가 행동을 고르지 않을 때

얻는 것

  • 되돌릴 수 없는 조치 방지
  • 도구 설명과 실제 권한의 불일치(X7) 예방
  • 감사 가능한 행동 기록

점검표

  • AI가 쓸 수 있는 시스템 목록을 답할 수 있는가
  • 도구별 읽기/쓰기 구분과 위험도가 있는가
  • 고위험 도구에 실행 승인이 걸려 있는가
  • 킬스위치가 있고 누가 누를 수 있는지 정해져 있는가
  • 도구 설명과 실제 권한이 일치하는가

구조 — 참여 부품

에이전트가 실행하려는 행동(도구·대상·인자·예상 결과)을 이용자가 이해할 수 있는 말로 먼저 보여 주고, 확인·수정·취소를 받은 뒤 실행한다. 확인 대상은 C8 권한 정책의 위험도로 정해, 되돌리기 어려운 조치에 집중한다. 확인 결과는 C4에 남긴다.

이럴 때 쓴다

  • E4 P2 이상(필수)
  • 되돌리는 데 사람 시간이 많이 드는 조치
  • 유형 ②·⑤b의 필수 상호작용

이럴 때는 쓰지 않는다

  • P0 읽기 전용 조회로 부작용이 없을 때
  • 쉽게 되돌릴 수 있는 저위험 조치(확인 피로를 피함)

얻는 것

  • 되돌릴 수 없는 조치 방지
  • 이용자가 에이전트 행동을 이해

점검표

  • 되돌리기 어려운 행동이 실행 전 확인을 거치는가
  • 확인 화면이 대상·인자·예상 결과를 보여 주는가
  • 확인 이력이 기록되는가

구조 — 참여 부품

  • C8 권한 경계·킬스위치 — 확인이 필요한 행동의 기준

F7 한계·신뢰도 안내 상호작용 패턴

AI가 무엇을 못 하는지, 얼마나 확신하는지, 공식 판단이 아님을 이용자가 볼 수 있는 곳에 적어 과신을 막는다.

PAX 사례 63건이 이 부품을 쓴다

맥락

대민 상담·안내(유형 ①), 대조·점검(⑦), 분석·예측(5a·⑩), 비식별 도구(⑬). 대체 경로로 운영 중인 C7 상황.

맞서는 힘(긴장)

  • 정직한 한계 고지 vs 서비스 신뢰도 하락 우려
  • 신뢰도 수치 표시의 정확성 vs 이용자 이해

해법

화면에 사용 한계(대상 범위·미검증 항목·처리 시간), 신뢰도, '공식 판단 아님' 고지를 결과 옆에 배치한다. 저신뢰 결과는 표시를 달리하고, C7 대체 경로로 운영 중이면 품질 저하를 알린다. 고지 문구는 법률 자문·유권해석을 대체하지 않는다는 점을 분명히 적는다.

이럴 때 쓴다

  • 대민 서비스 D1~D7(F1·F2·F7 최소 요건)
  • 유형 ①⑦5a⑩⑬처럼 F7이 필수인 유형
  • C7 대체 경로 운영 중

이럴 때는 쓰지 않는다

  • 유형 ①·⑦에서 model_dependency가 없음(비LLM)이면 필수에서 면제(R7). 단 비LLM 도구도 한계 고지는 권장된다

얻는 것

  • 과신·오인 방지
  • 기관 책임 범위 명확화

점검표

  • 이용자가 '공식 판단이 아님'을 결과 화면에서 읽을 수 있는가
  • 사용 한계가 명시되어 있는가
  • 저신뢰 결과가 구분 표시되는가

구조 — 참여 부품

  • 고지 문구 — 사용 한계·공식 판단 아님
  • 신뢰도 표시 — 결과별 확신 수준

변형

D8.3 초안·기안 서비스 블록

보고서·공문·답변·직무기술서·제안서의 첫 판을 서식에 맞춰 만드는 내부 운영 블록이다. B1 스킬 코파일럿에 A9 규범 스킬과 A10 HWPX 어댑터가 붙는다.

PAX 사례 64건이 이 부품을 쓴다

맥락

기관 내부 문서의 첫 판을 만드는 업무. §7.3 유형 ④ 내부 문서·기안 코파일럿(D8.3 · D8.2, P1)과 유형 ⑫ 개발 코파일럿(D8.3, P1)의 무대. PAX 64건(주 부품 B1 64%, B0 20%), 문서·기안 영역 31건.

맞서는 힘(긴장)

  • 초안 속도 vs 규범·서식 적합성
  • 편집 가능 출력 vs 완성본처럼 보이는 초안의 과신
  • 기관 문서 반출 제약 vs 상용 모델 품질
  • 생성자-비평가 반복 품질 vs 비용(반복 상한)

해법

B1 코파일럿이 초안을 만들되, 보고서 구조·문체·서식·검증 절차를 A9 규범 스킬로 코드 밖에 패키징해 재사용하고, 출력은 A10 어댑터로 HWPX 등 기관 서식에 맞춘다. 품질은 B′5 생성자-비평가로 올리되 반복 상한(2~3회)을 둔다. 출력은 F2 편집 가능 형태로 내고, F5 참고자료 첨부로 범위를 좁히고, F3로 대안을 준다. 담당자가 C1로 확정하고, C5 비식별로 첨부 속 개인정보를 거르며, C9 평가 세트로 스킬 변경을 잰다. 개발 코파일럿이면 S9 샌드박스를 더한다.

이럴 때 쓴다

  • 서식이 정해진 문서의 첫 판을 반복해 쓸 때
  • AI 초안을 다시 기관 서식에 옮기느라 시간이 들 때
  • 문서 규범을 여러 사람이 같은 방식으로 적용해야 할 때

이럴 때는 쓰지 않는다

  • 기존 문서를 요약·추출만 하면 D8.2
  • 초안을 규정·인용과 대조해 점검하는 것이 목적이면 D8.4(우선순위 높음)
  • 보도자료·카드뉴스처럼 발행물이면 D8.10(우선순위 높음)

얻는 것

  • 첫 판 작성 시간 단축
  • 기관 규범의 일관 적용
  • 스킬 단위 재사용

점검표

  • 초안이 기관 서식 그대로 열리고 고쳐지는가
  • 규범이 프롬프트가 아니라 재사용 스킬로 분리되어 있는가
  • 스킬 변경을 평가 세트로 재는가
  • 담당자 확정 없이 기안으로 나가지 않는가

구조 — 참여 부품

  • 담당자 — 요청·참고자료를 주고 초안을 고쳐 확정

D8.1 탐색·조회 서비스 블록

데이터·법령·공고·선례·타 지역 사례를 찾아 담당자 화면에 놓는 내부 운영 블록이다. B0 탐색·시각화, MCP 도구 제공, B3가 전형 부품이다.

PAX 사례 176건이 이 부품을 쓴다

맥락

기관 내부 담당자가 자료를 찾아 보는 업무. §7.3 유형 ⑤b 데이터 에이전트(D8.1, P0)와 ⑤a 분석 대시보드·브리핑(D8.1, P0~P1)의 무대. PAX 176건(주 부품 B0 80%, B3 10%).

맞서는 힘(긴장)

  • 검색 편의 vs 출처·기준 시점 확인
  • 자연어 질의 vs 질의 조작·도구 출력 인젝션
  • 대시보드 고정 화면 vs 에이전트의 유연한 질의
  • MCP 서버 수 vs 실제 업무 호출(X8)

해법

답이 원천 데이터에서 나오게 한다. 공공데이터·통계는 A8 MCP 서버나 A3 공공 API로 도구화하고, 호스트 쪽 에이전트는 B′7 ReAct 도구 루프로 조회하되 C8로 읽기 전용에 묶는다. 결과에는 F1 출처(통계표 ID)와 조회 시점을 붙이고, 도구 호출은 C4로 추적한다. 도구 출력이 새 지시가 되지 않도록 S5 계획 후 실행과 S1 비용 상한을 둔다. 에이전트가 필요 없으면 B0 대시보드·검색기로 끝내고(5a-agg), LLM이 해설을 붙이면 5a-brief로 C9·F9를 더한다(R19). MCP 서버만 만드는 사례는 5b-server로 A8·S11만 필수다(R18).

이럴 때 쓴다

  • 담당자가 흩어진 데이터·법령·공고·선례를 찾느라 시간을 쓸 때
  • 공공데이터·통계를 자연어로 조회해야 할 때
  • 다른 지역·기관 사례를 모아 봐야 할 때

이럴 때는 쓰지 않는다

  • 찾은 문서에서 할 일·핵심을 뽑으면 D8.2
  • 규정·기준과 대조해 확인 대상을 고르면 D8.4
  • 국민이 서비스를 찾으면 D1

얻는 것

  • 자료 찾는 시간 절감
  • 출처·시점이 붙은 근거 확보
  • 공공데이터 MCP의 재사용

점검표

  • 결과마다 원천 출처와 기준 시점이 보이는가
  • 도구 권한이 읽기 전용으로 묶여 있는가
  • 도구 호출 순서를 나중에 볼 수 있는가
  • MCP 서버가 실제 업무에서 호출되는지 재는가

구조 — 참여 부품

  • 담당자 — 자료를 찾고 결과를 업무에 씀
  • A8 MCP 서버·호스트 — 공공데이터·통계를 도구로 노출
  • B0 결정적 도구(탐색·시각화) — 검색기·대시보드
  • B6 도구 호출 에이전트 — 로컬 MCP 호스트로 조회·차트 생성
  • C8 권한 경계 — 읽기 전용 제한
  • F1 출처 표시 — 통계표 ID·출처·시점 표시

변형

  • 검색·대시보드형(비LLM): B0 탐색·시각화. 유형 5a-agg(필수 A1·F2·C4, R19).
  • 브리핑형: LLM이 조회 결과를 요약·해설. 유형 5a-brief(필수 A2.1|A2.2|A2.6·F9·C9, R19).

A9 업무 규범 스킬 공통 서비스

보고서 구조·문체·서식·검증 절차 같은 업무 규범을 모델 중립 스킬(지침 + 검증기 + 출력 서식)로 패키징해 어떤 모델·에이전트에서든 재사용한다.

PAX 사례 54건이 이 부품을 쓴다

맥락

기안·보고서·콘텐츠처럼 서식과 문체가 정해진 산출물을 만드는 B1·B7, BYO 코딩 에이전트 환경(E2 모델 중립), 개발 코파일럿에서 쓴다. 유형 4·6·12에서는 필수 기반이고, §7.2 진행 경로에서는 3단계에 놓인다.

맞서는 힘(긴장)

  • 규범 고정(일관성) vs 담당자 재량
  • 모델 중립(이식성) vs 특정 모델 최적화
  • 규범 공개·재사용 vs 프롬프트·규범 유출
  • 가중치에 넣기(튜닝) vs 문서로 주입하기

해법

규정집·매뉴얼·서식 예시에서 업무 규범을 뽑아 지침(구조·문체·금지 사항), 검증기(형식·인용·수치 검사), 출력 서식(HWPX·DOCX 등)으로 묶은 스킬 패키지로 만든다. 모델 호출 코드와 분리된 파일로 두어 어떤 코딩 에이전트·모델에서도 같은 절차가 돌게 한다(External Configuration). 산출·검증된 수치와 출처만 주입하고 미제공 수치·순위 생성을 금지하는 식으로 생성 범위를 규범으로 좁힌다. 스킬은 버전으로 관리해 규범 유출·변경을 추적하고, C9로 스킬 변경 전후 품질을 잰다.

이럴 때 쓴다

  • 산출물 서식·문체·구조가 정해져 있을 때
  • 출력 품질이 들쭉날쭉할 때(§7.5)
  • BYO 환경에서 모델과 무관하게 같은 절차를 돌려야 할 때
  • 갱신이 잦은 규범을 튜닝 없이 반영해야 할 때

이럴 때는 쓰지 않는다

  • 규범이 문서로 정리되지 않았고 정리할 담당도 없을 때
  • 지식 검색이 필요한 문제(B3 접지가 먼저)
  • 스킬 내용 자체가 민감해 배포할 수 없는데 버전 관리·접근 통제를 둘 수 없을 때

얻는 것

  • 출력 일관성
  • 모델 교체 가능(BYO에서는 교체 가능성이 곧 C7)
  • 타 기관 재사용
  • 튜닝 없이 규범 갱신

점검표

  • 규범이 모델 호출 코드와 분리된 파일로 있는가
  • 검증기가 출력 형식·인용·수치를 실제로 검사하는가
  • 스킬에 버전이 있는가
  • 다른 모델로 바꿔도 같은 서식이 나오는지 확인했는가

구조 — 참여 부품

  • 스킬 패키지 — 지침·검증기·출력 서식을 모델 밖 파일로 묶음
  • 코딩 에이전트·모델(BYO) — 스킬을 불러 규범대로 산출
  • A10 문서 형식 어댑터 — 출력 서식을 HWPX·DOCX로 내보냄
  • C9 평가 세트 — 스킬 변경 전후 품질 비교

변형

C1 검토 큐 운영 컴포넌트

AI 산출물이 다음 단계로 넘어가기 전에 사람이 맞고 틀림을 확인·수정·확정하는 대기열을 두어, 오류가 업무 결과로 흘러가지 않게 한다.

PAX 사례 46건이 이 부품을 쓴다

맥락

AI 산출물이 공문·처분·대민 안내·기록으로 이어지는 모든 B 부품(B1 코파일럿, B4 인식 파이프라인, B2 예측기, B7 콘텐츠 생성기 등). 이용자 본인이 최종 확정자인 자기서비스형 도구도 포함한다(R16).

맞서는 힘(긴장)

  • 정확성·책임성 vs 처리 속도(전건 검토는 자동화 이득을 깎는다)
  • 검토자의 숙련 vs 자동화 편향(AI 결과를 그대로 승인하는 경향)
  • 전건 검토의 안전 vs 위험도별 분기(C2)로 가야 하는 효율 압력

해법

AI 산출물에 신뢰도·근거를 붙여 검토 대기열에 올리고, 검토자가 승인·수정·반려 중 하나를 고르게 한다. 수정·반려 내역은 C4 감사 로그에 남겨 수정률을 집계하고 C6 환류의 입력으로 쓴다. 검토 화면은 원문 위치·근거를 함께 보여 줘 확인 비용을 줄인다. 전건 검토로 시작하되, 수정률 실측이 쌓이면 C2 위험도 라우터로 저위험 건을 자동 종결하는 단계로 옮긴다.

이럴 때 쓴다

  • AI 산출물이 공문·처분·대민 안내로 그대로 이어질 때
  • E4가 P1 이상이고 되돌리는 데 사람 시간이 많이 드는 조치가 있을 때
  • 서비스 유형 ② 접수·심사, ④ 기안 코파일럿, ⑥ 콘텐츠 제작, ⑦ 대조·점검, ⑩ 위험 예측, ⑪ 추천·매칭, ⑫ 개발 코파일럿처럼 C1이 필수인 유형

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 런타임 AI 산출물이 없을 때
  • 쉽게 되돌릴 수 있고 저위험인 조치를 이미 C2로 자동 종결하도록 실측 근거를 갖춘 구간(전건 검토를 영원히 남기지 않는다)

얻는 것

  • 오류가 업무 결과로 나가기 전에 차단
  • 책임 소재가 명확해짐
  • 수정 내역이 C4 지표와 C6 환류의 원천 데이터가 됨

점검표

  • AI 산출물이 확정 전 상태로 머무는 지점이 명시되어 있는가
  • 검토자와 승인·수정·반려 선택지가 정해져 있는가
  • 검토 결정과 수정 내역이 로그로 남는가
  • 실증 기간의 검토·수정 건수가 기록되어 있는가
  • 전건 검토에서 분기로 옮길 조건이 정해져 있는가

구조 — 참여 부품

  • 검토 대기열 — AI 산출물을 확정 전 상태로 보관하고 검토자에게 배정
  • 검토자(담당자 또는 이용자 본인) — 승인·수정·반려를 결정하는 최종 책임자
  • F2 편집 가능한 출력 — 검토자가 산출물을 직접 고치는 화면
  • C4 감사 로그·지표 — 검토 결정과 수정 내역을 적재해 수정률로 집계

변형

  • 전건 검토형: 모든 AI 산출물을 담당자가 확인·확정
  • 예외 검수형: 정상 건은 일괄 승인하고 저신뢰 항목만 개별 검수하는 검수 UI
  • 파이프라인 내장 관문형: 멀티에이전트·다단계 파이프라인의 각 관문에 승인·보완·재작성 선택지를 둠
  • 자기서비스형: 이용자 본인이 최종 확정자인 HITL. 실제 운영 중이면 C1 present(R16)
  • 심의 게이트: 팩트체크·법무·윤리처럼 제3자 전문가가 수행하는 승인 게이트

F2 편집 가능한 출력 상호작용 패턴

생성물을 이용자가 직접 고쳐 확정하게 한다. 통제감의 실체이며, 수정 내역은 C4 지표와 C6 환류의 입력이 된다.

PAX 사례 50건이 이 부품을 쓴다

맥락

B1 코파일럿(필수 면), B7 콘텐츠 생성기, B4 인식 결과 확정. 유형 ② 접수·심사, ④ 기안 코파일럿, ⑫ 개발 코파일럿, 5a-agg(R19), 2b 시민 제출 준비(R20).

맞서는 힘(긴장)

  • 편집 자유도 vs 원본 추적(무엇을 고쳤는지)
  • 편집 가능한 공공 서식(HWPX 등) 출력 vs 구현 비용

해법

생성물을 이용자가 바로 고칠 수 있는 형식(편집 화면, HWPX·PPTX 등 네이티브 파일)으로 내고, 이용자가 고친 뒤 확정하게 한다. AI 원안과 수정본의 차이를 기록해 C4 수정률과 C6 환류 입력으로 쓴다. 문서 형식 출력은 A10 어댑터가 받친다.

이럴 때 쓴다

  • B1 코파일럿 전반(필수 면)
  • 대민 서비스 D1~D7(F1·F2·F7이 최소 요건)
  • 유형 ②④⑫, 5a-agg, 2b처럼 F2가 필수인 유형

이럴 때는 쓰지 않는다

  • 이용자가 결과를 수정하면 안 되는 판정 결과(판정은 C1 확정 절차로 다룸)
  • 조회 결과만 보여 주는 P0 도구

얻는 것

  • 이용자 통제감
  • 수정 내역이 품질 지표·환류 데이터가 됨
  • 공공 서식 재작업 감소

점검표

  • 산출물을 이용자가 직접 고칠 수 있는가
  • 원안과 수정본 차이가 기록되는가

X11 처음부터 멀티에이전트 안티패턴

하위 작업이 분리되지 않는데 에이전트를 여럿 두어 조정 비용만 늘리는 함정이다. 단일 에이전트로 되돌리면 더 잘 되는 경우가 많다.

맥락

B6 오케스트레이터를 설계하거나 B′3 병렬·B′4 계층 분해를 도입하려는 과제, 특히 단일 에이전트 구성을 시도해 본 기록이 없는 과제.

맞서는 힘(긴장)

  • 역할 분리의 설계 명료함 vs 에이전트 간 조정 비용
  • 병렬 처리의 지연 단축 vs 결과 통합의 복잡도
  • 기술적 인상 vs 단순한 구조의 품질·비용

해법

B′ 원형 선택 규칙대로 단일 에이전트(B′1 순차, B′7 ReAct 도구 루프)에서 시작한다. 하위 작업이 진짜로 분리되거나, 병렬이 지연을 의미 있게 줄이거나, 컨텍스트 창이 부족할 때만 B′3 병렬·B′4 계층 분해로 승급한다. 승급 판단은 C9 평가 세트로 단일 구성과 비교해 내린다. 에이전트끼리 충돌·중복이 관측되면 B′4 감독자 계층이나 B′2 라우터로 정리하거나 단일 에이전트로 후퇴한다. B6 태그는 R2 요건(복수 LLM 역할 + 도구 호출 루프 + AI가 계획·도구를 선택)을 만족할 때만 붙인다.

이럴 때 쓴다

  • 에이전트가 여럿인데 하위 작업의 입력·출력이 서로 얽혀 독립적으로 돌지 않는다
  • 단일 에이전트 구성과 비교한 기록이 없다
  • 에이전트끼리 충돌·중복·재작업이 관측된다
  • 호출 비용·지연이 에이전트 수에 비례해 늘었는데 품질 개선 근거가 없다

이럴 때는 쓰지 않는다

  • 하위 작업이 진짜로 분리되고(서로 다른 데이터·도구), 병렬이 지연을 줄이거나 컨텍스트가 부족해 승급한 경우
  • R2 요건을 만족하는 B6로, 단일 구성보다 나음이 C9로 확인된 경우
  • 고정 순서 파이프라인을 B′1으로 정직하게 서술한 경우

얻는 것

  • 구조도가 명료하고 기술적으로 인상적이다
  • 역할별로 프롬프트를 나눠 관리하기 쉬워 보인다

점검표

  • 하위 작업이 서로 다른 데이터·도구로 독립적으로 도는가
  • 단일 에이전트 구성과 C9로 비교한 기록이 있는가
  • 승급 사유가 문서에 적혀 있는가
  • 에이전트 사이 충돌을 정리하는 감독자·라우터가 있는가

구조 — 참여 부품

  • C9 평가 세트·회귀시험 — 단일 vs 멀티 구성을 같은 자로 비교

X13 도구 출력이 지시가 되는 에이전트 안티패턴

검색 결과·첨부·API 응답을 읽은 모델이 그 안의 문장을 새 명령으로 받아 도구를 부르는 구조를, 탐지 필터 하나로 지키려는 함정이다.

맥락

E4가 P2 이상(시스템 쓰기·처분 보조)이면서 민원 입력·제출 서류·웹 문서·타 기관 API 응답 같은 신뢰 불가 입력을 읽는 에이전트. 특히 B6·5b 데이터 에이전트.

맞서는 힘(긴장)

  • 범용 에이전트의 유연성 vs 신뢰 불가 입력 뒤의 행동 제약
  • 단일 LLM 구조의 단순함 vs 격리·계획 고정의 설계 비용
  • 탐지 필터의 손쉬움 vs 증명 가능한 보증

해법

과제의 AI가 읽는 입력 중 기관 밖에서 작성된 것을 untrusted_inputs로 나열하고, §4.2 신뢰 불가 입력 규칙대로 S4 행동 선택기(미리 정한 행동 중 선택만, 결과가 LLM으로 돌아가지 않음), S5 계획 후 실행(외부 데이터를 읽기 전에 도구 호출 계획을 고정), S6 격리 LLM(도구 있는 LLM은 외부 데이터를 읽지 않고, 읽는 LLM은 도구가 없음) 중 하나를 갖춘다. S3 컨텍스트 방화벽과 S8 독립 검증기는 보조로 붙이되 S8만으로는 규칙을 충족하지 못한다. C8 승인 게이트도 신뢰 불가 입력 규칙의 대체 통제로 인정되지 않는다(R6). 그 전 단계에서는 E4를 P0~P1 읽기·산출물 범위에 묶어 두는 것이 곧 보안이다.

이럴 때 쓴다

  • E4가 P2 이상이고 untrusted_inputs가 비어 있지 않은데 S4·S5·S6이 모두 없다(신뢰 불가 입력 규칙 위반)
  • 외부 문서를 읽는 LLM이 같은 컨텍스트에서 쓰기 도구를 호출할 수 있다
  • 인젝션 대책이 탐지 필터·프롬프트 경고문뿐이다
  • 읽은 텍스트 중 어떤 것이 어떤 도구를 부를 수 있는지 답하지 못한다

이럴 때는 쓰지 않는다

  • E4가 P0~P1로 읽기·산출물 생성에만 묶여 도구 호출·시스템 쓰기가 없는 경우(S4·S5·S6 판정 전제 불충족, R6)
  • S4·S5·S6 중 하나가 구조적으로 갖춰진 경우(보안 목적 서술이 없어도 구조가 일치하면 충족)
  • AI가 읽는 입력이 모두 기관 내부에서 작성된 경우

얻는 것

  • 단일 LLM 범용 에이전트로 구조가 단순하다
  • 새 입력·새 도구를 자유롭게 붙인다

점검표

  • untrusted_inputs가 나열되어 있는가
  • 신뢰 불가 입력을 읽은 LLM이 쓰기 도구를 직접 부를 수 없는가
  • S4·S5·S6 중 하나가 구조로 구현되어 있는가
  • S8 탐지를 유일한 방어로 두지 않았는가

구조 — 참여 부품

  • S4 행동 선택기 — LLM이 정해진 행동 중 선택만 하게 제약
  • S5 계획 후 실행·코드 후 실행 — 외부 데이터를 읽기 전에 도구 계획 고정
  • S6 격리 LLM·맵리듀스 — 읽는 LLM과 도구 있는 LLM을 분리
  • S8 독립 검증기·이중 심판 — 보조 탐지. 단독으로는 보증이 아님

변형

  • 문서 속 지시: 첨부·제출 서류 안의 문장대로 에이전트가 도구를 호출
  • API 응답 오염: 타 기관 API·웹 검색 결과에 섞인 지시가 후속 행동을 바꿈
  • 탐지 단독 방어: 인젝션 탐지 필터(S8) 하나만 두고 구조적 제약이 없음

X14 재생할 수 없는 사고 안티패턴

잘못된 처분이 나갔는데 그때의 프롬프트·검색·도구 호출 순서를 아무도 복원하지 못하는 함정이다. 지표는 있는데 기록이 없다.

맥락

E4가 P2 이상, 특히 P3 처분 보조(지급·승인·반려 결과에 직결)에 관여하는 AI 부품. 모델·프롬프트가 자주 바뀌는 상용 API 과제.

맞서는 힘(긴장)

  • 집계 지표의 손쉬움 vs 건별 재생 기록의 저장·보호 비용
  • 개인정보 최소 보관 vs 사고 재현 가능성
  • 빠른 모델·프롬프트 변경 vs 버전별 재현

해법

  • '이 답의 근거 문서와 도구 호출 순서를 지금 볼 수 있는가'에 답하지 못한다
  • P3 처분 보조에 관여하면서 재생 기록이 없다
  • 모델·프롬프트 버전을 기록하지 않는다

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 같은 입력이면 같은 출력이 나와 재생이 자명한 경우
  • E4가 P0~P1이고 산출물을 사람이 전건 확정해 AI 출력이 처분에 직접 닿지 않는 경우(S10 필요도는 낮지만 C4는 여전히 필요)
  • S10 수준의 건별 추적이 구현된 경우

얻는 것

  • 저장 비용과 개인정보 보관 부담이 적다
  • 집계 지표만으로 운영 보고가 가능하다

점검표

  • 임의의 과거 건 하나를 골라 프롬프트·검색·도구 호출 순서를 복원할 수 있는가
  • 기록에 당시 모델·프롬프트 버전이 포함되는가
  • 기록의 변조 방지 장치가 있는가
  • 이의제기 처리에 재생 기록이 쓰이는가

구조 — 참여 부품

  • S10 결정적 재생 — 빠진 부품. 사고를 그대로 재현

  • C3 상태 머신·롤백 — 재생 기록을 근거로 되돌림·이의 처리

변형

X7 도구 설명 ≠ 실제 권한 안티패턴

MCP 도구 설명은 '조회'인데 코드는 쓰기·실행 권한을 가져, 설명만 믿고 도구를 부르는 에이전트가 의도하지 않은 변경을 일으키는 함정이다.

맥락

E3 MCP·CLI 설정 환경에서 A8 MCP 서버·호스트를 만들거나 가져다 쓰는 과제. 특히 업무 시스템 MCP(쓰기, P2)와 공공데이터 MCP(읽기, P0)가 한 호스트에 함께 연결된 경우.

맞서는 힘(긴장)

  • 빠른 MCP 래핑 vs 도구별 권한 분리
  • 도구 하나로 묶는 편의 vs 읽기/쓰기 분리의 운영 부담
  • 에이전트 자율 호출 vs 실행 전 승인

해법

A8의 각 도구에 실제 권한 수준(P0~P4)을 설명과 함께 명시하고, C8 권한 경계로 읽기 전용 도구와 쓰기 도구를 서로 다른 서버·인증으로 분리한다. 쓰기·실행 도구는 도구별 실행 승인과 호출 상한, 킬스위치를 둔다. 반입하는 MCP 서버는 S11 인제스천·공급망 검증에서 PAX 6축(권한 표면·비밀·공급망·위생·인젝션·데이터 흐름)을 통과해야 활성화한다. 사람에게는 F6 에이전트 행동 검토·확인으로 실행 전 무엇을 할지 보여 주고, 승인·실패는 C4에 남긴다.

이럴 때 쓴다

  • MCP 도구 설명과 실제 권한(쓰기·삭제·발송)이 다르다
  • 읽기와 쓰기 도구가 같은 서버·같은 인증 토큰을 쓴다
  • 도구별 권한 수준·실행 승인이 문서에 없다
  • 6축 검증에서 권한 표면이 '주의'로 나왔다

이럴 때는 쓰지 않는다

  • 읽기 전용 MCP로 설계되어 쓰기 기능이 배제된 경우
  • 쓰기 도구가 있지만 설명에 부수 효과가 명시되고 C8 실행 승인이 있는 경우
  • MCP가 아닌 결정적 스크립트로 권한이 코드에 고정된 경우

얻는 것

  • 기존 API를 빠르게 에이전트 도구로 만든다
  • 도구 수가 적어 관리가 쉬워 보인다

점검표

  • 모든 도구의 설명에 실제 권한과 부수 효과가 적혀 있는가
  • 읽기와 쓰기 도구가 서로 다른 인증을 쓰는가
  • 쓰기 도구에 실행 전 승인이 있는가
  • 반입 MCP가 6축 검증을 통과했는가

구조 — 참여 부품

  • A8 MCP 서버·호스트 — 도구 설명과 실제 권한이 일치해야 하는 곳
  • C8 권한 경계·킬스위치 — 읽기/쓰기 분리, 도구별 승인
  • S11 인제스천·공급망 검증 — 반입 시 6축 검증
  • F6 에이전트 행동 검토·확인 — 실행 전 사람에게 행동을 보여 줌

변형

  • API 통째 래핑: 기존 API 클라이언트를 감싸 조회·수정 함수가 같은 도구·인증으로 노출
  • 과대 인증: 조회 도구가 쓰기 권한 토큰으로 실행됨
  • 설명 누락: 도구 설명에 부수 효과(삭제·발송)가 적혀 있지 않음

관련 부품

C8 대체 — 읽기/쓰기 분리와 도구별 실행 승인 · A8 발생 자리 — 도구 설명과 권한이 일치해야 하는 곳 · S11 선행 — 반입 시 6축 검증 · F6 이용자 쪽 대응 — 실행 전 행동 확인 · X13 이웃 안티패턴 — 권한 표면이 넓을수록 인젝션 피해가 커짐

X8 MCP 서버 개수 세기 안티패턴

MCP 서버를 몇 개 만들었는지가 성과가 되고, 실제 업무에서 호출되는지·흐름이 바뀌었는지는 아무도 묻지 않는 함정이다.

맥락

공공데이터·업무 시스템을 MCP로 감싸는 과제, MCP 서버를 사례 단위로 등록하는 커뮤니티 아카이브, 'MCP N종 구축'을 성과 지표로 둔 과제.

맞서는 힘(긴장)

  • 보고하기 쉬운 개수 vs 측정하기 어려운 업무 전환
  • 서버 제공자 책임 vs 호스트·업무 쪽 활용 책임
  • 빠른 확장 vs 서버마다의 검증·유지보수

해법

서버마다 그것을 호출하는 B 업무 컴포넌트와 업무 산출물을 연결해 '어느 업무의 어떤 산출물에 쓰이는가'를 적는다. C4 감사 로그·지표로 호출 수·호출 주체·업무 건을 집계하고, transition.stage와 파급력 척도(M1~M5)로 전환 경로를 추적한다(PAX: 도구 수보다 전환 경로를 추적). R18대로 서버 제공자 사례(5b-server)와 호스트 통합 사례(5b-host)를 나눠 서버 쪽은 A8·S11·문서화된 스키마를, 호스트 쪽은 C4·F1·S5|S6을 갖춘다. 호출되지 않는 서버는 레지스트리에서 정리한다.

이럴 때 쓴다

  • 성과가 MCP 서버·도구 개수로 보고된다
  • 호출 수·호출 주체·업무 건 지표가 없다
  • 서버를 호출하는 업무 산출물이 서술되지 않는다
  • 흐름이 바뀌었다는 서술 없이 'MCP 기반 전환'을 주장한다

이럴 때는 쓰지 않는다

  • 단일 MCP 서버를 만들어 A8·S11·문서화된 스키마를 갖춘 5b-server 사례(R18). 서버 제공 자체가 사례 단위이므로 개수를 성과로 주장하지 않으면 함정이 아니다
  • MCP 서버 여러 개를 호스트 업무에 연결하고 호출 지표를 C4로 집계한 경우

얻는 것

  • 성과를 개수로 명확히 보고할 수 있다
  • 공공 API를 빠르게 에이전트 도구로 공개한다

점검표

  • 서버마다 호출하는 업무 산출물이 적혀 있는가
  • 서버별 월 호출 수와 호출 주체를 말할 수 있는가
  • 호출되지 않는 서버를 정리하는 절차가 있는가
  • 성과 지표가 개수가 아니라 업무 전환으로 잡혀 있는가

구조 — 참여 부품

  • A8 MCP 서버·호스트 — 개수로 세어지는 도구 인터페이스
  • C4 감사 로그·지표 — 호출 수·호출 주체·업무 건을 집계하는 빠진 부품
  • B 업무 컴포넌트 — 서버를 실제로 호출해 산출물을 만드는 쪽
  • S11 인제스천·공급망 검증 — 서버 제공자 쪽 필수 검증(R18)

변형

  • 개수 성과형: 'MCP N종 구축'이 과제의 주요 성과 지표
  • 호스트 없는 서버: 서버만 공개하고 어떤 호스트·업무에서 쓰이는지 기록이 없음
  • 방치 서버: 원천 API 변경 후 갱신되지 않아 호출이 실패하는 서버가 목록에 남음

관련 부품

C4 대체 — 서버별 호출 지표 · A8 발생 자리 — 개수로 세어지는 도구 인터페이스 · B6 교정 목표 — 도구를 호출해 산출물을 만드는 업무 컴포넌트 · S11 서버 제공자 필수 — 반입·공급망 검증(R18) · X1 이웃 안티패턴 — 탑재·개수를 성과로 세는 같은 뿌리
