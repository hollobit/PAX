판정 근거

모델까지 노트북에서 구동해 인터넷 없이 동작하는 로컬 AI 에이전트로, 복수 역할의 도구(115종 내장 도구·58개 사전설정 MCP)를 위험도 등급(L0-L5)과 In-the-loop 승인으로 통제하며 국가통계포털(KOSIS) 공식 MCP에 연결해 통계 조회부터 차트 생성까지 시연했다. 도구 호출 루프와 실행 전 승인·샌드박스가 있어 B6 에이전트 오케스트레이터(로컬 MCP 호스트 변형)로 판정한다. 58개 MCP 서버 사전 설정을 성과처럼 강조하는 서술은 X8(MCP 서버 개수 세기) 소지가 있다. 파일시스템 쓰기 도구가 포함돼 permission_scope는 P2다.

구현 가이드

주 패턴 B6 에이전트 오케스트레이터을 구현할 때

구현 단계

  1. 업무를 도구 목록으로 나누고 도구마다 읽기/쓰기, 되돌리기 비용을 적어 C8 권한표를 먼저 만든다.
  2. 단일 에이전트 + ReAct 루프(B′7)로 시작해 C9 평가 세트로 재고, 하위 작업이 분리될 때만 B′4·B′3으로 승급한다.
  3. 신뢰 불가 입력(외부 문서·API 응답)을 읽는지 확인하고, P2 이상이면 S5 계획 고정 또는 S6 격리를 설계한다.
  4. 단계 상태·되돌림(C3), 호출 추적(C4), 되돌리기 어려운 조치 앞 확인(F6)을 붙인다.
  5. 모델 장애 대비 C7과 킬스위치를 시험하고 결정적 재생(S10) 기록을 남긴다.

점검표

  • 복수 LLM 역할·도구 호출 루프·AI의 계획 선택이 실제로 있는가(R2)
  • 도구별 읽기/쓰기 권한과 실행 승인이 명시되어 있는가
  • 모든 도구 호출이 추적되는가
  • 도구 출력이 새 행동을 촉발하지 못하게 막는 구조가 있는가

환경 조건

E3 MCP·CLI. E1 폐쇄망이면 A8 로컬 MCP 호스트 + A2 로컬 모델 변형만 가능하다. E2 해외 상용 API면 A2 게이트웨이 + C7 + C8 도구별 승인. E4가 P2 이상으로 올라가기 가장 쉬운 부품이라 C2·C3·C4·C8 킬스위치가 필수이며, 신뢰 불가 입력 + P2 이상이면 S5 또는 S6 + S9가 필요하다(§5 매트릭스).

주의할 점

  • 도구 출력 인젝션(X13)

피해야 할 안티패턴

  • X8 MCP 서버 개수 세기 (이 사례에서 확인) MCP 서버를 몇 개 만들었는지가 성과가 되고, 실제 업무에서 호출되는지·흐름이 바뀌었는지는 아무도 묻지 않는 함정이다. 대처: 서버마다 그것을 호출하는 B 업무 컴포넌트와 업무 산출물을 연결해 '어느 업무의 어떤 산출물에 쓰이는가'를 적는다. C4 감사 로그·지표로 호출 수·호출 주체·업무 건을 집계하고, transition.stage와 파급력 척도(M1~M5)로 전환 경로를 추적한다(PAX: 도구 수보다 전환 경로를 추적). R18대로 서버 제공자 사례(5b-server)와 호스트 통합 사례(5b-host)를 나눠 서버 쪽은 A8·S11·문서화된 스키마를, 호스트 쪽은 C4·F1·S5|S6을 갖춘다. 호출되지 않는 서버는 레지스트리에서 정리한다.
  • X11 처음부터 멀티에이전트 하위 작업이 분리되지 않는데 에이전트를 여럿 두어 조정 비용만 늘리는 함정이다. 단일 에이전트로 되돌리면 더 잘 되는 경우가 많다. 대처: B′ 원형 선택 규칙대로 단일 에이전트(B′1 순차, B′7 ReAct 도구 루프)에서 시작한다. 하위 작업이 진짜로 분리되거나, 병렬이 지연을 의미 있게 줄이거나, 컨텍스트 창이 부족할 때만 B′3 병렬·B′4 계층 분해로 승급한다. 승급 판단은 C9 평가 세트로 단일 구성과 비교해 내린다. 에이전트끼리 충돌·중복이 관측되면 B′4 감독자 계층이나 B′2 라우터로 정리하거나 단일 에이전트로 후퇴한다. B6 태그는 R2 요건(복수 LLM 역할 + 도구 호출 루프 + AI가 계획·도구를 선택)을 만족할 때만 붙인다.
  • X13 도구 출력이 지시가 되는 에이전트 검색 결과·첨부·API 응답을 읽은 모델이 그 안의 문장을 새 명령으로 받아 도구를 부르는 구조를, 탐지 필터 하나로 지키려는 함정이다. 대처: 과제의 AI가 읽는 입력 중 기관 밖에서 작성된 것을 untrusted_inputs로 나열하고, §4.2 신뢰 불가 입력 규칙대로 S4 행동 선택기(미리 정한 행동 중 선택만, 결과가 LLM으로 돌아가지 않음), S5 계획 후 실행(외부 데이터를 읽기 전에 도구 호출 계획을 고정), S6 격리 LLM(도구 있는 LLM은 외부 데이터를 읽지 않고, 읽는 LLM은 도구가 없음) 중 하나를 갖춘다. S3 컨텍스트 방화벽과 S8 독립 검증기는 보조로 붙이되 S8만으로는 규칙을 충족하지 못한다. C8 승인 게이트도 신뢰 불가 입력 규칙의 대체 통제로 인정되지 않는다(R6). 그 전 단계에서는 E4를 P0~P1 읽기·산출물 범위에 묶어 두는 것이 곧 보안이다.
  • X14 재생할 수 없는 사고 잘못된 처분이 나갔는데 그때의 프롬프트·검색·도구 호출 순서를 아무도 복원하지 못하는 함정이다. 지표는 있는데 기록이 없다. 대처: S10 결정적 재생으로 프롬프트·검색 결과·도구 호출·정책 결정·실행 흔적을 시각·주체·컨텍스트 해시와 함께 순서대로 기록하고, 필요하면 변조 방지 서명을 붙인다. 기록은 S1 단일 진입점에서 시작해 C4와 같은 파이프라인으로 적재하되, C4가 '얼마나'를 세고 S10은 '정확히 무엇이 일어났나'를 되돌리게 역할을 나눈다. 모델·프롬프트·설정 조합을 C9로 버전 고정해 그 시점의 구성을 재현할 수 있게 하고, 재생 기록을 C3 롤백·이의제기의 근거로 쓴다. 개인정보는 C5 비식별과 E5 등급에 맞춘 보관 기간으로 다룬다.
  • X7 도구 설명 ≠ 실제 권한 MCP 도구 설명은 '조회'인데 코드는 쓰기·실행 권한을 가져, 설명만 믿고 도구를 부르는 에이전트가 의도하지 않은 변경을 일으키는 함정이다. 대처: A8의 각 도구에 실제 권한 수준(P0~P4)을 설명과 함께 명시하고, C8 권한 경계로 읽기 전용 도구와 쓰기 도구를 서로 다른 서버·인증으로 분리한다. 쓰기·실행 도구는 도구별 실행 승인과 호출 상한, 킬스위치를 둔다. 반입하는 MCP 서버는 S11 인제스천·공급망 검증에서 PAX 6축(권한 표면·비밀·공급망·위생·인젝션·데이터 흐름)을 통과해야 활성화한다. 사람에게는 F6 에이전트 행동 검토·확인으로 실행 전 무엇을 할지 보여 주고, 승인·실패는 C4에 남긴다.

PAX 사례 15건이 이 부품을 쓴다

맥락

여러 시스템·도구(A8 MCP·API·문서)를 오가는 다단계 업무, 데이터 조회·분석 에이전트(유형 5b), 망분리 환경의 로컬 MCP 호스트에 쓴다. 하위 작업이 실제로 분리되거나 AI가 도구를 골라야 할 때만 해당한다.

맞서는 힘(긴장)

  • 자율성 vs 권한 통제(P2 이상에서 C8 필수)
  • 멀티에이전트의 분업 vs 조정 비용·충돌(X11)
  • 도구 출력 활용 vs 도구 출력 속 지시가 명령이 되는 위험(X13)
  • 탐색적 유연성 vs 재생·감사 가능성

해법

목표와 도구 목록(A8 MCP·API)을 받아 AI가 계획을 세우고 도구를 골라 호출하며, 필요하면 하위 전문 에이전트에 위임한다(B′4·B′7·B′8). 단일 에이전트에서 시작해 하위 작업이 분리될 때만 계층·병렬로 승급한다. 도구별 읽기/쓰기 권한과 실행 승인은 C8로, 단계 상태와 되돌림은 C3로, 모든 호출은 C4 추적 로그로 남긴다. 신뢰 불가 입력을 읽는 경우 S5 계획 고정이나 S6 격리로 도구 출력이 새 행동을 끼워 넣지 못하게 하고, 되돌리기 어려운 조치 앞에는 F6 확인을 둔다.

이럴 때 쓴다

  • 한 건의 처리가 여러 시스템 조회·작성·검증에 걸쳐 있고 AI가 도구 순서를 골라야 할 때
  • 하위 작업이 실제로 분리되거나 컨텍스트 창이 부족할 때
  • C8·C3·C4 통제를 함께 갖출 수 있을 때

이럴 때는 쓰지 않는다

  • 단계 순서가 고정된 파이프라인일 때(B′1을 가진 B1·B4)
  • 실제 흐름이 초안 → 사람 확정일 때(B1)
  • 스케줄러·크롤러 수준 자동화일 때(agent_system=true라도 B6 아님)
  • 단일 에이전트가 되기 전에 멀티에이전트부터 만들려 할 때(X11)

얻는 것

  • 여러 시스템을 오가는 업무 흐름 자체를 재설계
  • 도구 교체로 다른 기관이 그래프를 재사용 가능
  • First 지향 구조

점검표

  • 복수 LLM 역할·도구 호출 루프·AI의 계획 선택이 실제로 있는가(R2)
  • 도구별 읽기/쓰기 권한과 실행 승인이 명시되어 있는가
  • 모든 도구 호출이 추적되는가
  • 도구 출력이 새 행동을 촉발하지 못하게 막는 구조가 있는가

맞서는 힘(긴장)

  • 탐색적 유연성 vs 긴 정형 과제에서의 실행 무질서
  • 도구 출력 활용 vs 도구 출력 속 지시가 명령이 되는 위험(X13)
  • 추론 흔적의 투명성 vs 호출 수·비용

해법

모델이 현재 목표에 대해 생각을 적고, 도구 하나를 골라 호출하고, 결과를 관찰한 뒤 다음 행동을 정한다. 추론 흔적과 호출 순서는 C4 추적 로그로 남기고 답에는 근거(F1)를 붙인다. 도구는 A8 레지스트리에 등록된 것만 쓰게 하고 도구별 권한을 C8로 제한한다. 신뢰 불가 데이터를 읽은 뒤 새 행동을 부를 수 있으면 S5 계획 고정이나 S6 격리로 막고, 최대 호출 횟수를 둔다.

이럴 때 쓴다

  • 질의가 탐색적이라 순서를 미리 정할 수 없을 때
  • 답의 근거와 도구 호출 순서를 보여 줘야 할 때(§7.5)
  • 단일 에이전트로 시작하는 첫 에이전트 배선일 때

이럴 때는 쓰지 않는다

  • 긴 정형 과제로 단계 누락이 문제일 때(B′8)
  • 순서가 고정된 파이프라인일 때(B′1)
  • 신뢰 불가 입력을 읽고 P2 이상 행동을 하는데 S5·S6을 둘 수 없을 때

얻는 것

  • 근거와 호출 순서의 투명성
  • 탐색적 질의에 적합

A2.2 모델 서빙 · 주권형 온프레미스 공통 서비스

오픈웨이트 모델을 기관 서버·폐쇄망·로컬 PC 안에서 Ollama·vLLM 등으로 구동해 데이터를 기관 밖으로 내보내지 않고 추론한다.

PAX 사례 54건이 이 부품을 쓴다

맥락

E1은 폐쇄망·행정망·로컬 PC, E2는 해외 오픈웨이트(로컬) 또는 국산 오픈웨이트, E5는 S 이상이다. 폐쇄망 B3·B6·B8, 유형 3(현장 폐쇄망 서버 추론), 유형 12 개발 코파일럿은 이 변형을 기본으로 쓴다.

맞서는 힘(긴장)

  • 데이터 주권 vs 상용 최신 모델 대비 성능
  • GPU·서버 고정비 vs 종량 과금
  • 모델 운영·갱신 역량 vs 외부 의존 제거
  • 저사양 장비 구동 vs 모델 크기

해법

오픈웨이트 모델을 기관 안에 설치하고 서빙 계층(Ollama·vLLM·LM Studio 등)으로 업무 부품에 노출한다. 임베딩 모델도 로컬로 두어 B3 검색까지 망 안에서 끝낸다(§5 E1 폐쇄망 행 '로컬 임베딩'). 모델 선정은 C9 평가 세트로 상용·온프레미스 후보를 같은 조건에서 비교해 정한다. 폐쇄망에서 C7 경로는 수동 전환·다른 로컬 모델로 제한되므로 둘 이상의 로컬 모델이나 수동 절차를 미리 둔다. 모델·패키지 반입은 S11 인제스천 검증을 거친다.

이럴 때 쓴다

  • E1이 폐쇄망·행정망이거나 문서가 PC 밖으로 나가면 안 될 때
  • E5가 S 이상인데 내부망 프록시(A2.4)를 쓸 수 없을 때
  • 현장 폐쇄망 서버에서 추론해야 하는 유형 3
  • C7의 대체 경로로 로컬 모델을 둘 때

이럴 때는 쓰지 않는다

  • 추론 인프라·운영 인력을 확보할 수 없을 때
  • 현장 기기 자체에서 돌아야 하면 A5(엣지 런타임)
  • 모델을 재학습했으면 A2.3

얻는 것

  • 데이터가 기관 밖으로 나가지 않음
  • 호출 비용이 고정비로 바뀜
  • 폐쇄망에서도 LLM 사용 가능
  • C7의 대체 경로 후보

점검표

  • 추론·임베딩 어디에서도 데이터가 망 밖으로 나가지 않는가
  • 모델 선정 근거(평가 세트 비교)가 남아 있는가
  • 반입한 모델·패키지의 무결성 검사 기록이 있는가
  • 대체 로컬 모델 또는 수동 전환 절차가 있는가

구조 — 참여 부품

  • A2 서빙 계층 — 로컬 모델을 업무 부품에 노출

변형

  • 범정부 공통기반 내부망 설치형: 국산 독자모델·오픈웨이트를 공통기반 내부망에 직접 설치해 여러 부처에 제공한다(PAX 행정안전부 사례).

A8 MCP 서버·호스트 공통 서비스

공공 API·업무 시스템·로컬 파일을 에이전트가 부를 수 있는 도구로 감싸고, 도구 목록·권한·호출 로그를 한 층에서 관리한다.

PAX 사례 94건이 이 부품을 쓴다

맥락

에이전트(B6)·코파일럿(B1)이 도구를 호출하는 과제나, 공공데이터를 AI 도구로 공개하려는 기관에 쓴다. E3 값은 MCP·CLI 설정이다. 유형 5b에서는 필수이고(R10 'A8 또는 자체 도구 인터페이스'), 서버만 있는 사례는 5b-server로 분류한다(A8·S11 필수, R18).

맞서는 힘(긴장)

  • 도구 재사용·생태계 확산 vs 권한 표면 확대
  • 도구 설명의 편의 vs 실제 권한과의 불일치(X7)
  • 서버 개수 성과 vs 실제 업무 호출(X8)
  • 도구 출력 활용 vs 도구 출력을 타고 오는 간접 인젝션(X13)

해법

공공 API·업무 시스템·로컬 파일을 도구 설명·인증·정책과 함께 MCP 서버로 감싸 에이전트에 노출하고, 호출 결과에 출처·갱신 시각을 붙이며 호출 로그를 남긴다. 읽기(P0) 서버와 쓰기(P2) 서버를 분리하고 C8로 도구별 실행 승인을 건다. 배포·등재 전에 PAX MCP 6축 검증(권한 표면·비밀·공급망·위생·인젝션·데이터 흐름)을 통과시키고 S11로 반입을 검사하며, 통과하지 못한 축이 있으면 전이 범위를 부서 공유 이하로 둔다. 도구 목록·버전·갱신 공지는 레지스트리(Service Discovery)로 관리한다. 폐쇄망에서는 로컬 모델(A2.2)로 여러 MCP를 구동하는 로컬 호스트 변형을 쓴다.

이럴 때 쓴다

  • 에이전트가 공공 API·업무 시스템을 도구로 호출해야 할 때
  • 기관 데이터를 외부 AI 클라이언트와 타 기관이 직접 호출하게 공개할 때
  • 표준 시스템에 API를 열어 레거시 오버레이(B8)를 대체할 때

이럴 때는 쓰지 않는다

  • 호출할 도구가 로컬 파일뿐인 단순 작업(§5 E1 로컬 PC 행: 드묾)
  • 실제 업무 호출 없이 서버 개수를 성과로 삼으려 할 때(X8)
  • 6축 검증·권한 분리를 할 수 없는데 쓰기 도구를 노출하려 할 때

얻는 것

  • 도구 재사용과 생태계 확산
  • 권한·호출을 한 층에서 관리
  • 공공데이터를 AI가 직접 쓰는 경로

점검표

  • 도구 설명이 '조회'인데 쓰기·실행 권한을 가진 도구가 없는가
  • 6축 검증 결과가 기록되어 있는가
  • 호출 로그와 실제 업무 호출 지표가 있는가
  • 호스트가 도구 출력을 명령으로 받지 않도록 S5·S6 등이 있는가(P2 이상)

구조 — 참여 부품

  • MCP 서버 — 공공 API·업무 시스템·로컬 파일을 도구로 감쌈
  • MCP 호스트(에이전트) — 도구를 선택·호출하고 결과를 업무 흐름에 사용
  • C8 권한 경계·킬스위치 — 읽기/쓰기 분리와 도구별 실행 승인
  • S11 인제스천·공급망 검증 — 서버 반입·등재 전 6축 검증
  • C4 감사 로그·지표 — 호출 추적과 실제 업무 호출 지표

변형

  • 공공데이터 MCP 서버(읽기, P0): 국회 API 276개 MCP, KOSIS 통계 MCP, 나라장터 MCP, 법령 MCP 등.

  • 로컬 MCP 호스트: 폐쇄망에서 여러 MCP를 로컬 모델로 돌린다(망분리 로컬 AI 에이전트 + KOSIS 공식 MCP).

참조 구현 예

A3 공공 API 제공자 공통 서비스

정부·공공이 운영하는 모델·데이터·개발 도구(범정부 AI 공통기반, 모두의 AI 실험실, 공공데이터포털, 공공 깃랩)를 범정부 Provider로 소비한다.

PAX 사례 154건이 이 부품을 쓴다

맥락

모델·공공데이터·법령 원문·개발 환경을 공공 플랫폼에서 가져올 수 있다면 어느 과제든 해당한다. §7.1 2단계 '기반 부품은 새로 만들지 말고 Provider에서 먼저 찾는다'가 바로 이 부품을 가리킨다. 유형 7(대조·점검)에서는 법령·기준 출처를 대는 필수 기반이다.

맞서는 힘(긴장)

  • 공통 Provider 재사용 vs 기관 고유 요구 반영
  • 공공 API 가용성·갱신 주기 vs 서비스 신뢰성
  • 인가·검증 절차의 통제 vs 에이전트 루프의 병목(PAX 공공API 진단)

해법

기반을 새로 만들기 전에 범정부 AI 공통기반(모델), 공공데이터포털·법령 API(데이터), 모두의 AI 실험실·공공 깃랩(개발·실험 환경)에서 먼저 찾아 소비한다. 인증은 GPKI·디지털원패스 같은 연합 신원(Federated Identity)으로 위임하고, 공공 API 응답은 출처·조회 시각과 함께 업무 부품에 넘긴다. 에이전트가 부를 수 있게 하려면 A8 MCP 서버로 감싸고, 결과를 재가공해 기준선으로 고정하면 A1을 더한다. 기관이 만든 도구는 공공 깃랩에 등재해 다음 기관의 Provider가 되게 한다.

이럴 때 쓴다

  • 모델·데이터·개발 환경을 기관이 새로 만들려 할 때 — 먼저 Provider 확인
  • 법령·기준 원문을 최신으로 대조해야 하는 유형 7
  • 여러 부서가 같은 기반을 따로 만들고 있을 때(X3 교정)

이럴 때는 쓰지 않는다

  • 필요한 모델·데이터가 공공 Provider에 없을 때(만들고 레지스트리에 올림)
  • 타 기관 데이터를 계약·키 매핑으로 결합하는 경우는 A4

얻는 것

  • 기관별 중복 구축 방지(X3 교정)
  • 공인된 원천 데이터·모델 사용
  • 등재를 통해 전이 경로 확보

점검표

  • 같은 기반을 기관 안에서 따로 만들지 않았는가
  • 공공 API 응답의 출처·조회 시각이 결과에 남는가
  • API 장애·변경 시 어떻게 되는지 답할 수 있는가
  • 만든 도구가 공공 깃랩 등에 등재되었는가

구조 — 참여 부품

A12 접근성·모달리티 어댑터 공통 서비스

음성 입출력(STT·TTS), 웨어러블·AI글래스, 다국어·쉬운 언어 변환, 자막, 디지털휴먼 발화, 키오스크 출력으로 AI 부품과 사람 사이의 모달리티를 바꾼다.

PAX 사례 12건이 이 부품을 쓴다

맥락

대민 상담·안내(D1·D7), 현장 작업자 지원, 통역·자막이 필요한 과제에 쓴다. 카탈로그 등재 상태는 후보이고, PAX 557건에서 A12가 붙은 사례는 12건이다.

맞서는 힘(긴장)

  • 포용성·접근성 vs 변환 단계 추가에 따른 오류 누적
  • 현장 착용 기기의 편의 vs 기기 비용·개인정보(시야 영상)
  • 쉬운 언어 변환 vs 원문 의미 보존

해법

업무 부품의 입출력 앞뒤에 모달리티 변환 층을 두어, 음성·시야·다국어 입력을 텍스트로 바꾸고 텍스트 출력을 음성·자막·번역·아바타 발화로 바꾼다. 업무 로직은 텍스트 기준으로 유지하고 변환 층만 채널별로 교체한다. 번역·쉬운 언어 변환처럼 의미가 바뀔 수 있는 출력에는 날짜·숫자·금액 같은 확인 필요 항목을 표시하는 C5 가드레일과 F7 한계 안내를 붙인다. 현장 기기에서 돌려야 하면 A5와 함께 조립한다.

이럴 때 쓴다

  • 대민 접점에서 고령자·장애인·외국인 이용을 보장해야 할 때
  • 현장 작업자가 손을 쓸 수 없어 음성·착용 기기가 필요할 때
  • 안내문을 다국어·쉬운 언어·자막으로 내야 할 때

이럴 때는 쓰지 않는다

  • 음성 인식 결과가 판정 단계로 흐르는 인식 파이프라인 자체는 B4(STT·통역 변형)
  • 문서 형식 변환은 A10

얻는 것

  • 대민 서비스 포용성
  • 현장 작업자의 손 자유
  • 채널을 바꿔도 업무 로직 유지

점검표

  • 텍스트 외 접근 경로가 최소 하나 있는가
  • 변환 과정에서 숫자·날짜·기관명 오류를 확인하는 장치가 있는가
  • 변환 결과의 한계가 이용자에게 안내되는가

구조 — 참여 부품

  • 입력 변환(STT·시야·번역) — 사람의 음성·영상·외국어를 업무 부품이 읽는 텍스트로
  • 출력 변환(TTS·자막·쉬운 언어·아바타) — 업무 부품의 텍스트를 이용자에게 맞는 형태로
  • C5 가드레일 필터 — 번역·쉬운 언어 변환의 확인 필요 항목 표시
  • F7 한계·신뢰도 안내 — 변환 결과의 한계 고지

변형

  • 음성 입출력: STT·TTS로 대화형 안내와 현장 방송을 한다.
  • 웨어러블·AI글래스: 현장 작업자의 시야를 입력으로 받고 안내를 착용 기기로 내보낸다.
  • 다국어·쉬운 언어·자막: 번역·쉬운 글 변환·자막 생성.
  • 디지털휴먼·키오스크·사이니지: 아바타 발화와 공공장소 화면 출력.

C8 권한 경계·킬스위치 운영 컴포넌트

AI 부품이 할 수 있는 일의 상한을 P0~P4로 못 박고, 도구별 실행 승인·읽기/쓰기 분리·속도 제한·즉시 중단 스위치를 제공한다.

PAX 사례 22건이 이 부품을 쓴다

맥락

도구를 호출하거나 시스템에 쓰는 B6 오케스트레이터, A8 MCP 서버·호스트, B8 레거시 오버레이, 처분 보조(P3) 서비스. 유형 ⑤b 데이터 에이전트, ⑨ 인수인계(접근 범위).

맞서는 힘(긴장)

  • 자동화 범위 vs 통제
  • 승인 절차의 안전 vs 이용 마찰
  • 도구 설명의 편의 vs 실제 권한과의 일치 검증 비용

해법

부품별 허용 권한 범위(P0 읽기 전용 ~ P4 자율 처분)를 정하고, 도구 목록마다 읽기/쓰기를 분리한다. 위험도가 높은 도구는 실행 전 사람 승인(C2·F6)을 받게 하고, 호출 상한(속도 제한)을 둔다. 전역 킬스위치로 즉시 중단할 수 있게 하고, 승인·실패·중단 이력을 C4에 남긴다. MCP 도구는 설명과 실제 권한이 일치하는지 A8 6축 검증으로 확인한다.

이럴 때 쓴다

  • E4 P2 이상(필수, First 관문)
  • E3 MCP·CLI 환경에서 에이전트가 도구를 호출할 때
  • B6 오케스트레이터에 상용 API를 쓰는 경우(A2 + C7 + C8 도구별 승인)
  • 유형 ⑤b-host, ⑨ 인수인계(접근 범위)

이럴 때는 쓰지 않는다

  • 도구 호출·시스템 쓰기가 없는 서술 전용 코파일럿(P1)
  • B0 결정적 도구로 AI가 행동을 고르지 않을 때

얻는 것

  • 되돌릴 수 없는 조치 방지
  • 도구 설명과 실제 권한의 불일치(X7) 예방
  • 감사 가능한 행동 기록

점검표

  • AI가 쓸 수 있는 시스템 목록을 답할 수 있는가
  • 도구별 읽기/쓰기 구분과 위험도가 있는가
  • 고위험 도구에 실행 승인이 걸려 있는가
  • 킬스위치가 있고 누가 누를 수 있는지 정해져 있는가
  • 도구 설명과 실제 권한이 일치하는가

구조 — 참여 부품

  • 권한 정책 — 부품·도구별 허용 범위(P0~P4)와 읽기/쓰기 구분
  • A8 MCP 서버·호스트 — 도구 설명과 실제 권한의 일치 검증 대상
  • F6 에이전트 행동 검토·확인 — 실행 전 이용자 승인 화면
  • 킬스위치 — 전역 즉시 중단
  • C4 감사 로그·지표 — 승인·실패·롤백·중단 이력

변형

  • 읽기 전용·쓰기 배제: 도구 세트를 읽기 전용으로 한정하거나 쓰기 기능을 설계에서 배제
  • 도구별 위험도·실행 승인: 도구마다 위험도를 평가하고 고위험 도구는 실행 전 승인
  • 판정 필드 비도달 설계: AI가 판정·업무 필드에 쓸 수 없게 코드 수준으로 분리
  • 속도 제한: 도구 호출 상한(Rate Limiter)
  • 킬스위치: 전역 즉시 중단과 기존 절차 전환

참조 구현 예

  • PAX 망분리 환경용 로컬 AI 에이전트 — 도구별 위험도 평가·실행 승인·감사 대시보드(§9, PAX 557건 태깅에서 C8이 운영 중(present)으로 확인된 2건 가운데 하나. 구현 단계까지 합치면 22건)
  • PAX 갈피 법령 MCP — 쓰기 배제 설계

C2 위험도 라우터 운영 컴포넌트

건별 위험도·신뢰도를 매겨 저위험은 자동 처리, 중간은 검토 큐, 고위험은 숙련자에게 보내 사람의 검토를 필요한 곳에 집중시킨다.

PAX 사례 4건이 이 부품을 쓴다

맥락

C1 검토 큐가 이미 운영되고 수정률 실측이 쌓인 B 부품. 특히 E4 P2 이상이거나 D3 자격·심사, D6 점검·감시, ⑩ 위험 예측처럼 건수가 많고 위험 편차가 큰 업무.

맞서는 힘(긴장)

  • 자동 처리율 vs 오류 비용
  • 임계값의 보수성 vs 검토 인력 부담
  • 분기 기준의 일관성 vs 기관·업무별 기준 차이

해법

건마다 위험도(업무 규칙상 위험 유형)와 신뢰도(모델 확신·정합도)를 산출하고, 버전이 붙은 분기 기준으로 자동 종결·검토 큐·숙련자 이관 중 하나로 보낸다. 사람 개입 조건(근거 없음·신뢰도 미달·안전·개인정보 등)은 명문화한다. 분기 결과와 자동 처리율은 C4에 적재하고, 이관 시 이용자에게는 F11로 진행 상태를 알린다. 임계값은 실측 오류율로 조정하고 조정 이력을 남긴다.

이럴 때 쓴다

  • C1 전건 검토가 병목이고 수정률 실측이 있을 때
  • E4 P2 이상(§7.1 필수)
  • 유형 ② 접수·심사, ③ 현장 감시(등급 분기), ⑩ 위험 예측에서 등급 자동분류가 있을 때

이럴 때는 쓰지 않는다

  • 실측 수정률이 없어 임계값 근거가 없을 때(먼저 C1·C4로 데이터를 쌓는다)
  • 연속값 예측·참고용 순위만 내고 등급 분류가 없을 때(R10: 유형 ⑩에서 면제)
  • P0 조회 도구처럼 자동 처리할 조치가 없을 때

얻는 것

  • 사람의 검토를 고위험 건에 집중
  • 자동화 범위를 실측 근거로 넓힐 수 있음
  • 업무 순서가 실제로 바뀜(First 진입)

점검표

  • 분기 기준과 사람 개입 조건이 문서로 명시되어 있는가
  • 분기 기준에 버전이 있는가
  • 자동 처리율·검토 비율 실측치가 있는가
  • 고위험 건이 자동 종결되지 않음을 확인했는가

구조 — 참여 부품

  • 위험도·신뢰도 산정기 — 업무 규칙과 모델 신호로 건별 점수 산출
  • 분기 기준표 — 버전이 붙은 임계값·사람 개입 조건
  • C1 검토 큐 — 중간 위험 건의 사람 확인
  • 숙련자 — 고위험 건의 최종 판단
  • C4 감사 로그·지표 — 경로별 건수·자동 처리율 기록

S1 AI 게이트웨이·단일 진입점 보안 패턴

PAX 사례 3건이 이 부품을 쓴다

맥락

상용 API(E2)나 공용 모델 서빙(A2)을 여러 과제·부서가 함께 쓰는 기관, 대민 접점처럼 외부 이용자가 호출량을 좌우하는 서비스, 데이터 조회 에이전트(유형 ⑤)처럼 도구 호출이 반복되는 구조. 카탈로그 등재 상태는 후보(PAX 557건 중 3건).

맞서는 힘(긴장)

  • 요청 상한으로 비용을 막는 효과 vs 정상 업무량 급증 시 서비스 거부
  • 기관별 자율 도입 속도 vs 범정부 공통기반 경유 의무

해법

  • 현장 감시·경보(유형 ③)에서 경보 채널 남용을 막아야 할 때

S9 임시 샌드박스 보안 패턴

PAX 사례 1건이 이 부품을 쓴다

맥락

개발 코파일럿(유형 ⑫), 코드 후 실행(S5), 도구 루프(B′7), AI 코딩 도구로 기관 인력이 직접 만든 스크립트(A7), 제출 파일의 OCR·파싱 실행, 매크로가 있을 수 있는 부서별 제출 파일 취합(유형 ⑧). 카탈로그 등재 상태는 후보(PAX 557건 중 1건).

맞서는 힘(긴장)

  • 격리 강도 vs 실행 환경 구축·유지 비용
  • 일회용 파기의 안전성 vs 상태 유지가 필요한 작업

해법

코드·명령을 실행할 때마다 컨테이너·microVM·제한 런타임 중 하나로 일회용 격리 환경을 띄우고, 네트워크·파일 접근을 최소로 연다. 실행이 끝나면 결과값과 로그만 호스트로 넘기고 환경을 파기한다. 실행 전 정적 검사(AI 생성 코드 보안 린터)를 붙이면 샌드박스의 절반을 앞단에서 채운다. 격리 강도에 비례해 보호 수준이 정해지므로 행정망 자격 증명은 샌드박스 안에 두지 않는다.

이럴 때 쓴다

  • 개발 코파일럿(유형 ⑫)의 필수 부품(R7)

  • 실행 대상이 기관이 검수·고정한 결정적 코드뿐일 때

얻는 것

점검표

S5 계획 후 실행·코드 후 실행 보안 패턴

신뢰 불가 데이터를 읽기 전에 도구 호출 계획이나 프로그램을 고정하고 정책으로 검증해, 도구 출력이 새 행동을 끼워 넣지 못하게 한다.

PAX 사례 1건이 이 부품을 쓴다

맥락

도구 호출 또는 시스템 쓰기가 있는 구조(R6)에서 계획을 미리 정할 수 있는 정형 업무. 데이터 조회·분석 에이전트(유형 ⑤, 5b-host), 그리고 '오늘 접수 건을 조회해 담당자에게 통지'하는 식의 접수·통지 자동화(유형 ②). 카탈로그 등재 상태는 후보(PAX 557건 중 1건).

맞서는 힘(긴장)

  • 행동 집합의 증명 가능한 고정 vs 중간에 계획을 바꿔야 하는 탐색 과제
  • 정책 검증의 엄격함 vs 계획 작성 실패율
  • 행동 고정 vs 인자 조작(도구 출력이 인자를 바꾸는 것)은 남음

해법

이용자 지시를 받아 신뢰 불가 데이터를 읽기 전에 도구 호출 목록 [tool1(…), tool2(…)] 또는 실행 코드를 먼저 확정한다. 고정된 계획은 제어면(C8 도구별 권한)이 허용 도구·권한·파괴적 행동·사람 승인 필요 여부를 규칙으로 검증한 뒤에만 실행한다. 도구 출력은 인자 값을 채울 수는 있지만 계획에 없는 행동을 추가할 수 없다. 코드 후 실행이면 코드는 S9 샌드박스에서 돌린다. 인자 조작까지 막으려면 S6을 함께 둔다.

이럴 때 쓴다

  • 데이터 조회·분석 에이전트(유형 ⑤)의 필수 부품(S1과 함께)
  • 5b-host(에이전트 호출자) 필수 S5 또는 S6(R18)
  • 접수·통지 자동화처럼 계획을 미리 정할 수 있는 정형 업무
  • 내부 문서 코파일럿(유형 ④)이 행정망에 쓰기를 할 때(권장)

이럴 때는 쓰지 않는다

  • 중간에 계획을 바꿔야 하는 탐색 과제
  • 도구 호출·시스템 쓰기가 없는 서술 전용 LLM(R6)
  • 도구 출력 속 인자 조작이 핵심 위협일 때 S5만으로는 부족 — S6 필요

얻는 것

  • 간접 인젝션에 의한 행동 변경에 증명 가능한 저항
  • 권한 상승 차단
  • 계획이 사전에 보이므로 감사·승인이 쉬움

점검표

  • 외부 데이터를 읽기 전에 계획이 확정되는가
  • 계획이 실행 전에 정책으로 검증되는가
  • 도구 출력이 계획에 없는 도구 호출을 유발할 수 없는가
  • 파괴적 행동에 사람 승인이 걸려 있는가

구조 — 참여 부품

D8.1 탐색·조회 서비스 블록

데이터·법령·공고·선례·타 지역 사례를 찾아 담당자 화면에 놓는 내부 운영 블록이다. B0 탐색·시각화, MCP 도구 제공, B3가 전형 부품이다.

PAX 사례 176건이 이 부품을 쓴다

맥락

기관 내부 담당자가 자료를 찾아 보는 업무. §7.3 유형 ⑤b 데이터 에이전트(D8.1, P0)와 ⑤a 분석 대시보드·브리핑(D8.1, P0~P1)의 무대. PAX 176건(주 부품 B0 80%, B3 10%).

맞서는 힘(긴장)

  • 검색 편의 vs 출처·기준 시점 확인
  • 자연어 질의 vs 질의 조작·도구 출력 인젝션
  • 대시보드 고정 화면 vs 에이전트의 유연한 질의
  • MCP 서버 수 vs 실제 업무 호출(X8)

해법

답이 원천 데이터에서 나오게 한다. 공공데이터·통계는 A8 MCP 서버나 A3 공공 API로 도구화하고, 호스트 쪽 에이전트는 B′7 ReAct 도구 루프로 조회하되 C8로 읽기 전용에 묶는다. 결과에는 F1 출처(통계표 ID)와 조회 시점을 붙이고, 도구 호출은 C4로 추적한다. 도구 출력이 새 지시가 되지 않도록 S5 계획 후 실행과 S1 비용 상한을 둔다. 에이전트가 필요 없으면 B0 대시보드·검색기로 끝내고(5a-agg), LLM이 해설을 붙이면 5a-brief로 C9·F9를 더한다(R19). MCP 서버만 만드는 사례는 5b-server로 A8·S11만 필수다(R18).

이럴 때 쓴다

  • 담당자가 흩어진 데이터·법령·공고·선례를 찾느라 시간을 쓸 때
  • 공공데이터·통계를 자연어로 조회해야 할 때
  • 다른 지역·기관 사례를 모아 봐야 할 때

이럴 때는 쓰지 않는다

  • 찾은 문서에서 할 일·핵심을 뽑으면 D8.2
  • 규정·기준과 대조해 확인 대상을 고르면 D8.4
  • 국민이 서비스를 찾으면 D1

얻는 것

  • 자료 찾는 시간 절감
  • 출처·시점이 붙은 근거 확보
  • 공공데이터 MCP의 재사용

점검표

  • 결과마다 원천 출처와 기준 시점이 보이는가
  • 도구 권한이 읽기 전용으로 묶여 있는가
  • 도구 호출 순서를 나중에 볼 수 있는가
  • MCP 서버가 실제 업무에서 호출되는지 재는가

구조 — 참여 부품

  • 담당자 — 자료를 찾고 결과를 업무에 씀
  • A8 MCP 서버·호스트 — 공공데이터·통계를 도구로 노출

X8 MCP 서버 개수 세기 안티패턴

MCP 서버를 몇 개 만들었는지가 성과가 되고, 실제 업무에서 호출되는지·흐름이 바뀌었는지는 아무도 묻지 않는 함정이다.

맥락

공공데이터·업무 시스템을 MCP로 감싸는 과제, MCP 서버를 사례 단위로 등록하는 커뮤니티 아카이브, 'MCP N종 구축'을 성과 지표로 둔 과제.

맞서는 힘(긴장)

  • 보고하기 쉬운 개수 vs 측정하기 어려운 업무 전환
  • 서버 제공자 책임 vs 호스트·업무 쪽 활용 책임
  • 빠른 확장 vs 서버마다의 검증·유지보수

해법

서버마다 그것을 호출하는 B 업무 컴포넌트와 업무 산출물을 연결해 '어느 업무의 어떤 산출물에 쓰이는가'를 적는다. C4 감사 로그·지표로 호출 수·호출 주체·업무 건을 집계하고, transition.stage와 파급력 척도(M1~M5)로 전환 경로를 추적한다(PAX: 도구 수보다 전환 경로를 추적). R18대로 서버 제공자 사례(5b-server)와 호스트 통합 사례(5b-host)를 나눠 서버 쪽은 A8·S11·문서화된 스키마를, 호스트 쪽은 C4·F1·S5|S6을 갖춘다. 호출되지 않는 서버는 레지스트리에서 정리한다.

이럴 때 쓴다

  • 성과가 MCP 서버·도구 개수로 보고된다
  • 호출 수·호출 주체·업무 건 지표가 없다
  • 서버를 호출하는 업무 산출물이 서술되지 않는다
  • 흐름이 바뀌었다는 서술 없이 'MCP 기반 전환'을 주장한다

이럴 때는 쓰지 않는다

  • 단일 MCP 서버를 만들어 A8·S11·문서화된 스키마를 갖춘 5b-server 사례(R18). 서버 제공 자체가 사례 단위이므로 개수를 성과로 주장하지 않으면 함정이 아니다
  • MCP 서버 여러 개를 호스트 업무에 연결하고 호출 지표를 C4로 집계한 경우

얻는 것

  • 성과를 개수로 명확히 보고할 수 있다
  • 공공 API를 빠르게 에이전트 도구로 공개한다

점검표

  • 서버마다 호출하는 업무 산출물이 적혀 있는가
  • 서버별 월 호출 수와 호출 주체를 말할 수 있는가
  • 호출되지 않는 서버를 정리하는 절차가 있는가
  • 성과 지표가 개수가 아니라 업무 전환으로 잡혀 있는가

구조 — 참여 부품

  • A8 MCP 서버·호스트 — 개수로 세어지는 도구 인터페이스
  • C4 감사 로그·지표 — 호출 수·호출 주체·업무 건을 집계하는 빠진 부품

  • S11 인제스천·공급망 검증 — 서버 제공자 쪽 필수 검증(R18)

  • 역할 분리의 설계 명료함 vs 에이전트 간 조정 비용

  • 기술적 인상 vs 단순한 구조의 품질·비용

해법

B′ 원형 선택 규칙대로 단일 에이전트(B′1 순차, B′7 ReAct 도구 루프)에서 시작한다. 하위 작업이 진짜로 분리되거나, 병렬이 지연을 의미 있게 줄이거나, 컨텍스트 창이 부족할 때만 B′3 병렬·B′4 계층 분해로 승급한다. 승급 판단은 C9 평가 세트로 단일 구성과 비교해 내린다. 에이전트끼리 충돌·중복이 관측되면 B′4 감독자 계층이나 B′2 라우터로 정리하거나 단일 에이전트로 후퇴한다. B6 태그는 R2 요건(복수 LLM 역할 + 도구 호출 루프 + AI가 계획·도구를 선택)을 만족할 때만 붙인다.

이럴 때 쓴다

  • 에이전트가 여럿인데 하위 작업의 입력·출력이 서로 얽혀 독립적으로 돌지 않는다
  • 단일 에이전트 구성과 비교한 기록이 없다
  • 에이전트끼리 충돌·중복·재작업이 관측된다
  • 호출 비용·지연이 에이전트 수에 비례해 늘었는데 품질 개선 근거가 없다

이럴 때는 쓰지 않는다

  • R2 요건을 만족하는 B6로, 단일 구성보다 나음이 C9로 확인된 경우
  • 고정 순서 파이프라인을 B′1으로 정직하게 서술한 경우

얻는 것

  • 구조도가 명료하고 기술적으로 인상적이다
  • 역할별로 프롬프트를 나눠 관리하기 쉬워 보인다

점검표

X13 도구 출력이 지시가 되는 에이전트 안티패턴

검색 결과·첨부·API 응답을 읽은 모델이 그 안의 문장을 새 명령으로 받아 도구를 부르는 구조를, 탐지 필터 하나로 지키려는 함정이다.

맥락

E4가 P2 이상(시스템 쓰기·처분 보조)이면서 민원 입력·제출 서류·웹 문서·타 기관 API 응답 같은 신뢰 불가 입력을 읽는 에이전트. 특히 B6·5b 데이터 에이전트.

맞서는 힘(긴장)

  • 범용 에이전트의 유연성 vs 신뢰 불가 입력 뒤의 행동 제약
  • 단일 LLM 구조의 단순함 vs 격리·계획 고정의 설계 비용
  • 탐지 필터의 손쉬움 vs 증명 가능한 보증

해법

과제의 AI가 읽는 입력 중 기관 밖에서 작성된 것을 untrusted_inputs로 나열하고, §4.2 신뢰 불가 입력 규칙대로 S4 행동 선택기(미리 정한 행동 중 선택만, 결과가 LLM으로 돌아가지 않음), S5 계획 후 실행(외부 데이터를 읽기 전에 도구 호출 계획을 고정), S6 격리 LLM(도구 있는 LLM은 외부 데이터를 읽지 않고, 읽는 LLM은 도구가 없음) 중 하나를 갖춘다. S3 컨텍스트 방화벽과 S8 독립 검증기는 보조로 붙이되 S8만으로는 규칙을 충족하지 못한다. C8 승인 게이트도 신뢰 불가 입력 규칙의 대체 통제로 인정되지 않는다(R6). 그 전 단계에서는 E4를 P0~P1 읽기·산출물 범위에 묶어 두는 것이 곧 보안이다.

이럴 때 쓴다

  • E4가 P2 이상이고 untrusted_inputs가 비어 있지 않은데 S4·S5·S6이 모두 없다(신뢰 불가 입력 규칙 위반)
  • 외부 문서를 읽는 LLM이 같은 컨텍스트에서 쓰기 도구를 호출할 수 있다
  • 인젝션 대책이 탐지 필터·프롬프트 경고문뿐이다
  • 읽은 텍스트 중 어떤 것이 어떤 도구를 부를 수 있는지 답하지 못한다

이럴 때는 쓰지 않는다

  • E4가 P0~P1로 읽기·산출물 생성에만 묶여 도구 호출·시스템 쓰기가 없는 경우(S4·S5·S6 판정 전제 불충족, R6)
  • S4·S5·S6 중 하나가 구조적으로 갖춰진 경우(보안 목적 서술이 없어도 구조가 일치하면 충족)
  • AI가 읽는 입력이 모두 기관 내부에서 작성된 경우

얻는 것

  • 단일 LLM 범용 에이전트로 구조가 단순하다
  • 새 입력·새 도구를 자유롭게 붙인다

점검표

  • untrusted_inputs가 나열되어 있는가
  • 신뢰 불가 입력을 읽은 LLM이 쓰기 도구를 직접 부를 수 없는가
  • S4·S5·S6 중 하나가 구조로 구현되어 있는가
  • S8 탐지를 유일한 방어로 두지 않았는가

구조 — 참여 부품

  • S4 행동 선택기 — LLM이 정해진 행동 중 선택만 하게 제약
  • S5 계획 후 실행·코드 후 실행 — 외부 데이터를 읽기 전에 도구 계획 고정
  • S6 격리 LLM·맵리듀스 — 읽는 LLM과 도구 있는 LLM을 분리
  • S8 독립 검증기·이중 심판 — 보조 탐지. 단독으로는 보증이 아님

변형

  • 문서 속 지시: 첨부·제출 서류 안의 문장대로 에이전트가 도구를 호출
  • API 응답 오염: 타 기관 API·웹 검색 결과에 섞인 지시가 후속 행동을 바꿈
  • 탐지 단독 방어: 인젝션 탐지 필터(S8) 하나만 두고 구조적 제약이 없음

X14 재생할 수 없는 사고 안티패턴

잘못된 처분이 나갔는데 그때의 프롬프트·검색·도구 호출 순서를 아무도 복원하지 못하는 함정이다. 지표는 있는데 기록이 없다.

맥락

E4가 P2 이상, 특히 P3 처분 보조(지급·승인·반려 결과에 직결)에 관여하는 AI 부품. 모델·프롬프트가 자주 바뀌는 상용 API 과제.

맞서는 힘(긴장)

  • 집계 지표의 손쉬움 vs 건별 재생 기록의 저장·보호 비용
  • 개인정보 최소 보관 vs 사고 재현 가능성
  • 빠른 모델·프롬프트 변경 vs 버전별 재현

해법

  • P3 처분 보조에 관여하면서 재생 기록이 없다
  • 모델·프롬프트 버전을 기록하지 않는다

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 같은 입력이면 같은 출력이 나와 재생이 자명한 경우

얻는 것

  • 기록에 당시 모델·프롬프트 버전이 포함되는가
  • 기록의 변조 방지 장치가 있는가
  • 이의제기 처리에 재생 기록이 쓰이는가

X7 도구 설명 ≠ 실제 권한 안티패턴

MCP 도구 설명은 '조회'인데 코드는 쓰기·실행 권한을 가져, 설명만 믿고 도구를 부르는 에이전트가 의도하지 않은 변경을 일으키는 함정이다.

맥락

E3 MCP·CLI 설정 환경에서 A8 MCP 서버·호스트를 만들거나 가져다 쓰는 과제. 특히 업무 시스템 MCP(쓰기, P2)와 공공데이터 MCP(읽기, P0)가 한 호스트에 함께 연결된 경우.

맞서는 힘(긴장)

  • 빠른 MCP 래핑 vs 도구별 권한 분리
  • 도구 하나로 묶는 편의 vs 읽기/쓰기 분리의 운영 부담
  • 에이전트 자율 호출 vs 실행 전 승인

해법

A8의 각 도구에 실제 권한 수준(P0~P4)을 설명과 함께 명시하고, C8 권한 경계로 읽기 전용 도구와 쓰기 도구를 서로 다른 서버·인증으로 분리한다. 쓰기·실행 도구는 도구별 실행 승인과 호출 상한, 킬스위치를 둔다. 반입하는 MCP 서버는 S11 인제스천·공급망 검증에서 PAX 6축(권한 표면·비밀·공급망·위생·인젝션·데이터 흐름)을 통과해야 활성화한다. 사람에게는 F6 에이전트 행동 검토·확인으로 실행 전 무엇을 할지 보여 주고, 승인·실패는 C4에 남긴다.

이럴 때 쓴다

  • MCP 도구 설명과 실제 권한(쓰기·삭제·발송)이 다르다
  • 읽기와 쓰기 도구가 같은 서버·같은 인증 토큰을 쓴다
  • 도구별 권한 수준·실행 승인이 문서에 없다
  • 6축 검증에서 권한 표면이 '주의'로 나왔다

이럴 때는 쓰지 않는다

  • 읽기 전용 MCP로 설계되어 쓰기 기능이 배제된 경우
  • 쓰기 도구가 있지만 설명에 부수 효과가 명시되고 C8 실행 승인이 있는 경우
  • MCP가 아닌 결정적 스크립트로 권한이 코드에 고정된 경우

얻는 것

  • 기존 API를 빠르게 에이전트 도구로 만든다
  • 도구 수가 적어 관리가 쉬워 보인다

점검표

  • 모든 도구의 설명에 실제 권한과 부수 효과가 적혀 있는가
  • 읽기와 쓰기 도구가 서로 다른 인증을 쓰는가
  • 쓰기 도구에 실행 전 승인이 있는가
  • 반입 MCP가 6축 검증을 통과했는가

구조 — 참여 부품

  • A8 MCP 서버·호스트 — 도구 설명과 실제 권한이 일치해야 하는 곳
  • C8 권한 경계·킬스위치 — 읽기/쓰기 분리, 도구별 승인
  • S11 인제스천·공급망 검증 — 반입 시 6축 검증
  • F6 에이전트 행동 검토·확인 — 실행 전 사람에게 행동을 보여 줌

변형

  • API 통째 래핑: 기존 API 클라이언트를 감싸 조회·수정 함수가 같은 도구·인증으로 노출

  • 설명 누락: 도구 설명에 부수 효과(삭제·발송)가 적혀 있지 않음
