판정 근거

Screen Studio 대안을 표방하는 오픈소스 화면 녹화 도구(Rust·Tauri). 사람이 받는 산출물은 녹화 영상이며 클릭 기반 자동 줌·주석은 규칙 기반이라 B0. 자막만 Whisper.cpp 온디바이스 STT로 만들어 B4(STT·자막) secondary, 오픈웨이트 모델 로컬 구동 A2.2·온디바이스 추론 A5. '음성 데이터가 PC 밖으로 나가지 않는다'는 설계 서술이 S12 데이터 비도달. 원장 model_dependency는 없음(비LLM)이라 그대로 옮겼으나 음성 모델 의존은 표현되지 않는다. 공공 도구 시연·교육 영상 제작용 참고 도구라 D8.10·유형 6. 해외 오픈소스 참고 사례라 전이 단계는 적용 불가(개인 사용은 형식값). URL 없음.

구현 가이드

주 패턴 B0 결정적 도구을 구현할 때

구현 단계

  1. 반복 업무의 입력 파일·서식과 원하는 산출물을 나열하고, 처리 규칙을 사람이 읽을 수 있는 조건→결과 표로 먼저 적는다.
  2. HWP·HWPX·엑셀 입출력은 A10 어댑터로 분리하고, 공공 깃랩(A3) 등에 있는 기존 어댑터를 먼저 찾는다.
  3. AI 코딩 도구(A7)로 규칙 코드와 화면을 만들고, 런타임에 모델·외부 API를 부르지 않는지 네트워크 의존을 점검한다.
  4. 대표 입력 세트로 같은 입력에 같은 결과가 나오는지 확인하고 규칙 표와 코드의 대응을 문서로 남긴다.
  5. 부서 공유 이상으로 옮길 때 라이선스·저장소 위치·처리 로그(C4)·원복 경로(C3)를 갖춰 담당자 이동에 대비한다.

점검표

  • 런타임에 LLM·ML 호출이 전혀 없는가
  • 규칙 표가 코드와 별도로 문서화되어 있는가
  • 같은 입력에 같은 결과가 나오는지 확인했는가
  • 라이선스와 저장소 위치가 명시되어 인수인계가 가능한가

환경 조건

E2 = 없음(비LLM). E1 로컬 완결이 다수이며 폐쇄망 이식이 가장 쉬운 부품이다. E4는 대개 P0~P1이다. 로컬 PC 완결이면 C5 비식별 부담은 줄지만 C4 로그가 사라지므로 기관으로 전이할 때 다시 장착한다(§5 매트릭스).

주의할 점

  • 비정형 입력에 취약
  • 규칙 유지보수가 사람에게 남음
  • 개인 제작 도구가 담당자 이동과 함께 멈출 위험(X9)
  • AX 단계는 Ready에 머묾

기본 배선 예

A7 → B0 → A10 (HWPX 출력) · B0 → C4 (처리 로그, 기관 전이 시)

보완이 필요한 필수 부품

이 조합에서 카탈로그가 함께 갖추라고 권하는 부품 가운데 아직 확인되지 않은 것이다.

  • A9 업무 규범 스킬 보고서 구조·문체·서식·검증 절차 같은 업무 규범을 모델 중립 스킬(지침 + 검증기 + 출력 서식)로 패키징해 어떤 모델·에이전트에서든 재사용한다.
  • C5 가드레일 필터 개인정보·환각·편향·형식 오류가 프롬프트나 산출물에 들어가지 못하게 시스템이 경계에서 걸러낸다. 비식별 전처리, 출처 검증, 구조적 출력 제약이 대표 변형이다.
  • C1 검토 큐 AI 산출물이 다음 단계로 넘어가기 전에 사람이 맞고 틀림을 확인·수정·확정하는 대기열을 두어, 오류가 업무 결과로 흘러가지 않게 한다.
  • F3 결과 대안·부분 재생성 한 요청에 여러 안을 주고 일부만 다시 만들게 해, 첫 결과가 마음에 들지 않을 때 전체를 다시 요청하지 않아도 되게 한다. B′6 반복 개선의 이용자 면이다.

피해야 할 안티패턴

  • X9 담당자와 함께 사라지는 도구 개인이 만든 도구가 부서에 퍼졌지만 라이선스·저장소·인수인계가 없어, 만든 사람의 인사이동과 함께 멈추는 함정이다. 대처: 도구가 부서에 퍼지기 시작하면 A7 산출물에 MIT·Apache 등 라이선스를 명시하고, 코드를 개인 PC가 아니라 A3 공공 깃랩 같은 공용 저장소에 등재한다. 업무 규범·프롬프트는 A9 업무 규범 스킬로 패키징해 다른 담당자가 그대로 쓸 수 있게 하고, 설치·설정·데이터 경로를 담은 인수인계 문서를 둔다. 도구를 참조 구현 레지스트리(§13)에 올려 소유를 개인에서 조직으로 옮긴다. transition.blocker에 '담당자 이동'이 적힌 과제는 이 조치를 먼저 한다.
  • X1 AI 스티커 기존 화면에 요약·챗봇 버튼만 붙이고 업무 순서와 사람·AI의 역할 분담은 그대로 두어, AI가 있어도 업무 산출물이 바뀌지 않는 함정이다. 대처: 먼저 가치 흐름 규칙(R1)으로 사람 또는 국민이 최종으로 받는 핵심 산출물을 정하고, 그 산출물을 AI가 어떤 모양으로 분담할지 B 업무 컴포넌트를 하나 고른다(초안→사람 확정이면 B1, 근거 접지 답변이면 B3, 서류 추출이면 B4). 사람이 확정하는 지점은 C1 검토 큐로, 이용자가 고쳐 확정하는 면은 F2 편집 가능한 출력으로 명시한다. 흐름이 바뀌었는지는 C4 감사 로그·지표의 처리시간·수정률로 잰다. AI 런타임이 전혀 없는 행정정보시스템이라면 AI로 포장하지 말고 R24대로 B0·service_type 0·platform 공란·X1(AI 무관)으로 정직하게 분류한다.

B4 인식 파이프라인 업무 컴포넌트

서류·음성·영상·도면 같은 비정형 입력을 인식 → 구조화 → 판정으로 연쇄 처리해 사람이 옮겨 적던 단계를 없앤다.

PAX 사례 34건이 이 부품을 쓴다

맥락

접수·심사(유형 ②), 서류 진위확인, 민원 통화 정리, 실시간 자막, 원격탐사·도면 판독처럼 비정형 입력이 업무의 출발점인 경우에 쓴다. 민감 서류가 많아 행정망·로컬 모델 조건이 자주 붙는다.

맞서는 힘(긴장)

  • 자동 연결의 효율 vs 오인식이 판정으로 번지는 위험
  • 인식 정확도 vs 로컬 모델 제약(E1·E5)
  • 단계 분리의 추적 용이성 vs 단계 간 지연

해법

인식(OCR·STT·비전·VLM)은 정형 필드만 내게 하고, 기준정보와의 대조·요건 판정은 규칙 단계가 맡는다(B′1 + B′9). 저신뢰·불일치 건은 보류해 C1 검토 큐로 보내고, 오인식은 C3 상태 머신으로 되돌린다. 공공 문서 형식은 A10으로 받으며 OCR·STT 엔진은 A2 공통 후보를 쓴다. 제출 서류처럼 신뢰 불가 입력을 읽고 시스템 쓰기가 있으면 문서별 격리(S6)로 서류 속 지시가 판정을 바꾸지 못하게 한다.

이럴 때 쓴다

  • 비정형 입력을 사람이 옮겨 적는 단계가 업무의 병목일 때
  • 추출값이 규칙 판정·다음 처리로 이어질 수 있을 때
  • 유형 ② 접수·심사 자동화의 기본 조립일 때

이럴 때는 쓰지 않는다

  • 추출 결과가 초안으로 멈추고 사람이 확정할 때(B1)
  • 추출 뒤 질의응답이 핵심 산출물일 때(B3)
  • 상시 관측 스트림 감시가 핵심일 때(B5)

얻는 것

  • 옮겨 적기 단계 제거
  • 판정 기준이 규칙으로 남아 설명 가능
  • OCR·STT 엔진을 범정부 공통으로 공유 가능

점검표

  • 인식과 판정이 서로 다른 단계로 분리되어 있는가
  • 저신뢰 건이 보류되어 사람에게 가는가
  • 오인식 건을 되돌리는 경로가 있는가(C3)
  • 필드별 정확도를 잰 시험 세트가 있는가

구조 — 참여 부품

  • A2 모델 서빙 계층 — OCR·STT·VLM 엔진

  • C3 상태 머신·롤백 — 오인식 되돌림·재처리

변형

B0 결정적 도구 업무 컴포넌트

AI 코딩으로 만들었지만 런타임에는 AI를 부르지 않고 규칙과 원문 발췌만으로 같은 입력에 같은 결과를 내는 취합·변환·검색·시각화 도구다.

PAX 사례 413건이 이 부품을 쓴다

맥락

AI 코딩 도구(A7)로 기관 인력이 직접 만든 자생 도구가 대부분이다(PAX 557건 가운데 주 부품이 B0인 사례 390건, 70%). 로컬 PC 완결이나 폐쇄망 이식이 필요한 업무, 판정 재현성이 감사에서 중요한 업무에도 맞는다. model_dependency가 '없음(비LLM)'으로 확인될 때만 해당한다.

맞서는 힘(긴장)

  • 재현성·설명 가능성 vs 비정형 입력을 다루는 유연성
  • 로컬 완결의 보안 이점 vs 기관 전이 시 처리 로그(C4)와 인수인계가 사라지는 문제
  • 규칙을 코드에 넣는 단순함 vs 규정이 바뀔 때마다 사람이 규칙을 고쳐야 하는 유지 부담

해법

업무 절차를 입력 형식(A10 어댑터)과 처리 규칙으로 나누고, AI 코딩 도구(A7)는 개발 시점에만 써서 규칙 코드와 화면을 만든다. 런타임에는 모델을 호출하지 않으므로 같은 입력에 같은 결과가 나오고 인터넷 없이 로컬에서 돈다. 판정이 필요한 경우에도 결정적 규칙 엔진이 낸다. 비정형 입력을 다뤄야 하는 단계가 생기면 그 단계만 B1·B3로 승격하고 결정적 부분은 전처리로 남긴다. 부서 밖으로 옮길 때는 라이선스·저장소·처리 로그를 함께 갖춘다.

이럴 때 쓴다

  • 입력이 정형(엑셀·서식)이고 처리 결과를 규칙으로 정의할 수 있을 때
  • 파일이 PC 밖으로 나가면 안 되거나 폐쇄망·로컬 완결이 필요할 때
  • 판정 재현성이 필요해 같은 입력에 늘 같은 결과가 나와야 할 때(규칙 점검기, 결정론 점수 엔진)
  • LLM 도입 전에 데이터·기준선을 정비하는 단계일 때

이럴 때는 쓰지 않는다

  • 비정형 문서의 요약·초안처럼 규칙으로 산출물을 정의할 수 없을 때(B1)
  • 질문이 다양해 규정·선례 접지가 필요한 상담일 때(B3)
  • 학습 모델의 수치·등급 예측이 핵심 산출물일 때(B2)

얻는 것

  • 재현성과 감사 가능성
  • 폐쇄망·로컬 이식이 가장 쉬움
  • 모델 호출 비용과 모델 장애 위험이 없음
  • B1·B3의 전처리 부품으로 승격할 자산

점검표

  • 런타임에 LLM·ML 호출이 전혀 없는가
  • 규칙 표가 코드와 별도로 문서화되어 있는가
  • 같은 입력에 같은 결과가 나오는지 확인했는가
  • 라이선스와 저장소 위치가 명시되어 인수인계가 가능한가

구조 — 참여 부품

  • A7 자체 제작 환경 — 개발 시점에 AI 코딩으로 규칙 코드와 화면을 만드는 곳

  • 규칙 엔진 — 조건→결과 표에 따라 결정적으로 취합·판정·정렬
  • 담당자 — 결과를 받아 쓰고 규칙 변경을 요청

변형

  • 문서·엑셀 자동화: 부서별 제출 파일 취합·병합·서식 변환(카드 기본 변형)
  • 데이터 탐색·시각화: 공공데이터·내부 데이터를 지도·차트·대시보드로 보여 준다(카드 기본 변형)

  • 도구 허브·링크 큐레이션: 흩어진 업무 도구·링크를 한 화면에 모은다(R15)

  • 알림·컨텍스트 복귀 도구: 마감·할 일 알림, 작업 맥락 복귀(R15)

오픈웨이트 모델을 기관 서버·폐쇄망·로컬 PC 안에서 Ollama·vLLM 등으로 구동해 데이터를 기관 밖으로 내보내지 않고 추론한다.

PAX 사례 54건이 이 부품을 쓴다

맥락

E1은 폐쇄망·행정망·로컬 PC, E2는 해외 오픈웨이트(로컬) 또는 국산 오픈웨이트, E5는 S 이상이다. 폐쇄망 B3·B6·B8, 유형 3(현장 폐쇄망 서버 추론), 유형 12 개발 코파일럿은 이 변형을 기본으로 쓴다.

맞서는 힘(긴장)

  • 데이터 주권 vs 상용 최신 모델 대비 성능
  • GPU·서버 고정비 vs 종량 과금
  • 모델 운영·갱신 역량 vs 외부 의존 제거
  • 저사양 장비 구동 vs 모델 크기

해법

오픈웨이트 모델을 기관 안에 설치하고 서빙 계층(Ollama·vLLM·LM Studio 등)으로 업무 부품에 노출한다. 임베딩 모델도 로컬로 두어 B3 검색까지 망 안에서 끝낸다(§5 E1 폐쇄망 행 '로컬 임베딩'). 모델 선정은 C9 평가 세트로 상용·온프레미스 후보를 같은 조건에서 비교해 정한다. 폐쇄망에서 C7 경로는 수동 전환·다른 로컬 모델로 제한되므로 둘 이상의 로컬 모델이나 수동 절차를 미리 둔다. 모델·패키지 반입은 S11 인제스천 검증을 거친다.

이럴 때 쓴다

  • E1이 폐쇄망·행정망이거나 문서가 PC 밖으로 나가면 안 될 때
  • E5가 S 이상인데 내부망 프록시(A2.4)를 쓸 수 없을 때
  • 현장 폐쇄망 서버에서 추론해야 하는 유형 3
  • C7의 대체 경로로 로컬 모델을 둘 때

이럴 때는 쓰지 않는다

  • 추론 인프라·운영 인력을 확보할 수 없을 때
  • 현장 기기 자체에서 돌아야 하면 A5(엣지 런타임)
  • 모델을 재학습했으면 A2.3

얻는 것

  • 데이터가 기관 밖으로 나가지 않음
  • 호출 비용이 고정비로 바뀜
  • 폐쇄망에서도 LLM 사용 가능
  • C7의 대체 경로 후보

점검표

  • 추론·임베딩 어디에서도 데이터가 망 밖으로 나가지 않는가
  • 모델 선정 근거(평가 세트 비교)가 남아 있는가
  • 반입한 모델·패키지의 무결성 검사 기록이 있는가
  • 대체 로컬 모델 또는 수동 전환 절차가 있는가

구조 — 참여 부품

  • A2 서빙 계층 — 로컬 모델을 업무 부품에 노출
  • 오픈웨이트 모델·로컬 임베딩 — 기관 안에서 추론·색인
  • GPU 서버 또는 워크스테이션 — 추론 인프라
  • S11 인제스천·공급망 검증 — 폐쇄망 반입 모델·패키지 검사

변형

  • 기관 서버형: vLLM 등으로 기관 GPU 서버에서 다수 이용자에게 서빙한다.
  • 로컬 PC·워크스테이션형: Ollama·LM Studio로 개인 PC나 단일 워크스테이션에서 돌린다(온나라 sAIde).
  • 범정부 공통기반 내부망 설치형: 국산 독자모델·오픈웨이트를 공통기반 내부망에 직접 설치해 여러 부처에 제공한다(PAX 행정안전부 사례).

참조 구현 예

  • PAX 01963ce2b093182c — 양산시, 저사양 온프레미스 로컬 LLM으로 보고서 작성 전 과정을 폐쇄망 안에서 처리(§13 A2.2)
  • PAX 온나라 sAIde — 온나라 사이드패널 + 로컬 Ollama 요약(§9)

A5 엣지 추론 런타임 공통 서비스

현장 기기에 경량 모델을 배포·갱신해 망 단절·지연·영상 반출 없이 현장에서 추론한다.

PAX 사례 3건이 이 부품을 쓴다

맥락

E1이 로컬·폐쇄망인 B5 현장 감지·경보의 기반이다. 유형 3에서는 필수 부품 후보 가운데 하나다(R10: A5 또는 A2.2 또는 A2.5). PAX 557건에서는 3건뿐이다.

맞서는 힘(긴장)

  • 현장 추론의 저지연·무반출 vs 경량화에 따른 정확도 손실
  • 기기 분산 배포 vs 모델 버전 일관성
  • 망 단절 내성 vs 원격 갱신·감시의 어려움

해법

중앙에서 학습·검증한 모델을 ONNX·TensorRT 등으로 경량화해 현장 단말·NPU·카메라에 배포하고, 추론·위험 판정·경보 제어까지 현장에서 완결한다. 중앙에서 검증·승인한 모델 버전만 단말에 올리고, 망이 없으면 물리매체로 갱신한다. 원본 영상은 상시 저장하지 않고 이벤트 시에만 짧게 저장하는 식으로 반출을 줄인다. 현장 출력은 A11로, 조치 기록은 C4로 보내고, 상시 서비스이므로 C7 Fail-safe를 함께 둔다.

이럴 때 쓴다

  • 현장 통신이 불안정하거나 폐쇄망일 때
  • 영상·음성을 중앙으로 보내면 안 될 때
  • 경보 지연이 곧 피해로 이어지는 상시 감시

이럴 때는 쓰지 않는다

  • 추론을 기관 서버에서 해도 지연·반출 문제가 없으면 A2.2·A2.5
  • 모델이 커서 현장 기기에 올릴 수 없을 때

얻는 것

  • 망 단절에도 서비스 지속
  • 지연 최소화
  • 원본 영상 반출 감소

점검표

  • 현장 기기에 배포된 모델 버전을 중앙에서 알 수 있는가
  • 승인되지 않은 모델이 단말에 올라갈 수 없는가
  • 원본 영상의 저장·반출 범위가 정해져 있는가
  • 단말 장애 시 안전 상태가 정의되어 있는가

구조 — 참여 부품

  • 현장 단말·NPU·카메라 — 경량 모델로 현장 추론
  • 중앙 학습·검증 서버 — 모델을 학습·검증·승인해 패키지로 배포
  • A11 액추에이션·현장 통지 어댑터 — 현장 추론 결과를 경보·설비로 출력
  • C7 폴백 스위치 — 상시 서비스의 Fail-safe

변형

  • 단말 완결형: 외부 통신 없이 NPU 단말 안에서 탐지→위험판정→경보제어와 운영 웹서버까지 완결한다.
  • 3계층 물리매체형: 학습(내부망 GPU)–현장 단말–취득 장비를 온라인 없이 물리매체로 잇고 승인된 모델만 배포한다.
  • 기존 설비 재사용형: 기존 CCTV·센서를 재사용해 현장에서 추론한다.
  • 브라우저 모델형: WebGPU로 브라우저 안에서 모델을 돌린다.

S12 데이터 비도달 설계 보안 패턴

개인정보·원문을 단말(브라우저·PC·기기)에서 처리해 서버나 외부로 아예 보내지 않는다. v0.6 후보 부품으로, 카드 없이 R4 한 줄 정의와 §13 레지스트리로만 등재되어 있다.

PAX 사례 36건이 이 부품을 쓴다

맥락

PAX 자생 도구처럼 브라우저 단독 HTML·데스크톱 앱·로컬 모델로 업무 PC 안에서 완결되는 도구(E1 로컬 PC 완결). PAX 557건 태깅에서 S 부품 중 최다(36건)로 관측되었다. 카탈로그상 후보이며 위협 매트릭스·조립 템플릿에는 아직 들어가 있지 않다.

맞서는 힘(긴장)

  • 유출 경로 제거 vs 중앙 로그·감사 기록 부재(C4 소실)
  • 로컬 처리의 단순함 vs 단말 성능·로컬 모델 품질 한계
  • 개인 도구의 자율성 vs 기관 전이 시 운영 통제 재장착

해법

개인정보·원문을 다루는 처리를 브라우저 내 로컬 처리·데스크톱 앱·로컬 모델(A2.2·A5)로 단말 안에서 끝낸다. 외부 호출이 꼭 필요하면 호출 범위를 한 기능(예: 음성 인식)으로 좁히고 키·원문·결과는 호스트 밖으로 내보내지 않는다. 무통신 여부를 이용자가 직접 확인할 수 있게(인터넷 차단 후 동작, 개발자 도구로 네트워크 확인) 안내한다. 기관으로 전이할 때는 사라진 C4 로그를 다시 붙인다. ^[inferred]

이럴 때 쓴다

  • 개인정보가 담긴 문서를 마스킹·취합하는 개인·부서 도구
  • 외부 전송이 허용되지 않는 데이터(E5 S 이상)를 다루는 소규모 도구
  • 인터넷 차단 환경에서 쓰는 문서 도구

이럴 때는 쓰지 않는다

  • 여러 사용자의 데이터를 모아야 하는 기관 서비스(중앙 저장이 과업 자체)
  • 감사 로그(C4·S10)가 필수인 처분 관여(P3) 과제에서 기록 없이 로컬 완결만 주장할 때
  • 단말 성능으로 필요한 모델 품질을 낼 수 없을 때

얻는 것

  • 서버 쪽 유출 경로 제거
  • 비식별 전처리(C5)가 불필요해짐
  • 1인 개발 도구도 개인정보를 다룰 수 있음

점검표

  • 원문·개인정보가 단말 밖으로 전송되는 경로가 없는가
  • 외부 호출이 있다면 무엇이 나가는지 문서화되어 있는가
  • 이용자가 무통신을 검증할 수 있는가
  • 기관 전이 시 기록 재장착 계획이 있는가

구조 — 참여 부품

  • 단말 처리기 — 브라우저·데스크톱 앱에서 파싱·마스킹·취합 수행
  • A2.2 주권형 온프레미스 — 로컬 Ollama 등으로 추론을 단말에서 수행
  • A5 엣지 추론 런타임 — 현장 기기에서 추론
  • 이용자 검증 안내 — 무통신을 이용자가 직접 확인하도록 안내

변형

  • 브라우저 단독형: 단독 HTML 한 파일 또는 브라우저 내 로컬 처리로 파일이 서버에 도달하지 않음
  • 로컬 모델 오프라인형: 데스크톱 앱과 로컬 모델로 완전 오프라인 동작
  • 부분 외부 호출형: 키·원문·결과는 호스트에 두고 특정 기능 호출만 범정부 공통기반으로 내보냄

D8.10 발간·홍보 서비스 블록

보도자료·카드뉴스·포스터·정보지를 기획부터 발행까지 만드는 내부 운영 블록이다. B7 콘텐츠 제작의 업무 블록 버전이다.

PAX 사례 22건이 이 부품을 쓴다

맥락

기관이 외부에 내는 발행물을 만드는 업무. §7.3 유형 ⑥ 정책·홍보 콘텐츠 제작(D8.10, P1). PAX 22건(주 부품 B0 45%, B7 36%).

맞서는 힘(긴장)

  • 제작 속도 vs 사실·저작권 검수
  • 스타일 일관성 vs 매번 다른 요구
  • 생성자-비평가·반복 개선 품질 vs 반복 비용(X12)
  • 참고 링크 활용 vs 보도자료·링크 속 유출 링크 삽입 위협

해법

B7 콘텐츠 제작을 B′8 계획-실행(기획 → 구성 → 생성 → 편집)과 B′6 반복 개선으로 배선하고, 반복 상한을 둔다. 기관 스타일은 A9 스타일 스킬로 패키징하고, 보도자료 입력은 A10(HWPX)으로 읽는다. 발행 전에는 C5 저작권·사실 검증과 C1 검수를 필수로 두고, 필요하면 C1.2 심의 게이트(법무·표시광고)를 더한다. 출력은 F2 편집 가능(PPTX·피그마 등)과 F3 대안·부분 재생성으로 담당자가 고치게 한다. S8 독립 검증기로 유출 링크·사실 오류를 거른다.

이럴 때 쓴다

  • 보도자료를 여러 발행 형식으로 반복 제작할 때
  • 기관 스타일을 여러 담당자가 일관되게 써야 할 때
  • 외부 디자인 용역 의존을 줄이고 싶을 때

이럴 때는 쓰지 않는다

  • 내부 보고서·공문 첫 판이면 D8.3
  • 발행 없이 자료 요약만 하면 D8.2
  • 국민에게 개인 맞춤 안내를 주면 D7

얻는 것

  • 발행물 제작 시간 단축
  • 기관 스타일 일관성
  • 외부 용역 의존 감소

점검표

  • 발행 전 사람 검수가 필수로 걸려 있는가
  • 사실·저작권 검증 절차가 있는가
  • 결과를 편집 가능한 형식으로 고칠 수 있는가
  • 반복 개선에 상한이 있는가

A9 업무 규범 스킬 공통 서비스

보고서 구조·문체·서식·검증 절차 같은 업무 규범을 모델 중립 스킬(지침 + 검증기 + 출력 서식)로 패키징해 어떤 모델·에이전트에서든 재사용한다.

PAX 사례 54건이 이 부품을 쓴다

맥락

기안·보고서·콘텐츠처럼 서식과 문체가 정해진 산출물을 만드는 B1·B7, BYO 코딩 에이전트 환경(E2 모델 중립), 개발 코파일럿에서 쓴다. 유형 4·6·12에서는 필수 기반이고, §7.2 진행 경로에서는 3단계에 놓인다.

맞서는 힘(긴장)

  • 규범 고정(일관성) vs 담당자 재량
  • 모델 중립(이식성) vs 특정 모델 최적화
  • 규범 공개·재사용 vs 프롬프트·규범 유출
  • 가중치에 넣기(튜닝) vs 문서로 주입하기

해법

규정집·매뉴얼·서식 예시에서 업무 규범을 뽑아 지침(구조·문체·금지 사항), 검증기(형식·인용·수치 검사), 출력 서식(HWPX·DOCX 등)으로 묶은 스킬 패키지로 만든다. 모델 호출 코드와 분리된 파일로 두어 어떤 코딩 에이전트·모델에서도 같은 절차가 돌게 한다(External Configuration). 산출·검증된 수치와 출처만 주입하고 미제공 수치·순위 생성을 금지하는 식으로 생성 범위를 규범으로 좁힌다. 스킬은 버전으로 관리해 규범 유출·변경을 추적하고, C9로 스킬 변경 전후 품질을 잰다.

이럴 때 쓴다

  • 산출물 서식·문체·구조가 정해져 있을 때
  • 출력 품질이 들쭉날쭉할 때(§7.5)
  • BYO 환경에서 모델과 무관하게 같은 절차를 돌려야 할 때
  • 갱신이 잦은 규범을 튜닝 없이 반영해야 할 때

이럴 때는 쓰지 않는다

  • 규범이 문서로 정리되지 않았고 정리할 담당도 없을 때
  • 지식 검색이 필요한 문제(B3 접지가 먼저)
  • 스킬 내용 자체가 민감해 배포할 수 없는데 버전 관리·접근 통제를 둘 수 없을 때

얻는 것

  • 출력 일관성
  • 모델 교체 가능(BYO에서는 교체 가능성이 곧 C7)
  • 타 기관 재사용
  • 튜닝 없이 규범 갱신

점검표

  • 규범이 모델 호출 코드와 분리된 파일로 있는가
  • 검증기가 출력 형식·인용·수치를 실제로 검사하는가
  • 스킬에 버전이 있는가
  • 다른 모델로 바꿔도 같은 서식이 나오는지 확인했는가

구조 — 참여 부품

  • A10 문서 형식 어댑터 — 출력 서식을 HWPX·DOCX로 내보냄
  • C9 평가 세트 — 스킬 변경 전후 품질 비교

C5 가드레일 필터 운영 컴포넌트

개인정보·환각·편향·형식 오류가 프롬프트나 산출물에 들어가지 못하게 시스템이 경계에서 걸러낸다. 비식별 전처리, 출처 검증, 구조적 출력 제약이 대표 변형이다.

PAX 사례 44건이 이 부품을 쓴다

맥락

외부 모델을 부르거나 대민에 답하는 모든 B 부품. 특히 E2 해외 상용 API, E5 S 이상 데이터, B3 지식 접지 상담, 유형 ① 대민 상담, ④ 기안, ⑥ 콘텐츠, ⑦ 대조·점검, ⑨ 인수인계, ⑬ 비식별·정제 도구.

맞서는 힘(긴장)

  • 차단의 엄격함 vs 과잉 차단으로 인한 유용성 저하
  • 비식별 강도 vs 문맥 보존
  • 결정적 검증의 신뢰성 vs 구현 범위

해법

프롬프트가 기관 밖으로 나가기 전 PII를 마스킹하고 원복 키를 보관하는 비식별 전처리기를 둔다. 응답에는 인용을 원본(법령정보센터·통계표 등)과 대조하는 출처 검증기와, JSON 스키마·허용 목록 같은 구조적 출력 제약을 건다. 근거가 없으면 답하지 않거나 '확인 필요'로 표시한다. 차단 사유는 C4에 남기고, 이용자에게는 F1 출처와 F7 한계 안내로 보인다. 사람이 하는 팩트체크·법무 심의는 C5가 아니라 C1.2에 둔다.

이럴 때 쓴다

  • E2 해외 상용 API로 행정망 본문이 외부로 나갈 때(필수)
  • E5 S 이상 개인정보·민감정보를 다룰 때
  • B3 대민 응답처럼 인용·수치의 정확성이 신뢰의 핵심일 때
  • C5가 필수인 유형 ①④⑥⑦⑨⑪⑬

이럴 때는 쓰지 않는다

  • E1 로컬 PC 완결로 데이터가 밖으로 나가지 않을 때 비식별은 불필요해질 수 있다(§5 매트릭스, 단 출처 검증은 별개)
  • 사람이 수행하는 심의만 있을 때(C1.2로 태그)
  • 적대적 입력 탐지가 목적일 때(S8)

얻는 것

  • 개인정보 외부 유출 차단
  • 환각 인용 감소
  • 상용 API 사용 조건 충족

점검표

  • 외부 전송 전 무엇이 걸러지는지 답할 수 있는가
  • 인용이 원본과 대조되는가
  • 근거 없을 때의 동작이 정해져 있는가
  • 차단 사유가 기록되는가

구조 — 참여 부품

  • 비식별 전처리기 — 외부 전송 전 PII 마스킹과 원복
  • 출처 검증기 — 인용을 원본과 대조해 환각을 걸러냄
  • 출력 제약 — 스키마·허용 목록·금칙어로 출력 형식 제한
  • F1 출처 표시 — 검증된 출처를 이용자에게 보임

변형

C1 검토 큐 운영 컴포넌트

AI 산출물이 다음 단계로 넘어가기 전에 사람이 맞고 틀림을 확인·수정·확정하는 대기열을 두어, 오류가 업무 결과로 흘러가지 않게 한다.

PAX 사례 46건이 이 부품을 쓴다

맥락

AI 산출물이 공문·처분·대민 안내·기록으로 이어지는 모든 B 부품(B1 코파일럿, B4 인식 파이프라인, B2 예측기, B7 콘텐츠 생성기 등). 이용자 본인이 최종 확정자인 자기서비스형 도구도 포함한다(R16).

맞서는 힘(긴장)

  • 정확성·책임성 vs 처리 속도(전건 검토는 자동화 이득을 깎는다)
  • 검토자의 숙련 vs 자동화 편향(AI 결과를 그대로 승인하는 경향)
  • 전건 검토의 안전 vs 위험도별 분기(C2)로 가야 하는 효율 압력

해법

AI 산출물에 신뢰도·근거를 붙여 검토 대기열에 올리고, 검토자가 승인·수정·반려 중 하나를 고르게 한다. 수정·반려 내역은 C4 감사 로그에 남겨 수정률을 집계하고 C6 환류의 입력으로 쓴다. 검토 화면은 원문 위치·근거를 함께 보여 줘 확인 비용을 줄인다. 전건 검토로 시작하되, 수정률 실측이 쌓이면 C2 위험도 라우터로 저위험 건을 자동 종결하는 단계로 옮긴다.

이럴 때 쓴다

  • AI 산출물이 공문·처분·대민 안내로 그대로 이어질 때
  • E4가 P1 이상이고 되돌리는 데 사람 시간이 많이 드는 조치가 있을 때
  • 서비스 유형 ② 접수·심사, ④ 기안 코파일럿, ⑥ 콘텐츠 제작, ⑦ 대조·점검, ⑩ 위험 예측, ⑪ 추천·매칭, ⑫ 개발 코파일럿처럼 C1이 필수인 유형

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 런타임 AI 산출물이 없을 때
  • 쉽게 되돌릴 수 있고 저위험인 조치를 이미 C2로 자동 종결하도록 실측 근거를 갖춘 구간(전건 검토를 영원히 남기지 않는다)

얻는 것

  • 오류가 업무 결과로 나가기 전에 차단
  • 책임 소재가 명확해짐
  • 수정 내역이 C4 지표와 C6 환류의 원천 데이터가 됨

점검표

  • AI 산출물이 확정 전 상태로 머무는 지점이 명시되어 있는가
  • 검토자와 승인·수정·반려 선택지가 정해져 있는가
  • 검토 결정과 수정 내역이 로그로 남는가
  • 실증 기간의 검토·수정 건수가 기록되어 있는가
  • 전건 검토에서 분기로 옮길 조건이 정해져 있는가

구조 — 참여 부품

  • 검토 대기열 — AI 산출물을 확정 전 상태로 보관하고 검토자에게 배정
  • 검토자(담당자 또는 이용자 본인) — 승인·수정·반려를 결정하는 최종 책임자
  • F2 편집 가능한 출력 — 검토자가 산출물을 직접 고치는 화면
  • C4 감사 로그·지표 — 검토 결정과 수정 내역을 적재해 수정률로 집계

변형

  • 전건 검토형: 모든 AI 산출물을 담당자가 확인·확정
  • 예외 검수형: 정상 건은 일괄 승인하고 저신뢰 항목만 개별 검수하는 검수 UI
  • 파이프라인 내장 관문형: 멀티에이전트·다단계 파이프라인의 각 관문에 승인·보완·재작성 선택지를 둠
  • 자기서비스형: 이용자 본인이 최종 확정자인 HITL. 실제 운영 중이면 C1 present(R16)
  • 심의 게이트: 팩트체크·법무·윤리처럼 제3자 전문가가 수행하는 승인 게이트

X9 담당자와 함께 사라지는 도구 안티패턴

개인이 만든 도구가 부서에 퍼졌지만 라이선스·저장소·인수인계가 없어, 만든 사람의 인사이동과 함께 멈추는 함정이다.

맥락

  • 공식 절차 없이 바로 퍼진다

점검표

  • 라이선스가 명시되어 있는가
  • 원본이 공용 저장소에 있는가
  • 만든 사람 없이 후임이 설치·실행할 수 있는 문서가 있는가

X1 AI 스티커 안티패턴

기존 화면에 요약·챗봇 버튼만 붙이고 업무 순서와 사람·AI의 역할 분담은 그대로 두어, AI가 있어도 업무 산출물이 바뀌지 않는 함정이다.

맥락

기존 행정정보시스템·업무 포털에 AI 기능을 추가하는 과제, 특히 성과 지표가 'AI 기능 탑재 여부'나 호출 수로 잡힌 과제. R24에 따라 AI 런타임이 전혀 없는 순수 행정정보시스템도 이 태그(AI 무관)로 표기한다.

맞서는 힘(긴장)

  • 빠른 도입 실적 vs 업무 흐름 재설계 비용
  • 기존 시스템 무변경(안정성) vs 산출물 단위의 역할 분담
  • 'AI 탑재' 홍보 효과 vs 실제 처리시간·수정률 개선

해법

먼저 가치 흐름 규칙(R1)으로 사람 또는 국민이 최종으로 받는 핵심 산출물을 정하고, 그 산출물을 AI가 어떤 모양으로 분담할지 B 업무 컴포넌트를 하나 고른다(초안→사람 확정이면 B1, 근거 접지 답변이면 B3, 서류 추출이면 B4). 사람이 확정하는 지점은 C1 검토 큐로, 이용자가 고쳐 확정하는 면은 F2 편집 가능한 출력으로 명시한다. 흐름이 바뀌었는지는 C4 감사 로그·지표의 처리시간·수정률로 잰다. AI 런타임이 전혀 없는 행정정보시스템이라면 AI로 포장하지 말고 R24대로 B0·service_type 0·platform 공란·X1(AI 무관)으로 정직하게 분류한다.

이럴 때 쓴다

  • AI 기능이 추가됐다는 서술은 있으나 처리 단계 수·결재선·담당자 역할이 바뀌었다는 서술이 없다
  • 성과 지표가 AI 호출 수·이용 만족도뿐이고 처리시간·수정률 같은 산출물 지표가 없다
  • 챗봇이 기관 업무 데이터·시스템과 연결되지 않은 범용 대화에 머문다
  • AI 런타임이 전혀 없는 행정정보시스템이 AX 과제로 분류되어 있다(R24)

이럴 때는 쓰지 않는다

  • B1 코파일럿처럼 AI가 초안을 만들고 사람이 확정하는 역할 분담이 실제로 서술된 경우
  • B8 레거시 오버레이처럼 표준 시스템 위에 얹었지만 업무 산출물을 AI가 만들어 내는 경우
  • B0 결정적 도구가 반복 취합 업무를 실제로 줄이고 AI로 포장하지 않은 경우(Ready 부품으로 정직하게 분류된 경우)

얻는 것

  • 기존 시스템을 건드리지 않아 도입이 빠르고 장애 위험이 낮다
  • 'AI 탑재' 실적을 즉시 보고할 수 있다

점검표

  • AI 도입 전후 처리 단계·담당자 역할의 차이를 한 장으로 보여 줄 수 있는가
  • AI가 만드는 산출물과 사람이 확정하는 지점이 명시되어 있는가
  • 처리시간·수정률 같은 산출물 지표가 도입 전 기준선과 함께 있는가
  • AI 런타임이 없는데 AI 과제로 보고하고 있지 않은가

구조 — 참여 부품

  • 덧붙인 AI 기능 — 요약·대화 버튼. 업무 산출물 생산에 역할이 없음
  • B1 코파일럿 — 교정 후 초안→사람 확정으로 산출물 역할을 나누는 대체 부품
  • C1 검토 큐 — 교정 후 사람이 확정하는 지점을 명시
  • C4 감사 로그·지표 — 흐름이 실제로 바뀌었는지 처리시간·수정률로 측정

변형

  • 요약 버튼형: 기존 화면에 '요약' 버튼만 추가하고 결재·처리 단계는 그대로
  • 범용 챗봇 부착형: 업무 데이터와 연결되지 않은 범용 대화창을 포털에 부착
  • AI 무관 행정시스템(R24): AI 런타임이 전혀 없는 순수 행정정보시스템(예: 교육·인증 학습관리시스템). B0·service_type 0·platform 공란과 함께 X1(AI 무관)로 표기

관련 부품

B1 대체 — 초안→사람 확정으로 산출물 역할을 나누는 교정 목표 · C1 교정에 끼울 자리 — 사람이 확정하는 지점 · B0 정직한 분류 — AI 런타임이 없으면 B0 Ready 부품으로(R24) · C4 기록처 — 흐름 변화의 증거(처리시간·수정률) · X8 이웃 안티패턴 — 개수·탑재를 성과로 세는 같은 뿌리
