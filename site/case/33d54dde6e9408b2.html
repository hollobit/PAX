판정 근거

G마켓·11번가·SSG닷컴·아이스크림몰·쿠팡 장바구니의 상품명·수량·금액·배송비를 읽어 K-에듀파인 품의등록 화면 품목내역에 채워 주는 크롬 확장이다. API가 닫힌 표준 시스템 화면 위에 덧입히는 구조라 B8(레거시 오버레이)이며 AI는 쓰지 않는다. 화면 필드 입력까지만 하고 저장·결재 요청은 담당자가 결과를 확인한 뒤 직접 하도록 남겨 두어 쓰기 범위 경계(C8)와 자기확인형 HITL(C1)이 구현돼 있으나 운영 실측이 없어 implemented. 운영 화면에 값을 입력하므로 PAX p축대로 P2(잠정) — C8은 implemented뿐이라 P2 경고는 남긴다. 장바구니 페이지는 외부 작성이지만 읽는 주체가 결정적 파서(AI 아님)라 untrusted_inputs는 비움. 크롬 웹스토어 URL은 리다이렉트 초과로 URL 미확인.

구현 가이드

주 패턴 B8 레거시 오버레이을 구현할 때

구현 단계

  1. 대상 화면과 반복 조작을 정하고, 확장이 읽을 DOM 요소와 파일을 목록으로 적는다.
  2. 권한을 P0~P1에 묶고, 쓰기 조작이 필요하면 C3 되돌림과 F6 확인을 먼저 설계한다.
  3. 요약을 붙이면 로컬 모델(A2.2)로 처리해 문서가 PC 밖으로 나가지 않게 하고 C5를 둔다.
  4. 화면 텍스트를 신뢰 불가 입력으로 보고 S3 구역 분리를 적용한다.
  5. 시스템 개편 시 점검 절차와, 정식 API·MCP가 열리면 걷어낼 조건을 문서로 남긴다.

점검표

  • 권한이 읽기·산출물 생성(P0~P1)에 묶여 있는가
  • 문서가 PC 밖으로 나가지 않는가
  • 시스템 개편 시 점검 절차가 있는가
  • 정식 연계가 열리면 걷어낼 조건이 적혀 있는가

환경 조건

E1 행정망이 필수 조건이다. E2는 로컬 오픈웨이트(온나라 sAIde: Ollama). E4는 P0~P1에 묶어야 하며, P2 이상이면 C3 되돌림이 필요하나 DOM 조작은 원자성이 없다. 신뢰 불가 입력 + P2 이상이면 DOM 텍스트를 전부 신뢰 불가로 보고 S4 행동 선택기가 필요하다(§5 매트릭스).

주의할 점

  • DOM 의존으로 시스템 개편에 취약(전이 차단: 레거시 미연동)
  • DOM 조작은 원자성이 없어 쓰기 시 되돌림이 어려움
  • 화면 텍스트를 통한 인젝션 위험
  • 개인 도구가 담당자와 함께 사라질 위험(X9)

기본 배선 예

B8 → A2.2 (로컬 요약) → A10 → D8.2 · A8 (정식 MCP가 열리면 B8 대체)

  • A7 자체 제작 환경 외부 용역 없이 기관 인력이 저작도구·AI 코딩 에이전트로 도구를 직접 만들고 고치는 제작 환경이다.

B8 레거시 오버레이 업무 컴포넌트

API가 닫힌 표준 업무 시스템(온나라·나이스·K-에듀파인·업무포털) 화면 위에 브라우저 확장·사이드패널로 검색·요약 기능을 덧입힌다. 시스템 자체는 고치지 않는다.

PAX 사례 13건이 이 부품을 쓴다

맥락

행정망의 표준 업무 시스템을 쓰는 담당자가 개인·부서 단위로 만든 도구가 여기에 든다. 문서가 PC 밖으로 나가면 안 되므로 로컬 모델과 짝을 이룬다. PAX 557건에서 13건이 확인됐다.

맞서는 힘(긴장)

  • 즉시 도입 vs 시스템 개편에 따른 취약성(DOM 의존)
  • 사용자 세션 공유의 편의 vs 권한 경계
  • 요약 기능 추가 vs 문서 외부 유출 금지

해법

브라우저 확장·사이드패널이 담당자 로그인 세션 안에서 화면 DOM과 다운로드 파일을 읽어 통합 검색, 일괄 다운로드, 원클릭 이동을 제공한다. 요약·분석이 필요하면 로컬 오픈웨이트 모델(A2.2)로 처리해 문서가 PC 밖으로 나가지 않게 한다. 권한은 P0~P1(읽기·산출물)에 묶고, 쓰기 조작이 있으면 C3 되돌림을 둔다. 화면 텍스트는 모두 신뢰 불가 입력으로 보고 S3·S4를 적용하며, 표준 시스템에 정식 API·MCP(A8)가 열리면 이 부품을 걷어낸다.

이럴 때 쓴다

  • API가 닫힌 표준 시스템 위에서 반복 조회·다운로드가 병목일 때
  • 행정망에서 문서를 PC 밖으로 내보낼 수 없을 때
  • 정식 연계가 열리기 전 과도기 도구가 필요할 때

이럴 때는 쓰지 않는다

  • 표준 시스템에 정식 API·MCP가 이미 있을 때(A8로 연결)
  • 화면 조작으로 시스템에 쓰기를 해야 하는데 되돌림을 보장할 수 없을 때
  • 독립 화면에서 파일을 처리하는 도구일 때(B0)

얻는 것

  • 표준 시스템을 고치지 않고 즉시 도입
  • 행정망에서 로컬 완결 가능
  • 현장 반복 조작 제거

점검표

  • 권한이 읽기·산출물 생성(P0~P1)에 묶여 있는가
  • 문서가 PC 밖으로 나가지 않는가
  • 시스템 개편 시 점검 절차가 있는가
  • 정식 연계가 열리면 걷어낼 조건이 적혀 있는가

구조 — 참여 부품

  • 브라우저 확장·사이드패널 — 화면 위에 기능을 덧입힘
  • A2.2 주권형 온프레미스 모델 — PC 안에서 요약·분석
  • A10 문서 형식 어댑터 — 첨부 파싱
  • C5 가드레일 필터 — 민감정보 처리
  • 표준 업무 시스템 — 손대지 않는 원 시스템

변형

  • 검색·이동형: AI 없이 통합 검색·원클릭 이동·일괄 다운로드를 제공한다(Ready)
  • 로컬 모델 요약형: 사이드패널에 로컬 모델 요약·분석을 붙인다(Enabled)

참조 구현 예

  • PAX 온나라 sAIde — 사이드패널 + 로컬 Ollama 요약 + 첨부 일괄 다운로드(카드·§9)
  • PAX 온나라 문서 검색 서포터 — 문서등록대장 통합 검색(카드 참조 구현)
  • PAX 업무포털 원클릭 이동 — 카드 참조 구현
  • PAX 8c5458af8f13435d — 웹한글 기안기 위 크롬 확장 + 100% 로컬 LLM(§13)
  • PAX 6e89aaf95f6ffbd9 — AI 없이 온나라 부서 통합 검색 — AI 없이도 B8 성립(§13)

관련 부품

C1 검토 큐 운영 컴포넌트

AI 산출물이 다음 단계로 넘어가기 전에 사람이 맞고 틀림을 확인·수정·확정하는 대기열을 두어, 오류가 업무 결과로 흘러가지 않게 한다.

PAX 사례 46건이 이 부품을 쓴다

맥락

AI 산출물이 공문·처분·대민 안내·기록으로 이어지는 모든 B 부품(B1 코파일럿, B4 인식 파이프라인, B2 예측기, B7 콘텐츠 생성기 등). 이용자 본인이 최종 확정자인 자기서비스형 도구도 포함한다(R16).

맞서는 힘(긴장)

  • 정확성·책임성 vs 처리 속도(전건 검토는 자동화 이득을 깎는다)
  • 검토자의 숙련 vs 자동화 편향(AI 결과를 그대로 승인하는 경향)
  • 전건 검토의 안전 vs 위험도별 분기(C2)로 가야 하는 효율 압력

해법

AI 산출물에 신뢰도·근거를 붙여 검토 대기열에 올리고, 검토자가 승인·수정·반려 중 하나를 고르게 한다. 수정·반려 내역은 C4 감사 로그에 남겨 수정률을 집계하고 C6 환류의 입력으로 쓴다. 검토 화면은 원문 위치·근거를 함께 보여 줘 확인 비용을 줄인다. 전건 검토로 시작하되, 수정률 실측이 쌓이면 C2 위험도 라우터로 저위험 건을 자동 종결하는 단계로 옮긴다.

이럴 때 쓴다

  • AI 산출물이 공문·처분·대민 안내로 그대로 이어질 때
  • E4가 P1 이상이고 되돌리는 데 사람 시간이 많이 드는 조치가 있을 때
  • 서비스 유형 ② 접수·심사, ④ 기안 코파일럿, ⑥ 콘텐츠 제작, ⑦ 대조·점검, ⑩ 위험 예측, ⑪ 추천·매칭, ⑫ 개발 코파일럿처럼 C1이 필수인 유형

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 런타임 AI 산출물이 없을 때
  • 쉽게 되돌릴 수 있고 저위험인 조치를 이미 C2로 자동 종결하도록 실측 근거를 갖춘 구간(전건 검토를 영원히 남기지 않는다)

얻는 것

  • 오류가 업무 결과로 나가기 전에 차단
  • 책임 소재가 명확해짐
  • 수정 내역이 C4 지표와 C6 환류의 원천 데이터가 됨

점검표

  • AI 산출물이 확정 전 상태로 머무는 지점이 명시되어 있는가
  • 검토자와 승인·수정·반려 선택지가 정해져 있는가
  • 검토 결정과 수정 내역이 로그로 남는가
  • 실증 기간의 검토·수정 건수가 기록되어 있는가
  • 전건 검토에서 분기로 옮길 조건이 정해져 있는가

구조 — 참여 부품

  • 검토 대기열 — AI 산출물을 확정 전 상태로 보관하고 검토자에게 배정
  • 검토자(담당자 또는 이용자 본인) — 승인·수정·반려를 결정하는 최종 책임자
  • F2 편집 가능한 출력 — 검토자가 산출물을 직접 고치는 화면
  • C4 감사 로그·지표 — 검토 결정과 수정 내역을 적재해 수정률로 집계

변형

  • 전건 검토형: 모든 AI 산출물을 담당자가 확인·확정
  • 예외 검수형: 정상 건은 일괄 승인하고 저신뢰 항목만 개별 검수하는 검수 UI
  • 파이프라인 내장 관문형: 멀티에이전트·다단계 파이프라인의 각 관문에 승인·보완·재작성 선택지를 둠
  • 자기서비스형: 이용자 본인이 최종 확정자인 HITL. 실제 운영 중이면 C1 present(R16)
  • 심의 게이트: 팩트체크·법무·윤리처럼 제3자 전문가가 수행하는 승인 게이트

참조 구현 예

  • PAX 9dc1a7081bc869b1 — 광진구 — 담당자·팀장 최종 판단 책임 등 4대 관리 원칙 명문화

관련 부품

C2 다음 단계 — 전건 검토에서 위험도 분기로 승급 · C1.2 변형 — 제3자 전문가 심의 게이트 · F2 이용자 쪽 대응 — 검토자가 직접 고치는 화면 · F6 이용자 쪽 대응 — 에이전트 행동 실행 전 확인 · C4 기록처 — 검토 결정·수정 내역 · C6 후속 — 수정 내역이 환류의 입력

C8 권한 경계·킬스위치 운영 컴포넌트

AI 부품이 할 수 있는 일의 상한을 P0~P4로 못 박고, 도구별 실행 승인·읽기/쓰기 분리·속도 제한·즉시 중단 스위치를 제공한다.

PAX 사례 22건이 이 부품을 쓴다

맥락

도구를 호출하거나 시스템에 쓰는 B6 오케스트레이터, A8 MCP 서버·호스트, B8 레거시 오버레이, 처분 보조(P3) 서비스. 유형 ⑤b 데이터 에이전트, ⑨ 인수인계(접근 범위).

맞서는 힘(긴장)

  • 자동화 범위 vs 통제
  • 승인 절차의 안전 vs 이용 마찰
  • 도구 설명의 편의 vs 실제 권한과의 일치 검증 비용

해법

부품별 허용 권한 범위(P0 읽기 전용 ~ P4 자율 처분)를 정하고, 도구 목록마다 읽기/쓰기를 분리한다. 위험도가 높은 도구는 실행 전 사람 승인(C2·F6)을 받게 하고, 호출 상한(속도 제한)을 둔다. 전역 킬스위치로 즉시 중단할 수 있게 하고, 승인·실패·중단 이력을 C4에 남긴다. MCP 도구는 설명과 실제 권한이 일치하는지 A8 6축 검증으로 확인한다.

이럴 때 쓴다

  • E4 P2 이상(필수, First 관문)
  • E3 MCP·CLI 환경에서 에이전트가 도구를 호출할 때
  • B6 오케스트레이터에 상용 API를 쓰는 경우(A2 + C7 + C8 도구별 승인)
  • 유형 ⑤b-host, ⑨ 인수인계(접근 범위)

이럴 때는 쓰지 않는다

  • 도구 호출·시스템 쓰기가 없는 서술 전용 코파일럿(P1)
  • B0 결정적 도구로 AI가 행동을 고르지 않을 때

얻는 것

  • 되돌릴 수 없는 조치 방지
  • 도구 설명과 실제 권한의 불일치(X7) 예방
  • 감사 가능한 행동 기록

점검표

  • AI가 쓸 수 있는 시스템 목록을 답할 수 있는가
  • 도구별 읽기/쓰기 구분과 위험도가 있는가
  • 고위험 도구에 실행 승인이 걸려 있는가
  • 킬스위치가 있고 누가 누를 수 있는지 정해져 있는가
  • 도구 설명과 실제 권한이 일치하는가

구조 — 참여 부품

  • 권한 정책 — 부품·도구별 허용 범위(P0~P4)와 읽기/쓰기 구분

D8.9 변환·서식 서비스 블록

HWP·HWPX·PDF·DOCX·엑셀 사이를 오가고 양식을 만드는 내부 운영 블록이다. A10 문서 어댑터가 서비스로 독립한 형태다.

PAX 사례 80건이 이 부품을 쓴다

맥락

문서 형식 변환과 양식 생성 업무. §7.3 유형 ⑧ 취합·변환 자동화(D8.5 · D8.9, P1). PAX 80건(주 부품 B0 80%, B1 12%).

맞서는 힘(긴장)

  • 변환 충실도 vs 형식별 특이 구조(표·수식·첨자)
  • 설치형·오프라인 편의 vs 배포·갱신 관리
  • 개인 도구의 민첩성 vs 인사이동 시 소멸(X9)
  • 파일 자동 변환 vs 파일 속 매크로·지시 위협

해법

A10 어댑터를 결정적 변환기(B0)로 만들어 HWP·HWPX·PDF·DOCX·엑셀 사이를 오가게 한다. 스캔 문서는 B4 OCR로 텍스트를 얻는다. 변환은 원본을 보존하고 새 파일을 만들며(C3 원복·F8 되돌리기), 파일은 S11 검사와 S9 격리 실행을 거친다. 규정·양식을 MCP로 노출하면 다른 AI 도구가 기관 서식을 쓸 수 있는 공통 부품이 된다(A8). 개인 제작 도구는 라이선스·저장소를 명시한다(A7).

이럴 때 쓴다

  • 공공 문서 형식 간 변환이 반복될 때
  • AI 도구가 HWP·HWPX를 읽고 쓰지 못해 막힐 때
  • 양식을 반복해 새로 만들 때

이럴 때는 쓰지 않는다

  • 여러 부서 파일을 모아 합치면 D8.5(우선순위 높음)
  • 변환 뒤 첫 판 작성이 목적이면 D8.3
  • 변환한 문서를 찾는 것이 핵심이면 D8.1 검토

얻는 것

  • AI 도구와 공공 문서 형식의 연결
  • 형식 변환 시간 절감
  • 재사용 부품의 최대 공급원

점검표

  • 변환 결과의 표·서식이 원본과 같은지 확인했는가
  • 원본이 보존되는가
  • 입력 파일 속 매크로가 실행되지 않는가
  • 라이선스·저장소가 명시되어 있는가

구조 — 참여 부품

  • 담당자 — 변환·양식 결과를 확인

  • B4 인식 파이프라인 — 스캔 문서 OCR
  • A8 MCP 서버·호스트 — 규정·양식을 도구로 노출(선택)

변형

  • 형식 변환기: HWP·HWPX·PDF·DOCX·엑셀 간 변환(Kordoc, 쉽다한글).
  • 오프라인 문서 검색기: 본문 텍스트 추출로 문서를 찾게 함(Anything(Docufinder)).

A10 문서 형식 어댑터 공통 서비스

HWP·HWPX·엑셀·한셀·PDF 같은 한국 공공 문서 형식을 AI 부품이 읽고(구조화) 쓰게(서식 생성) 하는 변환 계층이다.

PAX 사례 136건이 이 부품을 쓴다

맥락

문서를 입력으로 받거나 기안·보고서·취합본을 산출하는 과제라면 거의 다 쓴다. 유형 2·4·8에서는 필수 기반이고 유형 6·7에서도 쓰인다. E1 로컬 PC 조건에서 도는 경우가 많다.

맞서는 힘(긴장)

  • 형식 충실도(표·각주·조항 구조 보존) vs 파서 구현 비용
  • 로컬 처리(무반출) vs 클라우드 변환 도구의 편의
  • 기관별 서식 다양성 vs 공통 어댑터 재사용

해법

입력 쪽에서는 HWPX 압축 구조·PDF에서 조·항·호·별표 계층과 표를 보존해 구조화 텍스트·표로 바꾸고, 머리말·각주 같은 잡음을 걷어 조항 단위로 정규화한다. 출력 쪽에서는 스킬(A9)의 출력 서식을 받아 HWPX·XLSX 기안 서식을 역방향으로 생성한다. 민감 문서는 PC 밖으로 보내지 않도록 로컬에서 변환하고, 파서를 라이브러리·CLI·MCP로 함께 제공하면 다른 부품과 기관이 그대로 쓴다. 형식 변환 정확도는 C9 판정 체계로 잰다.

이럴 때 쓴다

  • 입력이 HWP·HWPX·엑셀·PDF 공공 문서일 때
  • 산출물을 기안·보고 서식으로 내보내야 할 때
  • 유형 2·4·8 조립

이럴 때는 쓰지 않는다

  • 스캔 이미지·음성처럼 인식이 필요한 입력은 B4 인식 파이프라인(OCR·STT)
  • 입출력이 이미 정형 데이터·API인 경우

얻는 것

  • 공공 문서를 AI 입력·출력으로 연결
  • 기관 간 재사용 가능한 공통 부품
  • 로컬 처리로 무반출

점검표

  • 표·조항 계층이 변환 후에도 보존되는가
  • 출력이 기관 기안 서식 그대로 열리는가
  • 민감 문서가 변환 과정에서 PC 밖으로 나가지 않는가
  • 변환 정확도 판정 기록이 있는가

구조 — 참여 부품

  • 입력 파서 — 조·항·호·표 구조를 보존해 구조화
  • 서식 생성기 — 구조화 결과를 HWPX·엑셀 서식으로 출력
  • A9 업무 규범 스킬 — 출력 서식 규범 제공
  • B3 지식 접지 상담 — 구조화된 규정을 색인해 검색

변형

  • 규정 구조 파서: HWP/HWPX·PDF 규정을 조항 단위로 정규화한다.
  • 엑셀·한셀 취합: 폐쇄망에서 엑셀·한셀 파일을 취합한다(GatherFlow).
  • 서식 출력: HWPX 직무기술서·보도자료 등 공공 서식으로 역방향 생성한다(NCS JD, ReleasePick 입력).
  • 완결형 문서 엔진: HWP/HWPX 파싱·조판·렌더링·편집·PDF 출력을 자체 구현하고 MCP·CLI로 제공한다(PAX e18d5e018e0cd10d).
  • AI 친화 병행 등록: 기관이 발간자료를 마크다운으로 함께 등록하도록 표준화한다(PAX 17329009668eb397).

참조 구현 예

  • PAX GatherFlow — 엑셀·한셀 취합(폐쇄망)(§6 A10 카드)
  • PAX 7ad16f34cfb6cca7 — HWP·HWPX·PDF에서 신구대비표 초안을 로컬 생성(§13 A10)
  • PAX e18d5e018e0cd10d — HWP/HWPX 파싱·조판·렌더링·편집·PDF 출력 + MCP·CLI(§13 A10)

A7 자체 제작 환경 공통 서비스

외부 용역 없이 기관 인력이 저작도구·AI 코딩 에이전트로 도구를 직접 만들고 고치는 제작 환경이다.

PAX 사례 317건이 이 부품을 쓴다

맥락

업무 담당자가 AI 코딩 도구·저작도구·오픈소스로 직접 만드는 과제에 쓴다. 유형 8(취합·변환 자동화)에서는 필수 기반이다. PAX 557건에서 A7이 붙고 BYO 모델을 쓰는 사례는 29건이다.

맞서는 힘(긴장)

  • 제작 속도·현장 적합성 vs 유지보수 연속성
  • 개인 역량 의존 vs 조직 인수인계
  • 무예산 제작 vs 보안 검토·기관 공식화 절차

해법

기관 인력이 AI 코딩 에이전트·저작도구·오픈소스로 직접 만들되, 처음부터 전이를 전제로 한다. 설정·데이터(연락처·업무분장 등)는 코드 밖 파일로 빼 비개발자도 고치게 하고, 작업 지시서 자체를 코딩 에이전트가 수행할 프롬프트로 설계해 제작 절차를 남긴다. MIT·Apache 등 라이선스를 명시하고 공공 깃랩(A3)이나 혁신24 자료실에 등재해 담당자가 바뀌어도 이어지게 한다. 실사용 건수로 성과를 재 기관 공식으로 올린다.

이럴 때 쓴다

  • 반복 업무를 줄이는 소규모 도구를 빠르게 만들 때
  • 용역 없이 작은 수정을 계속해야 할 때
  • 유형 8 취합·변환 자동화

이럴 때는 쓰지 않는다

  • P2 이상 시스템 쓰기·처분이 걸려 보안 검토·통제 부품이 먼저 필요한데 이를 갖출 수 없을 때
  • 라이선스·저장소·인수인계를 정할 수 없어 전이가 불가능할 때(X9 위험)

얻는 것

  • 제작 속도와 현장 적합성
  • 내부 유지보수 역량 축적
  • 무예산·소예산 제작

점검표

  • 라이선스가 명시되어 있는가
  • 저장소가 개인 PC가 아닌 공유 위치에 있는가
  • 담당자가 바뀌어도 고칠 수 있는 문서·설정 분리가 있는가
  • 실사용 지표가 있는가

구조 — 참여 부품

  • 업무 담당자 — 요구를 알고 직접 만드는 제작자
  • AI 코딩 에이전트·저작도구 — 코드·화면·워크플로 생성
  • A3 공공 깃랩·자료실 — 등재처 — 담당자 이동 후에도 이어지게
  • A9 업무 규범 스킬 — 제작 규범·지시서를 재사용 가능한 형태로

변형

  • 비개발자 바이브코딩: 교육 후 비개발 직원이 AI 코딩으로 웹앱을 만들고 실사용 지표까지 잰다.
  • 용역 탈피 단계형: 1단계는 전문기업과, 2단계는 직원이 도구를 대여해 라벨링·학습·개발을 직접 한다.
  • 오픈소스 조립형: n8n·FastAPI·Qdrant·LM Studio 등 오픈소스로 워크플로를 직접 조립하고 설정을 공유한다.
  • 사람+에이전트 작업 단위형: 작업 지시서를 코딩 에이전트 입력 프롬프트로 설계해 '사람 1인 + 에이전트 1세션' 단위로 일한다.

참조 구현 예

X9 담당자와 함께 사라지는 도구 안티패턴

개인이 만든 도구가 부서에 퍼졌지만 라이선스·저장소·인수인계가 없어, 만든 사람의 인사이동과 함께 멈추는 함정이다.

맥락

A7 자체 제작 환경으로 태깅된 도구(PAX 557건 중 317건, 57%), 특히 개인 사용에서 부서 공유로 막 퍼지기 시작한 바이브코딩 도구.

맞서는 힘(긴장)

  • 개인의 빠른 제작 vs 조직의 유지보수 책임
  • 비공식 공유의 편의 vs 라이선스·저장소 절차
  • 현장 맞춤 vs 다른 담당자가 이해할 수 있는 구조

해법

도구가 부서에 퍼지기 시작하면 A7 산출물에 MIT·Apache 등 라이선스를 명시하고, 코드를 개인 PC가 아니라 A3 공공 깃랩 같은 공용 저장소에 등재한다. 업무 규범·프롬프트는 A9 업무 규범 스킬로 패키징해 다른 담당자가 그대로 쓸 수 있게 하고, 설치·설정·데이터 경로를 담은 인수인계 문서를 둔다. 도구를 참조 구현 레지스트리(§13)에 올려 소유를 개인에서 조직으로 옮긴다. transition.blocker에 '담당자 이동'이 적힌 과제는 이 조치를 먼저 한다.

이럴 때 쓴다

  • 개인이 만든 도구를 부서원 여러 명이 쓰는데 라이선스 표기가 없다
  • 원본 코드가 개인 PC·개인 계정에만 있다
  • 인수인계 문서·설치 절차가 없다
  • transition.blocker가 '담당자 이동'이다

이럴 때는 쓰지 않는다

  • 개인만 쓰는 도구로 부서에 퍼지지 않은 경우(개인 사용 단계는 정상)
  • A7로 만들었지만 라이선스 명시·공용 저장소 등재·인수인계가 갖춰진 경우
  • 기관 정보화 부서가 넘겨받아 운영 중인 경우

얻는 것

  • 현장 담당자가 필요한 도구를 빠르게 만든다
  • 공식 절차 없이 바로 퍼진다

점검표

  • 라이선스가 명시되어 있는가
  • 원본이 공용 저장소에 있는가
  • 만든 사람 없이 후임이 설치·실행할 수 있는 문서가 있는가
  • 개인 구독·개인 키에 의존하지 않는가

구조 — 참여 부품

  • A7 자체 제작 환경 — 도구가 태어난 곳. 라이선스 명시가 전이 조건
  • A3 공공 API 제공자(공공 깃랩) — 개인 저장소를 대체하는 공용 등재처
  • A9 업무 규범 스킬 — 암묵적 업무 규범을 패키지로 남김
  • 후임 담당자 — 인수인계 문서로 도구를 이어받는 사람

변형

  • 라이선스 미명시: 코드는 공개했지만 라이선스가 없어 타 기관이 가져다 쓸 수 없음
  • 개인 저장소형: 개인 PC·개인 계정에만 원본이 있음
  • 개인 구독 의존형: 개인 AI 구독·API 키로 돌아가 담당자가 떠나면 호출이 끊김
