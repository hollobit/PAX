구현 단계

  1. 업무를 도구 목록으로 나누고 도구마다 읽기/쓰기, 되돌리기 비용을 적어 C8 권한표를 먼저 만든다.
  2. 단일 에이전트 + ReAct 루프(B′7)로 시작해 C9 평가 세트로 재고, 하위 작업이 분리될 때만 B′4·B′3으로 승급한다.
  3. 신뢰 불가 입력(외부 문서·API 응답)을 읽는지 확인하고, P2 이상이면 S5 계획 고정 또는 S6 격리를 설계한다.
  4. 단계 상태·되돌림(C3), 호출 추적(C4), 되돌리기 어려운 조치 앞 확인(F6)을 붙인다.
  5. 모델 장애 대비 C7과 킬스위치를 시험하고 결정적 재생(S10) 기록을 남긴다.

점검표

  • 도구별 읽기/쓰기 권한과 실행 승인이 명시되어 있는가
  • 모든 도구 호출이 추적되는가
  • 도구 출력이 새 행동을 촉발하지 못하게 막는 구조가 있는가

이 조합에서 카탈로그가 함께 갖추라고 권하는 부품 가운데 아직 확인되지 않은 것이다.

  • A2 모델 서빙 계층 업무 부품이 모델을 직접 부르지 않고 서빙 계층을 거쳐 부르게 해 모델을 바꿔 끼우고 라우팅·캐싱·버전 고정·폴백을 한 자리에서 다룬다. A2.0~A2.6을 묶는 부모 항목이다.
  • C5 가드레일 필터 개인정보·환각·편향·형식 오류가 프롬프트나 산출물에 들어가지 못하게 시스템이 경계에서 걸러낸다. 비식별 전처리, 출처 검증, 구조적 출력 제약이 대표 변형이다.
  • C9 평가 세트·회귀시험 배포 전에 업무 맥락의 질문·정답·채점 기준을 세트로 만들어, 프롬프트·모델·설정의 모든 변경을 같은 자로 재고 회귀를 잡는다.
  • C7 폴백 스위치 모델·API·도구가 멈추거나 품질이 떨어질 때 대체 모델·규칙 기반 축소·수동 처리로 경로를 바꿔 서비스가 끊기지 않게 한다.
  • F7 한계·신뢰도 안내 AI가 무엇을 못 하는지, 얼마나 확신하는지, 공식 판단이 아님을 이용자가 볼 수 있는 곳에 적어 과신을 막는다.

피해야 할 안티패턴

  • X9 담당자와 함께 사라지는 도구 (이 사례에서 확인) 개인이 만든 도구가 부서에 퍼졌지만 라이선스·저장소·인수인계가 없어, 만든 사람의 인사이동과 함께 멈추는 함정이다. 대처: 도구가 부서에 퍼지기 시작하면 A7 산출물에 MIT·Apache 등 라이선스를 명시하고, 코드를 개인 PC가 아니라 A3 공공 깃랩 같은 공용 저장소에 등재한다. 업무 규범·프롬프트는 A9 업무 규범 스킬로 패키징해 다른 담당자가 그대로 쓸 수 있게 하고, 설치·설정·데이터 경로를 담은 인수인계 문서를 둔다. 도구를 참조 구현 레지스트리(§13)에 올려 소유를 개인에서 조직으로 옮긴다. transition.blocker에 '담당자 이동'이 적힌 과제는 이 조치를 먼저 한다.
  • X11 처음부터 멀티에이전트 하위 작업이 분리되지 않는데 에이전트를 여럿 두어 조정 비용만 늘리는 함정이다. 단일 에이전트로 되돌리면 더 잘 되는 경우가 많다. 대처: B′ 원형 선택 규칙대로 단일 에이전트(B′1 순차, B′7 ReAct 도구 루프)에서 시작한다. 하위 작업이 진짜로 분리되거나, 병렬이 지연을 의미 있게 줄이거나, 컨텍스트 창이 부족할 때만 B′3 병렬·B′4 계층 분해로 승급한다. 승급 판단은 C9 평가 세트로 단일 구성과 비교해 내린다. 에이전트끼리 충돌·중복이 관측되면 B′4 감독자 계층이나 B′2 라우터로 정리하거나 단일 에이전트로 후퇴한다. B6 태그는 R2 요건(복수 LLM 역할 + 도구 호출 루프 + AI가 계획·도구를 선택)을 만족할 때만 붙인다.
  • X13 도구 출력이 지시가 되는 에이전트 검색 결과·첨부·API 응답을 읽은 모델이 그 안의 문장을 새 명령으로 받아 도구를 부르는 구조를, 탐지 필터 하나로 지키려는 함정이다. 대처: 과제의 AI가 읽는 입력 중 기관 밖에서 작성된 것을 untrusted_inputs로 나열하고, §4.2 신뢰 불가 입력 규칙대로 S4 행동 선택기(미리 정한 행동 중 선택만, 결과가 LLM으로 돌아가지 않음), S5 계획 후 실행(외부 데이터를 읽기 전에 도구 호출 계획을 고정), S6 격리 LLM(도구 있는 LLM은 외부 데이터를 읽지 않고, 읽는 LLM은 도구가 없음) 중 하나를 갖춘다. S3 컨텍스트 방화벽과 S8 독립 검증기는 보조로 붙이되 S8만으로는 규칙을 충족하지 못한다. C8 승인 게이트도 신뢰 불가 입력 규칙의 대체 통제로 인정되지 않는다(R6). 그 전 단계에서는 E4를 P0~P1 읽기·산출물 범위에 묶어 두는 것이 곧 보안이다.
  • X14 재생할 수 없는 사고 잘못된 처분이 나갔는데 그때의 프롬프트·검색·도구 호출 순서를 아무도 복원하지 못하는 함정이다. 지표는 있는데 기록이 없다. 대처: S10 결정적 재생으로 프롬프트·검색 결과·도구 호출·정책 결정·실행 흔적을 시각·주체·컨텍스트 해시와 함께 순서대로 기록하고, 필요하면 변조 방지 서명을 붙인다. 기록은 S1 단일 진입점에서 시작해 C4와 같은 파이프라인으로 적재하되, C4가 '얼마나'를 세고 S10은 '정확히 무엇이 일어났나'를 되돌리게 역할을 나눈다. 모델·프롬프트·설정 조합을 C9로 버전 고정해 그 시점의 구성을 재현할 수 있게 하고, 재생 기록을 C3 롤백·이의제기의 근거로 쓴다. 개인정보는 C5 비식별과 E5 등급에 맞춘 보관 기간으로 다룬다.
  • X7 도구 설명 ≠ 실제 권한 MCP 도구 설명은 '조회'인데 코드는 쓰기·실행 권한을 가져, 설명만 믿고 도구를 부르는 에이전트가 의도하지 않은 변경을 일으키는 함정이다. 대처: A8의 각 도구에 실제 권한 수준(P0~P4)을 설명과 함께 명시하고, C8 권한 경계로 읽기 전용 도구와 쓰기 도구를 서로 다른 서버·인증으로 분리한다. 쓰기·실행 도구는 도구별 실행 승인과 호출 상한, 킬스위치를 둔다. 반입하는 MCP 서버는 S11 인제스천·공급망 검증에서 PAX 6축(권한 표면·비밀·공급망·위생·인젝션·데이터 흐름)을 통과해야 활성화한다. 사람에게는 F6 에이전트 행동 검토·확인으로 실행 전 무엇을 할지 보여 주고, 승인·실패는 C4에 남긴다.
  • X8 MCP 서버 개수 세기 MCP 서버를 몇 개 만들었는지가 성과가 되고, 실제 업무에서 호출되는지·흐름이 바뀌었는지는 아무도 묻지 않는 함정이다. 대처: 서버마다 그것을 호출하는 B 업무 컴포넌트와 업무 산출물을 연결해 '어느 업무의 어떤 산출물에 쓰이는가'를 적는다. C4 감사 로그·지표로 호출 수·호출 주체·업무 건을 집계하고, transition.stage와 파급력 척도(M1~M5)로 전환 경로를 추적한다(PAX: 도구 수보다 전환 경로를 추적). PAX 사례 15건이 이 부품을 쓴다

맥락

여러 시스템·도구(A8 MCP·API·문서)를 오가는 다단계 업무, 데이터 조회·분석 에이전트(유형 5b), 망분리 환경의 로컬 MCP 호스트에 쓴다. 하위 작업이 실제로 분리되거나 AI가 도구를 골라야 할 때만 해당한다.

맞서는 힘(긴장)

  • 자율성 vs 권한 통제(P2 이상에서 C8 필수)
  • 멀티에이전트의 분업 vs 조정 비용·충돌(X11)
  • 도구 출력 활용 vs 도구 출력 속 지시가 명령이 되는 위험(X13)
  • 탐색적 유연성 vs 재생·감사 가능성

해법

목표와 도구 목록(A8 MCP·API)을 받아 AI가 계획을 세우고 도구를 골라 호출하며, 필요하면 하위 전문 에이전트에 위임한다(B′4·B′7·B′8). 단일 에이전트에서 시작해 하위 작업이 분리될 때만 계층·병렬로 승급한다. 도구별 읽기/쓰기 권한과 실행 승인은 C8로, 단계 상태와 되돌림은 C3로, 모든 호출은 C4 추적 로그로 남긴다. 신뢰 불가 입력을 읽는 경우 S5 계획 고정이나 S6 격리로 도구 출력이 새 행동을 끼워 넣지 못하게 하고, 되돌리기 어려운 조치 앞에는 F6 확인을 둔다.

이럴 때 쓴다

  • 한 건의 처리가 여러 시스템 조회·작성·검증에 걸쳐 있고 AI가 도구 순서를 골라야 할 때
  • 하위 작업이 실제로 분리되거나 컨텍스트 창이 부족할 때
  • C8·C3·C4 통제를 함께 갖출 수 있을 때

이럴 때는 쓰지 않는다

  • 단계 순서가 고정된 파이프라인일 때(B′1을 가진 B1·B4)
  • 실제 흐름이 초안 → 사람 확정일 때(B1)
  • 스케줄러·크롤러 수준 자동화일 때(agent_system=true라도 B6 아님)
  • 단일 에이전트가 되기 전에 멀티에이전트부터 만들려 할 때(X11)

얻는 것

  • 여러 시스템을 오가는 업무 흐름 자체를 재설계
  • 도구 교체로 다른 기관이 그래프를 재사용 가능
  • First 지향 구조

점검표

  • 복수 LLM 역할·도구 호출 루프·AI의 계획 선택이 실제로 있는가(R2)
  • 도구별 읽기/쓰기 권한과 실행 승인이 명시되어 있는가
  • 모든 도구 호출이 추적되는가
  • 도구 출력이 새 행동을 촉발하지 못하게 막는 구조가 있는가

B′3 병렬 팬아웃·수집 제어 흐름

PAX 사례 8건이 이 부품을 쓴다

맥락

다중 출처 검색, 여러 후보 생성 방법의 병렬 적용, 같은 추출을 여러 번 돌려 다수결하는 앙상블에 쓴다. B6 로컬 호스트 변형(유형 5b)이 이 배선을 쓰고, S6 맵리듀스는 이 원형의 격리·보안형이다.

맞서는 힘(긴장)

  • 지연 단축·관점 다양화 vs 호출 수·비용 증가
  • 취합 규칙의 단순함 vs 결과가 엇갈릴 때의 판정 기준
  • 하위 작업 독립성 가정 vs 실제로는 의존이 있는 경우

해법

작업을 서로 의존하지 않는 하위 작업으로 나눠 동시에 실행하고, 결과를 결정적 규칙이나 합성 단계로 취합한다. 구획형은 하위 작업마다 다른 출처·관점을 맡기고, 투표형은 같은 작업을 여러 번 돌려 다수결·일치 여부로 신뢰도를 정한다. 결과가 엇갈리면 보류해 사람에게 보낸다. 신뢰 불가 문서를 다룬다면 문서마다 격리 인스턴스를 두고 규칙으로 합쳐 S6으로 만든다.

이럴 때 쓴다

  • 하위 작업이 진짜로 독립일 때
  • 병렬화가 지연을 의미 있게 줄일 때
  • 단일 실행의 우연한 오류를 다수결로 줄여야 할 때

이럴 때는 쓰지 않는다

  • 하위 작업이 서로의 결과에 의존할 때(B′1·B′8)
  • 호출 비용을 늘릴 여유가 없을 때
  • 단일 에이전트가 아직 제대로 동작하지 않을 때(X11)

얻는 것

  • 지연 단축
  • 다관점·다출처 결과
  • 다수결로 우연한 오류 감소

점검표

  • 하위 작업이 서로 독립인가
  • 취합 규칙과 불일치 처리 규칙이 정의되어 있는가
  • 병렬화로 얻은 지연·품질 이득을 쟀는가

구조 — 참여 부품

  • 분배기 — 하위 작업으로 나눠 동시에 실행
  • 하위 작업 실행기 — 출처·관점·방법별 처리
  • 수집기 — 규칙·다수결로 취합하고 불일치 건 보류

변형

  • 구획(Sectioning): 서로 다른 부분 작업을 병렬로 돌린다(UrbanLaw 5인 AI 패널)
  • 투표(Voting): 같은 작업을 여러 번 돌려 다수결로 정한다

B′1 순차 파이프라인 제어 흐름

한 단계의 출력을 다음 단계의 입력으로 넘기는 고정 순서 배선이다. 한 프롬프트에 많은 일을 몰아 시켜 품질이 떨어지는 문제를 막는다.

PAX 사례 109건이 이 부품을 쓴다

맥락

B4 인식 파이프라인의 기본 배선이며, B1·B0·B5 안에서도 흔하다. 단계 순서가 업무 절차로 미리 정해져 있고 AI가 순서를 고를 필요가 없을 때 쓴다.

맞서는 힘(긴장)

  • 디버깅·출처 추적의 쉬움 vs 병렬화 불가로 인한 지연
  • 단계 분리의 품질 이점 vs 단계가 늘수록 오류 누적
  • 고정 순서의 예측 가능성 vs 예외 경로 처리의 경직성

해법

업무 절차를 단계로 나누고 각 단계의 입력·출력 형식을 정해 앞 단계 출력을 다음 단계에 넘긴다. 단계 사이에 형식 검증(스키마)을 두어 오류가 번지기 전에 멈추고, 멈춘 건은 C1 검토 큐나 C3 재처리로 보낸다. 판정·산수 단계는 가능한 한 규칙(B′9)으로 두고 모델은 추출·서술 단계만 맡긴다. 단계 순서를 AI가 바꿔야 한다면 B′8이나 B′7로 옮긴다.

이럴 때 쓴다

  • 업무 절차가 고정 순서로 정해져 있을 때
  • 각 단계를 따로 검증·추적해야 할 때(유형 ② 접수·심사, ⑧ 취합·변환)
  • 단일 에이전트에서 시작하는 첫 배선일 때

이럴 때는 쓰지 않는다

  • 하위 작업이 서로 독립이라 동시에 돌려야 지연이 줄 때(B′3)
  • 입력에 따라 AI가 다음 도구를 골라야 할 때(B′7)
  • 긴 업무를 계획부터 세워야 할 때(B′8)

얻는 것

  • 디버깅과 출처 추적이 쉬움
  • 단계별 품질 검증 가능
  • 구현이 가장 단순

점검표

  • 단계마다 입력·출력 형식이 정의되어 있는가
  • 단계 사이 검증에서 실패하면 멈추는가
  • 단계별 중간 결과를 추적할 수 있는가

구조 — 참여 부품

  • 단계 처리기 — 각 단계에서 추출·변환·작성 수행
  • 단계 간 형식 검증 — 다음 단계로 넘기기 전 스키마 확인
  • C3 상태 머신·롤백 — 실패 단계 재처리

A1 데이터 자산 서비스 공통 서비스

흩어진 업무 기록을 정제·라벨링해 AI 부품이 붙여 쓸 수 있는 데이터셋·라벨·데이터 사전 형태의 기준선으로 제공한다.

PAX 사례 110건이 이 부품을 쓴다

맥락

학습 모델(A2.5·B2), 지식 접지(B3)의 코퍼스, 평가 세트(C9)의 정답 출처가 필요한 과제라면 모두 이 부품을 쓴다. 서비스 유형 5a·9·10·11에서는 필수 기반이다. 비LLM 규칙 기반 대민 안내에서는 A2를 거치지 않고 결정론 조회의 대상이 된다(R21).

맞서는 힘(긴장)

  • 정제 품질 vs 구축 기간·라벨링 인력 비용
  • 과제 전용 가공(빠름) vs 기관 공통 기준선(재사용)
  • 데이터 활용 범위 vs 데이터 등급(E5) 보호
  • 기준선 고정(재현성) vs 원천 갱신 반영

해법

원천 기록을 수집→정제(중복·결측 처리)→라벨링→정의 문서화 순으로 가공하고, 결과를 정제 데이터셋·라벨·데이터 사전의 세 산출물로 고정해 제공한다. 'N건→M건 정제'처럼 정제 전후 규모와 기준을 기록하고, 변수·테이블·인터페이스 정의서로 소비 부품이 같은 정의를 쓰게 한다. 기준선은 버전으로 관리해 C9 평가 세트의 정답 출처와 C6 재학습의 입력으로 재사용한다. 데이터 경계는 부품별로 두고(DB per Service), 타 기관 데이터와의 결합은 A4로 분리한다.

이럴 때 쓴다

  • 예측·추천기(B2)나 비전 모델(A2.5)을 학습·재학습할 때
  • 지식 접지(B3)의 코퍼스를 구축할 때
  • 평가 세트(C9)의 정답 출처가 필요할 때
  • 서비스 유형 5a-agg·9·10·11처럼 A1이 필수인 조립

이럴 때는 쓰지 않는다

  • 공공 API 응답을 가공 없이 조회만 할 때(A3)
  • 정제·정의 없이 파일을 올려 바로 검색하는 경우(태그 대상 아님)
  • 타 기관 데이터 결합이 핵심일 때는 A4를 함께 태그해 계약·키 매핑을 따로 드러낸다

얻는 것

  • 모델 교체와 무관하게 남는 기관 자산
  • C9·C6·B3가 같은 기준선을 재사용
  • 데이터 사전이 기관 간 표준 확산의 단위가 됨

점검표

  • 정제 전후 규모와 정제 기준이 기록되어 있는가
  • 데이터 사전(정의·단위·출처)이 있는가
  • 기준선에 버전이 있고 평가용 분할이 학습용과 분리되어 있는가
  • 데이터 등급(E5)에 맞는 가명·비식별 처리가 적용되었는가

구조 — 참여 부품

  • 원천 시스템·기록 — 가공 전 업무 기록을 내주는 출처
  • 정제·라벨링 파이프라인 — 중복 제거·결측 처리·라벨 부여·품질관리를 수행
  • 데이터 사전 — 정의·단위·출처를 문서로 고정해 소비 부품이 같은 뜻으로 쓰게 함
  • C9 평가 세트·회귀시험 — 기준선을 정답 출처로 사용
  • A2.5 비LLM 학습 모델 — 기준선으로 학습·재학습하는 소비 부품

변형

  • 학습데이터 구축형: 영상·이미지 등을 수집해 품질관리 단계(중복 제거·재라벨링·학습/검증/평가 분리)를 거쳐 학습 기준선으로 만든다.
  • RAG 코퍼스 정본화형: 법령·규정 원문을 현행 시행본 기준으로 정본화하고 조문 구조·메타데이터를 부여해 색인한다.
  • 지표 표준화형: 여러 자료원의 지표를 도메인별로 표준화하고 정의·단위·분모·결측·원본 링크를 메타데이터로 관리한다.
  • 자동 피처 파이프라인형: 수집→정제→파생 변수 생성→자동 검증→담당자 승인을 주기 실행하고 승인만 사람에게 남긴다.

A3 공공 API 제공자 공통 서비스

정부·공공이 운영하는 모델·데이터·개발 도구(범정부 AI 공통기반, 모두의 AI 실험실, 공공데이터포털, 공공 깃랩)를 범정부 Provider로 소비한다.

PAX 사례 154건이 이 부품을 쓴다

맥락

모델·공공데이터·법령 원문·개발 환경을 공공 플랫폼에서 가져올 수 있다면 어느 과제든 해당한다. §7.1 2단계 '기반 부품은 새로 만들지 말고 Provider에서 먼저 찾는다'가 바로 이 부품을 가리킨다. 유형 7(대조·점검)에서는 법령·기준 출처를 대는 필수 기반이다.

맞서는 힘(긴장)

  • 공통 Provider 재사용 vs 기관 고유 요구 반영
  • 공공 API 가용성·갱신 주기 vs 서비스 신뢰성
  • 인가·검증 절차의 통제 vs 에이전트 루프의 병목(PAX 공공API 진단)

해법

기반을 새로 만들기 전에 범정부 AI 공통기반(모델), 공공데이터포털·법령 API(데이터), 모두의 AI 실험실·공공 깃랩(개발·실험 환경)에서 먼저 찾아 소비한다. 인증은 GPKI·디지털원패스 같은 연합 신원(Federated Identity)으로 위임하고, 공공 API 응답은 출처·조회 시각과 함께 업무 부품에 넘긴다. 에이전트가 부를 수 있게 하려면 A8 MCP 서버로 감싸고, 결과를 재가공해 기준선으로 고정하면 A1을 더한다. 기관이 만든 도구는 공공 깃랩에 등재해 다음 기관의 Provider가 되게 한다.

이럴 때 쓴다

  • 모델·데이터·개발 환경을 기관이 새로 만들려 할 때 — 먼저 Provider 확인
  • 법령·기준 원문을 최신으로 대조해야 하는 유형 7
  • 여러 부서가 같은 기반을 따로 만들고 있을 때(X3 교정)

이럴 때는 쓰지 않는다

  • 필요한 모델·데이터가 공공 Provider에 없을 때(만들고 레지스트리에 올림)
  • 타 기관 데이터를 계약·키 매핑으로 결합하는 경우는 A4

얻는 것

  • 기관별 중복 구축 방지(X3 교정)
  • 공인된 원천 데이터·모델 사용
  • 등재를 통해 전이 경로 확보

점검표

  • 같은 기반을 기관 안에서 따로 만들지 않았는가
  • 공공 API 응답의 출처·조회 시각이 결과에 남는가
  • API 장애·변경 시 어떻게 되는지 답할 수 있는가
  • 만든 도구가 공공 깃랩 등에 등재되었는가

구조 — 참여 부품

  • 공공 Provider — 범정부 AI 공통기반·공공데이터포털·모두의 AI 실험실·공공 깃랩
  • 연합 신원 인증 — GPKI·디지털원패스 등으로 호출 주체를 확인
  • 소비 부품(B·A2·A8) — Provider를 직접 만들지 않고 가져다 씀
  • S1 AI 게이트웨이·단일 진입점 — 공공 인증을 위임받아 호출을 통제

변형

  • 공공 모델 Provider: 범정부 AI 공통기반(HCX-GOV-THINK) 위에서 모델을 소비한다. 온나라 AI 문서 분배기가 공통기반 RAG 위에서 돈다.
  • 공공 데이터·법령 Provider: 공공데이터포털 OpenAPI·법제처 API 등을 실서비스 파이프라인에 상시 연동한다.
  • 개발·실험 환경 Provider: 모두의 AI 실험실·공공 깃랩에서 개발하고 결과물을 등재한다.

참조 구현 예

  • PAX ef389de4efadc258 — 법제처 API로 매일 최신성 검증(§13 A3)
  • PAX 3d07b6da99f5e1ed — 직제·시행규칙을 법령 API로 파싱·결합, 시행일 스냅샷 비교(§13 A3)

F1 출처 표시 상호작용 패턴

답변에 근거 문서·조문·통계표 ID를 붙여 이용자가 원문을 직접 확인할 수 있게 한다. C5 출처 검증의 이용자 면이다.

PAX 사례 87건이 이 부품을 쓴다

맥락

B3 지식 접지 상담, A8 공공데이터 MCP, 법령·통계·규정을 인용하는 모든 응답. 유형 ① 대민 상담, ⑤b 데이터 에이전트, ⑦ 대조·점검, ⑨ 인수인계(원문 위치).

맞서는 힘(긴장)

  • 출처 상세도 vs 화면 복잡도
  • 출처 표시 vs 실제 검증(표시만 하고 검증하지 않으면 잘못된 신뢰)
  • 원문 링크의 신선도 vs 유지 비용

해법

답변의 각 주장에 근거 문서·조문 번호·통계표 ID·원문 위치를 붙이고, 원문으로 바로 이동하는 링크를 제공한다. 출처의 갱신 시각과 이용 조건을 함께 보여 오래된 자료를 현재로 오인하지 않게 한다. 표시되는 출처는 C5 출처 검증을 통과한 것이어야 한다.

이럴 때 쓴다

  • B3 지식 접지 응답 전반
  • 대민 서비스 D1~D7(F1·F2·F7이 최소 요건)
  • 유형 ①⑤b⑦⑨처럼 F1이 필수인 유형

이럴 때는 쓰지 않는다

  • 모델의 판정 근거(요인·BBox·사유 코드)를 보여 주려는 경우(F9)
  • B0 결정적 도구로 원천 데이터를 그대로 보여 주는 경우(출처가 곧 화면)

얻는 것

  • 이용자 신뢰 확보
  • 원문 대조로 오류 발견
  • 공식 판단 여부를 이용자가 스스로 확인

점검표

  • 모든 답변에 출처가 붙는가
  • 출처가 원본과 대조되는가
  • 갱신 시각이 보이는가
  • 이용자가 원문을 바로 열 수 있는가

구조 — 참여 부품

  • C5 가드레일 필터 — 출처 검증
  • 이용자 — 원문을 열어 대조

변형

  • 문서·조문 인용: 근거 문서명과 조문 번호를 답변에 붙임
  • 통계표 ID 인용: 통계 답변에 통계표 ID를 자동 인용(KOSIS MCP 방식)
  • 출처·신선도 표시: 출처에 갱신 시각과 이용 조건을 함께 표시

참조 구현 예

  • PAX Korean Stats MCP — KOSIS 통계를 자연어로, 출처 자동 인용
  • PAX 224e2d82d9369735 — 모든 출처에 갱신 시각과 이용 조건을 함께 저장한 출처·신선도 표시
  • PAX 9998aba2d1f55c24 — 항목별 법령·처분사례 원문 연계(F1)

관련 부품

D7 상담·처방 서비스 블록

개인 상황에 맞춘 정보·처방·법령 안내를 주는 대민 접점 블록이다. B1 코파일럿이나 B3 지식 접지가 이 자리에 들어간다.

PAX 사례 14건이 이 부품을 쓴다

맥락

국민에게 개인 맞춤 정보·처방·법령 안내를 주는 접점. §7.3 유형 ① 대민 상담·안내(D1·D7)와 유형 ⑪ 추천·매칭(D7·D4)의 무대다.

맞서는 힘(긴장)

  • 맞춤화 정도 vs 오답의 대가
  • 전문가 전건 검토 vs 처리량
  • 민원인이 원하는 답 vs 규정·데이터에서 나오는 답(S4)
  • 쉬운 설명 vs '공식 해석 아님' 고지

해법

답이 데이터·규정에서 나오게 한다. 개인 조건은 F4 구조화 입력으로 받고, B3가 공개 규정·법령에 접지하거나 B1이 전문가 검토용 처방 초안을 만든다. 처방처럼 오답의 대가가 크면 C1 검토 큐로 전문가가 확정하고, 저위험 건만 C2로 자동 확정한다. 답에는 F1 출처와 F7 한계 고지, 추천이면 F9 추천 사유와 F3 대안을 붙인다. 민원인 입력에는 S4 행동 선택기·S7로 규정 밖 답을 막고, 이용자 반응과 전문가 수정은 C6로 되돌린다.

이럴 때 쓴다

  • 개인 조건에 따라 답이 달라지는 정보·처방·법령 안내
  • 전문가 상담 수요가 인력을 넘을 때
  • 일반 안내(D1)로는 무엇을 할지 결정하지 못할 때

이럴 때는 쓰지 않는다

  • 서비스·창구를 찾는 데서 끝나면 D1
  • 지급·승인 같은 자격 판정이면 D3
  • 이용자가 기관 담당자면 D8 하위 블록

얻는 것

  • 전문가 상담 대기 감소
  • 개인 조건에 맞는 행동 제시
  • 전문가 수정의 누적으로 품질 개선

점검표

  • 맞춤 답이 데이터·규정에서 나오는가
  • 오답의 대가가 큰 건에 전문가 확정이 있는가
  • 공식 판단이 아님이 고지되는가
  • 전문가 수정이 개선으로 되돌아오는가

구조 — 참여 부품

  • 국민 — 자기 상황을 말하고 맞춤 안내를 받음
  • B1 직접 프롬프트 코파일럿 — 처방·안내 초안 생성
  • B3 지식 접지 상담 — 법령·조례·규정에 접지한 답변
  • C1 검토 큐 — 전문가가 처방을 확정
  • F7 한계·신뢰도 안내 — 공식 판단이 아님을 고지
  • F9 판정 근거 표시 — 추천·처방 사유를 보여 줌

변형

  • 전문가 확정 처방형: B1이 초안을 만들고 전문가가 전건 검토.
  • 법령·조례 안내형: B3가 법령·조례에 접지해 답함(경기도의회 법·조례 안내).
  • 추천·매칭형: 조건 점수화로 맞춤 프로그램·서비스를 추천(유형 ⑪).

X9 담당자와 함께 사라지는 도구 안티패턴

개인이 만든 도구가 부서에 퍼졌지만 라이선스·저장소·인수인계가 없어, 만든 사람의 인사이동과 함께 멈추는 함정이다.

맥락

A7 자체 제작 환경으로 태깅된 도구(PAX 557건 중 317건, 57%), 특히 개인 사용에서 부서 공유로 막 퍼지기 시작한 바이브코딩 도구.

맞서는 힘(긴장)

  • 개인의 빠른 제작 vs 조직의 유지보수 책임
  • 비공식 공유의 편의 vs 라이선스·저장소 절차
  • 현장 맞춤 vs 다른 담당자가 이해할 수 있는 구조

해법

도구가 부서에 퍼지기 시작하면 A7 산출물에 MIT·Apache 등 라이선스를 명시하고, 코드를 개인 PC가 아니라 A3 공공 깃랩 같은 공용 저장소에 등재한다. 업무 규범·프롬프트는 A9 업무 규범 스킬로 패키징해 다른 담당자가 그대로 쓸 수 있게 하고, 설치·설정·데이터 경로를 담은 인수인계 문서를 둔다. 도구를 참조 구현 레지스트리(§13)에 올려 소유를 개인에서 조직으로 옮긴다. transition.blocker에 '담당자 이동'이 적힌 과제는 이 조치를 먼저 한다.

이럴 때 쓴다

  • 개인이 만든 도구를 부서원 여러 명이 쓰는데 라이선스 표기가 없다
  • 원본 코드가 개인 PC·개인 계정에만 있다
  • 인수인계 문서·설치 절차가 없다
  • transition.blocker가 '담당자 이동'이다

이럴 때는 쓰지 않는다

  • 개인만 쓰는 도구로 부서에 퍼지지 않은 경우(개인 사용 단계는 정상)
  • A7로 만들었지만 라이선스 명시·공용 저장소 등재·인수인계가 갖춰진 경우
  • 기관 정보화 부서가 넘겨받아 운영 중인 경우

얻는 것

  • 현장 담당자가 필요한 도구를 빠르게 만든다
  • 공식 절차 없이 바로 퍼진다

점검표

  • 라이선스가 명시되어 있는가
  • 원본이 공용 저장소에 있는가
  • 만든 사람 없이 후임이 설치·실행할 수 있는 문서가 있는가
  • 개인 구독·개인 키에 의존하지 않는가

구조 — 참여 부품

  • A7 자체 제작 환경 — 도구가 태어난 곳. 라이선스 명시가 전이 조건
  • A3 공공 API 제공자(공공 깃랩) — 개인 저장소를 대체하는 공용 등재처
  • A9 업무 규범 스킬 — 암묵적 업무 규범을 패키지로 남김
  • 후임 담당자 — 인수인계 문서로 도구를 이어받는 사람

변형

  • 라이선스 미명시: 코드는 공개했지만 라이선스가 없어 타 기관이 가져다 쓸 수 없음
  • 개인 저장소형: 개인 PC·개인 계정에만 원본이 있음
  • 개인 구독 의존형: 개인 AI 구독·API 키로 돌아가 담당자가 떠나면 호출이 끊김

A2 모델 서빙 계층 공통 서비스

업무 부품이 모델을 직접 부르지 않고 서빙 계층을 거쳐 부르게 해 모델을 바꿔 끼우고 라우팅·캐싱·버전 고정·폴백을 한 자리에서 다룬다. A2.0~A2.6을 묶는 부모 항목이다.

맥락

런타임에 모델(LLM·VLM·비전·ML)을 부르는 모든 B 부품. E2 모델 의존 값이 곧 어떤 하위 변형을 쓸지를 정하고, E1 배포망과 E5 데이터 등급이 허용 범위를 좁힌다. B0 결정적 도구처럼 런타임 AI가 없으면 해당하지 않는다.

맞서는 힘(긴장)

  • 모델 교체 가능성 vs 추상화 계층을 운영하는 비용
  • 모델 성능 vs 데이터 주권(E1·E5)
  • 비용 통제(라우팅·캐싱·배칭) vs 지연
  • 벤더 고유 기능 활용 vs 종속

해법

업무 부품과 모델 사이에 서빙 계층을 두고 모든 호출을 이 층으로 보낸다. 계층은 모델 버전을 고정하고 사용량·지연 로그를 C4로 넘기며, 대체 모델을 함께 등록해 C7이 전환할 자리를 만든다. 지능형 모델 라우팅(경량 모델이 복잡도를 보고 큰 모델로 넘김)·프롬프트 캐싱·동적 배칭은 모두 이 계층이 있어야 가능한 비용 통제다. 하위 변형은 모델이 어디서 도는가로 고른다: 기관 밖 상용 API면 A2.1(행정망·민감 등급이면 A2.4), 오픈웨이트를 기관 안에서 돌리면 A2.2, 재학습했으면 A2.3, 비LLM 자체 학습이면 A2.5, 장비·솔루션에 내장돼 있으면 A2.6, 알 수 없거나 이용자가 가져오면 A2.0이다.

이럴 때 쓴다

  • 업무 부품이 런타임에 모델을 한 번이라도 부를 때
  • 상용 API에 의존해 C7 폴백을 끼워야 할 때(E2 해외 상용 API)
  • 호출당 비용·지연을 관리해야 할 때(라우팅·캐싱)
  • 모델 업데이트 후 품질 회귀를 막아야 할 때(버전 고정 + C9)

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 런타임에 모델을 부르지 않을 때
  • 모델이 아니라 도구·데이터를 감싸는 층이 필요할 때(A8·A3)

얻는 것

  • 모델 교체와 C7 폴백이 가능해짐
  • 라우팅·캐싱으로 비용 통제
  • 버전 고정으로 회귀시험 가능
  • 민감정보 반출 통제 지점 확보

점검표

  • 업무 코드가 특정 모델 API를 직접 호출하지 않는가
  • 모델 버전이 고정·기록되는가
  • 대체 모델 또는 대체 경로가 계층에 등록되어 있는가
  • 선택한 변형이 E1·E5 조건과 모순되지 않는가

구조 — 참여 부품

  • 업무 컴포넌트(B) — 모델을 직접 부르지 않고 서빙 계층의 인터페이스만 호출
  • 라우터·캐시 — 요청 복잡도에 따라 모델을 고르고 반복 요청을 캐싱·배칭
  • 모델 풀(A2.0~A2.6) — 실제로 추론하는 모델들. 주 경로와 대체 경로를 함께 등록
  • C4 감사 로그·지표 — 호출별 사용량·지연·모델 버전 기록처
  • C7 폴백 스위치 — 장애·품질 저하 시 모델 풀 안에서 경로 전환

변형

  • 모델 미상: LLM 사용은 확인되지만 모델명이 없거나 이용자 구독 모델(BYO)에 얹혀 있다. v0.7에서 추가했다.
  • 상용 API 호출: GPT·Gemini·Claude·HyperCLOVA X·Upstage 등 상용 모델 API를 부른다.
  • 주권형 온프레미스: 오픈웨이트 모델을 자체 서버·폐쇄망·로컬 PC에서 돌린다(Ollama·vLLM).
  • 튜닝형: 파인튜닝·LoRA·재학습으로 만든 자체 모델이다. 진행 경로의 마지막 단계에 놓인다.
  • 내부망 프록시: 행정망·내부망에서 상용 모델을 기관 게이트웨이·사설 엔드포인트·범정부 공통기반을 거쳐 부른다.
  • 비LLM 학습 모델: XGBoost·LightGBM·YOLO·U-Net 등 기관이 직접 학습한 모델을 서빙한다.
  • 벤더 블랙박스: 장비·상용 제품에 내장돼 있어 기관이 모델을 보지도 바꾸지도 못한다.

C5 가드레일 필터 운영 컴포넌트

개인정보·환각·편향·형식 오류가 프롬프트나 산출물에 들어가지 못하게 시스템이 경계에서 걸러낸다. 비식별 전처리, 출처 검증, 구조적 출력 제약이 대표 변형이다.

PAX 사례 44건이 이 부품을 쓴다

맥락

외부 모델을 부르거나 대민에 답하는 모든 B 부품. 특히 E2 해외 상용 API, E5 S 이상 데이터, B3 지식 접지 상담, 유형 ① 대민 상담, ④ 기안, ⑥ 콘텐츠, ⑦ 대조·점검, ⑨ 인수인계, ⑬ 비식별·정제 도구.

맞서는 힘(긴장)

  • 차단의 엄격함 vs 과잉 차단으로 인한 유용성 저하
  • 비식별 강도 vs 문맥 보존
  • 결정적 검증의 신뢰성 vs 구현 범위

해법

프롬프트가 기관 밖으로 나가기 전 PII를 마스킹하고 원복 키를 보관하는 비식별 전처리기를 둔다. 응답에는 인용을 원본(법령정보센터·통계표 등)과 대조하는 출처 검증기와, JSON 스키마·허용 목록 같은 구조적 출력 제약을 건다. 근거가 없으면 답하지 않거나 '확인 필요'로 표시한다. 차단 사유는 C4에 남기고, 이용자에게는 F1 출처와 F7 한계 안내로 보인다. 사람이 하는 팩트체크·법무 심의는 C5가 아니라 C1.2에 둔다.

이럴 때 쓴다

  • E2 해외 상용 API로 행정망 본문이 외부로 나갈 때(필수)
  • E5 S 이상 개인정보·민감정보를 다룰 때
  • B3 대민 응답처럼 인용·수치의 정확성이 신뢰의 핵심일 때
  • C5가 필수인 유형 ①④⑥⑦⑨⑪⑬

이럴 때는 쓰지 않는다

  • E1 로컬 PC 완결로 데이터가 밖으로 나가지 않을 때 비식별은 불필요해질 수 있다(§5 매트릭스, 단 출처 검증은 별개)
  • 사람이 수행하는 심의만 있을 때(C1.2로 태그)
  • 적대적 입력 탐지가 목적일 때(S8)

얻는 것

  • 개인정보 외부 유출 차단
  • 환각 인용 감소
  • 상용 API 사용 조건 충족

점검표

  • 외부 전송 전 무엇이 걸러지는지 답할 수 있는가
  • 인용이 원본과 대조되는가
  • 근거 없을 때의 동작이 정해져 있는가
  • 차단 사유가 기록되는가

구조 — 참여 부품

  • 비식별 전처리기 — 외부 전송 전 PII 마스킹과 원복
  • 출처 검증기 — 인용을 원본과 대조해 환각을 걸러냄
  • 출력 제약 — 스키마·허용 목록·금칙어로 출력 형식 제한
  • F1 출처 표시 — 검증된 출처를 이용자에게 보임

변형

  • 로컬 비식별 전처리기: 외부 전송 전 PII 마스킹·원복(PAX에서 독립 부품으로 확인)
  • 출처 검증기: 인용을 법령정보센터·KCI·CrossRef 원본과 대조
  • 구조적 출력 제약·스키마 검증: JSON 스키마·허용 목록으로 출력 범위를 고정(v0.6 식별 신호 추가)
  • 근거 재대조형 환각 검증: 추출값의 근거 문장을 원문에서 재대조해 '문서확인/AI추정/문서에없음'으로 재분류

C9 평가 세트·회귀시험 운영 컴포넌트

배포 전에 업무 맥락의 질문·정답·채점 기준을 세트로 만들어, 프롬프트·모델·설정의 모든 변경을 같은 자로 재고 회귀를 잡는다.

PAX 사례 15건이 이 부품을 쓴다

맥락

모델·프롬프트·검색 설정이 바뀌는 모든 AI 부품. 특히 B3 지식 접지(검색 품질은 평가 없이 개선 불가), E2 상용 API(예고 없는 모델 업데이트), 유형 ①④⑤a⑦⑩⑫.

맞서는 힘(긴장)

  • 평가 세트 구축 비용 vs 변경의 안전
  • 사람 라벨의 정확성 vs LLM 심판의 규모
  • 세트 고정(비교 가능성) vs 업무 변화 반영(세트 갱신)

해법

RAG를 붙이거나 모델을 고르기 전에 업무 질문·정답·채점 기준(사람 라벨 + LLM 심판)을 세트로 만든다. 프롬프트·모델·설정 조합을 릴리스처럼 버전 관리하고, 모든 변경마다 같은 세트로 재평가해 점수표와 회귀 실패 목록을 남긴다. 기준을 넘지 못하면 배포하지 않는 게이트를 둔다. 학습 데이터와 평가 세트는 누수 없이 분리한다.

이럴 때 쓴다

  • RAG·튜닝을 붙이기 전(§7.1 4단계, §7.2 진행 경로 2단계)
  • E2 상용 API로 모델 업데이트가 예고 없이 올 때(필수)
  • 폐쇄망 로컬 모델의 교체 시점
  • C6 환류·C7 모델 교체를 하려 할 때(선행 조건)

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 비결정적 출력이 없을 때
  • 유형 5a 중 순수 시각화(R10: 면제)

얻는 것

  • 변경의 효과와 회귀를 숫자로 확인
  • 모델 교체·재학습의 안전
  • 모델 선정 근거 확보

점검표

  • 업무 질문·정답·채점 기준 세트가 있는가
  • 프롬프트·모델·설정이 버전 관리되는가
  • 변경마다 재평가한 기록이 있는가
  • 기준 미달 시 배포를 막는 절차가 있는가

구조 — 참여 부품

  • A1 데이터 자산 서비스 — 정답의 출처
  • A2 모델 서빙 계층 — 평가 대상 모델의 버전 고정
  • 채점기 — 사람 라벨과 LLM 심판으로 점수 산출
  • 배포 게이트 — 기준 미달 변경의 배포 차단

C7 폴백 스위치 운영 컴포넌트

모델·API·도구가 멈추거나 품질이 떨어질 때 대체 모델·규칙 기반 축소·수동 처리로 경로를 바꿔 서비스가 끊기지 않게 한다.

PAX 사례 12건이 이 부품을 쓴다

맥락

상용 API 또는 단일 모델에 의존하는 모든 B 부품. 특히 E2가 해외 상용 API이거나 B5처럼 상시 가동해야 하는 서비스.

맞서는 힘(긴장)

  • 가용성 vs 비용(대체 경로를 상시 유지하는 비용)
  • 품질 일관성 vs 대체 경로의 품질 저하
  • 자동 전환의 신속성 vs 전환 판단의 오작동 위험

해법

오류율·지연·단가 신호를 감시하다가 임계를 넘으면 재시도 → 기존 API → 대체 MCP → 대체 모델 → 규칙 기반 축소 → 수동 전환 순으로 경로를 바꾼다. 장애 범위는 격리(Bulkhead)로 한 부품에 가두고, 모델 교체는 무중단(Blue-Green)으로 한다. 전환은 C4 감사 로그에 남기고, 복구 후에는 원래 경로로 되돌리는 조건도 함께 정한다. 대체 경로의 품질 저하는 이용자에게 F7 한계 안내로 알린다.

이럴 때 쓴다

  • E2가 해외 상용 API이거나 혼합일 때
  • B5 현장 감지·경보처럼 상시 서비스일 때 필수
  • 대민 자동응답(B3 대민형)처럼 중단 비용이 큰 경우
  • 유형 ① 대민 상담(상시), ③ 현장 감시

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 런타임 AI가 없을 때
  • 로컬 완결 도구로 외부 의존이 없을 때
  • 유형 ①·⑦에서 model_dependency가 없음(비LLM)일 때는 필수에서 면제(R7)

얻는 것

  • 핵심 서비스 연속성
  • 벤더 종속 완화(X4 예방)

점검표

  • 대체 경로가 최소 하나 구현되어 있는가
  • 전환 임계와 복귀 조건이 수치로 정의되어 있는가
  • 전환 이력이 로그로 남는가
  • 실증 기간에 전환을 1회 이상 실행한 기록이 있는가

구조 — 참여 부품

  • A2 모델 서빙 계층 — 주 경로와 대체 모델을 함께 노출하는 끼울 자리
  • 상태 감시기 — 오류율·지연을 임계와 비교해 전환을 결정
  • C4 감사 로그·지표 — 전환 시점·사유·복구를 기록
  • 수동 처리 담당자 — 모든 자동 경로가 실패했을 때의 최종 경로

변형

F7 한계·신뢰도 안내 상호작용 패턴

AI가 무엇을 못 하는지, 얼마나 확신하는지, 공식 판단이 아님을 이용자가 볼 수 있는 곳에 적어 과신을 막는다.

PAX 사례 63건이 이 부품을 쓴다

맥락

맞서는 힘(긴장)

  • 정직한 한계 고지 vs 서비스 신뢰도 하락 우려
  • 신뢰도 수치 표시의 정확성 vs 이용자 이해

해법

화면에 사용 한계(대상 범위·미검증 항목·처리 시간), 신뢰도, '공식 판단 아님' 고지를 결과 옆에 배치한다. 저신뢰 결과는 표시를 달리하고, C7 대체 경로로 운영 중이면 품질 저하를 알린다. 고지 문구는 법률 자문·유권해석을 대체하지 않는다는 점을 분명히 적는다.

이럴 때 쓴다

  • 대민 서비스 D1~D7(F1·F2·F7 최소 요건)
  • 유형 ①⑦5a⑩⑬처럼 F7이 필수인 유형
  • C7 대체 경로 운영 중

이럴 때는 쓰지 않는다

  • 유형 ①·⑦에서 model_dependency가 없음(비LLM)이면 필수에서 면제(R7). 단 비LLM 도구도 한계 고지는 권장된다

얻는 것

  • 과신·오인 방지
  • 기관 책임 범위 명확화

점검표

  • 이용자가 '공식 판단이 아님'을 결과 화면에서 읽을 수 있는가
  • 사용 한계가 명시되어 있는가
  • 저신뢰 결과가 구분 표시되는가

구조 — 참여 부품

  • 고지 문구 — 사용 한계·공식 판단 아님
  • 신뢰도 표시 — 결과별 확신 수준
  • C7 폴백 스위치 — 대체 경로 운영 여부 제공

변형

X11 처음부터 멀티에이전트 안티패턴

하위 작업이 분리되지 않는데 에이전트를 여럿 두어 조정 비용만 늘리는 함정이다. 단일 에이전트로 되돌리면 더 잘 되는 경우가 많다.

맥락

B6 오케스트레이터를 설계하거나 B′3 병렬·B′4 계층 분해를 도입하려는 과제, 특히 단일 에이전트 구성을 시도해 본 기록이 없는 과제.

맞서는 힘(긴장)

  • 역할 분리의 설계 명료함 vs 에이전트 간 조정 비용
  • 병렬 처리의 지연 단축 vs 결과 통합의 복잡도
  • 기술적 인상 vs 단순한 구조의 품질·비용

해법

B′ 원형 선택 규칙대로 단일 에이전트(B′1 순차, B′7 ReAct 도구 루프)에서 시작한다. 하위 작업이 진짜로 분리되거나, 병렬이 지연을 의미 있게 줄이거나, 컨텍스트 창이 부족할 때만 B′3 병렬·B′4 계층 분해로 승급한다. 승급 판단은 C9 평가 세트로 단일 구성과 비교해 내린다. 에이전트끼리 충돌·중복이 관측되면 B′4 감독자 계층이나 B′2 라우터로 정리하거나 단일 에이전트로 후퇴한다. B6 태그는 R2 요건(복수 LLM 역할 + 도구 호출 루프 + AI가 계획·도구를 선택)을 만족할 때만 붙인다.

이럴 때 쓴다

  • 에이전트가 여럿인데 하위 작업의 입력·출력이 서로 얽혀 독립적으로 돌지 않는다
  • 단일 에이전트 구성과 비교한 기록이 없다
  • 에이전트끼리 충돌·중복·재작업이 관측된다
  • 호출 비용·지연이 에이전트 수에 비례해 늘었는데 품질 개선 근거가 없다

이럴 때는 쓰지 않는다

  • 하위 작업이 진짜로 분리되고(서로 다른 데이터·도구), 병렬이 지연을 줄이거나 컨텍스트가 부족해 승급한 경우
  • R2 요건을 만족하는 B6로, 단일 구성보다 나음이 C9로 확인된 경우
  • 고정 순서 파이프라인을 B′1으로 정직하게 서술한 경우

얻는 것

  • 구조도가 명료하고 기술적으로 인상적이다
  • 역할별로 프롬프트를 나눠 관리하기 쉬워 보인다

점검표

X13 도구 출력이 지시가 되는 에이전트 안티패턴

검색 결과·첨부·API 응답을 읽은 모델이 그 안의 문장을 새 명령으로 받아 도구를 부르는 구조를, 탐지 필터 하나로 지키려는 함정이다.

맥락

E4가 P2 이상(시스템 쓰기·처분 보조)이면서 민원 입력·제출 서류·웹 문서·타 기관 API 응답 같은 신뢰 불가 입력을 읽는 에이전트. 특히 B6·5b 데이터 에이전트.

맞서는 힘(긴장)

  • 범용 에이전트의 유연성 vs 신뢰 불가 입력 뒤의 행동 제약
  • 단일 LLM 구조의 단순함 vs 격리·계획 고정의 설계 비용
  • 탐지 필터의 손쉬움 vs 증명 가능한 보증

해법

과제의 AI가 읽는 입력 중 기관 밖에서 작성된 것을 untrusted_inputs로 나열하고, §4.2 신뢰 불가 입력 규칙대로 S4 행동 선택기(미리 정한 행동 중 선택만, 결과가 LLM으로 돌아가지 않음), S5 계획 후 실행(외부 데이터를 읽기 전에 도구 호출 계획을 고정), S6 격리 LLM(도구 있는 LLM은 외부 데이터를 읽지 않고, 읽는 LLM은 도구가 없음) 중 하나를 갖춘다. S3 컨텍스트 방화벽과 S8 독립 검증기는 보조로 붙이되 S8만으로는 규칙을 충족하지 못한다. C8 승인 게이트도 신뢰 불가 입력 규칙의 대체 통제로 인정되지 않는다(R6). 그 전 단계에서는 E4를 P0~P1 읽기·산출물 범위에 묶어 두는 것이 곧 보안이다.

이럴 때 쓴다

  • E4가 P2 이상이고 untrusted_inputs가 비어 있지 않은데 S4·S5·S6이 모두 없다(신뢰 불가 입력 규칙 위반)
  • 외부 문서를 읽는 LLM이 같은 컨텍스트에서 쓰기 도구를 호출할 수 있다
  • 인젝션 대책이 탐지 필터·프롬프트 경고문뿐이다
  • 읽은 텍스트 중 어떤 것이 어떤 도구를 부를 수 있는지 답하지 못한다

이럴 때는 쓰지 않는다

  • E4가 P0~P1로 읽기·산출물 생성에만 묶여 도구 호출·시스템 쓰기가 없는 경우(S4·S5·S6 판정 전제 불충족, R6)
  • S4·S5·S6 중 하나가 구조적으로 갖춰진 경우(보안 목적 서술이 없어도 구조가 일치하면 충족)
  • AI가 읽는 입력이 모두 기관 내부에서 작성된 경우

얻는 것

  • 단일 LLM 범용 에이전트로 구조가 단순하다
  • 새 입력·새 도구를 자유롭게 붙인다

점검표

  • untrusted_inputs가 나열되어 있는가
  • 신뢰 불가 입력을 읽은 LLM이 쓰기 도구를 직접 부를 수 없는가
  • S4·S5·S6 중 하나가 구조로 구현되어 있는가
  • S8 탐지를 유일한 방어로 두지 않았는가

구조 — 참여 부품

  • S4 행동 선택기 — LLM이 정해진 행동 중 선택만 하게 제약
  • S5 계획 후 실행·코드 후 실행 — 외부 데이터를 읽기 전에 도구 계획 고정
  • S6 격리 LLM·맵리듀스 — 읽는 LLM과 도구 있는 LLM을 분리
  • S8 독립 검증기·이중 심판 — 보조 탐지. 단독으로는 보증이 아님

변형

  • 문서 속 지시: 첨부·제출 서류 안의 문장대로 에이전트가 도구를 호출
  • API 응답 오염: 타 기관 API·웹 검색 결과에 섞인 지시가 후속 행동을 바꿈
  • 탐지 단독 방어: 인젝션 탐지 필터(S8) 하나만 두고 구조적 제약이 없음

관련 부품

X14 재생할 수 없는 사고 안티패턴

잘못된 처분이 나갔는데 그때의 프롬프트·검색·도구 호출 순서를 아무도 복원하지 못하는 함정이다. 지표는 있는데 기록이 없다.

맥락

E4가 P2 이상, 특히 P3 처분 보조(지급·승인·반려 결과에 직결)에 관여하는 AI 부품. 모델·프롬프트가 자주 바뀌는 상용 API 과제.

맞서는 힘(긴장)

  • 집계 지표의 손쉬움 vs 건별 재생 기록의 저장·보호 비용
  • 개인정보 최소 보관 vs 사고 재현 가능성
  • 빠른 모델·프롬프트 변경 vs 버전별 재현

해법

  • P3 처분 보조에 관여하면서 재생 기록이 없다
  • 모델·프롬프트 버전을 기록하지 않는다

이럴 때는 쓰지 않는다

얻는 것

  • 기록에 당시 모델·프롬프트 버전이 포함되는가
  • 기록의 변조 방지 장치가 있는가
  • 이의제기 처리에 재생 기록이 쓰이는가

X7 도구 설명 ≠ 실제 권한 안티패턴

MCP 도구 설명은 '조회'인데 코드는 쓰기·실행 권한을 가져, 설명만 믿고 도구를 부르는 에이전트가 의도하지 않은 변경을 일으키는 함정이다.

맥락

E3 MCP·CLI 설정 환경에서 A8 MCP 서버·호스트를 만들거나 가져다 쓰는 과제. 특히 업무 시스템 MCP(쓰기, P2)와 공공데이터 MCP(읽기, P0)가 한 호스트에 함께 연결된 경우.

맞서는 힘(긴장)

  • 빠른 MCP 래핑 vs 도구별 권한 분리
  • 도구 하나로 묶는 편의 vs 읽기/쓰기 분리의 운영 부담
  • 에이전트 자율 호출 vs 실행 전 승인

해법

A8의 각 도구에 실제 권한 수준(P0~P4)을 설명과 함께 명시하고, C8 권한 경계로 읽기 전용 도구와 쓰기 도구를 서로 다른 서버·인증으로 분리한다. 쓰기·실행 도구는 도구별 실행 승인과 호출 상한, 킬스위치를 둔다. 반입하는 MCP 서버는 S11 인제스천·공급망 검증에서 PAX 6축(권한 표면·비밀·공급망·위생·인젝션·데이터 흐름)을 통과해야 활성화한다. 사람에게는 F6 에이전트 행동 검토·확인으로 실행 전 무엇을 할지 보여 주고, 승인·실패는 C4에 남긴다.

이럴 때 쓴다

  • MCP 도구 설명과 실제 권한(쓰기·삭제·발송)이 다르다
  • 읽기와 쓰기 도구가 같은 서버·같은 인증 토큰을 쓴다
  • 도구별 권한 수준·실행 승인이 문서에 없다
  • 6축 검증에서 권한 표면이 '주의'로 나왔다

이럴 때는 쓰지 않는다

  • 읽기 전용 MCP로 설계되어 쓰기 기능이 배제된 경우
  • 쓰기 도구가 있지만 설명에 부수 효과가 명시되고 C8 실행 승인이 있는 경우
  • MCP가 아닌 결정적 스크립트로 권한이 코드에 고정된 경우

얻는 것

  • 기존 API를 빠르게 에이전트 도구로 만든다
  • 도구 수가 적어 관리가 쉬워 보인다

점검표

  • 모든 도구의 설명에 실제 권한과 부수 효과가 적혀 있는가
  • 읽기와 쓰기 도구가 서로 다른 인증을 쓰는가
  • 쓰기 도구에 실행 전 승인이 있는가
  • 반입 MCP가 6축 검증을 통과했는가

구조 — 참여 부품

  • A8 MCP 서버·호스트 — 도구 설명과 실제 권한이 일치해야 하는 곳
  • C8 권한 경계·킬스위치 — 읽기/쓰기 분리, 도구별 승인
  • S11 인제스천·공급망 검증 — 반입 시 6축 검증
  • F6 에이전트 행동 검토·확인 — 실행 전 사람에게 행동을 보여 줌

변형

  • API 통째 래핑: 기존 API 클라이언트를 감싸 조회·수정 함수가 같은 도구·인증으로 노출
  • 과대 인증: 조회 도구가 쓰기 권한 토큰으로 실행됨
  • 설명 누락: 도구 설명에 부수 효과(삭제·발송)가 적혀 있지 않음

X8 MCP 서버 개수 세기 안티패턴

MCP 서버를 몇 개 만들었는지가 성과가 되고, 실제 업무에서 호출되는지·흐름이 바뀌었는지는 아무도 묻지 않는 함정이다.

맥락

공공데이터·업무 시스템을 MCP로 감싸는 과제, MCP 서버를 사례 단위로 등록하는 커뮤니티 아카이브, 'MCP N종 구축'을 성과 지표로 둔 과제.

맞서는 힘(긴장)

  • 보고하기 쉬운 개수 vs 측정하기 어려운 업무 전환
  • 서버 제공자 책임 vs 호스트·업무 쪽 활용 책임
  • 빠른 확장 vs 서버마다의 검증·유지보수

해법

서버마다 그것을 호출하는 B 업무 컴포넌트와 업무 산출물을 연결해 '어느 업무의 어떤 산출물에 쓰이는가'를 적는다. C4 감사 로그·지표로 호출 수·호출 주체·업무 건을 집계하고, transition.stage와 파급력 척도(M1~M5)로 전환 경로를 추적한다(PAX: 도구 수보다 전환 경로를 추적). R18대로 서버 제공자 사례(5b-server)와 호스트 통합 사례(5b-host)를 나눠 서버 쪽은 A8·S11·문서화된 스키마를, 호스트 쪽은 C4·F1·S5|S6을 갖춘다. 호출되지 않는 서버는 레지스트리에서 정리한다.

이럴 때 쓴다

  • 성과가 MCP 서버·도구 개수로 보고된다
  • 호출 수·호출 주체·업무 건 지표가 없다
  • 서버를 호출하는 업무 산출물이 서술되지 않는다
  • 흐름이 바뀌었다는 서술 없이 'MCP 기반 전환'을 주장한다

이럴 때는 쓰지 않는다

  • 단일 MCP 서버를 만들어 A8·S11·문서화된 스키마를 갖춘 5b-server 사례(R18). 서버 제공 자체가 사례 단위이므로 개수를 성과로 주장하지 않으면 함정이 아니다
  • MCP 서버 여러 개를 호스트 업무에 연결하고 호출 지표를 C4로 집계한 경우

얻는 것

  • 성과를 개수로 명확히 보고할 수 있다
  • 공공 API를 빠르게 에이전트 도구로 공개한다

점검표

  • 서버마다 호출하는 업무 산출물이 적혀 있는가
  • 서버별 월 호출 수와 호출 주체를 말할 수 있는가
  • 호출되지 않는 서버를 정리하는 절차가 있는가
  • 성과 지표가 개수가 아니라 업무 전환으로 잡혀 있는가

구조 — 참여 부품

  • A8 MCP 서버·호스트 — 개수로 세어지는 도구 인터페이스
  • C4 감사 로그·지표 — 호출 수·호출 주체·업무 건을 집계하는 빠진 부품
  • B 업무 컴포넌트 — 서버를 실제로 호출해 산출물을 만드는 쪽
  • S11 인제스천·공급망 검증 — 서버 제공자 쪽 필수 검증(R18)

변형

  • 개수 성과형: 'MCP N종 구축'이 과제의 주요 성과 지표
  • 호스트 없는 서버: 서버만 공개하고 어떤 호스트·업무에서 쓰이는지 기록이 없음
  • 방치 서버: 원천 API 변경 후 갱신되지 않아 호출이 실패하는 서버가 목록에 남음
