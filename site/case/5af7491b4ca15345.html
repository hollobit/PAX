판정 근거

특정 도메인용 챗봇이 아니라 사용자가 문서 컬렉션·MCP 서버·모델·워크플로우를 직접 등록하고 조합하는 범용 에이전트 바탕 시스템이다. 도구 호출 루프와 복수 역할(라우팅·검색·생성)을 갖춘 오케스트레이터라 B6으로 판정했고, MCP 서버·모델을 사용자가 자유롭게 붙이는 구조라 변형은 '로컬 MCP 호스트'다. 모든 검색 단계를 재고 수치로만 채택하고 기각한 15건의 실패 기전을 기술 보고서로 남긴 점이 C9 평가·회귀시험에 정확히 부합해 present로 태깅했다. 특허·상표 심사 문서는 예시 데이터일 뿐이라고 밝혀 실제 운영 데이터는 아니다.

구현 가이드

구현 단계

  1. 업무를 도구 목록으로 나누고 도구마다 읽기/쓰기, 되돌리기 비용을 적어 C8 권한표를 먼저 만든다.
  2. 단일 에이전트 + ReAct 루프(B′7)로 시작해 C9 평가 세트로 재고, 하위 작업이 분리될 때만 B′4·B′3으로 승급한다.
  3. 신뢰 불가 입력(외부 문서·API 응답)을 읽는지 확인하고, P2 이상이면 S5 계획 고정 또는 S6 격리를 설계한다.
  4. 단계 상태·되돌림(C3), 호출 추적(C4), 되돌리기 어려운 조치 앞 확인(F6)을 붙인다.
  5. 모델 장애 대비 C7과 킬스위치를 시험하고 결정적 재생(S10) 기록을 남긴다.

점검표

  • 복수 LLM 역할·도구 호출 루프·AI의 계획 선택이 실제로 있는가(R2)
  • 도구별 읽기/쓰기 권한과 실행 승인이 명시되어 있는가
  • 모든 도구 호출이 추적되는가
  • 도구 출력이 새 행동을 촉발하지 못하게 막는 구조가 있는가

환경 조건

E3 MCP·CLI. E1 폐쇄망이면 A8 로컬 MCP 호스트 + A2 로컬 모델 변형만 가능하다. E2 해외 상용 API면 A2 게이트웨이 + C7 + C8 도구별 승인. E4가 P2 이상으로 올라가기 가장 쉬운 부품이라 C2·C3·C4·C8 킬스위치가 필수이며, 신뢰 불가 입력 + P2 이상이면 S5 또는 S6 + S9가 필요하다(§5 매트릭스).

  • X9 담당자와 함께 사라지는 도구 (이 사례에서 확인) 개인이 만든 도구가 부서에 퍼졌지만 라이선스·저장소·인수인계가 없어, 만든 사람의 인사이동과 함께 멈추는 함정이다. 대처: 도구가 부서에 퍼지기 시작하면 A7 산출물에 MIT·Apache 등 라이선스를 명시하고, 코드를 개인 PC가 아니라 A3 공공 깃랩 같은 공용 저장소에 등재한다. 업무 규범·프롬프트는 A9 업무 규범 스킬로 패키징해 다른 담당자가 그대로 쓸 수 있게 하고, 설치·설정·데이터 경로를 담은 인수인계 문서를 둔다. 도구를 참조 구현 레지스트리(§13)에 올려 소유를 개인에서 조직으로 옮긴다. transition.blocker에 '담당자 이동'이 적힌 과제는 이 조치를 먼저 한다.
  • X11 처음부터 멀티에이전트 하위 작업이 분리되지 않는데 에이전트를 여럿 두어 조정 비용만 늘리는 함정이다. 단일 에이전트로 되돌리면 더 잘 되는 경우가 많다. 대처: B′ 원형 선택 규칙대로 단일 에이전트(B′1 순차, B′7 ReAct 도구 루프)에서 시작한다. 하위 작업이 진짜로 분리되거나, 병렬이 지연을 의미 있게 줄이거나, 컨텍스트 창이 부족할 때만 B′3 병렬·B′4 계층 분해로 승급한다. 승급 판단은 C9 평가 세트로 단일 구성과 비교해 내린다. 에이전트끼리 충돌·중복이 관측되면 B′4 감독자 계층이나 B′2 라우터로 정리하거나 단일 에이전트로 후퇴한다.   • X13 도구 출력이 지시가 되는 에이전트 검색 결과·첨부·API 응답을 읽은 모델이 그 안의 문장을 새 명령으로 받아 도구를 부르는 구조를, 탐지 필터 하나로 지키려는 함정이다. 대처: 과제의 AI가 읽는 입력 중 기관 밖에서 작성된 것을 untrusted_inputs로 나열하고, §4.2 신뢰 불가 입력 규칙대로 S4 행동 선택기(미리 정한 행동 중 선택만, 결과가 LLM으로 돌아가지 않음), S5 계획 후 실행(외부 데이터를 읽기 전에 도구 호출 계획을 고정), S6 격리 LLM(도구 있는 LLM은 외부 데이터를 읽지 않고, 읽는 LLM은 도구가 없음) 중 하나를 갖춘다. S3 컨텍스트 방화벽과 S8 독립 검증기는 보조로 붙이되 S8만으로는 규칙을 충족하지 못한다. C8 승인 게이트도 신뢰 불가 입력 규칙의 대체 통제로 인정되지 않는다(R6). 그 전 단계에서는 E4를 P0~P1 읽기·산출물 범위에 묶어 두는 것이 곧 보안이다.
  • X14 재생할 수 없는 사고 잘못된 처분이 나갔는데 그때의 프롬프트·검색·도구 호출 순서를 아무도 복원하지 못하는 함정이다. 지표는 있는데 기록이 없다. 대처: S10 결정적 재생으로 프롬프트·검색 결과·도구 호출·정책 결정·실행 흔적을 시각·주체·컨텍스트 해시와 함께 순서대로 기록하고, 필요하면 변조 방지 서명을 붙인다. 기록은 S1 단일 진입점에서 시작해 C4와 같은 파이프라인으로 적재하되, C4가 '얼마나'를 세고 S10은 '정확히 무엇이 일어났나'를 되돌리게 역할을 나눈다. 모델·프롬프트·설정 조합을 C9로 버전 고정해 그 시점의 구성을 재현할 수 있게 하고, 재생 기록을 C3 롤백·이의제기의 근거로 쓴다. 개인정보는 C5 비식별과 E5 등급에 맞춘 보관 기간으로 다룬다.

  • X8 MCP 서버 개수 세기 MCP 서버를 몇 개 만들었는지가 성과가 되고, 실제 업무에서 호출되는지·흐름이 바뀌었는지는 아무도 묻지 않는 함정이다. 대처: 서버마다 그것을 호출하는 B 업무 컴포넌트와 업무 산출물을 연결해 '어느 업무의 어떤 산출물에 쓰이는가'를 적는다. PAX 사례 15건이 이 부품을 쓴다

맥락

여러 시스템·도구(A8 MCP·API·문서)를 오가는 다단계 업무, 데이터 조회·분석 에이전트(유형 5b), 망분리 환경의 로컬 MCP 호스트에 쓴다. 하위 작업이 실제로 분리되거나 AI가 도구를 골라야 할 때만 해당한다.

맞서는 힘(긴장)

  • 자율성 vs 권한 통제(P2 이상에서 C8 필수)
  • 멀티에이전트의 분업 vs 조정 비용·충돌(X11)
  • 도구 출력 활용 vs 도구 출력 속 지시가 명령이 되는 위험(X13)
  • 탐색적 유연성 vs 재생·감사 가능성

해법

목표와 도구 목록(A8 MCP·API)을 받아 AI가 계획을 세우고 도구를 골라 호출하며, 필요하면 하위 전문 에이전트에 위임한다(B′4·B′7·B′8). 단일 에이전트에서 시작해 하위 작업이 분리될 때만 계층·병렬로 승급한다. 도구별 읽기/쓰기 권한과 실행 승인은 C8로, 단계 상태와 되돌림은 C3로, 모든 호출은 C4 추적 로그로 남긴다. 신뢰 불가 입력을 읽는 경우 S5 계획 고정이나 S6 격리로 도구 출력이 새 행동을 끼워 넣지 못하게 하고, 되돌리기 어려운 조치 앞에는 F6 확인을 둔다.

이럴 때 쓴다

  • 한 건의 처리가 여러 시스템 조회·작성·검증에 걸쳐 있고 AI가 도구 순서를 골라야 할 때
  • 하위 작업이 실제로 분리되거나 컨텍스트 창이 부족할 때
  • C8·C3·C4 통제를 함께 갖출 수 있을 때

이럴 때는 쓰지 않는다

  • 단계 순서가 고정된 파이프라인일 때(B′1을 가진 B1·B4)
  • 실제 흐름이 초안 → 사람 확정일 때(B1)
  • 스케줄러·크롤러 수준 자동화일 때(agent_system=true라도 B6 아님)
  • 단일 에이전트가 되기 전에 멀티에이전트부터 만들려 할 때(X11)

얻는 것

  • 여러 시스템을 오가는 업무 흐름 자체를 재설계
  • 도구 교체로 다른 기관이 그래프를 재사용 가능
  • First 지향 구조

점검표

  • 복수 LLM 역할·도구 호출 루프·AI의 계획 선택이 실제로 있는가(R2)
  • 도구별 읽기/쓰기 권한과 실행 승인이 명시되어 있는가
  • 모든 도구 호출이 추적되는가
  • 도구 출력이 새 행동을 촉발하지 못하게 막는 구조가 있는가

B′2 라우터·디스패처 제어 흐름

요청의 의도·유형·난이도를 읽어 전문 경로·모델·도구·담당자로 보내는 배선이다. 모든 건을 같은 경로로 보내는 낭비를 막는다.

PAX 사례 23건이 이 부품을 쓴다

맥락

대민 상담(B3)의 예외 이관, 규칙 선필터로 LLM 호출 줄이기, 폐쇄망 모델과 외부 모델 사이의 모델 라우팅, 여러 MCP를 한 서버에서 경로별로 제공하는 구성에 쓴다. C2 위험도 라우터의 내부 원형이고, D4 분류·이관을 기술로 구현한 실체다.

맞서는 힘(긴장)

  • 경로 분리의 효율 vs 라우팅 오류라는 새 위험
  • 규칙 라우팅의 예측 가능성 vs 모델 라우팅의 유연성
  • 외부 모델 분기의 품질 vs 경계 통제(E1·E5)

해법

요청을 분류하는 단계(규칙·경량 모델·LLM)를 앞에 두고, 분류 결과마다 처리 경로(규칙 판정, LLM 판정, 담당자 이관, 판단 불필요)를 정한다. 경로별 처리 비율을 C4로 실측해 라우팅 품질을 보고, 분류가 불확실한 건은 사람에게 보낸다(C2·F11). 모델 라우팅은 A2 서빙 계층의 기능으로 두고 외부 모델로 나가는 분기에는 C5 비식별을 건다. 보안이 필요한 대민 접점에서는 LLM이 미리 정한 행동 중 선택만 하게 제약해 S4로 만든다.

이럴 때 쓴다

  • 요청 유형마다 처리 비용·방법이 뚜렷이 다를 때
  • 답할 수 없는 건을 담당자로 이관해야 할 때(유형 ① 대민 상담)
  • LLM 호출 비용을 줄여야 할 때

이럴 때는 쓰지 않는다

  • 요청 유형이 하나뿐일 때
  • 분류 오류의 비용이 큰데 분류 품질을 잴 방법이 없을 때
  • 라우팅 대신 규칙으로 판정 모델 호출 대상 자체를 좁히는 구조일 때(B′10)

얻는 것

  • 호출 비용 절감
  • 답할 수 없는 건의 이관
  • 경로별 전문화

점검표

  • 경로별 처리 비율을 실측하는가
  • 분류가 불확실할 때 사람에게 가는 경로가 있는가
  • 외부 모델로 나가는 분기에 비식별이 걸려 있는가

세션 안의 맥락과 세션을 넘는 장기 기억을 유지하는 배선이다. 공공에서는 개인정보 축적과 직결되므로 등급·비식별 없이 장기 기억을 두지 않는다.

맥락

  • 토큰 절약 vs 요약 과정의 정보 손실

해법

공공 API·업무 시스템·로컬 파일을 도구 설명·인증·정책과 함께 MCP 서버로 감싸 에이전트에 노출하고, 호출 결과에 출처·갱신 시각을 붙이며 호출 로그를 남긴다. 읽기(P0) 서버와 쓰기(P2) 서버를 분리하고 C8로 도구별 실행 승인을 건다. 배포·등재 전에 PAX MCP 6축 검증(권한 표면·비밀·공급망·위생·인젝션·데이터 흐름)을 통과시키고 S11로 반입을 검사하며, 통과하지 못한 축이 있으면 전이 범위를 부서 공유 이하로 둔다. 도구 목록·버전·갱신 공지는 레지스트리(Service Discovery)로 관리한다. 폐쇄망에서는 로컬 모델(A2.2)로 여러 MCP를 구동하는 로컬 호스트 변형을 쓴다.

이럴 때 쓴다

  • 에이전트가 공공 API·업무 시스템을 도구로 호출해야 할 때
  • 기관 데이터를 외부 AI 클라이언트와 타 기관이 직접 호출하게 공개할 때
  • 표준 시스템에 API를 열어 레거시 오버레이(B8)를 대체할 때

이럴 때는 쓰지 않는다

  • 호출할 도구가 로컬 파일뿐인 단순 작업(§5 E1 로컬 PC 행: 드묾)
  • 실제 업무 호출 없이 서버 개수를 성과로 삼으려 할 때(X8)
  • 6축 검증·권한 분리를 할 수 없는데 쓰기 도구를 노출하려 할 때

얻는 것

  • 도구 재사용과 생태계 확산
  • 권한·호출을 한 층에서 관리
  • 공공데이터를 AI가 직접 쓰는 경로

점검표

  • 도구 설명이 '조회'인데 쓰기·실행 권한을 가진 도구가 없는가
  • 6축 검증 결과가 기록되어 있는가
  • 호출 로그와 실제 업무 호출 지표가 있는가
  • 호스트가 도구 출력을 명령으로 받지 않도록 S5·S6 등이 있는가(P2 이상)

구조 — 참여 부품

  • MCP 서버 — 공공 API·업무 시스템·로컬 파일을 도구로 감쌈
  • MCP 호스트(에이전트) — 도구를 선택·호출하고 결과를 업무 흐름에 사용
  • C8 권한 경계·킬스위치 — 읽기/쓰기 분리와 도구별 실행 승인

A1 데이터 자산 서비스 공통 서비스

흩어진 업무 기록을 정제·라벨링해 AI 부품이 붙여 쓸 수 있는 데이터셋·라벨·데이터 사전 형태의 기준선으로 제공한다.

PAX 사례 110건이 이 부품을 쓴다

맥락

학습 모델(A2.5·B2), 지식 접지(B3)의 코퍼스, 평가 세트(C9)의 정답 출처가 필요한 과제라면 모두 이 부품을 쓴다. 서비스 유형 5a·9·10·11에서는 필수 기반이다. 비LLM 규칙 기반 대민 안내에서는 A2를 거치지 않고 결정론 조회의 대상이 된다(R21).

맞서는 힘(긴장)

  • 정제 품질 vs 구축 기간·라벨링 인력 비용
  • 과제 전용 가공(빠름) vs 기관 공통 기준선(재사용)
  • 데이터 활용 범위 vs 데이터 등급(E5) 보호
  • 기준선 고정(재현성) vs 원천 갱신 반영

해법

원천 기록을 수집→정제(중복·결측 처리)→라벨링→정의 문서화 순으로 가공하고, 결과를 정제 데이터셋·라벨·데이터 사전의 세 산출물로 고정해 제공한다. 'N건→M건 정제'처럼 정제 전후 규모와 기준을 기록하고, 변수·테이블·인터페이스 정의서로 소비 부품이 같은 정의를 쓰게 한다. 기준선은 버전으로 관리해 C9 평가 세트의 정답 출처와 C6 재학습의 입력으로 재사용한다. 데이터 경계는 부품별로 두고(DB per Service), 타 기관 데이터와의 결합은 A4로 분리한다.

이럴 때 쓴다

  • 예측·추천기(B2)나 비전 모델(A2.5)을 학습·재학습할 때
  • 지식 접지(B3)의 코퍼스를 구축할 때
  • 평가 세트(C9)의 정답 출처가 필요할 때
  • 서비스 유형 5a-agg·9·10·11처럼 A1이 필수인 조립

이럴 때는 쓰지 않는다

  • 공공 API 응답을 가공 없이 조회만 할 때(A3)
  • 정제·정의 없이 파일을 올려 바로 검색하는 경우(태그 대상 아님)
  • 타 기관 데이터 결합이 핵심일 때는 A4를 함께 태그해 계약·키 매핑을 따로 드러낸다

얻는 것

  • 모델 교체와 무관하게 남는 기관 자산
  • C9·C6·B3가 같은 기준선을 재사용
  • 데이터 사전이 기관 간 표준 확산의 단위가 됨

점검표

  • 정제 전후 규모와 정제 기준이 기록되어 있는가
  • 데이터 사전(정의·단위·출처)이 있는가
  • 기준선에 버전이 있고 평가용 분할이 학습용과 분리되어 있는가
  • 데이터 등급(E5)에 맞는 가명·비식별 처리가 적용되었는가

구조 — 참여 부품

  • 원천 시스템·기록 — 가공 전 업무 기록을 내주는 출처
  • 정제·라벨링 파이프라인 — 중복 제거·결측 처리·라벨 부여·품질관리를 수행
  • 데이터 사전 — 정의·단위·출처를 문서로 고정해 소비 부품이 같은 뜻으로 쓰게 함
  • C9 평가 세트·회귀시험 — 기준선을 정답 출처로 사용
  • A2.5 비LLM 학습 모델 — 기준선으로 학습·재학습하는 소비 부품

변형

  • 학습데이터 구축형: 영상·이미지 등을 수집해 품질관리 단계(중복 제거·재라벨링·학습/검증/평가 분리)를 거쳐 학습 기준선으로 만든다.
  • RAG 코퍼스 정본화형: 법령·규정 원문을 현행 시행본 기준으로 정본화하고 조문 구조·메타데이터를 부여해 색인한다.
  • 지표 표준화형: 여러 자료원의 지표를 도메인별로 표준화하고 정의·단위·분모·결측·원본 링크를 메타데이터로 관리한다.
  • 자동 피처 파이프라인형: 수집→정제→파생 변수 생성→자동 검증→담당자 승인을 주기 실행하고 승인만 사람에게 남긴다.

A2.1 모델 서빙 · 상용 API 호출 공통 서비스

GPT·Gemini·Claude·HyperCLOVA X·Upstage 등 상용 모델 API를 서빙 계층을 거쳐 호출해 자체 인프라 없이 최신 모델 성능을 쓴다.

PAX 사례 88건이 이 부품을 쓴다

맥락

E2는 해외 상용 API(또는 국산 상용 모델 API), E1은 인터넷망·클라우드다. E5 등급이 O이거나 비식별 후 전송해도 되는 업무에 맞는다. 대민 상담(B3)·코파일럿(B1)·콘텐츠 생성(B7)에서 흔하다.

맞서는 힘(긴장)

  • 모델 성능·도입 속도 vs 데이터 반출·주권
  • 종량 과금의 초기 저비용 vs 호출량 증가 시 비용 예측 어려움
  • 벤더의 모델 개선 vs 예고 없는 품질 회귀
  • 단일 API의 단순함 vs 장애 시 서비스 중단

해법

업무 코드는 서빙 계층만 부르고, 서빙 계층이 상용 API를 호출한다. 행정망 본문이 나가는 경로 앞에는 C5 비식별 전처리를 두고, 대체 모델을 등록해 C7 폴백을 건다(§5 매트릭스 E2 해외 상용 API 행). 모델 버전을 고정하고 모델·프롬프트·설정 조합을 릴리스처럼 관리해 업데이트 전후를 C9로 비교한다. 비용이 문제면 라우팅·캐싱으로 큰 모델 호출을 줄인다. E5가 S 이상이면 이 변형 단독으로는 안 되고 A2.4 내부망 프록시를 거친다.

이럴 때 쓴다

  • 인터넷망·클라우드 환경이고 데이터 등급이 O이거나 비식별 후 전송 가능할 때
  • PoC 초기에 모델 성능을 빠르게 확인해야 할 때
  • 자체 GPU·운영 인력이 없을 때

이럴 때는 쓰지 않는다

  • E1이 폐쇄망이면 조립 오류(A2.2·A2.4로)
  • E5가 S 이상인데 내부망 프록시가 없을 때(A2.4 필수)
  • 상시 서비스인데 대체 경로를 둘 수 없을 때

얻는 것

  • 인프라 없이 최신 모델 성능
  • 빠른 PoC
  • 벤더의 지속적 개선

점검표

  • 업무 코드가 상용 API를 직접 부르지 않는가
  • 외부로 나가는 프롬프트에서 무엇이 걸러지는지 답할 수 있는가
  • API 장애 시 대체 경로가 있는가
  • 모델 버전과 호출당 비용·지연이 기록되는가

구조 — 참여 부품

  • A2 서빙 계층 — 업무 코드 대신 상용 API를 호출하고 버전·사용량을 기록
  • C5 가드레일(비식별 전처리) — 외부 전송 전 민감정보 제거
  • 상용 모델 API — 기관 밖에서 추론을 수행
  • C7 폴백 스위치 — API 장애·품질 저하 시 대체 모델·수동 처리로 전환

변형

  • 해외 상용 API: GPT·Gemini·Claude 등이다. E2 값은 해외 상용 API.
  • 국산 상용 API: HyperCLOVA X·Upstage 등 국내 사업자 API. 망·등급 조건은 해외와 같이 따진다.

X9 담당자와 함께 사라지는 도구 안티패턴

개인이 만든 도구가 부서에 퍼졌지만 라이선스·저장소·인수인계가 없어, 만든 사람의 인사이동과 함께 멈추는 함정이다.

맥락

A7 자체 제작 환경으로 태깅된 도구(PAX 557건 중 317건, 57%), 특히 개인 사용에서 부서 공유로 막 퍼지기 시작한 바이브코딩 도구.

맞서는 힘(긴장)

  • 개인의 빠른 제작 vs 조직의 유지보수 책임
  • 비공식 공유의 편의 vs 라이선스·저장소 절차
  • 현장 맞춤 vs 다른 담당자가 이해할 수 있는 구조

해법

도구가 부서에 퍼지기 시작하면 A7 산출물에 MIT·Apache 등 라이선스를 명시하고, 코드를 개인 PC가 아니라 A3 공공 깃랩 같은 공용 저장소에 등재한다. 업무 규범·프롬프트는 A9 업무 규범 스킬로 패키징해 다른 담당자가 그대로 쓸 수 있게 하고, 설치·설정·데이터 경로를 담은 인수인계 문서를 둔다. 도구를 참조 구현 레지스트리(§13)에 올려 소유를 개인에서 조직으로 옮긴다. transition.blocker에 '담당자 이동'이 적힌 과제는 이 조치를 먼저 한다.

이럴 때 쓴다

  • 개인이 만든 도구를 부서원 여러 명이 쓰는데 라이선스 표기가 없다
  • 원본 코드가 개인 PC·개인 계정에만 있다
  • 인수인계 문서·설치 절차가 없다
  • transition.blocker가 '담당자 이동'이다

이럴 때는 쓰지 않는다

  • 개인만 쓰는 도구로 부서에 퍼지지 않은 경우(개인 사용 단계는 정상)
  • A7로 만들었지만 라이선스 명시·공용 저장소 등재·인수인계가 갖춰진 경우
  • 기관 정보화 부서가 넘겨받아 운영 중인 경우

얻는 것

  • 현장 담당자가 필요한 도구를 빠르게 만든다
  • 공식 절차 없이 바로 퍼진다

점검표

  • 라이선스가 명시되어 있는가
  • 원본이 공용 저장소에 있는가
  • 만든 사람 없이 후임이 설치·실행할 수 있는 문서가 있는가
  • 개인 구독·개인 키에 의존하지 않는가

구조 — 참여 부품

  • A7 자체 제작 환경 — 도구가 태어난 곳. 라이선스 명시가 전이 조건
  • A3 공공 API 제공자(공공 깃랩) — 개인 저장소를 대체하는 공용 등재처
  • A9 업무 규범 스킬 — 암묵적 업무 규범을 패키지로 남김
  • 후임 담당자 — 인수인계 문서로 도구를 이어받는 사람

변형

  • 라이선스 미명시: 코드는 공개했지만 라이선스가 없어 타 기관이 가져다 쓸 수 없음
  • 개인 저장소형: 개인 PC·개인 계정에만 원본이 있음
  • 개인 구독 의존형: 개인 AI 구독·API 키로 돌아가 담당자가 떠나면 호출이 끊김

C8 권한 경계·킬스위치 운영 컴포넌트

AI 부품이 할 수 있는 일의 상한을 P0~P4로 못 박고, 도구별 실행 승인·읽기/쓰기 분리·속도 제한·즉시 중단 스위치를 제공한다.

PAX 사례 22건이 이 부품을 쓴다

맥락

도구를 호출하거나 시스템에 쓰는 B6 오케스트레이터, A8 MCP 서버·호스트, B8 레거시 오버레이, 처분 보조(P3) 서비스. 유형 ⑤b 데이터 에이전트, ⑨ 인수인계(접근 범위).

맞서는 힘(긴장)

  • 자동화 범위 vs 통제
  • 승인 절차의 안전 vs 이용 마찰
  • 도구 설명의 편의 vs 실제 권한과의 일치 검증 비용

해법

부품별 허용 권한 범위(P0 읽기 전용 ~ P4 자율 처분)를 정하고, 도구 목록마다 읽기/쓰기를 분리한다. 위험도가 높은 도구는 실행 전 사람 승인(C2·F6)을 받게 하고, 호출 상한(속도 제한)을 둔다. 전역 킬스위치로 즉시 중단할 수 있게 하고, 승인·실패·중단 이력을 C4에 남긴다. MCP 도구는 설명과 실제 권한이 일치하는지 A8 6축 검증으로 확인한다.

이럴 때 쓴다

  • E4 P2 이상(필수, First 관문)
  • E3 MCP·CLI 환경에서 에이전트가 도구를 호출할 때
  • B6 오케스트레이터에 상용 API를 쓰는 경우(A2 + C7 + C8 도구별 승인)
  • 유형 ⑤b-host, ⑨ 인수인계(접근 범위)

이럴 때는 쓰지 않는다

  • 도구 호출·시스템 쓰기가 없는 서술 전용 코파일럿(P1)
  • B0 결정적 도구로 AI가 행동을 고르지 않을 때

얻는 것

  • 되돌릴 수 없는 조치 방지
  • 도구 설명과 실제 권한의 불일치(X7) 예방
  • 감사 가능한 행동 기록

점검표

  • AI가 쓸 수 있는 시스템 목록을 답할 수 있는가
  • 도구별 읽기/쓰기 구분과 위험도가 있는가
  • 고위험 도구에 실행 승인이 걸려 있는가
  • 킬스위치가 있고 누가 누를 수 있는지 정해져 있는가
  • 도구 설명과 실제 권한이 일치하는가

구조 — 참여 부품

  • 권한 정책 — 부품·도구별 허용 범위(P0~P4)와 읽기/쓰기 구분
  • A8 MCP 서버·호스트 — 도구 설명과 실제 권한의 일치 검증 대상
  • F6 에이전트 행동 검토·확인 — 실행 전 이용자 승인 화면
  • 킬스위치 — 전역 즉시 중단
  • C4 감사 로그·지표 — 승인·실패·롤백·중단 이력

변형

  • 읽기 전용·쓰기 배제: 도구 세트를 읽기 전용으로 한정하거나 쓰기 기능을 설계에서 배제
  • 도구별 위험도·실행 승인: 도구마다 위험도를 평가하고 고위험 도구는 실행 전 승인
  • 판정 필드 비도달 설계: AI가 판정·업무 필드에 쓸 수 없게 코드 수준으로 분리
  • 속도 제한: 도구 호출 상한(Rate Limiter)
  • 킬스위치: 전역 즉시 중단과 기존 절차 전환

참조 구현 예

C4 감사 로그·지표 운영 컴포넌트

처리 건마다 흔적을 적재하고 수정률·처리시간·자동처리율·가용성을 집계해, '지난달 수정률'을 숫자로 말할 수 있게 한다.

PAX 사례 16건이 이 부품을 쓴다

맥락

AI 산출물이 업무 결과에 영향을 주는 모든 B 부품. 특히 C2·C6·C7을 붙이려는 서비스, E4 P2 이상, 기관 공식으로 전이하려는 자생 도구.

맞서는 힘(긴장)

  • 기록의 완전성 vs 저장·개인정보 부담
  • 지표의 단순성 vs 업무 실상 반영
  • 로그 적재 vs 실제로 지표를 보고 조치하는 조직 습관

해법

모든 부품의 이벤트(요청·응답·검토 결정·수정·전환·오류)를 건 단위로 적재한다. 로그 집계, 성능 지표(수정률·처리시간·자동처리율), 분산 추적(에이전트 호출 연쇄), 헬스체크(도구·모델 가용성)의 네 하위 항목으로 나눠 구현한다. 지표는 대시보드나 정기 보고로 실제로 보고, C2·C6·C7이 이 지표를 읽어 판단하게 한다. 개인정보가 들어가는 로그는 E5 등급에 맞춰 보관 범위를 정한다.

이럴 때 쓴다

  • C2·C6·C7 중 하나라도 붙이려 할 때(이들이 C4를 읽는다)
  • E4 P2 이상
  • 유형 ② 접수·심사, ③ 현장 감시, ⑤b 데이터 에이전트(호출 추적), ⑧ 취합·변환의 기관 전이

얻는 것

  • 성과를 숫자로 말할 수 있음
  • C2·C6·C7의 판단 근거
  • 사고 시 원인 추적

점검표

  • 건별 로그가 적재되는가
  • 수정률·처리시간 등 지표가 정의되어 있는가
  • 실증 기간 지표가 실제로 집계되었는가
  • C2·C6·C7이 읽는 지표가 C4에서 나오는가

  • 감사 대시보드 — 지표를 사람이 보고 조치하는 화면

S5 계획 후 실행·코드 후 실행 보안 패턴

신뢰 불가 데이터를 읽기 전에 도구 호출 계획이나 프로그램을 고정하고 정책으로 검증해, 도구 출력이 새 행동을 끼워 넣지 못하게 한다.

PAX 사례 1건이 이 부품을 쓴다

맥락

도구 호출 또는 시스템 쓰기가 있는 구조(R6)에서 계획을 미리 정할 수 있는 정형 업무. 데이터 조회·분석 에이전트(유형 ⑤, 5b-host), 그리고 '오늘 접수 건을 조회해 담당자에게 통지'하는 식의 접수·통지 자동화(유형 ②). 카탈로그 등재 상태는 후보(PAX 557건 중 1건).

맞서는 힘(긴장)

  • 행동 집합의 증명 가능한 고정 vs 중간에 계획을 바꿔야 하는 탐색 과제
  • 정책 검증의 엄격함 vs 계획 작성 실패율
  • 행동 고정 vs 인자 조작(도구 출력이 인자를 바꾸는 것)은 남음

해법

이용자 지시를 받아 신뢰 불가 데이터를 읽기 전에 도구 호출 목록 [tool1(…), tool2(…)] 또는 실행 코드를 먼저 확정한다. 고정된 계획은 제어면(C8 도구별 권한)이 허용 도구·권한·파괴적 행동·사람 승인 필요 여부를 규칙으로 검증한 뒤에만 실행한다. 도구 출력은 인자 값을 채울 수는 있지만 계획에 없는 행동을 추가할 수 없다. 코드 후 실행이면 코드는 S9 샌드박스에서 돌린다. 인자 조작까지 막으려면 S6을 함께 둔다.

이럴 때 쓴다

  • 데이터 조회·분석 에이전트(유형 ⑤)의 필수 부품(S1과 함께)
  • 5b-host(에이전트 호출자) 필수 S5 또는 S6(R18)
  • 접수·통지 자동화처럼 계획을 미리 정할 수 있는 정형 업무
  • 내부 문서 코파일럿(유형 ④)이 행정망에 쓰기를 할 때(권장)

이럴 때는 쓰지 않는다

  • 중간에 계획을 바꿔야 하는 탐색 과제
  • 도구 호출·시스템 쓰기가 없는 서술 전용 LLM(R6)
  • 도구 출력 속 인자 조작이 핵심 위협일 때 S5만으로는 부족 — S6 필요

얻는 것

  • 간접 인젝션에 의한 행동 변경에 증명 가능한 저항
  • 권한 상승 차단
  • 계획이 사전에 보이므로 감사·승인이 쉬움

점검표

  • 외부 데이터를 읽기 전에 계획이 확정되는가
  • 계획이 실행 전에 정책으로 검증되는가
  • 도구 출력이 계획에 없는 도구 호출을 유발할 수 없는가
  • 파괴적 행동에 사람 승인이 걸려 있는가

구조 — 참여 부품

  • 계획 LLM — 신뢰 불가 데이터를 읽기 전에 계획·코드를 작성
  • C8 권한 경계(제어면) — 허용 도구·권한·파괴적 행동·사람 승인 여부를 규칙으로 검증
  • C3 상태 머신 — 계획 단계 진행과 종료 상태 관리
  • S9 임시 샌드박스 — 코드 후 실행 시 코드 격리 실행
  • 실행기 — 검증된 계획만 실행하고 도구 출력은 인자 값으로만 사용

변형

  • 계획 후 실행: 도구 호출 목록을 고정하고 순서대로 실행
  • 코드 후 실행: LLM이 프로그램을 먼저 쓰고 샌드박스에서 실행
  • 에이전틱 제어면: LLM이 쓴 JSON 실행계획을 서버가 비신뢰 입력으로 보고 권한·도구·인자를 규칙으로 재검증한 뒤 허용목록 도구만 실행

S6 격리 LLM·맵리듀스 보안 패턴

도구를 가진 권한 LLM은 신뢰 불가 데이터를 읽지 않고, 데이터를 읽는 격리 LLM은 도구가 없게 나눈 뒤 결과를 형식 제약이나 기호 참조로만 넘긴다.

맥락

제출 서류(PDF·HWPX·이미지)를 읽어 판정하는 접수·심사 자동화(유형 ②), 대상 문서가 점검기를 속일 수 있는 대조·점검(유형 ⑦), 부서별 제출 파일을 취합하는 자동화(유형 ⑧). 모두 도구 호출 또는 시스템 쓰기가 있는 구조(R6)를 전제로 한다. 카탈로그 등재 상태는 후보(PAX 557건 중 0건).

맞서는 힘(긴장)

  • 증명 가능한 격리 vs 호출 수 증가
  • 형식 제약(불리언·숫자·정규식)의 안전성 vs 풍부한 판정 사유 전달
  • 기호 참조 설계 난이도 vs 권한 LLM의 유연성

해법

권한 LLM(도구 보유)과 격리 LLM(도구 없음)을 분리한다. 문서마다 격리 LLM 인스턴스를 띄워(맵) 요건 충족 여부처럼 형식이 제약된 값만 내게 하고, 비-LLM 규칙으로 합친다(리듀스). 권한 LLM은 격리 LLM의 결과를 $VAR 같은 기호 참조로만 다루고, 실제 값은 비-LLM 오케스트레이터가 실행 시 치환한다. 형식 제약 검증은 C9·스키마 검증으로 강제하고, OCR·파싱 같은 실행은 S9에 둔다. 악성 문서는 자기 판정만 속일 수 있을 뿐 다른 문서나 도구 호출에 영향을 줄 수 없다.

이럴 때 쓴다

  • 접수·심사 자동화(유형 ②)의 정석 — 필수 부품
  • 대조·점검 도우미(유형 ⑦)에서 대상별 격리(S4의 대안)
  • 취합·변환 자동화(유형 ⑧)에서 파일별 격리(권장)
  • 5b-host 필수 S5 또는 S6(R18)
  • S5로 막지 못하는 인자 조작이 위협일 때

이럴 때는 쓰지 않는다

  • 도구 호출·시스템 쓰기가 없는 서술 전용 LLM(R6)
  • 문서 간 교차 참조가 판정의 핵심이라 문서별 격리가 불가능할 때 — S5나 C1 사람 검토로 보완
  • 보안 목적 없이 판정-확정 분리만 있는 구조는 B′9(R11), 다만 신뢰 불가 입력 격리가 함께 있으면 둘 다 태그(R27)

얻는 것

  • 간접 인젝션 전파에 증명 가능한 저항
  • 문서 간 교차 오염 차단
  • 권한 상승 차단
  • 판정이 규칙 집계라 설명·재현이 쉬움

점검표

  • 도구를 가진 LLM이 신뢰 불가 데이터를 직접 읽지 않는가
  • 격리 LLM 출력이 형식 제약 값으로만 전달되는가
  • 문서별로 격리되어 한 문서가 다른 문서 판정에 영향을 줄 수 없는가
  • 집계가 LLM이 아닌 규칙으로 이루어지는가

구조 — 참여 부품

  • 격리 LLM(문서별) — 도구 없이 한 문서만 읽고 불리언·숫자·정규식 형식의 값만 출력
  • 비-LLM 집계기 — 문서별 판정을 규칙으로 합침(리듀스)
  • 권한 LLM — 도구를 가지되 신뢰 불가 데이터를 읽지 않고 기호 참조만 조작
  • 비-LLM 오케스트레이터 — 실행 시 기호 참조를 실제 값으로 치환
  • C9 평가 세트·형식 검증 — 격리 LLM 출력의 형식 제약 검증

변형

  • 이중 LLM(Dual LLM): 권한 LLM과 격리 LLM 두 역할로 나누고 기호 참조로 연결(Willison)
  • LLM 맵리듀스: 문서마다 격리 인스턴스를 띄우고 규칙으로 집계
  • 다중 에이전트 분할: 에이전트별로 읽는 데이터와 가진 도구를 분리
  • 수치·문장 분리형: 수치는 예측 모듈만 산출하고 LLM은 도구 결과를 설명만 하는 구조

관련 부품

X11 처음부터 멀티에이전트 안티패턴

하위 작업이 분리되지 않는데 에이전트를 여럿 두어 조정 비용만 늘리는 함정이다. 단일 에이전트로 되돌리면 더 잘 되는 경우가 많다.

맥락

B6 오케스트레이터를 설계하거나 B′3 병렬·B′4 계층 분해를 도입하려는 과제, 특히 단일 에이전트 구성을 시도해 본 기록이 없는 과제.

맞서는 힘(긴장)

  • 역할 분리의 설계 명료함 vs 에이전트 간 조정 비용
  • 병렬 처리의 지연 단축 vs 결과 통합의 복잡도
  • 기술적 인상 vs 단순한 구조의 품질·비용

해법

B′ 원형 선택 규칙대로 단일 에이전트(B′1 순차, B′7 ReAct 도구 루프)에서 시작한다. 하위 작업이 진짜로 분리되거나, 병렬이 지연을 의미 있게 줄이거나, 컨텍스트 창이 부족할 때만 B′3 병렬·B′4 계층 분해로 승급한다. 승급 판단은 C9 평가 세트로 단일 구성과 비교해 내린다. 에이전트끼리 충돌·중복이 관측되면 B′4 감독자 계층이나 B′2 라우터로 정리하거나 단일 에이전트로 후퇴한다. B6 태그는 R2 요건(복수 LLM 역할 + 도구 호출 루프 + AI가 계획·도구를 선택)을 만족할 때만 붙인다.

이럴 때 쓴다

  • 에이전트가 여럿인데 하위 작업의 입력·출력이 서로 얽혀 독립적으로 돌지 않는다
  • 단일 에이전트 구성과 비교한 기록이 없다
  • 에이전트끼리 충돌·중복·재작업이 관측된다
  • 호출 비용·지연이 에이전트 수에 비례해 늘었는데 품질 개선 근거가 없다

이럴 때는 쓰지 않는다

  • 하위 작업이 진짜로 분리되고(서로 다른 데이터·도구), 병렬이 지연을 줄이거나 컨텍스트가 부족해 승급한 경우
  • R2 요건을 만족하는 B6로, 단일 구성보다 나음이 C9로 확인된 경우
  • 고정 순서 파이프라인을 B′1으로 정직하게 서술한 경우

얻는 것

  • 구조도가 명료하고 기술적으로 인상적이다
  • 역할별로 프롬프트를 나눠 관리하기 쉬워 보인다

점검표

  • 하위 작업이 서로 다른 데이터·도구로 독립적으로 도는가
  • 단일 에이전트 구성과 C9로 비교한 기록이 있는가
  • 승급 사유가 문서에 적혀 있는가
  • 에이전트 사이 충돌을 정리하는 감독자·라우터가 있는가

구조 — 참여 부품

  • B′1 순차 파이프라인 — 시작점이 되는 단일 흐름
  • B′7 ReAct 도구 루프 — 단일 에이전트 도구 사용의 기본형
  • B′4 계층 분해·감독자 — 하위 작업이 분리될 때만 승급하는 형태
  • C9 평가 세트·회귀시험 — 단일 vs 멀티 구성을 같은 자로 비교

변형

X13 도구 출력이 지시가 되는 에이전트 안티패턴

검색 결과·첨부·API 응답을 읽은 모델이 그 안의 문장을 새 명령으로 받아 도구를 부르는 구조를, 탐지 필터 하나로 지키려는 함정이다.

맥락

E4가 P2 이상(시스템 쓰기·처분 보조)이면서 민원 입력·제출 서류·웹 문서·타 기관 API 응답 같은 신뢰 불가 입력을 읽는 에이전트. 특히 B6·5b 데이터 에이전트.

맞서는 힘(긴장)

  • 범용 에이전트의 유연성 vs 신뢰 불가 입력 뒤의 행동 제약
  • 단일 LLM 구조의 단순함 vs 격리·계획 고정의 설계 비용
  • 탐지 필터의 손쉬움 vs 증명 가능한 보증

해법

과제의 AI가 읽는 입력 중 기관 밖에서 작성된 것을 untrusted_inputs로 나열하고, §4.2 신뢰 불가 입력 규칙대로 S4 행동 선택기(미리 정한 행동 중 선택만, 결과가 LLM으로 돌아가지 않음), S5 계획 후 실행(외부 데이터를 읽기 전에 도구 호출 계획을 고정), S6 격리 LLM(도구 있는 LLM은 외부 데이터를 읽지 않고, 읽는 LLM은 도구가 없음) 중 하나를 갖춘다. S3 컨텍스트 방화벽과 S8 독립 검증기는 보조로 붙이되 S8만으로는 규칙을 충족하지 못한다. C8 승인 게이트도 신뢰 불가 입력 규칙의 대체 통제로 인정되지 않는다(R6). 그 전 단계에서는 E4를 P0~P1 읽기·산출물 범위에 묶어 두는 것이 곧 보안이다.

이럴 때 쓴다

  • E4가 P2 이상이고 untrusted_inputs가 비어 있지 않은데 S4·S5·S6이 모두 없다(신뢰 불가 입력 규칙 위반)
  • 외부 문서를 읽는 LLM이 같은 컨텍스트에서 쓰기 도구를 호출할 수 있다
  • 인젝션 대책이 탐지 필터·프롬프트 경고문뿐이다
  • 읽은 텍스트 중 어떤 것이 어떤 도구를 부를 수 있는지 답하지 못한다

이럴 때는 쓰지 않는다

  • E4가 P0~P1로 읽기·산출물 생성에만 묶여 도구 호출·시스템 쓰기가 없는 경우(S4·S5·S6 판정 전제 불충족, R6)
  • S4·S5·S6 중 하나가 구조적으로 갖춰진 경우(보안 목적 서술이 없어도 구조가 일치하면 충족)
  • AI가 읽는 입력이 모두 기관 내부에서 작성된 경우

얻는 것

  • 단일 LLM 범용 에이전트로 구조가 단순하다
  • 새 입력·새 도구를 자유롭게 붙인다

점검표

  • untrusted_inputs가 나열되어 있는가
  • 신뢰 불가 입력을 읽은 LLM이 쓰기 도구를 직접 부를 수 없는가
  • S4·S5·S6 중 하나가 구조로 구현되어 있는가
  • S8 탐지를 유일한 방어로 두지 않았는가

구조 — 참여 부품

  • S4 행동 선택기 — LLM이 정해진 행동 중 선택만 하게 제약
  • S5 계획 후 실행·코드 후 실행 — 외부 데이터를 읽기 전에 도구 계획 고정
  • S6 격리 LLM·맵리듀스 — 읽는 LLM과 도구 있는 LLM을 분리
  • S8 독립 검증기·이중 심판 — 보조 탐지. 단독으로는 보증이 아님

변형

  • 문서 속 지시: 첨부·제출 서류 안의 문장대로 에이전트가 도구를 호출
  • API 응답 오염: 타 기관 API·웹 검색 결과에 섞인 지시가 후속 행동을 바꿈
  • 탐지 단독 방어: 인젝션 탐지 필터(S8) 하나만 두고 구조적 제약이 없음

X14 재생할 수 없는 사고 안티패턴

잘못된 처분이 나갔는데 그때의 프롬프트·검색·도구 호출 순서를 아무도 복원하지 못하는 함정이다. 지표는 있는데 기록이 없다.

맥락

해법

X7 도구 설명 ≠ 실제 권한 안티패턴

MCP 도구 설명은 '조회'인데 코드는 쓰기·실행 권한을 가져, 설명만 믿고 도구를 부르는 에이전트가 의도하지 않은 변경을 일으키는 함정이다.

맥락

E3 MCP·CLI 설정 환경에서 A8 MCP 서버·호스트를 만들거나 가져다 쓰는 과제. 특히 업무 시스템 MCP(쓰기, P2)와 공공데이터 MCP(읽기, P0)가 한 호스트에 함께 연결된 경우.

맞서는 힘(긴장)

  • 빠른 MCP 래핑 vs 도구별 권한 분리
  • 도구 하나로 묶는 편의 vs 읽기/쓰기 분리의 운영 부담
  • 에이전트 자율 호출 vs 실행 전 승인

해법

A8의 각 도구에 실제 권한 수준(P0~P4)을 설명과 함께 명시하고, C8 권한 경계로 읽기 전용 도구와 쓰기 도구를 서로 다른 서버·인증으로 분리한다. 쓰기·실행 도구는 도구별 실행 승인과 호출 상한, 킬스위치를 둔다. 반입하는 MCP 서버는 S11 인제스천·공급망 검증에서 PAX 6축(권한 표면·비밀·공급망·위생·인젝션·데이터 흐름)을 통과해야 활성화한다. 사람에게는 F6 에이전트 행동 검토·확인으로 실행 전 무엇을 할지 보여 주고, 승인·실패는 C4에 남긴다.

이럴 때 쓴다

  • MCP 도구 설명과 실제 권한(쓰기·삭제·발송)이 다르다
  • 읽기와 쓰기 도구가 같은 서버·같은 인증 토큰을 쓴다
  • 도구별 권한 수준·실행 승인이 문서에 없다
  • 6축 검증에서 권한 표면이 '주의'로 나왔다

이럴 때는 쓰지 않는다

  • 읽기 전용 MCP로 설계되어 쓰기 기능이 배제된 경우
  • 쓰기 도구가 있지만 설명에 부수 효과가 명시되고 C8 실행 승인이 있는 경우
  • MCP가 아닌 결정적 스크립트로 권한이 코드에 고정된 경우

얻는 것

  • 기존 API를 빠르게 에이전트 도구로 만든다
  • 도구 수가 적어 관리가 쉬워 보인다

점검표

  • 모든 도구의 설명에 실제 권한과 부수 효과가 적혀 있는가
  • 읽기와 쓰기 도구가 서로 다른 인증을 쓰는가
  • 쓰기 도구에 실행 전 승인이 있는가
  • 반입 MCP가 6축 검증을 통과했는가

구조 — 참여 부품

  • A8 MCP 서버·호스트 — 도구 설명과 실제 권한이 일치해야 하는 곳
  • C8 권한 경계·킬스위치 — 읽기/쓰기 분리, 도구별 승인

맥락

공공데이터·업무 시스템을 MCP로 감싸는 과제, MCP 서버를 사례 단위로 등록하는 커뮤니티 아카이브, 'MCP N종 구축'을 성과 지표로 둔 과제.

맞서는 힘(긴장)

  • 보고하기 쉬운 개수 vs 측정하기 어려운 업무 전환
  • 서버 제공자 책임 vs 호스트·업무 쪽 활용 책임
  • 빠른 확장 vs 서버마다의 검증·유지보수

해법

서버마다 그것을 호출하는 B 업무 컴포넌트와 업무 산출물을 연결해 '어느 업무의 어떤 산출물에 쓰이는가'를 적는다. C4 감사 로그·지표로 호출 수·호출 주체·업무 건을 집계하고, transition.stage와 파급력 척도(M1~M5)로 전환 경로를 추적한다(PAX: 도구 수보다 전환 경로를 추적). R18대로 서버 제공자 사례(5b-server)와 호스트 통합 사례(5b-host)를 나눠 서버 쪽은 A8·S11·문서화된 스키마를, 호스트 쪽은 C4·F1·S5|S6을 갖춘다. 호출되지 않는 서버는 레지스트리에서 정리한다.

이럴 때 쓴다

  • 성과가 MCP 서버·도구 개수로 보고된다
  • 호출 수·호출 주체·업무 건 지표가 없다
  • 서버를 호출하는 업무 산출물이 서술되지 않는다
  • 흐름이 바뀌었다는 서술 없이 'MCP 기반 전환'을 주장한다

이럴 때는 쓰지 않는다

  • 단일 MCP 서버를 만들어 A8·S11·문서화된 스키마를 갖춘 5b-server 사례(R18). 서버 제공 자체가 사례 단위이므로 개수를 성과로 주장하지 않으면 함정이 아니다
  • MCP 서버 여러 개를 호스트 업무에 연결하고 호출 지표를 C4로 집계한 경우

얻는 것

  • 성과를 개수로 명확히 보고할 수 있다
  • 공공 API를 빠르게 에이전트 도구로 공개한다

점검표

  • 서버마다 호출하는 업무 산출물이 적혀 있는가
  • 서버별 월 호출 수와 호출 주체를 말할 수 있는가
  • 호출되지 않는 서버를 정리하는 절차가 있는가
  • 성과 지표가 개수가 아니라 업무 전환으로 잡혀 있는가

구조 — 참여 부품

  • A8 MCP 서버·호스트 — 개수로 세어지는 도구 인터페이스
  • C4 감사 로그·지표 — 호출 수·호출 주체·업무 건을 집계하는 빠진 부품
  • B 업무 컴포넌트 — 서버를 실제로 호출해 산출물을 만드는 쪽
  • S11 인제스천·공급망 검증 — 서버 제공자 쪽 필수 검증(R18)

변형

  • 개수 성과형: 'MCP N종 구축'이 과제의 주요 성과 지표
  • 호스트 없는 서버: 서버만 공개하고 어떤 호스트·업무에서 쓰이는지 기록이 없음
  • 방치 서버: 원천 API 변경 후 갱신되지 않아 호출이 실패하는 서버가 목록에 남음

관련 부품

C4 대체 — 서버별 호출 지표 · A8 발생 자리 — 개수로 세어지는 도구 인터페이스 · B6 교정 목표 — 도구를 호출해 산출물을 만드는 업무 컴포넌트 · S11 서버 제공자 필수 — 반입·공급망 검증(R18) · X1 이웃 안티패턴 — 탑재·개수를 성과로 세는 같은 뿌리
