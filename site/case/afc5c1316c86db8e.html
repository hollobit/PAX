판정 근거

온나라 문서시스템 화면을 저채도 다크모드와 벡터 아이콘으로 개선하는 크롬·엣지 확장으로, API가 닫힌 표준 시스템 화면 위에 브라우저 확장으로 덧입히는 정의에 정확히 부합해 B8 레거시 오버레이로 분류했다. AI를 전혀 쓰지 않는 순수 UI 개선이며 폐쇄망에서 완전히 동작하도록 설계됐다. 전 공무원이 매일 보는 화면의 사용성 문제를 실무자가 직접 고친 사례로, 데이터 쓰기·조회 권한 변경 없이 시각적 표현만 바꾸므로 P0 읽기 전용으로 판정했다.

구현 가이드

주 패턴 B8 레거시 오버레이을 구현할 때

구현 단계

  1. 대상 화면과 반복 조작을 정하고, 확장이 읽을 DOM 요소와 파일을 목록으로 적는다.
  2. 권한을 P0~P1에 묶고, 쓰기 조작이 필요하면 C3 되돌림과 F6 확인을 먼저 설계한다.
  3. 요약을 붙이면 로컬 모델(A2.2)로 처리해 문서가 PC 밖으로 나가지 않게 하고 C5를 둔다.
  4. 화면 텍스트를 신뢰 불가 입력으로 보고 S3 구역 분리를 적용한다.
  5. 시스템 개편 시 점검 절차와, 정식 API·MCP가 열리면 걷어낼 조건을 문서로 남긴다.

점검표

  • 권한이 읽기·산출물 생성(P0~P1)에 묶여 있는가
  • 문서가 PC 밖으로 나가지 않는가
  • 시스템 개편 시 점검 절차가 있는가
  • 정식 연계가 열리면 걷어낼 조건이 적혀 있는가

환경 조건

E1 행정망이 필수 조건이다. E2는 로컬 오픈웨이트(온나라 sAIde: Ollama). E4는 P0~P1에 묶어야 하며, P2 이상이면 C3 되돌림이 필요하나 DOM 조작은 원자성이 없다. 신뢰 불가 입력 + P2 이상이면 DOM 텍스트를 전부 신뢰 불가로 보고 S4 행동 선택기가 필요하다(§5 매트릭스).

주의할 점

  • DOM 의존으로 시스템 개편에 취약(전이 차단: 레거시 미연동)
  • DOM 조작은 원자성이 없어 쓰기 시 되돌림이 어려움
  • 화면 텍스트를 통한 인젝션 위험
  • 개인 도구가 담당자와 함께 사라질 위험(X9)

기본 배선 예

B8 → A2.2 (로컬 요약) → A10 → D8.2 · A8 (정식 MCP가 열리면 B8 대체)

피해야 할 안티패턴

  • X9 담당자와 함께 사라지는 도구 개인이 만든 도구가 부서에 퍼졌지만 라이선스·저장소·인수인계가 없어, 만든 사람의 인사이동과 함께 멈추는 함정이다. 대처: 도구가 부서에 퍼지기 시작하면 A7 산출물에 MIT·Apache 등 라이선스를 명시하고, 코드를 개인 PC가 아니라 A3 공공 깃랩 같은 공용 저장소에 등재한다. 업무 규범·프롬프트는 A9 업무 규범 스킬로 패키징해 다른 담당자가 그대로 쓸 수 있게 하고, 설치·설정·데이터 경로를 담은 인수인계 문서를 둔다. 도구를 참조 구현 레지스트리(§13)에 올려 소유를 개인에서 조직으로 옮긴다. transition.blocker에 '담당자 이동'이 적힌 과제는 이 조치를 먼저 한다.

PAX 사례 13건이 이 부품을 쓴다

맥락

행정망의 표준 업무 시스템을 쓰는 담당자가 개인·부서 단위로 만든 도구가 여기에 든다. 문서가 PC 밖으로 나가면 안 되므로 로컬 모델과 짝을 이룬다. PAX 557건에서 13건이 확인됐다.

맞서는 힘(긴장)

  • 즉시 도입 vs 시스템 개편에 따른 취약성(DOM 의존)
  • 사용자 세션 공유의 편의 vs 권한 경계
  • 요약 기능 추가 vs 문서 외부 유출 금지

해법

브라우저 확장·사이드패널이 담당자 로그인 세션 안에서 화면 DOM과 다운로드 파일을 읽어 통합 검색, 일괄 다운로드, 원클릭 이동을 제공한다. 요약·분석이 필요하면 로컬 오픈웨이트 모델(A2.2)로 처리해 문서가 PC 밖으로 나가지 않게 한다. 권한은 P0~P1(읽기·산출물)에 묶고, 쓰기 조작이 있으면 C3 되돌림을 둔다. 화면 텍스트는 모두 신뢰 불가 입력으로 보고 S3·S4를 적용하며, 표준 시스템에 정식 API·MCP(A8)가 열리면 이 부품을 걷어낸다.

이럴 때 쓴다

  • API가 닫힌 표준 시스템 위에서 반복 조회·다운로드가 병목일 때
  • 행정망에서 문서를 PC 밖으로 내보낼 수 없을 때
  • 정식 연계가 열리기 전 과도기 도구가 필요할 때

이럴 때는 쓰지 않는다

  • 표준 시스템에 정식 API·MCP가 이미 있을 때(A8로 연결)
  • 화면 조작으로 시스템에 쓰기를 해야 하는데 되돌림을 보장할 수 없을 때
  • 독립 화면에서 파일을 처리하는 도구일 때(B0)

얻는 것

  • 표준 시스템을 고치지 않고 즉시 도입
  • 행정망에서 로컬 완결 가능
  • 현장 반복 조작 제거

점검표

  • 권한이 읽기·산출물 생성(P0~P1)에 묶여 있는가
  • 문서가 PC 밖으로 나가지 않는가
  • 시스템 개편 시 점검 절차가 있는가
  • 정식 연계가 열리면 걷어낼 조건이 적혀 있는가

구조 — 참여 부품

  • 브라우저 확장·사이드패널 — 화면 위에 기능을 덧입힘
  • A2.2 주권형 온프레미스 모델 — PC 안에서 요약·분석
  • A10 문서 형식 어댑터 — 첨부 파싱
  • C5 가드레일 필터 — 민감정보 처리
  • 표준 업무 시스템 — 손대지 않는 원 시스템

변형

  • 검색·이동형: AI 없이 통합 검색·원클릭 이동·일괄 다운로드를 제공한다(Ready)

  • 무예산 제작 vs 보안 검토·기관 공식화 절차

해법

기관 인력이 AI 코딩 에이전트·저작도구·오픈소스로 직접 만들되, 처음부터 전이를 전제로 한다. 설정·데이터(연락처·업무분장 등)는 코드 밖 파일로 빼 비개발자도 고치게 하고, 작업 지시서 자체를 코딩 에이전트가 수행할 프롬프트로 설계해 제작 절차를 남긴다. MIT·Apache 등 라이선스를 명시하고 공공 깃랩(A3)이나 혁신24 자료실에 등재해 담당자가 바뀌어도 이어지게 한다. 실사용 건수로 성과를 재 기관 공식으로 올린다.

이럴 때 쓴다

  • 반복 업무를 줄이는 소규모 도구를 빠르게 만들 때
  • 용역 없이 작은 수정을 계속해야 할 때
  • 유형 8 취합·변환 자동화

이럴 때는 쓰지 않는다

  • P2 이상 시스템 쓰기·처분이 걸려 보안 검토·통제 부품이 먼저 필요한데 이를 갖출 수 없을 때
  • 라이선스·저장소·인수인계를 정할 수 없어 전이가 불가능할 때(X9 위험)

얻는 것

  • 제작 속도와 현장 적합성
  • 내부 유지보수 역량 축적
  • 무예산·소예산 제작

점검표

  • 라이선스가 명시되어 있는가
  • 저장소가 개인 PC가 아닌 공유 위치에 있는가
  • 담당자가 바뀌어도 고칠 수 있는 문서·설정 분리가 있는가
  • 실사용 지표가 있는가

구조 — 참여 부품

  • 업무 담당자 — 요구를 알고 직접 만드는 제작자
  • AI 코딩 에이전트·저작도구 — 코드·화면·워크플로 생성
  • A3 공공 깃랩·자료실 — 등재처 — 담당자 이동 후에도 이어지게
  • A9 업무 규범 스킬 — 제작 규범·지시서를 재사용 가능한 형태로

변형

  • 비개발자 바이브코딩: 교육 후 비개발 직원이 AI 코딩으로 웹앱을 만들고 실사용 지표까지 잰다.
  • 용역 탈피 단계형: 1단계는 전문기업과, 2단계는 직원이 도구를 대여해 라벨링·학습·개발을 직접 한다.
  • 오픈소스 조립형: n8n·FastAPI·Qdrant·LM Studio 등 오픈소스로 워크플로를 직접 조립하고 설정을 공유한다.
  • 사람+에이전트 작업 단위형: 작업 지시서를 코딩 에이전트 입력 프롬프트로 설계해 '사람 1인 + 에이전트 1세션' 단위로 일한다.

참조 구현 예

  • PAX 145a534a79c6fc53 — 공무원 1인 개발 도구가 혁신24 자료실로 여러 기관에 확산(§13 A7)

관련 부품

D8.0 기타·범용 서비스 블록

동작 키워드로 판정되지 않는 내부 운영 도구(범용 플랫폼·에이전트 개발 환경·교육)를 담는 블록이다. 다음 판에서 하위 블록을 추가할 후보군이다.

PAX 사례 45건이 이 부품을 쓴다

맥락

국민 접점이 없고 D8.1~D8.10의 어느 동작 키워드에도 걸리지 않는 내부 도구. PAX 45건. 범용 플랫폼, 에이전트 개발 환경, 교육·학습 도구, AI 런타임 없는 행정정보시스템(R24) 등. 업무 영역별 PAX 건수(557건 태깅): 공통·범용 26, 문서·기안 4, 기획·정책 4, 시설·안전 3, 인사·복무 3, 감사·법무 2, 데이터·통계 2, 회계·정산 1.

맞서는 힘(긴장)

  • 분류 완결성 vs 억지 분류로 인한 블록 의미 희석
  • 범용 도구의 넓은 재사용성 vs 업무 산출물 불명확(X8·X1 위험)
  • 후보군 보존 vs 카탈로그 세분화 과잉

해법

먼저 동작 키워드 우선순위를 끝까지 적용해 D8.1~D8.10 중 하나로 판정되는지 확인한다. 어느 것에도 걸리지 않을 때만 D8.0에 두고, 카탈로그 피드백(missing_patterns)에 반복 구조를 기록한다. 범용 도구는 그 자체보다 그것이 어느 업무 산출물로 이어지는지가 중요하므로, 대표 사용 시나리오를 하나 골라 해당 하위 블록의 조립 템플릿으로 설계를 점검한다. AI 런타임이 없는 행정정보시스템은 유형 0 기타·X1 표기로 따로 표시한다(R24).

이럴 때 쓴다

  • 동작 키워드 우선순위를 끝까지 적용해도 D8.1~D8.10 어디에도 걸리지 않을 때
  • 범용 플랫폼·개발 환경·교육처럼 특정 업무 동작이 없을 때

이럴 때는 쓰지 않는다

  • 하나라도 동작 키워드가 걸리면 그 하위 블록
  • 국민 접점이 있으면 D1~D7
  • 범용 도구라도 대표 PoC가 특정 업무 산출물을 내면 그 산출물의 블록(R1)

얻는 것

  • 억지 분류를 피해 하위 블록 의미 보존
  • 새 하위 블록 후보군 확보

점검표

  • 우선순위를 끝까지 적용했는가
  • 대표 업무 산출물이 무엇인지 적혀 있는가
  • 반복 구조가 피드백으로 기록되었는가

구조 — 참여 부품

  • 공직자(개발자·학습자) — 범용 도구를 써서 자기 업무 도구를 만들거나 배움
  • B6 도구 호출 에이전트 — 범용 에이전트·멀티에이전트 프레임워크
  • B0 결정적 도구 — AI 런타임 없는 범용 플랫폼·행정시스템
  • A7 자체 제작 환경 — 기관 인력이 직접 제작하는 환경

변형

  • 범용 에이전트·멀티에이전트 프레임워크: 특정 업무에 묶이지 않는 에이전트 개발 환경(DevEval Agents).
  • 교육·학습 도구: AI 활용 교육, 챔피언 인증 학습관리 등.
  • AI 무관 행정정보시스템: AI 런타임이 없는 순수 행정시스템. 유형 0 기타, X1 명시(R24).

참조 구현 예

  • DevEval Agents — 카탈로그 D8.0 카드 예: ODA 사업평가 멀티 에이전트 프레임워크
  • 정부 지원사업 전수조사 에이전트 스킬 ir-search — 카탈로그 D8.0 카드 예

관련 부품

X9 담당자와 함께 사라지는 도구 안티패턴

개인이 만든 도구가 부서에 퍼졌지만 라이선스·저장소·인수인계가 없어, 만든 사람의 인사이동과 함께 멈추는 함정이다.

맥락

A7 자체 제작 환경으로 태깅된 도구(PAX 557건 중 317건, 57%), 특히 개인 사용에서 부서 공유로 막 퍼지기 시작한 바이브코딩 도구.

맞서는 힘(긴장)

  • 개인의 빠른 제작 vs 조직의 유지보수 책임
  • 비공식 공유의 편의 vs 라이선스·저장소 절차
  • 현장 맞춤 vs 다른 담당자가 이해할 수 있는 구조

해법

도구가 부서에 퍼지기 시작하면 A7 산출물에 MIT·Apache 등 라이선스를 명시하고, 코드를 개인 PC가 아니라 A3 공공 깃랩 같은 공용 저장소에 등재한다. 업무 규범·프롬프트는 A9 업무 규범 스킬로 패키징해 다른 담당자가 그대로 쓸 수 있게 하고, 설치·설정·데이터 경로를 담은 인수인계 문서를 둔다. 도구를 참조 구현 레지스트리(§13)에 올려 소유를 개인에서 조직으로 옮긴다. transition.blocker에 '담당자 이동'이 적힌 과제는 이 조치를 먼저 한다.

이럴 때 쓴다

  • 개인이 만든 도구를 부서원 여러 명이 쓰는데 라이선스 표기가 없다
  • 원본 코드가 개인 PC·개인 계정에만 있다
  • 인수인계 문서·설치 절차가 없다
  • transition.blocker가 '담당자 이동'이다

이럴 때는 쓰지 않는다

  • 개인만 쓰는 도구로 부서에 퍼지지 않은 경우(개인 사용 단계는 정상)
  • A7로 만들었지만 라이선스 명시·공용 저장소 등재·인수인계가 갖춰진 경우
  • 기관 정보화 부서가 넘겨받아 운영 중인 경우

얻는 것

  • 현장 담당자가 필요한 도구를 빠르게 만든다
  • 공식 절차 없이 바로 퍼진다

점검표

  • 라이선스가 명시되어 있는가
  • 원본이 공용 저장소에 있는가
  • 만든 사람 없이 후임이 설치·실행할 수 있는 문서가 있는가
  • 개인 구독·개인 키에 의존하지 않는가

구조 — 참여 부품

  • A7 자체 제작 환경 — 도구가 태어난 곳. 라이선스 명시가 전이 조건
  • A3 공공 API 제공자(공공 깃랩) — 개인 저장소를 대체하는 공용 등재처
  • A9 업무 규범 스킬 — 암묵적 업무 규범을 패키지로 남김
  • 후임 담당자 — 인수인계 문서로 도구를 이어받는 사람

변형

  • 라이선스 미명시: 코드는 공개했지만 라이선스가 없어 타 기관이 가져다 쓸 수 없음
  • 개인 저장소형: 개인 PC·개인 계정에만 원본이 있음
  • 개인 구독 의존형: 개인 AI 구독·API 키로 돌아가 담당자가 떠나면 호출이 끊김

관련 부품
