판정 근거

로컬 네트워크 안에서 온디바이스로 다국어 음성 방송을 내보내는 도구. 문구→번역→음성 합성→방송의 고정 파이프라인(B′1)으로 비정형 산출물(음성)을 만드는 인식·생성 파이프라인이므로 B4, 변형은 R5의 통역(STT→MT→TTS)에 가장 가까워 'MT→TTS 다국어 방송'으로 기재(STT 유무는 요약에 없어 미확인). 온디바이스 추론은 A5 엣지 추론 런타임과 A2.2 해외 오픈웨이트 로컬(원장 model_dependency), 다국어·음성 출력은 A12 접근성·모달리티 어댑터, 스피커 방송 전달은 A11 액추에이션·현장 통지 어댑터. 현장 안내 방송은 시민 접점이라 D1. 서비스 유형은 현장 방송에 맞는 것이 없어 0 기타. deployment·runtime은 원장에 없으나 온디바이스 도구라 로컬 PC·설치 필요로 잠정. Apache-2.0 공개. case_url 없음(URL 미확인).

구현 가이드

주 패턴 B4 인식 파이프라인을 구현할 때

구현 단계

  1. 입력 종류와 추출할 필드, 필드별 기준정보(대장·코드표)를 정의한다.
  2. 인식 단계는 정형 출력(JSON 스키마)만 내게 하고, 판정·산수는 규칙 단계로 분리한다(B′9).
  3. 신뢰도 임계와 보류 조건을 정해 C1 검토 큐로 보내고, C3로 재처리 경로를 둔다.
  4. E5 민감 서류면 행정망 + 로컬 모델로 두고, 제출 서류를 읽는 P2 이상 구성은 S6 문서별 격리를 둔다.
  5. C9 시험 세트로 필드별 정확도를 재고 C4로 보류율·수정률을 집계한다.

점검표

  • 인식과 판정이 서로 다른 단계로 분리되어 있는가
  • 저신뢰 건이 보류되어 사람에게 가는가
  • 오인식 건을 되돌리는 경로가 있는가(C3)
  • 필드별 정확도를 잰 시험 세트가 있는가

환경 조건

E5 민감 서류면 E1 행정망 + A2 로컬(Whisper 로컬 등). E4는 P1~P2이며, 건별 검수 없이 운영 DB로 직행하면 P2, 승인·반려에 직결되면 P3다. 제출 서류는 신뢰 불가 입력이므로 P2 이상이면 S6 문서별 격리 + 규칙 집계가 필수다(§7.4 유형 ②).

주의할 점

  • 오인식이 판정으로 번질 위험(C3 필수)
  • 민감 서류는 로컬 모델 제약
  • 제출 서류 속 숨은 지시로 판정이 조작될 위협

기본 배선 예

A10 → B4 (B′1 → B′9) → C1 → D3 · B4 → C3 (재처리)

PAX 사례 34건이 이 부품을 쓴다

맥락

접수·심사(유형 ②), 서류 진위확인, 민원 통화 정리, 실시간 자막, 원격탐사·도면 판독처럼 비정형 입력이 업무의 출발점인 경우에 쓴다. 민감 서류가 많아 행정망·로컬 모델 조건이 자주 붙는다.

맞서는 힘(긴장)

  • 자동 연결의 효율 vs 오인식이 판정으로 번지는 위험
  • 인식 정확도 vs 로컬 모델 제약(E1·E5)
  • 단계 분리의 추적 용이성 vs 단계 간 지연

해법

이럴 때 쓴다

  • 비정형 입력을 사람이 옮겨 적는 단계가 업무의 병목일 때
  • 추출값이 규칙 판정·다음 처리로 이어질 수 있을 때
  • 유형 ② 접수·심사 자동화의 기본 조립일 때

이럴 때는 쓰지 않는다

  • 추출 결과가 초안으로 멈추고 사람이 확정할 때(B1)
  • 추출 뒤 질의응답이 핵심 산출물일 때(B3)
  • 상시 관측 스트림 감시가 핵심일 때(B5)

얻는 것

  • 옮겨 적기 단계 제거
  • 판정 기준이 규칙으로 남아 설명 가능
  • OCR·STT 엔진을 범정부 공통으로 공유 가능

점검표

  • 인식과 판정이 서로 다른 단계로 분리되어 있는가
  • 저신뢰 건이 보류되어 사람에게 가는가
  • 오인식 건을 되돌리는 경로가 있는가(C3)
  • 필드별 정확도를 잰 시험 세트가 있는가

구조 — 참여 부품

변형

B′1 순차 파이프라인 제어 흐름

한 단계의 출력을 다음 단계의 입력으로 넘기는 고정 순서 배선이다. 한 프롬프트에 많은 일을 몰아 시켜 품질이 떨어지는 문제를 막는다.

PAX 사례 109건이 이 부품을 쓴다

맥락

B4 인식 파이프라인의 기본 배선이며, B1·B0·B5 안에서도 흔하다. 단계 순서가 업무 절차로 미리 정해져 있고 AI가 순서를 고를 필요가 없을 때 쓴다.

맞서는 힘(긴장)

  • 디버깅·출처 추적의 쉬움 vs 병렬화 불가로 인한 지연
  • 단계 분리의 품질 이점 vs 단계가 늘수록 오류 누적
  • 고정 순서의 예측 가능성 vs 예외 경로 처리의 경직성

해법

업무 절차를 단계로 나누고 각 단계의 입력·출력 형식을 정해 앞 단계 출력을 다음 단계에 넘긴다. 단계 사이에 형식 검증(스키마)을 두어 오류가 번지기 전에 멈추고, 멈춘 건은 C1 검토 큐나 C3 재처리로 보낸다. 판정·산수 단계는 가능한 한 규칙(B′9)으로 두고 모델은 추출·서술 단계만 맡긴다. 단계 순서를 AI가 바꿔야 한다면 B′8이나 B′7로 옮긴다.

이럴 때 쓴다

  • 업무 절차가 고정 순서로 정해져 있을 때
  • 각 단계를 따로 검증·추적해야 할 때(유형 ② 접수·심사, ⑧ 취합·변환)
  • 단일 에이전트에서 시작하는 첫 배선일 때

이럴 때는 쓰지 않는다

  • 하위 작업이 서로 독립이라 동시에 돌려야 지연이 줄 때(B′3)
  • 입력에 따라 AI가 다음 도구를 골라야 할 때(B′7)
  • 긴 업무를 계획부터 세워야 할 때(B′8)

얻는 것

  • 디버깅과 출처 추적이 쉬움
  • 단계별 품질 검증 가능
  • 구현이 가장 단순

점검표

  • 단계마다 입력·출력 형식이 정의되어 있는가
  • 단계 사이 검증에서 실패하면 멈추는가
  • 단계별 중간 결과를 추적할 수 있는가

구조 — 참여 부품

  • 단계 처리기 — 각 단계에서 추출·변환·작성 수행
  • 단계 간 형식 검증 — 다음 단계로 넘기기 전 스키마 확인
  • C3 상태 머신·롤백 — 실패 단계 재처리

PAX 사례 54건이 이 부품을 쓴다

맥락

E1은 폐쇄망·행정망·로컬 PC, E2는 해외 오픈웨이트(로컬) 또는 국산 오픈웨이트, E5는 S 이상이다. 폐쇄망 B3·B6·B8, 유형 3(현장 폐쇄망 서버 추론), 유형 12 개발 코파일럿은 이 변형을 기본으로 쓴다.

맞서는 힘(긴장)

  • 데이터 주권 vs 상용 최신 모델 대비 성능

해법

오픈웨이트 모델을 기관 안에 설치하고 서빙 계층(Ollama·vLLM·LM Studio 등)으로 업무 부품에 노출한다. 임베딩 모델도 로컬로 두어 B3 검색까지 망 안에서 끝낸다(§5 E1 폐쇄망 행 '로컬 임베딩'). 모델 선정은 C9 평가 세트로 상용·온프레미스 후보를 같은 조건에서 비교해 정한다. 폐쇄망에서 C7 경로는 수동 전환·다른 로컬 모델로 제한되므로 둘 이상의 로컬 모델이나 수동 절차를 미리 둔다. 모델·패키지 반입은 S11 인제스천 검증을 거친다.

이럴 때 쓴다

  • E1이 폐쇄망·행정망이거나 문서가 PC 밖으로 나가면 안 될 때

이럴 때는 쓰지 않는다

  • 추론 인프라·운영 인력을 확보할 수 없을 때
  • 현장 기기 자체에서 돌아야 하면 A5(엣지 런타임)
  • 모델을 재학습했으면 A2.3

얻는 것

  • 데이터가 기관 밖으로 나가지 않음
  • 호출 비용이 고정비로 바뀜
  • 폐쇄망에서도 LLM 사용 가능
  • C7의 대체 경로 후보

점검표

  • 추론·임베딩 어디에서도 데이터가 망 밖으로 나가지 않는가
  • 모델 선정 근거(평가 세트 비교)가 남아 있는가
  • 반입한 모델·패키지의 무결성 검사 기록이 있는가
  • 대체 로컬 모델 또는 수동 전환 절차가 있는가

구조 — 참여 부품

A5 엣지 추론 런타임 공통 서비스

현장 기기에 경량 모델을 배포·갱신해 망 단절·지연·영상 반출 없이 현장에서 추론한다.

PAX 사례 3건이 이 부품을 쓴다

맥락

E1이 로컬·폐쇄망인 B5 현장 감지·경보의 기반이다. 유형 3에서는 필수 부품 후보 가운데 하나다(R10: A5 또는 A2.2 또는 A2.5). PAX 557건에서는 3건뿐이다.

맞서는 힘(긴장)

  • 현장 추론의 저지연·무반출 vs 경량화에 따른 정확도 손실
  • 기기 분산 배포 vs 모델 버전 일관성
  • 망 단절 내성 vs 원격 갱신·감시의 어려움

해법

중앙에서 학습·검증한 모델을 ONNX·TensorRT 등으로 경량화해 현장 단말·NPU·카메라에 배포하고, 추론·위험 판정·경보 제어까지 현장에서 완결한다. 중앙에서 검증·승인한 모델 버전만 단말에 올리고, 망이 없으면 물리매체로 갱신한다. 원본 영상은 상시 저장하지 않고 이벤트 시에만 짧게 저장하는 식으로 반출을 줄인다. 현장 출력은 A11로, 조치 기록은 C4로 보내고, 상시 서비스이므로 C7 Fail-safe를 함께 둔다.

이럴 때 쓴다

  • 현장 통신이 불안정하거나 폐쇄망일 때
  • 영상·음성을 중앙으로 보내면 안 될 때
  • 경보 지연이 곧 피해로 이어지는 상시 감시

이럴 때는 쓰지 않는다

  • 추론을 기관 서버에서 해도 지연·반출 문제가 없으면 A2.2·A2.5
  • 모델이 커서 현장 기기에 올릴 수 없을 때

얻는 것

  • 망 단절에도 서비스 지속
  • 지연 최소화
  • 원본 영상 반출 감소

점검표

  • 현장 기기에 배포된 모델 버전을 중앙에서 알 수 있는가
  • 승인되지 않은 모델이 단말에 올라갈 수 없는가
  • 원본 영상의 저장·반출 범위가 정해져 있는가
  • 단말 장애 시 안전 상태가 정의되어 있는가

구조 — 참여 부품

  • 현장 단말·NPU·카메라 — 경량 모델로 현장 추론
  • 중앙 학습·검증 서버 — 모델을 학습·검증·승인해 패키지로 배포
  • A11 액추에이션·현장 통지 어댑터 — 현장 추론 결과를 경보·설비로 출력
  • C7 폴백 스위치 — 상시 서비스의 Fail-safe

변형

  • 단말 완결형: 외부 통신 없이 NPU 단말 안에서 탐지→위험판정→경보제어와 운영 웹서버까지 완결한다.
  • 3계층 물리매체형: 학습(내부망 GPU)–현장 단말–취득 장비를 온라인 없이 물리매체로 잇고 승인된 모델만 배포한다.
  • 기존 설비 재사용형: 기존 CCTV·센서를 재사용해 현장에서 추론한다.
  • 브라우저 모델형: WebGPU로 브라우저 안에서 모델을 돌린다.

A11 액추에이션·현장 통지 어댑터 공통 서비스

AI 판정을 화면이 아니라 스피커·경광등·VMS·PTZ·모바일 푸시·알림톡으로 내보내고, 재알림·에스컬레이션과 처리 상태 종결까지 추적한다.

PAX 사례 6건이 이 부품을 쓴다

맥락

B5 현장 감지·경보나 대민 알림·통지(D5)가 있는 과제에 쓴다. 유형 3에서 물리 액추에이션이 있으면 A11a가 필수다(R10·R14). PAX 557건에서 A11이 붙은 사례는 6건이다.

맞서는 힘(긴장)

  • 즉시 출력(대응 시간 단축) vs 오탐 시 물리·사회적 피해
  • 자동 구동 vs 사람 개입 가능성(킬스위치)
  • 알림 도달 보장(재알림) vs 알림 피로

해법

판정 이벤트·등급을 받아 등급별 출력 채널(물리 설비 또는 통지 채널)로 내보내는 어댑터를 둔다. 미처리 이벤트는 정해진 간격(예: 300초)으로 재알림하고 에스컬레이션하며, 처리 상태 코드로 종결까지 추적해 C4에 남긴다. 물리 설비를 구동하는 A11a는 E4를 P2a로 두고 C8 킬스위치와 C7 안전 상태 전환을 반드시 함께 단다. 통지 채널인 A11b는 일반 P1~P2 규칙을 따르되, 대민 알림톡·아웃바운드 발신은 P2로 본다(R8).

이럴 때 쓴다

  • 감지 결과를 현장 설비로 즉시 출력해야 할 때(A11a)
  • 이동 중인 담당자·시민에게 통지하고 처리 종결을 추적해야 할 때(A11b)
  • 유형 3에서 물리 액추에이션이 있을 때(필수)

이럴 때는 쓰지 않는다

  • 판정을 사람이 먼저 검토하고 나서 조치하는 구조(C1 검토 큐가 주)
  • 대시보드 화면 표시만 있을 때
  • 킬스위치·안전 상태를 둘 수 없는데 물리 설비를 자동 구동하려 할 때

얻는 것

  • 대응 시간 단축
  • 현장·이동 담당자에게 도달
  • 처리 종결 추적

점검표

  • 물리 구동을 즉시 멈추는 스위치가 있는가
  • 장애 시 안전 상태가 정의되어 있는가
  • 미처리 이벤트가 재알림·에스컬레이션되는가
  • 이벤트별 처리 상태가 종결까지 추적되는가

구조 — 참여 부품

  • 출력 어댑터 — 등급별로 설비·채널을 골라 명령·통지를 보냄
  • 재알림·에스컬레이션 정책 — 미처리 이벤트를 주기 재알림하고 상위로 올림

  • C4 감사 로그·지표 — 발송·처리 상태·반응 시간 기록

  • 유형 8 취합·변환 자동화

이럴 때는 쓰지 않는다

  • P2 이상 시스템 쓰기·처분이 걸려 보안 검토·통제 부품이 먼저 필요한데 이를 갖출 수 없을 때
  • 라이선스·저장소·인수인계를 정할 수 없어 전이가 불가능할 때(X9 위험)

얻는 것

  • 제작 속도와 현장 적합성
  • 내부 유지보수 역량 축적
  • 무예산·소예산 제작

점검표

  • 라이선스가 명시되어 있는가
  • 저장소가 개인 PC가 아닌 공유 위치에 있는가
  • 담당자가 바뀌어도 고칠 수 있는 문서·설정 분리가 있는가
  • 실사용 지표가 있는가

구조 — 참여 부품

  • 업무 담당자 — 요구를 알고 직접 만드는 제작자
  • AI 코딩 에이전트·저작도구 — 코드·화면·워크플로 생성
  • A3 공공 깃랩·자료실 — 등재처 — 담당자 이동 후에도 이어지게
  • A9 업무 규범 스킬 — 제작 규범·지시서를 재사용 가능한 형태로

변형

  • 비개발자 바이브코딩: 교육 후 비개발 직원이 AI 코딩으로 웹앱을 만들고 실사용 지표까지 잰다.
  • 용역 탈피 단계형: 1단계는 전문기업과, 2단계는 직원이 도구를 대여해 라벨링·학습·개발을 직접 한다.
  • 오픈소스 조립형: n8n·FastAPI·Qdrant·LM Studio 등 오픈소스로 워크플로를 직접 조립하고 설정을 공유한다.
  • 사람+에이전트 작업 단위형: 작업 지시서를 코딩 에이전트 입력 프롬프트로 설계해 '사람 1인 + 에이전트 1세션' 단위로 일한다.

D1 안내·탐색 서비스 블록

국민이 어떤 서비스를 받을 수 있고 어디로 가야 하는지 알려 주는 대민 접점 블록이다. B3 지식 접지나 B0 탐색기가 이 자리에 들어간다.

PAX 사례 99건이 이 부품을 쓴다

맥락

국민·기업이 직접 쓰는 대민 접점. §7.3 유형 ① 대민 상담·안내(D1·D7, P0~P1)의 입구다. 규칙 기반 공공데이터 조회로 안내하는 비LLM 도구도 이 블록에 속한다(R21).

맞서는 힘(긴장)

  • 안내 범위의 폭 vs 답의 정확성
  • 자유 질의의 편의 vs 규정 밖 답을 끌어내려는 입력(S4가 막는 위협)
  • 상시 운영 요구 vs 상용 API 장애(C7)
  • 쉬운 말 vs 법령·공고 원문 충실성

해법

블록은 렌즈이고, 해법은 이 자리에 끼우는 부품 조합이다. 주 부품은 공개(O) 문서에 접지한 B3 대민 자동응답형이나 조건으로 대상 서비스를 좁히는 B0 탐색기다. 답은 F1 출처와 F7 "공식 판단 아님" 고지와 함께 내고, 입력은 F4 구조화 입력으로 받아 조건 누락을 줄인다. 민원인 입력은 신뢰 불가 입력이므로 S4 행동 선택기와 S7 컨텍스트 최소화로 규정 밖 답을 막고, 상시 서비스이므로 C7 폴백을 둔다. 판단이 필요한 질문은 B′2 라우터로 D4 분류·이관이나 담당자에게 넘기고 F11로 이관을 알린다.

이럴 때 쓴다

  • 국민이 받을 수 있는 서비스나 담당 창구를 몰라 헤매는 문제가 있을 때
  • 같은 안내 질문이 반복되고 답이 공개 규정·공고에 있을 때
  • 뒤따르는 신청(D2)의 입구를 정리해 잘못된 접수를 줄이고 싶을 때

이럴 때는 쓰지 않는다

  • 개인별 요건 충족 판정이 필요하면 D3 자격·심사
  • 개인 상황에 맞춘 정보·처방·법령 해석을 주면 D7 상담·처방
  • 이용자가 기관 내부 담당자면 D8.1 탐색·조회

얻는 것

  • 창구를 찾아 헤매는 시간 감소
  • 반복 안내 업무 경감
  • 후속 신청(D2)의 입구 정리

점검표

  • 안내마다 근거 출처가 보이는가
  • "공식 판단 아님" 고지가 화면에 있는가
  • 규정 밖 질문을 사람에게 넘기는 경로가 있는가
  • 평가 세트로 안내 정확도를 재는가
  • 모델 장애 시에도 안내가 멈추지 않는가

구조 — 참여 부품

  • 국민·기업 — 자기 상황을 말하고 받을 서비스와 창구를 찾는 주체
  • B3 지식 접지 상담 — 공개 문서에 접지해 안내 답변을 생성
  • B0 결정적 도구(탐색기) — 조건 선택으로 해당 서비스 목록을 좁힘
  • F1 출처 표시 — 안내의 근거 문서·데이터를 보여 줌
  • F7 한계·신뢰도 안내 — 공식 판단이 아님과 안내 범위를 고지
  • 담당자 — 라우터가 넘긴 판단 필요 질문을 처리

변형

  • 조건 탐색형: B0 탐색기. 나이·가구·지역 같은 조건을 넣으면 받을 수 있는 서비스 목록을 준다(생애주기 혜택 내비게이터).
  • 접지 질의응답형: B3 대민 자동응답형. 자유 질의에 공개 규정·공고로 답하고 예외만 이관한다.
  • 비LLM 공공데이터 안내형: 모델 없이 A1 결정론 조회로 안내한다. 유형 1의 A2 요건을 A1로 대체한다(R21).

참조 구현 예

  • 생애주기 혜택 내비게이터 — 카탈로그 D1 카드의 B3·B0 탐색기 예

관련 부품

X13 도구 출력이 지시가 되는 에이전트 안티패턴

검색 결과·첨부·API 응답을 읽은 모델이 그 안의 문장을 새 명령으로 받아 도구를 부르는 구조를, 탐지 필터 하나로 지키려는 함정이다.

맥락

E4가 P2 이상(시스템 쓰기·처분 보조)이면서 민원 입력·제출 서류·웹 문서·타 기관 API 응답 같은 신뢰 불가 입력을 읽는 에이전트. 특히 B6·5b 데이터 에이전트.

맞서는 힘(긴장)

  • 범용 에이전트의 유연성 vs 신뢰 불가 입력 뒤의 행동 제약
  • 단일 LLM 구조의 단순함 vs 격리·계획 고정의 설계 비용
  • 탐지 필터의 손쉬움 vs 증명 가능한 보증

해법

과제의 AI가 읽는 입력 중 기관 밖에서 작성된 것을 untrusted_inputs로 나열하고, §4.2 신뢰 불가 입력 규칙대로 S4 행동 선택기(미리 정한 행동 중 선택만, 결과가 LLM으로 돌아가지 않음), S5 계획 후 실행(외부 데이터를 읽기 전에 도구 호출 계획을 고정), S6 격리 LLM(도구 있는 LLM은 외부 데이터를 읽지 않고, 읽는 LLM은 도구가 없음) 중 하나를 갖춘다. S3 컨텍스트 방화벽과 S8 독립 검증기는 보조로 붙이되 S8만으로는 규칙을 충족하지 못한다. C8 승인 게이트도 신뢰 불가 입력 규칙의 대체 통제로 인정되지 않는다(R6). 그 전 단계에서는 E4를 P0~P1 읽기·산출물 범위에 묶어 두는 것이 곧 보안이다.

이럴 때 쓴다

  • E4가 P2 이상이고 untrusted_inputs가 비어 있지 않은데 S4·S5·S6이 모두 없다(신뢰 불가 입력 규칙 위반)
  • 외부 문서를 읽는 LLM이 같은 컨텍스트에서 쓰기 도구를 호출할 수 있다
  • 인젝션 대책이 탐지 필터·프롬프트 경고문뿐이다
  • 읽은 텍스트 중 어떤 것이 어떤 도구를 부를 수 있는지 답하지 못한다

이럴 때는 쓰지 않는다

  • E4가 P0~P1로 읽기·산출물 생성에만 묶여 도구 호출·시스템 쓰기가 없는 경우(S4·S5·S6 판정 전제 불충족, R6)
  • S4·S5·S6 중 하나가 구조적으로 갖춰진 경우(보안 목적 서술이 없어도 구조가 일치하면 충족)
  • AI가 읽는 입력이 모두 기관 내부에서 작성된 경우

얻는 것

  • 단일 LLM 범용 에이전트로 구조가 단순하다
  • 새 입력·새 도구를 자유롭게 붙인다

점검표

  • untrusted_inputs가 나열되어 있는가
  • 신뢰 불가 입력을 읽은 LLM이 쓰기 도구를 직접 부를 수 없는가
  • S4·S5·S6 중 하나가 구조로 구현되어 있는가
  • S8 탐지를 유일한 방어로 두지 않았는가

구조 — 참여 부품

  • S4 행동 선택기 — LLM이 정해진 행동 중 선택만 하게 제약
  • S5 계획 후 실행·코드 후 실행 — 외부 데이터를 읽기 전에 도구 계획 고정
  • S6 격리 LLM·맵리듀스 — 읽는 LLM과 도구 있는 LLM을 분리
  • S8 독립 검증기·이중 심판 — 보조 탐지. 단독으로는 보증이 아님

변형

  • 문서 속 지시: 첨부·제출 서류 안의 문장대로 에이전트가 도구를 호출
  • API 응답 오염: 타 기관 API·웹 검색 결과에 섞인 지시가 후속 행동을 바꿈
  • 탐지 단독 방어: 인젝션 탐지 필터(S8) 하나만 두고 구조적 제약이 없음

관련 부품

S6 대체 — 읽는 LLM과 도구 있는 LLM 격리 · S5 대체 — 외부 데이터 읽기 전 계획 고정 · S4 대체 — 정해진 행동 중 선택만 · S3 보조 — 신뢰 구역 분리 표기 · S8 보조 — 탐지(단독으로는 보증 아님) · S10 기록처 — 사고 재현

X16 기준을 노출하는 위조 탐지 안티패턴

진위 판정 근거를 이용자 화면에 그대로 보여 줘 위조범이 탐지 기준을 역추적하게 만드는 함정이다. F9 근거 표시가 적대적 접점에서는 취약점이 된다.

맥락

D3 자격·심사, D2 접수·제출에서 제출 서류·이미지의 진위를 판정하는 B4 인식 파이프라인·B2 분류기. 이용자 중 일부가 탐지를 회피하려는 동기를 가진 경우.

맞서는 힘(긴장)

  • 설명 가능성·투명성 vs 적대적 이용자의 기준 역추적
  • 이용자 자기확인 편의 vs 판정 기준 보호
  • 행정 절차상 사유 고지 vs 탐지 성능 유지

해법

F9 판정 근거·기여도 표시를 역할별로 나눈다. 이용자 화면에는 '정상/위조의심'만 노출하고, 의심 부위·사유 코드·기여도 같은 세부 근거는 관리자 화면에만 보여 준다(근거 은닉, anti-oracle — 카탈로그가 S 계층 후보로 둔 반대편 부품). 관리자 화면 접근은 C8 권한 경계로 제한하고, '위조의심' 건은 C1 검토 큐에서 담당자가 세부 근거를 보고 확정한다. 이용자에게는 F7 한계·신뢰도 안내로 추가 확인 절차를 알리고, 반복 제출·판정 이력은 C4·S10에 남겨 역추적 시도를 탐지할 근거로 삼는다.

이럴 때 쓴다

  • 진위·위조 판정 결과와 함께 세부 근거(의심 부위·사유 코드·점수)가 제출자 화면에 표시된다
  • 제출자가 근거를 보고 수정해 반복 재제출할 수 있다
  • 이용자 중 탐지 회피 동기를 가진 적대자가 있을 수 있다
  • 관리자와 이용자의 판정 화면이 같다

이럴 때는 쓰지 않는다

  • 내부 담당자만 쓰는 판독 도구로 제출자에게 결과가 노출되지 않는 경우
  • 이용자가 적대자가 아닌 접점(예: 내부 품질 점검, 자기 서류 오류 안내)에서 F9로 근거를 보여 주는 경우 — 이때 F9는 정상 부품이다
  • 이용자에게 '정상/위조의심'만 보여 주고 세부 근거는 관리자 화면에 둔 경우

얻는 것

  • 투명성·설명 가능성 요구를 쉽게 충족한다
  • 선의의 이용자가 오류를 스스로 고칠 수 있다

점검표

  • 제출자 화면에 세부 판정 근거가 노출되지 않는가
  • 세부 근거가 관리자 화면에서만 보이고 접근이 제한되는가
  • 위조의심 건을 사람이 확정하는가
  • 반복 재제출 이력이 기록되는가

구조 — 참여 부품

  • F9 판정 근거·기여도 표시 — 적대적 접점에서 역할별로 나눠야 할 설명
  • 근거 은닉(anti-oracle, S 후보) — 이용자에게는 판정만, 세부 근거는 관리자에게만
  • C1 검토 큐 — 위조의심 건을 담당자가 세부 근거로 확정
  • C8 권한 경계 — 관리자 화면 접근 제한

변형

  • 의심 부위 표시형: 이용자 화면에 BBox·히트맵으로 위조 의심 부위를 표시
  • 사유 코드 노출형: 반려 사유 코드·점수를 이용자에게 그대로 반환
  • 무제한 재제출형: 근거를 보고 고쳐 무제한 재제출할 수 있어 기준 탐색이 가능
