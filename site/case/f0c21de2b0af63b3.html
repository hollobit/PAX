판정 근거

README 확인: 'Turn any process — actors × stages × steps — into a vertical swimlane board (SVG, optional PNG), audit its composition quality'. 도구 자체는 런타임 LLM 호출이 없고 board-v1 스키마 JSON을 SVG로 컴파일하는 결정적 도구(B0)이며, Claude Code·Codex가 SKILL.md로 자연어를 board로 바꾸는 단계가 앞에 붙어 B1 스킬 코파일럿을 secondary로 둔다. LLM은 정형 JSON만 내고 ajv 스키마 검증·audit이 판정하므로 B′9, 스키마 검증은 C5(구조적 출력 제약) implemented. 상용 코딩 에이전트 BYO라 A2.1, 스킬 패키징 A9, 자체 제작 A7. MIT.

구현 가이드

주 패턴 B0 결정적 도구을 구현할 때

구현 단계

  1. 반복 업무의 입력 파일·서식과 원하는 산출물을 나열하고, 처리 규칙을 사람이 읽을 수 있는 조건→결과 표로 먼저 적는다.
  2. HWP·HWPX·엑셀 입출력은 A10 어댑터로 분리하고, 공공 깃랩(A3) 등에 있는 기존 어댑터를 먼저 찾는다.
  3. AI 코딩 도구(A7)로 규칙 코드와 화면을 만들고, 런타임에 모델·외부 API를 부르지 않는지 네트워크 의존을 점검한다.
  4. 대표 입력 세트로 같은 입력에 같은 결과가 나오는지 확인하고 규칙 표와 코드의 대응을 문서로 남긴다.
  5. 부서 공유 이상으로 옮길 때 라이선스·저장소 위치·처리 로그(C4)·원복 경로(C3)를 갖춰 담당자 이동에 대비한다.

점검표

  • 런타임에 LLM·ML 호출이 전혀 없는가
  • 규칙 표가 코드와 별도로 문서화되어 있는가
  • 같은 입력에 같은 결과가 나오는지 확인했는가
  • 라이선스와 저장소 위치가 명시되어 인수인계가 가능한가

환경 조건

E2 = 없음(비LLM). E1 로컬 완결이 다수이며 폐쇄망 이식이 가장 쉬운 부품이다. E4는 대개 P0~P1이다. 로컬 PC 완결이면 C5 비식별 부담은 줄지만 C4 로그가 사라지므로 기관으로 전이할 때 다시 장착한다(§5 매트릭스).

주의할 점

  • 비정형 입력에 취약
  • 규칙 유지보수가 사람에게 남음
  • 개인 제작 도구가 담당자 이동과 함께 멈출 위험(X9)
  • AX 단계는 Ready에 머묾

기본 배선 예

A7 → B0 → A10 (HWPX 출력) · B0 → C4 (처리 로그, 기관 전이 시)

보완이 필요한 필수 부품

이 조합에서 카탈로그가 함께 갖추라고 권하는 부품 가운데 아직 확인되지 않은 것이다.

B1 코파일럿 업무 컴포넌트

사람이 하던 문서·판단 작업 옆에 AI가 초안·요약·검토안을 놓고, 사람이 고쳐서 확정한다.

PAX 사례 111건이 이 부품을 쓴다

맥락

문서·기안·검토의견처럼 산출물 형식이 정해져 있고 최종 확정자가 사람인 업무에 쓴다. BYO 코딩 에이전트와 A9 스킬을 쓰는 스킬 코파일럿이 PAX 자생 도구에 많다.

맞서는 힘(긴장)

  • 초안 속도 vs 전건 검토에 드는 사람 시간
  • 상용 모델 품질 vs 행정망·민감정보 제약(E1·E5)
  • 양식 일관성(A9 규범) vs 사안별 유연성

해법

업무 서식과 참고 자료를 입력으로 받아 모델(A2 또는 BYO 구독)이 초안·근거·신뢰도를 내고, 사람이 편집 가능한 형태(F2)로 받아 고쳐서 확정한다. 보고서 구조·문체·검증 절차는 A9 규범 스킬로 코드 밖에 두고, 공공 문서 형식은 A10 어댑터로 입출력한다. 확정 전 검토는 C1 검토 큐로 운영하고 수정 내역을 C4·C6의 입력으로 남긴다. First로 가려면 저위험 건을 C2로 자동 확정하는 분기를 더한다.

이럴 때 쓴다

  • 산출물 형식이 정해진 문서를 반복 작성할 때
  • 최종 판단과 책임이 사람에게 남아야 할 때(P1 산출물 생성)
  • 유형 ④ 내부 문서·기안, 유형 ⑫ 개발 코파일럿의 기본 조립일 때

이럴 때는 쓰지 않는다

  • 답이 기관 규정·선례 속에 있어 접지와 출처가 핵심일 때(B3)
  • 추출 결과가 사람 확정 없이 다음 판정 단계로 흐를 때(B4)
  • 런타임에 모델이 필요 없는 정형 취합일 때(B0)

얻는 것

  • 문서 작성 시간 단축
  • 책임 소재가 사람에게 명확히 남음
  • 도입이 쉬워 Enabled의 전형 경로

점검표

  • 담당자가 최종 확정한다는 절차가 운영되는가
  • 서식·문체 규범이 A9 스킬로 분리되어 있는가
  • 초안을 이용자가 직접 고칠 수 있는가(F2)
  • 수정 내역이 기록되어 품질 개선에 쓰이는가

구조 — 참여 부품

  • A2 모델 서빙 계층 — 초안 생성 모델 호출(행정망이면 내부망 프록시)
  • A9 업무 규범 스킬 — 서식·문체·검증 절차를 프롬프트 템플릿으로 고정
  • A10 문서 형식 어댑터 — HWPX·엑셀 입출력
  • C1 검토 큐 — 담당자가 초안을 확인·수정·확정
  • 담당자 — 최종 확정자이자 책임자

변형

B0 결정적 도구 업무 컴포넌트

AI 코딩으로 만들었지만 런타임에는 AI를 부르지 않고 규칙과 원문 발췌만으로 같은 입력에 같은 결과를 내는 취합·변환·검색·시각화 도구다.

PAX 사례 413건이 이 부품을 쓴다

맥락

AI 코딩 도구(A7)로 기관 인력이 직접 만든 자생 도구가 대부분이다(PAX 557건 가운데 주 부품이 B0인 사례 390건, 70%). 로컬 PC 완결이나 폐쇄망 이식이 필요한 업무, 판정 재현성이 감사에서 중요한 업무에도 맞는다. model_dependency가 '없음(비LLM)'으로 확인될 때만 해당한다.

맞서는 힘(긴장)

  • 재현성·설명 가능성 vs 비정형 입력을 다루는 유연성
  • 로컬 완결의 보안 이점 vs 기관 전이 시 처리 로그(C4)와 인수인계가 사라지는 문제
  • 규칙을 코드에 넣는 단순함 vs 규정이 바뀔 때마다 사람이 규칙을 고쳐야 하는 유지 부담

해법

업무 절차를 입력 형식(A10 어댑터)과 처리 규칙으로 나누고, AI 코딩 도구(A7)는 개발 시점에만 써서 규칙 코드와 화면을 만든다. 런타임에는 모델을 호출하지 않으므로 같은 입력에 같은 결과가 나오고 인터넷 없이 로컬에서 돈다. 판정이 필요한 경우에도 결정적 규칙 엔진이 낸다. 비정형 입력을 다뤄야 하는 단계가 생기면 그 단계만 B1·B3로 승격하고 결정적 부분은 전처리로 남긴다. 부서 밖으로 옮길 때는 라이선스·저장소·처리 로그를 함께 갖춘다.

이럴 때 쓴다

  • 입력이 정형(엑셀·서식)이고 처리 결과를 규칙으로 정의할 수 있을 때
  • 파일이 PC 밖으로 나가면 안 되거나 폐쇄망·로컬 완결이 필요할 때
  • 판정 재현성이 필요해 같은 입력에 늘 같은 결과가 나와야 할 때(규칙 점검기, 결정론 점수 엔진)
  • LLM 도입 전에 데이터·기준선을 정비하는 단계일 때

이럴 때는 쓰지 않는다

  • 비정형 문서의 요약·초안처럼 규칙으로 산출물을 정의할 수 없을 때(B1)
  • 질문이 다양해 규정·선례 접지가 필요한 상담일 때(B3)
  • 학습 모델의 수치·등급 예측이 핵심 산출물일 때(B2)

얻는 것

  • 재현성과 감사 가능성
  • 폐쇄망·로컬 이식이 가장 쉬움
  • 모델 호출 비용과 모델 장애 위험이 없음
  • B1·B3의 전처리 부품으로 승격할 자산

점검표

  • 런타임에 LLM·ML 호출이 전혀 없는가
  • 규칙 표가 코드와 별도로 문서화되어 있는가
  • 같은 입력에 같은 결과가 나오는지 확인했는가
  • 라이선스와 저장소 위치가 명시되어 인수인계가 가능한가

구조 — 참여 부품

B′1 순차 파이프라인 제어 흐름

한 단계의 출력을 다음 단계의 입력으로 넘기는 고정 순서 배선이다. 한 프롬프트에 많은 일을 몰아 시켜 품질이 떨어지는 문제를 막는다.

PAX 사례 109건이 이 부품을 쓴다

맥락

B4 인식 파이프라인의 기본 배선이며, B1·B0·B5 안에서도 흔하다. 단계 순서가 업무 절차로 미리 정해져 있고 AI가 순서를 고를 필요가 없을 때 쓴다.

맞서는 힘(긴장)

  • 디버깅·출처 추적의 쉬움 vs 병렬화 불가로 인한 지연
  • 단계 분리의 품질 이점 vs 단계가 늘수록 오류 누적
  • 고정 순서의 예측 가능성 vs 예외 경로 처리의 경직성

해법

업무 절차를 단계로 나누고 각 단계의 입력·출력 형식을 정해 앞 단계 출력을 다음 단계에 넘긴다. 단계 사이에 형식 검증(스키마)을 두어 오류가 번지기 전에 멈추고, 멈춘 건은 C1 검토 큐나 C3 재처리로 보낸다. 판정·산수 단계는 가능한 한 규칙(B′9)으로 두고 모델은 추출·서술 단계만 맡긴다. 단계 순서를 AI가 바꿔야 한다면 B′8이나 B′7로 옮긴다.

이럴 때 쓴다

  • 업무 절차가 고정 순서로 정해져 있을 때
  • 각 단계를 따로 검증·추적해야 할 때(유형 ② 접수·심사, ⑧ 취합·변환)
  • 단일 에이전트에서 시작하는 첫 배선일 때

이럴 때는 쓰지 않는다

  • 하위 작업이 서로 독립이라 동시에 돌려야 지연이 줄 때(B′3)
  • 입력에 따라 AI가 다음 도구를 골라야 할 때(B′7)
  • 긴 업무를 계획부터 세워야 할 때(B′8)

얻는 것

  • 디버깅과 출처 추적이 쉬움
  • 단계별 품질 검증 가능
  • 구현이 가장 단순

점검표

  • 단계마다 입력·출력 형식이 정의되어 있는가
  • 단계 사이 검증에서 실패하면 멈추는가
  • 단계별 중간 결과를 추적할 수 있는가

구조 — 참여 부품

  • 단계 처리기 — 각 단계에서 추출·변환·작성 수행
  • 단계 간 형식 검증 — 다음 단계로 넘기기 전 스키마 확인
  • C3 상태 머신·롤백 — 실패 단계 재처리

관련 부품

B′9 결정론 판정 게이트 제어 흐름

판정 모델(LLM·VLM·비전 분류기·통계 모델)은 정형 출력만 내고, 규칙 엔진이 최종 판정·산수·분기를 하며, 사람 또는 시스템이 확정한다.

PAX 사례 17건이 이 부품을 쓴다

맥락

법정 기준·지침 임계값이 있는 심사·점검·감시 업무에 쓴다. B4 인식 파이프라인, B5 감지·경보(유형 ③), B2 위험 예측(유형 ⑩)에서 판정 단계를 맡는다. v0.6에서 LLM·VLM 한정으로 신설하고 R11에서 판정 모델 일반으로 확장했다.

맞서는 힘(긴장)

  • 모델의 추출 유연성 vs 판정의 재현성·설명 가능성
  • 기준 변경 시 설정만 바꾸는 편의 vs 규칙 유지보수 부담
  • 강등·기각의 보수성 vs 자동 처리율

해법

판정 모델은 JSON 스키마로 제약된 정형 출력(추출값·근거 문장·신뢰도·확률)만 낸다. 규칙 엔진이 기준 임계값·산식·대조로 판정과 산수를 수행하고, 기준이 바뀌면 재학습 없이 설정만 고친다. 서버가 근거 문장을 원문과 재대조해 '문서확인/AI추정/문서에없음'으로 강등하는 비루프 검증을 둘 수 있다. 불합격·저신뢰 건은 재생성하지 않고 기각·강등해 사람 확정(C1)으로 보낸다.

이럴 때 쓴다

  • 판정 기준이 법령·지침·임계값으로 정해져 있을 때
  • 판정 재현성과 근거 설명이 필요할 때
  • 기준 변경 시 재학습 없이 설정만 바꾸고 싶을 때

이럴 때는 쓰지 않는다

  • 판정 기준을 규칙으로 적을 수 없는 서술형 평가일 때
  • 불통과 시 다시 생성해 품질을 올려야 할 때(B′5)
  • 추출 없이 규칙만으로 판정할 수 있을 때(B0)

얻는 것

  • 임의 확정·환각 수치 방지
  • 기준 변경 시 재학습 불필요
  • 판정 근거를 조항 단위로 설명 가능
  • C2 자동 분기의 신뢰 근거

점검표

  • 모델이 판정·산수를 하지 않는가
  • 기준 변경이 재학습 없이 설정 변경으로 가능한가
  • 저신뢰·근거 불일치 건이 강등되어 사람에게 가는가
  • 같은 입력에 같은 판정이 나오는가

구조 — 참여 부품

  • 판정 모델 — 정형 출력(추출값·근거·신뢰도·확률)만 생성
  • 규칙 엔진 — 임계값·산식·대조로 판정과 산수
  • C5 가드레일 필터 — 구조적 출력 제약·스키마 검증, 근거 재대조
  • C1 검토 큐 — 강등·저신뢰 건의 사람 확정

변형

  • LLM·VLM 추출형: LLM·VLM은 추출·서술만 하고 규칙이 판정한다(v0.6 원정의)
  • 비전·통계 판정 모델형: 비전 분류기·통계 모델 확률을 규칙이 판정한다(R11 확장)
  • 근거 재대조 강등형: 근거 문장을 원문과 재대조해 문서확인/AI추정/문서에없음으로 강등한다(비루프 검증)
  • 병렬 교차 검증형: LLM 추출과 규칙 파서를 병렬로 돌려 불일치를 규칙으로 잡는다
  • 정형 IR → 결정론 컴파일: 에이전트가 정형 중간표현을 내고 결정론적으로 변환한다(§13 해외 참고)

참조 구현 예

  • PAX 90f8afce65c6f327 — VLM 추출 + 차량 대장 규칙 대조 + 담당자 확정, 소형 실물(§13)

A9 업무 규범 스킬 공통 서비스

보고서 구조·문체·서식·검증 절차 같은 업무 규범을 모델 중립 스킬(지침 + 검증기 + 출력 서식)로 패키징해 어떤 모델·에이전트에서든 재사용한다.

PAX 사례 54건이 이 부품을 쓴다

맥락

기안·보고서·콘텐츠처럼 서식과 문체가 정해진 산출물을 만드는 B1·B7, BYO 코딩 에이전트 환경(E2 모델 중립), 개발 코파일럿에서 쓴다. 유형 4·6·12에서는 필수 기반이고, §7.2 진행 경로에서는 3단계에 놓인다.

맞서는 힘(긴장)

  • 규범 고정(일관성) vs 담당자 재량
  • 모델 중립(이식성) vs 특정 모델 최적화
  • 규범 공개·재사용 vs 프롬프트·규범 유출
  • 가중치에 넣기(튜닝) vs 문서로 주입하기

해법

규정집·매뉴얼·서식 예시에서 업무 규범을 뽑아 지침(구조·문체·금지 사항), 검증기(형식·인용·수치 검사), 출력 서식(HWPX·DOCX 등)으로 묶은 스킬 패키지로 만든다. 모델 호출 코드와 분리된 파일로 두어 어떤 코딩 에이전트·모델에서도 같은 절차가 돌게 한다(External Configuration). 산출·검증된 수치와 출처만 주입하고 미제공 수치·순위 생성을 금지하는 식으로 생성 범위를 규범으로 좁힌다. 스킬은 버전으로 관리해 규범 유출·변경을 추적하고, C9로 스킬 변경 전후 품질을 잰다.

이럴 때 쓴다

  • 산출물 서식·문체·구조가 정해져 있을 때
  • 출력 품질이 들쭉날쭉할 때(§7.5)
  • BYO 환경에서 모델과 무관하게 같은 절차를 돌려야 할 때
  • 갱신이 잦은 규범을 튜닝 없이 반영해야 할 때

이럴 때는 쓰지 않는다

  • 규범이 문서로 정리되지 않았고 정리할 담당도 없을 때
  • 지식 검색이 필요한 문제(B3 접지가 먼저)
  • 스킬 내용 자체가 민감해 배포할 수 없는데 버전 관리·접근 통제를 둘 수 없을 때

얻는 것

  • 출력 일관성
  • 모델 교체 가능(BYO에서는 교체 가능성이 곧 C7)
  • 타 기관 재사용
  • 튜닝 없이 규범 갱신

점검표

  • 규범이 모델 호출 코드와 분리된 파일로 있는가
  • 검증기가 출력 형식·인용·수치를 실제로 검사하는가
  • 스킬에 버전이 있는가
  • 다른 모델로 바꿔도 같은 서식이 나오는지 확인했는가

구조 — 참여 부품

  • 규범 원천(규정집·매뉴얼·서식) — 스킬로 옮길 업무 규범의 출처
  • 스킬 패키지 — 지침·검증기·출력 서식을 모델 밖 파일로 묶음
  • 코딩 에이전트·모델(BYO) — 스킬을 불러 규범대로 산출
  • A10 문서 형식 어댑터 — 출력 서식을 HWPX·DOCX로 내보냄
  • C9 평가 세트 — 스킬 변경 전후 품질 비교

변형

  • 보고서·문서 규범 스킬: gov-report-skill(기획보고서 7대 항목), 원페이퍼 스킬(A4 한 쪽·DOCX 검증).
  • 스타일·콘텐츠 스킬: Public Cardnews(6개 스타일), 제작 가이드·검수 체크리스트를 묶은 제작 스킬 패키지.
  • 검증 스킬: paper-verify(인용 검증)처럼 검증 절차 자체를 패키징한다.
  • 규정집→스킬 변환: book-to-skill은 PDF 규정집을 에이전트 스킬로 자동 변환한다(A9+A10 조합).
  • 지식 가이드 In-Context 주입: 파인튜닝 대신 추출·판정 기준을 문서형 가이드로 증류해 주입한다.

참조 구현 예

  • PAX paper-verify — 인용 검증 스킬(§6 A9 카드)

A7 자체 제작 환경 공통 서비스

외부 용역 없이 기관 인력이 저작도구·AI 코딩 에이전트로 도구를 직접 만들고 고치는 제작 환경이다.

PAX 사례 317건이 이 부품을 쓴다

맥락

업무 담당자가 AI 코딩 도구·저작도구·오픈소스로 직접 만드는 과제에 쓴다. 유형 8(취합·변환 자동화)에서는 필수 기반이다. PAX 557건에서 A7이 붙고 BYO 모델을 쓰는 사례는 29건이다.

맞서는 힘(긴장)

  • 제작 속도·현장 적합성 vs 유지보수 연속성
  • 개인 역량 의존 vs 조직 인수인계
  • 무예산 제작 vs 보안 검토·기관 공식화 절차

해법

기관 인력이 AI 코딩 에이전트·저작도구·오픈소스로 직접 만들되, 처음부터 전이를 전제로 한다. 설정·데이터(연락처·업무분장 등)는 코드 밖 파일로 빼 비개발자도 고치게 하고, 작업 지시서 자체를 코딩 에이전트가 수행할 프롬프트로 설계해 제작 절차를 남긴다. MIT·Apache 등 라이선스를 명시하고 공공 깃랩(A3)이나 혁신24 자료실에 등재해 담당자가 바뀌어도 이어지게 한다. 실사용 건수로 성과를 재 기관 공식으로 올린다.

이럴 때 쓴다

  • 반복 업무를 줄이는 소규모 도구를 빠르게 만들 때
  • 용역 없이 작은 수정을 계속해야 할 때
  • 유형 8 취합·변환 자동화

이럴 때는 쓰지 않는다

  • P2 이상 시스템 쓰기·처분이 걸려 보안 검토·통제 부품이 먼저 필요한데 이를 갖출 수 없을 때
  • 라이선스·저장소·인수인계를 정할 수 없어 전이가 불가능할 때(X9 위험)

얻는 것

  • 제작 속도와 현장 적합성
  • 내부 유지보수 역량 축적
  • 무예산·소예산 제작

A2.1 모델 서빙 · 상용 API 호출 공통 서비스

GPT·Gemini·Claude·HyperCLOVA X·Upstage 등 상용 모델 API를 서빙 계층을 거쳐 호출해 자체 인프라 없이 최신 모델 성능을 쓴다.

PAX 사례 88건이 이 부품을 쓴다

맥락

E2는 해외 상용 API(또는 국산 상용 모델 API), E1은 인터넷망·클라우드다. E5 등급이 O이거나 비식별 후 전송해도 되는 업무에 맞는다. 대민 상담(B3)·코파일럿(B1)·콘텐츠 생성(B7)에서 흔하다.

맞서는 힘(긴장)

  • 모델 성능·도입 속도 vs 데이터 반출·주권
  • 종량 과금의 초기 저비용 vs 호출량 증가 시 비용 예측 어려움
  • 벤더의 모델 개선 vs 예고 없는 품질 회귀
  • 단일 API의 단순함 vs 장애 시 서비스 중단

해법

업무 코드는 서빙 계층만 부르고, 서빙 계층이 상용 API를 호출한다. 행정망 본문이 나가는 경로 앞에는 C5 비식별 전처리를 두고, 대체 모델을 등록해 C7 폴백을 건다(§5 매트릭스 E2 해외 상용 API 행). 모델 버전을 고정하고 모델·프롬프트·설정 조합을 릴리스처럼 관리해 업데이트 전후를 C9로 비교한다. 비용이 문제면 라우팅·캐싱으로 큰 모델 호출을 줄인다. E5가 S 이상이면 이 변형 단독으로는 안 되고 A2.4 내부망 프록시를 거친다.

이럴 때 쓴다

  • 인터넷망·클라우드 환경이고 데이터 등급이 O이거나 비식별 후 전송 가능할 때
  • PoC 초기에 모델 성능을 빠르게 확인해야 할 때
  • 자체 GPU·운영 인력이 없을 때

이럴 때는 쓰지 않는다

  • E1이 폐쇄망이면 조립 오류(A2.2·A2.4로)
  • E5가 S 이상인데 내부망 프록시가 없을 때(A2.4 필수)
  • 상시 서비스인데 대체 경로를 둘 수 없을 때

얻는 것

  • 인프라 없이 최신 모델 성능
  • 빠른 PoC
  • 벤더의 지속적 개선

점검표

  • 업무 코드가 상용 API를 직접 부르지 않는가
  • 외부로 나가는 프롬프트에서 무엇이 걸러지는지 답할 수 있는가
  • API 장애 시 대체 경로가 있는가
  • 모델 버전과 호출당 비용·지연이 기록되는가

구조 — 참여 부품

  • A2 서빙 계층 — 업무 코드 대신 상용 API를 호출하고 버전·사용량을 기록
  • C5 가드레일(비식별 전처리) — 외부 전송 전 민감정보 제거
  • 상용 모델 API — 기관 밖에서 추론을 수행
  • C7 폴백 스위치 — API 장애·품질 저하 시 대체 모델·수동 처리로 전환

변형

  • 해외 상용 API: GPT·Gemini·Claude 등이다. E2 값은 해외 상용 API.
  • 국산 상용 API: HyperCLOVA X·Upstage 등 국내 사업자 API. 망·등급 조건은 해외와 같이 따진다.
  • 구조화 호출: function calling·JSON Schema로 출력 형식을 고정해 부른다. 판정은 규칙 엔진에 남긴다.

C5 가드레일 필터 운영 컴포넌트

개인정보·환각·편향·형식 오류가 프롬프트나 산출물에 들어가지 못하게 시스템이 경계에서 걸러낸다. 비식별 전처리, 출처 검증, 구조적 출력 제약이 대표 변형이다.

PAX 사례 44건이 이 부품을 쓴다

맥락

외부 모델을 부르거나 대민에 답하는 모든 B 부품. 특히 E2 해외 상용 API, E5 S 이상 데이터, B3 지식 접지 상담, 유형 ① 대민 상담, ④ 기안, ⑥ 콘텐츠, ⑦ 대조·점검, ⑨ 인수인계, ⑬ 비식별·정제 도구.

맞서는 힘(긴장)

  • 차단의 엄격함 vs 과잉 차단으로 인한 유용성 저하
  • 비식별 강도 vs 문맥 보존
  • 결정적 검증의 신뢰성 vs 구현 범위

해법

프롬프트가 기관 밖으로 나가기 전 PII를 마스킹하고 원복 키를 보관하는 비식별 전처리기를 둔다. 응답에는 인용을 원본(법령정보센터·통계표 등)과 대조하는 출처 검증기와, JSON 스키마·허용 목록 같은 구조적 출력 제약을 건다. 근거가 없으면 답하지 않거나 '확인 필요'로 표시한다. 차단 사유는 C4에 남기고, 이용자에게는 F1 출처와 F7 한계 안내로 보인다. 사람이 하는 팩트체크·법무 심의는 C5가 아니라 C1.2에 둔다.

이럴 때 쓴다

  • E2 해외 상용 API로 행정망 본문이 외부로 나갈 때(필수)
  • E5 S 이상 개인정보·민감정보를 다룰 때
  • B3 대민 응답처럼 인용·수치의 정확성이 신뢰의 핵심일 때
  • C5가 필수인 유형 ①④⑥⑦⑨⑪⑬

이럴 때는 쓰지 않는다

  • E1 로컬 PC 완결로 데이터가 밖으로 나가지 않을 때 비식별은 불필요해질 수 있다(§5 매트릭스, 단 출처 검증은 별개)
  • 사람이 수행하는 심의만 있을 때(C1.2로 태그)
  • 적대적 입력 탐지가 목적일 때(S8)

얻는 것

  • 개인정보 외부 유출 차단
  • 환각 인용 감소
  • 상용 API 사용 조건 충족

점검표

  • 외부 전송 전 무엇이 걸러지는지 답할 수 있는가
  • 인용이 원본과 대조되는가
  • 근거 없을 때의 동작이 정해져 있는가
  • 차단 사유가 기록되는가

D8.9 변환·서식 서비스 블록

HWP·HWPX·PDF·DOCX·엑셀 사이를 오가고 양식을 만드는 내부 운영 블록이다. A10 문서 어댑터가 서비스로 독립한 형태다.

PAX 사례 80건이 이 부품을 쓴다

맥락

문서 형식 변환과 양식 생성 업무. §7.3 유형 ⑧ 취합·변환 자동화(D8.5 · D8.9, P1). PAX 80건(주 부품 B0 80%, B1 12%).

맞서는 힘(긴장)

  • 변환 충실도 vs 형식별 특이 구조(표·수식·첨자)
  • 설치형·오프라인 편의 vs 배포·갱신 관리
  • 개인 도구의 민첩성 vs 인사이동 시 소멸(X9)
  • 파일 자동 변환 vs 파일 속 매크로·지시 위협

해법

A10 어댑터를 결정적 변환기(B0)로 만들어 HWP·HWPX·PDF·DOCX·엑셀 사이를 오가게 한다. 스캔 문서는 B4 OCR로 텍스트를 얻는다. 변환은 원본을 보존하고 새 파일을 만들며(C3 원복·F8 되돌리기), 파일은 S11 검사와 S9 격리 실행을 거친다. 규정·양식을 MCP로 노출하면 다른 AI 도구가 기관 서식을 쓸 수 있는 공통 부품이 된다(A8). 개인 제작 도구는 라이선스·저장소를 명시한다(A7).

이럴 때 쓴다

  • 공공 문서 형식 간 변환이 반복될 때
  • AI 도구가 HWP·HWPX를 읽고 쓰지 못해 막힐 때
  • 양식을 반복해 새로 만들 때

이럴 때는 쓰지 않는다

  • 여러 부서 파일을 모아 합치면 D8.5(우선순위 높음)
  • 변환 뒤 첫 판 작성이 목적이면 D8.3
  • 변환한 문서를 찾는 것이 핵심이면 D8.1 검토

D8.10 발간·홍보 서비스 블록

보도자료·카드뉴스·포스터·정보지를 기획부터 발행까지 만드는 내부 운영 블록이다. B7 콘텐츠 제작의 업무 블록 버전이다.

PAX 사례 22건이 이 부품을 쓴다

맥락

기관이 외부에 내는 발행물을 만드는 업무. §7.3 유형 ⑥ 정책·홍보 콘텐츠 제작(D8.10, P1). PAX 22건(주 부품 B0 45%, B7 36%).

맞서는 힘(긴장)

  • 제작 속도 vs 사실·저작권 검수
  • 스타일 일관성 vs 매번 다른 요구
  • 생성자-비평가·반복 개선 품질 vs 반복 비용(X12)
  • 참고 링크 활용 vs 보도자료·링크 속 유출 링크 삽입 위협

해법

B7 콘텐츠 제작을 B′8 계획-실행(기획 → 구성 → 생성 → 편집)과 B′6 반복 개선으로 배선하고, 반복 상한을 둔다. 기관 스타일은 A9 스타일 스킬로 패키징하고, 보도자료 입력은 A10(HWPX)으로 읽는다. 발행 전에는 C5 저작권·사실 검증과 C1 검수를 필수로 두고, 필요하면 C1.2 심의 게이트(법무·표시광고)를 더한다. 출력은 F2 편집 가능(PPTX·피그마 등)과 F3 대안·부분 재생성으로 담당자가 고치게 한다. S8 독립 검증기로 유출 링크·사실 오류를 거른다.

이럴 때 쓴다

  • 보도자료를 여러 발행 형식으로 반복 제작할 때
  • 기관 스타일을 여러 담당자가 일관되게 써야 할 때
  • 외부 디자인 용역 의존을 줄이고 싶을 때

이럴 때는 쓰지 않는다

  • 내부 보고서·공문 첫 판이면 D8.3
  • 발행 없이 자료 요약만 하면 D8.2
  • 국민에게 개인 맞춤 안내를 주면 D7

얻는 것

  • 발행물 제작 시간 단축
  • 기관 스타일 일관성
  • 외부 용역 의존 감소

점검표

  • 발행 전 사람 검수가 필수로 걸려 있는가
  • 사실·저작권 검증 절차가 있는가
  • 결과를 편집 가능한 형식으로 고칠 수 있는가
  • 반복 개선에 상한이 있는가

구조 — 참여 부품

  • C5 가드레일·출처 검증 — 저작권·사실 검증
  • C1 검토 큐 — 발행 전 검수

변형

A10 문서 형식 어댑터 공통 서비스

HWP·HWPX·엑셀·한셀·PDF 같은 한국 공공 문서 형식을 AI 부품이 읽고(구조화) 쓰게(서식 생성) 하는 변환 계층이다.

PAX 사례 136건이 이 부품을 쓴다

맥락

문서를 입력으로 받거나 기안·보고서·취합본을 산출하는 과제라면 거의 다 쓴다. 유형 2·4·8에서는 필수 기반이고 유형 6·7에서도 쓰인다. E1 로컬 PC 조건에서 도는 경우가 많다.

맞서는 힘(긴장)

  • 형식 충실도(표·각주·조항 구조 보존) vs 파서 구현 비용
  • 로컬 처리(무반출) vs 클라우드 변환 도구의 편의
  • 기관별 서식 다양성 vs 공통 어댑터 재사용

해법

입력 쪽에서는 HWPX 압축 구조·PDF에서 조·항·호·별표 계층과 표를 보존해 구조화 텍스트·표로 바꾸고, 머리말·각주 같은 잡음을 걷어 조항 단위로 정규화한다. 출력 쪽에서는 스킬(A9)의 출력 서식을 받아 HWPX·XLSX 기안 서식을 역방향으로 생성한다. 민감 문서는 PC 밖으로 보내지 않도록 로컬에서 변환하고, 파서를 라이브러리·CLI·MCP로 함께 제공하면 다른 부품과 기관이 그대로 쓴다. 형식 변환 정확도는 C9 판정 체계로 잰다.

이럴 때 쓴다

  • 입력이 HWP·HWPX·엑셀·PDF 공공 문서일 때
  • 산출물을 기안·보고 서식으로 내보내야 할 때
  • 유형 2·4·8 조립

이럴 때는 쓰지 않는다

  • 스캔 이미지·음성처럼 인식이 필요한 입력은 B4 인식 파이프라인(OCR·STT)
  • 입출력이 이미 정형 데이터·API인 경우

얻는 것

  • 공공 문서를 AI 입력·출력으로 연결
  • 기관 간 재사용 가능한 공통 부품
  • 로컬 처리로 무반출

점검표

  • 표·조항 계층이 변환 후에도 보존되는가
  • 출력이 기관 기안 서식 그대로 열리는가
  • 민감 문서가 변환 과정에서 PC 밖으로 나가지 않는가
  • 변환 정확도 판정 기록이 있는가

구조 — 참여 부품

  • 입력 파서 — 조·항·호·표 구조를 보존해 구조화
  • 서식 생성기 — 구조화 결과를 HWPX·엑셀 서식으로 출력
  • A9 업무 규범 스킬 — 출력 서식 규범 제공
  • B3 지식 접지 상담 — 구조화된 규정을 색인해 검색

변형

  • 규정 구조 파서: HWP/HWPX·PDF 규정을 조항 단위로 정규화한다.

X9 담당자와 함께 사라지는 도구 안티패턴

개인이 만든 도구가 부서에 퍼졌지만 라이선스·저장소·인수인계가 없어, 만든 사람의 인사이동과 함께 멈추는 함정이다.

맥락

A7 자체 제작 환경으로 태깅된 도구(PAX 557건 중 317건, 57%), 특히 개인 사용에서 부서 공유로 막 퍼지기 시작한 바이브코딩 도구.

맞서는 힘(긴장)

  • 개인의 빠른 제작 vs 조직의 유지보수 책임
  • 비공식 공유의 편의 vs 라이선스·저장소 절차
  • 현장 맞춤 vs 다른 담당자가 이해할 수 있는 구조

해법

도구가 부서에 퍼지기 시작하면 A7 산출물에 MIT·Apache 등 라이선스를 명시하고, 코드를 개인 PC가 아니라 A3 공공 깃랩 같은 공용 저장소에 등재한다. 업무 규범·프롬프트는 A9 업무 규범 스킬로 패키징해 다른 담당자가 그대로 쓸 수 있게 하고, 설치·설정·데이터 경로를 담은 인수인계 문서를 둔다. 도구를 참조 구현 레지스트리(§13)에 올려 소유를 개인에서 조직으로 옮긴다. transition.blocker에 '담당자 이동'이 적힌 과제는 이 조치를 먼저 한다.

이럴 때 쓴다

  • 개인이 만든 도구를 부서원 여러 명이 쓰는데 라이선스 표기가 없다
  • 원본 코드가 개인 PC·개인 계정에만 있다
  • 인수인계 문서·설치 절차가 없다
  • transition.blocker가 '담당자 이동'이다

이럴 때는 쓰지 않는다

  • 개인만 쓰는 도구로 부서에 퍼지지 않은 경우(개인 사용 단계는 정상)
  • A7로 만들었지만 라이선스 명시·공용 저장소 등재·인수인계가 갖춰진 경우
  • 기관 정보화 부서가 넘겨받아 운영 중인 경우

얻는 것

  • 현장 담당자가 필요한 도구를 빠르게 만든다
  • 공식 절차 없이 바로 퍼진다

점검표

  • 라이선스가 명시되어 있는가
  • 원본이 공용 저장소에 있는가
  • 만든 사람 없이 후임이 설치·실행할 수 있는 문서가 있는가
  • 개인 구독·개인 키에 의존하지 않는가

구조 — 참여 부품

  • A7 자체 제작 환경 — 도구가 태어난 곳. 라이선스 명시가 전이 조건
  • A3 공공 API 제공자(공공 깃랩) — 개인 저장소를 대체하는 공용 등재처
  • A9 업무 규범 스킬 — 암묵적 업무 규범을 패키지로 남김
  • 후임 담당자 — 인수인계 문서로 도구를 이어받는 사람

변형

  • 라이선스 미명시: 코드는 공개했지만 라이선스가 없어 타 기관이 가져다 쓸 수 없음
  • 개인 저장소형: 개인 PC·개인 계정에만 원본이 있음
  • 개인 구독 의존형: 개인 AI 구독·API 키로 돌아가 담당자가 떠나면 호출이 끊김

X1 AI 스티커 안티패턴

기존 화면에 요약·챗봇 버튼만 붙이고 업무 순서와 사람·AI의 역할 분담은 그대로 두어, AI가 있어도 업무 산출물이 바뀌지 않는 함정이다.

맥락

기존 행정정보시스템·업무 포털에 AI 기능을 추가하는 과제, 특히 성과 지표가 'AI 기능 탑재 여부'나 호출 수로 잡힌 과제. R24에 따라 AI 런타임이 전혀 없는 순수 행정정보시스템도 이 태그(AI 무관)로 표기한다.

맞서는 힘(긴장)

  • 빠른 도입 실적 vs 업무 흐름 재설계 비용
  • 기존 시스템 무변경(안정성) vs 산출물 단위의 역할 분담
  • 'AI 탑재' 홍보 효과 vs 실제 처리시간·수정률 개선

해법

먼저 가치 흐름 규칙(R1)으로 사람 또는 국민이 최종으로 받는 핵심 산출물을 정하고, 그 산출물을 AI가 어떤 모양으로 분담할지 B 업무 컴포넌트를 하나 고른다(초안→사람 확정이면 B1, 근거 접지 답변이면 B3, 서류 추출이면 B4). 사람이 확정하는 지점은 C1 검토 큐로, 이용자가 고쳐 확정하는 면은 F2 편집 가능한 출력으로 명시한다. 흐름이 바뀌었는지는 C4 감사 로그·지표의 처리시간·수정률로 잰다. AI 런타임이 전혀 없는 행정정보시스템이라면 AI로 포장하지 말고 R24대로 B0·service_type 0·platform 공란·X1(AI 무관)으로 정직하게 분류한다.

이럴 때 쓴다

  • AI 기능이 추가됐다는 서술은 있으나 처리 단계 수·결재선·담당자 역할이 바뀌었다는 서술이 없다
  • 성과 지표가 AI 호출 수·이용 만족도뿐이고 처리시간·수정률 같은 산출물 지표가 없다
  • 챗봇이 기관 업무 데이터·시스템과 연결되지 않은 범용 대화에 머문다
  • AI 런타임이 전혀 없는 행정정보시스템이 AX 과제로 분류되어 있다(R24)

이럴 때는 쓰지 않는다

  • B1 코파일럿처럼 AI가 초안을 만들고 사람이 확정하는 역할 분담이 실제로 서술된 경우
  • B8 레거시 오버레이처럼 표준 시스템 위에 얹었지만 업무 산출물을 AI가 만들어 내는 경우
  • B0 결정적 도구가 반복 취합 업무를 실제로 줄이고 AI로 포장하지 않은 경우(Ready 부품으로 정직하게 분류된 경우)

얻는 것

  • 기존 시스템을 건드리지 않아 도입이 빠르고 장애 위험이 낮다
  • 'AI 탑재' 실적을 즉시 보고할 수 있다

점검표

  • AI 도입 전후 처리 단계·담당자 역할의 차이를 한 장으로 보여 줄 수 있는가
  • AI가 만드는 산출물과 사람이 확정하는 지점이 명시되어 있는가
  • 처리시간·수정률 같은 산출물 지표가 도입 전 기준선과 함께 있는가
  • AI 런타임이 없는데 AI 과제로 보고하고 있지 않은가

구조 — 참여 부품

  • 덧붙인 AI 기능 — 요약·대화 버튼. 업무 산출물 생산에 역할이 없음
  • B1 코파일럿 — 교정 후 초안→사람 확정으로 산출물 역할을 나누는 대체 부품
  • C1 검토 큐 — 교정 후 사람이 확정하는 지점을 명시
  • C4 감사 로그·지표 — 흐름이 실제로 바뀌었는지 처리시간·수정률로 측정

변형

  • 요약 버튼형: 기존 화면에 '요약' 버튼만 추가하고 결재·처리 단계는 그대로
  • 범용 챗봇 부착형: 업무 데이터와 연결되지 않은 범용 대화창을 포털에 부착
  • AI 무관 행정시스템(R24): AI 런타임이 전혀 없는 순수 행정정보시스템(예: 교육·인증 학습관리시스템). B0·service_type 0·platform 공란과 함께 X1(AI 무관)로 표기

관련 부품
