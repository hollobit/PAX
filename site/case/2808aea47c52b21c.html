판정 근거

광진구 실무자가 만든 LexDiff를 경기도의회가 재사용해 구축한 지능형 법령정보 서비스로, 위임법령 3단 비교·신구법 대조·판례 통합 검색이라는 결정적 대조 기능(B0, secondary)과 일상 언어 AI 법률 질의응답(B3, primary)이 결합됐다. 법제처 데이터 기반 연계이므로 A4, 판례·조례 통합 검색에 근거 표시가 있어 F1을 태그했다. 화면 하단에 원작자 권한을 표기하고 API 비용 보호를 위해 수도권 접속 제한을 둔 점이 개인 개발 도구의 타 기관 재사용 계보를 명시한 모범 사례라 reference_candidate로 등록했다.

구현 가이드

주 패턴 B3 지식 접지 상담을 구현할 때

구현 단계

  1. 대표 질문·정답·채점 기준으로 C9 평가 세트를 먼저 만든다.
  2. A1로 코퍼스를 정리하고 데이터 등급(E5)과 공개 범위를 메타로 붙인다. 등급 문서가 섞이면 S2 권한 인식 검색을 둔다.
  3. E1에 맞게 임베딩·벡터DB·모델 위치를 정한다(폐쇄망이면 전부 로컬, A2.2·A2.4).
  4. 근거 밖 답변 금지·출처 상시 표시·근거 없으면 이관하는 규칙을 C5·F1·B′2로 구현한다.
  5. 검색 품질 3패턴을 하나씩 붙이며 C9로 재고, 문서 갱신 주기를 C6으로 운영한다.

점검표

  • 답마다 출처가 표시되는가
  • 근거가 없을 때 답하지 않고 이관하는가
  • 평가 세트로 검색·답변 품질을 재고 있는가
  • 코퍼스 갱신 주기와 책임자가 정해져 있는가

환경 조건

E1 폐쇄망·행정망이면 임베딩·벡터DB·모델 전부 로컬(A2.2 주권형 또는 A2.4 내부망 프록시 + 로컬 임베딩). E2 해외 상용 API면 C5 비식별 전처리와 C7 폴백이 필수다. E4는 P0~P1이 기본이다. 신뢰 불가 입력(민원 입력·공개 웹)을 읽고 P2 이상이면 S6 문서별 격리와 S2가 필요하다. 대민형은 S4·S7이 권장된다(§7.4).

주의할 점

  • 평가 없이 붙이면 품질을 알 수 없음(X10)
  • 코퍼스 갱신이 멈추면 오답이 됨
  • 부서마다 따로 만들면 중복(X3)
  • 대민형은 인젝션·유출 위협에 노출

기본 배선 예

A1 → A2.2 → B3 (B′7 · B′2) → F1 · B3 → C2 → 담당자 이관

  • A3 공공 API 제공자 정부·공공이 운영하는 모델·데이터·개발 도구(범정부 AI 공통기반, 모두의 AI 실험실, 공공데이터포털, 공공 깃랩)를 범정부 Provider로 소비한다.
  • C1 검토 큐 AI 산출물이 다음 단계로 넘어가기 전에 사람이 맞고 틀림을 확인·수정·확정하는 대기열을 두어, 오류가 업무 결과로 흘러가지 않게 한다.

  • F7 한계·신뢰도 안내 AI가 무엇을 못 하는지, 얼마나 확신하는지, 공식 판단이 아님을 이용자가 볼 수 있는 곳에 적어 과신을 막는다.

    쓰는 작업: 운영 단계에서 AI 결과물을 외부로 배포하는 부서가 배포 전 확인 절차를 만들 때 쓴다. PAX 목록이 꼽은 결과물 유사성과 AI 이용 사실 기록이 이 절차의 항목이다.
    주의: 지식베이스 문서를 그대로 옮겨 답하는 RAG 서비스도 결과물 유사성 문제를 안는다.

B0 결정적 도구 업무 컴포넌트

AI 코딩으로 만들었지만 런타임에는 AI를 부르지 않고 규칙과 원문 발췌만으로 같은 입력에 같은 결과를 내는 취합·변환·검색·시각화 도구다.

PAX 사례 413건이 이 부품을 쓴다

맥락

AI 코딩 도구(A7)로 기관 인력이 직접 만든 자생 도구가 대부분이다(PAX 557건 가운데 주 부품이 B0인 사례 390건, 70%). 로컬 PC 완결이나 폐쇄망 이식이 필요한 업무, 판정 재현성이 감사에서 중요한 업무에도 맞는다. model_dependency가 '없음(비LLM)'으로 확인될 때만 해당한다.

맞서는 힘(긴장)

  • 재현성·설명 가능성 vs 비정형 입력을 다루는 유연성
  • 로컬 완결의 보안 이점 vs 기관 전이 시 처리 로그(C4)와 인수인계가 사라지는 문제
  • 규칙을 코드에 넣는 단순함 vs 규정이 바뀔 때마다 사람이 규칙을 고쳐야 하는 유지 부담

해법

업무 절차를 입력 형식(A10 어댑터)과 처리 규칙으로 나누고, AI 코딩 도구(A7)는 개발 시점에만 써서 규칙 코드와 화면을 만든다. 런타임에는 모델을 호출하지 않으므로 같은 입력에 같은 결과가 나오고 인터넷 없이 로컬에서 돈다. 판정이 필요한 경우에도 결정적 규칙 엔진이 낸다. 비정형 입력을 다뤄야 하는 단계가 생기면 그 단계만 B1·B3로 승격하고 결정적 부분은 전처리로 남긴다. 부서 밖으로 옮길 때는 라이선스·저장소·처리 로그를 함께 갖춘다.

이럴 때 쓴다

  • 입력이 정형(엑셀·서식)이고 처리 결과를 규칙으로 정의할 수 있을 때
  • 파일이 PC 밖으로 나가면 안 되거나 폐쇄망·로컬 완결이 필요할 때
  • 판정 재현성이 필요해 같은 입력에 늘 같은 결과가 나와야 할 때(규칙 점검기, 결정론 점수 엔진)
  • LLM 도입 전에 데이터·기준선을 정비하는 단계일 때

이럴 때는 쓰지 않는다

  • 비정형 문서의 요약·초안처럼 규칙으로 산출물을 정의할 수 없을 때(B1)
  • 질문이 다양해 규정·선례 접지가 필요한 상담일 때(B3)
  • 학습 모델의 수치·등급 예측이 핵심 산출물일 때(B2)

얻는 것

  • 재현성과 감사 가능성
  • 폐쇄망·로컬 이식이 가장 쉬움
  • 모델 호출 비용과 모델 장애 위험이 없음
  • B1·B3의 전처리 부품으로 승격할 자산

점검표

  • 런타임에 LLM·ML 호출이 전혀 없는가
  • 규칙 표가 코드와 별도로 문서화되어 있는가
  • 같은 입력에 같은 결과가 나오는지 확인했는가
  • 라이선스와 저장소 위치가 명시되어 인수인계가 가능한가

구조 — 참여 부품

B3 지식 접지 상담 업무 컴포넌트

기관 규정·매뉴얼·사례 문서에 접지(RAG)해 질문에 답하고, 답마다 출처를 붙이며, 근거가 없으면 답하지 않고 담당자에게 넘긴다.

PAX 사례 48건이 이 부품을 쓴다

맥락

규정·매뉴얼·FAQ·사례가 문서로 쌓인 기관에서 내부 검색·검수, 대민 자동응답, 폐쇄망 로컬 검색에 쓴다. PAX 557건에서 주 부품이 B3인 사례는 31건으로 B0·B1 다음이다. 유형 ① 대민 상담·안내의 기본 조립이기도 하다.

맞서는 힘(긴장)

  • 답변 범위 vs 환각 위험(근거 밖 답변 금지)
  • 대민 자동응답의 효율 vs 예외 건 이관 필요
  • 검색 품질 개선 vs 평가 세트 없이는 개선을 잴 수 없음
  • 폐쇄망 요구 vs 로컬 임베딩·모델 품질

해법

기관 문서를 A1 자산으로 정리해 임베딩·색인하고, 질문이 오면 검색한 근거 범위 안에서만 모델이 답하게 한다. 답에는 출처(F1)를 상시 붙이고, 근거가 없으면 '확인 불가'로 답하거나 담당자·소관기관으로 이관한다(B′2). 검색 품질은 Hybrid Retriever·Query Rewriting·Reranker로 높이되, 변경마다 C9 평가 세트로 잰다. 대민형은 한계 안내(F7)와 폴백(C7)을 두고, 문서 갱신 주기를 C6으로 정한다.

이럴 때 쓴다

  • 같은 질문이 반복되고 답의 근거가 기관 문서에 있을 때
  • 답변에 조문·문서 출처를 반드시 붙여야 할 때
  • 유형 ① 대민 상담·안내, 유형 ⑦ 법령 접지 점검

이럴 때는 쓰지 않는다

  • 평가 세트가 없어 검색 품질을 잴 수 없을 때(먼저 C9, X10)
  • 질문 유형이 몇 개로 정해져 행동 선택기(S4)나 규칙 조회로 충분할 때
  • 문서를 요약해 초안을 쓰는 것이 핵심이면(B1)

얻는 것

  • 답변에 근거를 댈 수 있음
  • 반복 질의 처리 시간 단축
  • 범정부 엔진 + 기관별 코퍼스로 공유 가능

점검표

  • 답마다 출처가 표시되는가
  • 근거가 없을 때 답하지 않고 이관하는가
  • 평가 세트로 검색·답변 품질을 재고 있는가
  • 코퍼스 갱신 주기와 책임자가 정해져 있는가

구조 — 참여 부품

  • A1 데이터 자산 서비스 — 코퍼스 정제·등급 메타
  • A2 모델 서빙 계층 — 임베딩·생성 모델(폐쇄망이면 로컬)
  • 검색기 — 벡터·키워드 검색, 재작성·재순위
  • C5 가드레일 필터 — 출처 검증·근거 밖 답변 차단
  • F1 출처 표시 — 근거 문서·조문을 답에 표시
  • 담당자 — 내부형 검수, 대민형 예외 건 처리

변형

  • 내부 검수형: 직원이 쓰고 답을 검수(Enabled)
  • 대민 자동응답형: 국민에게 직접 답하고 예외만 이관(이관 분기가 있으면 First)
  • 폐쇄망 로컬 RAG: 내부망 LLM + 로컬 임베딩·벡터DB
  • 검색 품질 하위 항목: Hybrid Retriever(벡터+키워드)·Query Rewriting·Reranker. 태깅 시 variant에 기재(Fowler)
  • 그래프 RAG: A6 지식그래프를 검색에 결합(rag_type = Graph)

A4 데이터 연계 서비스 공통 서비스

타 기관 데이터를 연계 계약과 표준 인터페이스·키 매핑으로 결합해 한 기관의 데이터로는 풀 수 없는 문제의 기준선을 만든다.

PAX 사례 11건이 이 부품을 쓴다

맥락

타 기관·민간 데이터를 결합해야 하는 과제에 쓴다. 유형 5a·10·11의 기반이다(§7.3). 전이 차단 요인 '기관 간 협약'(R8)에 바로 걸린다.

맞서는 힘(긴장)

  • 결합 데이터의 가치 vs 개인정보·기업비밀 보호
  • 계약·협의 기간 vs 과제 일정
  • 실시간 연계 vs 연계 기관 시스템 부담

해법

연계 계약(또는 협약)과 키 매핑 규칙을 먼저 확정하고, 표준 인터페이스로 결합한다. 식별자가 민감하면 가명키·키맵 분리 보관으로 결합하고, 원본·마스킹·제출용 데이터를 분리한다. 결합 결과는 A1 기준선처럼 정의서(결합키·변수 정의)로 문서화한다. 상대 기관이 원자료 제공에 난색을 보이면 그룹핑·집계 수준으로 협의안을 만들고, 기존 전산망을 재활용해 자동 전송한다.

이럴 때 쓴다

  • 한 기관 데이터로는 예측·판정 근거가 부족할 때
  • 타 기관 데이터로 신청 정보의 누락·불일치를 교차 확인할 때
  • 관할이 갈린 다부처 데이터를 하나의 파이프라인으로 묶을 때

이럴 때는 쓰지 않는다

  • 공개 API를 조회만 하면 A3
  • 자기 기관 기록만 정제하면 A1
  • 계약 없이 '연계 예정'만 있으면 태그하지 않는다(계획서 단계)

얻는 것

  • 단일 기관으로 불가능한 판정 근거 확보
  • 재사용 가능한 연계 설계(키·정의서)
  • 가점 ➋ 대상

점검표

  • 연계 계약·협약이 체결되었는가
  • 결합키·변수 정의서가 있는가
  • 키맵과 원본이 분리 보관되는가
  • 연계 중단 시 서비스가 어떻게 되는지 정해져 있는가

구조 — 참여 부품

  • 연계 기관 — 데이터를 제공하고 계약 조건을 정함
  • 키 매핑·가명결합 절차 — 공통 연계키로 레코드를 잇고 식별자를 보호
  • A1 데이터 자산 서비스 — 결합 결과를 기준선으로 정의·버전 관리
  • C5 가드레일(비식별) — 결합 전후 민감정보 처리

변형

  • 가명결합형: 이중 식별축 가명키와 원본/마스킹/제출용·키맵 분리 보관으로 여러 기관 데이터를 결합한다.
  • 시공간 결합형: 기관 시설 좌표·행정구역에 기상청 등 공공 API 값을 최근접·구역 단위로 맞춘다.
  • 동의 기반 마이데이터형: 공통 연계키로 공공·민간 데이터를 당사자 동의로 결합한다.
  • 협의·전산망 재활용형: 제공 기관의 우려를 집계 수준 협의안으로 풀고 기존 전산망으로 자동 전송한다.

A1 데이터 자산 서비스 공통 서비스

흩어진 업무 기록을 정제·라벨링해 AI 부품이 붙여 쓸 수 있는 데이터셋·라벨·데이터 사전 형태의 기준선으로 제공한다.

PAX 사례 110건이 이 부품을 쓴다

맥락

학습 모델(A2.5·B2), 지식 접지(B3)의 코퍼스, 평가 세트(C9)의 정답 출처가 필요한 과제라면 모두 이 부품을 쓴다. 서비스 유형 5a·9·10·11에서는 필수 기반이다. 비LLM 규칙 기반 대민 안내에서는 A2를 거치지 않고 결정론 조회의 대상이 된다(R21).

맞서는 힘(긴장)

  • 정제 품질 vs 구축 기간·라벨링 인력 비용
  • 과제 전용 가공(빠름) vs 기관 공통 기준선(재사용)
  • 데이터 활용 범위 vs 데이터 등급(E5) 보호
  • 기준선 고정(재현성) vs 원천 갱신 반영

해법

원천 기록을 수집→정제(중복·결측 처리)→라벨링→정의 문서화 순으로 가공하고, 결과를 정제 데이터셋·라벨·데이터 사전의 세 산출물로 고정해 제공한다. 'N건→M건 정제'처럼 정제 전후 규모와 기준을 기록하고, 변수·테이블·인터페이스 정의서로 소비 부품이 같은 정의를 쓰게 한다. 기준선은 버전으로 관리해 C9 평가 세트의 정답 출처와 C6 재학습의 입력으로 재사용한다. 데이터 경계는 부품별로 두고(DB per Service), 타 기관 데이터와의 결합은 A4로 분리한다.

이럴 때 쓴다

  • 예측·추천기(B2)나 비전 모델(A2.5)을 학습·재학습할 때
  • 지식 접지(B3)의 코퍼스를 구축할 때
  • 평가 세트(C9)의 정답 출처가 필요할 때
  • 서비스 유형 5a-agg·9·10·11처럼 A1이 필수인 조립

이럴 때는 쓰지 않는다

  • 공공 API 응답을 가공 없이 조회만 할 때(A3)
  • 정제·정의 없이 파일을 올려 바로 검색하는 경우(태그 대상 아님)
  • 타 기관 데이터 결합이 핵심일 때는 A4를 함께 태그해 계약·키 매핑을 따로 드러낸다

얻는 것

  • 모델 교체와 무관하게 남는 기관 자산
  • C9·C6·B3가 같은 기준선을 재사용
  • 데이터 사전이 기관 간 표준 확산의 단위가 됨

점검표

  • 정제 전후 규모와 정제 기준이 기록되어 있는가
  • 데이터 사전(정의·단위·출처)이 있는가
  • 기준선에 버전이 있고 평가용 분할이 학습용과 분리되어 있는가
  • 데이터 등급(E5)에 맞는 가명·비식별 처리가 적용되었는가

구조 — 참여 부품

  • 원천 시스템·기록 — 가공 전 업무 기록을 내주는 출처
  • 정제·라벨링 파이프라인 — 중복 제거·결측 처리·라벨 부여·품질관리를 수행
  • 데이터 사전 — 정의·단위·출처를 문서로 고정해 소비 부품이 같은 뜻으로 쓰게 함
  • C9 평가 세트·회귀시험 — 기준선을 정답 출처로 사용
  • A2.5 비LLM 학습 모델 — 기준선으로 학습·재학습하는 소비 부품

변형

  • 학습데이터 구축형: 영상·이미지 등을 수집해 품질관리 단계(중복 제거·재라벨링·학습/검증/평가 분리)를 거쳐 학습 기준선으로 만든다.
  • RAG 코퍼스 정본화형: 법령·규정 원문을 현행 시행본 기준으로 정본화하고 조문 구조·메타데이터를 부여해 색인한다.
  • 지표 표준화형: 여러 자료원의 지표를 도메인별로 표준화하고 정의·단위·분모·결측·원본 링크를 메타데이터로 관리한다.
  • 자동 피처 파이프라인형: 수집→정제→파생 변수 생성→자동 검증→담당자 승인을 주기 실행하고 승인만 사람에게 남긴다.

F1 출처 표시 상호작용 패턴

PAX 사례 87건이 이 부품을 쓴다

맥락

맞서는 힘(긴장)

  • 출처 상세도 vs 화면 복잡도
  • 출처 표시 vs 실제 검증(표시만 하고 검증하지 않으면 잘못된 신뢰)
  • 원문 링크의 신선도 vs 유지 비용

해법

이럴 때 쓴다

  • B3 지식 접지 응답 전반
  • 대민 서비스 D1~D7(F1·F2·F7이 최소 요건)
  • 유형 ①⑤b⑦⑨처럼 F1이 필수인 유형

이럴 때는 쓰지 않는다

  • 모델의 판정 근거(요인·BBox·사유 코드)를 보여 주려는 경우(F9)
  • B0 결정적 도구로 원천 데이터를 그대로 보여 주는 경우(출처가 곧 화면)

얻는 것

  • 이용자 신뢰 확보
  • 원문 대조로 오류 발견
  • 공식 판단 여부를 이용자가 스스로 확인

점검표

  • 모든 답변에 출처가 붙는가
  • 출처가 원본과 대조되는가
  • 갱신 시각이 보이는가
  • 이용자가 원문을 바로 열 수 있는가

구조 — 참여 부품

  • C5 가드레일 필터 — 출처 검증
  • 이용자 — 원문을 열어 대조

변형

D8.4 대조·점검 서비스 블록

법령·규정·서식·인용·근태·보안 기준과 대조해 확인할 대상을 먼저 골라 주는 내부 운영 블록이다. "최종 판단은 사람"이 가장 자주 붙는다.

PAX 사례 81건이 이 부품을 쓴다

맥락

기관 내부 문서·자료를 기준과 대조하는 업무. §7.3 유형 ⑦ 대조·점검 도우미(D8.4, P0~P1)와 유형 ⑩ 위험 예측·표적 선별(D6·D3·D8.4)의 무대. PAX 81건(주 부품 B0 73%, B1 12%), 감사·법무 25건·문서·기안 12건.

맞서는 힘(긴장)

  • 점검 범위 확대 vs 오탐으로 인한 확인 부담
  • 규칙 점검의 결정성 vs LLM 대조의 유연성
  • 점검 대상이 점검기를 속이는 위협 vs 자동 점검
  • 출처 대조의 엄격성 vs 원문 접근 권한(공공 API 인가)

해법

기준이 규칙으로 옮겨지면 B0 규칙 점검기로, 해석이 필요하면 B3 법령 접지로 대조한다. 기준 원문은 A3 공공 API(법령·판례)에서 가져와 C5 출처 검증으로 인용이 실제 원문과 일치하는지 확인한다. 결과는 판정이 아니라 "확인할 대상 목록"으로 내고, C1으로 "최종 판단은 사람"을 명시하며, F7 한계와 F1 출처를 붙인다. 점검 대상 문서·코드가 점검기를 속이지 못하게 대상별 격리(S6)나 고정 규칙 실행(S4)을 쓰고, 코드 점검이면 S9 샌드박스를 둔다. C9 평가 세트로 누락률을 잰다.

이럴 때 쓴다

  • 문서·자료를 법령·규정·서식과 한 줄씩 대조하는 업무
  • 인용·근거가 원문과 맞는지 확인해야 할 때
  • 점검 대상이 많아 확인 대상을 먼저 좁혀야 할 때

이럴 때는 쓰지 않는다

  • 국민 신청 건의 자격 판정이면 D3
  • 현장 시설을 관측해 점검하면 D6
  • 대조 없이 자료를 찾아 보여 주면 D8.1

얻는 것

  • 대조 시간 단축과 누락 감소
  • 사람 판단을 확인 대상에 집중
  • 인용 오류의 사전 차단

점검표

  • 결과가 판정이 아닌 확인 대상으로 표시되는가
  • 근거 원문 출처가 연결되는가
  • 누락률을 평가 세트로 재는가
  • 점검 대상 속 문장이 점검 결과를 바꾸지 못하는가

A3 공공 API 제공자 공통 서비스

정부·공공이 운영하는 모델·데이터·개발 도구(범정부 AI 공통기반, 모두의 AI 실험실, 공공데이터포털, 공공 깃랩)를 범정부 Provider로 소비한다.

PAX 사례 154건이 이 부품을 쓴다

맥락

모델·공공데이터·법령 원문·개발 환경을 공공 플랫폼에서 가져올 수 있다면 어느 과제든 해당한다. §7.1 2단계 '기반 부품은 새로 만들지 말고 Provider에서 먼저 찾는다'가 바로 이 부품을 가리킨다. 유형 7(대조·점검)에서는 법령·기준 출처를 대는 필수 기반이다.

맞서는 힘(긴장)

  • 공통 Provider 재사용 vs 기관 고유 요구 반영
  • 공공 API 가용성·갱신 주기 vs 서비스 신뢰성
  • 인가·검증 절차의 통제 vs 에이전트 루프의 병목(PAX 공공API 진단)

해법

기반을 새로 만들기 전에 범정부 AI 공통기반(모델), 공공데이터포털·법령 API(데이터), 모두의 AI 실험실·공공 깃랩(개발·실험 환경)에서 먼저 찾아 소비한다. 인증은 GPKI·디지털원패스 같은 연합 신원(Federated Identity)으로 위임하고, 공공 API 응답은 출처·조회 시각과 함께 업무 부품에 넘긴다. 에이전트가 부를 수 있게 하려면 A8 MCP 서버로 감싸고, 결과를 재가공해 기준선으로 고정하면 A1을 더한다. 기관이 만든 도구는 공공 깃랩에 등재해 다음 기관의 Provider가 되게 한다.

이럴 때 쓴다

  • 모델·데이터·개발 환경을 기관이 새로 만들려 할 때 — 먼저 Provider 확인
  • 법령·기준 원문을 최신으로 대조해야 하는 유형 7
  • 여러 부서가 같은 기반을 따로 만들고 있을 때(X3 교정)

이럴 때는 쓰지 않는다

  • 필요한 모델·데이터가 공공 Provider에 없을 때(만들고 레지스트리에 올림)
  • 타 기관 데이터를 계약·키 매핑으로 결합하는 경우는 A4

얻는 것

  • 기관별 중복 구축 방지(X3 교정)
  • 공인된 원천 데이터·모델 사용
  • 등재를 통해 전이 경로 확보

점검표

  • 같은 기반을 기관 안에서 따로 만들지 않았는가
  • 공공 API 응답의 출처·조회 시각이 결과에 남는가
  • API 장애·변경 시 어떻게 되는지 답할 수 있는가
  • 만든 도구가 공공 깃랩 등에 등재되었는가

구조 — 참여 부품

  • 연합 신원 인증 — GPKI·디지털원패스 등으로 호출 주체를 확인

C1 검토 큐 운영 컴포넌트

AI 산출물이 다음 단계로 넘어가기 전에 사람이 맞고 틀림을 확인·수정·확정하는 대기열을 두어, 오류가 업무 결과로 흘러가지 않게 한다.

PAX 사례 46건이 이 부품을 쓴다

맥락

AI 산출물이 공문·처분·대민 안내·기록으로 이어지는 모든 B 부품(B1 코파일럿, B4 인식 파이프라인, B2 예측기, B7 콘텐츠 생성기 등). 이용자 본인이 최종 확정자인 자기서비스형 도구도 포함한다(R16).

맞서는 힘(긴장)

  • 정확성·책임성 vs 처리 속도(전건 검토는 자동화 이득을 깎는다)
  • 검토자의 숙련 vs 자동화 편향(AI 결과를 그대로 승인하는 경향)
  • 전건 검토의 안전 vs 위험도별 분기(C2)로 가야 하는 효율 압력

해법

AI 산출물에 신뢰도·근거를 붙여 검토 대기열에 올리고, 검토자가 승인·수정·반려 중 하나를 고르게 한다. 수정·반려 내역은 C4 감사 로그에 남겨 수정률을 집계하고 C6 환류의 입력으로 쓴다. 검토 화면은 원문 위치·근거를 함께 보여 줘 확인 비용을 줄인다. 전건 검토로 시작하되, 수정률 실측이 쌓이면 C2 위험도 라우터로 저위험 건을 자동 종결하는 단계로 옮긴다.

이럴 때 쓴다

  • AI 산출물이 공문·처분·대민 안내로 그대로 이어질 때
  • E4가 P1 이상이고 되돌리는 데 사람 시간이 많이 드는 조치가 있을 때
  • 서비스 유형 ② 접수·심사, ④ 기안 코파일럿, ⑥ 콘텐츠 제작, ⑦ 대조·점검, ⑩ 위험 예측, ⑪ 추천·매칭, ⑫ 개발 코파일럿처럼 C1이 필수인 유형

이럴 때는 쓰지 않는다

  • B0 결정적 도구처럼 런타임 AI 산출물이 없을 때
  • 쉽게 되돌릴 수 있고 저위험인 조치를 이미 C2로 자동 종결하도록 실측 근거를 갖춘 구간(전건 검토를 영원히 남기지 않는다)

얻는 것

  • 오류가 업무 결과로 나가기 전에 차단
  • 책임 소재가 명확해짐
  • 수정 내역이 C4 지표와 C6 환류의 원천 데이터가 됨

점검표

  • AI 산출물이 확정 전 상태로 머무는 지점이 명시되어 있는가
  • 검토자와 승인·수정·반려 선택지가 정해져 있는가
  • 검토 결정과 수정 내역이 로그로 남는가
  • 실증 기간의 검토·수정 건수가 기록되어 있는가
  • 전건 검토에서 분기로 옮길 조건이 정해져 있는가

구조 — 참여 부품

  • 검토 대기열 — AI 산출물을 확정 전 상태로 보관하고 검토자에게 배정
  • 검토자(담당자 또는 이용자 본인) — 승인·수정·반려를 결정하는 최종 책임자
  • F2 편집 가능한 출력 — 검토자가 산출물을 직접 고치는 화면
  • C4 감사 로그·지표 — 검토 결정과 수정 내역을 적재해 수정률로 집계

변형

  • 예외 검수형: 정상 건은 일괄 승인하고 저신뢰 항목만 개별 검수하는 검수 UI

X3 부서마다 챗봇 안티패턴

같은 기관의 과제들이 각자 모델·벡터DB·프롬프트를 따로 만들어, 공유할 수 있는 기반 부품을 부서 수만큼 중복 구축하는 함정이다.

맥락

한 기관 안에서 여러 부서가 동시에 대민·내부 챗봇, 문서 검색, 요약 도구를 추진하는 경우. 특히 각 과제가 상용 API를 직접 호출하는 경우.

맞서는 힘(긴장)

  • 부서의 빠른 자율 구축 vs 기관 전체의 중복 비용
  • 부서별 맞춤(코퍼스·문체) vs 공통 모델·게이트웨이
  • 과제 단위 예산·성과 vs 공통 기반 등재·유지 책임

해법

§7.1의 두 번째 단계대로 기반 부품은 새로 만들지 말고 Provider에서 먼저 가져온다. 모델 호출은 A2 모델 서빙 계층(범정부 AI 공통기반 또는 기관 게이트웨이) 뒤로 모으고, S1 단일 진입점에서 인증·요청 상한·비용 상한·감사 기록을 일괄 적용한다. 공공 API·공공 클라우드·공공 깃랩은 A3 공공 API 제공자로 쓴다. 부서별 차이는 모델을 따로 두지 말고 A9 업무 규범 스킬과 부서 코퍼스(A1)로 표현하며, 부서·등급별 코퍼스 분리가 필요하면 S2 권한 인식 검색으로 푼다. 없어서 새로 만든 부품은 §13 참조 구현 레지스트리에 올린다.

이럴 때 쓴다

  • 같은 기관의 두 과제 이상이 각자 모델 계약·API 키·벡터DB를 갖는다
  • 범정부 AI 공통기반·공공 API를 쓰지 않은 이유가 서술되지 않는다
  • 공통 규정·매뉴얼 코퍼스를 과제마다 따로 임베딩한다
  • 모델 호출 비용을 기관 단위로 집계할 수 없다

이럴 때는 쓰지 않는다

  • 데이터 등급(E5)이나 망 조건(E1) 때문에 공통 기반을 쓸 수 없고 그 사유가 서술된 경우
  • A2 게이트웨이를 공유하면서 부서별 코퍼스·스킬만 따로 둔 경우(정상 조립)
  • 개인이 만든 단일 도구로 기관 내 중복 과제가 없는 경우

얻는 것

  • 부서가 협의 없이 빠르게 만든다
  • 부서 요구에 딱 맞는 맞춤 구성을 갖는다

X10 평가 없는 RAG, RAG 없는 튜닝 안티패턴

평가 세트 없이 검색을 붙여 '좋아진 것 같다'로 배포하고, 검색으로 풀릴 문제를 파인튜닝으로 푸는, 진행 경로를 건너뛰는 함정이다.

맥락

B3 지식 접지·B1 코파일럿에 RAG를 붙이거나 A2.3 튜닝형 모델을 만드는 과제, 특히 규정·매뉴얼 기반 질의응답.

맞서는 힘(긴장)

  • 눈에 보이는 기술 성과 vs 지루한 평가 세트 구축
  • 빠른 배포 vs 변경마다 재는 자
  • 자체 모델 보유 인상 vs 검색으로 충분한 문제

해법

§7.2 진행 경로를 순서대로 밟는다. B1 직접 프롬프트에서 시작해 두 번째 단계에서 C9 평가 세트(업무 질문·정답·채점 기준)를 먼저 만들고, 이후 A9 규범 스킬·F4, B3 지식 접지(A1 데이터 자산), B3 검색 품질(Hybrid·Rewriting·Reranker), C5 가드레일·F1 순으로 붙이며 매 단계를 C9로 잰다. A2.3 튜닝은 진행 경로의 마지막 단계로, 검색·규범 스킬로 풀리지 않는다는 것이 C9 점수로 확인됐을 때만 한다. 모델·프롬프트·설정 조합은 릴리스처럼 버전 관리한다.

이럴 때 쓴다

  • RAG·튜닝을 도입했는데 업무 질문·정답·채점 기준 세트가 없다
  • '답변 품질 향상'을 수치 없이 서술하거나 단발 정확도만 보고한다
  • 자주 바뀌는 규정·매뉴얼 질의를 파인튜닝으로 풀었다
  • 검색 품질(재현율·리랭킹)을 재지 않고 튜닝으로 넘어갔다

이럴 때는 쓰지 않는다

  • C9 세트로 RAG 전후를 비교한 뒤 배포한 경우
  • 검색·스킬로 풀리지 않음을 C9 점수로 확인한 뒤 튜닝한 경우
  • B2·B4처럼 비LLM 학습 모델로 원래 학습이 해법인 경우(RAG가 대안이 아님)

얻는 것

  • RAG·튜닝이라는 눈에 보이는 기술 성과를 빨리 낸다
  • 평가 세트 구축에 현업 시간을 쓰지 않는다

점검표

  • 업무 질문·정답·채점 기준 세트가 있는가
  • RAG 전후 점수 비교가 있는가
  • 튜닝을 선택한 근거가 C9 점수로 설명되는가
  • 모델·프롬프트·설정 조합이 버전 관리되는가

구조 — 참여 부품

  • C9 평가 세트·회귀시험 — 빠진 부품. 모든 변경을 같은 자로 잼
  • B3 지식 접지 — 튜닝 전에 먼저 시도할 검색 기반 접지
  • A2.3 튜닝형 모델 — 진행 경로의 마지막 단계
  • A1 데이터 자산 서비스 — 정답 출처와 검색 코퍼스

변형

  • 평가 없는 RAG: 검색을 붙이고 몇 개 질문을 눈으로 보고 배포
  • RAG 없는 튜닝: 문서 검색으로 풀릴 최신 규정 질의를 파인튜닝으로 해결하려 함
  • 평가 없는 튜닝: 튜닝 전후를 같은 세트로 비교하지 않음

관련 부품
