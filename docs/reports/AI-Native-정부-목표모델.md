## 0. 이 문서의 뼈대 — 세 개의 층위와 의존 관계

"AI-Ready", "Agentic", "AI-Native"는 같은 말의 다른 표현이 아니다. **아래층이 성립하지 않으면 위층은 원리적으로 불가능한 적층 구조**다.

```
┌──────────────────────────────────────────────────────┐
│  Ⅳ. AI-NATIVE 정부   — 제도·조직·행정 프로세스 계층    │
│     "정부가 AI를 전제로 재설계된다"                    │
│     Rules as Code · 선제적 행정 · 알고리즘 거버넌스     │
├──────────────────────────────────────────────────────┤
│  Ⅲ. AGENTIC API      — 인터페이스·행위 계층            │
│     "에이전트가 자율적으로 발견·인가·호출·행위한다"     │
│     MCP · OAuth M2M · 멱등성 · 위임 체인               │
├──────────────────────────────────────────────────────┤
│  Ⅱ. AI-READY 데이터  — 자원·의미 계층                  │
│     "기계가 데이터의 의미를 오해 없이 해석한다"          │
│     스키마 · 코드북 · 계보 · 신선도 · 인용가능성         │
└──────────────────────────────────────────────────────┘
        ↑ 각 층은 아래층의 완성도를 상한선으로 갖는다
```

**의존 관계의 실제 함의:**

- AI-Ready 데이터 없이 Agentic API를 만들면 → **에이전트가 빠르고 정확하게 틀린 답을 낸다.** (`9999`가 결측인지 값인지 모르는 채 통계를 산출)
- Agentic API 없이 AI-Native 정부를 선언하면 → **챗봇 UI만 바뀌고 뒷단은 그대로다.** (사람이 하던 일을 AI가 대신 스크래핑)
- 그리고 **한국은 현재 Ⅱ층조차 미완성 상태에서 Ⅳ층을 논의하고 있다.** 이것이 "공공 AI 에이전트 공표만 되고 미출시", "검증·신뢰 체계(18억)를 운영형 MCP보다 우선"이라는 GAPI2 관찰의 구조적 배경이다.

# Ⅰ. 근본 문제 — 왜 같은 증상이 반복되는가

선행 문서에서 정리한 7계층(프로토콜 정직성 / 포맷 / 기계 발견성 / 인증·인가 / 파편화 / 도구 생태계 / 경제성)은 **증상**이다. 4개월간 개발자 불만 TOP10 완전 해소 0건, 기관별 대응 항목 개선율 정확히 0%라는 결과는 증상 목록으로 설명되지 않는다. 아래는 그 **아래에 있는 12개 근본 결함**이다.

## A. 목적 설계의 결함

### 1. "개방"을 목적으로 삼고 "사용"을 목적으로 삼지 않았다

한국 공공데이터 체계의 성립 목적은 **투명성·공개(disclosure)** 였다. 이것이 OECD OURdata Index 4회 연속 1위(0.93/1.0)를 만들었다. 그러나 개방 패러다임과 제품 패러다임은 성공 조건이 완전히 다르다.

| | 개방(Disclosure) 패러다임 | 제품(Product) 패러다임 |
|---|---|---|
| 성공 = | 공개했다 | 사용됐다 |
| 지표 | 개방 데이터셋 수 | 활성 이용자·호출 성공률·재사용 사례 |
| 완료 시점 | 게시 시점 | 없음 (지속 운영) |
| 품질 기준 | 원본 충실성 | 이용자 성공 |
| 실패 정의 | 미공개 | 공개했으나 아무도 못 씀 |

**핵심**: 개방 패러다임에서 "HTTP 200으로 오류 반환"은 실패가 아니다. 데이터는 공개돼 있기 때문이다. 제품 패러다임에서만 그것은 치명적 결함이 된다. **한국은 개방 패러다임의 챔피언이며, 바로 그 이유로 제품 품질이 낮다.** 이것은 모순이 아니라 인과다.

### 2. 공급자 논리: "던져두면 민간이 알아서 쓴다"

원천 시스템의 데이터를 최소 가공으로 노출하는 것이 기본 설계다. 그 결과:

- 내부 코드값이 그대로 노출 (기관마다 다른 코드 체계)
- 원천 DB의 컬럼명·자료형이 API 필드로 직행
- 이용자가 필요로 하는 **결합·정규화·요약**은 전적으로 이용자 부담

에이전트 시대에 이 부담은 **토큰 비용으로 정량화**된다. GAPI2 실측: 검색 1페이지 132,810 토큰, **가시 정보율 3.2%**. 즉 이용자에게 전가된 가공 비용의 크기다.

### 3. 개방 범위의 수요 비연동 — "열기 쉬운 것부터 열렸다"

무엇을 개방할지가 **기관의 개방 용이성**으로 결정되고 **사회적 수요**로 결정되지 않는다. 수요 신호를 수집·반영하는 상설 메커니즘이 없다.

> 역설적 증거: 커뮤니티 MCP 79종의 분야 분포(법령·사법 17 · 통계 14 · 조달 11 · 금융·공시 9)가 **실제 수요의 지도**다. 민간이 자비로 만든 래퍼의 분포가 정부의 개방 우선순위보다 정확한 수요 정보를 담고 있다.

## B. 책임·조직 구조의 결함

### 4. 소유자는 있으나 운영자가 없다 — Product Owner의 부재

**"이 API의 책임자는 누구인가?"** 에 답할 수 있는 조직 구조가 없다. 데이터 소관 부서는 있지만, API를 *제품으로* 운영하는 주체 — 이용자 피드백을 받고, 로드맵을 정하고, 품질에 책임지는 역할 — 가 정의돼 있지 않다.

**귀결**: 무공지 점검·다운타임(불만 8위, 미개선), 갱신 주기 표기와 실측의 괴리, API Key 2년 만료 무통보 폐기. 모두 "운영 주체가 있다면 발생할 수 없는" 유형의 문제다.

### 5. 파편화는 사고가 아니라 제도의 산출물이다

215개 포털은 실수의 누적이 아니라 **합리적 개별 선택의 총합**이다.

```
기관별 정보화 예산 배정
   → 각 기관이 자기 예산으로 자기 포털 구축이 합리적
   → 통합의 비용은 개별 기관이 부담, 편익은 국가가 수취
   → 아무도 통합을 시작할 유인이 없음
   → 신규 포털은 계속 생성 (2026-08 재조사에서 22개 신규 발굴)
```

**이것은 조정 실패(coordination failure)의 교과서적 사례다.** 따라서 "통합하자"는 권고로는 절대 해결되지 않는다. **비용-편익 구조 자체를 바꾸는 제도 개입**이 있어야만 움직인다.

> 🟢 반증 사례가 이미 존재한다: **LOCALDATA 통합 폐지**(2026-01~04, 인허가 195종·생활편의 14종을 data.go.kr로 흡수 후 누리집 종료). 그리고 **국가데이터처 신설**(2025-10). 즉 **비용-편익 구조를 바꿀 권한을 가진 주체와 첫 성공 선례가 이미 확보됐다.**

### 6. 표준의 부재가 아니라 표준 강제 게이트의 부재

기술 표준 문서는 존재한다. 문제는 **미준수의 결과가 없다**는 것이다.

- API 등록 심사가 **품질 게이트로 작동하지 않는다** (등록 = 목록 등재)
- HWP 명세를 첨부해도 등록이 반려되지 않는다 → 그래서 문서 품질 개선 **0/18**
- OpenAPI 미제공이 등록 결격 사유가 아니다 → 그래서 **1/215 (0.5%)**

**개선율 분포가 이를 증명한다**: 게이트웨이 중앙 설정 항목 4~8% vs 기관별 개별 작업 항목 **0%**. 강제 게이트가 없으면 자발적 개선은 통계적으로 0에 수렴한다.

## C. 경제·조달 구조의 결함

### 7. 구축 예산은 있고 운영 예산은 없다

공공 정보화 예산은 **구축(SI) 중심**으로 편성되고, 유지보수는 정률(요율) 방식으로 최소 배정된다.

| | 구축 단계 | 운영 단계 |
|---|---|---|
| 예산 | 충분 | 요율 기반 최소 |
| 성과 인정 | 준공 = 성과 | 없음 |
| 가능한 활동 | 신규 개발 | 장애 대응만 |
| **품질 개선** | 명세에 없으면 불가 | **예산 항목 자체가 없음** |

**귀결**: "HTTP 상태코드를 정상화하자"는 작업은 **어느 예산 항목에도 속하지 않는다.** 신규 구축이 아니고 장애 대응도 아니다. 그래서 4개월이 아니라 10년이 지나도 안 된다. 이것이 "serviceKey 이중 인코딩 Critical·미개선"의 진짜 이유다.

### 8. 발주자가 품질을 정의할 수 없다

- 일괄 발주 + 기능 명세 중심 → API 품질 특성(오류 의미론, 응답 포맷, 명세 제공)이 **RFP에 들어가지 않는다**
- 발주 기관에 API 설계를 검수할 내부 역량이 없다 → 수행사 관행이 그대로 산출물이 된다
- 최저가·단기 납기 → 표준 준수는 비용으로만 인식된다

### 9. 레거시의 자기 복제

2010년대 XML/SOAP 설계가 **템플릿으로 상속**된다. 신규 API도 기존 API를 복사해 만들기 때문에 `resultCode`를 바디에 넣고 HTTP 200을 반환하는 패턴이 재생산된다.

**증상이 아니라 유전자다.** 그래서 "신규 API부터 표준 적용"이 실효를 가지려면 **표준 준수 레퍼런스 구현(reference implementation)과 스캐폴딩을 정부가 직접 배포**해야 한다. 금지보다 복사할 좋은 원본을 주는 것이 빠르다.

## D. 법·제도 전제의 결함

### 10. 모든 것이 "자연인"을 전제로 설계됐다

| 전제 | 구현 | 에이전트 시대의 결과 |
|---|---|---|
| 이용자 = 사람 | 휴대폰 본인인증 | **하드블록** — 자동화 원천 불가 |
| 신청 = 사람의 의사표시 | 화면 폼 제출 | 관리 API 부재 → 스크래핑 강요 |
| 책임 주체 = 사람 | 개인 계정 | 조직·서비스·에이전트 계정 유형 없음 |
| 문의 = 사람의 질문 | 전화·게시판 | 기계 판독 가능 에스컬레이션 경로 없음 |

이것은 기술 결함이 아니라 **법적·제도적 전제**다. 따라서 게이트웨이 설정 변경으로 해결되지 않으며, GAPI2가 L1(에이전트 계정 유형 신설)을 **장기 18개월+** 로 분류한 이유다.

### 11. 이용 권리가 기계 판독 불가능하다

라이선스·재사용 조건·출처 표시 의무가 **산문으로만** 기술된다. 에이전트는 "이 데이터를 상업적으로 재배포해도 되는가"를 판단할 수 없다. AI 학습 사용 가부는 아예 언급되지 않는 경우가 많다.

**AI 시대에 이것은 새로운 차원의 문제다.** 데이터가 모델 학습·RAG·추론 결과에 들어갈 때 권리 관계가 불명확하면, 민간은 **법적 리스크 때문에 사용을 회피**한다. 개방했으나 쓸 수 없는 데이터가 된다.

## E. 피드백 루프의 결함

### 12. 이용자가 시스템 안에 존재하지 않는다

**개발자 불만 TOP10이 4개월간 완전 해소 0건**이라는 사실은, 그 불만이 시스템에 입력조차 되지 않고 있음을 뜻한다.

- 불만은 **"민원"으로 처리**되지 "버그 리포트"로 처리되지 않는다 → 개별 응답 후 종결, 근본 수정 없음
- **호출 실패율·오류 코드 분포·이탈 지점**을 수집·공개하지 않는다 → 무엇이 아픈지 모름
- 이용 통계가 **"호출 건수"** 로만 관리된다 → 실패한 호출도 성공으로 집계됨 (HTTP 200 문제와 결합하면 **실패율을 구조적으로 측정할 수 없다**)

> 🔴 **가장 위험한 신호**: GAPI2에서 **"부분측정" 배지 급증**. 외부에서 품질을 측정하는 것 자체가 어려워지고 있다. 측정 불가 → 개선 압력 소멸 → 추가 악화의 자기강화 루프.

# Ⅱ. AI-Ready 공공데이터 환경이란 무엇인가

## 2.1 정의

> **AI-Ready 데이터** = 기계가 **의미를 오해 없이** 해석하고, **출처를 검증 가능하게** 인용하며, **신선도를 판단**할 수 있는 상태로 제공되는 데이터.

핵심은 "기계가 읽을 수 있다"가 아니다. CSV는 기계가 읽는다. 그러나 컬럼 `STAT_CD`의 값 `03`이 무엇인지, `9999`가 결측인지 실제 값인지, 좌표가 WGS84인지 Bessel인지 모르면 **읽었으나 이해하지 못한 것**이다.

**Machine-Readable ≠ AI-Ready.** 전자는 파싱 가능성이고, 후자는 **의미 해석 가능성**이다.

## 2.2 AI-Ready 데이터의 5대 성립 조건

### 조건 1 — 발견 가능성 (Discoverable)

에이전트가 "이런 데이터가 필요하다"에서 출발해 **사전 지식 없이** 해당 데이터셋에 도달할 수 있어야 한다.

| 요소 | 목표 상태 | 표준 |
|---|---|---|
| 통합 카탈로그 | 전 부처·지자체 단일 검색 | DCAT-AP, schema.org/Dataset |
| AI 진입점 | 루트에서 구조 파악 가능 | `/llms.txt` (커뮤니티 관행), `/.well-known/` |
| 의미 기반 검색 | 키워드 아닌 의도 기반 | 임베딩 인덱스 + 시맨틱 검색 API |
| 데이터셋 식별자 | 영속 고유 ID | DOI 또는 URI (URL 변경에도 불변) |
| 관계 표현 | "이 데이터와 함께 쓰이는 것" | DCAT `qualifiedRelation`, 결합키 명시 |

> **현재 한국**: 통합 카탈로그가 215개 포털의 18%(31개)만 포괄. `llms.txt` 사실상 전무. 데이터셋 영속 식별자 미도입.

### 조건 2 — 의미 해석 가능성 (Semantically Interpretable) ⭐

**AI-Ready의 가장 본질적이고 가장 간과된 조건.** 데이터 옆에 **의미 계약(semantic contract)** 이 기계 판독 형태로 동반돼야 한다.

| 항목 | 반드시 명시할 것 | 미명시 시 발생하는 오류 |
|---|---|---|
| **코드값 사전** | 각 코드 필드의 전체 값 목록과 의미 (행정표준코드 연계) | `03`을 임의 해석 → 통계 왜곡 |
| **결측 표현** | `null` vs `""` vs `0` vs `9999` vs `-` 의 구분 규칙 | 결측을 0으로 집계 → **평균 붕괴** |
| **단위** | 원/천원/백만원, m/km, ℃/K | 1,000배 오차 |
| **시간대·기준시점** | KST/UTC, 기준일 vs 집계일 vs 게시일 | 시계열 정렬 오류 |
| **좌표계** | EPSG 코드 명시 (4326 / 5186 등) | 수백 m~수 km 위치 오차 |
| **집계 수준** | 개별/읍면동/시군구/전국, 중복 포함 여부 | 이중 계산 |
| **비공개 처리** | 마스킹·가명처리·비공개 셀 표시 규칙 | 마스킹값을 실값으로 오인 |
| **개정 규칙** | 잠정치/확정치 구분, 소급 개정 여부 | 확정 전 수치로 의사결정 |

> 💡 **이 조건이 왜 결정적인가**: LLM은 **모르는 것을 그럴듯하게 채우는** 특성이 있다. 의미 계약이 없으면 에이전트는 멈추지 않고 **추측한다.** 그리고 그 추측은 자연어로 유창하게 제시된다. **의미 계약의 부재는 침묵하는 오류가 아니라 유창한 오류를 생산한다.**

**목표 표준**: JSON Schema + 코드북 API + [Croissant](https://mlcommons.org/croissant/)(ML 데이터셋 메타데이터) 또는 Frictionless Data Package, 지리정보는 OGC API + EPSG 명시.

### 조건 3 — 신선도와 계보 (Fresh & Traceable)

| 요소 | 목표 상태 |
|---|---|
| 갱신 주기 | **선언값이 아니라 실측값 공개** — "일 1회"가 아니라 "최근 30일 실제 갱신 이력" |
| 최종 갱신 시각 | 레코드/데이터셋 단위 타임스탬프 + `Last-Modified` 헤더 |
| 조건부 요청 | `ETag` / `If-None-Match` → 변경 없으면 **304**, 토큰 0 소비 |
| 변경 이력 | 무엇이 언제 왜 바뀌었는지 (changelog API) |
| 계보(provenance) | 원천 시스템 → 가공 단계 → 개방까지의 경로 (W3C PROV-O) |
| 지연 시간 | 원천 발생 ~ 개방까지의 실제 latency 공개 |

> **K-GAPI가 "갱신 주기 실측 vs 공식 표기" 섹션을 별도로 둔 것은 정확한 문제 인식이다.** 에이전트가 "최신 데이터"라고 제시한 것이 3개월 전 것이면, 이는 데이터 오류가 아니라 **신뢰 파괴**다.

### 조건 4 — 인용 가능성·근거성 (Groundable & Citable) ⭐

**AI 시대에 새로 등장한 요구 조건이며, 환각(hallucination) 방지의 인프라 계층이다.**

에이전트가 "2025년 서울시 인구는 X명입니다"라고 답할 때, 이용자와 감사자가 **그 수치의 원본 레코드까지 역추적**할 수 있어야 한다.

| 요소 | 요구사항 |
|---|---|
| 레코드 영속 식별자 | 개별 레코드 단위 URI. 재조회 시 동일 값 보장 |
| 원문 링크 | 응답에 해당 레코드의 공식 페이지 URL 포함 |
| 스냅샷·버전 고정 | `?as_of=2026-08-04` — 과거 시점 재현 가능 |
| 무결성 검증 | 데이터셋 체크섬 |
| 권위 표시 | 이 값이 공식 확정치인지, 잠정치인지, 파생 계산인지 |
| 인용 포맷 제공 | 기계가 그대로 쓸 수 있는 citation 문자열 |

> **공공 영역에서 이것이 특히 중요한 이유**: 민간 데이터의 오류는 상업적 손해로 끝나지만, 공공 통계의 오류는 **정책 결정과 법적 효과**로 이어진다. AI가 공공데이터를 인용하는 시대에 **인용 가능성은 선택이 아니라 안전장치**다.

### 조건 5 — 사용 권리의 기계 판독성 (Machine-Readable Rights)

| 요소 | 목표 상태 |
|---|---|
| 라이선스 | SPDX 식별자 또는 CC 표준 URI로 기계 표기 |
| AI 사용 가부 | **학습(training) / 추론(inference·RAG) / 재배포**를 각각 명시 |
| 출처 표시 의무 | 필요 여부와 정확한 표기 문구를 기계 판독 형태로 |
| 상업적 이용 | 명시적 허용/제한 |
| 개인정보 포함 여부 | 가명처리 수준, 재식별 금지 조건 |

> 💡 **"AI 사용 가부의 3분할 명시"는 현재 어느 나라도 충분히 하지 않고 있으며, 선점 가치가 있는 영역이다.** 공공데이터의 AI 학습 활용 조건을 명확히 선언하는 것 자체가 국내 AI 산업의 리스크를 제거한다.

## 2.3 요약 — AI-Ready 데이터 체크리스트

```
□ 통합 카탈로그에서 발견 가능한가
□ 영속 식별자(DOI/URI)가 있는가
□ 기계 판독 스키마가 있는가 (JSON Schema)
□ 코드값 사전이 API로 제공되는가
□ 결측·단위·시간대·좌표계가 명시돼 있는가
□ 실측 갱신 주기가 공개되는가
□ ETag 조건부 요청이 되는가
□ 레코드 단위로 원문 역추적이 되는가
□ 과거 시점 재현(as_of)이 되는가
□ 라이선스가 SPDX/CC로 기계 표기돼 있는가
□ AI 학습/추론/재배포 가부가 각각 명시돼 있는가
```

# Ⅲ. Agentic AI 시대의 공공 API — 무엇이 바뀌어야 하는가

## 3.1 관점의 전환: "API 품질"이 아니라 "에이전트 루프의 완주율"

기존 평가는 **구현 여부**를 센다(OpenAPI가 있는가? CORS가 되는가?). Agentic 시대의 올바른 질문은 다르다:

> **"사전 지식이 전혀 없는 에이전트에게 목표를 주면, 사람의 개입 없이 완주하는가?"**

에이전트는 **6단계 루프**를 돈다. 각 단계가 하나라도 끊기면 전체가 실패한다. **API 품질은 각 항목의 평균이 아니라 최약 고리로 결정된다.**

## 3.2 에이전트 루프 6단계 — As-Is vs To-Be

### ① 발견 (Discover) — "무엇이 있는지 안다"

| | 현재 | 목표 |
|---|---|---|
| 경로 | 포털 HTML 검색 (**132,810 토큰**, 가시율 3.2%) | 카탈로그 API + 시맨틱 검색 (**~2,000 토큰**) |
| 범위 | 215개 포털 각각 | 단일 연합 카탈로그 |
| 진입점 | 없음 | `/llms.txt`, `/.well-known/api-catalog` |
| 결과 | 사람이 미리 URL을 알아야 함 | **의도 → 데이터셋 자동 도달** |

### ② 이해 (Understand) — "어떻게 쓰는지 안다"

| | 현재 | 목표 |
|---|---|---|
| 명세 | HWP/PDF 산문 (**OpenAPI 1/215 = 0.5%**) | **OpenAPI 3.x 100%** + JSON Schema |
| 의미 | 코드값·단위·결측 규칙 미제공 | 코드북 API + 의미 계약 |
| 예시 | 산문 속 예시 | 명세 내 `examples` + 실행 가능 샌드박스 |
| 결과 | 사람이 문서 읽고 래퍼 작성 | **명세 → MCP·SDK·함수스키마 자동 생성** |

> 🎯 **이 단계가 전체 루프의 최대 병목이다.** 명세가 없으면 이후 4단계 전부가 사람의 수작업에 의존한다. 커뮤니티 MCP 79종은 **사람이 HWP를 읽고 손으로 만든 것**이며, 이것이 "수요는 있는데 커버리지 5.6%"의 이유다.

### ③ 인가 (Authorize) — "쓸 권리를 얻는다" 🔴 최대 난제

| | 현재 | 목표 |
|---|---|---|
| 계정 | 휴대폰 본인인증 (**자동화 하드블록**) | **조직·서비스·에이전트 계정 유형** |
| 신원 수 | 전체 커버 시 **약 130개 ID** | **1~3개** (국가 신원 페더레이션) |
| 신청 | 화면 폼, 승인 대기 3일+ | **관리 API** (신청·발급·쿼터 조회) |
| 키 | URL 쿼리 `serviceKey` (로그·Referrer 유출) | OAuth 2.0 Client Credentials, 단기 토큰 |
| 갱신 | 2년 만료, 수동, 무통보 | 자동 갱신 + 사전 알림 |
| 체험 | 가입·신청 후에만 가능 | **공용 샌드박스 키 (신청 불요)** |
| 권한 | 전부 또는 전무 | scope 기반 최소권한 |
| 단계 수 | **9~13단계** (10개 API 조합 시 60~100+) | **0~2단계** |

**여기서 GAPI2의 핵심 문장이 나온다: "데이터는 열려 있지만 접근권을 얻는 절차가 닫혀 있다."**

> 🎯 **최우선 단일 조치 — 공용 샌드박스 키**: 미국 `api.data.gov`의 `DEMO_KEY` 모델. 가입·신청 없이 저쿼터로 즉시 호출. GAPI2 추정으로 **앞 10단계 → 2단계, 수만 토큰 → 수천 토큰**. 게이트웨이 설정 변경 수준이며 법 개정도 215개 기관 동원도 불필요하다.

### ④ 호출 (Invoke) — "정확하고 저렴하게 부른다"

| | 현재 | 목표 |
|---|---|---|
| 기본 포맷 | XML (JSON 대비 **2.5배 토큰**), 오류 시 XML 강제 회귀 | **JSON 기본**, 오류도 JSON, 콘텐츠 협상 |
| 필드 선택 | 전체 응답만 | **sparse fieldsets** (`?fields=`) |
| 페이징 | offset 방식 (대용량 시 붕괴) | **커서 기반** + 안정 정렬 |
| 캐싱 | 없음 | `ETag`/`If-None-Match` → **304, 토큰 0** |
| 대량 조회 | 반복 호출 | 벌크·비동기 잡 + 결과 파일 |
| 브라우저 | **CORS 미지원** (172개 중 13~14개만 개선) | 공개 API 전면 허용 |
| 요약 | 없음 | **요약 엔드포인트** (점진적 공개) |

> 💡 **새로 필요한 설계 원칙 — 컨텍스트 예산(Context Budget)**: 에이전트에게 토큰은 비용이자 **유한한 작업 기억**이다. "필요한 것만, 필요한 만큼" 반환하는 것이 성능 최적화가 아니라 **기능 요건**이 된다. 전통적 API 설계에 없던 축이다.

### ⑤ 검증 (Verify) — "성공했는지 판별한다" 🔴 현재 완전 붕괴

| | 현재 | 목표 |
|---|---|---|
| 상태코드 | **모든 상황 200 OK** (172개 중 8개만 개선) | 400/401/403/404/409/429/500 일관 |
| 오류 구조 | 바디 `resultCode`, 비표준 | **RFC 9457 Problem Details** |
| 오류 내용 | 코드만, 때로 오타 | `type`/`title`/`status`/`detail`/`instance` + **수정 힌트** |
| 쿼터 | 정보 없음 (**개선 0/172 = 0%**) | `RateLimit-*` + `Retry-After` |
| 서비스 상태 | 무공지 점검 | status page + 사전 공지 API |
| 폐기 예고 | 없음 | `Deprecation`(RFC 9745) + `Sunset`(RFC 8594) |

> 💡 **"교정 가능한 오류(actionable error)"라는 새 요건**: 사람은 오류를 보고 문서를 다시 읽지만, **에이전트는 오류 메시지 자체에서 수정 방법을 얻어야 자율적으로 재시도**한다.
> ```json
> { "type": "https://api.data.go.kr/errors/invalid-date-range",
>   "title": "조회 기간이 허용 범위를 초과했습니다",
>   "status": 400, "detail": "요청 기간 365일 > 최대 90일",
>   "hint": "startDt와 endDt 간격을 90일 이내로 조정하세요",
>   "max_range_days": 90 }
> ```
> 에이전트는 이것만으로 스스로 고쳐 재호출한다. **오류 응답의 품질이 자율성의 상한을 결정한다.**

### ⑥ 행위 (Act) — "읽기를 넘어 쓰기로" 🆕 미개척 영역

**현재 논의는 전부 읽기 전용이다. 그러나 Agentic 정부의 실질은 여기서 시작된다** — 에이전트가 민원을 신청하고, 예약을 잡고, 신고를 접수하는 순간.

**공공 영역의 쓰기 API는 민간과 근본적으로 다르다: 법적 효과가 발생한다.** 따라서 아래 요소가 **필수**다.

| 요소 | 요구사항 | 표준 |
|---|---|---|
| **멱등성** | 재시도가 중복 신청을 만들면 안 됨 | `Idempotency-Key` 헤더 |
| **2단계 커밋** | 미리보기(preflight) → 확인 → 확정 | dry-run 엔드포인트 |
| **취소·정정** | 잘못된 제출의 되돌리기 경로 | 명시적 취소 API + 정정 기한 |
| **위임 증명** | "누구를 대신해" 하는가 | OAuth 위임(RFC 8693 Token Exchange), on-behalf-of |
| **인간 게이트** | 법적 효과 발생 행위는 **사람의 명시적 승인 필수** | 승인 대기 상태 + 알림 + 만료 |
| **감사 추적** | 사람–에이전트–호출의 전 체인 기록 | 불변 감사 로그 |
| **행위 등급** | 조회 / 저위험 / 법적 효과 / 되돌릴 수 없음 | 등급별 차등 통제 |

> ⚠️ **인간 게이트 설계 원칙**: "모든 행위에 사람 승인"은 자동화를 무의미하게 만들고, "전부 자동"은 통제 불능을 만든다. **행위를 되돌림 가능성(reversibility)과 법적 효과로 4등급 분류하고, 등급별로 게이트를 차등 적용**하는 것이 유일하게 작동하는 설계다.

## 3.3 도구 계층 — MCP를 정부가 직접 운영해야 하는 이유

| 구분 | 2026-04 | 2026-08 | 해외 |
|---|---|---|---|
| 커뮤니티 MCP | 약 6종 | **79종 (13배)** | — |
| 중앙정부 공식 MCP | 0 | **0** | 🇺🇸 GovInfo · 🇫🇷 mcp.data.gouv.fr(4만 데이터셋) · 🇬🇧 parliament-mcp |
| 지자체 공식 | 0 | 1 (서울시, 민간 호스팅·선착순 100명 파일럿) | — |

**79종이 의미하는 것 두 가지:**

1. 🟢 **수요 검증 완료** — 공식 접근층이 나오면 **즉시 소비할 생태계가 대기 중**이다.
2. 🔴 **공급망 리스크 고착** — 국가 데이터에 대한 접근이 **유지 주체가 불명확한 개인 저장소**에 의존한다. 유지 중단·의도적 변조·잘못된 파싱이 그대로 국민에게 전달된다. 정부는 통제권도, 인지 수단도 없다.

**따라서 공식 MCP는 "편의 기능"이 아니라 데이터 무결성의 안전장치다.**

**목표 상태**: 국가 공식 MCP 서버(정부 운영, SLA 보장, 주요 클라이언트 호환) + **커뮤니티 MCP 인증·등재 제도**(공식이 못 덮는 영역을 안전하게 흡수).

# Ⅳ. AI-Native 정부 — 무엇이 필요한가

## 4.1 정의: AI-Enabled ≠ AI-Native

| | AI-Enabled 정부 | **AI-Native 정부** |
|---|---|---|
| 접근 | 기존 프로세스에 AI를 **부착** | AI를 전제로 프로세스를 **재설계** |
| 전형 | 민원 챗봇, 문서 요약 도구 | 선제적 급여 지급, 규정의 기계 실행 |
| 데이터 | 사후에 AI가 긁어옴 | 설계 시점부터 기계 소비 전제 |
| 규정 | 문서로 작성 → 사람이 해석 | **코드로 동시 작성 (Rules as Code)** |
| 신청 | 국민이 찾아와서 신청 | **정부가 자격을 찾아 먼저 제안** |
| 조직 | IT 부서가 도입 | 업무 부서가 AI로 일함 |
| 성공 지표 | 도입률·이용 건수 | **처리 시간·자동 완결률·미수급자 감소** |
| 실패 유형 | 챗봇 UI만 바뀌고 뒷단 그대로 | — |

> **한국의 현 위치**: data.go.kr 대화형 검색(2026-08 시범, 응답 27.3초), 서울 데이터 허브 RAG 챗봇, 과기정통부 공공 AI 에이전트(**공표만, 미출시**). 모두 **AI-Enabled 단계**다. 그리고 그 아래 Ⅱ·Ⅲ층이 미완성이므로 **성능 상한이 이미 결정돼 있다.**

## 4.2 AI-Native 정부의 8대 구성 요소

### 요소 1. Rules as Code — 규정의 기계 실행 가능화 ⭐

**가장 근본적이면서 가장 실행되지 않은 요소.**

현재: 법령·시행령·지침이 자연어로 작성 → 각 기관이 각자 해석 → 각 시스템이 각자 구현 → **같은 법이 시스템마다 다르게 작동**한다.

**목표**: 법령 제정·개정 시 **자연어 조문과 기계 실행 가능 로직을 동시에 작성**한다.

| 효과 | 설명 |
|---|---|
| 일관성 | 모든 시스템이 동일 로직 사용 → 기관별 해석 편차 소멸 |
| 검증 가능성 | 입법 단계에서 **시뮬레이션** 가능 (누가 얼마를 받는가) |
| 모순 탐지 | 법령 간 충돌을 자동 검출 |
| 즉시 반영 | 개정 시 전 시스템 동시 갱신 |
| 설명 가능성 | 결정 근거를 **조문 단위로 역추적** |
| AI 안전성 | LLM이 법을 "해석"하지 않고 **결정 엔진을 호출** → 환각 차단 |

**참조**: 🇳🇿 뉴질랜드 Better Rules · 🇫🇷 OpenFisca(사회급여 규칙 엔진, 오픈소스) · 🇦🇺 호주 Rules as Code 시범.

> 💡 **AI 시대에 이 요소의 위상이 바뀌었다.** 과거에는 "행정 효율화"였지만, 지금은 **LLM이 법령을 추론하게 두지 않기 위한 안전장치**다. 자격 판정을 LLM에게 맡기면 유창한 오답이 나온다. 결정론적 규칙 엔진을 호출하고 LLM은 설명만 담당해야 한다.

### 요소 2. 선제적 행정 — 신청주의의 종료

| | 현재 (신청주의) | 목표 (선제적) |
|---|---|---|
| 트리거 | 국민이 알고 찾아와 신청 | **정부가 자격 발생을 인지하고 먼저 제안** |
| 전제 | 국민이 제도를 알아야 함 | 몰라도 받음 |
| 실패 모드 | **미수급 (자격자가 못 받음)** | — |
| 조직 단위 | 부처별 개별 창구 | **인생 사건(life event) 단위** |

**"한 번만 원칙(Once-Only Principle)"** — 정부가 이미 보유한 정보를 국민에게 다시 요구하지 않는다. (🇪🇺 EU Single Digital Gateway 규정, 🇪🇪 에스토니아)

> **이것이 AI-Native의 진짜 얼굴이다.** 챗봇을 잘 만드는 것이 아니라, **챗봇에 물어볼 필요 자체를 없애는 것.** 그리고 이것은 Ⅱ·Ⅲ층(기관 간 데이터 결합 + 자격 판정 엔진 + 신뢰 가능한 API) 없이는 성립하지 않는다.

### 요소 3. 디지털 공공 인프라 (DPI)

정부가 **직접 소유·운영**해야 하는 공통 기반. 개별 서비스마다 재구축하지 않는다.

| 구성 | 내용 | 참조 |
|---|---|---|
| 신원 | 사람·법인·**서비스·에이전트** 통합 신원 (OIDC) | 🇪🇪 e-ID, EU eIDAS 2.0 |
| 데이터 교환 | 기관 간 표준 데이터 교환 + 감사 | 🇪🇪 X-Road |
| **동의 관리** | 누가 내 데이터에 접근했는지 열람·철회 | 🇪🇪 data tracker |
| 카탈로그 | 전 부처 통합 데이터·API 목록 | 🇪🇺 data.europa.eu |
| 결정 엔진 | Rules as Code 실행 기반 | 🇫🇷 OpenFisca |
| 에이전트 게이트웨이 | 공식 MCP + 통합 인증 + 쿼터 | 🇺🇸 api.data.gov |

> ⭐ **동의 관리가 AI 시대에 새롭게 결정적인 이유**: 에이전트가 내 데이터를 대신 조회할 때, **국민이 그 사실을 알고 철회할 수 있어야 한다.** 이것이 없으면 선제적 행정은 감시로 인식된다. 편의성이 아니라 **정당성(legitimacy)의 조건**이다.

### 요소 4. 알고리즘 거버넌스

AI가 행정 결정에 관여하는 순간 필요해지는 통제 장치.

| 요소 | 내용 | 참조 |
|---|---|---|
| **알고리즘 등록부** | 어떤 AI가 어디에 쓰이는지 공개 목록 | 🇳🇱 암스테르담, 🇫🇮 헬싱키 |
| 영향평가 | 도입 전 권리 침해 가능성 평가 | 🇨🇦 AIA, EU AI Act |
| 설명 의무 | 불리한 결정 시 근거 제시 | 행정절차 원칙 |
| **이의제기·인간 재심** | 자동 결정에 대한 사람의 재검토 요구권 | GDPR 제22조 계열 |
| 편향 모니터링 | 집단별 결과 격차 정기 측정 | — |
| 감사 로그 | 어떤 데이터·모델·버전이 결정에 쓰였는지 | — |
| 책임 소재 | 자동 결정의 법적 책임 주체 명확화 | — |

> ⚠️ **행정에서 AI 도입의 실패는 성능 문제로 오지 않는다. 정당성 문제로 온다.** 네덜란드 아동수당 스캔들처럼, 기술적으로 작동한 시스템이 통제 장치 부재로 사회적 재앙이 된 사례가 이미 존재한다. **거버넌스는 도입의 브레이크가 아니라 도입을 지속 가능하게 하는 조건이다.**

### 요소 5. 조달·예산 구조 전환 🔴 가장 저평가된 요소

Ⅰ장 근본 결함 7·8번에 대한 직접 처방. **이것이 바뀌지 않으면 나머지 7개 요소는 문서로만 존재한다.**

| 현재 | 목표 |
|---|---|
| 구축(SI) 중심 예산, 운영은 요율 | **제품 운영 예산 상설 편성** |
| 준공 = 성과 | **이용자 성과 지표로 평가** (호출 성공률, 자동 완결률) |
| 기능 명세 중심 RFP | **API 품질 요건을 RFP 필수 항목화** (OpenAPI, 상태코드, JSON, 오류 표준) |
| 발주 기관 검수 역량 부재 | **중앙 품질 게이트** — 표준 미준수 시 등록 반려 |
| 일괄 발주 | 모듈화 + 레퍼런스 구현 제공 |
| 최저가 | 표준 준수 가점 |

> 💡 **가장 실효적인 단일 개입**: **표준 준수 레퍼런스 구현과 스캐폴딩을 정부가 직접 배포하는 것.** 근본 결함 9번(레거시 자기 복제)은 "복사할 나쁜 원본"이 있어서 발생한다. 금지하는 것보다 **복사할 좋은 원본을 주는 것**이 훨씬 빠르고 저항이 적다.

### 요소 6. 조직과 인력

| 요소 | 내용 |
|---|---|
| **Product Owner 직위 신설** | 주요 데이터·API마다 책임자 명시 (근본 결함 4번 처방) |
| 내부 기술 역량 | 외주 의존 탈피 — 설계·검수 가능한 내부 인력 |
| 데이터·AI 직군 | 전문 직렬 신설, 순환보직 예외 |
| 디지털 서비스 조직 | 🇬🇧 GDS, 🇺🇸 USDS 모델의 중앙 실행 조직 |
| 전 직원 AI 리터러시 | 사용법이 아니라 **한계와 위험**에 대한 이해 |
| 실패 허용 | 파일럿 → 학습 → 확산. 실패가 감사 지적이 되지 않는 제도적 보호 |

> ⚠️ **순환보직과 AI-Native는 구조적으로 충돌한다.** 2년마다 담당자가 바뀌는 조직에서 "제품을 지속 개선"은 성립하지 않는다. 이것이 근본 결함 4번(Product Owner 부재)의 뿌리이며, 조직 제도 차원의 예외 설계 없이는 해결되지 않는다.

### 요소 7. 신뢰·안전·주권

| 요소 | 내용 |
|---|---|

| 데이터 경계 | 국외 이전 가능 데이터의 명확한 분류 |
| 소버린 옵션 | 민감 업무용 자체 운영 가능 모델 확보 |
| **프롬프트 인젝션 방어** | 공공데이터에 포함된 텍스트가 에이전트를 조종하는 공격 |
| 오남용 탐지 | 비정상 조회 패턴 탐지 (에이전트 트래픽은 비선형 증가) |
| 폴백 | AI 실패 시 인간 경로 상시 보장 |

> 🆕 **프롬프트 인젝션은 공공 영역에서 새로운 유형의 위험이다.** 민원 내용, 게시글, 개방 데이터의 자유기재 필드에 삽입된 텍스트가 이를 읽는 에이전트의 행동을 바꿀 수 있다. **공공데이터가 공격 표면이 되는 상황**이며, 현재 어느 나라도 충분한 대응 체계를 갖추지 못했다.

### 요소 8. 측정과 피드백 루프

근본 결함 12번(이용자 부재)에 대한 직접 처방.

| 요소 | 내용 |
|---|---|
| **실패율 공개** | 호출 성공률·오류 코드 분포를 **공개 대시보드로 상설** |
| 이용자 채널 | 불만을 "민원"이 아닌 **이슈 트래커**로 처리 |
| 수요 신호 수집 | 검색됐으나 없는 데이터, 커뮤니티 MCP 분포 → 개방 우선순위 반영 |
| 외부 감시 유지 | K-GAPI/GAPI2식 **증거 우선 측정**을 공식 체계로 채택, 분기 공표 |
| 자가 진단 | 각 API가 자기 준수 상태를 노출하는 엔드포인트 |

> 🔴 **"부분측정" 급증에 대한 처방이 여기에 있다.** 측정 가능성이 낮아지면 개선 압력이 사라지고 추가 악화가 온다. **측정 가능성 자체를 보호해야 할 자산으로 취급**해야 한다.

# Ⅴ. 통합 성숙도 모델과 새로운 측정 지표

## 5.1 3계층 통합 성숙도

| Level | 명칭 | 데이터 (Ⅱ) | API (Ⅲ) | 정부 (Ⅳ) |
|---|---|---|---|---|
| **L0** | Closed | 파일 게시만 | 없음/화면만 | 종이·대면 |
| **L1** | Machine-Readable | CSV/XML 다운로드 | REST 있으나 비표준 | 전자민원 |
| **L2** | **AI-Ready** | 스키마·코드북·계보·라이선스 기계 표기 | OpenAPI·JSON 기본·표준 HTTP·RFC 9457 | AI 보조 도구 (AI-Enabled) |
| **L3** | **Agent-Ready** | 인용 가능·as_of 재현·실측 신선도 | 공식 MCP·OAuth M2M·샌드박스·통합 신원 | 에이전트 셀프서비스 |
| **L4** | **AI-Native** | 실시간 결합 가능 데이터 제품 | 쓰기 API·멱등성·위임·인간 게이트 | Rules as Code·선제적 행정·알고리즘 거버넌스 |

**한국의 현 위치**: 데이터 **L1**, API **L1 미만**(7기둥 평균 ≈ L0.6), 정부 **L2 시도 중**.

> 🔴 **가장 중요한 진단**: 층 간 **불균형**이 발생하고 있다. 데이터·API가 L1인 상태에서 정부 계층만 L2를 시도하면, **표면만 AI로 덮인 시스템**이 만들어진다. 응답 27.3초의 대화형 검색이 바로 그 증상이다 — 뒷단이 HTML 스크래핑이면 앞단이 아무리 좋아도 그 이상 갈 수 없다.

## 5.2 새로운 측정 지표 — "구현 여부"에서 "성공 여부"로

현재 지표는 **구현 여부**를 센다(OpenAPI가 있는가?). 그러나 실제로 알아야 하는 것은 **에이전트가 성공하는가**다. 아래는 결과 기반 지표 제안이다.

| 지표 | 정의 | 측정 방법 | 목표 |
|---|---|---|---|
| **TTFC**<br>Time To First Call | 사전 지식 0인 에이전트가 첫 유효 응답까지 걸리는 시간 | 표준 과제 세트 실행 | 현재 3일+ → **5분 이내** |
| **TTFA**<br>Tokens To First Answer | 질문 → 근거 있는 답까지 소비 토큰 | 실측 | 현재 80만~120만 → **2천** (싱가포르 수준) |
| **ACR**<br>Autonomous Completion Rate | 인간 개입 없이 완주한 과제 비율 | 표준 과제 세트 | 현재 20~40% → **90%+** |
| **ISR**<br>Interpretation Success Rate | 코드값·단위·결측을 **오해 없이** 해석한 비율 | 정답셋 대조 | **99%+** |
| **Citation Integrity** | 응답의 수치가 원본 레코드로 역추적되는 비율 | 샘플 검증 | **100%** |
| **Error Actionability** | 에이전트가 오류 메시지만으로 자가 수정한 비율 | 오류 주입 테스트 | **80%+** |
| **Freshness Gap** | 선언 갱신주기 vs 실측 갱신주기의 괴리 | 지속 관측 | **0** |
| **Identity Burden** | 목표 달성에 필요한 계정 수 | 시나리오 계산 | 현재 약 130 → **1~3** |
| **Silent Failure Rate** | HTTP 200으로 반환된 실제 실패 비율 | 잘못된 키·파라미터 주입 | 현재 사실상 100% → **0%** |

> 💡 **이 지표 체계의 핵심 전환**: 기존 14점 체계는 **공급자가 무엇을 갖췄는지**를 잰다. 위 지표는 **이용자(에이전트)가 실제로 성공하는지**를 잰다. 근본 결함 1번(개방 ≠ 사용)에 대한 측정 차원의 처방이며, **평가 지표를 바꾸지 않으면 행동은 바뀌지 않는다.**

**운영 방식 제안**: 표준 과제 세트(예: "특정 지역의 최근 3년 인허가 추이를 근거와 함께 산출") 30~50개를 정의하고, **분기별로 실제 에이전트를 돌려 위 지표를 공표**한다. K-GAPI/GAPI2가 증명한 증거 우선 방법론을 공식 체계로 승격하는 것이다.

# Ⅵ. 한국의 실행 경로

## 6.1 우선순위 원칙 — 무엇을 먼저 할 것인가

개선율 데이터(중앙 설정 4~8% vs 기관별 0%)가 알려주는 실행 원칙:

> **① 중앙에서 혼자 할 수 있는 것을 먼저 한다 → ② 강제 게이트를 만든다 → ③ 그 다음에 기관을 움직인다.**
>
> 순서를 바꾸면 4개월 0%가 반복된다.

## 6.3 성공의 필수 조건 3가지

1. **단일 책임 주체** — **국가데이터처**가 Ⅱ·Ⅲ층의 단일 실행 책임을 갖고 게이트웨이 통합 권한을 행사해야 한다. 조정 실패는 조정 권한으로만 해결된다.

2. **지표 전환이 선행돼야 한다** — "개방 데이터셋 수"를 세는 한 어떤 로드맵도 실행되지 않는다. **평가받지 않는 것은 개선되지 않는다**는 것이 4개월 0%의 교훈이다.

3. **운영 예산 항목의 신설** — "HTTP 상태코드 정상화"가 속할 예산 항목이 없다는 사실이 모든 미개선의 최종 원인이다. **제품 운영 예산이 상설 편성되지 않으면 나머지는 전부 문서로 남는다.**

# Ⅶ. 결론

## 7.1 문제의 최종 정식화

세 층위의 문제는 하나의 문장으로 수렴한다.

> **한국 공공데이터 체계는 "공개된 상태를 유지하는 것"에 최적화돼 있고, "사용되는 것"에는 최적화돼 있지 않다.**

- **Ⅱ층 (데이터)**: 파일은 공개됐으나 **의미는 공개되지 않았다.** 코드값·단위·결측 규칙 없이 기계는 유창하게 오해한다.
- **Ⅲ층 (API)**: 데이터는 열렸으나 **접근권은 닫혀 있다.** 130개 ID, 9~13단계, 13만 토큰.
- **Ⅳ층 (정부)**: AI를 도입했으나 **AI를 전제로 재설계하지는 않았다.** 챗봇 뒤의 뒷단은 여전히 HTML이다.

## 7.2 세 가지 인식 전환

| 기존 인식 | 전환된 인식 |
|---|---|
| "API 품질을 개선하자" | **"에이전트 루프의 완주율을 높이자"** — 평균이 아니라 최약 고리가 결정한다 |
| "AI를 위한 특별 시스템이 필요하다" | **"웹 표준을 정상적으로 지키면 된다"** — 어느 선진 사례도 AI 전용 시스템을 만들지 않았다 |
| "기술 문제다" | **"조정 문제(coordination problem)다"** — 중앙 설정 4~8% vs 기관별 0%가 증명 |

## 7.3 실행의 세 지렛대

1. **최대 레버리지 조치 — 공용 샌드박스 키.** 법 개정도, 215개 기관 동원도, 신규 시스템도 불필요한 게이트웨이 설정 변경 하나가 10단계를 2단계로, 수만 토큰을 수천 토큰으로 줄인다. **6개월 내 실행 가능한 유일한 구조적 조치.**

2. **최대 자산 — OpenAPI 명세.** 다른 항목이 "고칠 결함"이라면 명세는 **하나 만들면 MCP·SDK·함수 스키마가 자동 생성되는 시드**다. 215개 중 1개(0.5%)라는 수치가 MCP 커버리지 5.6%를 통째로 설명한다.

3. **최대 제도 개입 — 평가 지표 전환.** 개방 건수에서 AI 적합성으로. **측정되지 않는 것은 개선되지 않으며, 4개월간의 0%가 이를 실증했다.**

## 7.4 마지막 관찰

두 자료를 겹쳐 읽을 때 가장 무거운 사실은 개별 수치가 아니라 **분포**다. 게이트웨이 한 곳에서 처리 가능한 항목은 4~8% 개선됐고, 215개 기관이 각자 해야 하는 항목은 **정확히 0%** 개선됐다.

그리고 같은 4개월 동안, **커뮤니티는 MCP 서버를 6종에서 79종으로 13배 늘렸다.**

기술 사양은 이미 전부 알려져 있다. RFC 9457도, OpenAPI 3.x도, OAuth 2.0도, MCP도, Rules as Code도 새로 발명할 것이 없다. 수요도 이미 증명됐다. 실행 주체(국가데이터처)와 성공 선례(LOCALDATA 통합)도 확보됐다.

> **남은 것은 단 하나 — 아무도 하지 않으면 아무 일도 일어나지 않는다는 사실이다.**
