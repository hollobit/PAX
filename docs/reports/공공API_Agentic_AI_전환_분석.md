# 한국 공공 API의 AI 적합성 진단

## 두 차례 실측과 이용자의 경험이 드러낸 것

---

### 들어가며

이 보고서는 두 건의 조사를 분석 대상으로 삼는다. 하나는 2026년 4월 2일을 기준으로 국내 공공 Open API 173개 포털을 전수 조사한 [K-GAPI](https://hollobit.github.io/K-GAPI/)이고, 다른 하나는 넉 달 뒤인 8월 4일에 대상을 215개로 넓혀 같은 항목을 다시 측정한 [GAPI2 Δ](https://hollobit.github.io/GAPI2/)이다. 두 조사는 모두 전종홍(ETRI)이 수행했다.

두 자료를 따로 읽으면 각각 하나의 현황 보고서다. 그러나 겹쳐 읽으면 성격이 달라진다. 동일한 척도로 동일한 대상을 두 시점에 측정한 자료이기 때문에, **넉 달이라는 시간 동안 무엇이 움직였고 무엇이 움직이지 않았는지**가 드러난다. 그리고 움직인 것과 움직이지 않은 것 사이의 경계선이 문제의 성격을 알려준다.

여기에 이 보고서는 한 가지 층위를 더한다. 측정값만으로는 잡히지 않는 **이용자의 실제 경험**이다. 계정을 만들고, 키를 신청하고, 승인을 기다리고, 사용 목적을 소명하고, 때로는 거절당하는 과정에서 이용자가 마주하는 것은 기술적 결함만이 아니다. 그 절차의 형태 자체가 **제도가 스스로를 어떻게 이해하고 있는지**를 드러낸다. 4장에서 이 문제를 정면으로 다루며, 현행 공공데이터법 조문과 대조한다.

구성은 다음과 같다. 먼저 두 조사의 방법론과 핵심 결과를 정리한다(1~2장). 이어서 관측된 문제들을 성격에 따라 일곱 개 층위로 나누어 진단하고(3장), 이용자 경험과 제도 운영 문화를 법 조문과 함께 검토한다(4장). 그다음 넉 달간 개선이 일어나지 않은 구조적 이유를 분석하고(5장), 원자료가 제시한 개선 프레임과 실행 로드맵을 검토한다(6~7장). 마지막으로 함께 관리해야 할 위험을 짚는다(8장).

정량 수치는 모두 위 두 조사에서 인용했고, 법 조문은 국가법령정보센터에서 확인했다. 구조적 원인에 대한 해석, 운영 문화의 유형 분류, 로드맵의 우선순위 판단은 필자의 분석이며 원자료의 주장이 아니다. 4장의 법 조문 대조는 제도 설계를 논의하기 위한 것이지 개별 사안에 대한 법률 자문이 아니다.

## 1. 두 조사의 방법론과 성격

### 1.1 K-GAPI — 기준선

K-GAPI는 2026년 4월 기준으로 국내 공공 API 포털 173개를 전수 조사했고, 조사 과정에서 추가로 발굴된 것까지 포함하면 199개를 파악했다. 평가는 두 개의 축으로 이루어진다. **사용자 편의성 7개 항목**과 **AI 적합성 7개 항목**이며, 각 항목은 0점에서 2점 사이로 채점되어 합계 14점 만점이고 A부터 E까지 등급이 부여된다.

사용자 편의성 축은 가입 용이성, 승인 속도, 데이터 포맷, 문서 품질, 호출 한도, 에러 처리, SDK와 샘플코드 제공 여부를 본다. 가입 용이성의 경우 공동인증서를 요구하면 0점, 휴대폰 본인인증이면 1점, 이메일이나 소셜 로그인이면 2점이다. 승인 속도는 3일 이상 수동 심사면 0점, 1일 이내면 1점, 즉시 자동이면 2점이다. **이 두 항목이 뒤에서 다룰 문제의 실마리다.**

AI 적합성 축은 성격이 다르다. **언어 모델 기반 에이전트가 사람의 개입 없이 API를 발견하고 호출하고 오류를 처리할 수 있는가**를 기준으로 삼는다. 기계 판독 스키마의 존재, HTTP 상태 코드의 의미론적 사용, JSON 네이티브 지원, 오류의 자기 설명성, 프로그래매틱 인증 가능성, 레이트 리밋의 투명성, CORS와 HTTPS 지원이 항목이다.

여기에 아홉 개국을 대상으로 한 국제 벤치마크가 더해진다.

### 1.2 GAPI2 Δ — 재측정

GAPI2는 넉 달 뒤 같은 척도로 다시 측정하되 방법론을 강화했다. 대상은 215개로 늘었고, 측정 방식은 두 갈래로 나뉜다. 17개 포털에 대해서는 실제로 모든 엔드포인트를 호출하는 **심층 라이브 측정**을 수행했고, 215개 전체에 대해서는 무인증 도달성·HTTPS·CORS·OpenAPI·llms.txt를 확인하는 **경량 프로브**를 돌렸다. 라이브 재측정 건수는 117건이다.

주목할 것은 이 조사가 채택한 **증거 우선(evidence-first)** 원칙이다. 모든 판정에 실행한 curl 명령과 받은 응답 샘플을 첨부한다. HTTP 의미론을 검증할 때는 의도적으로 잘못된 인증키를 넣어 어떤 상태 코드가 돌아오는지 확인하는 역검증 방식을 쓴다. 그리고 각 판정의 근거를 **실측(measured/live)**, **문헌(doc)**, **측정불가** 세 가지로 분류해 신뢰도를 명시한다.

이 방법론은 공공 API 품질 평가에서 흔치 않은 수준의 재현 가능성을 확보한다. 누구든 같은 명령을 실행해 판정을 확인하거나 반박할 수 있다.

## 2. 관측된 결과

### 2.1 개방 지수와 기술 품질의 병존

K-GAPI가 출발점으로 삼은 사실은 두 지표의 병존이다. 한국은 OECD의 공공데이터 개방 지수(OURdata Index)에서 네 차례 연속 1위를 기록했으며 2023년 점수는 1.0 만점에 0.93이었다. 같은 나라의 공공 API 기술 품질을 K-GAPI의 척도로 평가한 결과는 10점 만점에 2.0이었다.

아홉 개국 국제 비교에서 한국은 사용자 중심성과 AI 적합성 두 축 모두에서 최하위였다. 개별 항목 중 격차가 가장 컸던 것은 **HTTP 상태 코드 의미론**으로, 한국이 0.0점인 반면 해외 평균은 1.80점이었다. 사실상 모든 비교 대상국이 이 항목에서 표준을 지키고 있고 한국만 지키지 않는다는 뜻이다.

### 2.2 넉 달 뒤의 재측정

GAPI2의 재측정 결과, **개발자 커뮤니티에서 반복적으로 제기되어 온 불만 열 가지 가운데 완전히 해소된 것은 하나도 없었다.** 부분적으로 개선된 항목이 세 가지 있었을 뿐이다.

| 순위 | 불만 항목 | 심각도 | 2026-08 판정 |
|---|---|---|---|
| 1 | serviceKey 이중 인코딩 | Critical | 미개선 |
| 2 | CORS 미지원 | Critical | 미개선 |
| 3 | 오류에도 HTTP 200 반환 | Critical | 부분 개선 |
| 4 | XML 강제·JSON 부분 지원 | High | 부분 개선 |
| 5 | API 문서가 HWP 파일 | High | 미개선 |
| 6 | 포털 파편화·계정 난립 | High | 미개선 |
| 7 | 키 발급 후 대기 | Medium | 부분 개선 |
| 8 | 해외·클라우드 IP 차단 | High | 측정불가 |
| 9 | 무공지 점검·다운타임 | High | 미개선 |
| 10 | API Key 만료·갱신 미지원 | High | 미개선 |

AI 적합성 7개 지표를 항목별로 보면 개선의 규모가 더 분명해진다. 아래는 재측정이 가능했던 172개 포털을 모집단으로 한 수치다.

| 지표 | 개선된 포털 | 개선율 |
|---|---|---|
| CORS·HTTPS | 13~14 / 172 | 7.6~8.1% |
| JSON 기본 지원 | 9 / 172 | 5.2% |
| HTTP 상태 코드 의미론 | 8 / 172 | 4.7% |
| OpenAPI 명세 제공 | 7 / 172 | 4.1% |
| 레이트 리밋 헤더 | **0 / 172** | **0%** |
| 문서 품질(HWP 탈피) | **0 / 18** | **0%** |
| 공식 MCP 서버 | **0** | **0%** |

AI 적합성 평균 점수는 14점 만점에 2.37에서 2.35로 사실상 제자리였고 등급은 E에 머물렀다. 등급이 오른 포털이 열일곱에서 열여덟 개, 내려간 포털이 열 개, 나머지 백사십여 개는 변동이 없었다. 아홉 개국 중 9위라는 순위에도 변화가 없었다.

215개 전체를 모집단으로 한 에이전트 준비도 지표는 다음과 같다. 정부가 공식으로 운영하는 MCP 서버는 **0개**, OpenAPI 3.x 명세를 제공하는 포털은 **1개(0.5퍼센트)**, 공식과 비공식을 합쳐 MCP가 존재하는 포털은 **12개(5.6퍼센트)** 였다.

### 2.3 결과를 읽는 첫 번째 방식

이 수치들을 항목별로 나열하면 "여전히 부족하다"는 익숙한 결론에 도달한다. 그러나 개선 여부를 **그 개선에 필요한 작업의 성격**으로 분류하면 훨씬 강한 신호가 나온다.

중앙 게이트웨이 한 곳의 설정을 바꾸면 되는 항목 — HTTP 상태 코드, CORS, JSON 지원 — 은 4퍼센트에서 8퍼센트 사이의 개선율을 보였다. 반면 215개 기관이 각자 자기 시스템을 손봐야 하는 항목 — 문서 형식 전환, 레이트 리밋 헤더 노출, 공식 MCP 구축 — 은 **정확히 0퍼센트**였다.

이 경계선은 우연이 아니다. 만약 개선을 가로막은 것이 기술적 난이도였다면 개선율은 작업의 복잡도를 따라 분포했을 것이다. 실제로는 그렇지 않다. **응답에 레이트 리밋 헤더 세 줄을 추가하는 일은 HTTP 상태 코드 체계 전반을 정상화하는 일보다 비교할 수 없이 단순하다.** 그럼에도 후자는 8건이 개선되었고 전자는 0건이었다.

차이를 만든 것은 난이도가 아니라 **그 일을 하기로 결정할 수 있는 주체가 몇이었는가**다.

## 3. 문제의 일곱 층위

### 3.1 프로토콜 정직성 — 성공했다고 보고하는 실패

가장 근본적인 층위의 문제는 API가 실패했을 때 실패했다고 말하지 않는다는 것이다.

인증키가 잘못되었을 때도, 파라미터가 유효하지 않을 때도, 호출 한도를 초과했을 때도 응답은 `HTTP 200 OK`다. 실제 실패 사실은 응답 본문의 `resultCode` 같은 필드에만 기록된다.

사람 이용자에게 이것은 불편에 그친다. 화면을 보면 오류라는 것을 알 수 있기 때문이다. 에이전트에게는 사정이 완전히 다르다. **에이전트의 재시도 로직, 백오프 계산, 폴백 경로 선택은 전적으로 상태 코드에 의존한다.** 200이 돌아오면 성공으로 판단하는 것 외에 다른 선택지가 없다. 그 결과 빈 데이터나 오류 메시지가 담긴 응답이 정상 결과로 취급되어 다음 처리 단계로 넘어간다. 오류가 즉시 드러나지 않고 **조용히 오염된 결과로 전파되는 것**이다.

같은 층위에 속하는 부수 문제로, `Retry-After`와 `RateLimit-*` 계열 헤더가 제공되지 않아 에이전트가 서버의 백프레셔 신호를 읽을 수 없다. 남은 호출 가능 횟수도, 언제 다시 시도해야 하는지도 알 수 없으므로 에이전트는 무한 재시도에 빠지거나 과도하게 보수적으로 대기하는 두 극단 중 하나를 택한다. 이 항목은 172개 중 개선된 곳이 **0개**다.

### 3.2 표현 포맷 — XML 기본값이 부과하는 비용

JSON을 지원하는 API는 늘고 있으나 **기본값은 여전히 XML**이다. 더 문제가 되는 것은 게이트웨이 수준의 오류가 발생할 때 응답이 XML로 강제 회귀한다는 점이다.

이 비대칭이 만드는 결과는 명확하다. 정상 경로에서는 JSON을 받도록 파서를 작성했는데 오류 경로에서 XML이 돌아오므로 **파서는 오류 상황에서 반드시 깨진다.** 그리고 앞 절에서 본 것처럼 그 오류 상황은 HTTP 200으로 위장되어 있어 사전에 감지할 수도 없다. **두 결함이 겹치면 실패는 진단조차 불가능해진다.**

토큰 측면의 비용도 있다. XML은 동일한 내용에 대해 JSON의 **2.5배 토큰**을 소비한다.

### 3.3 기계 발견성 — HWP로 배포되는 API 명세

215개 포털 가운데 OpenAPI 3.x 명세를 제공하는 곳은 **1개, 0.5퍼센트**다. 나머지는 HWP나 PDF, 혹은 HTML 산문으로 API를 설명한다. 문서 품질 개선은 관측 대상 18개 중 0건이었다.

이 층위가 중요한 이유는 파급 구조에 있다. 기계 판독 가능한 명세가 존재하면 그로부터 **MCP 서버와 SDK와 함수 호출 스키마가 자동으로 생성된다.** 명세가 없으면 사람이 문서를 읽고 손으로 래퍼를 작성해야 한다.

따라서 **OpenAPI 명세의 부재는 여러 결함 중 하나가 아니라, MCP 커버리지가 5퍼센트대에 머무는 이유의 거의 전부를 설명하는 단일 원인이다.** 다른 항목들이 고쳐야 할 결함이라면 명세는 **하나를 만들면 나머지가 자동으로 따라오는 자산**이다.

### 3.4 인증과 인가 — 열린 데이터, 닫힌 접근권

GAPI2의 이용 절차 분석은 이 층위를 한 문장으로 요약한다. **"데이터는 열려 있지만 접근권을 얻는 절차가 닫혀 있습니다."**

| 시나리오 | 단계 수 | 세부 액션 | 인간 개입 | 자동화 가능성 |
|---|---|---|---|---|
| 파일 다운로드 | 3~5 | 5~8 | 0~1회 | 높음 |
| OpenAPI 시험 호출 | 9~13 | 20+ | 3~5회 | 30~50% |
| 상용 운영 | 14~20 | 30+ | 5~8회+ | 20~40% |
| 10개 API 조합 | **60~100+** | — | 10회+ | 매우 낮음 |

병목의 위치가 중요하다. 일단 키를 확보한 뒤의 운영 구간은 70~90퍼센트까지 자동화가 가능하다. 막혀 있는 것은 **발견에서 계약을 거쳐 인가에 이르는 중간 구간**이며 이곳의 자동화 가능성이 30~50퍼센트에 그친다. 파이프의 양끝은 뚫려 있고 가운데가 막혀 있다.

이 구간을 막고 있는 여섯 가지 구조적 장벽이 있다. 계정 체계가 자연인을 전제하므로 휴대폰 본인인증이 자동화를 원천 차단한다. 신청·발급·쿼터 조회를 위한 관리 API가 없어 화면 자동화에 의존해야 한다. 승인 정책이 즉시·1일·3일 이상으로 혼재해 결과를 예측할 수 없다. 문서 포맷이 파편화되어 파싱이 실패한다. 서비스 상태에 대한 표준 정보가 없다. 그리고 문제 해결이 전화와 게시판이라는 인간 경로를 전제한다.

키 자체에도 문제가 있다. URL 쿼리 파라미터에 키를 실어 보내므로 **키가 서버 접근 로그와 브라우저 히스토리와 리퍼러 헤더에 평문으로 남는다.** 유효기간은 2년이고 자동 갱신이 없으며 만료 시 통보도 없다. serviceKey 이중 인코딩 버그는 Critical 등급으로 넉 달째 미개선이다.

**이 층위의 문제는 기술적 결함으로만 설명되지 않는다. 절차의 형태 자체가 제도의 자기 인식을 반영하고 있기 때문이며, 이는 4장에서 별도로 다룬다.**

### 3.5 파편화 — 하나의 국가, 130개의 신원

포털 수는 2026년 4월 기준 199개에서 8월 기준 약 215개로 늘었다. 신규 발굴이 22개, 소멸하거나 통합된 것이 6개다.

이 가운데 **159개 포털이 별도 가입을 요구한다.** data.go.kr 게이트웨이가 포괄하는 범위는 전체의 18퍼센트, 즉 31개 포털에 그치며 나머지 82퍼센트는 원 기관에 따로 가입해야 한다. 전체를 커버하려면 **130개 안팎의 계정**이 필요하다.

미국은 `api.data.gov`의 통합 키 하나로 수백 개 API를 호출한다. 싱가포르의 APEX 게이트웨이는 31개 기관, 2,400개 이상의 API, 월 1억 건의 호출을 단일 진입점에서 처리한다.

다만 반증도 함께 기록해야 한다. 2026년 1월부터 4월 사이에 LOCALDATA가 data.go.kr로 통합되면서 기존 누리집이 종료되었고, 인허가 195종과 생활편의 14종이 이관되었다. GAPI2는 이를 **파편화가 역전된 첫 사례**로 기록했다. 2025년 10월에는 국가데이터처가 신설되었다.

### 3.6 도구 생태계 — 수요는 이미 증명되었다

| 구분 | 2026-04 | 2026-08 | 변화 |
|---|---|---|---|
| 커뮤니티 MCP 서버 | 약 6종 | **79종** | 약 13배 |
| 중앙정부 공식 MCP | 0 | **0** | 없음 |
| 지자체 공식 MCP | 0 | 1(서울시) | 신규 |

커뮤니티 MCP 79종의 분야별 분포는 법령·사법 17종, 통계 14종, 조달 11종, 금융·공시 9종, 기상·환경 7종, 부동산·국토 3종, 국회·입법 1종, 기타 17종이다. `korean-law-mcp`는 깃허브 스타 2,363개, `real-estate-mcp`는 366개를 기록했다.

서울시는 2026년 7월 실시간 도시데이터 MCP를 공개해 국내 최초의 공식 사례가 되었으나, 카카오 PlayMCP에 호스팅되고 선착순 100명을 대상으로 하는 파일럿이다. 해외에서는 미국 GovInfo, 프랑스 mcp.data.gouv.fr(4만 데이터셋), 영국 parliament-mcp가 모두 정부 공식으로 운영된다.

**79종이라는 숫자는 두 가지를 동시에 말한다.** 하나는 수요가 이미 검증되었다는 것이다. 아무도 지시하지 않았는데 개발자들이 자기 시간과 비용을 들여 넉 달 만에 79종을 만들었다. 다른 하나는 공급망 위험이다. 국가 데이터에 대한 접근이 유지 주체가 불명확한 개인 저장소에 의존하고 있으며, 정부는 이를 통제할 권한도 인지할 수단도 갖고 있지 않다. **따라서 공식 MCP 서버는 편의 기능이 아니라 데이터 무결성의 안전장치다.**

한편 정부의 AI 도구 현황을 보면, data.go.kr의 대화형 검색이 2026년 8월 3일 시범 운영을 시작했고 응답 시간은 27.3초로 측정되었다. 과학기술정보통신부의 공공 AI 에이전트는 공표되었으나 미출시 상태다. 정부는 "검증·신뢰 체계 구축"에 18억 원을 배정하고 2026년 12월을 목표로 삼으면서 운영형 MCP보다 우선순위를 두고 있다.

### 3.7 경제성 — 정량화된 접근 비용

GAPI2의 가장 독창적인 기여는 접근 비용을 **토큰이라는 단위로 실측**했다는 점이다.

2026년 8월 4일 실측 기준으로, data.go.kr 메인 페이지는 **48,300 토큰**(4.97메가바이트), 검색 결과 한 페이지는 **132,810 토큰**, API 상세 페이지는 57,998 토큰이 소요된다. 검색 결과 465킬로바이트 HTML 가운데 실제로 의미 있는 정보의 비율은 **3.2퍼센트**다. 즉 **에이전트가 소비하는 토큰의 96.8퍼센트가 마크업과 스크립트다.**

전 과정으로 확장하면 격차는 더 벌어진다.

| 방식 | 토큰 |
|---|---|
| 원문 HTML 파싱(현재) | 80만 ~ 120만 |
| 최적화된 경로 | 3만 ~ 8만 |
| 싱가포르 | **2천** |
| 미국 | 5천 ~ 1만 |
| 프랑스 | 1만 |

**400배에서 600배의 격차**다. 토큰은 AI 서비스에서 비용이자 지연이자 작업 기억의 한계를 동시에 의미하므로, 이 격차는 **국내에서 공공데이터를 활용하는 AI 서비스의 단위 경제성을 구조적으로 훼손한다.** 같은 기능을 만들어도 한국 공공데이터를 쓰면 수백 배의 비용이 든다면 합리적인 사업자는 다른 데이터원을 찾는다.

## 4. 이용자의 경험 — 절차가 드러내는 제도의 자기 인식

앞 장까지가 측정 가능한 결함이라면, 이 장은 측정값에 잡히지 않는 층위를 다룬다. 이용자가 실제로 겪는 과정과, 그 과정의 형태가 드러내는 제도의 자기 이해다.

### 4.1 이용자가 실제로 마주하는 것

공공데이터를 실무에 쓰려고 시도해 본 사람이 반복적으로 증언하는 경험은 다음과 같다.

첫째, **계정이 하나로 끝나지 않는다.** 필요한 데이터를 모으다 보면 포털마다 따로 가입해야 하고, 전체를 아우르려면 130개 안팎의 계정이 필요하다. 이는 K-GAPI가 산출한 수치이자 이용자가 체감하는 현실이다.

둘째, **계정을 만들어도 데이터를 쓸 수 없다.** 인증키를 API마다 따로 신청해야 하고, 신청한다고 바로 나오지도 않는다. 승인을 기다려야 하며 대기 시간은 즉시부터 3일 이상까지 예측할 수 없이 흩어져 있다. 이 편차 자체가 K-GAPI의 평가 항목에 들어가 있다.

셋째, **왜 쓰려는지를 설명해야 한다.** 활용 목적, 활용 분야, 서비스 계획 같은 항목을 기재해야 하고, 그 내용이 심사의 대상이 된다.

넷째, **어떤 곳은 이 절차를 정보공개청구와 거의 같은 방식으로 운영한다.** 청구인이 목적과 사유를 소명하고, 기관이 심사해서 공개 여부를 결정하고, 거부되면 사실상 끝나는 구조다.

다섯째, 그리고 가장 근본적으로, **어떤 기관은 데이터와 API의 공개를 이용자에게 권한이나 혜택을 부여하는 일로 인식한다.** 승인은 시혜이고, 따라서 승인권을 행사하는 것은 기관의 재량이며, 이용자는 그 재량의 수혜자라는 전제다.

여섯째, **이런 불만이 반복해서 제기되지만 반영되지 않는다.** GAPI2의 재측정이 이를 수치로 확인해 준다. 개발자 불만 열 가지 가운데 넉 달 동안 완전히 해소된 것은 0건이었다.

일곱째, 그럼에도 **개방 성과에 대한 시상과 표창은 계속된다.** OECD 지수 1위가 반복 인용되고, 우수 사례가 발표되고, 기관은 표창을 받는다. 정작 쓸 만한 데이터를 찾는 이용자의 경험과는 무관하게 진행된다.

이 일곱 가지는 서로 다른 불만이 아니다. **하나의 일관된 제도 인식이 서로 다른 지점에서 드러난 것이다.**

### 4.2 개발자들이 실제로 남긴 기록

위의 서술은 증언의 요약이므로, 공개된 기록으로 뒷받침할 필요가 있다. 아래는 개발 블로그와 커뮤니티에 남은 구체적 사례들이다. 이들은 개별 사건이지만 모아 놓으면 앞 장에서 측정한 결함들이 실무에서 어떤 형태로 나타나는지 보여준다.

#### 두 개의 키와 두 개의 표준 — 인증키 문제의 실체

가장 많이 기록된 문제는 인증키다. 그리고 그 원인은 흔히 알려진 "인코딩을 안 해서"가 아니라 훨씬 구조적이다.

공공데이터포털은 인증키를 **인코딩키(encodedKey)와 디코딩키(decodedKey) 두 가지로 제공**한다. 그런데 어느 것을 언제 써야 하는지는 개발 환경에 따라 달라지고, 포털의 안내는 이를 충분히 설명하지 않는다.

문제의 핵심은 `+` 문자다. [한 iOS 개발자의 기록](https://velog.io/@yeahg_dev/%EA%B3%B5%EA%B3%B5%EB%8D%B0%EC%9D%B4%ED%84%B0%ED%8F%AC%ED%84%B8-SERVICEKEYISNOTREGISTEREDERROR-%EC%9B%90%EC%9D%B8-%ED%8C%8C%ED%97%A4%EC%B9%98%EA%B8%B0)에 따르면, Postman에서는 정상 동작하던 호출이 iOS 앱에서만 실패했다. 원인을 추적한 결과는 다음과 같다.

RFC 3986은 `+`를 쿼리 문자열에서 유효한 문자로 취급하므로 퍼센트 인코딩 대상이 아니다. 그러나 W3C의 폼 인코딩 관행에서 `+`는 공백의 축약 표기다. **두 표준이 같은 문자를 다르게 해석한다.** 공공데이터포털은 후자를 따라 `+`를 `%2B`로 변환할 것을 전제하는데, iOS의 `URLComponents`는 전자를 따라 `+`를 그대로 둔다. 결과적으로 키가 불일치한다.

이 사례가 드러내는 것은 세 가지다.

첫째, **표준 충돌의 해소 책임이 이용자에게 전가되어 있다.** 두 표준이 충돌하는 지점은 API 제공자가 명시적으로 규정해야 할 사항이다. 그런데 현재는 각 이용자가 자기 플랫폼의 동작을 조사해서 알아내야 한다.

둘째, **오류 메시지가 원인을 잘못 지목한다.** 반환되는 코드는 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`, 즉 "등록되지 않은 인증키"다. 그러나 키는 정상적으로 등록되어 있다. 실제 원인은 인코딩 불일치다. 개발자는 등록 상태를 확인하는 데 시간을 쓰다가 엉뚱한 곳에서 원인을 찾게 된다.

셋째, **HTTP 200 문제가 여기서 증폭된다.** 이 오류는 200으로 반환되고 응답 본문이 XML이므로, JSON 파서를 쓰는 클라이언트에게는 인증 오류가 아니라 파싱 실패로 나타난다. 위 개발자가 도달한 결론은 이렇다. "XML 타입으로 데이터가 왔는지 체크하는 로직을 추가로 구현해야겠다."

**즉 이용자가 API 제공자의 결함을 우회하는 방어 코드를 직접 작성하고 있다.** 그리고 이 방어 코드는 215개 포털을 쓰는 모든 이용자가 각자 중복해서 작성한다.

#### `totalCount=0`의 두 가지 의미 — 조용한 실패

3.1절에서 논한 HTTP 200 문제가 실무에서 나타나는 가장 흔한 형태는 빈 결과다.

[공공데이터 API 오류를 정리한 한 기술 블로그](https://datadoctorblog.com/2025/03/21/Py-Crawling-API-gov-Errors/)는 이를 명확히 기록한다. **파라미터명을 잘못 입력하거나 허용 범위를 벗어난 값을 전달하면, 오류가 발생하지 않고 `totalCount=0`인 정상 응답이 돌아온다.**

이 동작의 문제는 두 상황이 구분되지 않는다는 데 있다. "조회 조건에 해당하는 데이터가 실제로 없음"과 "요청이 잘못되어 아무것도 조회되지 않음"이 **완전히 동일한 응답**으로 표현된다. 사람이라면 파라미터를 다시 확인해 보겠지만, 에이전트에게 이 응답은 "데이터 없음"이라는 확정적 사실이다. 그리고 그 사실은 그대로 다음 단계로 전달된다.

같은 기록은 다른 오류 유형도 나열한다. API 경로를 잘못 입력하면 HTTP 500과 함께 `Policy Falsified`라는 메시지가 돌아온다. 이는 게이트웨이 제품의 내부 메시지가 그대로 노출된 것으로, 이용자에게는 무엇이 잘못되었는지 아무 정보도 주지 않는다. 그 밖에 인증키 등록 지연, 키 만료, 서버 다운타임, 조직 보안 정책에 의한 차단 등이 각기 다른 형태의 실패로 나타나는데 **이들을 구분할 표준적 신호가 없다.**

블로그가 독자에게 남긴 조언이 상황을 요약한다. "결과가 빈 상태일 때도 반드시 파라미터와 경로를 재확인해야 한다." 정상 응답을 받고도 의심해야 한다는 것이다.

#### 개발계정과 운영계정, 그리고 공개되지 않은 기준

계정 체계도 이원화되어 있다. 일반적으로 **개발계정은 일일 트래픽이 1만 건 수준으로 제한**되며, 그 이상을 쓰려면 **운영계정으로 전환**해야 한다. 전환에는 활용 사례 등록이 요구되는 경우가 있다.

문제는 그다음이다. 운영계정의 트래픽도 부족할 때 증설을 요청할 수 있는데, **그 기준이 공개되어 있지 않다.** [한 커뮤니티 게시글](https://www.clien.net/service/board/kin/9360470)은 이 상황을 이렇게 정리한다. 증설 요청이 어디까지 가능한지 명시된 가이드라인이 없고, 한계치가 존재하는지도 불명확하며, 포털의 QA를 검색해도 답을 찾을 수 없다는 것이다.

승인 방식도 두 갈래다. 신청 즉시 사용 가능한 자동승인이 있고, 제공기관이 심사한 뒤에야 사용할 수 있는 승인심사가 있다. **후자는 2~3일이 소요되며 결과가 이메일로 통보된다.** 어떤 API가 어느 쪽인지는 미리 알기 어렵다.

이 구조가 만드는 실무적 결과는 **계획의 불가능**이다. 열 개의 API를 조합하는 서비스를 설계할 때, 각각이 자동승인인지 심사 대상인지, 심사에 며칠이 걸릴지, 필요한 트래픽을 받을 수 있을지를 사전에 알 수 없다. 개발 일정을 세울 수 없다는 뜻이다.

#### 응답 구조의 비일관성

여러 기록이 공통으로 지적하는 또 하나는 **API마다 규칙이 다르다**는 점이다. 필수 파라미터의 이름과 형식이 API마다 다르고, JSON과 XML 응답의 구조도 데이터마다 다르며, 문서에 실린 샘플 응답과 실제 응답이 일치하지 않는 경우가 있다.

이것은 개별 API의 결함이 아니라 **표준의 부재가 누적된 결과**다. 하나의 API를 익혀도 다음 API에 그 지식을 적용할 수 없으므로, 이용자의 학습 비용이 API 수에 비례해서 늘어난다. 3.3절에서 본 OpenAPI 명세의 부재가 이 문제를 고착시킨다. 명세가 있으면 클라이언트 코드가 자동 생성되므로 비일관성의 비용이 사라지지만, 명세가 없으면 사람이 매번 문서를 읽어야 한다.

#### 상업적 이용 제한 조항

여러 기관의 이용 안내에는 **"상업적 이용이 불가능한 API를 상업적으로 활용한 경우"** 이용이 제한될 수 있다는 조항이 포함되어 있다. 트래픽 초과로 시스템 부하가 발생한 경우도 함께 열거된다.

후자는 합리적이다. 그러나 전자는 4.5절에서 확인할 공공데이터법 제3조 제4항 — 다른 법률의 특별 규정이나 제28조 제1항 각 호를 제외하고는 영리적 이용을 금지하거나 제한할 수 없다는 원칙 — 과 긴장 관계에 놓인다. 개별 API에 상업적 이용 제한이 붙어 있다면 그 근거가 무엇인지, 제3조 제4항이 정한 예외에 해당하는지가 확인되어야 한다.

### 4.3 정책과 감사 차원에서 확인된 문제

개발자의 개별 경험만이 아니라 공식 평가와 감사에서도 같은 방향의 문제가 확인된다.

**행정안전부의 공공데이터 제공 운영실태 평가**는 민간 활용지원 수준과 품질 수준이 미흡하다고 집계했으며, 그 세부 항목에 **오류신고 적기처리율**이 포함되어 있다. 이 항목의 존재 자체가 중요하다. **정부도 이미 오류 신고가 제때 처리되지 않는다는 사실을 지표로 잡아 두고 있다는 뜻**이기 때문이다. 4.9절에서 다룰 피드백 회로의 단절이 외부의 관찰이 아니라 공식 평가 항목으로 확인되는 셈이다.

**품질 수준의 편차**도 반복해서 지적된다. 중앙행정기관은 대체로 양호하게 평가되는 반면 지방자치단체와 공공기관은 미흡한 것으로 나타나며, [한 지역 언론의 보도](https://www.kyeonggi.com/article/202005241126790)는 도내 지자체 세 곳 중 한 곳의 공공데이터 관리가 부실하다고 전했다. 품질 관리에는 조직 규모와 예산이 필요한데 소규모 기관에는 그것이 없다는 구조적 진단이 함께 제시된다.

**국가중점데이터에 대한 학술 연구**는 개방의 내용 자체를 문제 삼는다. [54개 기관 64종 436개 국가중점데이터를 분석한 연구](https://www.kci.go.kr/kciportal/ci/sereArticleSearch/ciSereArtiView.kci?sereArticleSearchBean.artiId=ART002456940)는 제공 기관과 분야가 매우 한정되어 있고, **활용 가치가 높은 오픈API 방식의 비중이 낮으며**, 가공과 편집이 자유로운 오픈 포맷을 늘릴 필요가 있다고 지적했다. 활용도가 기관별·분야별·파일형식별로 큰 편차를 보인다는 관찰도 함께 제시된다. **개방 건수는 늘었으나 그 구성이 이용에 적합하지 않다는 진단**이다.

**감사원의 인공지능 산업 육성 실태 감사**는 더 직접적이다. [보도에 따르면](https://biz.heraldcorp.com/article/10838247) 과학기술정보통신부는 2017년부터 총 1조 6,328억 원을 투입해 학습용 데이터 908종을 구축했는데, 기관들이 이미 구축된 데이터의 활용 가능성을 사전 검토하거나 기관 간 조정 절차를 거치지 않고 개별적으로 사업을 추진해 **유사 데이터를 중복 구축한 사례가 다수 적발**되었다.

**이 감사 결과는 5장에서 논할 인센티브 구조의 가장 선명한 증거다.** 성과가 구축 건수로 집계되면, 이미 있는 데이터를 찾아 쓰는 것보다 새로 만드는 것이 합리적이다. 조정 절차를 거치면 사업이 축소될 수 있지만 그냥 만들면 실적이 남는다. 1조 6천억 원 규모의 중복이 발생한 것은 담당자들의 태만이 아니라 **평가 체계가 정확히 그렇게 행동하도록 설계되어 있었기 때문**이다.

**연구 목적 활용의 제약**도 별도의 문제로 제기된다. [한 경제지 보도](https://www.hankyung.com/article/2025101639171)에서 연구자들은 보건·의료·교육 등 사회서비스 분야의 행정 데이터에 접근하기 어렵다고 지적하며, 개인정보보호법 등의 규제로 실증 연구가 제약된다고 밝혔다. 제안된 방향은 **접근 금지가 아니라 심사를 거친 제공과 오용에 대한 강력한 사후 제재**였다. 이 구도는 7.6절과 8장에서 논할 "사전 심사에서 사후 관리로"라는 설계 원칙과 같은 방향이다. 같은 기사에서 국가데이터처 격상과 관련해 **데이터 수집뿐 아니라 활용과 서비스 제공에도 인력과 예산을 배정해야 한다**는 의견이 제시된 것도 5.4절의 예산 구조 문제와 정확히 맞물린다.

### 4.4 세 가지 운영 문화

215개 기관의 운영 방식을 이용자 경험의 관점에서 유형화하면 세 가지로 나뉜다. 이는 필자의 분류이며 통계적 조사 결과가 아니다.

**첫째는 정보공개형이다.** 데이터 개방을 정보공개청구의 연장으로 이해한다. 이용자는 청구인이고, 목적을 소명해야 하며, 기관은 심사자다. 절차의 문법이 「공공기관의 정보공개에 관한 법률」에서 온다. 이 유형에서 데이터 제공은 **개별 심사를 거쳐 개별적으로 이루어지는 처분**이다.

**둘째는 시혜형이다.** 데이터와 API 접근권을 기관이 베푸는 혜택으로 이해한다. 승인권을 보유하는 것이 조직의 권한이며, 그 권한을 행사하는 데서 조직적 효능감이 나온다. 이 유형에서 이용자는 권리자가 아니라 **수혜자**다.

**셋째는 제품형이다.** 데이터를 이용자가 쓰라고 만든 제품으로 이해한다. 승인은 오남용 방지를 위한 최소한의 장치이지 심사가 아니며, 이용자의 성공이 기관의 성과다. 이 유형은 관측되는 사례가 드물다.

첫째와 둘째 유형이 지배적일 때 나타나는 공통 증상이 있다. **접근 절차가 정교해지고 데이터 품질은 방치된다.** 심사 항목은 늘어나는데 API 문서는 HWP로 남아 있고, 승인 프로세스는 다단계인데 오류 응답은 HTTP 200이다. 조직의 관심이 **"누구에게 줄 것인가"에 집중되고 "어떻게 쓸 수 있게 할 것인가"에는 가지 않기 때문**이다.

이 관찰은 앞 장의 데이터와 정확히 맞물린다. 3.4절에서 인가 구간이 병목이라고 했고 3.3절에서 문서 품질 개선이 0건이라고 했다. 두 사실은 별개가 아니다. **같은 제도 인식의 두 얼굴이다.**

### 4.5 법 조문과의 대조

여기서 확인해야 할 것이 있다. 위와 같은 운영 방식이 법이 요구하는 바인가 하는 점이다. 「공공데이터의 제공 및 이용 활성화에 관한 법률」(약칭 공공데이터법, 법률 제19408호, 2023년 11월 17일 시행) 조문을 확인한 결과는 그렇지 않다.

**제1조는 이 법의 목적을 "국민의 공공데이터에 대한 이용권을 보장"하는 것으로 규정한다.** 이용권은 권리이지 시혜가 아니다. 법문이 명시적으로 "권"이라는 표현을 쓰고 있다.

**제3조 기본원칙은 네 개 항으로 나뉘어 있으며, 각각이 4.1절의 증언과 정면으로 대응한다.**

제1항은 공공기관이 "누구든지 공공데이터를 편리하게 이용할 수 있도록 노력하여야 하며, 이용권의 보편적 확대를 위하여 필요한 조치를 취하여야 한다"고 정한다. **"편리하게"와 "보편적 확대"가 법문의 표현이다.** 130개 계정과 API별 개별 신청은 이 방향과 반대로 작동한다.

제2항은 "공공데이터에 관한 국민의 접근과 이용에 있어서 **평등의 원칙**을 보장하여야 한다"고 정한다. 활용 목적을 심사해 승인 여부를 달리 결정하는 관행은 이 원칙과 긴장 관계에 놓인다.

제3항이 가장 직접적이다. "정보통신망을 통하여 **일반에 공개된** 공공데이터에 관하여 제28조제1항 각 호의 경우를 제외하고는 **이용자의 접근제한이나 차단 등 이용저해행위를 하여서는 아니 된다.**" 여기서 두 가지가 확인된다. 이미 공개된 데이터에 대한 접근 제한은 원칙적으로 금지되며, 예외는 제28조제1항의 열거된 사유로 한정된다.

제4항은 "다른 법률에 특별한 규정이 있는 경우 또는 제28조제1항 각 호의 경우를 제외하고는 공공데이터의 **영리적 이용인 경우에도 이를 금지 또는 제한하여서는 아니 된다**"고 정한다. **영리 목적이라는 이유로 제한할 수 없다는 뜻이다.**

**제17조 제1항은 "공공기관의 장은 해당 공공기관이 보유·관리하는 공공데이터를 국민에게 제공하여야 한다"고 정한다.** 제공은 재량이 아니라 **의무**다. 단서로 정한 예외는 두 가지뿐이다. 정보공개법 제9조에 따른 비공개대상정보를 포함하는 경우, 그리고 제3자의 권리가 포함되어 정당한 이용허락을 받지 못한 경우다. 제2항은 여기서 한 걸음 더 나아가, 그런 정보가 포함되어 있더라도 **기술적으로 분리할 수 있으면 나머지 부분은 제공하여야 한다**고 정한다.

**제26조 제1항은 공표된 제공대상 공공데이터의 경우 이용자가 "소관 공공기관이나 공공데이터 포털 등에서 제공받을 수 있다"고 정한다.** 별도의 제공신청은 **공표된 목록에 포함되지 않은 데이터**에 한한다. 즉 이미 목록에 올라 공표된 데이터에 대해 개별 심사 절차를 두는 것은 법이 예정한 구조가 아니다.

**제27조는 목록에 없는 데이터를 신청하는 경우의 절차를 정하는데, 여기에도 기한이 있다.** 제3항에 따라 공공기관의 장은 **요청을 받은 날부터 10일 이내에 제공 여부를 결정하여야 한다.** 제4항에 따라 연장하더라도 10일 이내다. 그리고 제6항은 거부 결정을 한 때에는 **거부의 내용과 사유를 신청인과 행정안전부장관에게 통보하여야 한다**고 정한다. 거부는 기록되고 보고되는 행위다.

**제28조 제1항은 제공을 중단할 수 있는 사유를 네 가지로 한정해 열거한다.** 이용요건 위반으로 기관 본래의 업무수행에 상당한 지장을 초래할 우려가 있는 경우, 제3자의 권리를 현저하게 침해하는 경우, 범죄 등 불법행위에 악용하는 경우, 그리고 공공데이터분쟁조정위원회가 정하는 그 밖의 경우다. **"활용 목적이 불분명하다"거나 "사업 계획이 구체적이지 않다"는 사유는 여기에 없다.**

**제31조 제1항은 제공거부나 제공중단을 받은 자가 그 처분이 있은 날부터 60일 이내에 공공데이터분쟁조정위원회에 분쟁조정을 신청할 수 있도록 정한다.** 위원회는 신청을 받은 날부터 30일 이내에 조정안을 작성해야 한다.

이 조문들을 종합하면 다음이 도출된다. **법의 기본 구조는 "제공이 원칙, 예외는 열거"다. 그리고 예외 사유는 데이터의 성질(비공개대상정보, 제3자 권리)이나 이용자의 행위(요건 위반, 불법행위)에 관한 것이지, 이용자의 의도나 사업성에 관한 것이 아니다.**

### 4.6 정보공개법과의 관계를 어디서 오독하는가

4.4절에서 정보공개형 운영을 지적했는데, 이 오독이 어디서 발생하는지는 조문 구조에서 확인된다.

공공데이터법이 정보공개법을 원용하는 지점은 **제17조 제1항 제1호 하나뿐**이다. 그리고 그 원용은 "정보공개법 제9조에 따른 비공개대상정보"라는 **판단 기준**을 가져오는 것이지, 정보공개 절차를 가져오는 것이 아니다.

두 법의 성격은 다르다. 정보공개법은 **무엇을 공개할 것인가**를 다루며, 청구와 심사와 결정의 구조를 갖는다. 공공데이터법은 **이미 공개할 수 있는 데이터를 어떻게 이용하게 할 것인가**를 다루며, 등록과 공표와 제공의 구조를 갖는다. 전자는 개별 처분의 법이고 후자는 상시 제공의 법이다.

**그런데 현장에서는 후자를 전자의 문법으로 운영한다.** 비공개대상정보인지 판단하는 기준만 빌려와야 할 것을, 청구인이 목적을 소명하고 기관이 심사한다는 절차 전체로 확대 적용하는 것이다. 이것은 법 해석의 문제라기보다 **익숙한 업무 문법의 관성**에 가깝다. 담당자에게 정보공개 업무는 익숙하고 데이터 제품 운영은 낯설다. 낯선 일이 들어오면 익숙한 틀에 넣는 것은 조직의 자연스러운 반응이다.

문제는 그 결과다. 상시 제공되어야 할 것이 개별 처분이 되고, 권리였던 것이 신청 대상이 되며, 기본값이 "제공"인 체계가 기본값이 "심사"인 체계로 바뀐다.

### 4.7 목적을 묻는 것이 AI 시대에 갖는 특별한 문제

활용 목적 소명 요구는 그동안 불편의 문제로 다루어져 왔다. 그러나 여기에는 그보다 근본적인 세 가지 문제가 있다.

**첫째, 탐색을 원천적으로 배제한다.** 데이터를 보기 전에는 그 데이터로 무엇을 할 수 있는지 알 수 없다. 실제 분석은 데이터를 열어 보고, 결측을 확인하고, 다른 데이터와 결합해 보면서 방향이 정해진다. 그런데 현행 절차는 **보기 전에 용도를 확정해서 제출하라고 요구한다.** 이는 논리적으로 불가능한 요구이며, 결과적으로 이용자는 형식적인 문구를 지어내게 된다. 심사는 그 지어낸 문구를 심사한다.

**둘째, 혁신을 정의상 배제한다.** 데이터의 가치 있는 활용은 대체로 데이터를 만든 기관이 예상하지 못한 용도에서 나온다. 그런데 사전 목적 심사는 심사자가 이해할 수 있는 용도만 통과시킨다. **즉 이 절차는 예상 가능한 활용을 선별하고 예상 밖의 활용을 걸러내는 필터로 작동한다.** 혁신의 정의가 예상 밖이라면, 이 필터는 정확히 혁신을 제거한다.

**셋째, 에이전트는 목적을 소명할 수 없다.** 이것이 AI 시대에 새로 발생한 문제다. 자율적으로 작동하는 에이전트는 상황에 따라 필요한 데이터를 그때그때 판단한다. 사전에 등록된 목적 문장을 갖고 있지 않으며, 갖고 있다 해도 실제 사용과 일치하리라는 보장이 없다. 목적 심사를 전제한 절차는 **에이전트를 원리적으로 배제한다.**

여기에 3.4절의 사실을 겹치면 상황이 분명해진다. 인가 구간의 자동화 가능성이 30~50퍼센트에 머무는 이유는 기술적 한계가 아니다. **그 구간이 자동화되면 안 된다고 전제하고 설계되었기 때문이다.** 사람이 목적을 쓰고 사람이 심사하는 것이 절차의 본질이므로, 자동화는 절차의 취지를 훼손하는 것이 된다.

**이 전제를 바꾸지 않으면 어떤 기술적 개선도 이 구간을 통과하지 못한다.**

### 4.8 시상 제도의 역설

개방 성과에 대한 시상과 표창이 활발한데 정작 쓸 만한 데이터를 찾기 어렵다는 지적은, 표면적으로는 평가의 부정확성 문제로 보인다. 그러나 좀 더 정확히 보면 **평가가 정확하게 작동한 결과**다.

시상 기준이 개방 건수와 개방률과 신규 개방 실적이라면, 그 기준을 잘 충족한 기관이 상을 받는 것은 평가 체계가 제대로 작동한 것이다. 문제는 그 기준이 **이용자의 성공과 무관하다**는 데 있다.

여기서 발생하는 것이 인센티브의 뒤틀림이다. 기관 입장에서 합리적 행동은 이렇게 정렬된다.

- 새 데이터셋을 하나 더 여는 것 → **평가에 반영됨**
- 기존 API의 HTTP 상태 코드를 고치는 것 → 반영되지 않음
- HWP 문서를 OpenAPI 명세로 바꾸는 것 → 반영되지 않음
- 승인 절차를 없애 즉시 발급으로 바꾸는 것 → 반영되지 않을 뿐 아니라 **관리 소홀로 지적받을 위험이 있음**

마지막 항목이 특히 중요하다. **품질 개선은 평가되지 않는 반면, 통제를 완화하는 조치는 사고 발생 시 책임 소재가 된다.** 즉 개선의 기대 편익은 0이고 기대 비용은 양수다. 이 구조에서 아무도 개선하지 않는 것은 태만이 아니라 합리적 판단이다.

넉 달간 완전 개선 0건이라는 결과는 이 계산의 산출물이다.

### 4.9 이용자 목소리가 반영되지 않는 이유

마지막으로, 불만이 반복 제기되는데도 반영되지 않는 구조를 짚는다.

**첫째, 문제 제기가 버그 리포트가 아니라 민원으로 분류된다.** 민원 처리의 목표는 문제의 해결이 아니라 응답의 완료다. 개별 문의에 답변하고 종결하면 성과가 인정되며, 같은 문제가 백 번 제기되어도 백 번의 개별 응답이 있을 뿐 근본 수정으로 이어지지 않는다. 이슈 트래커에서라면 중복 신고가 우선순위를 높이는 신호가 되지만, 민원 처리에서 중복은 처리 건수를 늘릴 뿐이다.

**둘째, 실패가 집계되지 않는다.** 이용 통계는 호출 건수로만 관리되는데, 여기에 3.1절의 HTTP 200 문제가 결합하면 심각한 결과가 나온다. **실패한 호출도 성공으로 집계되므로 현재 체계로는 실패율을 구조적으로 측정할 수 없다.** 어느 API가 얼마나 실패하는지, 이용자가 어느 단계에서 이탈하는지에 대한 데이터가 존재하지 않는다.

**셋째, 개선을 집행할 예산 항목이 없다.** 이는 5.4절에서 자세히 다룬다.

**넷째, 이의 제기 경로가 알려져 있지 않다.** 앞서 확인한 대로 공공데이터법 제31조는 제공거부나 제공중단에 대해 60일 이내에 공공데이터분쟁조정위원회에 분쟁조정을 신청할 수 있도록 정하고 있고, 위원회는 30일 이내에 조정안을 작성해야 한다. 그러나 이 경로의 존재 자체가 이용자에게 충분히 안내되고 있다고 보기 어렵다. 거부 통지에 이 안내가 포함되는지, 포털에서 이 절차를 찾을 수 있는지가 점검 대상이다.

**제도가 마련해 둔 구제 수단이 활용되지 않으면, 거부는 사실상 최종 결정이 된다.** 그리고 최종 결정이 되면 거부의 기준은 검증받지 않고 기관마다 흩어진 채로 굳는다.

## 5. 왜 넉 달 동안 고쳐지지 않았는가

2.3절의 관찰 — 중앙 설정 항목은 4~8퍼센트, 기관별 항목은 0퍼센트 — 로 돌아온다. GAPI2 자신의 판정도 같다. **"게이트웨이 설정 수준의 개선만 진행되었고, 포털별로 대응해야 하는 항목은 정체되었다."**

### 5.1 인센티브의 부재 — 개방과 사용의 혼동

기관의 성과 지표는 **개방한 데이터셋의 수**이지 API의 품질이 아니다. 이것은 우연이 아니라 이 체계가 설립된 목적의 반영이다. 한국 공공데이터 정책의 성립 목적은 투명성과 공개였고, 그 목적에 비추어 이 체계는 대단히 성공적이었다.

그러나 공개를 목적으로 하는 체계와 사용을 목적으로 하는 체계는 성공 조건을 다르게 정의한다. 공개 패러다임에서 성공은 "공개했다"는 사실로 달성되고, 게시하는 순간 작업이 완료되며, 실패란 공개하지 않은 상태를 뜻한다. 제품 패러다임에서 성공은 "사용되었다"는 결과로만 달성되고, 완료 시점이라는 것이 없으며, 실패란 공개했는데도 아무도 쓰지 못하는 상태를 뜻한다.

두 패러다임의 차이는 구체적 판정에서 갈린다. 오류에도 HTTP 200을 반환하는 API를 보자. 공개 패러다임에서 이것은 실패가 아니다. 데이터는 공개되어 있고 오류 내용도 본문에 들어 있으며 마음먹고 읽으면 알아낼 수 있다. 제품 패러다임에서만 이것은 치명적 결함이 된다.

여기서 중요한 결론이 나온다. **OECD 1위와 기술 품질 2.0점은 서로 모순되는 두 사실이 아니라 하나의 원인이 낳은 두 결과다.** 개방 지수를 최적화한 바로 그 지표 체계가 기술 품질을 개선할 유인을 제공하지 않았다. 4.8절에서 본 시상 제도의 역설이 이 인과의 구체적 작동 방식이며, 4.3절에서 인용한 감사원의 중복 구축 지적이 그 비용의 규모를 보여준다.

### 5.2 승인 권한이 조직에 주는 효용

4.4절에서 지적한 시혜형 운영 문화에는 실무적 이유가 있다. **승인 권한은 조직에 실질적 효용을 제공한다.**

승인권을 보유하면 데이터의 흐름을 통제할 수 있고, 문제가 발생했을 때 "우리는 심사했다"고 말할 수 있으며, 조직의 존재 이유를 설명하는 근거가 된다. 반대로 승인 절차를 없애 즉시 발급으로 전환하면 이 세 가지가 모두 사라진다. 통제력이 줄고, 사고 시 방어 논거가 약해지며, 담당 업무의 비중이 감소한다.

**따라서 인가 절차를 간소화하는 개선은 다른 기술적 개선과 성격이 다르다.** HTTP 상태 코드를 고치는 일은 누구의 권한도 줄이지 않지만, 승인 절차를 없애는 일은 특정 조직의 권한을 직접 줄인다. 전자에 대한 저항이 무관심이라면 후자에 대한 저항은 능동적이다.

이 차이를 인식하지 못하면 로드맵은 실패한다. **기술 개선과 권한 조정을 같은 난이도로 취급하는 계획은 후자에서 반드시 막힌다.** 권한 조정에는 별도의 상위 권한과 명시적 면책이 필요하다.

### 5.3 레거시의 자기 복제

2010년대의 XML/SOAP 설계 자산은 이미 수만 종에 이른다. 이 규모에서 기존 자산을 고치는 것보다 새 기능을 덧붙이는 것이 언제나 저렴하다. 그 결과가 `?type=json` 같은 옵트인 방식의 패치이고, 오류 경로에서 XML로 회귀하는 비대칭이다.

더 근본적인 문제는 신규 API도 기존 API를 복사해서 만들어진다는 점이다. 응답 본문에 `resultCode`를 넣고 HTTP 200을 반환하는 패턴이 그대로 상속된다. 이것은 남아 있는 증상이 아니라 **재생산되는 유전자**다.

따라서 "앞으로 만드는 API부터 표준을 적용한다"는 방침이 실효를 가지려면 금지 규정만으로는 부족하다. **표준을 준수한 레퍼런스 구현과 스캐폴딩을 정부가 직접 배포하는 것**이 훨씬 빠르고 저항도 적다. 복사할 나쁜 원본이 있어서 생긴 문제는 복사할 좋은 원본을 제공해서 푸는 것이 합리적이다.

### 5.4 예산 항목의 부재

지금까지의 어떤 원인보다도 직접적인 이유가 예산 구조에 있다.

공공 정보화 예산은 구축 중심으로 편성된다. 새 시스템을 만드는 사업에는 예산이 배정되고 준공이 성과로 인정되지만, 이미 운영 중인 시스템의 유지보수는 정률 요율 방식으로 최소한만 배정되며 그 범위에서 가능한 활동은 사실상 장애 대응에 국한된다.

이 구조에서 "HTTP 상태 코드를 정상화한다"는 작업이 어디에 속하는지 보자. 그것은 신규 구축이 아니다. 새로 만드는 것이 아니라 이미 있는 것을 고치는 일이기 때문이다. 그렇다고 장애 대응도 아니다. 시스템은 멀쩡히 돌아가고 있고 아무것도 멈추지 않았기 때문이다.

**따라서 이 작업은 어떤 예산 항목에도 속하지 않는다.** 담당자가 문제를 인식하고 고치고 싶어 해도 집행할 근거가 없다. 이것이 serviceKey 이중 인코딩 문제가 Critical 등급으로 분류되어 있으면서도 넉 달째 미개선으로 남아 있는 실질적 이유이며, 왜 넉 달이 아니라 십 년이 지나도 같은 결과가 나올 것인지에 대한 답이다.

### 5.5 소관의 분산 — 조정 실패

215개 포털에는 215개의 소관 기관이 대응한다. 중앙의 강제력이 없으면 0퍼센트가 기본값이다.

이것을 단순한 관리 실패로 보면 처방을 놓친다. 파편화는 **개별적으로는 완벽하게 합리적인 선택들의 총합**이기 때문이다. 기관별로 정보화 예산이 배정되는 구조에서 각 기관이 자기 예산으로 자기 포털을 구축하는 것은 최적 행동이다. 통합에 참여하려면 시스템을 개조하고 운영 권한을 넘기고 이용자 지원 체계를 조정해야 하는데, 그 비용은 전적으로 개별 기관이 부담하는 반면 편익은 국가 전체에 분산된다.

경제학의 용어로 이것은 **조정 실패(coordination failure)** 다. 이 구분은 처방의 방향을 결정한다. 기술 문제라면 더 나은 표준과 가이드라인으로 해결되지만, 조정 실패는 표준을 아무리 잘 만들어도 해결되지 않는다. 각 행위자가 그것을 따를 유인이 없기 때문이다. **조정 실패는 비용과 편익의 구조 자체를 바꾸는 개입으로만 풀린다.**

LOCALDATA 통합이 의미를 갖는 것은 이 지점이다. 그것은 자발적 협력의 사례가 아니라 **권한 행사의 첫 성공 사례**다.

### 5.6 우선순위의 역전

정부는 "AI 검증·신뢰 체계 구축"에 18억 원을 배정하고 2026년 12월을 목표로 삼으면서 운영형 MCP보다 우선순위를 두고 있다.

검증과 신뢰 체계가 불필요하다는 말이 아니다. 순서의 문제다. **검증할 대상이 존재해야 검증 체계가 의미를 갖는다.** 접근 계층이 없으면 무엇을 검증할 것인가. 신뢰는 사용 가능성 위에 쌓이는 것이지 그 역이 아니다.

같은 맥락에서, data.go.kr 대화형 검색의 응답 시간 27.3초는 모델의 성능 문제라기보다 **뒷단에서 HTML을 긁어오고 있기 때문일 가능성이 높다.** 표면 계층을 아무리 개선해도 그 아래가 바뀌지 않으면 넘을 수 없는 한계가 있다.

### 5.7 관측 가능성의 저하

GAPI2 재측정에서 "부분측정" 판정을 받은 항목이 급증했다. 외부에서 품질을 측정하는 일 자체가 어려워지고 있다는 뜻이다.

이것이 위험한 이유는 자기강화적 악순환의 조건이기 때문이다. 측정이 불가능해지면 개선 압력이 사라지고, 개선 압력이 사라지면 품질이 더 떨어지며, 그 결과 측정은 더 어려워진다.

## 6. 개선의 프레임 — 7개 기둥과 성숙도 루브릭

GAPI2는 진단에 그치지 않고 목표 상태를 정의하는 프레임을 제시한다. **Agentic 공공 API 7개 기둥**과 각 기둥의 Level 0~3 성숙도 루브릭이다.

| 기둥 | Level 0 | Level 1 | Level 2 | Level 3 | 현재 |
|---|---|---|---|---|---|
| **정직한 HTTP** | 항상 200 반환 | 일부 코드만 사용 | 표준 코드 일관 적용 | + RFC 9457 + Retry-After/RateLimit | **L0** |
| **구조화 포맷** | XML 전용·기본 | JSON 옵트인 | JSON 기본, 오류도 JSON | + 콘텐츠 협상·ISO 8601·UTF-8 | **L1** |
| **기계 발견성** | HWP/PDF 산문 | 포털 내 표 형식 | 유효한 OpenAPI 3.x | + llms.txt 등 AI 진입점 | **L0** |
| **도구 네이티브** | 없음 | 비공식 커뮤니티 MCP | OpenAPI 기반 자동 생성 | 정부 공식 MCP 운영 | **L1** |
| **에이전트 인증** | URL 쿼리 키 | HTTP 헤더 키 | OAuth 2.0 Client Credentials | + OIDC·scope 최소권한 | **L0** |
| **데이터 제품화** | SDK·샌드박스 없음 | 커뮤니티 SDK 일부 | 공식 SDK + 테스트 콘솔 + DEMO_KEY | + 다국어 SDK·SLA·DCAT-AP | **L1** |
| **통합 정체성** | 포털별 별도 가입 | 일부 게이트웨이 연결 | 주요 포털 SSO + 통합 카탈로그 | 국가 신원 페더레이션 | **L1** |

일곱 기둥의 평균은 대략 **Level 0.6**에 해당한다.

여기에 실행 아키텍처로 **Agent Access Layer 6층**이 제안되어 있다.

| 층 | 내용 | 제안 기간 |
|---|---|---|
| L1 | 조직·서비스·에이전트 계정 유형 신설 | 장기(18개월+) |
| L2 | 관리 API 표준화(활용신청·키 발급·쿼터) | 중기(6~18개월) |
| L3 | OpenAPI·JSON Schema·DCAT·오류 표준 의무화 | 중기 |
| L4 | 패키지 인가(관련 API 묶음 일괄 승인) | 중기 |
| **L5** | **공용 샌드박스 키(신청 없는 저쿼터)** | **단기(6개월)** |
| L6 | 저위험 API 자동 승인 | 중기 |

**L5 공용 샌드박스 키**의 위상은 특별히 언급할 만하다. GAPI2의 추정에 따르면 이 조치 하나만으로 시험 호출 시나리오의 앞 열 단계가 두 단계로 압축되고, 에이전트가 소비하는 토큰이 수만 단위에서 수천 단위로 떨어진다. 미국 `api.data.gov`의 DEMO_KEY 모델이 원형이다.

그리고 이 조치는 법 개정을 요구하지 않고, 215개 기관을 동원하지 않으며, 새로운 시스템 구축도 필요로 하지 않는다. **게이트웨이에 낮은 쿼터의 공용 키 하나를 여는 설정 변경**이다.

여기에 4장의 논의를 겹치면 한 가지가 더 보인다. **공용 샌드박스 키는 기술 조치인 동시에 제도 조치다.** 그것은 "쓰기 전에 목적을 밝혀야 한다"는 전제를 깨는 첫 번째 구멍이기 때문이다. 낮은 쿼터로나마 목적 소명 없이 데이터를 만져 볼 수 있게 되면, 4.7절에서 지적한 "보기 전에 용도를 확정하라"는 논리적 모순이 해소된다. 4.2절에서 본 계정 이원화와 승인 방식의 불투명성 — 어떤 API가 자동승인인지 심사 대상인지 미리 알 수 없어 개발 일정을 세울 수 없다는 문제 — 도 최소한 탐색 단계에서는 사라진다. 탐색이 가능해지고, 탐색이 가능해야 진짜 목적이 생긴다.

## 7. 실행 로드맵

### 7.1 순서의 원칙

**중앙이 혼자 할 수 있는 것을 먼저 하고, 그다음 강제할 관문을 만들고, 마지막에 기관을 움직인다.** 이 순서를 뒤집어 기관의 자발적 개선을 먼저 기대하면 넉 달간의 0퍼센트가 반복된다.

여기에 5.2절의 통찰을 더해 원칙을 하나 보탠다. **권한을 줄이는 개선은 기술을 고치는 개선과 분리해서 다루고, 상위 권한과 명시적 면책을 함께 설계한다.** 승인 절차 간소화를 다른 기술 항목과 같은 목록에 섞어 두면 그 항목만 남고 나머지가 진행되거나, 그 항목 때문에 전체가 멈춘다.

### 7.2 첫 6개월 — 중앙 단독으로 실행 가능한 조치

**기술 조치**로는 다음을 한다.

가장 먼저 **공용 샌드박스 키**를 연다. 낮은 쿼터의 읽기 전용 공용 키를 가입과 신청 없이 제공한다.

**HTTP 상태 코드를 정상화**한다. 400, 401, 403, 404, 409, 429, 500을 상황에 따라 일관되게 반환하고, 특히 잘못된 인증키에는 401을, 쿼터 초과에는 429를 반환한다. 함께 **레이트 리밋 헤더**를 노출한다. `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`은 IETF에서 논의 중인 초안 사양이고, `Retry-After`는 RFC 9110에 포함된 확립된 표준이다.

**JSON을 기본 응답으로 전환**하되 오류 응답에서도 JSON이 유지되도록 한다. **CORS를 전면 허용**하고, **serviceKey를 HTTP 헤더로 전달하는 방식을 병행 지원**해 URL 노출과 이중 인코딩 문제를 함께 우회한다.

발견 비용을 낮추기 위해 **`/llms.txt`와 통합 카탈로그 API**를 연다. **표준 상태 페이지와 점검 사전 공지 API**로 무공지 다운타임 문제를 해소한다.

**제도 조치**로는 다음을 한다. 이 항목들이 4장의 문제에 대응하며, 대부분 법 개정 없이 운영 지침과 표준 양식 변경으로 가능하다.

**공표된 목록의 데이터에 대해서는 개별 심사 절차를 폐지한다.** 공공데이터법 제26조 제1항은 공표된 제공대상 공공데이터를 이용자가 포털에서 제공받을 수 있도록 정하고 있고, 별도 신청은 목록에 없는 데이터에 한한다. 현행 관행이 이 구조와 어긋나 있는지 전수 점검이 필요하다.

**활용 목적 기재를 필수 항목에서 임의 항목으로 전환한다.** 제28조 제1항이 열거한 제공중단 사유에 목적의 불명확성은 포함되어 있지 않다. 통계 목적의 임의 수집은 가능하되, **기재 내용이 승인 여부의 판단 근거가 되지 않도록** 심사 기준에서 분리한다.

**거부 통지 양식을 표준화한다.** 공공데이터법 제17조 제1항 각 호 중 어느 사유에 해당하는지를 명시하도록 하고, 제31조에 따른 분쟁조정 신청 절차와 60일 기한을 함께 안내한다. 제27조 제6항은 이미 거부 시 사유를 신청인과 행정안전부장관에게 통보하도록 정하고 있으므로, 이 통보가 실제로 이루어지고 집계되는지 점검한다.

**승인 처리 기한을 공표하고 실측한다.** 제27조 제3항의 10일 기한이 실제로 지켜지는지, 목록 외 데이터가 아닌 경우에도 심사가 이루어지고 있는지를 측정해 공개한다.

**분쟁조정위원회의 접수와 처리 현황을 공개한다.** 구제 수단이 존재한다는 사실 자체가 알려져야 작동한다.

**품질 공개 대시보드를 상설화**하고 **표준 준수 레퍼런스 구현을 배포**한다.

이 단계가 완료되면 7개 기둥 중 정직한 HTTP와 구조화 포맷이 Level 2에 도달하고, 4장에서 지적한 절차 문제 가운데 상당 부분이 법의 원래 구조로 되돌아온다.

### 7.3 6개월에서 2년 — 제도적 강제

이 단계의 핵심은 **관문을 만드는 것**이다.

**OpenAPI 3.x 명세를 등록 요건으로 만든다.** 명세를 제공하지 않는 신규 API는 등록이 반려되어야 하고, 기존 API는 2년 내 소급 적용한다. HWP 형식의 명세 등록은 금지한다.

오류 표현은 **RFC 9457 Problem Details**로 통일하되, 한 가지를 더한다. 에이전트가 스스로 요청을 수정할 수 있도록 **교정 힌트를 함께 반환**하는 것이다. 조회 기간이 허용 범위를 넘었을 때 단순히 "잘못된 요청"이라고 답하는 대신, 요청 기간이 365일이고 최대 허용이 90일이므로 간격을 조정하라는 정보를 구조화된 형태로 제공하면 에이전트는 사람을 부르지 않고 스스로 고쳐 재호출한다. **오류 응답의 품질이 자율성의 상한을 결정한다.**

인증 체계에서는 **신청·발급·쿼터 조회를 위한 관리 API를 표준화**해 화면 스크래핑 의존을 끊고, **OAuth 2.0 Client Credentials로 전환**해 단기 토큰이 자동 발급·갱신되도록 한다. 키의 만료 전 사전 알림과 자동 갱신도 이 시기에 도입한다.

**공식 SDK와 샌드박스**를 제공하고, 메타데이터는 **DCAT-AP** 표준을 따른다. 관련 API를 묶어 일괄 승인하는 패키지 인가와 저위험 API의 자동 승인도 이 단계에 속한다.

그러나 이 시기에 가장 중요한 것은 기술 항목이 아니라 제도 변화다. 5장의 원인 분석에 대응하는 처방이 여기에 놓인다.

**기관 평가와 시상 기준을 전환한다.** 개방 데이터셋 수에서 **AI 적합성 등급과 이용자 성과**로 옮긴다. 7개 기둥 점수를 공공기관 경영평가에 반영하고, 개방 우수 시상의 심사 기준에 호출 성공률·문서 품질·승인 소요 시간을 포함한다. **이것이 5.1절과 4.8절에 대한 직접 처방이다.**

**승인 절차 간소화에 대한 면책 근거를 마련한다.** 5.2절에서 본 대로 통제 완화는 사고 시 책임 소재가 되므로, 표준 절차를 따른 간소화는 감사 지적 대상이 아니라는 점을 명시적으로 규정해야 한다. **이것이 없으면 담당자가 개선을 선택할 이유가 없다.**

**API 품질 요건을 제안요청서의 필수 항목으로 명문화하고 중앙 품질 관문을 신설한다.** OpenAPI 제공, 표준 상태 코드, JSON 기본 응답, 오류 형식 준수가 기능 요구사항과 동등한 지위를 갖도록 한다.

**국가데이터처를 Agent Access Layer의 단일 책임 주체로 지정하고 게이트웨이 통합 권한을 부여한다.** 조정 실패는 조정 권한으로만 해결된다.

**주요 데이터·API에 제품 책임자를 지정하고**, **검증·신뢰 체계 사업에 운영형 MCP 구축을 선행 과제로 편입한다.**

### 7.4 2년에서 3년 — 구조 전환

**국가 공식 MCP 서버**를 SLA를 보장하며 운영한다. 프랑스 mcp.data.gouv.fr가 4만 데이터셋을 노출하는 모델이 참조 대상이며, 공식이 덮지 못하는 영역은 **커뮤니티 MCP 인증·등재 제도**로 흡수한다.

**통합 신원 페더레이션**을 구축해 필요한 계정 수를 130개에서 1~3개로 줄인다. 싱가포르 data.gov.sg처럼 키 없이 탐색할 수 있는 경로를 병행한다.

**조직·서비스·에이전트 계정 유형을 신설**해 자연인 전제를 벗어난다. 이것이 3.4절의 본인인증 하드블록과 4.7절의 목적 소명 문제를 동시에 해소하는 경로다. 에이전트 계정에는 목적 소명 대신 **행위 범위(scope)와 쿼터와 감사 로그**로 통제를 대체한다.

**포털 통합을 정책으로 표준화**한다. LOCALDATA 선례를 국가데이터처의 표준 정책으로 격상하고 신규 포털 신설 요건을 강화한다.

여기에 가용성과 응답 시간을 명시한 **SLA**와 명확한 **재사용 라이선스**가 더해지면 데이터 제품화 기둥이 Level 3에 도달한다.

**불만 처리 전환율** — 제기된 문제 가운데 개별 응답으로 종결되지 않고 실제 수정으로 이어진 비율.

**마지막 지표가 특히 중요하다.** 4.9절에서 본 대로 현재는 민원 응답 완료가 성과로 집계되므로, 같은 문제가 반복 제기되어도 개선 신호로 전환되지 않는다. 이 전환율을 측정하기 시작하면 비로소 피드백 회로가 성립한다.

### 7.6 해외 참조 사례

**싱가포르**는 APEX 게이트웨이로 31개 기관, 2,400개 이상 API, 월 1억 건의 호출을 단일 진입점에서 처리하며, data.gov.sg는 인증 없이 실시간 API를 제공한다. 첫 답변까지 2천 토큰이라는 수치가 여기서 나온다. **7.2절 공용 샌드박스 설계의 원형**이다.

**미국**은 `api.data.gov`가 통합 키 하나로 수백 개 API를 포괄하고 GovInfo가 공식 MCP를 운영한다. **7.4절 신원 통합의 참조 모델**이다.

**프랑스**는 data.gouv.fr가 기계 판독 가능한 swagger.json을 제공하고 mcp.data.gouv.fr가 4만 데이터셋을 노출한다. **명세에서 MCP로 이어지는 경로**를 실제로 구현했다.

**영국**은 GDS 기술 표준을 통해 OpenAPI를 제도적으로 강제하는 방식을 보여준다.

**EU**는 data.europa.eu와 DCAT-AP로 메타데이터 상호운용성의 틀을 제공한다.

이 사례들의 공통점을 지적해 둘 필요가 있다. **어느 나라도 AI를 위한 별도의 특별한 시스템을 새로 만들지 않았다.** HTTP를 정직하게 사용하고, 명세를 기계가 읽을 수 있게 하고, 신원을 하나로 합쳤을 뿐이다. 에이전트 준비도는 **웹 표준 준수도의 다른 이름**이다.

그리고 또 하나의 공통점이 있다. **이들 중 어느 곳도 데이터를 쓰려는 이유를 묻지 않는다.** 싱가포르는 인증조차 요구하지 않고, 미국은 이메일 하나로 키를 즉시 발급한다. 접근을 통제하는 대신 쿼터로 부하를 관리하고, 오남용은 사후에 차단한다. **사전 심사에서 사후 관리로의 전환**이 이들의 공통된 설계다.

## 8. 함께 관리해야 할 위험

**측정 신뢰도의 저하**가 첫째다. "부분측정" 판정의 급증은 등급이 하락한 포털 가운데 일부가 실제 품질 저하가 아니라 관측 범위 축소의 결과일 수 있음을 뜻한다. 공식 관측 체계 구축과 자가 진단 엔드포인트가 대응책이다.

**비공식 MCP의 공급망 위험**이 둘째다. 79종의 커뮤니티 구현은 유지 주체가 불명확하며, 그 위에서 국가 데이터가 소비되고 있다. 공식 MCP의 조기 출시와 인증·등재 제도가 필요하다.

**파일럿의 함정**이 셋째다. 서울시 MCP가 민간 호스팅과 선착순 100명 규모에 머문다면 성공 사례가 아니라 "이미 하고 있다"는 알리바이로 기능한다. 종료 조건과 확산 로드맵을 사전에 명시해야 한다.

**개방과 보안의 긴장**이 넷째다. 무인증 샌드박스와 자동 승인은 남용 우려를 낳는다. 저쿼터·읽기 전용·저위험 API로 범위를 한정하고 레이트 리밋 헤더로 통제를 투명하게 노출하는 방식으로 관리한다. **다만 이 우려가 현행 목적 심사를 정당화하지는 않는다.** 목적 소명은 남용을 걸러내지 못한다. 악용할 사람은 그럴듯한 목적을 쓸 수 있고, 선의의 이용자만 절차 비용을 부담한다. **남용 통제의 올바른 지점은 신청 시점이 아니라 사용 시점이며, 수단은 심사가 아니라 쿼터와 로그와 사후 차단이다.**

**에이전트 트래픽의 비선형 증가**가 다섯째다. 접근이 쉬워지면 호출량은 선형이 아니라 비선형으로 늘어난다. 쿼터 설계와 캐싱, `ETag`와 `If-Modified-Since`를 활용한 조건부 요청 지원이 7.2절의 개방 조치와 **반드시 함께 가야 한다.** 개방만 먼저 하고 부하 관리를 나중에 하면 첫 트래픽 급증에서 서비스가 무너진다.

**권한 조정에 대한 저항**이 여섯째다. 5.2절에서 본 대로 승인 절차 간소화는 특정 조직의 권한을 직접 줄이므로 다른 기술 항목과 저항의 성격이 다르다. 상위 권한의 명시적 지시와 면책 규정 없이 이 항목을 추진하면 로드맵 전체가 여기서 멈춘다.

**AI 특별 대응이라는 오해**가 일곱째다. 이 작업이 AI 전용 사업으로 프레이밍되면 예산 경쟁에서 불리해진다. 웹 표준 정상화로 규정하는 편이 정확하기도 하고 유리하기도 하다.

## 9. 결론

### 9.1 문제의 재정의

한국 공공데이터의 문제는 양이 아니라 인터페이스와 접근권에 있다. OECD 개방 지수 1위와 기술 품질 2.0점, 그리고 아홉 개국 중 9위라는 세 사실의 공존이 이를 증명한다.

그리고 에이전트의 시대에 이 격차의 **성격**이 달라진다. 같은 결함이 사람 이용자에게는 불편이지만 에이전트에게는 사용 불가가 되기 때문이다.

오류에도 HTTP 200을 반환하는 것을 사람은 화면을 보고 판단하지만, 에이전트는 성공으로 오인하고 오염된 결과를 전파한다. HWP 명세를 사람은 열어서 읽지만 에이전트는 파싱조차 하지 못한다. 130개의 계정을 사람은 필요한 것만 골라 만들지만, 에이전트는 본인인증에서 원천 차단된다. 465킬로바이트의 HTML을 사람은 스크롤해서 넘기지만, 에이전트는 132,810 토큰을 소비하고 그중 96.8퍼센트를 버린다. 그리고 활용 목적을 사람은 그럴듯하게 지어낼 수 있지만, **에이전트는 지어낼 목적을 갖고 있지 않다.**

**불편의 축적이 임계점을 넘으면 불가능이 된다.** 그 임계점을 넘긴 것이 에이전트다.

### 9.2 기술 문제 아래에 제도 인식이 있다

이 보고서가 앞선 논의에 더한 층위는 4장이다. 측정 가능한 결함 아래에 측정되지 않는 전제가 있다.

**데이터를 여는 것이 시혜라고 전제하면 접근 절차는 정교해지고 데이터 품질은 방치된다.** 조직의 관심이 "누구에게 줄 것인가"에 머물고 "어떻게 쓸 수 있게 할 것인가"로 가지 않기 때문이다. 심사 항목이 늘어나는 동안 API 문서는 HWP로 남아 있고, 승인 프로세스가 다단계인 동안 오류 응답은 HTTP 200으로 남아 있다. 이것은 우연한 병존이 아니라 **같은 인식의 두 얼굴**이다.

그런데 공공데이터법의 구조는 이와 다르다. 제1조는 목적을 **국민의 이용권 보장**으로 정하고, 제3조는 **평등의 원칙**과 **이용저해행위 금지**와 **영리적 이용 제한 금지**를 기본원칙으로 선언하며, 제17조는 제공을 **의무**로 규정하고 예외를 두 가지로 한정한다. 제26조는 공표된 데이터를 그냥 제공받을 수 있게 하고, 제28조는 제공중단 사유를 네 가지로 열거하며, 제31조는 거부에 대한 구제 수단을 마련해 두었다.

**즉 법은 이미 제품형 운영을 전제하고 있다.** 현장의 정보공개형·시혜형 운영은 법이 요구한 바가 아니라 익숙한 업무 문법이 낯선 대상에 적용된 결과에 가깝다.

이 진단이 실무적으로 중요한 이유가 있다. **법 개정 없이도 상당 부분을 되돌릴 수 있다는 뜻이기 때문이다.** 7.2절에 정리한 제도 조치들 — 공표 목록에 대한 개별 심사 폐지, 목적 기재의 임의 항목 전환, 거부 통지 양식 표준화, 분쟁조정 절차 안내 — 은 모두 운영 지침과 표준 양식의 변경 범위에 있다.

### 9.3 세 개의 지렛대

**가장 효과가 큰 즉시 조치는 공용 샌드박스 키다.** 법 개정도, 215개 기관의 동원도, 신규 시스템 구축도 필요 없는 게이트웨이 설정 변경 하나가 절차의 열 단계를 두 단계로, 토큰 비용을 수만 단위에서 수천 단위로 줄인다. 동시에 이것은 "쓰기 전에 목적을 밝혀야 한다"는 전제를 깨는 첫 구멍이기도 하다. **탐색이 가능해야 진짜 목적이 생긴다.**

**가장 파급력이 큰 자산은 OpenAPI 명세다.** 다른 항목들이 고쳐야 할 결함이라면 명세는 하나를 만들면 MCP와 SDK와 함수 호출 스키마가 자동으로 생성되는 시드다. 215개 중 1개, 0.5퍼센트라는 수치가 MCP 커버리지 5.6퍼센트를 통째로 설명한다.

**가장 근본적인 개입은 평가와 시상 기준의 전환이다.** 개방 건수를 세는 동안 기관의 합리적 선택은 언제나 데이터를 하나 더 여는 것이지 이미 연 API를 고치는 것이 아니다. 게다가 통제를 완화하는 조치는 평가되지 않을 뿐 아니라 사고 시 책임 소재가 된다. **개선의 기대 편익이 0이고 기대 비용이 양수인 구조에서 아무도 개선하지 않는 것은 태만이 아니라 합리적 판단이다.**

이 구조가 얼마나 비싼지는 이미 감사로 확인되었다. 감사원의 인공지능 산업 육성 실태 감사는 2017년 이후 1조 6,328억 원이 투입된 학습용 데이터 908종 구축 과정에서, 기관들이 기존 데이터의 활용 가능성을 검토하지 않고 개별적으로 사업을 추진해 유사 데이터를 중복 구축한 사례가 다수 적발되었다고 밝혔다. **구축 건수를 세는 평가 체계는 중복을 낭비가 아니라 실적으로 계산한다.** 이 계산을 바꾸지 않으면 어떤 로드맵도 실행되지 않는다.

### 9.4 마지막 관찰

두 조사를 겹쳐 읽을 때 가장 무겁게 다가오는 것은 개별 수치가 아니라 분포였다. 게이트웨이 한 곳에서 처리할 수 있는 항목은 4~8퍼센트가 개선되었고, 215개 기관이 각자 해야 하는 항목은 정확히 0퍼센트가 개선되었다.

그리고 같은 넉 달 동안, 아무도 지시하지 않은 커뮤니티는 MCP 서버를 여섯 종에서 일흔아홉 종으로 늘렸다. 130개의 계정을 만들고, API마다 키를 신청하고, 목적을 지어내 심사를 통과한 사람들이 만든 것이다.

**수요는 이미 증명되었다. 증명한 쪽은 정부가 아니라 이용자다.**

기술 사양은 전부 알려져 있다. RFC 9457도, OpenAPI 3.x도, OAuth 2.0도, MCP도 새로 발명할 것이 없다. 법적 근거도 이미 있다. 공공데이터법은 이용권 보장을 목적으로 명시하고, 제공을 의무로 규정하며, 이용저해행위를 금지하고 있다. 실행 권한을 가진 주체와 그 권한이 작동한다는 선례도 확보되었다.

**남은 것은 하나뿐이다. 아무도 하지 않으면 아무 일도 일어나지 않는다.**

## 부록 D — 인용된 기술 표준

HTTP 의미론은 RFC 9110이 규정하며 `Retry-After`도 여기에 포함된다. 오류 표현의 표준은 RFC 9457 Problem Details이고 이전의 RFC 7807을 대체한다. 레이트 리밋 헤더(`RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`)는 IETF의 `draft-ietf-httpapi-ratelimit-headers`로 논의 중인 **초안 단계**임에 유의해야 한다. API 폐기 예고는 RFC 9745의 `Deprecation`과 RFC 8594의 `Sunset` 헤더로 표현한다.

명세 기술에는 OpenAPI 3.x와 JSON Schema를, 인증에는 RFC 6749의 OAuth 2.0과 OpenID Connect를 사용한다. 데이터 카탈로그 메타데이터 표준은 DCAT-AP이며, 날짜와 시각은 ISO 8601을 따른다. 도구 연결의 사실상 표준은 MCP(Model Context Protocol)다. `llms.txt`는 커뮤니티 관행이며 **아직 공식 표준이 아니다.**

## 부록 E — 출처와 한계

본문의 정량 수치는 모두 K-GAPI(2026-04-02 기준)와 GAPI2 Δ(2026-08-04 실측)에서 인용했고, 법 조문은 법제처 국가법령정보센터에서 확인했다.

두 조사와 하위 분석 페이지 사이에 일부 수치가 다르게 표기된다. 포털 수는 199개와 215개로, 필요 계정 수는 130개와 131개로, 등급 상승 포털은 17개와 18개로, CORS 개선은 13개와 14개로 각각 다르게 나타난다. 이는 조사 시점의 차이와 집계 모집단의 차이 — 전체 215개인지 재측정이 가능했던 172개인지 — 에서 비롯된 것으로 보이며, 본문에서는 맥락에 따라 범위로 표기하고 모집단을 문장 안에 명시했다.

GAPI2 스스로가 "부분측정" 판정의 급증을 경고하고 있으므로, 등급이 하락한 것으로 나타난 포털 가운데 일부는 실제 품질 저하가 아니라 외부에서 측정할 수 있는 범위가 좁아진 결과일 수 있다.

**4장의 이용자 경험 서술은 현장에서 반복적으로 제기되어 온 증언을 정리한 것이며, 표본 조사나 설문에 기반한 통계가 아니다. 4.4절의 세 가지 운영 문화 유형 분류 역시 필자의 분석 도구이지 기관별 실태 조사 결과가 아니다. 다만 4.2절과 4.3절은 공개된 개발 기록과 공식 평가·감사 자료에 근거하며 각 항목에 출처를 명시했다. 이 부분을 정책 근거로 쓰려면 별도의 실태 조사가 필요하다.** 구체적으로는 215개 포털을 대상으로 활용 목적 기재 요구 여부, 즉시 발급 여부, 승인 소요 시간 분포, 거부 사유의 법정 사유 부합률, 분쟁조정 안내 포함률을 전수 조사하는 것이 7.5절 지표의 기준선을 확보하는 방법이다.

마지막으로 출처의 경계를 밝혀 둔다. **원자료가 제공한 것은 실측 데이터, 7개 기둥 성숙도 루브릭, Agent Access Layer 6층 구조, 이용 절차 분석, 개선 기간 제안이다. 4장의 운영 문화 분석과 법 조문 대조, 5장의 구조적 원인 분석, 7장의 제도 처방과 추가 지표 제안, 8장의 위험 분석은 필자의 정리이며 원자료의 주장이 아니다.**
