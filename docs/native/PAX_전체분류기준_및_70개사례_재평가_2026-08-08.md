## 2. 전체 분류체계

### 2.1 AX 단계: 현재 실현된 업무 변화

#### AI-Ready

데이터·권한·책임·기준선 중 하나 이상을 실제 AI 업무시험에 사용할 수 있는 상태로 만든 단계다. 네 요소를 모두 충족할 필요는 없다.

- 데이터·문서·업무지식 구조화 및 표준화
- 접근권한, 개인정보 보호, 로컬·내부망 처리조건 마련
- 결과 검토·승인·오류 대응 책임의 정의
- 기존 시간·비용·품질 또는 AI 평가 기준선 마련
- API·MCP·RAG·공통 AI 플랫폼·교육·실험환경 제공
- AI 또는 바이브 코딩을 이용해 위 준비요소를 구현한 경우

단순히 AI로 코딩했다는 사실만으로는 부족하다. 결과물이 데이터·권한·책임·기준선 또는 안전한 시험조건에 실질적으로 기여해야 한다.

#### AI-Enabled

기존 업무의 일부에서 AI가 검색·요약·분류·번역·초안·추천·분석 등 **검증 가능한 결과**를 만들고 사람이 확인하는 단계다. 기능 탑재가 아니라 실제 업무 산출물이 관건이다.

#### AI-First

AI를 전제로 업무 시작점, 처리경로와 사람·AI의 역할을 다시 설계한 단계다. 다음 관문을 모두 확인해야 한다.

- 저위험·반복 업무의 자동처리
- 불확실·민감·고위험 업무의 숙련자 이관
- 승인·거부·오류·이의제기·롤백 등 예외처리
- 사람의 수정과 운영결과를 평가 데이터로 수집
- 반복되는 예외를 정책·제품·업무절차 개선에 반영

#### AI-Native

AI가 서비스의 핵심 가치를 생산하고, 사용결과가 평가와 개선으로 돌아오며, 장애·가격·품질변동에도 핵심 서비스가 유지되는 단계다. `핵심 가치 결합 + C5 학습구조 + 복원력`을 필수관문으로 적용한다.

Native 판정 시에는 `MCP tool / Task / Workflow / Service / Organization / Ecosystem` 중 적용범위를 반드시 함께 기록한다. 원자적 단위업무도 Task-native가 될 수 있지만, 이를 근거로 기관 전체를 Native라고 부르지는 않는다.

### 2.2 업무 범위 S1～S5

| 코드 | 명칭 | 판정 단위 |
|---|---|---|
| S1 | Primitive tool | 단일 조회·변환·생성·검사 기능 |
| S2 | Tool bundle | 관련된 복수 도구·데이터·기능의 묶음 |
| S3 | Workflow | 하나의 업무목표를 위한 순차·조건부 처리 |
| S4 | End-to-end service | 접수·처리·승인·통지·종료 확인까지 연결 |
| S5 | Ecosystem | 여러 기관·서비스·에이전트가 공동 목표를 수행 |

도구 수가 많다고 범위가 자동으로 커지지 않는다. 독립 조회 도구 100개는 S2일 수 있고, 적은 도구로 접수부터 통지까지 연결하면 S4가 될 수 있다.

### 2.3 업무 완결성 C0～C5

| 코드 | 명칭 | 판정 기준 |
|---|---|---|
| C0 | 기능 제공 | 도구·서비스가 존재하고 호출·사용 가능 |
| C1 | 결과 제공 | 결과를 제시하며 후속 업무는 사람이 수행 |
| C2 | 연속 처리 | 여러 단계를 연결하지만 주요 판단·완료는 사람이 담당 |
| C3 | 운영 폐쇄루프 | 입력→처리→검증→완료 및 종료상태 확인 |
| C4 | 예외 포함 완결 | 오류·불확실성·승인·이의제기·이관·롤백 포함 |
| C5 | 적응형 완결 | 평가·학습·재검증·대체경로·장애복원 포함 |

기술적 완성도와 업무 완결성은 분리한다. 인증·감사·고가용성을 갖춘 공식 MCP도 실제 활용이 없다면 `AI-Ready / C0`일 수 있다.

### 2.4 MCP 파급력 M1～M5

M 등급은 MCP 사례에만 적용하며, 비-MCP 사례는 `해당 없음`으로 기록한다.

| 코드 | 명칭 | 판정 기준 |
|---|---|---|
| M1 | 제한적 | 개인·단일 도구·제한 사용자 중심 |
| M2 | 재사용형 | 공개 MCP 또는 복수 사용자·모델이 재사용 |
| M3 | 업무통합형 | 복수 MCP·API·업무시스템과 연결 |
| M4 | 생태계형 | 공식 기관 제공, 다기관·다에이전트 공동 이용 가능 |
| M5 | 핵심인프라형 | 공식 실행계층이며 SLA·책임·감사·복원력을 갖춤 |

MCP 개발·제공 자체는 원칙적으로 Ready다. MCP를 이용해 업무결과를 만들면 Enabled, MCP를 전제로 역할과 흐름을 다시 짜면 First, 핵심 가치·학습·복원력까지 결합하면 Native로 판정한다. 따라서 `AI-Ready / S2 / C0 / M4`처럼 현재 AX 단계와 파급력이 크게 다른 조합도 가능하다.

## 3. 보조 분류축

모든 사례에는 다음 필드를 함께 기록한다.

- 도입상태: Prototype / PoC / Pilot / Production / Published tool / Reported·Unknown
- 사용자 관계: G2E / G2G / G2C / G2B / G2R
- 서비스 범위: Internal / External / Hybrid
- 업무 위치: Front-office / Middle-office / Back-office / Infrastructure
- 개발·운영 주체와 개발방식
- 도구 유형과 실행범위
- MCP 역할·범위·권한, API 방향·범위·문서화
- 개방성, 소스 공개, 라이선스
- 위험도와 인간 통제
- 증거등급 E0～E5와 분류 신뢰도
- 피드백·학습 구조와 복원력

AX 단계와 도입상태는 독립적이다. `AI-Ready / Production`, `AI-Enabled / Prototype`이 모두 가능하다.

## 4. 판정 절차

1. 공개자료에서 AI의 실제 역할과 업무 산출물을 확인한다.
2. AI 활용조건만 마련했는지, 검증 가능한 결과까지 만드는지 구분한다.
3. 지원 업무범위를 S1～S5로 판정한다.
4. 시작·처리·완료·예외·학습·복원 수준을 C0～C5로 판정한다.
5. AX 단계의 필수관문을 적용한다. 총점보다 관문을 우선한다.
6. MCP 사례라면 재사용·시스템통합·기관공식성·운영책임을 M1～M5로 평가한다.
7. Native라면 적용범위를 별도로 기록한다.
8. 공개 근거가 없으면 `아니오`가 아니라 `미확인`으로 기록하고 상위단계 판정을 유보한다.
9. 신규 증거가 생기면 동일 사례를 새 버전으로 재평가한다.

## 5. 기존 판정에서 변경된 사례

| 사례 | 기존 | 재평가 | 변경 이유 |
|---|---|---|---|
| 서울시 기관 공용 AI 엔진 기반 AI 에이전트 구축 착수 | AI-First | **AI-Ready** | 공용 AI 엔진과 MCP 구조는 준비조건이지만 구축 착수 단계이며 자동처리·인간 이관·예외·평가 환류의 운영 증거가 없음 |
| 부서 수요 기반 ChatGPT 팀계정 지원 후 보안형 AI SaaS 도입 | AI-Ready | **AI-Enabled** | AI가 보고서 등 업무결과를 만들고 공무원이 검토하는 실제 이용방식이 명시됨 |
| 공무원용 로컬 AI 에이전트 워크플레이스 개발 | AI-First | **AI-Enabled** | 일정·파일·지식·문서작성·실행기록을 연결해 업무결과를 제공하지만 역할 재편과 예외·평가 폐쇄루프는 미확인 |

기존 First 2건을 낮춘 것은 에이전트의 기술적 잠재력을 부정한 것이 아니다. **First는 아키텍처의 의도보다 운영 중인 역할·경로·예외·평가 구조의 증거를 요구한다**는 새 관문을 일관되게 적용한 결과다.

## 6. MCP 사례 판독

공식 정부 MCP나 다수 공공데이터를 제공하는 MCP는 현재 활용이 C0에 머물더라도 M4까지 평가할 수 있다. 반대로 공개 MCP로 실제 법령분석을 수행한 사례는 Enabled이지만 재사용 범위가 제한적이면 M2일 수 있다.

권장 표기는 다음과 같다.

> **AI-Ready / S2 Tool bundle / C0 기능 제공 / M4 생태계형**

> **AI-Enabled / S2 Tool bundle / C2 연속 처리 / M2 재사용형**

> **AI-First / S4 End-to-end service / C4 예외 포함 완결 / M3 업무통합형**

> **AI-Native / S5 Ecosystem / C5 적응형 완결 / M5 핵심인프라형**

## 7. 해석과 개선 권고

1. **First 후보군을 별도 관리한다.** S3·C2 사례 중 역할분기, 이관, 종료확인, 평가 데이터 수집을 추가하면 First로 발전할 수 있는 사례를 추적한다.
2. **사례 등록양식에 S·C·M 근거필드를 추가한다.** 기능소개만으로는 업무범위와 완결성을 판정하기 어렵다.
3. **성과근거를 E4 이상으로 높인다.** 처리시간·오류율·수정률·이관률·사용량·비용을 기록한다.
4. **예외와 복원력을 사례 설명의 필수항목으로 만든다.** 모델·MCP·API 중단 시 폴백, 수동전환, 롤백을 확인한다.
5. **MCP 서버 수보다 전환경로를 추적한다.** `공개 → 실제 사용 → 업무결과 → 공식 편입 → 흐름 재설계 → 학습·복원`의 진행상태를 버전 관리한다.
6. **Primitive-native를 범위와 함께 표현한다.** Task-native를 기관 전체 Native와 혼동하지 않는다.

---

## 8. 최종 원칙

> **준비조건을 만들면 Ready, 검증 가능한 업무결과를 만들면 Enabled, 사람과 AI의 역할 및 흐름을 다시 짜면 First, 핵심 가치와 학습·복원 구조가 결합되면 Native로 판정한다.**

PAX에서는 등급 하나만 표시하지 않고 `AX × S × C × M`을 함께 기록해야 한다. 이 방식은 준비 자산의 잠재력을 과소평가하지 않으면서, 아직 실현되지 않은 자동화 효과를 현재 성과로 과대평가하는 문제도 막는다.
