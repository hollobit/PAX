# 공공 AX 사례 평가·분류 기준 상세 보고서

**대상:** 공공 AX 사례 아카이브(PAX)  
**기준일:** 2026-08-08  
**적용 범위:** PAX 등록 사례 63건  
**관련 자료:** [PAX 아카이브](https://hollobit.github.io/PAX/) · [PAX GitHub 저장소](https://github.com/hollobit/PAX)

## 요약

이 평가체계는 공공부문의 AI 전환 수준을 다음 네 단계로 구분한다.

> **AI-Ready는 데이터·권한·책임·기준선을 준비하는 단계이고, AI-Enabled는 기존 업무의 일부를 AI로 돕는 단계이며, AI-First는 AI를 전제로 업무 흐름과 역할을 다시 짜는 단계이다. AI-Native는 AI가 핵심 가치의 생산 방식과 지속적인 학습 구조에 결합된 단계이다.**

네 단계는 단순히 기술이 많아지는 순서가 아니다. 단계가 올라갈수록 변화의 대상이 `준비조건 → 업무 산출물 → 업무 운영모델 → 가치생산 및 학습체계`로 바뀐다.

| 단계 | 핵심 질문 | 주된 변화 대상 | 대표 산출물 |
|---|---|---|---|
| AI-Ready | AI를 활용할 수 있는 조건을 만들었는가? | 데이터·권한·책임·기준선 | 구조화 데이터, 업무지도, 안전한 실험환경, API·MCP, 교육·도구 기반 |
| AI-Enabled | 기존 업무의 일부 결과를 AI가 만들고 사람이 검증하는가? | 개별 작업·기능 | 검색, 요약, 분류, 번역, 초안, 추천, 제한적 도구호출 |
| AI-First | AI를 전제로 사람과 AI의 역할 및 업무 흐름을 재설계했는가? | 전체 워크플로와 운영 역할 | 자동처리·전문가 이관, 예외처리, 평가 데이터 수집, 다단계 실행 |
| AI-Native | AI가 핵심 가치와 학습 구조에 결합되어 있는가? | 서비스·기관의 가치생산 체계 | 지속적 평가·개선 루프, 동적 개인화·조정, 복원력 있는 핵심 서비스 |

현재 기준을 PAX 63건에 적용한 결과는 다음과 같다.

| 분류 | 사례 수 | 비율 |
|---|---:|---:|
| AI-Ready | 37 | 58.7% |
| AI-Enabled | 15 | 23.8% |
| AI-First | 2 | 3.2% |
| AI-Native | 0 | 0.0% |
| AX 단계 외 | 9 | 14.3% |
| **합계** | **63** | **100.0%** |

AI-Ready의 비중이 큰 것은 문턱을 과도하게 높이지 않았기 때문이다. 데이터·지식 구조화, 업무절차의 가시화, 개인정보 보호, 로컬 처리, 백업, 교육, API·MCP 기반처럼 향후 AI 활용에 필요한 요소 중 하나 이상을 실제 산출물로 마련하면 Ready로 인정한다. 이러한 산출물을 AI 또는 AI 바이브 코딩의 도움으로 만들었어도 Ready로 분류한다.

반면 AI-First와 AI-Native는 엄격하게 평가한다. 에이전트, MCP, RAG 또는 생성형 AI를 사용한다는 사실만으로 First나 Native가 되지 않는다. 사람과 AI의 역할 재배치, 위험에 따른 처리 경로, 예외처리, 평가 데이터 환류가 확인되어야 First로 볼 수 있으며, Native는 핵심 가치와 지속 학습 구조, 서비스 복원력까지 확인되어야 한다.

## 1. 평가체계의 목적

### 1.1 단순 사례 목록을 정책 데이터베이스로 전환

PAX에는 정부·공공기관의 공식 사업뿐 아니라 공무원 개인 개발, 커뮤니티 공개 도구, 바이브 코딩 결과물, 프로토타입, 공개 웹서비스, MCP 서버, 공공데이터 활용 서비스가 함께 등록되어 있다. 따라서 사례 수만 집계하면 공공 AX의 실제 성숙도를 파악하기 어렵다.

이 평가체계는 각 사례에 대해 다음을 구분하기 위한 것이다.

- AI 활용을 위한 준비인지, AI가 실제 업무 결과를 만드는지
- 기존 업무를 보조하는지, 업무 흐름 자체를 재설계했는지
- 시연·프로토타입인지, 실제 운영 서비스인지
- 공무원 내부용인지, 국민·기업·개발자 대상인지
- 누가 개발·소유·운영하는지
- MCP·API를 사용하거나 제공하는지
- 소스코드와 재사용 조건이 공개되어 있는지
- 공공서비스의 권리·안전·재정에 미치는 영향이 어느 정도인지
- 공개된 설명을 어느 정도 신뢰할 수 있는지

### 1.2 평가 결과의 활용

평가 결과는 다음과 같은 분석에 활용할 수 있다.

1. 공공부문 AX가 준비 단계에 머무는지, 실제 업무 재설계로 이동하는지 분석
2. 중앙부처·지자체·공공기관·공무원 개인별 혁신 방식 비교
3. 내부 업무도구와 대국민 서비스의 비중 파악
4. MCP·API·오픈소스를 통한 기관 간 재사용 가능성 평가
5. AI-First로 발전시킬 후보 사례 발굴
6. 고영향 서비스의 인간 통제·평가·감사 공백 확인
7. 홍보자료와 실제 운영성과를 구분한 증거 기반 사례 관리

## 2. 평가의 기본 원칙

### 2.1 기술명이 아니라 업무 변화로 평가

`생성형 AI`, `에이전트`, `MCP`, `RAG`, `바이브 코딩`이라는 표현은 기술 특성을 설명할 뿐 AX 수준을 자동으로 결정하지 않는다.

- 챗봇이 답변 초안을 만들면 대체로 Enabled이다.
- 에이전트가 여러 도구를 호출해도 기존 업무 흐름이 그대로라면 Enabled일 수 있다.
- MCP 서버가 공공데이터를 제공하면 Ready 기반에 해당할 수 있지만, 그 자체로 First는 아니다.
- 일반 프로그램을 AI 바이브 코딩으로 개발했다는 사실만으로 Enabled가 되지는 않는다.

핵심은 AI가 `무엇을 만들었는가`, `업무가 어떻게 달라졌는가`, `사용 결과가 어떻게 평가·개선되는가`이다.

### 2.2 기술 수준과 도입 상태를 분리

AX 단계와 도입 상태는 서로 다른 축이다.

- `AI-First / Prototype`이 가능하다.
- `AI-Enabled / Production`도 가능하다.
- `AI-Ready / Production`도 가능하다.

운영 중이라는 이유만으로 AX 수준이 높아지는 것은 아니며, 고도화된 개념 시연이라는 이유만으로 실제 성과가 입증되는 것도 아니다.

### 2.3 가장 높은 주장보다 확인 가능한 증거를 우선

사례 설명이 “혁신”, “자동화”, “에이전틱”이라고 주장하더라도 공개자료에서 업무 역할과 운영 방식이 확인되지 않으면 보수적으로 분류한다. 정보가 없을 때는 `아니오`로 단정하기보다 `미확인`으로 기록한다.

### 2.4 점수보다 단계별 관문을 우선

정량점수는 비교와 검토를 돕는 보조지표이다. 총점이 높더라도 다음 필수조건을 충족하지 않으면 상위 단계로 분류하지 않는다.

- AI-First: 업무 흐름 및 역할 재설계가 확인되어야 함
- AI-Native: 핵심 가치 결합, 실제 학습 루프, 복원력이 모두 확인되어야 함

### 2.5 공공부문에서는 자율성보다 통제가 중요

사람의 개입이 적다는 사실을 무조건 성숙도로 보지 않는다. 복지, 의료, 채용, 인허가, 법집행, 안전 등 고영향 업무에서는 적절한 인간 승인, 이의제기, 감사로그, 예외처리가 성숙도의 구성요소이다. 무통제 자율성은 고도화가 아니라 위험 신호가 될 수 있다.

## 3. AX 4단계 상세 기준

## 3.1 AI-Ready: 데이터·권한·책임·기준선을 준비한다

### 정의

AI-Ready는 기관이나 사용자가 향후 AI를 실제 업무에 적용할 수 있도록 필요한 준비요소를 마련한 단계이다. Ready의 산출물은 대규모 데이터 창고나 교육 수료증에 한정되지 않는다. 데이터·권한·책임·기준선 중 하나 이상을 실제 사용할 수 있는 형태로 구현한 결과물도 포함한다.

### Ready를 구성하는 네 요소

#### 1) 데이터

- 문서·법령·규정·업무지식을 기계가 읽을 수 있도록 구조화
- 파일을 검색·분석할 수 있도록 정제·색인
- 용어·주소·분류체계를 표준화
- API·MCP·RAG를 통해 AI가 접근할 수 있는 형태로 제공
- 데이터의 최신성·출처·버전 정보를 관리

#### 2) 권한

- AI가 접근할 수 있는 데이터와 실행할 수 있는 기능의 범위를 설정
- 공개·내부·기관 간·개인별 접근 범위를 구분
- 조회 전용과 쓰기·업무실행 권한을 분리
- 개인정보·민감정보의 외부 전송을 제한
- 인증, 직무별 권한, 승인 절차를 적용

#### 3) 책임

- AI 결과를 누가 확인하고 승인하는지 정의
- 오류·오판·정보유출 발생 시 대응 주체를 지정
- 개발자·소유기관·운영기관·서비스 제공자의 역할을 구분
- 자동 처리와 인간 판단의 경계를 명확히 함

#### 4) 기준선

- 기존 업무의 시간·비용·정확도·오류율을 측정
- AI 결과의 최소 품질과 허용오류를 설정
- 개인정보, 보안, 편향, 설명가능성의 평가기준을 마련
- 업무 절차·규칙·예외유형을 문서화 또는 시각화
- AI 적용 전후를 비교할 수 있는 기준 데이터를 확보

### 완화된 Ready 판정 원칙

네 요소를 모두 갖출 필요는 없다. 다음과 같은 준비요소 중 하나 이상이 실제 산출물로 확인되면 Ready로 인정한다.

- 데이터·문서·지식의 구조화 또는 표준화
- 업무절차·역할·규칙의 가시화
- 개인정보 마스킹, 로컬 처리, 내부망 운영
- 백업·복구 등 안전하고 복원력 있는 시험 여건
- AI 교육, 실험환경, 도구 허브
- API·MCP·RAG·공통 AI 플랫폼
- API 품질 또는 AI 적합성 기준선 측정

이러한 준비 산출물을 AI의 도움이나 AI 바이브 코딩으로 만들었다면 AI-Ready로 인정한다. 최종 결과물이 AI 기능을 직접 제공할 필요는 없다.

다만 “AI로 코딩했다”는 사실만으로 Ready가 되는 것은 아니다. AI 바이브 코딩 결과가 데이터, 권한, 책임, 기준선 또는 안전한 AI 활용환경에 실질적으로 기여해야 한다.

### Ready 판정 질문

1. 데이터·문서·업무지식이 AI가 활용하기 쉬운 형태로 정리되었는가?
2. 접근권한이나 개인정보 보호조건이 마련되었는가?
3. AI 결과를 확인·승인할 책임 주체가 정해졌는가?
4. 기존 업무 또는 AI 품질을 비교할 기준선이 마련되었는가?
5. 실제 업무 하나를 시험할 수 있는 도구·환경·인터페이스가 있는가?
6. 준비 결과물이 공개자료에서 확인되는가?

### Ready에 해당하지 않는 경우

- AI와 무관한 단순 정보 시각화
- 일반적인 원클릭 이동·편집 편의기능
- 데이터 구조화나 업무 기준선과 연결되지 않는 단순 웹사이트
- 무엇을 준비했는지 알 수 없는 바이브 코딩 시연
- 계획 또는 구호만 있고 실제 산출물이 없는 경우

## 3.2 AI-Enabled: 기존 업무의 일부를 AI로 돕는다

### 정의

AI-Enabled는 기존 업무 흐름의 일부에서 AI가 검색, 요약, 분류, 번역, 초안 작성, 추천, 분석 등의 결과를 만들고 사람이 이를 확인·검증하는 단계이다.

Enabled의 핵심은 기능의 존재가 아니라 `검증 가능한 업무 결과`이다. AI가 무엇을 출력하며, 사용자가 그 결과의 정확성과 적절성을 확인할 수 있어야 한다.

### 대표적인 업무 형태

- 내부 문서·법령·공공데이터 검색과 답변
- 보고서·공문·민원 답변 초안 작성
- 문서 요약·번역·분류
- 채용 면접 질문 생성
- 연구계획·논문 초안 지원
- 지원사업 탐색과 적합성 분류
- 안전관리 문서 작성 지원
- 제한된 범위의 도구 호출과 업무 실행

### Enabled의 특징

- 기존 업무 절차가 기본적으로 유지됨
- 사용자가 AI를 직접 호출하거나 명령함
- AI 결과를 사람이 검토·수정·승인함
- AI를 제거해도 기존 방식으로 업무 수행이 가능함
- 생산성, 시간 절감, 검색 편의가 주요 가치임
- 사람의 수정 결과가 체계적인 평가·학습 데이터로 환류되지는 않음

### Enabled 판정 질문

1. AI가 실제 업무 산출물 또는 판단자료를 만드는가?
2. 사람이 결과를 확인·수정·승인할 수 있는가?
3. AI가 담당하는 업무 범위가 명확한가?
4. AI가 실패했을 때 기존 업무방식으로 돌아갈 수 있는가?
5. 업무 흐름 전체보다 특정 작업의 효율화가 중심인가?

### Ready와 Enabled의 경계

- 법령 데이터를 MCP로 제공하기만 하면 Ready이다.
- 사용자가 MCP를 통해 법령을 검색하고 AI가 업무 답변을 만들면 Enabled이다.
- 내부 문서를 RAG로 색인하고 시험환경만 만들면 Ready이다.
- RAG 답변을 실제 보고서·민원·정책업무에 사용하고 사람이 검증하면 Enabled이다.

---

## 3.3 AI-First: AI를 전제로 업무 흐름과 역할을 다시 짠다

### 정의

AI-First는 모든 판단을 AI에 먼저 맡기는 상태가 아니다. 새로운 업무나 서비스를 설계할 때 AI의 능력과 한계를 처음부터 고려하고, 사람과 AI의 역할·처리경로·예외관리 방식을 다시 설계한 상태이다.

### 핵심 변화

Enabled에서는 AI가 기존 업무의 한 단계를 돕는다. First에서는 업무가 접수되는 순간부터 처리경로가 달라진다.

예를 들어 민원·문의 처리에서 다음 구조가 확인되어야 한다.

1. 반복적이고 피해 가능성이 낮은 건은 AI가 자동 처리
2. 불확실성·민감도·위험도가 높은 건은 숙련자에게 자동 이관
3. 사람은 모든 건을 반복 처리하기보다 예외·고위험 건에 집중
4. 사람이 수정한 결과는 평가 데이터로 축적
5. 반복되는 예외는 프롬프트·모델·규정·업무절차를 고치는 신호로 사용

### First의 필수 구성요소

- AI를 전제로 설계된 시작점과 기본 처리경로
- 사람과 AI의 명시적인 역할 분담
- 위험·불확실성에 따른 자동처리와 인간 이관 기준
- 복수 단계 또는 복수 시스템의 연결
- 실패·예외 발생 시 처리 절차
- 결과와 사람의 수정내용을 기록하는 평가 기반
- 부서 또는 기관 차원의 운영 책임

### First 판정 질문

1. AI가 없어지면 업무 흐름 자체를 다시 설계해야 하는가?
2. AI 처리와 인간 처리의 분기기준이 있는가?
3. 정상건·저위험 건과 예외·고위험 건의 경로가 다른가?
4. AI가 여러 단계나 업무시스템을 연결하는가?
5. 인간의 수정·거부·예외처리가 기록되는가?
6. 반복되는 오류가 정책·업무·제품 개선 신호로 사용되는가?

### First 후보와 확정의 구분

공개자료에서 에이전트 워크플로, 공용 AI 엔진, MCP 기반 업무연결 등이 확인되지만 실제 역할 분기와 평가 환류가 충분히 확인되지 않으면 `AI-First 잠정 후보`로 표시한다. 현재 PAX의 AI-First 2건은 이러한 잠정 후보 성격을 가진다.

---

## 3.4 AI-Native: AI가 핵심 가치와 학습 구조에 결합된다

### 정의

AI-Native는 AI가 서비스의 부가기능이 아니라 핵심 가치를 생산하는 방식에 들어가 있고, 사용 과정에서 얻은 결과와 피드백이 지속적인 평가와 개선으로 되돌아가는 상태이다.

기능을 많이 탑재했는지가 아니라 다음 순환이 실제로 작동하는지가 중요하다.

> **사용 → 결과 관찰 → 품질·위험 평가 → 사람의 수정·이의제기 반영 → 모델·데이터·정책·업무 개선 → 재검증**

### Native의 필수 관문

#### 1) 핵심 가치 결합

- AI 없이는 서비스의 핵심 가치나 운영모델을 유지하기 어려움
- AI가 개인화, 선제 대응, 예측, 자원조정 등 핵심 기능을 담당
- AI 성능이 기관의 공공가치 성과와 직접 연결됨

#### 2) 학습·개선 구조

- 실제 사용 결과와 오류·수정·이의제기가 기록됨
- 기록이 평가 데이터로 정제됨
- 평가 결과가 모델·프롬프트·지식·정책·서비스 개선에 반영됨
- 개선 후 성능과 위험을 재검증함
- 이 과정이 일회성이 아니라 운영주기로 정착됨

#### 3) 거버넌스 내장

- 책임주체, 승인권한, 감사로그, 이의제기 절차가 운영체계에 포함
- 품질·편향·보안·개인정보·안전 지표를 지속 감시
- 고위험 결정에 대한 인간 개입과 중단권한이 존재

#### 4) 복원력

Native가 될수록 AI 장애가 핵심 서비스 장애로 이어질 가능성이 커진다. 따라서 복원력은 부가사항이 아니라 필수조건이다.

- 주 모델 장애 시 대체모델 또는 폴백 경로
- 외부 API 중단 시 로컬·내부 모델 또는 수동업무 전환
- 모델 가격 급등에 대비한 비용 한도와 대체 공급자
- 품질 급락·모델 변경을 탐지하는 회귀시험
- 데이터·프롬프트·평가셋·설정의 버전 관리
- 핵심 기능의 최소 서비스 수준과 복구목표
- 공급자 종속성·클라우드 종속성 관리
- 비상 중단, 롤백, 인간 인수 절차

### Native 판정 질문

1. AI가 핵심 공공가치를 생산하는 데 필수적인가?
2. 실제 사용결과가 평가 데이터로 축적되는가?
3. 평가가 모델·데이터·정책·업무 개선으로 되돌아가는가?
4. 개선 후 재검증이 이루어지는가?
5. 공급자 장애·가격변동·품질저하에 대한 대체 경로가 있는가?
6. AI 중단 시 핵심 서비스를 유지할 수 있는가?

현재 PAX 공개자료에서는 이 네 관문을 모두 확인할 수 있는 사례가 없어 AI-Native는 0건으로 평가하였다.

## 4. 단계 외 분류

PAX에 등록되었다는 사실이 곧 AX 4단계 중 하나에 해당한다는 뜻은 아니다. 다음 사례는 `AX 단계 외`로 분리할 수 있다.

- 일반적인 정보 시각화·비교 사이트
- AI 활용조건과 연결되지 않는 단순 편의 프로그램
- 공공데이터를 보여주기만 하는 지역정보 서비스
- AI 산출물이나 AI 준비조건이 확인되지 않는 웹서비스
- AI로 개발했지만 결과물이 데이터·권한·책임·기준선에 기여하지 않는 도구

단계 외는 가치가 낮다는 뜻이 아니다. 디지털정부·공공데이터 활용 사례로는 유용할 수 있으나, AX 성숙도 통계에 포함하면 Ready 비율이 과도하게 부풀려질 수 있기 때문에 별도로 표시한다.

## 5. 도입 상태 분류

| 상태 | 판정 기준 |
|---|---|
| Concept | 아이디어·계획·정책 발표 |
| Prototype | 개인 또는 조직이 기능을 구현·시연 |
| PoC | 실제 데이터 또는 제한된 사용자를 대상으로 개념 검증 |
| Pilot | 특정 부서·기관·지역에서 제한 운영 |
| Production | 공식 업무나 공개서비스로 상시 이용 가능 |

| Published tool | 코드·실행파일·웹 도구가 공개되었으나 공식 운영 여부는 불명확 |

기술 성숙도와 도입 상태는 조합해서 표시한다.

> 예: `AI-Enabled / Production`, `AI-First 후보 / Prototype`, `AI-Ready / Published tool`

## 7. 개발주체·도구·연계·개방성 분류

### 7.1 개발·운영 역할

`누가 개발했는가`는 하나의 필드로 처리하지 않는다.

- Initiator: 사업 제안·추진 주체
- Owner: 소유 및 최종 책임기관
- Funder: 예산 부담기관
- Developer: 실제 개발자·개발조직
- Operator: 운영·유지관리 주체
- Provider: 모델·클라우드·API 제공자
- Contributor: 데이터·코드·연구 기여자

개발방식은 자체개발, 공무원 개인개발, 외주·용역, 민관협력, 산학연 공동개발, 상용제품 도입, 오픈소스 개작 등으로 분류한다.

### 7.2 도구 유형

- Desktop/local app
- Web service/platform
- Chatbot/copilot
- Agent/agent skill
- Multi-agent
- Workflow/RPA
- Search/RAG
- Dashboard/visualization
- API service
- MCP server/client/gateway
- Data/AI platform
- Library/SDK/plugin

### 7.3 MCP

MCP는 사용 여부뿐 아니라 역할과 권한을 기록한다.

| 역할 | 의미 |
|---|---|
| Client | 외부 MCP 서버 호출 |
| Server | 데이터·기능을 MCP 도구로 제공 |
| Client+Server | 양방향 활용 |
| Gateway/Host | 여러 MCP 서버를 연결·통제 |
| Planned | 도입 예정 |
| Unknown/None | 공개자료로 확인되지 않음 |

추가로 공개/내부, 조회 전용/쓰기·실행, 인증, 직무권한, 감사로그, 인간승인 여부를 기록한다.

### 7.4 API

- Consumer: 외부 API 사용
- Provider: 자체 기능·데이터를 API로 제공
- Both: 양방향
- Unknown/None: 미확인

공개범위, 인증, 쓰기권한, 문서화, OpenAPI 명세, 운영상태를 함께 관리한다.

### 7.5 개방성

| 등급 | 재사용 수준 |
|---|---|
| O0 | 소개만 확인 |
| O1 | 서비스 화면 이용 가능 |
| O2 | 실행파일·프롬프트·자료 공개 |
| O3 | 소스코드 공개 |
| O4 | API·MCP·SDK 공개 |
| O5 | 설치·배포·테스트 문서 제공 |
| O6 | 여러 기관이 공식 재사용·공동운영 |

코드가 공개되어도 라이선스가 없으면 법적 재사용 가능성이 보장되지 않으므로 `소스 공개 여부`와 `라이선스`를 분리한다.

## 8. 위험·인간 통제·증거등급

### 8.1 위험도

| 수준 | 예시 |
|---|---|
| R0 최소 | 공개정보 검색, 일반 교육, 아이디어 지원 |
| R1 낮음 | 내부 초안·요약·편집, 사람이 전면 검토 |
| R2 보통 | 민원 분류, 업무 우선순위, 법령·채용·안전 관련 추천 |
| R3 높음 | 복지·채용·인허가·의료·법집행에 실질 영향 |
| R4 중대 | 생명·신체·기본권·국가안보·대규모 재정에 직접 영향 |

### 8.2 인간 통제

| 코드 | 방식 |
|---|---|
| H1 | AI는 정보만 제공, 사람이 판단·실행 |
| H2 | 모든 AI 결과를 사람이 승인 |
| H3 | AI가 실행하고 사람이 감독·예외처리 |
| H4 | 사람은 목표·정책·권한·감사를 관리 |
| H5 | 사람의 사전승인 없이 주요 결정을 자율 실행 |

H5를 최고 성숙도로 보지 않는다. 업무위험에 적합한 통제 수준인지 평가해야 한다.

### 8.3 증거등급

| 등급 | 확인 가능한 근거 |
|---|---|
| E0 | 게시글 주장만 존재 |
| E1 | 화면·영상·코드·실행파일·서비스 확인 |
| E2 | 기관 또는 개발자의 공식 설명자료 확인 |
| E3 | 운영 URL·운영주체·운영기간 확인 |
| E4 | 이용량·시간·비용·품질 등 성과지표 확인 |
| E5 | 독립평가·감사·연구 결과 확인 |

증거가 부족하면 단계를 무조건 낮추기보다 `잠정 분류`, `미확인`, `신뢰도 낮음`으로 표시한다.

## 9. 정량점수와 단계 관문

사례 비교를 위해 다음 6개 항목을 각각 0~3점으로 평가할 수 있다.

| 평가영역 | 0점 | 1점 | 2점 | 3점 |
|---|---|---|---|---|
| AI 역할 | 없음 | 정보·생성 | 판단·부분실행 | 계획·조정 |
| 업무 재설계 | 없음 | 일부 개선 | AI 중심 재설계 | 신규 운영모델 |
| 시스템 통합 | 독립 | 단일 연계 | 복수 시스템 | 기관 간 동적 연계 |
| 운영 범위 | 실험 전 | 개인·소규모 | 기관 운영 | 범기관·대국민 |
| 인간 개입 | 전 과정 수작업 | 결과 검토 | 승인·예외 중심 | 목표·정책·감사 중심 |
| 피드백·학습 | 없음 | 로그·수정 수집 | 평가 데이터 환류 | 지속 개선·재검증 |

총점은 0~18점이지만 단계는 총점만으로 정하지 않는다.

- Ready는 데이터·권한·책임·기준선 등 준비 산출물의 존재로 판단
- Enabled는 검증 가능한 AI 업무결과가 필수
- First는 업무 흐름과 역할 재설계가 필수
- Native는 핵심 가치, 학습 루프, 거버넌스, 복원력이 모두 필수

특히 Native는 점수가 높아도 피드백·학습과 복원력 관문을 충족하지 못하면 분류하지 않는다.

---

## 10. 실제 평가 절차

### 1단계: 원자료 확인

- 제목, 요약, 태그, 기관, 게시일 확인
- 원 게시물, 서비스 URL, GitHub 저장소 확인
- 공식자료와 개인 게시물을 구분

### 2단계: AX 대상성 확인

다음 중 하나라도 확인되는지 본다.

- AI 활용 준비요소
- AI가 만든 검증 가능한 업무결과
- AI 전제 업무 재설계
- AI 기반 핵심 가치와 학습 구조

없으면 단계 외로 분류한다.

### 3단계: 4단계 잠정 판정

Ready → Enabled → First → Native의 순서로 상위 단계 관문을 확인한다. 상위 관문을 충족하지 못하면 확인 가능한 가장 높은 단계로 분류한다.

### 4단계: 도입 상태와 사용자 분류

AX 단계와 별도로 도입상태, 사용자, 서비스 방향, 업무 위치를 기록한다.

### 5단계: 개발·기술·개방성 기록

개발·운영 주체, 도구 유형, MCP·API 방향, 오픈소스, 라이선스를 기록한다.

### 6단계: 위험·통제·증거 평가

영향도, 개인정보, 자동결정, 인간승인, 감사로그, 증거등급을 평가한다.

### 7단계: 사람 검토

다음 사례는 반드시 사람이 재검토한다.

- AI-First 이상
- R3 이상 고위험 사례
- 자동 행정결정 또는 쓰기·실행 권한이 있는 사례
- 증거가 상충하는 사례
- 분류 신뢰도가 낮은 사례

### 8단계: 버전 관리

평가일, 근거 URL, 평가자, 변경 전후 단계와 변경 사유를 기록한다. 서비스가 Prototype에서 Production으로 전환되거나 피드백 구조가 새로 확인되면 재평가한다.

## 11. 경계 사례 판정 예시

### 예시 1: AI 바이브 코딩으로 서무 자동화 도구 개발

- AI가 개발을 도왔지만 완성된 프로그램은 규칙 기반일 수 있음
- 업무 양식·데이터·절차·기준선을 구조화했다면 AI-Ready
- 프로그램 자체가 AI 결과를 만들고 사람이 검증한다면 AI-Enabled
- 바이브 코딩을 했다는 이유만으로 Enabled나 First로 분류하지 않음

### 예시 2: 공공데이터 MCP 서버

- 공공데이터를 AI가 호출할 수 있게 제공: AI-Ready
- AI가 데이터를 이용해 사용자의 실제 업무 답변을 생성: AI-Enabled
- 문의 유형별 자동처리·전문가 이관까지 업무가 재설계: AI-First
- 사용결과가 지속 개선되고 핵심 서비스에 내재화되며 폴백까지 운영: AI-Native

### 예시 3: 내부 문서 RAG

- 문서 색인과 로컬 시험환경 구축: AI-Ready
- 직원이 검색·요약 결과를 검토해 업무에 사용: AI-Enabled
- AI가 문서접수부터 분류·작성·담당자 배정까지 수행하고 예외만 이관: AI-First
- 기관의 핵심 지식서비스가 사용 피드백으로 지속 개선되고 장애 시 대체경로 보유: AI-Native

### 예시 4: 실시간 인파 지도

- 공공데이터를 화면에 표시하는 일반 서비스라면 AX 단계 외
- 데이터 품질·표준·API 기준선을 만들어 AI 활용을 준비한다면 AI-Ready
- AI가 혼잡을 예측하고 사람이 결과를 검증한다면 AI-Enabled
- AI 예측에 따라 현장 인력과 교통통제를 재배치한다면 AI-First 후보
- 도시 안전의 핵심 운영체계로서 결과가 지속 학습되고 장애 복원력까지 갖추면 AI-Native 후보

## 12. 현재 PAX 평가 결과의 해석

### 12.1 Ready가 37건으로 많은 이유

현재 아카이브에는 공무원 개인·커뮤니티가 만든 데이터 정비, 문서 구조화, 업무지도, 개인정보 마스킹, 로컬 도구, API·MCP, 교육·도구 허브가 많다. 완화된 Ready 기준은 이러한 상향식 준비활동을 공공 AX의 유효한 출발점으로 인정한다.

이는 Ready를 “대규모 데이터센터·전사 거버넌스 구축 완료”로만 보는 것보다 현장의 초기 혁신을 잘 포착한다. 다만 Ready의 폭이 넓은 만큼 상세 필드에서 어떤 준비요소를 갖췄는지 표시하는 것이 중요하다.

### 12.2 Enabled는 실질적 업무보조 사례

15건은 AI가 검색·요약·초안·번역·연구지원·민원작성·지원사업 탐색 등 검증 가능한 결과를 만든다. 대부분 사용자가 AI를 호출하고 결과를 확인하는 방식이므로 Enabled에 해당한다.

### 12.3 First는 아직 잠정 후보

기관 공용 AI 엔진과 공무원용 로컬 AI 에이전트 워크플레이스는 여러 기능을 연결하고 AI 중심 업무환경을 지향하므로 First 후보로 평가하였다. 그러나 위험에 따른 자동처리·전문가 이관, 수정 데이터 환류, 예외정책 개선이 실제 운영되는지는 추가 확인이 필요하다.

### 12.4 Native가 없는 이유

현재 공개자료에서는 다음을 동시에 확인하기 어렵다.

- AI가 핵심 공공가치 생산에 필수적임
- 실제 사용결과가 평가 데이터로 축적됨
- 평가가 모델·데이터·정책·업무 개선으로 환류됨
- 개선 후 재검증이 반복됨
- 공급자 장애·가격·품질변동에 대한 복원력이 있음

따라서 Native 0건은 공공 AX가 실패했다는 의미가 아니라, 아카이브가 아직 초기·상향식 사례 중심이며 운영학습과 복원력에 관한 증거가 부족하다는 의미이다.

## 13. 향후 개선 권고

### 13.1 Ready 세부요소를 배지로 표시

Ready 사례에는 다음 배지를 복수로 부여하는 것이 좋다.

- `Data-ready`
- `Access-ready`
- `Responsibility-ready`
- `Baseline-ready`
- `Security-ready`
- `Resilience-ready`
- `Skill-ready`
- `Integration-ready`

이렇게 하면 Ready 37건이 모두 같은 준비상태라는 오해를 줄일 수 있다.

### 13.2 First와 Native에 필수 증거 체크리스트 적용

First 후보에는 다음 자료를 추가 수집한다.

- 기존·변경 업무 흐름도
- 사람과 AI의 역할표
- 자동처리·이관 기준
- 예외·오류 처리절차
- 수정·거부 로그
- 운영성과

Native 후보에는 다음 자료를 추가한다.

- 평가·개선 주기
- 피드백 데이터 흐름
- 모델·프롬프트·정책 변경 이력
- 회귀시험 결과
- 대체모델·폴백 구조
- 장애훈련·복구목표

### 13.3 자동분류와 사람검토 결합

AI가 제목·요약·원문에서 1차 분류와 근거문장을 생성하되 다음 규칙을 적용한다.

1. 공개자료에 없는 내용은 추정하지 않고 `Unknown` 처리
2. AI-First 이상과 고위험 사례는 사람 승인 필수
3. 기술명만으로 상위 단계 부여 금지
4. 분류 근거문장을 사례별로 저장
5. 평가 버전과 변경이력을 유지

### 13.4 카드 표시 권고

사례 카드 전면에는 다음 정보만 간결하게 표시한다.

> **AI-Enabled · Production · 내부업무 · 공무원용**  
> **공무원 개인개발 · 로컬 앱/RAG · MCP 없음 · 코드 공개**  
> **위험 R1 · 인간검토 H2 · 증거 E1**

상세 화면에서는 준비요소, 개발·운영주체, MCP·API, 위험·통제, 피드백·복원력, 평가근거를 제공한다.

## 14. 결론

이 평가체계에서 Ready는 넓고 실용적인 출발점이다. 데이터·권한·책임·기준선을 모두 완비해야 하는 단계가 아니라, 향후 AI 활용에 필요한 준비요소 중 하나 이상을 실제 산출물로 만든 상태이다. AI나 AI 바이브 코딩을 활용해 데이터 정비, 업무절차 가시화, 개인정보 보호, 기준선 마련을 수행한 경우도 포함한다.

Enabled부터는 AI가 실제 업무결과를 만들고 사람이 검증해야 한다. First는 기능의 수가 아니라 AI를 전제로 한 역할·흐름·예외관리의 재설계로 판단한다. Native는 여기에 핵심 가치 생산, 지속 학습, 거버넌스와 복원력이 결합된 상태이다.

따라서 PAX의 AX 수준은 다음 문장으로 요약할 수 있다.

> **현재 공공 AX는 다양한 Ready 기반과 검증 가능한 Enabled 도구가 빠르게 늘어나는 단계이며, AI-First는 초기 후보가 나타났지만 AI-Native를 입증할 학습·운영·복원력 구조는 아직 공개적으로 확인되지 않는다.**

이 체계를 지속 적용하면 PAX는 단순 사례 모음에서 벗어나 공공부문의 AX 전환 경로, 확산 조건, 정책 공백과 재사용 가능성을 분석하는 증거 기반 정책 데이터베이스로 발전할 수 있다.
